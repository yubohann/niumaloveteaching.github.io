第 083 章：多智能体SAC：混合任务

把 4 个 SAC 智能体分成两队丢进同一片道具场：队内共享奖励（合作）、两队争抢同一批道具（竞争），对比"各练各的"与"评论家看队友"两种模式下净胜分、场均得分与分工行为的差异。

  • 主题：多智能体机制 / 混合合作-竞争与 CTDE 最小实现
  • 关键公式：yi = ri + γ(1−d)·minkQktarget(o′i, a′i, o′mate, a′mate) − α·logπi
  • 预计学时：55 分钟
  • 前置章节：第 082 章

学习目标

  • 理解集中训练分散执行（Centralized Training with Decentralized Execution, CTDE）在"混合合作-竞争"结构中的意义：评论家可以用队友信息，策略仍只依赖本地观测。
  • 读懂一个混合动机环境的设计：队内奖励共享产生合作压力，跨队争抢同一批道具产生竞争压力。
  • 掌握两种评论家输入模式（indep 与 ctde）的实现差别，并能用净胜分、场均得分、撞目标率三个指标对比。
  • 掌握"下一状态的队友动作"在回放缓冲中的回填技巧，以及回合边界必须断开的原因。
  • 解释为什么 CTDE 的收益常常表现在队友分工上（撞目标率下降），单体动作的"聪明程度"未必可见。

背景与动机

真实的多智能体系统很少是"纯合作"或"纯竞争"：公司里同一部门的同事要合作，但部门之间在争预算；游戏里队友共享胜负，对面的队伍在研究怎么克制你。这种混合合作-竞争（mixed cooperative-competitive）结构让价值估计更难：奖励既有"队内任何一人得分都算我得分"的公共品成分，又有"对手得分等于我损失"的零和成分。

第 082 章的对手建模处理"对手在干什么"；本章把镜头转向另一半，队友。既然训练时队友的观测和动作都能拿到，就让每个智能体的评论家"看着队友"来评估自己的动作，这就是 CTDE 的做法。它与独立训练（indep）的差别有多大？本章用 2v2 道具争抢环境给出量化答案：关键观测点是撞目标率，两个队友各追各的"最近道具"时极易撞车，而 CTDE 评论家能看到队友动作，策略有动力学会错峰。

核心原理

1. 混合任务的回报结构

设 T(i) 为智能体 i 的队号。捡到一个道具的时刻，该队所有成员的奖励都加 1：

ri = 𝟙[道具被 i 所在队捡到] − cstep − ccrowd · 𝟙[贴住队友]

其中 cstep=0.02 是每步时间成本（催促智能体别磨蹭），ccrowd=0.05 是队友靠太近的挤压惩罚（迫使两人分开）。队内是公共品博弈：即使你站着不动，队友捡到道具你也加分，这带来搭便车的诱惑；队间是零和结构：道具被对面抢走就等于自己少一分。混合结构恰好同时检验"合作能否涌现"与"竞争是否有效"。

2. CTDE 评论家的输入

分散执行要求策略只用本地观测：πi(ai|oi)。但训练时的评论家可以使用更多信息，因为它只存在于训练阶段、部署时被丢弃。本章采用最小版本，评论家只看"自己 + 队友"：

indep : Qi( oi, ai )
ctde  : Qi( oi, ai, omate, amate )

多出的两项让评论家能区分"我自己很努力但和队友撞了车"与"队友配合我完成夹击"这两种从本地观测看起来差不多、但价值完全不同的情形。这也是多智能体信用分配的雏形：评论家以队友为条件，把一部分功劳/责任自然归因出去。

3. Bellman 目标里的队友动作

CTDE 的灵魂在目标值的构造上。每个智能体 i 的软 Bellman 目标为：

yi = ri + γ(1−d) · [ mink=1,2 Qktarget(o′i, a′i, o′mate, a′mate) − α·logπi(a′i|o′i) ]

符号逐一对照：γ 是折扣因子、d 是真终止标志、mink 取双 Q 的较小值抑制过估计、α 是自动温度、a′i 是策略对下一观测重采样得到的动作。注意 a′mate 是队友在下一时刻实际采取的动作，采样时并不知道未来，所以要等下一步队友动作确定后再"回填"给上一条转移（代码里的 patch_next_mate_act）。回合一旦结束，回填链必须断开，否则会把新回合的动作塞给旧回合的边界转移，污染 bootstrap。

4. 三个评价指标

净胜分衡量对抗表现；场均得分衡量绝对效率；撞目标率衡量分工，每步检查同队两人最近的道具是否为同一个，若长期接近 1，说明两人在浪费运力。分工是合作的直接证据，也是 CTDE 最该改善的量。三者缺一不可：动态博弈里净胜分围绕 0 不代表没学会，可能只是双方同步变强。

实现思路与设计

模块划分

数据流

每个联合步的顺序很有讲究：先选动作 → 回填上一条转移的 next_mate_act → 环境步进 → 各智能体按"队友视角"存新转移 → 每 2 步各做一次 SAC 更新 → done 时清空回填链并重置。四个智能体各自维护缓冲，同一批联合经验被四个视角分别消费：每个智能体关心的是"我的队友"（0 号看 1 号，1 号看 0 号，2、3 号同理），所以 0/1 号训练数据里队友与对手的角色恰好互换。

与前一章的差异

第 082 章在评论家输入中加对手的预测动作（pred/true 对照 off）；本章把对象换成队友，而且不是预测、直接用真实动作，因为队友动作在训练期完全可见。另一个差异在奖励结构：082 是纯零和，本章是"队内公共品 + 队间零和"的混合结构，因此评估指标也从单一贴获率扩展到三个维度。

为什么撞目标率可以作为合作指标

道具重生是随机的，两个队友如果各自朝"离自己最近的道具"移动，很容易同时盯上同一个，在观测里两人看到的是两个不同的最近道具相对坐标，但在空间中可能指向同一处。CTDE 评论家能看到队友动作，因此策略有动力学会"错峰"：一个追近处的、一个守远处的，撞目标率随之下降。这是"合作"在指标上的可观测痕迹。

关键代码与解读

片段 1：共享奖励与道具重生，合作信号的全部来源

rewards = np.full(4, -0.02, dtype=np.float32)   # 每步时间成本：催促智能体别磨蹭
collected_by_team = [0, 0]
for i in range(4):
    k, d = self._nearest_item(self.pos[i])
    if d <= self.pickup_radius:                  # 进入捡取半径判定成功
        team = self.teams[i]
        self.score[team] += 1.0
        collected_by_team[team] += 1
        rewards[i] += 1.0                        # 捡到者拿全额
        rewards[self.teammates[i]] += 1.0        # 队内共享：队友同样 +1，这行是合作的来源
        # 道具换位重生：保持场上道具数量恒定，避免"捡完就没事干"
        self.items[k] = self.rng.uniform(-0.7, 0.7, size=2).astype(np.float32)
# 队友挤在一起的轻微惩罚：迫使队友错开分工，减少粘连
for i in range(4):
    if np.linalg.norm(self.pos[i] - self.pos[self.teammates[i]]) < 0.08:
        rewards[i] -= 0.05

解读：奖励设计是本章的"剧情"所在。（1）rewards[self.teammates[i]] += 1.0 一行制造了公共品：队友捡到等于我得分，于是团队总奖励在"两人分开跑"时增长最快，这是合作压力。（2）道具换位重生让一局 100 步始终有 2 个可抢目标，保证竞争的持续性；若道具不重生，后期双方都无目标可抢，学习信号会枯竭。（3）挤压惩罚 0.05 虽小，但它是逐帧累积的，等价于告诉策略"贴在队友身上没有好果子吃"，与共享奖励形成微妙的拉锯：既要靠近协作，又不能妨碍对方。（4）注意这段没有"终止"条件，回合只在 100 步上限被截断，所以后面所有 done 都来自 truncated，入缓冲时仍然只把真终止（本章没有）写进 done，保持接口一致性。

片段 2：队友动作的回填与回合边界断开

def patch_next_mate_act(self, mate_act):
    """把本步队友动作写入上一条转移的 next_mate_act（同一回合内才有效）。"""
    if self.pending_idx is not None:
        self.buffer[self.pending_idx]["next_mate_act"] = mate_act

def clear_pending(self):
    """回合结束（含时间截断）时调用：断开跨回合的动作回填链。"""
    self.pending_idx = None

def store(self, obs, act, rew, next_obs, terminated,
          mate_obs, mate_act, next_mate_obs, next_mate_act):
    """存一条转移；调用前应先调用 patch_next_mate_act 回填上一条。"""
    entry = {
        "obs": obs, "act": act, "rew": rew, "next_obs": next_obs,
        "done": float(terminated),               # 只记真终止；截断回合保留 bootstrap
        "mate_obs": mate_obs, "mate_act": mate_act,
        "next_mate_obs": next_mate_obs, "next_mate_act": next_mate_act,
    }
    self.buffer.append(entry)
    if len(self.buffer) > self.args.buffer_size:
        del self.buffer[: len(self.buffer) // 2]
        self.pending_idx = None
    self.pending_idx = None if terminated else len(self.buffer) - 1

解读：与 082 章 pending_idx 同款机制的"跨智能体移植"。（1）调用顺序是硬约束：必须"先 patch、后 store"，patch 写的是上一条（pending 指向它），store 之后 pending 才挪到新条目。顺序颠倒会让队友的下一动作错位一步，Bellman 目标系统性偏差。（2）clear_pending 在主循环里对 done 的回合调用（本章 done 来自时间截断）；如果漏掉，新回合第一步的队友动作会被写进上一回合末尾的样本，把两条轨迹缝在一起。（3）与 082 相比，本章把 pending 维护拆成三个小函数，是因为主循环需要"步进前 patch、回合末 clear"两个不同的调用点，拆开后每个调用点的语义一目了然。

片段 3：评论家输入的 indep / ctde 开关

# __init__ 里按模式计算评论家输入维度：ctde 额外装入队友的观测+动作
extra = (env.obs_dim + env.act_dim) if args.mode == "ctde" else 0
critic_in = env.obs_dim + env.act_dim + extra     # 15+2+17=34 或 15+2=17

def _q_input(self, obs, act, mate_obs, mate_act):
    if self.args.mode == "ctde":
        return torch.cat([obs, act, mate_obs, mate_act], dim=-1)
    return torch.cat([obs, act], dim=-1)          # 基线：评论家对队友一无所知

解读：一个开关切换两种实验条件，训练主体完全共享。（1）维度计算发生在构造期，网络结构随之确定，所以对照实验不掺入结构差异。（2）注意 mate_obs 在 indep 模式下也照常存进缓冲，数据完全一样，只是评论家不看；这样"换模式重训"不需要改环境与采样逻辑。（3）策略网络（Actor）两种模式完全相同，输入都只含本地观测，集中信息只进评论家，这是 CTDE 的定义；若把 mate_obs 拼进 Actor，执行期就必须能拿到队友观测（需要通信），那就超出了本章的设定，属于第 079 章通信一章讨论的主题。

片段 4：主循环里的调用顺序

# 1) 先回填"上一状态的下一队友动作"（必须发生在环境步进、存新样本之前）
if step > args.warmup:
    for i in range(4):
        agents[i].patch_next_mate_act(actions[env.teammates[i]])

next_obs, rew, terminated, truncated, info = env.step(actions)
done = terminated or truncated

# 2) 各智能体存转移；teammate 视角随智能体不同（0 看 1、1 看 0）
if step > args.warmup:
    for i in range(4):
        j = env.teammates[i]
        agents[i].store(obs[i], actions[i], rew[i], next_obs[i],
                        float(terminated), obs[j], actions[j], next_obs[j],
                        None)                # next_mate_act 留待下一步回填
        if done:
            agents[i].clear_pending()        # 回合边界：断开回填链

解读：这十几行是"时间一致性"的完整拼图。（1）patch 放在最前：此刻 actions 已经算好但环境还没步进，上一条转移的 pending 仍有效，队友在下一状态将要执行的动作正是 actions[env.teammates[i]]。（2）store 时 next_mate_act 先填 None，占位等待下一步补上；传 None 作哨兵值，sample_batch 才能识别"还没回填的边界样本"并零填充，避免脏数据。（3）if done: clear_pending() 紧跟 store 之后：先正常记录本步，再切断跨回合的链条。（4）注意 patch 只对 step > warmup 生效，预热期的随机动作不经过智能体缓冲，自然也不回填。

训练日志每 2500 步打印两队近 20 回合均分与撞目标率。预期：两队得分都随训练上升（双方同步变强），ctde 模式撞目标率从 0.6 附近降到 0.3～0.4，indep 下降更慢或停在 0.5 左右；净胜分围绕 0 波动属正常。以实跑为准，对比时固定 --seed 并至少换 3 个种子看趋势。

常见坑

  • patch 和 store 顺序颠倒：因果上"patch 写的是上一条"，必须在新样本入缓冲之前调用。顺序颠倒后队友的下一动作整体错位一步，症状是 bug 不报错但 CTDE 增益消失，先检查主循环里两行的相对位置。
  • 队友动作回填跨越回合边界：忘记在 done 时调用 clear_pending()，新回合第一步的动作会污染上回合末尾的 Bellman 目标。这类污染只在回合边界出现，日志上看不出，却会系统性地抬高边界样本的目标值。
  • 把共享奖励发漏了：rewards[self.teammates[i]] += 1.0 是合作信号的全部来源；只给捡到者发奖励，本章就退化成两个各自为战的单智能体任务，CTDE 也失去对比意义。
  • 观测里缺少比分差：没有相对比分，智能体无法在"落后"时调整风险偏好，日志上会看到后期两队得分不再上升，补上比分差维度后策略才有"追赶/保分"行为。
  • 只报净胜分：动态博弈里净胜分接近 0 不代表双方没学会；必须同时看场均得分和撞目标率，否则会把"双方都变强"误判成"没学到东西"。

练习与思考

  1. 用同一个种子分别跑 --mode ctde 与 --mode indep，先预测撞目标率哪个降得更低，再比较最终评估；解释 CTDE 的增益来自哪里。★
    提示
    只看评估段三行输出，重点比较"撞目标率"，它直接反映分工。若两者差距不明显，换 3 个种子看平均趋势。
  2. 把道具数从 2 改成 4（TeamGatherEnv(n_items=4)），预测撞目标率的绝对值会怎么变、分工的相对增益会怎么变，再实跑验证。★
    提示
    道具越多，两人抢同一个的"基础重叠率"本来就低，这是环境带来的。对比训练前后的下降幅度更有意义，绝对值受环境影响大。注意观测里只含"最近道具"的相对坐标，道具数不影响观测维度。
  3. 把队友的共享奖励减半（队友 +0.5、捡到者 +1），预测合作行为（撞目标率、场均得分）会怎么退化，再解释公共品激励的强度效应。★★
    提示
    改 step() 里 rewards[self.teammates[i]] += 1.0 那一行。反过来把队友奖励调到比捡到者更高，看是否出现"故意让队友捡"的行为，这是激励设计改变策略的直接证据。
  4. 把队伍规模从 2v2 改成 3v3，分析 CTDE 评论家输入维度会膨胀到多少、计算成本如何变化，并给出一种控制维度的方案。★★★
    提示
    teams 与 teammates 要重新定义，观测里对手数量也变。维度会快速膨胀，工程折衷是"观测只保留最近的对手"，评论家则需权衡"看全队"还是"只看关键队友"。
  5. 把 CTDE 评论家升级成"看队友 + 看两名对手的动作"，预测场均得分与撞目标率的走向。注意对手动作在训练期才可见，评估时不能使用。★★★
    提示
    需要在存转移时同时记录两名对手的动作，把 _q_input 扩成 obs+act+队友两人+对手两人；回填逻辑参考第 082 章的 true 模式。信息更多不一定更快：输入维度上升、非平稳性仍在，结论交给实验。

小结

  • 混合任务 = 队内公共品奖励（合作）+ 队间零和竞争（对抗），是检验多智能体算法鲁棒性的标准场景。
  • CTDE 的最小实现是让评论家接收队友的观测与动作，策略仍只依赖本地观测，满足分散执行要求。
  • Bellman 目标里的"下一状态队友动作"要按"先 patch、后 store、回合末 clear"的顺序维护，时间一致性是正确性底线。
  • 评价混合任务至少用三个指标：净胜分、场均得分、撞目标率；只看一个会被动态平衡误导。
  • 下一章换主角：在同一个协作任务上把多智能体 PPO 与本章的 SAC 家族放在一起，对比训练速度、最终回报与稳定性。
