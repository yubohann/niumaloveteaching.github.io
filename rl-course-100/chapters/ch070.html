第 070 章：多智能体PPO：参数共享

三个智能体长得一模一样、任务也对称，为什么还要三套策略网络？本章把三个 Actor 合并成一个共享网络，用同一份数据流更新，和"各管各的"版本正面对照。

  • 主题：参数共享 / 对称任务的归纳偏置
  • 关键公式：L(θ) = 𝔼[(1/N)Σi min(riÂi, clip(ri,1±ε)Âi)]，比率共用同一个 πθ
  • 预计学时：45 分钟
  • 前置章节：第 069 章

学习目标

  • 理解参数共享（parameter sharing）的动机：同质智能体 + 对称任务 = 一个策略可以服务所有人。
  • 掌握"合并批次"的实现：把 N 个智能体的转移拼成一个大批量，用共享网络一次更新。
  • 从数据效率和参数效率两个角度解释共享的优势：数据量约 ×N、策略参数量约 ÷N。
  • 识别参数共享的适用边界：角色异质、能力异质的团队适用"条件共享"，无条件共享会强迫网络折中两种最优行为。
  • 在合作导航环境上对照 separate 与 shared 两种配置，报告最终回报、末距与参数量。

背景与动机

在合作导航任务里，三个智能体的观测空间、动作空间、动力学完全相同，奖励也是对称的：没有任何一条规则说"一号位要当先锋、二号位要掩护"。换句话说，任务里不存在角色，只有位置的不同。既然所有智能体面对的是同一个决策问题，让它们各自从零开始学一套参数，就是把同一道题抄三遍。

参数共享把这"三份作业"合并成一份：一个共享策略 πθ 接收任意智能体的局部观测并输出动作，三个智能体的数据进同一个优化器。好处很直接：同一份参数获得约 N 倍的数据，梯度估计更稳；模型参数量降到约 1/N，训练与部署都更轻；策略天然对所有智能体一致，不会出现"一个学会了、一个还在原地"。代价是表达能力受限，如果团队里真有分工（不同速度、不同传感器、不同职责），一个无条件共享的网络会被迫折中。本章的环境恰好是"共享的理想场景"，用它来建立对参数共享的直觉。

本章沿用第 069 章的 CTDE 骨架：两种配置都配共享中央批评家，唯一变量是策略网络的数量与组织方式，separate 是三份 Actor 逐个更新，shared 是一份 Actor 批量更新。

核心原理

1. 共享策略的梯度是"所有人的和"

把参数共享写进目标函数：策略集合退化为同一个 πθ，每个智能体各自贡献经验，PPO 的裁剪目标变成对全部智能体转移的求和：

L(θ) = 𝔼t[ (1/N) Σi=1N min( rti(θ)·Âti, clip(rti(θ), 1−ε, 1+ε)·Âti ) ]
rti(θ) = πθ(ati|oti) / πθold(ati|oti) i 遍历智能体；分子分母是同一个共享策略（新旧两份参数快照），比率衡量"这一轮更新后共享策略变了多少"

注意求和的位置：每个智能体的每条转移都有自己的比率与优势，但梯度全部汇入同一组参数。同一批交互数据从"N×B 条有效样本"的角度参与更新，每个 epoch 优化器看到的 minibatch 数也是独立版本的大约 N 倍，这就是样本效率提升的直接来源。反过来说，共享也是一个方差分摊机制：单个智能体的噪声梯度被其他 N−1 个智能体的梯度平均掉。

2. 对称任务 + 共享参数 = 正确的归纳偏置

导航任务的奖励函数对智能体编号完全对称（二分匹配对配对排列取最优），因此最优策略集合里必然存在完全对称的策略：每个智能体执行同一个函数 π*(·)。参数共享把"策略应当对称"这个先验直接写进模型结构，归纳偏置与任务结构匹配时，学习会显著加速：策略不必再花费样本去"发现"对称性。

反过来，如果团队是非对称的（比如一个智能体是快车、另一个是慢车），无条件共享会把两个不同的最优行为强行平均，此时应改为条件共享：共享躯干、但把身份或能力特征拼进网络输入（如 one-hot ID、速度上界），让同一个网络表达"按角色分支"的策略。

3. 共享的隐性风险

共享网络意味着：一个智能体的坏更新会立刻影响所有智能体。早期如果某个智能体困在角落里产生了极端优势估计，梯度会把这个"坏习惯"写进全队参数；而且错误会通过共享传播，不像独立版本那样只污染一个网络。实践中通常配合两件事来观察：优势标准化的批次范围、以及策略熵是否整体塌缩。本章日志里的 KL 与裁剪比例可以用于这个诊断，共享模式下如果 KL 突然飙升，成因往往是某个智能体的异常批次带偏了整组梯度；排查时先看数据侧，再看学习率。

4. 数据效率与参数效率的双重账

用数字把账算清楚。设每次更新采样 3000 智能体步、3 个智能体：

separate：3 个 Actor × 各 1000 条转移；shared：1 个 Actor × 3000 条转移
策略参数量：3 × PActor → 1 × PActor 每个 epoch 的 minibatch 数：separate 约 3×⌈1000/B⌉，shared 约 ⌈3000/B⌉，后者约为前者 3 倍

共享版本每个 epoch 的梯度步数更多、每步的样本更多，因此同样预算下参数更新更充分。这也是为什么共享模式通常"学得更快"：数据利用率的结构变了，算法本身一行没动。

实现思路与设计

模块划分

组件职责关键点
Actor / CentralCritic两种模式共用的网络定义共享改变的是"数量与组织方式"，不是结构
SeparateActors三个独立 Actor + 中央批评家逐个智能体更新；策略参数量约为共享版 3 倍
SharedActor.act_all共享策略批量前向一次前向处理 (N, obs_dim)，天然支持批处理
SharedActor.update拼接批次后一次更新obs/act/logp 沿智能体维度拼接；优势按时间广播重复
collect两种模式共用的采样器数据结构完全一致，差异只在 update 阶段

关键超参数

参数默认值作用与取值理由
--modeboth先 separate 后 shared，同预算对照
--max-steps120000每种模式的智能体步预算
--batch-size256共享模式下每个 minibatch 仍是 256，但总样本量是 3 倍
--epochs8两种模式相同；共享模式每 epoch 的 minibatch 数约为 3 倍
--hidden64共享单一网络的宽度；总参数量对比会打印在日志里

数据流

相同部分：采样器 collect 两种模式共用，产出每智能体的 (obs, act, logp) 桶、全局状态序列、团队回报、中央价值与回合端点，数据完全一样。不同部分在更新：separate 循环三个 Actor 各自做 ppo_actor_update；shared 把三个桶沿样本维拼接成 3000 条的大批次，把优势向量按时间复制 N 份，一次更新一个 Actor。

与第 069 章的差异点

第 069 章的 CTDE 是"三个独立 Actor + 一个中央批评家"；本章 shared 版是"一个 Actor + 一个中央批评家"，并把三份转移拼成一个大 batch 更新。collect 采样器共用，数据完全一样，只有参数组织方式变了，标准的单变量对照。第 071 章会给共享策略加一条通信通道。

关键代码与解读

片段 1：一个网络服务所有智能体

class SharedActor:
    def __init__(self, env, args, device):
        self.n = env.n_agents
        self.device = device
        self.actor = Actor(env.obs_dim, env.act_dim, args.hidden).to(device)
        self.central = CentralCritic(env.state_dim, args.hidden).to(device)
        self.actor_opt = torch.optim.Adam(self.actor.parameters(), lr=args.lr)
        self.central_opt = torch.optim.Adam(self.central.parameters(), lr=args.lr)

    @torch.no_grad()
    def act_all(self, obs, global_state):
        """一次前向批量处理所有智能体，共享网络天然支持批处理。"""
        obs_t = torch.as_tensor(obs, dtype=torch.float32, device=self.device)
        state_t = torch.as_tensor(global_state, dtype=torch.float32,
                                  device=self.device).unsqueeze(0)
        actions, logps = self.actor.act(obs_t)             # (N, obs_dim) 一次前向
        value = float(self.central(state_t).item())
        return actions.cpu().numpy(), [float(x) for x in logps], value

    @torch.no_grad()
    def mean_actions_all(self, obs):
        obs_t = torch.as_tensor(obs, dtype=torch.float32, device=self.device)
        return self.actor.mean_action(obs_t).cpu().numpy()  # 评估也是一次前向

解读：对照第 069 章的分离版，这里的代码更"顺"了。（1）分离版的 act_all 里有一个 for i in range(self.n) 循环，逐个切行前向；共享版把整个 (N, obs_dim) 矩阵一次性送进网络，Linear 本来就按第一维批处理，"参数共享天然支持批处理"是矩阵乘法的语义，不是修辞。（2）共享版只维护一个 self.actor 和一个 actor_opt；分离版是两个列表加两个优化器列表。（3）中央批评家没有变化，两种模式都只有一个，本章的单变量对照只动策略网络。（4）注意 act 返回的 logp 按行对应每个智能体；后面存桶时每个智能体拿自己那一行，数据组织方式与分离版保持一致。

片段 2：拼接批次与优势广播

        # 把三个智能体的转移拼成一个大 batch，共享网络一次更新
        obs_cat = torch.as_tensor(
            np.concatenate([np.asarray(agent_bufs[i]["obs"]) for i in range(self.n)], axis=0),
            dtype=torch.float32, device=device)
        act_cat = torch.as_tensor(
            np.concatenate([np.asarray(agent_bufs[i]["act"]) for i in range(self.n)], axis=0),
            dtype=torch.float32, device=device)
        logp_cat = torch.as_tensor(
            np.concatenate([np.asarray(agent_bufs[i]["logp"]) for i in range(self.n)], axis=0),
            dtype=torch.float32, device=device)
        # 优势按时间广播：同一个时间步，所有智能体共享同一条优势
        adv_cat = torch.as_tensor(np.tile(adv, self.n), device=device)
        ps = ppo_actor_update(self.actor, self.actor_opt, obs_cat, act_cat,
                              logp_cat, adv_cat, args)

解读：这段十六行是参数共享最核心的实现细节，逐点展开。（1）三个桶的 obs 沿 axis=0 拼接成 (3T, obs_dim) 的大矩阵；act、logp_old 同样处理。旧对数概率必须与各自的转移严格配对，拼错顺序会让比率算错，训练静默失效。（2）np.tile(adv, self.n) 是最容易写错的一行：adv 是按环境步的团队优势（长度 T），而拼接后的批次布局是"先放智能体 1 的 T 条、再放智能体 2 的 T 条……"，所以每个时间步的优势要重复出现 N 次，tile 的结果与拼接顺序恰好对齐。如果改用 np.repeat(adv, self.n)，语义会变成"每条连续出现 N 次"，与批次布局错位，这是个值得亲手验证的坑。（3）更新调用 ppo_actor_update 只发生一次，函数内部按 3000 条样本划 minibatch，每个 epoch 约 12 个批次，相比之下分离版每个 Actor 只有约 4 个批次，数据利用率差了约 3 倍。（4）优势是共享的（团队优势）且被广播给所有智能体，这与第 069 章 CTDE 的口径一致，保证对照的公平性。

片段 3：分离版的对照更新

        stats = {"policy_loss": 0.0, "approx_kl": 0.0, "clip_frac": 0.0, "ev": ev}
        for i in range(self.n):                    # 三个 Actor 逐个更新
            obs = torch.as_tensor(np.asarray(agent_bufs[i]["obs"]), dtype=torch.float32,
                                  device=device)
            act = torch.as_tensor(np.asarray(agent_bufs[i]["act"]), dtype=torch.float32,
                                  device=device)
            logp_old = torch.as_tensor(np.asarray(agent_bufs[i]["logp"]), dtype=torch.float32,
                                       device=device)
            ps = ppo_actor_update(self.actors[i], self.actor_opts[i], obs, act,
                                  logp_old, adv_t, args)   # 每个 Actor 只看到自己的 1000 条
            stats["policy_loss"] += ps["policy_loss"]
            stats["approx_kl"] += ps["approx_kl"]
            stats["clip_frac"] += ps["clip_frac"]
        stats["policy_loss"] /= self.n
        stats["approx_kl"] /= self.n
        stats["clip_frac"] /= self.n

解读：把这段与片段 2 并排看，两种数据流的差异一目了然。（1）分离版每个 Actor 只看到自己那份约 1000 条转移；共享版一个 Actor 看到 3000 条。同一个 ppo_actor_update 被复用，差别只在传入的数据量和网络实例。（2）诊断统计按智能体平均（/= self.n），得到的是"三个 Actor 的平均 KL/裁剪比例"，与共享版单网络的对应量可比。（3）分离版没有"参数互相影响"的通道：Actor 1 的梯度只改 Actor 1。共享版的梯度是三人共享，数据效率与控制耦合是同一枚硬币的两面。

片段 4：参数量对比与汇总输出

    agents = SeparateActors(env, args, device) if mode == "separate" else SharedActor(env, args, device)
    modules = agents.actors + [agents.central] if mode == "separate" else [agents.actor, agents.central]
    n_params = sum(p.numel() for m in modules for p in m.parameters())
    print(f"[{mode.upper()}] 可训练参数量 {n_params}")

    # ---- 主流程汇总（两种模式跑完后）----
    for name, (curve, elapsed, final) in results.items():
        best = max(r for _, r in curve) if curve else float("nan")
        print(f"[{name:8s}] 用时 {elapsed:6.1f}s | 最佳评估 {best:7.2f} | "
              f"最终（回报/末距/碰撞） {final[0]:7.2f} / {final[1]:.3f} / {final[2]:.2f}")

解读：两段小代码合起来回答"共享省了多少参数、赢了还是输了"。（1）参数量统计按模式选模块列表：separate 是"三个 Actor + 一个批评家"，shared 是"一个 Actor + 一个批评家"；p.numel() 逐参数计数求和。你会在日志里看到 shared 的策略部分只有 separate 的约 1/3，总参数量约减半（批评家两边相同）。（2）汇总表把最佳评估与最终三指标并列：只看最终一次评估可能被噪声骗，最佳值与最终值一起看才完整。（3）曲线落盘为纯文本 separate_curve.txt / shared_curve.txt，方便后处理与画图，教学脚本不依赖 matplotlib，但数据给你留着。

以实跑为准的预期：同预算下参数共享通常学得更快、更稳，同一网络看到约 3 倍数据、参数量只有 1/3；最终回报两者接近（约 −5 ~ −3），但共享版往往更早到达（约 6 万~9 万步 vs 10 万步以后）。任务本身对称、智能体之间没有角色分工，共享几乎无副作用。

常见坑

  • 拼接顺序与优势广播错位：拼接后的批次是"智能体优先"排列（先 i=1 的全部 T 条，再 i=2……），优势必须用 np.tile(adv, N) 与拼接顺序对齐；np.repeat(adv, N) 形状相同、语义不同，写错不会报错，只会让训练变差。
  • 把共享网络当成免费午餐：角色异质的任务（快慢车、不同传感器）里，无条件共享会迫使一个网络折中两种最优行为。发现共享版明显更差时，先检查任务是否真的对称。
  • 学习率未随有效批量调整：共享版每个 minibatch 仍是 256，但更新的总样本量约 3 倍。若 KL 普遍偏高，可以先把学习率下调再考虑其他改动。
  • 评估还走分离版的接口：两种模式共用 mean_actions_all 签名，但共享版返回的是一次前向的动作矩阵；自己改代码时别保留旧的循环版本，否则评估速度与行为都会不同。
  • 用一次运行给共享"判胜"：共享与分离的差距可能小于种子波动，结论要用多种子平均，并同时报告参数量与达到目标步数。

练习与思考

  1. 把 --mode 分别跑 shared 与 separate，对比日志第一行的"可训练参数量"。理论比值是多少？实际打印值差多少，为什么？★
    提示
    策略部分约 1/3，中央批评家两边相同，所以总量不是精确 1/3。先手算 3 层 MLP 的参数数，再与日志对照。
  2. 把 np.tile(adv, self.n) 改成 np.repeat(adv, self.n) 跑一次（或只做纸面推导），解释为什么训练会变差。★
    提示
    写出拼接批次的索引顺序：第 0~T−1 条属于智能体 1，第 T~2T−1 条属于智能体 2……哪一条优势应该配哪一条转移，画出来就明白了。
  3. 把 --n-agents 改成 4，预测 shared 相对 separate 的优势会变大还是变小，并解释原因。★★
    提示
    共享的数据聚合倍数是 N，参数节省也是 N 倍；N 越大优势越明显，但碰撞更频繁、任务更难，注意区分"相对优势"与"绝对难度"。
  4. 给共享网络加"身份输入"（把智能体 one-hot ID 拼进观测）做条件共享，并制造一个不对称任务（如智能体 0 的加速度只有别人一半），比较无条件共享与条件共享。★★
    提示
    改两处：环境里让 accel 按智能体不同；网络输入维度 +N 并拼接 one-hot。预期：不对称任务上无条件共享明显更差，条件共享接近分离版但更省参数。
  5. 设计实验区分"共享的收益来自数据变多还是参数变少"：让 separate 版把三份数据分别过三遍（等于数据量 ×3），与 shared 对照。谁的收益更大？★★★
    提示
    可以让 separate 的 epochs 从 8 提到 24，或加一个"三网络同时看全量数据再取平均梯度"的变体。讨论：数据复用与参数共享是两种独立的正则/效率机制。

小结

  • 参数共享 = 一个策略 πθ 服务所有智能体；目标是全部转移裁剪项的求和，梯度是所有人的和。
  • 双重收益：每个 Actor 看到约 N 倍数据（样本效率）、策略参数量约 ÷N（参数效率）。
  • 对称任务是共享的主场：把"策略应对称"的先验写进结构；角色异质时应改条件共享（身份输入）。
  • 实现核心是"拼接 + 广播"：obs/act/logp 沿轴 0 拼接，优势用 np.tile 按时间对齐，这里最容易出错。
  • 风险同样存在：一个智能体的坏梯度会污染全队共享参数，KL 与裁剪比例要盯紧。
  • 下一章给共享策略加一条通信通道：智能体在动作之外还要发出消息，看看"能说话"的团队能多学到什么。
