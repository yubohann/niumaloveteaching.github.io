第四篇 · 多智能体强化学习

第 076 章：多智能体SAC：独立SAC

第四篇下半程开工：把 SAC 搬到多智能体世界。每个智能体拥有完整的 Actor、双 Q、目标网络与自动温度，共享一个联合回放池，各自为政地学习，这就是独立 SAC（ISAC）。

  • 主题：off-policy 多智能体起步 / 联合回放池
  • 关键公式：yi = ri + γ(1−d)[minkQi,ktgt(o′i,a′i) − αi·log πi(a′i|o′i)]
  • 预计学时：50 分钟
  • 前置章节：第 075 章

学习目标

  • 理解独立 SAC（Independent SAC, ISAC）的架构：每个智能体一套 off-policy 学习器，联合回放池共享数据。
  • 掌握联合转移的存储与采样，理清"时间维 × 智能体维"的索引方式。
  • 对比两种奖励信号（团队奖励 vs 个体奖励）对独立批评家的影响。
  • 认识 off-policy 在多智能体里的双刃剑：数据复用率高，但旧数据描述的是"旧对手"。
  • 在合作导航任务上把 ISAC 练到评估回报约 −8 ~ −4 分，并解释曲线里个体学习进度错位的现象。

背景与动机

第四篇用 PPO 走完了多智能体的六个机制。PPO 是 on-policy 的：每个更新批次用完即弃，样本效率受限。多智能体任务里数据成本更高（N 个智能体一步产生 N 条转移，环境交互却是同步的），于是"能不能把 SAC 那套经验回放搬过来"就成了自然问题。答案是能，而且要做的改动比想象中少：给每个智能体复制一份 SAC，把联合数据存进同一个池子，采样时各取所需。

但 off-policy 在多智能体里有个额外麻烦：回放池里的旧数据是"对上旧版本对手"的经验。智能体 i 的批评家在做 Bellman 备份时，下一状态的价值隐含"其他智能体按当前行为"的假设，而它们在变。第 076～081 章会依次用集中 Q、参数共享、通信、对称性、信用分配来应对这个挑战；本章先把最朴素的独立版本跑起来，并顺带回答一个实际问题：批评家到底该用团队奖励还是自己的奖励？

核心原理

1. 独立 SAC：每个智能体一套软 Bellman

智能体 i 只优化自己的软 Q 函数 Qi(oi, ai)，下一状态的动作从自己的策略采样：

yi = ri + γ(1−d)·[ mink Qi,ktgt(oi′, ai′) − αi log πi(ai′|oi′) ]，  ai′ ∼ πi Qi,ktgt 是智能体 i 的第 k 个目标 Q（k=1,2 双 Q 取小）；αi 是它自己的温度；Qi 不看队友的观测与动作

与单智能体 SAC 的唯一区别在于数据来源：转移由环境同步产生，回放池里存的是联合转移 (o1:N, a1:N, r1:N, o′1:N, d)。每个智能体只取自己那一列，等价于"把队友视为环境的一部分"，这正是独立学习方法论的立场。优势是每份数据都能被所有人复用（off-policy 的样本效率），代价是 Bellman 备份里对其他智能体的"行为假设"可能已经过期。

2. 奖励信号的选择：团队还是个体

本章对照两种选择：

  • team：所有智能体的批评家都用团队奖励 rteam = meani(ri)。目标一致，但"我的碰撞惩罚"被平均稀释。
  • own：智能体 i 用自己的奖励 ri（团队匹配项 + 自己的碰撞惩罚）。个体信号更精确，但不同智能体的目标存在轻微差异（每个人都在最大化"自己那份"）。

两者构成信号设计的权衡：团队奖励利于对齐，个体奖励避免搭便车、也让碰撞这种个体事件更可学。你可以把本章的对照结果带到后面的集中 Q 章节，那里会用全局状态与联合动作，让一个批评家同时看到双方信息。

3. 非平稳性影响了什么：回放池的"新鲜度"

off-policy 的理论保证假设环境平稳；多智能体里对手策略持续变化，旧转移的分布会过时。实践中三条经验：① 池子不宜太大（本章默认 20 万，对 2 万环境步的训练完全放得下）；② 更新频率与数据新鲜度要平衡（--update-every）；③ 优先做"近期数据偏置"采样（第 044 章的优先级回放思想）。本章先把基线跑稳，这些旋钮留给你在练习里调。

4. 为什么预热步数在 off-policy 里更关键

on-policy 的 PPO 可以用少量噪声数据起步，因为数据立刻被丢弃；off-policy 的 SAC 则会把最初的随机数据留在池子里反复采样。如果预热不足，前期几万次更新都在从贫瘠分布里学习，容易把 Q 带偏。本章 1000 步随机预热按 3 智能体折算约 3000 条转移，足以覆盖初始状态空间；调大 --start-steps 会更稳但更慢，调小则早期风险上升。

数据流

每个环境步：选动作（预热期随机，之后每个智能体用自己的策略采样）→ env.step 得到联合观测、个体奖励、团队奖励 → buffer.add 存下整条联合转移 → 按 update_every 决定是否更新：采样一个 batch，对每个智能体取"自己那一列"（[:, i]）做一次 SAC 更新。--reward 决定批评家吃 team_rew 还是 rew[:, i]。

与第 075 章的差异点

第 075 章是 on-policy 的 2v1 对抗；本章回到合作导航，算法换成 off-policy 的独立 SAC：① 引入联合回放池与采样；② 每个智能体有自动温度；③ 新增"团队 vs 个体奖励"的对照。环境与奖励定义保持不变，方便与第 068 章的 IPPO 做横向比较（正式的多智能体 PPO/SAC 对比在第 084 章）。

关键代码与解读

片段 1：联合回放池

class JointReplayBuffer:
    def __init__(self, capacity, n_agents, obs_dim, act_dim):
        self.capacity = capacity
        self.ptr = 0
        self.size = 0
        self.obs = np.zeros((capacity, n_agents, obs_dim), np.float32)      # (T, N, obs)
        self.act = np.zeros((capacity, n_agents, act_dim), np.float32)
        self.rew = np.zeros((capacity, n_agents), np.float32)               # 个体奖励
        self.team_rew = np.zeros((capacity,), np.float32)                   # 团队奖励
        self.next_obs = np.zeros((capacity, n_agents, obs_dim), np.float32)
        self.done = np.zeros((capacity,), np.float32)

    def add(self, obs, act, per_rew, team_rew, next_obs, done):
        i = self.ptr
        self.obs[i] = obs
        self.act[i] = act
        self.rew[i] = per_rew
        self.team_rew[i] = team_rew
        self.next_obs[i] = next_obs
        self.done[i] = done
        self.ptr = (self.ptr + 1) % self.capacity
        self.size = min(self.size + 1, self.capacity)

    def sample(self, batch_size, device):
        idx = np.random.randint(0, self.size, size=batch_size)
        return {
            "obs": torch.as_tensor(self.obs[idx], device=device),
            "act": torch.as_tensor(self.act[idx], device=device),
            "rew": torch.as_tensor(self.rew[idx], device=device),
            "team_rew": torch.as_tensor(self.team_rew[idx], device=device),
            "next_obs": torch.as_tensor(self.next_obs[idx], device=device),
            "done": torch.as_tensor(self.done[idx], device=device),
        }

解读：多智能体 off-policy 的核心数据结构，四点值得记住。（1）形状从单智能体的 (T, ·) 变成 (T, N, ·)：obs 是 (容量, N, obs_dim)、rew 是 (容量, N)、team_rew 是 (容量,)。个体与团队奖励同池共存，这是本章"team vs own"对照能在一个脚本里轻松切换的前提。（2）done 只存一个标量：N 个智能体的回合同步结束，没有 per-agent 终止（第 068 章起就如此）。（3）sample 返回整批联合数据，每个智能体更新时再切自己那一列，采样只做一次，N 个学习器共享同一批索引，比较公平也省 IO。（4）环形缓冲的 ptr/size 逻辑与单智能体版一致；训练规模（2 万步 × 3 智能体 = 6 万条）远小于容量 20 万，实际上池子不会绕圈。

片段 2：一个智能体的完整 SAC 更新

    def update(self, obs, act, rew, next_obs, done):
        """用单智能体的 (obs, act, rew, next_obs, done) 做一次完整更新。"""
        with torch.no_grad():
            next_act, next_logp = self.policy.sample(next_obs)
            q1t, q2t = self.q_target(next_obs, next_act)
            target = rew + self.gamma * (1.0 - done) * (
                torch.min(q1t, q2t) - self.alpha * next_logp)
        q1, q2 = self.q(obs, act)
        q_loss = F.mse_loss(q1, target) + F.mse_loss(q2, target)
        self.q_opt.zero_grad()
        q_loss.backward()
        self.q_opt.step()

        new_act, logp = self.policy.sample(obs)
        q1n, q2n = self.q(obs, new_act)
        policy_loss = (self.alpha.detach() * logp - torch.min(q1n, q2n)).mean()
        self.policy_opt.zero_grad()
        policy_loss.backward()
        self.policy_opt.step()

        alpha_loss = -(self.log_alpha * (logp.detach() + self.target_entropy)).mean()
        self.alpha_opt.zero_grad()
        alpha_loss.backward()
        self.alpha_opt.step()

        with torch.no_grad():
            for p, p_t in zip(self.q.parameters(), self.q_target.parameters()):
                p_t.data.mul_(1.0 - self.tau).add_(self.tau * p.data)
        return {"q_loss": q_loss.item(), "policy_loss": policy_loss.item(),
                "alpha": self.alpha.item()}

解读：这段与第 062 章的 SAC 更新逐字同构，唯一的区别是入参已经是"切开后的单智能体列"，obs 形状 (B, obs_dim)、rew 形状 (B,)，不再关心队友。调用方（片段 4）负责切列。（1）Bellman 目标里的 next_act 由自己的策略生成：独立学习假设"队友 = 环境"，所以不需要量化队友的下一步动作。（2）alpha 在策略损失里 .detach()、logp 在温度损失里 .detach()：与单智能体篇一致的双向隔离。（3）自动温度的目标熵 target_entropy = -act_dim（−2）：Pendulum 时代沿用下来的默认，合作导航的连续 2 维动作同样适用。（4）软更新在最后；三个优化器（Q、policy、alpha）各自独立，N 个智能体意味着 3N 个优化器同时活着，这是独立 SAC 参数量与计算量的直观账本。

片段 3：联合动作与存储

        if step <= args.start_steps:
            actions = np.random.uniform(-1.0, 1.0, (n, env.act_dim)).astype(np.float32)
        else:
            actions = []
            for i in range(n):
                with torch.no_grad():
                    a = agents[i].policy.sample(torch.as_tensor(
                        obs[i], dtype=torch.float32, device=device).unsqueeze(0))[0]
                actions.append(a.squeeze(0).cpu().numpy())
            actions = np.stack(actions)                      # (N, act_dim)

        next_obs, per_rew, team_rew, done, info = env.step(actions)
        buffer.add(obs, actions, per_rew, team_rew, next_obs, float(done))
        obs = next_obs
        if done:
            obs = env.reset()

解读：采样循环的形状账本很重要。（1）预热期直接生成 (N, act_dim) 的随机动作矩阵；之后逐个智能体采样再 np.stack 成同样形状，环境接口不区分"谁在哪学的"，只认联合动作。（2）每个智能体的策略采样都带 no_grad：数据收集不做反传，梯度只发生在 update 里。（3）buffer.add 一次写入整条联合转移：观测 (N, obs_dim)、动作 (N, act_dim)、个体奖励 (N,)、团队奖励标量。注意传的是 float(done) 标量；回合同步结束的约定再次出现。（4）回合结束后只重置环境，不需要清池子：off-policy 的转移天然跨回合复用，done 掩码会在 Bellman 目标里切断自举。

片段 4：奖励切换与逐智能体更新

        # ---- 每个智能体各自更新 ----
        if step > args.start_steps and step % args.update_every == 0:
            batch = buffer.sample(args.batch_size, device)      # 同一批索引，全员共享
            for i in range(n):
                rew_i = batch["team_rew"] if reward_mode == "team" else batch["rew"][:, i]
                last_stats = agents[i].update(
                    batch["obs"][:, i], batch["act"][:, i], rew_i,
                    batch["next_obs"][:, i], batch["done"])

        if step % args.eval_every == 0:
            ret, dist, coll = evaluate(eval_env, agents, args.eval_episodes, device)
            curve.append((step, ret))
            alphas = np.mean([float(a.alpha.item()) for a in agents])
            print(f"[{label} 步 {step:6d}] 评估回报 {ret:7.2f} | 平均末距 {dist:.3f} | "
                  f"碰撞 {coll:.2f}/回合 | α均值 {alphas:.3f} | "
                  f"用时 {time.time() - t0:5.1f}s")

解读：这一小段是 ISAC 的"管理调度"，也是两种奖励对照的实现处。（1）采样一次、N 个智能体共用同一批索引：每个智能体看到的转移样本在时间上对齐（同一步的联合数据），对照更公平。（2）batch["obs"][:, i] 取第 i 列，(B, N, obs_dim) → (B, obs_dim)；rew_i 在 team 模式取 (B,) 的团队奖励、own 模式取 batch["rew"][:, i]。切换逻辑就一行，两种信号共享全部其他代码。（3）诊断打印 α均值：三个智能体的温度平均值。它下降说明策略们在变确定；若某个智能体的 α 单独飙高，通常是它遇到了更难的状态分布（练习里会让你逐智能体打印）。（4）update_every 是算力与数据复用的旋钮：调大到 4 表示每 4 个环境步更新一轮，更新总数减少、单条数据被更新相对更少，这是应答非平稳性的手段之一（更少"盯着旧数据反复消化"）。

常见坑

  • 索引切错列：batch["obs"][:, i] 是"取所有时间的第 i 个智能体"，不是"取第 i 条转移"。切错维度不报错但语义全乱，是本类脚本最容易踩的坑。
  • 把 done 写成数组：回合同步结束，done 存标量或 (B,) 都行，但必须与 Bellman 里的 (1.0 - done) 广播兼容；混入 per-agent done 语义会破坏自举。
  • 预热步数太少：off-policy 会反复消化池里的早期数据；预热不足时 Q 会被贫瘠分布带偏，且很难纠正。
  • 池子过大而训练过短：数据永远填不满池子无所谓，但"过量采样旧数据"会加剧非平稳性问题。训练规模只有几万条时，20 万容量已经绰绰有余。
  • 希望 ISAC 像单智能体 SAC 一样稳：队友同时在学习，Bellman 目标里隐含的行为假设持续漂移。曲线抖动是机制性的，稳定化要等后面几章（集中 Q、参数共享等）。

练习与思考

  1. 把 --reward 跑 both，对比两条曲线的形状与终点。own 模式的开局优势来自哪一项奖励？★
    提示
    own 把"自己的碰撞惩罚"完整保留，碰撞事件对 Q 的影响更直接；team 模式里该信号被平均稀释。观察前 5000 步的末距/碰撞列。
  2. 把 --update-every 从 1 改为 4、8，观察收敛速度与曲线波动。更新频率和非平稳性耐受度是什么关系？★
    提示
    更新变稀 = 每条数据被"消化"的次数相对减少、策略变化更慢，旧数据的过时程度降低；代价是样本利用更慢。找"总更新次数 vs 最终回报"的平衡点。
  3. 把 --buffer-size 降到 20000（与训练总量同级）再跑，解释为什么影响可能很小、也可能明显，取决于训练长度。★★
    提示
    2 万步 ×3 智能体 = 6 万条 > 容量，池子会绕圈淘汰最老数据，相当于天然"只保留近期数据"，恰好缓解非平稳性。打印半径内数据的时间分布验证这个想法。
  4. 逐智能体打印 α 与评估中的个体末距（拆分 evaluate 的统计），检查是否存在"一个智能体一直学不好"的错位。错位更可能来自初始化还是数据分布？★★
    提示
    任务对称 + 数据共享时，错位主要来自初始化与探索噪声；如果某个智能体持续落后，检查它的观测列是否被错误裁剪。
  5. 给采样池加"近期偏置"：以 50% 概率从最近 20% 的转移里采样、50% 均匀采样，观察对非平稳性的缓解。它与优先级回放（第 044 章）的共同点是什么？★★★
    提示
    需要维护写入指针并构造两段采样索引。共同点：都在给"更相关的数据"更高权重；区别：一个是时间维度，一个是 TD 误差维度。

小结

  • 独立 SAC = N 份完整 SAC 学习器 + 一个联合回放池；每个智能体把队友当作环境的一部分。
  • 联合池形状 (T, N, ·)，个体奖励与团队奖励同池共存，--reward 一行切换对照信号。
  • 更新时"采样一次、全员共享索引、各自切列"，效率与公平性的兼顾。
