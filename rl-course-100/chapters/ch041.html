第二篇 · 离策略方法与 SAC

第 041 章：SAC的熵系数调度

不给 alpha 配优化器，改配一张时间表：从 0.4 线性或余弦退火到 0.02。在同一种子上对比常数、线性、余弦三条轨迹，看"开环控制"与第 032 章"闭环自动温度"各自的性格。

  • 主题：探索强度调度 / 开环 vs 闭环
  • 关键公式：α(p) = αend + ½(αstart−αend)(1+cos(π·p))（cosine）
  • 预计学时：45 分钟
  • 前置章节：第 040 章

学习目标

  • 理解 alpha 调度与自动温度的本质区别：一个是对训练进度的开环函数，一个是盯住熵缺口的闭环反馈。
  • 实现线性与余弦两种退火函数，并与常数 alpha、auto 模式共用同一套训练代码。
  • 在 Pendulum-v1 上比较三种调度的评估回报、alpha 与熵的轨迹联动。
  • 掌握选择起止值的原则，并能判断"我的环境更适合调度还是自动温度"。

背景与动机

从第 032 章开始，alpha 一直被当作"学习出来的量"：盯住目标熵，缺多少补多少。但工程里还有另一种常见做法，直接给 alpha 排一张时间表：训练早期给大 alpha 鼓励探索，后期调小让它收敛。这种思路在语言模型微调（RLHF）里非常普遍：KL 系数、熵系数经常按 token 位置或训练进度线性退火。

调度的吸引力在哪里？三个理由：(1) 可控，你能明确指定"第 10 万步时探索强度是多少"；(2) 省一个优化器，不引入 log_alpha 的参数与梯度；(3) 不依赖目标熵，目标熵本身也是个需要选定的超参数。当然代价也直白：调度不知道自己现在学到哪了，策略如果提前收敛，它还在按表逐步执行，开环控制对意外没有响应能力。

本章把 linear 和 cosine 两种典型退火实现出来，与常数基线同种子对照；--schedules 里还保留了 auto 选项，方便你把第 032 章的闭环方案拉进来做第四次实验。

核心原理

1. 两种退火函数

设训练总预算为 T 步，进度 p = t / T 从 0 增长到 1：

linear：α(t) = αstart + (αend − αstart)·p
cosine：α(t) = αend + ½(αstart − αend)·(1 + cos(π·p))

linear 以恒定速率下降；cosine 起步慢、中段快、收尾又变慢，形状与余弦学习率调度同源。两者都从 alpha_start=0.4 退到 alpha_end=0.02：前者让早期策略保持高随机性，后者把末期探索压到很低以精调。余弦的"收尾变慢"通常更利于最后阶段的策略抛光，这也是它被广泛使用的经验原因。

数值例子：两种退火在四个进度点的取值

取 αstart=0.4、αend=0.02，逐个代入公式：

1.1 数值算例：退火速率与探索总预算

对两条曲线求导可以比较"退火有多快"。linear 的斜率恒定：每推进 1 个进度单位下降 0.38，摊到 12000 步是每步 3.17×10−5。cosine 的斜率是 0.5(αstart−αend)π·sin(πp)，在 p=0.5 处最大：0.5×0.38×3.1416≈0.597，摊到每步 4.97×10−5，正好是 linear 的 π/2≈1.57 倍；两条曲线在 p=0.5 相交，但斜率并不相同，cosine 以更陡的姿态穿过中点。而 p 趋近 0 或 1 时斜率趋近于 0。也就是说 cosine 把"变化"集中在中间三分之一，两端都接近平台。把平台宽度量一下：p 小于 0.1 时 α 仍在 0.39 以上，p 大于 0.9 时 α 已低于 0.03，两个平台各占预算的一成。

更有意思的是总预算相同。两条曲线的时间平均恰好相等：linear 的平均值是 (0.4+0.02)/2=0.21；cosine 里 (1+cos(πp)) 在 [0,1] 上的积分等于 1，平均值同样是 0.21。折算到 12000 步，两者都花掉约 2520 个"α·步"的探索预算。差别在分布：到 p=0.25 为止，cosine 累计比 linear 多花约 86 个 α·步，这批预算被挪到了最需要探索的前段，末期少花的量恰好补回来。这就是"前慢后快"的算术含义：总预算不变，分配前移。

2. 开环与闭环：一张对照表

维度调度（本章）自动温度（第 032 章）
控制方式开环：α 只是步数 t 的函数闭环：α 由"熵缺口"反馈决定
需要的先验起止值、退火形状、总步数目标熵 H̄
对策略突变的响应无，按表执行有，缺口变大即调整
额外优化器无有（log_alpha）
常见使用场景训练预算固定、经验丰富的任务探索强度难以预估的任务

两者不是互斥的：也可以"调度目标熵、让 alpha 自动追"，把两者的性质组合起来，这正是练习 4 的题目。四种方案的横向对照如下：

方案alpha 轨迹形状需要的先验末期行为典型表现
const水平直线一个常数恒定探索基线，简单可靠
linear匀速下降的直线起止值 + 总步数以固定斜率收敛到终值与基线相当或略好
cosine前慢后快、尾部趋平的弧线起止值 + 总步数平缓贴住终值，利于抛光常略优于基线
auto由熵缺口决定，先升后稳/降目标熵跟随策略的熵水平省去起止值，但需选目标熵

3. 熵会跟着走吗

调度只规定了 alpha，不能直接规定熵。但策略损失里 alpha 乘在 log π 上，alpha 降低会持续减少熵项的梯度压力，策略自然变得更确定；再加上 Q 项一直在推动"挑好的动作"，熵通常呈现与 alpha 同向的下降。如果观察到 alpha 降了而熵不降，一般说明 Q 项太弱（奖励尺度问题）或策略还没学到东西；反过来，熵降得比 alpha 快，通常说明 Q 项过强，策略在过早地收敛。读日志时可以抓一个诀窍：α 是探索的"价格"、熵是成交的"数量"，两者同屏才看得出这一笔交易是否合理，只看回报则只能看到结果、看不到过程。

3.1 失效模式：开环调度对意外没有响应

调度的盲点可以用两个场景量化。场景一，提前学会：如果任务在第 3000 步（p=0.25）就接近解决，linear 仍按表维持 α=0.305、cosine 维持 0.344，末期的小数值探索对已收敛的策略属于持续扰动；自动温度此时会按熵缺口把 α 压到策略实际需要的水平。反过来场景二，训练停滞：若策略在第 6000 步（p=0.5）陷入局部行为，α 已按表降到 0.21 并继续下滑，调度不会回头加探索；闭环方案会因为熵下降、缺口扩大而把 α 抬回去。判断自己的任务属于哪种情况有个简单办法：先跑一次 auto，看它的 α 轨迹在预算半程时高于还是低于 0.21；高于说明任务仍需要探索、调度应放缓退火，低于则相反。这一步把开环时间表与真实学习进度对齐，比照抄论文起止值可靠。

4. 起止值怎么选

起点太大（比如 1.0）会让早期 Q 学习被熵项压住；终点太小（比如 0）会让末期梯度完全被 Q 主导，Pendulum 这类连续控制可能变得敏感。经验区间是起点 0.2～0.5、终点 0.01～0.05。调度对预算长度也敏感：预算从 1.2 万步改成 6 万步，同样的起止值对应的"退火速度"变了四倍，曲线自然不同，这跟第 004 章学习率调度的逻辑完全一致。

把预算敏感性用数字固定下来：在 1.2 万步预算下，cosine 到达 p=0.25 需要 3000 步；同样的 3000 步放到 6 万步预算里只是 p=0.05，alpha 还在 0.39 附近，探索强度几乎是前者的两倍。这意味着"照抄论文的起止值"在换了预算之后往往失效：正确做法是先确定预算，再按"希望第几千步开始快速收敛"反推退火形状。评估点也应该选在相同的进度 p 上；按绝对步数对齐会让两个调度落在不同的训练阶段，结论失去意义。

最后把 SAC 的 α 与 PPO 的熵系数做个对照，避免两边的经验区间混用。PPO 的熵奖励是 +ent_coef·H(π)，H(π) 是离散熵、取值 0 到 log|A|，典型 ent_coef 常落在 0～0.01；SAC 的 α 把熵项乘在 −log π 上，典型区间是 0.02～0.5。两者的熵项在目标函数里的结构相同，但相对量级不同：SAC 的 log π 是连续密度取对数、可以为正为负，α 需要与 |Q| 的量级配平；PPO 的熵奖励则常与归一化后的优势一起使用。跨算法借鉴超参数时，先看"熵项在损失里占多大比重"，再决定数字；把 α=0.2 直接填进 PPO 的 ent_coef，等价于把探索权重放大数倍到数十倍。

实现思路与设计

模块划分

数据流

每步：先设定 alpha（调度模式调 schedule_alpha + set_alpha；auto 模式跳过）→ 策略采样、入池 → update() 内用同一个 current_alpha 计算 TD 目标与策略损失 → auto 模式额外走温度损失一步 → 每 3000 步评估并记录 alpha 与熵轨迹。auto 与调度互斥：两处判定集中在类内部。

与前一章的差异点

  • 第 040 章动的是奖励量表；本章回到 alpha 本身，通过显式时间表设定，不经过梯度。
  • 与第 032 章的对照：那时 alpha 由损失函数学出来，本章由训练循环直接设定；代码里 set_alpha() 与 log_alpha 分支并存且互斥。
  • 新增纯函数 schedule_alpha()，把"控制律"从训练循环里抽出来，方便单独验证与替换。
  • 日志新增熵轨迹列，用于观察 alpha 与熵的联动，回报不再是唯一的观察对象。
互斥纪律：alpha 只能有一个"作者"

调度模式写的是 alpha_value 标量，auto 模式写的是 log_alpha 参数，两者只能有一个在生效。本章把互斥判定收在类内部的两处：set_alpha() 对 auto 直接返回、log_alpha 只在 auto 模式下创建。如果两种机制同时"写作"，alpha 轨迹会无法解释，实验结论作废。更隐蔽的情况是"半互斥"：调度写入了标量，但 auto 分支仍然存在并更新 log_alpha，此时 current_alpha 读的是 log_alpha，标量被悄悄忽略，表面一切正常，实际上时间表完全没有生效。排查方法很直接：在日志里同时打印 alpha_value 与 current_alpha，两者长期不一致就说明读错了来源。

关键代码与解读

片段 1：schedule_alpha，把控制律抽成纯函数

def schedule_alpha(name, step, total, start, end, const):
    """按调度类型计算当前步的 alpha。"""
    progress = min(1.0, step / max(total, 1))     # 进度归一化并封顶
    if name == "const":
        return const                              # 常数基线
    if name == "linear":
        return start + (end - start) * progress   # 匀速退火
    if name == "cosine":
        # 从 start 平滑降到 end：0.5*(1+cos(pi*progress))
        return end + 0.5 * (start - end) * (1.0 + math.cos(math.pi * progress))
    raise ValueError(f"未知调度: {name}")

解读：十二行函数，两种调度，三种性格。（1）progress = min(1.0, step / max(total, 1))：封顶保证超预算调用时 alpha 停在终值而不越界；max(total, 1) 防除零。（2）linear 是严格线性的插值，每个评估点的 alpha 应该连成一条直线，这也是日志自查的依据。（3）cosine 的公式里 0.5·(1+cos(πp)) 在 p=0 时为 1、p=1 时为 0，天然满足端点条件；中段变化最快，两端趋平，"起步慢、中段快、收尾慢"。（4）把控制律写成纯函数（不读任何训练状态、只用传入参数）有两个工程好处：可以单独跑单元测试（给定 step 验算 alpha），也可以把函数替换成指数退火、分段常数而完全不碰训练循环。

片段 2：alpha 的两种"作者"与互斥

        # 只有 auto 模式需要 log_alpha 与独立优化器
        if self.schedule == "auto":
            self.log_alpha = torch.tensor(math.log(alpha), requires_grad=True)
            self.alpha_optimizer = torch.optim.Adam([self.log_alpha], lr=lr)

    @property
    def current_alpha(self):
        if self.schedule == "auto":
            return float(self.log_alpha.exp().item())   # 学出来的
        return self.alpha_value                         # 表定的

    def set_alpha(self, value):
        """训练循环为调度模式设定 alpha。"""
        if self.schedule != "auto":                     # auto 模式拒绝被外部写
            self.alpha_value = float(value)

解读：三处代码回答了"谁有权写 alpha"。（1）构造期决定机制：只有 auto 模式才存在 log_alpha 与它的优化器，调度模式连参数都不创建，杜绝"偷偷学习"的可能。（2）current_alpha 是统一读取口：auto 读学习值、调度读标量。下游的 TD 目标、策略损失、日志都从这里取值，调用方不需要知道机制。（3）set_alpha() 对 auto 直接忽略写入，这是互斥纪律的第二道保险：即使训练循环忘记判断 name != "auto"，auto 模式的 alpha 也不会被时间表覆盖。（4）两种"作者"的实现差异（标量 vs 张量参数）被完整封装在类内，训练循环里只有一行 if name != "auto": agent.set_alpha(...)。

片段 3：训练循环，每步开头先定 alpha

    for step in range(1, args.max_steps + 1):
        # 调度模式：每个环境步先设定当前 alpha
        if name != "auto":
            agent.set_alpha(schedule_alpha(name, step, args.max_steps,
                                           args.alpha_start, args.alpha_end,
                                           args.alpha_const))

        if step <= args.start_steps:
            action = env.action_space.sample()
        else:
            action = agent.act(obs, deterministic=False)

        next_obs, rew, terminated, truncated, _ = env.step(action)
        buf.add(obs, action, rew, next_obs, float(terminated))
        obs = next_obs
        ep_ret += rew

        if buf.size >= args.batch_size:
            last_stats = agent.update(buf.sample(args.batch_size))

解读：alpha 的设定时机是本章最容易写出微妙 bug 的地方。（1）设定放在循环最开头：接下来这一步的动作采样、update() 里的 TD 目标与策略损失都读 current_alpha，因此"本步的全部计算"用的是同一个 alpha，不存在"半步切换"的歧义。（2）如果把设定挪到 update() 之前但采样之后，采样用的还是上一步的 alpha；挪到 update() 之后则更糟，损失与目标跨两个值。这些错位在单次实验里很难察觉，但会污染"alpha 与熵联动"的观测。（3）调度分母用 args.max_steps：如果训练实际只跑到一半（比如改小了预算），退火会整体被拉伸，分母必须是真实的总步数。（4）auto 模式这里完全不调 set_alpha，更新阶段走 log_alpha 分支；两条路互不打扰。

片段 4：update 内部与日志，以 current_alpha 为单一来源

    def update(self, batch):
        obs, act, rew = batch["obs"], batch["act"], batch["rew"]
        next_obs, done = batch["next_obs"], batch["done"]
        alpha = self.current_alpha                 # 本步的唯一 alpha 读数

        with torch.no_grad():
            next_act, next_logp = self.policy.sample(next_obs)
            q_next = torch.min(self.q1_target(next_obs, next_act),
                               self.q2_target(next_obs, next_act))
            target = rew + self.gamma * (1.0 - done) * (q_next - alpha * next_logp)

        # ... 评论家与演员更新略（与 031—040 章一致） ...

        # auto 模式才更新 alpha；调度模式的 alpha 由外部时间表决定
        if self.schedule == "auto":
            alpha_loss = -(self.log_alpha *
                           (logp + self.target_entropy).detach()).mean()
            self.alpha_optimizer.zero_grad()
            alpha_loss.backward()
            self.alpha_optimizer.step()

解读：update() 只做两件与本章相关的事。（1）函数开头把 current_alpha 抓进局部变量 alpha：保证同一次更新里 TD 目标与策略损失用的值完全一致，也方便追踪。auto 模式下这个值来自 log_alpha，调度模式下它是训练循环刚写入的标量，两种来源在这里被统一消费。（2）温度损失的整个分支被 if self.schedule == "auto" 包住：调度模式根本没有 log_alpha 属性，这个分支不会执行（如果误执行会直接 AttributeError，等于把互斥纪律变成硬保证）。（3）日志里同时打印 agent.current_alpha 与熵：cosine 的 alpha 轨迹应该呈现余弦弧，熵应与之同向，这张"双轨迹图"是判断调度是否生效、熵是否跟着动的最快方式。

python code/ch041.py --quick   # 快速跑通：约 1 分钟
python code/ch041.py --schedules linear,cosine,auto --max-steps 20000   # 拉上自动温度做第四组

以实跑为准：linear / cosine 的评估回报通常略好于常数基线（几十到一百分不等，也可能打平）；alpha 轨迹严格按公式走（linear 成直线、cosine 成余弦弧）；熵与 alpha 同向下降。auto 模式省去起止值却要多选目标熵，表现往往介于两者之间。别用单个种子宣判优劣。

常见坑

  • 调度分母与真实预算不一致：用 12000 训练却把 T 写成 20000，退火只走到一半，末端 alpha 停在 0.06，到不了 0.02。修复：分母必须用 args.max_steps。
  • alpha 更新发生在错误的时机：如果在 update() 之后才改 alpha，策略损失与目标值就会用两个不同的值。修复：统一在每步开头设定。
  • auto 与调度同时生效：两套机制都写 alpha 会让轨迹无法解释。修复：保留互斥分支，改代码时别把这条纪律弄丢。
  • 用不同总步数比较不同调度：调度是"进度"的函数，总步数不同意味着时间表不同。修复：所有对照组的 --max-steps 必须一致。
  • alpha_end 设成 0：末期完全没有熵奖励，梯度全由 Q 主导，在连续控制里容易变得敏感甚至不稳定。留一个小正数（0.01～0.05）。

练习与思考

  1. 把 --alpha-end 改成 0.0 和 0.2 各跑一次 cosine，观察末期熵与回报的变化。★
    提示
    终点 0 时末期没有探索压力，策略变得很确定；终点 0.2 时退火几乎没意义。对比最后两个评估点。
  2. 把 --alpha-start 从 0.4 提到 1.0，说明为什么早期评估回报反而可能变差。★
    提示
    熵项压过 Q 项时策略乱动、Q 学习被稀释，参考第 035 章"scale 小则熵相对贵"的等价视角。
  3. 实现指数退火 alpha = alpha_end * (alpha_start/alpha_end)^(1−p) 并加入 --schedules，与 linear / cosine 对比形状差异。★★
    提示
    指数退火前快后慢，与 cosine 的前慢后慢相反。先在 schedule_alpha() 里加分支，再改参数解析的白名单。
  4. 把第 032 章的自动温度改成"调度目标熵"：目标熵从 0 平滑降到 −2，alpha 仍由 log_alpha 学习。跑一组并与纯调度、纯 auto 对比。★★★
    提示
    alpha 损失里的 target_entropy 换成按步数计算的函数即可；这正是闭环与开环的组合方案。
  5. 给 schedule_alpha() 写三个断言测试：p=0 时等于 start、p=1 时等于 end、p=0.5 时 linear 与 cosine 都等于 0.21。不跑训练就能验证公式实现。★
    提示
    直接调用函数传不同 step 值即可。第三个断言依赖 start=0.4、end=0.02 这组参数，换参数时记得同步修改期望值。

小结

  • 熵系数调度用显式时间表控制探索强度，是对训练进度的开环控制，无需额外优化器与目标熵。
  • linear 匀速下降；cosine 前慢后慢、中段快，更利于末期精调；两者都要设定起止值与总步数，四项缺一不可。
  • Pendulum 上调度通常与常数基线相当或略好，真正的差异体现在熵轨迹的可控性上。
  • 与第 032 章的自动温度对照：闭环能自适应但要选目标熵，开环好控制但要选时间表。
  • cosine 的曲线关于中点对称，前段省着花探索预算、后段快速回落并平缓收尾，p=0.5 处与 linear 恰好相交于 0.21（当前参数下）。
  • 调度效果强烈依赖总预算：换了步数预算就要重新审视起止值与退火速度，评估点按进度对齐，绝对步数的对齐会让两组落在不同训练阶段。
