第二篇 · 离策略方法与 SAC

第 049 章：SAC的分布式实现

把"采集"与"学习"拆成两个角色：多个采集线程并行跑环境、往共享回放池里灌数据，主线程当学习器按积压的步数补更新。先测吞吐，再让整条流水线转起来。

  • 主题：分布式 RL 架构 / 生产者-消费者模式
  • 关键公式：吞吐系统 ≈ min(采集吞吐, 学习吞吐 ÷ UTD)
  • 预计学时：60 分钟
  • 前置章节：第 048 章

学习目标

  • 理解"采集器 + 学习器 + 共享回放池"的分布式 RL 标准架构，以及它与单线程训练循环的对应关系。
  • 用 threading 实现线程安全回放池与多采集器，掌握锁粒度的取舍。
  • 测量采集吞吐（steps/s）与 worker 数量的关系，理解 GIL 对 Python 线程加速比的限制。
  • 监控学习器的"更新滞后"，理解 update-to-data（UTD）比在异步系统中的实际含义。
  • 知道教学版（线程）与生产版（多进程/多机）的差别，以及迁移时要改哪几处。

背景与动机

单线程 SAC 循环里，环境交互和梯度更新交替进行：环境步偏 numpy 计算，梯度步偏 torch 计算，两者经常互相空等。网络变大、环境变慢时瓶颈更明显，采集器闲着等更新、学习器闲着等数据。分布式训练把两个角色解耦：采集器只跑环境（可以并行），学习器只从回放池取数据做梯度（可以独占算力）。

这是 SAC 相对 PPO 的又一处工程优势：off-policy 的共享回放池天然是"生产者-消费者"队列，采集与学习不需要严格同步。真实系统（Ape-X、R2D2 类）用数十上百个采集进程配一个或几个学习器。本章用单进程多线程做教学简化：结构、指标、瓶颈都真实，只是把"进程/机器"换成了"线程"。

核心原理

1. 生产者-消费者模型

把回放池看作一条带容量的缓冲区：采集器是生产者，学习器是消费者，双方通过锁互斥访问。系统吞吐由两侧的较小者决定：

吞吐系统 ≈ min( 采集吞吐, 学习吞吐 ÷ UTD ) UTD（update-to-data）= 每条新数据平均触发多少次梯度更新

符号说明：采集吞吐是全体 worker 每秒收集的环境步数；学习吞吐是单机每秒能做的梯度更新次数；UTD 是学习器给自己定的"每步数据补几次更新"（本章取 1，即收集多少步就补多少次）。当采集吞吐超过学习吞吐时，回放池被填满、更新滞后持续增长，学习器成为瓶颈；反之回放池始终很浅、采集器空等。设计目标就是让两侧匹配：调 worker 数、批大小或 UTD。

数值例子：用吞吐公式做一次配平

用一组假设数字走一遍配平计算（以本机实跑为准）。设 4 个采集线程合计能产出约 800 步/秒；学习器每次更新在 CPU 上耗时约 6.7 毫秒，即约 150 次更新/秒；UTD=1。

系统吞吐 ≈ min(800, 150 ÷ 1) = 150 步/秒。也就是说，即使采集器再快，整条流水线也只能按学习器的节奏前进，多余的步数全部堆进回放池。

更新滞后的增长速率约为 800 − 150 = 650 步/秒：10 秒后滞后约 6500 步，回放池很快被填满。日志里看到"滞后持续增大 + 回放池满"，就是学习器成为瓶颈的签名。

配平方案一：把 UTD 降到 0.2（每收集 5 步数据补 1 次更新），系统吞吐变成 min(800, 150÷0.2) = min(800, 750) = 750 步/秒，两侧接近平衡；代价是每条数据平均被学习的次数变少，样本效率需要重新评估。配平方案二：减少采集线程到 2 个，采集吞吐降到约 450 步/秒，仍高于 150，说明这台机器上学习器才是真正的稀缺资源，加采集器只会加剧积压。解读：先用吞吐基准测出两侧的原始能力，再用 UTD 与 worker 数把两者对齐，比盲目堆 worker 有效得多。

2. 同步与异步

  • 同步式：所有采集器用同一版本参数采完一批，学习器更新后一起分发新参数。偏差小、易调试，但每轮最慢的 worker 决定整体速度。
  • 异步式：每个采集器自由推进，随时用最新参数（或周期性拉取）。吞吐高，但数据来自不同版本的策略，回放池里混着"过时经验"，需要重要性修正或容忍偏差。

2.1 三种组织方式的对照

维度单线程交替同步式并行异步式并行（本章）
结构采集与更新交替执行所有采集器同版本参数，采完一轮再更新各采集器自由推进，学习器按积压补更新
吞吐上限两者互相空等，最低受最慢 worker 约束由两侧较小者决定，可满负荷
数据偏差无无有：回放池混着不同版本的策略数据
实现复杂度最低中：需要屏障与参数分发高：锁、停止标志、滞后监控
适用场景小任务、调试对可复现性要求高时吞吐优先的大规模训练

对照的结论是"按目标选结构"：本章的教学实现选择了异步式的骨架（共享回放池 + 积压驱动），因为它最贴近真实分布式系统；若把可复现性放在第一位，同步式更合适，代价是吞吐被最慢的采集器拖住。

3. 为什么线程版只是教学

CPython 的 GIL 让同一时刻只有一个线程执行字节码。numpy 与 torch 的底层 C 运算在多数情况下会释放 GIL，所以环境步进与网络前向能获得一定并行度；但 Python 层的循环、锁竞争、事件查询仍然串行。因此线程版加速比通常在 1.3×～2.5×，远低于 4 个线程的理想线性加速。真实部署用多进程绕开 GIL，代价是参数与数据需要序列化或共享内存。本章额外设 torch.set_num_threads(1)，避免 torch 内部线程池和采集线程抢核。

从线程版迁移到进程版，需要改动的其实是三处：其一，共享回放池从"内存共享 + 锁"改为"每进程本地池 + 定期向主进程传输"，传输内容就是 (s, a, r, s′, done) 五元组，序列化开销成为新的成本项；其二，策略参数的同步从"隐式共享"变为"显式广播"，采集进程要么周期性拉取最新参数，要么接受参数延迟（真正的异步算法就是后者）；其三，统计量（总步数、回合回报）不能再靠共享字典，需要汇总通道。三处改完，架构就从"教学版"升级为"可横向扩展版"，算法逻辑一行不用动。

实现思路与设计

数据流

运行分两个阶段。阶段一（吞吐基准）：用纯随机动作测量 1 与 W 个采集器的 steps/s，不涉及学习，单独启停线程。阶段二（训练）：启动 W 个采集线程（每个独立环境、共享策略与回放池），主线程扮演学习器，每轮读取总步数、计算积压、最多补 64 次更新后 look 循环；每 2000 步评估并打印吞吐、回放池大小与"更新滞后"。结束后停线程、汇总结论。

模块划分

组件职责关键点
SharedReplay带锁的环形回放池add 与 sample 都在锁内完成；sample 里 .copy() 防止采样后数组被覆写
collector_worker每线程一个环境，策略采样并写池每 20 步检查一次停止标志；回合回报写进共享 stats
benchmark_throughput纯随机动作测量 1 vs W 个采集器的 steps/s与训练逻辑解耦
学习器主循环按积压步数补更新，定期评估每轮最多补 64 次更新，避免长时间占住 GIL

关键超参数

参数默认值作用与取值理由
--workers4采集线程数；与 CPU 核数和环境开销相关
--bench-workers1,4吞吐基准的对照点
--bench-steps1500每个采集器在基准阶段的步数，避免测得太短噪声大
--start-steps1000随机探索预算，按 worker 数均分给各线程
--max-steps16000训练阶段总步数上限；评估按总步数触发
--buffer-size / --batch-size100000 / 256与前面章节一致，保证回放池够深、批量稳定

两个阶段的划分还有一个测试方法上的好处：吞吐基准用纯随机动作，完全不依赖学习器的状态，因此可以单独复现、单独比较机器性能；训练阶段的吞吐则混着锁竞争与 GIL 调度，两者相减才能估算"学习器抢走了多少采集能力"。若训练吞吐远低于基准吞吐，说明竞争开销显著，此时优先调小学习器的每轮更新上限或减少 worker 数，把环境本身太慢的嫌疑放在最后。

与前一章的差异点

  • 前几章都是"单线程采样循环"；本章把采集循环搬进 --workers 个线程，新增共享回放池与生产者-消费者协调。
  • 新增吞吐基准阶段与"更新滞后"指标，这是分布式系统独有的观测量。
  • 回放池从无锁单线程结构变成带锁结构，sample 增加 .copy() 保证线程安全。
  • 固定 torch.set_num_threads(1)，让吞吐对比不受 torch 内部并行度干扰。

关键代码与解读

片段 1：一把锁保护的回放池

class SharedReplay:
    """用一把锁保护的环形回放池：写入与采样都串行化，保证线程安全。"""

    def __init__(self, capacity: int, obs_dim: int, act_dim: int):
        self.capacity = capacity
        self.obs = np.zeros((capacity, obs_dim), dtype=np.float32)
        self.next_obs = np.zeros((capacity, obs_dim), dtype=np.float32)
        self.act = np.zeros((capacity, act_dim), dtype=np.float32)
        self.rew = np.zeros((capacity, 1), dtype=np.float32)
        self.done = np.zeros((capacity, 1), dtype=np.float32)
        self.ptr = 0
        self.size = 0
        self.lock = threading.Lock()         # 全部读写都在这一把锁内完成

    def add(self, obs, act, rew, next_obs, done) -> None:
        with self.lock:
            i = self.ptr                     # 临界区只有 5 次数组赋值，极短
            self.obs[i] = obs
            self.act[i] = act
            self.rew[i] = rew
            self.next_obs[i] = next_obs
            self.done[i] = done
            self.ptr = (self.ptr + 1) % self.capacity
            self.size = min(self.size + 1, self.capacity)

    def sample(self, batch_size: int) -> dict:
        with self.lock:
            idx = np.random.randint(0, self.size, size=batch_size)
            return {                         # .copy()：离开锁后数据也不会被环形覆写
                "obs": torch.as_tensor(self.obs[idx].copy()),
                "act": torch.as_tensor(self.act[idx].copy()),
                "rew": torch.as_tensor(self.rew[idx].copy()),
                "next_obs": torch.as_tensor(self.next_obs[idx].copy()),
                "done": torch.as_tensor(self.done[idx].copy()),
            }

解读：（1）锁的粒度是设计的核心：add 临界区只有 5 次数组赋值（微秒级），sample 在锁内完成索引抽样与拷贝，绝不能在持锁期间做 torch 前向或优化器更新，否则采集器会被阻塞到秒级。（2）.copy() 不能省：self.obs[idx] 本身是副本，但一旦有人把接口改成切片 self.obs[a:b] 就会返回视图，环形覆写会让训练"边训边变"。显式拷贝是防御性写法。（3）返回的已经是 torch 张量，学习器拿到即可用；rolling buffer 的 size 与 ptr 都在锁内维护，读到的状态永远自洽。

片段 2：采集线程，每 20 步看一眼停止标志

def collector_worker(worker_id: int, env_id: str, seed: int, agent: SAC,
                     buffer: SharedReplay, stats: dict, args,
                     stop_event: threading.Event) -> None:
    """单个采集器：独立环境 + 共享策略 + 共享回放池。"""
    env = make_env(env_id, seed + worker_id * 1000)      # 每个 worker 独立种子
    obs, _ = env.reset(seed=seed + worker_id * 1000)
    ep_ret = 0.0
    local_steps = 0
    random_steps = max(args.start_steps // max(args.workers, 1), 10)

    while not stop_event.is_set():
        # 每 20 步检查一次停止标志，减少事件查询开销
        for _ in range(20):
            if stop_event.is_set():
                break
            if local_steps < random_steps:
                action = env.action_space.sample()       # 预热期随机探索
            else:
                action = agent.act(obs, deterministic=False)  # no_grad 推理
            next_obs, rew, terminated, truncated, _ = env.step(action)
            buffer.add(obs, action, rew, next_obs, float(terminated))
            obs = next_obs
            ep_ret += rew
            local_steps += 1
            with stats["lock"]:
                stats["total_steps"] += 1                # 学习器靠它判断预算
                if terminated or truncated:
                    stats["ep_returns"].append(ep_ret)
                    ep_ret = 0.0
            if terminated or truncated:
                obs, _ = env.reset()
                ep_ret = 0.0

解读：（1）每个 worker 用 seed + worker_id * 1000 的独立种子，保证轨迹多样、互不重合。（2）内层 for 循环一次跑 20 步再查 stop_event：事件查询本身有开销，逐站查询会拖慢采集，20 步是一个实测舒服的折中。（3）策略推理走 agent.act（内部 no_grad）且不加锁：多线程共享同一份参数做前向，在 torch 下是安全的读操作，这也是"共享策略"能用内存换性能的地方。（4）total_steps 与 ep_returns 的写入都在 stats["lock"] 内，统计量也必须线程安全，否则计数器会丢更新。（5）注意 reset 与 ep_ret 清零做了两次（锁内记录、锁外复位），顺序不能乱。

片段 3：学习器按"积压"打工，不抢 GIL

    n_updates = 0
    last_steps = 0
    next_eval_at = args.eval_every

    while stats["total_steps"] < args.max_steps:
        with stats["lock"]:
            total = stats["total_steps"]
        # 学习器节奏：新收集多少步，就补多少次更新（update-to-data ≈ 1）
        backlog = total - last_steps
        if buffer.size >= max(args.start_steps, args.batch_size) and backlog > 0:
            n_todo = min(backlog, 64)  # 每次循环最多补 64 次，避免长时间占住 GIL
            for _ in range(n_todo):
                agent.update(buffer.sample(args.batch_size), args)
                n_updates += 1
            last_steps += n_todo
        else:
            time.sleep(0.002)  # 数据不够时让出 CPU 给采集线程

        if total >= next_eval_at:
            eval_ret = evaluate(agent, env, args.eval_episodes)
            eval_returns.append(eval_ret)
            elapsed = time.time() - t_start
            print(f"[学习器] 步数 {total:6d} | 更新 {n_updates:6d} | 回放池 {buffer.size:6d} | "
                  f"吞吐 {total / elapsed:7.1f} steps/s | 评估 {eval_ret:8.1f} | "
                  f"更新滞后 {total - last_steps:5d}")
            while next_eval_at <= total:
                next_eval_at += args.eval_every

解读：（1）backlog = total − last_steps 就是"更新滞后"：环境已经收集了多少步、学习器还没补的账。它与 UTD 的关系是：每轮把 backlog 消化掉一部分，长期均值反映两侧速率的差。（2）n_todo = min(backlog, 64) 是本章最重要的工程细节：没有这个上限，学习器会一口气跑几百次更新、长时间占住 GIL，采集线程几近停摆，吞吐反而崩掉。（3）数据不够时 time.sleep(0.002) 主动让出 CPU，这是 Python 线程协作的礼节，比空转 loop 友善得多。（4）评估在主线程做（复用训练环境对象），评估间隔用 next_eval_at 累加推进，跨多个评估点时 while 循环一次补足，避免漏评。

预期：纯采集吞吐随 worker 数提升，但加速比低于线性（约 1.5×～2.5×），这是 GIL 与锁竞争的真实代价；学习器吞吐低于纯采集，"更新滞后"稳定在几百到上千步，回放池持续被填满；评估回报曲线照常爬升，说明异步采集不影响学习正确性。以实跑为准，不同机器的核数与调度差异会让数字波动。

常见坑

  • 采样返回的数组是池内视图：花式索引 self.obs[idx] 会返回副本、看似安全；改成切片就变成视图，环形覆写让训练数据"边训边变"。统一显式 .copy() 最省心。
  • 持锁做 torch 前向：把 agent.update 包进锁里，采集器全部饿死。锁只保护共享数据结构的读写，计算一律放锁外。
  • 忘记 torch.set_num_threads(1)：torch 默认按核数开内部线程，与采集线程严重超订，吞吐可能反而比单线程低。
  • 退出时没设 daemon=True 或不 join(timeout)：某个 worker 卡在环境步里时主程序无法退出。daemon 线程 + 超时 join 是常见兜底组合。
  • 学习器一次补太多更新：没有 64 次上限，主线程长时间占住 GIL，采集吞吐骤降；日志上表现为"吞吐越来越低 + 滞后越来越大"同时出现。

练习与思考

  1. 把 --bench-workers 改成 1,2,4,8，画出吞吐-采集器数量曲线。它从哪一点开始不再增长？★
    提示
    只改参数。Pendulum 的 step 极轻，GIL 与调度开销占比高，观察加速比的边际收益，通常在 4 个采集器之后就迅速变小。
  2. 把学习器每轮的更新上限从 64 改成 512，跑到结束。预测"更新滞后"与吞吐的变化，再验证。★★
    提示
    上限越大，主线程一次占住 GIL 越久，采集线程被饿住，吞吐反而可能下降。对比修改前后的 steps/s 与滞后均值。
  3. 让每个采集器维护"本地策略副本"：worker 每 500 步从共享策略 load_state_dict 复制一次，其余时间用本地副本推理。这引入参数延迟，观察评估回报的变化。★★
    提示
    本地副本可用 copy.deepcopy(agent.policy)，推理时不受主线程更新影响。真正异步系统（Ape-X）就这样工作；延迟过大时早期评估回报会变差。
  4. 把共享回放池改成 collections.deque(maxlen=N) 加读写分离的两把锁，对比吞吐与代码复杂度。★★★
    提示
    deque 的 append 是 O(1)，但随机访问 deque[i] 是 O(n)，采样要先转 list，这是"数据结构选型影响吞吐"的实例。实测对比后你会更理解 numpy 环形数组的设计动机。
  5. 用 multiprocessing 把采集器改成两个进程（环境与推理在子进程，回放池用管道传输），与本实现对比吞吐，解释进程方案为什么能突破 GIL。★★★
    提示
    子进程各自初始化环境与策略，通信只传 (s,a,r,s′,done) 五元组；Windows 下 spawn 需要 if __name__ == "__main__" 保护与可序列化函数。目标在于测出"进程数 2 的吞吐是否超过线程数 4"，不必写出完整版实现。

小结

  • 分布式 SAC 的标准结构是生产者（采集器）/ 消费者（学习器）+ 共享回放池，off-policy 特性让它天然适合这种解耦。
  • 系统吞吐由两侧的较小者决定，UTD 与 worker 数量是配平速率的主旋钮；"更新滞后"是判断瓶颈在哪里的直接指标。
  • 本章实现完成了线程安全池、多采集器、积压驱动的学习器与吞吐基准；加速比低于线性是 GIL 的真实代价。
  • 异步采集不改变 SAC 的算法正确性，但真实系统要注意参数版本延迟带来的分布偏差。
  • 配平计算是本章的决策工具：系统吞吐 = min(采集, 学习 ÷ UTD)，滞后增长速率 = 采集 − 学习 ÷ UTD；两个式子就能判断该加 worker 还是该降 UTD。
  • 从线程到进程的迁移只动三处：回放池传输方式、参数广播方式、统计汇总方式；算法核心不需要任何修改。
  • 瓶颈的读法：滞后持续增大说明学习器落后，滞后长期接近 0 说明采集器供不上；两种情形对应完全相反的调参方向。
