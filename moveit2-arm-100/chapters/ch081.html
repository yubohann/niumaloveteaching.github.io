第 081 章：客户端调用模式：Client 接口

MoveIt2 的能力以服务（Service）与动作（Action）暴露，本章从通信语义出发，讲清客户端（Client）在等待、超时、取消与并发四类场景下的正确调用模式，并解释代码为何这样组织。

  • 主题：接口调用 / 客户端编程模型
  • 关键机制：请求应答语义、目标反馈结果语义、Future 与回调链、执行器与回调组
  • 预计学时：50 分钟
  • 前置章节：第 080 章

学习目标

  • 理解服务（Service）与动作（Action）的通信语义差异：请求应答、目标反馈结果、可取消性与生命周期。
  • 掌握 rclpy 与 rclcpp 中客户端（Client）的异步调用模型：未来对象（Future）、回调链、目标句柄（Goal Handle）。
  • 会用同步等待与异步回调两种风格调用 MoveIt2 的 /move_action、/compute_ik、/apply_planning_scene 等接口。
  • 能设计带截止时间（Deadline）、取消（Cancel）与重试（Retry）的调用封装。
  • 会识别死锁与假并发两类典型错误，并能解释执行器（Executor）与回调组（Callback Group）的作用。

背景与动机

MoveIt2 把规划能力集中在 move_group 节点，对外暴露一组动作与服务端点；用户程序站在客户端一侧调用它们完成任务。调用模式决定了系统在阻塞、超时、取消与并发请求下的行为，选错模式会让上层逻辑在压力下失效。

最常见的困惑来自两处：其一，ROS2 客户端的底层模型是异步的，"同步调用"只是对等待过程的封装；其二，等待发生的线程与回调执行的线程同属一个执行器时，等待可能反过来阻塞回调本身，形成自锁。本章把这两个机制讲透，并给出可直接套用的调用封装。

上一章剖析了服务端一侧的架构（Action Server 与 Service Server 如何组织），本章聚焦客户端一侧的对称问题：如何让调用语义、并发模型与任务需求匹配。

核心原理

1. 三种通信语义：话题、服务、动作

ROS2 的通信原语按语义分为三类，客户端编程的第一步是选对语义。选择依据是任务是否可长时运行、是否需要中间反馈、是否允许取消。

原语交互形态中间反馈可取消MoveIt2 中的典型用途
话题（Topic）持续发布/订阅，无配对应答无不适用关节状态、规划场景监视、轨迹显示
服务（Service）一次请求对应一次应答无不适用IK 查询、场景查询、场景差分应用
动作（Action）目标、反馈流、最终结果三段式有有规划与执行（move_action）、轨迹执行

动作在服务之上增加两层语义：中间反馈让调用者能观察任务进度，取消机制让长时任务可以被叫停。规划的耗时分布很宽（数十毫秒到数秒），取消能力对抢占式任务调度至关重要，因此规划与执行走动作语义，短查询走服务语义。

2. 客户端调用时序与 Future 模型

无论服务还是动作，ROS2 客户端的发送调用立即返回一个未来对象（rclpy 的 Future、rclcpp 的 SharedFuture），结果稍后由执行器在回调中填入。"同步调用"是通过循环等待这个对象完成的封装，等待期间调用线程被占用。

T完成 = T传输 + T排队 + T求解 + T回传 超时阈值必须覆盖四项之和；只放大求解预算无法补偿网络与排队开销

动作调用比服务多一层：第一次 Future 返回的是目标句柄（Goal Handle），表示服务器是否接受目标；第二次 Future 才返回最终结果。取消请求同样通过目标句柄发出，并且是请求语义，服务器在内部检查点响应，响应延迟取决于检查点间距。

动作调用 = send_goal_async → Future目标句柄 → get_result_async → Future结果 取消路径独立于结果路径：cancel_goal_async 与结果返回可能先后到达，最终状态以结果内的状态字段为准

3. 执行器、回调组与自锁

回调由执行器（Executor）调度。单线程执行器（SingleThreadedExecutor）串行执行所有回调；多线程执行器（MultiThreadedExecutor）按回调组（Callback Group）的约束并行化。默认回调组是互斥的（Mutually Exclusive），同一组的两个回调永不并发。

由此产生一个典型自锁：在某个回调中阻塞等待一个需要同组回调来完成填值的 Future，等待线程占住了组内唯一的执行机会，填值回调永远排不上，系统停死。修复路径有三条：把后续逻辑写进回调链（推荐，保持异步）；把等待放进独立线程；把等待与填值拆到不同回调组并启用多线程执行器。并发下限可以这样估算：

N线程 ≥ N同时阻塞等待 + 1 同时有 3 处阻塞等待时，单线程执行器必然停摆；多线程执行器下还需保证等待与填值不在同一互斥组

4. 超时、取消与状态一致性

超时表示调用者放弃等待，不表示服务器停止工作。规划目标在超时后可能仍在求解，轨迹可能仍被执行。正确的超时处理顺序是：发出取消请求、等待取消确认、重新同步机器人状态与规划场景。跳过第三步会让下一轮调用基于过期状态做决策。

实现思路与设计

设计客户端模块时，先做接口清点，再定并发结构，最后写调用封装，三步的顺序不能颠倒。接口清点回答"用哪个端点"，并发结构回答"等待放在哪"，调用封装回答"失败怎么办"。

1. 接口清点：MoveIt2 常用客户端端点

端点类型语义典型调用开销量级
/move_action动作规划，或规划加执行0.5–5 s（含求解预算）
/execute_trajectory动作执行一条给定轨迹由轨迹时长决定
/compute_ik服务单点逆解查询毫秒级到 50 ms
/get_planning_scene服务拉取当前场景快照与场景规模成正比
/apply_planning_scene服务提交场景差分毫秒级
/clear_octomap服务清空八叉树占用数据毫秒级

清点表的用途是分配等待预算：查询类端点适合短超时同步调用，任务类端点适合异步链式回调。

2. 并发结构：三种可选模型

  1. 单线程串行模型：一个执行器，一次只跑一个任务，调用之间顺序等待。实现最简单，适合教学与单臂单任务场景。
  2. 回调链模型：发送目标后立即返回，结果处理写进回调，主线程继续响应其它事件。适合界面程序与需要随时响应取消的编排器。
  3. 多线程模型：规划线程与状态监视线程分离，用互斥量保护共享状态；等待与回调组分离，避免自锁。适合同时维护多个调用乃至多机械臂的场景。
设计决策：为什么推荐回调链优先于加大线程数？

回调链把"等待"从事务中移除，状态转换全部发生在事件到达时，天然具备可取消性；增大线程数只是把自锁风险摊薄，阻塞等待仍在浪费线程资源，且共享状态的加锁复杂度上升。只有当上层框架本身要求阻塞式接口（例如顺序脚本）时，才用独立线程承载阻塞等待。

3. 调用封装：截止时间、取消、重试

封装目标是把"发送、等待、检查、清理"四件事绑定为一次原子操作。每次调用至少携带三项信息：截止时间、取消策略、结果错误码分类。重试只对可恢复错误生效，分类依据在第 094 章展开；本章先固定方法：错误码到动作的映射表放在封装内部，调用方只看到成功或异常。

与上一章的差异点：第 080 章从服务器视角划分端点职责与执行线程，本章从调用方视角补充等待与取消的对称义务，两者共同构成完整的接口契约。

关键代码与解读

片段 1：服务客户端的同步风格调用（逆解查询）

import rclpy
from rclpy.node import Node
from moveit_msgs.srv import GetPositionIK
from geometry_msgs.msg import PoseStamped


def query_ik(node: Node, pose: PoseStamped):
    """同步风格调用 /compute_ik：阻塞当前线程直到响应或超时。"""
    # 客户端对象可复用，这里为突出流程在函数内创建；频繁调用时应提升为成员
    client = node.create_client(GetPositionIK, "/compute_ik")
    # 服务器未就绪时直接失败，避免调用请求石沉大海后陷入无限等待
    if not client.wait_for_service(timeout_sec=2.0):
        return None
    req = GetPositionIK.Request()
    req.ik_request.group_name = "arm"          # 规划组决定用哪套运动学求解器
    req.ik_request.pose_stamped = pose         # 目标位姿必须带参考系信息
    req.ik_request.avoid_collisions = True     # 让查询与规划阶段使用一致的碰撞语义
    req.ik_request.timeout.sec = 0             # 0 表示采用求解器默认时间预算
    # ROS2 客户端没有阻塞式 call，call_async 返回 Future 才是底层真实模型
    future = client.call_async(req)
    rclpy.spin_until_future_complete(node, future, timeout_sec=1.0)
    if not future.done():                      # 超时返回：此时请求可能仍在服务端处理
        return None
    response = future.result()
    # 通信成功不等于求解成功：必须检查 error_code 再取解
    if response.error_code.val != 1:
        return None
    return response.solution.joint_state

解读：这段代码展示了"同步是封装的异步"。关键设计有三处：（1）wait_for_service 先确认端点可用，把不可达错误暴露在调用点上；（2）超时值分开设置，服务发现等待、求解预算、调用者等待三层预算互不替代；（3）通信层面的完成与业务层面的成功分开判断。需要强调的是，在需要取消的场合，服务语义没有取消通道，此类接口应保持短耗时，长耗时任务改用动作端点。

片段 2：动作客户端的回调链与取消（规划请求）

import rclpy
from rclpy.action import ActionClient
from rclpy.node import Node
from moveit_msgs.action import MoveGroup


class PlanClient(Node):
    def __init__(self):
        super().__init__("plan_client")
        # 只创建客户端对象；服务器可能在之后才启动，等待放在真正发送的时刻
        self._client = ActionClient(self, MoveGroup, "/move_action")
    def send(self, request, feedback_cb, result_cb):
        # 显式确认服务器可用，否则目标会被丢弃且没有任何提示
        if not self._client.wait_for_server(timeout_sec=3.0):
            raise RuntimeError("move_action 不可达")
        goal = MoveGroup.Goal()
        goal.request = request             # 动作目标内嵌规划请求消息
        # send_goal_async 立即返回 Future；回调链承担等待职责，调用线程即刻释放
        future = self._client.send_goal_async(
            goal, feedback_callback=feedback_cb)
        future.add_done_callback(self._on_goal_accepted)
    def _on_goal_accepted(self, future):
        handle = future.result()
        if not handle.accepted:
            self.get_logger().warn("目标被拒绝：检查规划组名与当前状态")
            return
        # 目标句柄保留引用，后续取消操作依赖它
        self._handle = handle
        result_future = handle.get_result_async()
        result_future.add_done_callback(self._on_result)
    def _on_result(self, future):
        wrapped = future.result()
        # 结果消息把业务结果嵌套在 result 字段中，错误码反映规划成败
        code = wrapped.result.error_code.val
        self.get_logger().info(f"规划结果错误码: {code}")

    def cancel(self):
        # 取消是请求语义：服务器在内部检查点响应，可能与结果同时到达
        if getattr(self, "_handle", None) is not None:
            self._handle.cancel_goal_async()

解读：回调链把一次动作调用拆成"发送、接受确认、结果到达"三个事件，每个事件只做局部状态转换，没有任何一处阻塞等待，因此取消与并发天然可行。设计细节上：目标句柄必须保存，取消依赖它；拒绝分支要在接受确认阶段处理，因为此后不再有独立的机会区分"未接受"与"执行失败"。若回调中需要发起下一次规划，直接在新回调内发送即可，形成事件驱动的调用序列。

片段 3：C++ 动作客户端的关键结构（发送选项与回调）

#include <rclcpp/rclcpp.hpp>
#include <rclcpp_action/rclcpp_action.hpp>
#include <moveit_msgs/action/move_group.hpp>

class PlanClient : public rclcpp::Node {
 public:
  using MoveGroup = moveit_msgs::action::MoveGroup;

  PlanClient() : Node("plan_client") {
    // 动作客户端按类型实例化；执行器通常由上层组合决定
    client_ = rclcpp_action::create_client<MoveGroup>(this, "/move_action");
    // 等待是带返回值的操作：失败时给出明确错误，进入恢复路径
    if (!client_->wait_for_action_server(std::chrono::seconds(3))) {
      RCLCPP_ERROR(get_logger(), "move_action 未就绪");
    }
  }

  void send(const MoveGroup::Goal& goal) {
    auto options = rclcpp_action::Client<MoveGroup>::SendGoalOptions();
    // 反馈回调用于进度观测：只做记录与转发，不做阻塞操作
    options.feedback_callback = [](auto, const auto feedback) {
      RCLCPP_INFO(rclcpp::get_logger("plan"), "状态: %s",
                  feedback->state.c_str());
    };
    // 结果回调负责业务判断：通信成功之后仍要检查错误码
    options.result_callback = [](const auto& wrapped) {
      RCLCPP_INFO(rclcpp::get_logger("plan"), "错误码: %d",
                  wrapped.result->error_code.val);
    };
    client_->async_send_goal(goal, options);
  }

 private:
  rclcpp_action::Client<MoveGroup>::SharedPtr client_;
};

解读：C++ 客户端把三段回调打包进发送选项（SendGoalOptions），与 Python 版相比多了编译期类型检查。反馈回调只允许做轻量操作，任何阻塞都会占用执行器线程；结果回调承担业务判断，错误码字段的嵌套层级（结果的 result 字段内再取 error_code）来自动作定义本身，读代码时要按消息定义逐层核对。Lambda 捕获采用空捕获配合日志器单例，避免把节点生命周期与回调强绑定，这在多线程执行器下更安全。

常见坑

  • 回调内阻塞等待：在默认互斥回调组的回调里调用 spin_until_future_complete 或等结果 Future，形成自锁，表现为整个节点无响应。修复：改为回调链；或把阻塞等待移入独立线程，并启用多线程执行器。
  • 未确认服务器可用：目标在服务器未发现时被静默丢弃，日志里没有错误。修复：发送前调用 wait_for_action_server 或 wait_for_service，失败进入明确的重试分支。
  • 通信成功即判定业务成功：动作结果到达不代表规划成功，错误码可能指示碰撞、超时或组名无效。修复：统一在结果回调中检查 error_code.val，按分类映射到恢复动作。
  • 取消语义误解：把取消当作立即停止，未等待取消确认就复用机器人状态。修复：取消后等待结果状态字段变为取消或成功，并重新同步状态与场景再发新目标。
  • 超时后未做清理：调用方超时返回，服务器侧规划仍在消耗计算资源，后续请求排队。修复：超时路径必须携带取消请求，且超时值按"传输加排队加求解"估算；只按求解预算设置会漏掉传输与排队开销。

练习与思考

  1. 把片段 2 中的回调链改为"发送后在主循环里等待结果"，分别用单线程与多线程执行器运行，预测两种配置下取消功能的行为差异。★
    提示
    单线程执行器下等待占用唯一执行机会，取消请求的回调无法被处理；多线程执行器下取消可行，但共享状态需要加锁。说明等待位置决定可取消性。
  2. 为 /compute_ik 设计一个带缓存与限流的封装：同一目标位姿在短窗口内重复查询直接返回缓存，并说明缓存失效条件。★★
    提示
    缓存键包含规划组、目标位姿与碰撞开关；机器人状态或场景变化后缓存必须失效，因此缓存键还要绑定场景版本或状态时间戳。
  3. 推导：一个节点同时发起 3 个规划目标的异步调用，全部走回调链。给出需要的最小执行器线程数，并说明若反馈回调里做可视化计算（耗时较长）时该如何处理。★★
    提示
    回调链不阻塞等待，单线程即可维持多目标状态机；但长耗时反馈处理会串行挤压其它目标的回调，应把可视化计算放入独立回调组或独立线程队列。
  4. 改参数并预测：把 wait_for_server 超时从 3 s 改为 0.5 s，在服务器启动较慢的场景中系统行为如何变化？给出两种合理的工程对策。★★
    提示
    缩短等待会把"服务器未就绪"提前暴露为调用失败，行为从长时间挂起变为快速失败；对策包括带退避的重试队列、把调用推迟到服务器就绪事件之后。
  5. 设计一个调用状态机，覆盖 PREEMPTED 与 CANCELED 两种结束状态的区别，并说明编排器在两种情况下各自应做什么。★★★
    提示
    PREEMPTED 通常由更高优先级目标抢占触发，原任务可考虑延后重发；CANCELED 由调用方主动取消，应丢弃任务或转入补偿逻辑。两者都需要重新同步状态。

小结

  • 服务适合短查询，动作适合长任务；动作语义的核心增量是中间反馈与可取消性。
  • ROS2 客户端的底层模型是异步的，同步调用是封装出的阻塞等待；等待位置决定可取消性与死锁风险。
  • 执行器与回调组决定并发：默认互斥组内不得阻塞等待，回调链是推荐结构。
  • 超时处理必须包含取消与状态重新同步，通信成功与业务成功分开判断。
