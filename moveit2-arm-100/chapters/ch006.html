第 006 章：编写第一个 MoveIt2 Python 脚本

本章把图形界面的操作翻译成可重复的程序：用官方 Python 接口初始化规划组件，设置目标，规划、检查并执行一条轨迹。

  • 主题：Python 接口 / 首个规划程序
  • 关键机制：moveit_py 初始化、规划组件（Planning Component）、规划结果检查
  • 预计学时：55 分钟
  • 前置章节：第 005 章

学习目标

  • 理解 MoveIt2 官方 Python 接口（moveit_py）的初始化流程与参数装载链路。
  • 掌握"设置目标、规划、检查结果、执行"四步骨架，能独立写出并运行最小脚本。
  • 理解脚本的进程内规划形态与独立 move_group 进程的关系，能说明两者的取舍。
  • 会在代码中显式声明起始状态，并读取规划结果的错误信息进行分支处理。
  • 能把脚本参数化，用启动文件注入配置，为后续章节的可复用工具打基础。

背景与动机

图形界面的交互无法被复用：每次验证同样的动作，都要重复点击步骤；批量实验、参数扫描、回归测试这些需求，界面都无法承载。把规划写成程序之后，一次调试过的流程可以反复执行，参数变成变量，结果变成可统计的数据。

第一个脚本的目标不在功能复杂度，而在完整走通"配置装载、请求构造、结果判定"的链条：脚本能规划成功，说明描述、语义、规划管线、运动学这些配置对程序同样可见；脚本能执行成功，说明控制器侧就绪。本章的程序是后续所有章节的模板：后续只是在目标形式、参数与结果处理上逐步加深。

核心原理

本节解释 Python 接口的两个关键概念：进程内的规划组件架构，以及规划请求分段的生命周期。

1. 进程内规划：moveit_py 的部署形态

官方 Python 接口在进程内直接构建规划能力：初始化时读取机器人描述与规划管线配置，在本地建立规划场景管理、规划管线加载与执行转发的完整机制。与"独立 move_group 进程加客户端"的部署相比，两者面向同一套底层库，差别在进程边界。

维度进程内（moveit_py）进程外（动作客户端）
通信开销无序列化，直接函数调用动作消息序列化与网络往返
场景数据访问可直接读取本进程的场景对象只能通过服务与话题获取快照
资源占用每个脚本进程一份模型与场景共享服务端一份场景
适用场景原型、批量实验、算法开发多客户端共享服务、系统集成

取舍的依据是"场景归属"：需要频繁读写场景做算法研发时用进程内形态；多个任务共享同一世界模型时用进程外形态。本课程 006 至 012 章用进程内形态建立行为直觉，013 章之后引入进程外接口的完整对比。

2. 规划组件：组名是接口的入口

接口以规划组件为操作单位：按 SRDF 中的组名取到组件，组件的目标状态、起始状态、规划与执行都以该组为范围。组件的状态模型很简单：设置起始状态，设置目标状态，调用规划。规划不修改任何状态，结果作为返回值交付。

组件状态 = (起始状态, 目标状态)，plan() 不改变状态，仅返回轨迹 起始状态默认取当前状态；显式声明起始状态是批处理场景的标准做法

起始状态默认跟随机器人当前状态，即来自关节状态与场景监视的实时数据。脚本连续规划多段时，如果不等待执行完成，下一段规划的起始状态仍然停留在旧值上，可能规划出与执行序列不一致的轨迹。起始状态的处理是第一个脚本就应养成的严谨习惯：要么显式等待执行，要么显式设置起始状态。第 009 章会展开状态表示，本章先把它当作规划的输入参数对待。

3. 请求生命周期：四步骨架

脚本的动作序列对应规划请求的四个阶段：

  1. 构造目标：把"想去的位姿"表达为命名位姿、关节值或末端位姿约束；接口在此处做目标形式校验。
  2. 规划：请求进入规划管线，经过适配器预处理、采样搜索、碰撞校验、时间参数化；返回值携带轨迹或失败信息。
  3. 判定：程序检查结果状态。失败分为无解、超时、无效请求三类，处理策略不同。
  4. 执行：把轨迹转交控制器；执行成败与规划成败相互独立。

四个阶段在代码里对应四个方法调用，理解分段后，任何一段异常都能定位到具体方法与其参数。脚本中的日志应在每个阶段输出一行关键信息，把失败定位压缩到一次运行之内。

4. 参数从哪里来

脚本进程必须自带机器人描述与配置：描述决定模型，语义决定组名与命名位姿，规划管线决定算法与参数，运动学配置决定位姿目标的求解方式。这些内容都来自第 004 章生成的配置包，惯例是在启动文件里把包内容物化成节点参数注入脚本进程。脚本本身保持"参数使用者"的角色，配置的切换不影响代码。

实现思路与设计

脚本按固定骨架组织，配一个启动文件负责配置注入；先跑通再逐步扩展。

脚本骨架与每一步的完成标志

  1. 初始化：完成 rclpy 初始化，构建规划实例；完成标志是日志出现"规划管线就绪"。
  2. 取组件：按组名取到规划组件；完成标志是组件对象可用且组自由度与预期一致。
  3. 设目标：先用命名位姿练手；完成标志是目标设置调用无异常。
  4. 规划：调用规划，检查返回值；完成标志是拿到轨迹或明确的失败信息。
  5. 执行：把轨迹交给控制器；演示环境用假控制器。
  6. 收尾：有序释放实例并关闭；完成标志是进程退出码为 0。

脚本参数表

参数建议值作用取值依据

设计决策：为什么第一个脚本选择显式日志、放弃静默执行？

规划的失败原因分布在目标、场景、算法三个层面，静默脚本的失败只剩一个退出码。每个阶段留一行日志（目标、规划结果、执行结果）把一次运行的关键信息留在终端，让第一次失败就能回答"卡在哪一步"。这份日志习惯将贯穿后续所有示例。

关键代码与解读

本节给出三段片段：最小可运行脚本、起始状态与结果处理的强化版、以及负责参数注入的启动文件。

片段 1：最小可运行脚本

import rclpy
import rclpy.logging
from moveit.planning import MoveItPy   # 模块路径随发行版演进，以对应版本文档为准

log = rclpy.logging.get_logger("first_moveit_script")   # 脚本侧日志器

def main():
    # 初始化客户端库；参数由启动文件注入，脚本只负责使用
    rclpy.init()
    # 构建进程内规划实例：内部装载描述、语义与规划管线配置
    arm = MoveItPy(node_name="first_moveit_script")
    # 按 SRDF 组名取规划组件：组名错误时此处即暴露，便于尽早发现配置问题
    group = arm.get_planning_component("arm")

    # 目标用命名位姿表达：名称与第 005 章界面里选择的是同一份定义
    group.set_goal_state(configuration_name="ready")
    # plan() 返回结果对象：内部完成适配、搜索、校验与时间参数化
    plan = group.plan()
    # 先检查再执行：结果成功时取真值，失败时经错误码属性读取原因
    if not plan:
        log.error("规划失败：检查目标可达性与场景碰撞")
    else:
        # 执行阶段把轨迹交给控制器；演示环境由假控制器接管
        arm.execute(plan.trajectory, controllers=[])
        log.info("执行请求已发送")

    # 有序释放：先关实例再关客户端库，避免后台线程在关闭后访问资源
    arm.shutdown()
    rclpy.shutdown()

if __name__ == "__main__":
    main()

解读：这段脚本是后续所有程序的最小内核。（1）初始化阶段把"配置从哪来"与"代码怎么写"分开：参数注入由启动文件承担，脚本只引用组名与位姿名。（2）set_goal_state 与 plan() 的先后顺序对应规划请求的分段，插入了日志与判断后，任何一步的异常都能被单独观察。（3）规划与执行之间的 if not plan 检查是安全习惯：结果对象在失败时为假值，轨迹字段只在成功路径上读取，避免把无效结果发往控制器。不同版本中结果对象的字段组织可能不同，以对应版本文档为准。

片段 2：显式起始状态与结果分支

def plan_sequence(arm, group, targets):
    """连续规划多个目标：显式声明起始状态，避免批次之间状态漂移。"""
    for i, name in enumerate(targets):
        # 第一段从当前状态出发；后续段从前一段的终点出发，保证链式一致
        if i == 0:
            group.set_start_state_to_current_state()
        else:
            # 用上一段目标作为本段起点：不依赖执行侧回读，批处理可离线运行
            group.set_start_state(configuration_name=targets[i - 1])

        group.set_goal_state(configuration_name=name)
        plan = group.plan()

        if not plan:
            # 失败即终止批次并返回失败目标名：调用方决定重试或降级
            log.warning(f"目标 {name} 规划失败，终止批次")
            return False, name

        # 每个目标一行成功日志：批量运行的进度与到达顺序可从终端回溯
        log.info(f"目标 {name} 规划成功")
        arm.execute(plan.trajectory, controllers=[])
        # 简单节拍等待：真机部署应改为监听执行结果，参见第 014 章
        log.info(f"已完成 {name} 的执行请求")
    return True, targets[-1]

解读：批量运动是脚本相对界面操作的最大收益，但批量引入了状态一致性要求。（1）首段绑定当前状态，后续段用上一段目标作起点，轨迹序列在逻辑上首尾相接；显式设置起点让整批规划不依赖执行反馈，适合离线演练。（2）失败策略选择"终止批次并回报失败点"：批量场景中继续执行后续目标通常失去意义，明确失败点便于单独重试。（3）注释标出与第 014 章的接口升级路径：本章用日志观察执行，后续章节接入执行结果监听，把节拍从日志观察升级为事件驱动。

片段 3：启动文件注入配置

from launch import LaunchDescription
from launch_ros.actions import Node
from moveit_configs_utils import MoveItConfigsBuilder

def generate_launch_description():
    # 配置包是所有参数的单一来源：与第 005 章界面验证使用同一份内容
    moveit_config = MoveItConfigsBuilder("arm_robot",
        package_name="arm_robot_moveit_config").to_moveit_configs()
    # 脚本作为普通节点启动：参数在节点构造时读取，替代了手工拼装 YAML
    script = Node(
        package="arm_robot_bringup",
        executable="first_moveit_script",
        output="screen",
        # 描述与语义决定模型，规划管线与运动学决定行为
        parameters=[moveit_config.to_dict()],
    )
    return LaunchDescription([script])

解读：启动文件在这里承担"配置物化"职责。（1）moveit_config.to_dict() 把描述、语义、规划、运动学参数打成一包注入节点，脚本进程因此具备完整的规划能力，不依赖外部 move_group。（2）输出重定向到屏幕，让片段 1 的日志立即可见，这是首个脚本调试期的必要设置。（3）该启动文件后续可直接扩展：加入 RViz 节点即可获得"界面加脚本"的一体化调试环境。

常见坑

  • 直接运行可执行文件缺少参数：组件初始化报参数缺失，表现为描述为空或规划管线加载失败。修复：经启动文件运行，或按渠道将配置注入节点参数。
  • 忘记释放资源：脚本结束后进程残留，下一次运行的端口或名称冲突。修复：成对编写初始化与关闭调用，实例先于客户端库关闭。
  • 组名或位姿名拼写错误：报组不存在或位姿未定义。修复：名称一律从配置包复制，不手工输入；把名称集中为脚本顶部常量。
  • 把规划与执行混为一谈：只检查规划返回值就认为动作完成。修复：规划成功只说明轨迹生成，执行结果需要独立跟踪，第 014 章接入执行结果监听。
  • 连续规划未更新起始状态：第二段轨迹的起点与实际姿态不符，执行时出现跳变。修复：采用片段 2 的显式起始状态策略。

练习与思考

  1. 把片段 1 的目标从 ready 改为 vertical，运行并记录规划是否一次成功以及日志中的关键信息。★
    提示
    观察目标位姿与当前状态的距离对规划的影响；两段命名位姿如果距离较远，采样规划通常仍能一次成功，但路点数会明显增加。
  2. 整理一张对比表：进程内脚本与"订阅 move_group 动作接口"的客户端，在启动依赖、场景可见性、资源占用三个维度的差异。★
    提示
    参考本章部署形态对比表，补充一条：进程内方案在 move_group 未启动时也能工作，进程外方案必须先有服务端。
  3. 改参数预测：把规划时间预算从 1.0 s 降到 0.05 s，在无障碍场景与桌面遮挡场景下分别预测成功率，并说明验证方法。★★

  4. 设计题：把片段 1 改造成命令行工具，接受"目标名称"参数，规划成功返回 0、失败返回 1，并输出一行机器可读的结果摘要。说明改造点与调试价值。★★★
    提示
    用参数解析库读取目标名；把日志摘要格式化为固定字段；退出码让外层的批量脚本或任务系统能直接判定结果。

小结

  • 官方 Python 接口采用进程内规划形态：无序列化开销，场景数据本地可见，代价是每进程一份模型。
  • 规划组件以组名入口，状态由起始与目标两个字段构成；plan() 不改变状态。
  • 四步骨架（设目标、规划、判定、执行）是第一支脚本的固定结构，日志覆盖每一步。
  • 批量规划必须显式管理起始状态，串行轨迹才具备逻辑一致性。
  • 下一章转向不写代码的路径：用命令行与既有工具完成规划操作，适合快速验证与接口探查。
