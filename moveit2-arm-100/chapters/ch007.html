第 007 章：使用命令行进行运动规划

本章在无图形、不写代码的条件下完成规划验证：用 ros2 命令行探查接口、读取参数、触发规划并观察轨迹消息。

  • 主题：命令行工具 / 接口探查与快速验证
  • 关键机制：动作与服务探查、演示程序触发、轨迹话题观察
  • 预计学时：50 分钟
  • 前置章节：第 006 章

学习目标

  • 掌握探测 move_group 接口清单的方法：动作、服务、话题三类接口的枚举与详情查询。
  • 会用参数工具读取规划系统的关键参数，验证配置包确实被服务端装载。
  • 会运行教程程序触发规划，并订阅轨迹话题观察规划结果的消息结构。
  • 能对简单服务（如正运动学查询）构造命令行请求，理解服务调用的完整往返。
  • 能制定无图形环境下的快速验证清单，覆盖启动、接口、规划、轨迹四层。

背景与动机

开发过程并不总有图形界面可用：远程终端、服务器环境、最小化安装的系统都只有命令行。即使有图形界面，命令行仍是验证系统最轻的入口：一条命令可以回答"服务在不在、参数对不对、话题有没有数据"这些问题，省去打开界面与配置显示的步骤。

命令行方式还有一个结构性优点：它展示的正是接口本身。后续章节所有的高层接口，无论 Python 还是 C++，最终都归结为本章看到的动作、服务与话题调用。把接口清单与消息结构看清楚，高层接口的行为就有了参照系。本章的内容按"探查、读取、触发、观察"四步展开，形成一套可以反复使用的验证流程。

核心原理

本节解释命令行验证的对象结构：move_group 对外暴露的接口全貌，以及规划触发与结果观察分别在哪些通道上进行。

1. move_group 的接口全景

move_group 对外提供三类接口，命令行工具分别有对应的枚举命令。下表的清单来自第 001 章的架构分析，这里落实到具体端点：

类别典型端点作用探查命令
动作/move_action规划与执行的主通道ros2 action list
服务/get_planning_scene获取当前场景快照ros2 service list
服务/compute_fk、/compute_ik正逆运动学查询ros2 service list
服务/apply_planning_scene向场景写入物体ros2 service list
话题/joint_states关节状态数据流ros2 topic list
话题/display_planned_path规划结果的显示通道ros2 topic list
话题/monitored_planning_scene场景增量更新ros2 topic list

端点名的前缀取决于部署方式：单机默认无前缀，多机与命名空间部署会在名称前带前缀。探查命令的输出就是实际存在的名字，复制输出比记忆名称可靠。

2. 命令行触发规划的两条路径

命令行触发规划有两条路径。第一条是运行现成的教程程序：教程仓库中的示例可执行文件本身就是完备的动作客户端，从终端启动即可完成"构造目标、规划、执行"全过程。第二条是手工构造动作目标：用命令行工具向动作端点发送目标消息。

第二条路径的门槛在于规划目标的消息结构复杂：一个完整的规划请求包含起始状态、目标约束、规划参数、工作空间边界等字段，逐一填写字段数量多且容易出错。手工构造适合简单服务；完整规划交由程序完成。实践中的分工：规划用教程程序或脚本触发，验证性的查询用命令行服务调用。

3. 轨迹消息：规划结果的载体

规划结果通过两组信息被外界观察：动作结果里携带的轨迹，以及供显示用的轨迹话题。轨迹消息的核心字段是机器人轨迹结构，内含起始状态与关节轨迹两段：起始状态记录轨迹的出发点，关节轨迹记录路点序列，每个路点包含关节位置、速度与相对起点的时间。

DisplayTrajectory ≈ { trajectory_start: 起始状态, trajectory: [关节轨迹] } 关节轨迹的 points 数组即路点序列，长度与时间戳是检查规划质量的第一手数据

命令行观察轨迹时，整条消息体量较大，全量打印会瞬间刷屏。按字段提取或单次捕获是标准做法，只取需要判断的字段：路点数量反映轨迹规模，首末点时间差反映运动时长，速度数组反映时间参数化是否已执行。

4. 命令行的能力边界

命令行适合回答问题：接口在不在、参数对不对、数据有没有、一次规划是否成功。它不适合承载条件逻辑：失败重试、参数扫描、统计成功率都需要脚本。把命令行放在验证链的第一环，把脚本放在第二环，是效率最高的组合。本章的清单在第 018 章的阶段实践中会成为集成验证的一部分。

实现思路与设计

命令行验证按四层推进：启动层、接口层、规划层、数据层，每层有明确的判定标准。

  1. 启动层：拉起演示系统，确认 move_group 与假控制器进入就绪状态。
  2. 接口层：枚举动作、服务、话题清单，核对上一节表格中的端点在列。
  3. 规划层：运行教程程序触发完整规划流程，观察终端输出与退出状态。
  4. 数据层：订阅轨迹话题与关节状态话题，核对消息字段与时间戳。

常用命令速查表

目的命令形态预期输出
枚举动作接口ros2 action list -t端点名与动作类型
查看动作详情ros2 action info <端点>客户端与服务端计数、动作类型
枚举服务ros2 service list服务名清单
查看服务类型ros2 service type <服务名>请求与响应类型
读取参数ros2 param get <节点> <参数>参数当前值
观察话题字段ros2 topic echo <话题> --field <字段>指定字段的流式输出
调用服务ros2 service call <服务> <类型> <请求>响应消息
设计决策：为什么先查接口再触发规划？

规划失败的排查方向很多，接口缺失是最容易被忽略的一类：端点名带命名空间前缀、服务尚未就绪、组件加载失败，这些都会让后续操作无从下手。先枚举接口清单，等于先确认"服务端提供了什么"，把触发失败的可能性压缩到参数与目标两个维度。这与第 005 章"先跑自检再排障"的思路一致。

关键代码与解读

本节给出三组命令片段：接口探查、教程程序触发与轨迹观察、以及服务调用与参数读取的组合验证。

片段 1：接口探查命令组

# 第 1 步：枚举动作接口并查看类型，确认规划主通道在线
ros2 action list -t
ros2 action info /move_action

# 第 2 步：枚举服务，过滤运动学与场景相关端点
ros2 service list | grep -E "compute_ik|compute_fk|get_planning_scene|apply_planning_scene"

# 第 3 步：枚举话题，核对状态流与轨迹显示通道
ros2 topic list | grep -E "joint_states|display_planned_path|monitored_planning_scene"

# 第 4 步：读取规划关键参数，验证配置包确实被装载
ros2 param list /move_group | head -n 20
ros2 param get /move_group robot_description_semantic

解读：这组命令按"动作、服务、话题、参数"的顺序覆盖四类检查。（1）先动作后服务的顺序对应规划主通道与辅助查询的优先级：动作端点缺席说明服务端没有真正就绪。（2）用过滤表达式缩小输出，避免在长清单中人工寻找；过滤关键字直接取自接口全景表，与文档口径一致。（3）参数读取选择语义描述、跳过完整描述：语义描述短小，能快速确认加载，也能直接看到组名定义；读取完整 URDF 参数会输出大量几何文本，不适合快速核对。

片段 2：教程程序触发规划与轨迹观察

# 终端一：启动演示系统（官方 Panda 配置为教程标准环境）
ros2 launch moveit_resources_panda_moveit_config demo.launch.py

# 终端二：运行教程程序，内部依次完成设目标、规划与执行
# 可执行程序名称以对应版本的教程仓库为准
ros2 run moveit2_tutorials move_group_interface_tutorial

# 终端三：订阅轨迹话题，只看路点数量与首末时间
# --field 提取嵌套字段，避免整条消息刷屏
ros2 topic echo /display_planned_path \
  --field trajectory.joint_trajectory.points --once | head -n 40

# 观察关节状态频率，确认数据面稳定（每秒约 50 至 100 帧）
ros2 topic hz /joint_states

解读：这组命令把"触发"与"观察"分到不同终端，形成最小闭环。（1）演示系统使用官方标准模型，教程程序的目标与该模型匹配，避免自定义配置带来的变量。（2）--once 让话题订阅在捕获一帧后自动退出，配合字段提取得到一条完整轨迹的快照；路点数量在几十到几百之间属于常见规模。（3）ros2 topic hz 输出帧间隔统计，是判断状态流健康的轻量工具；频率剧烈波动说明发布侧负载异常，第 009 章的状态管理会用到这个信号。

片段 3：服务调用与正运动学手算验证

# 调用正运动学服务：给定一组关节角，问末端法兰在哪里
# 请求字段包含参考系、待查询链接与机器人关节状态
ros2 service call /compute_fk moveit_msgs/srv/GetPositionFK \
"{header: {frame_id: 'base_link'},
  fk_link_names: ['flange'],
  robot_state: {joint_state: {
    name: ['joint_1', 'joint_2', 'joint_3', 'joint_4', 'joint_5', 'joint_6'],
    position: [0.0, -0.5, 0.9, 0.0, 0.9, 0.0]}}}"

# 对照：读取肘部关节当前的限位参数，确认查询用的关节在配置中一致
ros2 param get /move_group robot_description

# 若响应中位姿明显偏离预期，优先核对参考系与关节顺序
# 两大常见错误：frame_id 写成了法兰自身，position 顺序与 name 不匹配

解读：正运动学服务是最适合命令行手工调用的端点。（1）请求三要素清晰：参考系回答"相对哪里"，链接名单回答"问哪个部件"，关节状态回答"在什么姿态下问"。（2）关节名与角度两个数组必须一一对应，顺序错位会得到"语法正确、语义错误"的位姿，这是服务调用最常见的失误。（3）把结果与手算或与 RViz 中的姿态对照，可以同时验证模型、限位与接口三层配置；这一技巧在第 009 章讨论状态表示时会再次用到。

常见坑

  • 端点带命名空间前缀却按默认名调用：服务明明在运行，命令却报"未找到"。修复：以 ros2 service list 的实际输出为准，复制完整名称。
  • 手工构造的规划动作目标字段不完整：服务端拒绝请求或返回无效参数。修复：手工调用仅限正运动学这类简单服务；完整规划走教程程序或脚本。
  • 话题全量输出刷屏：整条轨迹消息包含大量路点，终端失去可读性。修复：使用字段提取参数或单次捕获，只看判定所需的字段。
  • 把命令行成功当成全链路成功：规划成功但执行无动作，原因在控制器侧。修复：在验证清单中加入控制器状态检查，执行链路问题留给第 014 章处理。
  • 参数读取路径写错：节点名少了命名空间，输出为空或报错。修复：先列参数清单确认节点全名，再读取具体参数。

练习与思考

  1. 启动演示系统，把本章接口全景表中的端点逐一对号入座，记录哪些端点存在、哪些在本版本中名称不同。★
    提示
    名称差异多出现在运动学服务端点上；以实际输出为准记录，形成自己环境的接口清单。
  2. 用正运动学服务查询基座姿态下（全部关节为零）法兰的位置，并与 URDF 中链上各段长度简单相加的结果对照，解释偏差来源。★★
    提示
    零位下各段朝向与安装变换决定结果；偏差主要来自关节 origin 的平移叠加与轴向朝向，逐段列出变换即可核对。
  3. 预测实验：先运行教程程序触发一次规划，随后立刻用 ros2 topic echo --once 捕获轨迹话题，与执行完成后再捕获一帧相比，trajectory_start 字段是否不同？说明依据。★★
    提示
    轨迹话题随每次规划刷新；执行本身不改变最近一次规划结果，但若执行期间发生新的规划（例如界面拖动），快照内容会变化。关键在确认观察的是哪一个时刻的快照。
  4. 设计题：为只有 SSH 访问的远程工作站编写一份"命令行冒烟清单"，覆盖启动、接口、参数、规划、轨迹五个环节，每项给出命令与通过标准。★★★
    提示
    参考四层验证流程与速查表；把每项判定写成"输出中应出现什么"，便于逐条核对；清单在第 018 章会与图形界面的验证结果合并使用。

小结

  • move_group 的接口全景可枚举：规划动作、场景与运动学服务、状态与轨迹话题。
  • 命令行触发规划走教程程序，命令行验证查询走服务调用；两条路径的分工由字段复杂度决定。
  • 轨迹消息由起始状态与关节轨迹两段构成，路点数与时间戳是首要检查数据。
  • 命令行适合回答"在不在、对不对"，条件逻辑与统计交给脚本。
