第二篇 · 规划场景与碰撞管理

第 033 章：视觉感知接口与 3D 感知

感知进入规划场景的两条通道：占据级（传感器插件写入地图）与物体级（检测结果作为碰撞物体写入场景）。本章讲两类接口的插件架构、生命周期与过期管理，以及感知误差不对称时规划侧的风险管理。

  • 主题：感知接口架构 / 3D 感知集成
  • 关键机制：占据地图更新器插件、物体级上报的刷新与过期清理、命名域划分
  • 预计学时：50 分钟
  • 前置章节：第 032 章

学习目标

  • 分清感知数据进入规划场景的两级接口：占据级（点云级）与物体级（几何级），及各自的适用条件。
  • 理解传感器插件的架构：加载方式、生命周期钩子与参数契约，能说明插件模型为什么适合扩展感知输入。
  • 掌握物体级接口的工程纪律：刷新心跳、过期清理、命名域隔离与置信度对应的几何处理。
  • 能按任务需求选择接口层级，设计"检测物体加占据地图"的混合架构。
  • 理解感知误差不对称（漏检与误检代价不同）对规划侧策略的影响。

背景与动机

第 030 至 032 章走通了"点云进地图"的占据级通路：传感器数据以体素形式表达世界，规划器对稠密几何做避障。这条通路有一个天然缺口：它不支持语义。规划场景知道"那里有一团占据体素"，却不知道"那是一盒工件、可以夹取、抓走之后体素应当消失"。抓取类任务恰恰需要物体身份：物体要能作为抓取目标、作为附着体随臂运动、作为可移除对象参与对账。

物体级接口补上这一层：检测模块把识别结果以碰撞物体的形式直接写入场景，物体携带标识与精确几何，享受第 022 至 026 章的全部生命周期管理。两级接口服务不同需求，工程系统通常混合使用。本章的关键落在数据契约的澄清上：谁负责刷新、谁负责过期、命名如何隔离、误差如何被规划侧的保守策略吸收。第 034 章将在此之上讲多路数据的融合。

核心原理

1. 两级感知接口的对照

维度占据级接口物体级接口
数据形态点云经插件写入八叉树检测结果作为碰撞物体写入世界
语义无（只有占据与空闲）有（标识、类别、可操作性）
几何精度受地图分辨率限制由检测与拟合精度决定，可用解析形状
过期行为依赖射线清除，自动但迟滞无自动过期，需要刷新与清理逻辑
典型来源深度相机、激光雷达的原始数据识别算法、标定后的固定物体集
规划用途未知形状、稠密杂乱的避障抓取目标、可移除障碍、语义关联

对照表的结论指向分工，两类接口之间不存在替代关系：占据级处理"形状难以描述"的环境，物体级处理"需要身份"的目标。两级的共存还有一条硬约束：同一个物理几何只应由一级负责，重复表示会让检测代价翻倍、清除行为互相矛盾（第 030 章已提出该纪律）。

2. 传感器插件：占据级接口的扩展点

占据级接口以插件形式组织：规划场景监视器在启动时按配置加载若干传感器插件，每个插件负责一路输入的完整通路（订阅、变换、过滤、写入）。插件暴露标准生命周期：初始化阶段读取参数并建立订阅，启动与停止阶段与监视器的生命周期联动，数据回调阶段把观测交给监视器写入八叉树。扩展新传感器时，插入点就是新写一个插件，规划场景核心代码保持不变。

插件模型的价值在三个场景中体现：接入标准驱动之外的自定义传感器（例如事件相机、专用测距模块）时，只需实现数据到点云的转换；需要特殊过滤（例如只保留工作区内的点、剔除与已知物体重叠的点）时，过滤逻辑写在插件内部，与其它传感器互不影响；同一类传感器多路部署时，每路一个插件实例，参数独立配置。插件的参数契约（话题名、量程、抽稀、退让）由配置声明，调参不触碰代码，这是第 031 章参数体系得以成立的结构性前提。

3. 物体级接口：刷新与过期的纪律

物体级接口把检测结果写成碰撞物体，但它没有自动生命周期：一条 ADD 写入的物体在场景中永久存在，直到有 REMOVE 显式清除。检测模块以固定节拍输出结果流，若直接"每次都 ADD"，会在检测暂时丢帧时留下过期物体，也会因重复写入放大场景流量。标准纪律由三件事组成：

  • 心跳刷新：每次检测到同一物体就重发一次写入（或使用移动操作更新位姿），并记录最近观测时刻；物体在观测中缺席超过存活时限（Time To Live, TTL）才判定离开。
  • 过期清理：清理动作也是写入，走与添加相同的确认路径；清理的判据来自心跳台账，不依赖检测模块的"删除事件"（该事件在网络抖动时不可靠）。
  • 命名域隔离：感知物体统一前缀（如 sensed_），与任务物体、对账清理的标识域分开（第 023 章），保证清理逻辑不会误伤。

TTL 的取值是检测节拍与误报代价的折中：TTL 过短，物体在检测短暂丢帧时被反复清除再添加，场景内容抖动并引发无谓的重规划；TTL 过长，已移走的物体长期滞留形成幽灵障碍。常用取值范围是检测周期的三到五倍。

4. 置信度与几何的保守处理

检测结果带有不确定性，把它写进规划场景时应当把不确定性"转译"为几何策略：检测置信度越高、拟合越精确的物体，可以按解析形状的紧包围写入；置信度一般或形状拟合粗糙的目标，按保守包围（适度扩张的几何或球包）写入。这与第 022 章的安全裕量一脉相承，只是裕量来源从"安装偏差"换成"识别误差"。把检测置信度映射为几何放大量，是一条简单且有效的工程规则：不改变规划算法，只改变进入场景的几何。

5. 感知误差的不对称与风险管理

感知的两类错误在规划场景中的后果并不对称：漏检（真实存在的障碍没进场景）让规划器在"虚假的畅通"中计算路径，后果是碰撞；误检（不存在的障碍进了场景）让规划绕行并不存在的物体，后果是效率损失。安全优先的系统因此把策略调成不对称：宁可多绕，不可漏检。可落地的措施有三条：检测缺失的区域用占据地图兜底（两级互补）；对高风险方向（人员可能进入的方向）提高几何保守度或扩大 TTL；对"检测与占据两种表示冲突"的区域按占据几何处理，把保守假设作为默认值。风险管理不追求感知完美，追求的是错误发生后系统仍然安全。

实现思路与设计

把感知接入规划场景的设计流程：

  1. 需求分层：列出任务需要语义的对象（抓取目标、可移除障碍）与只需避障的区域（杂物区、人员区），分别落到物体级与占据级。
  2. 定契约：为物体级定义命名前缀、TTL、置信度到几何的映射表；为占据级定义插件参数（第 031 章表）。
  3. 实现上报模块：检测输出加心跳与清理逻辑，写入路径选带去确认的服务或封装接口。
  4. 冲突规则：定义两级表示重叠时的处理（感知屏蔽区、占据优先或物体优先），形成书面规则并在代码中实现。
  5. 验证用例：漏检模拟（遮挡目标）、误检模拟（放入与检测目标相似的非目标物）、过期测试（移走物体后的清除时间）三类。
  6. 运行监测：统计感知物体数量、心跳年龄分布与清理事件频率，把接口健康度可视化。

两级接口契约要点

契约项占据级物体级
刷新责任插件随数据到达自动写入上报模块心跳刷新
过期责任射线清除（自动、有迟滞）上报模块按 TTL 清理（显式）
命名不适用（地图整体）统一前缀加检测模块标识
误差吸收地图退让参数置信度到几何的扩张规则

与上一章的差异点：第 032 章解决"数据从哪台设备来、坐标准不准"；本章解决"数据以什么接口形态进入规划场景"。前者是链路工程，后者是架构与契约设计。

片段 2：Python 物体级上报：心跳、命名域与过期清理

import rclpy
from rclpy.node import Node
from moveit_msgs.msg import CollisionObject

class DetectedObjectReporter(Node):
    """把检测结果以物体级接口写入场景，并承担刷新与清理责任。"""

    def __init__(self):
        super().__init__("detected_reporter")
        self.pub = self.create_publisher(CollisionObject, "/collision_object", 10)
        self.known = set()        # 本模块管理的标识台账
        self.last_seen = {}       # 标识 -> 最近一次被检测到的时刻

    def report(self, detections):
        now = self.get_clock().now()
        for det in detections:
            # 命名域隔离：清理与对账只处理 sensed_ 前缀
            det.id = "sensed_" + det.id
            det.operation = CollisionObject.ADD
            self.pub.publish(det)
            self.known.add(det.id)
            self.last_seen[det.id] = now     # 心跳：每次观测刷新年龄

    def cleanup(self, ttl=2.0):
        """超过存活时限未再被观测的物体按过期移除。"""
        now = self.get_clock().now()
        for obj_id in list(self.known):
            age = (now - self.last_seen[obj_id]).nanoseconds / 1e9
            if age > ttl:
                gone = CollisionObject()
                gone.header.frame_id = "world"
                gone.id = obj_id
                # 清理走与添加相同的写入通道，保证确认路径一致
                gone.operation = CollisionObject.REMOVE
                self.pub.publish(gone)
                self.known.discard(obj_id)
                del self.last_seen[obj_id]

解读：（1）台账（known 与 last_seen）是过期管理的核心：清理判据来自本地观测历史，检测模块的"删除事件"不在信任链上，网络抖动不会造成误删。（2）TTL 默认 2 s 对应检测周期 0.4 至 0.7 s 的三到五倍：足够覆盖偶发丢帧，又能在物体移走后及时清场。（3）命名前缀在写入处统一附加，把隔离规则收敛到一个位置；下游清理与对账按前缀筛选即可，规则简单且不易遗漏。

片段 3：Python 按掩码取回场景内容，核对感知物体

import rclpy
from moveit_msgs.srv import GetPlanningScene
from moveit_msgs.msg import PlanningSceneComponents

def count_sensed_objects(node):
    """取场景中的世界几何子集，核对感知物体的数量与命名域。"""
    client = node.create_client(GetPlanningScene, "get_planning_scene")
    if not client.wait_for_service(timeout_sec=1.0):
        node.get_logger().error("场景查询服务不可用")
        return None
    req = GetPlanningScene.Request()
    # 位掩码只请求世界物体几何，减少消息体积与序列化开销
    req.components.components = PlanningSceneComponents.WORLD_OBJECT_GEOMETRY
    future = client.call_async(req)
    rclpy.spin_until_future_complete(node, future, timeout_sec=2.0)
    if future.result() is None:
        node.get_logger().error("场景查询超时")
        return None
    scene = future.result().scene
    all_ids = [o.id for o in scene.world.collision_objects]
    sensed = [i for i in all_ids if i.startswith("sensed_")]
    node.get_logger().info(
        f"世界物体 {len(all_ids)} 个，其中感知物体 {len(sensed)} 个")
    return sensed

解读：（1）查询掩码是这类诊断工具的通用模式：只取需要的子集，消息体积与解析成本随之下降，适合放进周期性健康检查。（2）按前缀统计感知物体数量，能在联调时快速发现"检测模块上报的物体数与场景中的物体数不一致"这类契约断裂。（3）函数返回清单使调用方可以进一步核对（例如与检测模块的台账比对），把接口契约的验证做成可自动化的检查。

常见坑

  • 物体只写不删：检测模块每次都 ADD，从不清除，场景中感知物体数量随运行时长单调增长，规划逐渐变慢并出现幽灵障碍。修复是引入心跳台账与 TTL 清理（片段 2），并把清理事件纳入监测。
  • 命名域混用：感知物体与任务物体共享命名，对账清理误删任务物体或相反。修复是统一前缀规则并收敛到写入处，一处实现全局生效。
  • 两级表示重叠：同一几何既被检测为物体又由点云写入地图，检测代价上升且清除行为矛盾。修复是在插件内剔除与已知物体重叠的点（屏蔽区），或对已建物体区域的点云做过滤。
  • 置信度直接当几何精度：低置信度检测按紧包围写入，规划贴着不确定的边界运行。修复是建立置信度到几何扩张的映射，低置信目标按保守包围处理。
  • 插件参数与声明不一致：sensor_plugin 字符串与插件注册名拼写不同、参数缺项，加载失败通常只在启动日志中出现一次。修复是把"插件加载成功"写进启动自检，失败即拒绝进入任务流程。

练习与思考

  1. 层级选择：为一台"从料箱抓取散件"的工位划分两级接口职责：哪些内容走占据级、哪些走物体级，并说明料箱本身（已知几何）为什么不交给感知。 ★
    提示
    料箱与台面按显式物体部署（已知几何，精度要求高）；箱内散件与箱沿外的杂物交给占据级或检测模块；箱内散件的抓取目标若需语义，由检测模块给出物体级结果，箱内其余杂乱部分保持占据表示。
  2. 参数预测：TTL 从 2 s 改为 0.5 s，检测周期为 0.5 s 且偶发丢帧率为 10%。预测清理事件的频率变化与场景抖动风险，并给出建议。★
    提示
    TTL 等于一个检测周期时，单次丢帧即触发清理，随后重新写入，清理与添加频繁交替；建议 TTL 保持在检测周期的三到五倍，即 1.5 至 2.5 s。
  3. 设计题：为"检测漏检率为 5%、误检率为 2%"的场景设计风险管理方案，包含两级互补策略、置信度映射表与验证用例。★★
    提示
    低置信区域用占据地图兜底覆盖漏检方向；置信度映射按 0.9 以上紧包围、0.7–0.9 扩张 2 cm、0.7 以下扩张并降级使用；验证用例覆盖遮挡漏检、相似物误检与混合场景的规划行为。
  4. 诊断题：启动日志无报错，但点云不进地图、检测物体也不入场景。列出两类接口各自的检查点，并说明为什么"无报错"是正常现象。★★
    提示
    占据级检查插件是否被加载（启动参数中的 sensor_plugin 列表）与话题是否匹配；物体级检查上报模块是否运行与写入路径是否确认。两类路径的失败都可能静默发生，把"数据已进入场景"作为启动自检项，避免默认假设。
  5. 分析题：论证感知误差不对称（漏检代价高于误检）前提下，"保守几何、宁可多绕"策略的合理性，并讨论该策略在节拍敏感工位上遇到的困难与缓解办法。★★★
    提示
    安全侧：漏检直接对应碰撞风险，误检只损失效率，所以默认从严。节拍困难在于保守几何缩小可行空间、降低一次通过率；缓解办法包括分级保守（安全方向高、非安全方向低）、任务阶段切换保守度、提高检测质量压缩不确定性来源。

小结

  • 感知进入规划场景有两条通道：占据级提供稠密避障几何，物体级提供带身份的精确几何，二者分工互补。
  • 占据级以传感器插件扩展，插件承担订阅、变换、过滤、写入的完整通路，参数由配置声明。
  • 物体级需要显式生命周期管理：心跳刷新、TTL 过期清理、命名域隔离三件纪律缺一不可。
  • 检测置信度映射为几何保守度，把感知不确定性转译为规划侧可吸收的裕量。
