第二篇 · 规划场景与碰撞管理

第 022 章：添加碰撞物体

机器人之外的一切可碰撞几何都叫碰撞物体：本章讲把盒、球、柱、网格等障碍物写进规划场景的三条路径，位姿与坐标系的组合语义，以及"物体是否真正生效"的确认方法。

  • 主题：规划场景内容管理 / 世界物体
  • 关键机制：CollisionObject 消息、碰撞世界（CollisionWorld）插入、位姿与参考系解析
  • 预计学时：45 分钟
  • 前置章节：第 021 章

学习目标

  • 理解碰撞物体（Collision Object）在规划场景中的角色：它是机器人身体之外全部可碰撞几何的统一载体，规划器的碰撞检测以它为准。
  • 掌握添加碰撞物体的三条路径：PlanningSceneInterface 封装接口、应用规划场景（ApplyPlanningScene）服务、/collision_object 话题，并能说明各自何时适用。
  • 吃透 CollisionObject 消息中物体位姿（pose）、参考坐标系（frame_id）、形状（primitive 与 mesh）三者的组合语义。
  • 会为工作台上的典型物体选择参考坐标系与几何类型，并解释选择依据。
  • 能独立验证物体是否生效：查询场景物体清单、核对位姿，对比添加前后的规划结果。

背景与动机

规划器在计算一条轨迹时，依据的是两样数据：机器人模型与场景几何。第 021 章解决了"机器人现在在哪"的问题，本章解决"环境里有什么"的问题。机械臂的典型任务可以归纳为一句话：在障碍之间把末端工具送到目标位姿。工作台、料架、夹具、待抓工件，这些几何体如果不进入规划场景，规划器会认为空间是空的，所给轨迹在物理世界里必定发生碰撞。

碰撞物体管理在第二篇中拆为三章：本章负责"添加"，第 023 章负责"更新与移除"，第 024 章解剖消息结构本身。三者对应同一组接口的三个侧面。添加是场景内容管理的第一步，它把外部世界的几何事实翻译成规划器可查询的数据结构。后续的避障规划（第 029 章）、传感器融合（第 034 章）都建立在"物体已经正确进入场景"这一前提之上。

核心原理

1. 碰撞世界：一张以标识为键的几何表

规划场景内部把世界分解为两个来源：机器人本体（来自 RobotModel，自碰撞在机器人内部解决）与世界物体（World Objects）。世界物体的容器称为碰撞世界（CollisionWorld），结构上是一张映射表：物体标识（id）到碰撞物体对象（CollisionObject）的一一对应。每个物体携带几何形状、位姿以及派生信息（如包围盒）。

这张表有三个重要性质。（1）标识唯一：同一个 id 在表中只存在一项，重复添加同名物体会替换旧项，这为第 023 章的更新机制提供了基础。（2）位姿是快照：物体姿态在插入时解释并记录，之后不再跟随机器人运动，除非显式更新。（3）几何独立于机器人：世界物体的碰撞检测在物体坐标系与世界坐标系之间转换，与机器人关节值无关，因此物体数据可以缓存与复用。

2. 位姿语义：两级位姿的叠加

CollisionObject 消息里存在两级位姿：物体位姿 pose 与形状位姿 primitive_poses（网格对应 mesh_poses，平面对应 plane_poses）。物体位姿把物体放在参考系中，形状位姿把每个几何形状放在物体内部，最终几何的位置由两者的组合决定：

Tworld,shape = Tworld,frame · Tframe,obj · Tobj,shape frame 由 header.frame_id 给出；单个形状的物体通常把形状位姿留为单位阵，只调物体位姿

参考系的选择依据物体的运动学归属：固定安装在车间地面或工作台上的物体，用世界系（world）描述；随机器人整体移动的物体（移动底盘上的夹具），用机器人基座系（base_link）描述。参考系选错的典型症状是物体位置整体偏移，且偏移量随机器人移动而变化。

3. 形状的代价谱系与选择依据

解析形状（Analytic Shapes：长方体、球、圆柱、圆锥）在碰撞检测中代价最低，检测器对它们使用解析求交，单次查询通常在微秒量级。网格（Mesh）表达力最强，可以精确复刻复杂轮廓，代价与三角形数量成正比，且非凸网格的求交开销显著高于解析形状。通常在两者之间做工程折中：能用少数解析形状拼出近似轮廓的物体就不要用网格；必须用网格时，优先使用凸网格或把网格做凸分解（Convex Decomposition）成若干凸块，让检测器回到凸凸求交这条快路径。

几何类型表达力相对检测代价典型用途
长方体低低工作台、料箱、地板
球低最低近似球状障碍、快速原型
圆柱低低立柱、筒状工件
网格高随三角形数增长复杂工装、不规则零件

4. 生效路径：话题、服务与封装接口

把物体写进场景有三条路径，它们最终都经过同一段场景处理逻辑，差异在确认方式上：

  • 话题路径：发布 CollisionObject 到约定话题（默认 /collision_object），异步、发后即忘，适合静态环境的批量初始化，也适合与其他工具（如 RViz 场景编辑）共享同一条数据流。
  • 服务路径：调用 ApplyPlanningScene 服务提交场景差分，同步返回成功与否，适合需要明确结果的控制程序。
  • 封装接口路径：PlanningSceneInterface 把消息构造与差分确认打包在一起，调用后阻塞等待场景更新被确认，适合规划主控流程。

三条路径的可靠程度递增、灵活程度递减：快速脚本与可视化调试走话题，规划主循环内部走封装接口最为稳妥。需要强调的一点是：话题路径没有回执，发布完成后立刻规划存在竞态窗口，而"物体生效"恰恰是后续所有碰撞判断的前提。

5. 安全裕量：几何之外的一层工程防护

真实系统中的物体尺寸总有感知误差与安装偏差，把碰撞物体的几何直接建成标称尺寸，等于把全部误差留给规划结果承担。标准做法是在建模阶段留出安全裕量：把物体各方向尺寸增加 2δ（δ 常取 0.005–0.02 m），让规划出的路径与真实表面之间保有间隙。这一裕量与碰撞检测层面的退让距离（Padding）作用类似，前者作用在几何层面、对所有检测器生效，后者作用在检测器配置层面（第 028 章展开）。安全裕量是工程里最便宜的一道保险，代价只是少量工作空间的损失。

实现思路与设计

添加碰撞物体的完整流程按"先定义、后写入、再确认"组织：

  1. 建立物体清单：为每个物体确定四个要素：标识、参考系、几何、位姿。标识采用语义化命名（如 work_table、bin_upper、fixture_left），避免使用序号导致复用与排查困难。
  2. 构造消息：填充 header.frame_id、id、pose、primitives 或 meshes，操作字段取添加（ADD）。尺寸使用国际单位制的米，角度使用四元数。
  3. 选择写入路径：调试阶段用 RViz 的场景编辑或话题发布；主控程序用封装接口并等待确认。
  4. 确认生效：查询场景物体清单，核对标识、数量与位姿；RViz 中观察几何显示是否与预期一致。
  5. 规划联动验证：添加物体前后各规划一次相同目标，确认路径出现合理绕行；若路径没有变化，按 pitfalls 一节逐项排查。

与上一章的差异点：第 020、021 章处理的是"读"场景（订阅、监视、校验）；从本章开始进入"写"场景。读与写共用同一份场景数据，因此本章的每个写入动作都会立刻影响所有读方：规划器、RViz 显示、以及其它订阅场景的节点。

关键代码与解读

片段 1：C++ 封装接口添加工作台（接口以对应 ROS2 发行版与 MoveIt2 版本的官方文档为准）

#include <moveit/planning_interface/planning_scene_interface.hpp>

// 接口对象构造时建立内部节点，负责与移动组（move_group）的场景服务通信
moveit::planning_interface::PlanningSceneInterface psi;

// 直接构造物体消息：参考系、标识、几何三个要素一次配齐
moveit_msgs::msg::CollisionObject table;
table.header.frame_id = "world";       // 台面相对车间固定，使用世界系
table.id = "work_table";               // 场景内唯一标识，后续更新与移除都靠它定位
table.primitives.resize(1);
table.primitives[0].type = shape_msgs::msg::SolidPrimitive::BOX;
table.primitives[0].dimensions = { 1.2, 0.8, 0.04 };  // 三轴全尺寸，单位为米
// 形状位姿留为单位阵，几何整体由物体位姿摆放：中心下移 2 cm
// 使 4 cm 厚的台面上表面正好落在 z = 0 处（与机器人基座安装面一致）
table.pose.position.z = -0.02;
table.primitive_poses.resize(1);       // 与 primitives 一一对应，这里取默认零位姿
table.operation = moveit_msgs::msg::CollisionObject::ADD;

// 同步写入：接口内部提交差分并等待场景确认，返回时物体已经在场景中
psi.applyCollisionObject(table);

解读：这段代码把"定义、写入"两步压缩在一起，细节都在消息字段上。（1）dimensions 使用全尺寸，半宽写法属于常见误解，台面盒体给出 1.2 m × 0.8 m × 0.04 m；把中心下移 2 cm 是为了让几何上表面与真实台面（z = 0）重合，这类"几何对齐"细节直接决定规划是否把工具位姿抬到合适高度。（2）primitives 与 primitive_poses 是两个平行数组，长度必须一致，缺省时访问越界或行为未定义，示例里显式扩容是必要的防御写法。（3）applyCollisionObject 是同步接口，它内部完成"提交差分、等待确认"两个动作，返回后规划立即能看到该物体，避免了话题路径的竞态窗口。

片段 2：Python 话题路径添加障碍物

import rclpy
from moveit_msgs.msg import CollisionObject
from shape_msgs.msg import SolidPrimitive

class ObstaclePublisher(rclpy.node.Node):
    """以话题方式向规划场景写入长方体障碍，适合静态环境的快速布置。"""

    def __init__(self):
        super().__init__("obstacle_publisher")
        # 默认话题名 /collision_object；规划场景监视器订阅它并处理操作
        self.pub = self.create_publisher(CollisionObject, "/collision_object", 10)

    def add_box(self, name, center, size):
        obj = CollisionObject()
        obj.header.frame_id = "world"      # 与场景中其它物体统一参考系
        obj.id = name                      # 同名物体再次写入会替换旧值
        prim = SolidPrimitive()
        prim.type = SolidPrimitive.BOX
        # 尺寸含义随形状变化，长方体使用 [x, y, z] 三个全尺寸
        prim.dimensions = [size[0], size[1], size[2]]
        obj.primitives = [prim]
        # 物体位姿决定几何在世界中的整体摆放
        obj.pose.position.x = center[0]
        obj.pose.position.y = center[1]
        obj.pose.position.z = center[2]
        # 默认构造的四元数为全零，属于无效旋转，必须显式赋值
        obj.pose.orientation.w = 1.0
        # 操作字段缺省值为 ADD，这里显式书写以表明意图
        obj.operation = CollisionObject.ADD
        self.pub.publish(obj)              # 异步发送，生效与否需要另行确认

解读：（1）四元数从零开始构造时默认是 (0, 0, 0, 0)，这是无效取值，姿态定义随之失效；显式给 w = 1 得到单位旋转，这是消息构造里最容易被忽略的一行。（2）operation 字段缺省即 ADD，显式书写让代码意图可读，也让后续改成 REMOVE 或 MOVE 时改动点清晰。（3）publish 是异步调用，节点退出或立即规划都可能抢在场景处理之前，因此话题路径适用于"布置完成后统一等待与验证"的流程，不适用于"发布后马上规划"的紧耦合逻辑。

片段 3：C++ 生效确认

// 生效确认一：取回物体标识清单，核对新增物体是否在场景中
std::vector<std::string> ids = psi.getKnownObjectNames();

// 生效确认二：连同几何与位姿取回，把核对推进到内容层面
// 返回"标识到物体"的映射表；指定标识清单可以只看关心的对象
std::map<std::string, moveit_msgs::msg::CollisionObject> objects =
    psi.getObjects({ "work_table" });
auto it = objects.find("work_table");
if (it == objects.end())
{
  RCLCPP_ERROR(node->get_logger(), "工作台未进入场景，规划将缺失障碍约束");
}
else
{
  // 位姿单位米、四元数单位化；这里只抽查关注的分量
  RCLCPP_INFO(node->get_logger(), "工作台中心高度 %.3f m",
              it->second.pose.position.z);
}

解读：（1）getKnownObjectNames 回答"在不在"，getObjects 回答"对不对"，两级确认对应两类故障：写入路径断掉与位姿数值写错。（2）抽查位姿时核对的是消息里的量，与 RViz 显示互为印证；显示正常而消息错误、或消息正确而显示错位，分别指向不同的排查方向（前者查感知数据源，后者查可视化插件配置）。（3）把确认写进主控程序、减少对肉眼观察的依赖，是后续第 038 章阶段实践里"场景就绪门"的基础。

常见坑

  • 参考系错位：物体本体固定在工作台，位姿却用 base_link 描述。底盘移动后物体随坐标变换漂移，规划器绕行一个不再存在的障碍。修复是确认物体的运动学归属，固定物用 world 且保持该系稳定发布。
  • 尺寸语义误读：把 dimensions 当作半宽填入，几何只有实际的一半，路径贴着物体表面擦过。症状是规划结果"看似避障"但裕量极小。修复是核对消息定义：解析形状的尺寸全部为全尺寸。
  • 四元数缺省：只设置位置不设置姿态，默认全零四元数使旋转无效。症状是物体显示异常或碰撞检测结果与预期不符。修复是任何消息构造都显式给 orientation.w = 1.0（或真实姿态）。
  • 话题路径无回执：发布物体后立即调用规划，消息尚在传输路径上。症状是加物体后的第一次规划偶发失败或路径未绕行。修复是主控流程改用封装接口，或在规划前查询物体清单作为就绪条件。
  • 同名物体互相覆盖：多处代码各自写入 id 为 obstacle 的不同几何，后写的静默替换先写的。症状是障碍物内容与预期不符且难以定位来源。修复是全局统一命名规范，并在写入前查询既有清单。

练习与思考

  1. 形状语义：一个圆柱碰撞物体给出 dimensions = [0.03, 0.2]。解释两个数值的物理含义，并说明它最终覆盖的空间范围（半径与高）。★
    提示
    圆柱的 dimensions[0] 为半径、dimensions[1] 为高，因此覆盖半径 3 cm、高 20 cm 的圆柱体。与长方体不同，这里没有三个分量，残缺的数组会让检测器读到未定义值。
  2. 参数预测：把工作台盒体高度从 0.04 m 改为 0.08 m，位姿保持不变（中心仍在 z = -0.02）。上表面此时位于什么高度？对末端路径会带来什么变化？★
    提示
    中心 -0.02 加半高 0.04，上表面升到 0.02 m，比真实台面（z = 0）高出 2 cm；路径会相应抬高一截，若夹具接近工件的动作高度依赖台面标称值，会出现够不到或蹭到的情况。
  3. 设计题：为一台桌面装配工作站列出五个碰撞物体的定义要素表（id、参考系、几何、位姿、安全裕量），并说明哪个物体应该改用 base_link 参考系。★★
    提示
    典型清单：world 系的工作台、料箱、夹具底板、防护栏；随机器人整体移动的工装用 base_link 系。裕量建议 0.005–0.02 m，按感知误差与安装偏差选取。
  4. 诊断题：添加了一个手中障碍物后，规划结果与添加前完全相同。列出至少三种原因及验证手段。★★
    提示
    原因候选：物体未生效（查询清单）；物体位姿写到了工作空间之外（核对位姿）；物体恰好不在原路径附近（对比路径与障碍的几何距离）；规划器用了缓存或被其它约束限制（换目标重测）。
  5. 分析题：比较话题、服务、封装接口三条添加路径在"确认性、灵活性、可调试性"三个维度上的取舍，并为一个需要人机协作工位（操作员偶尔用 RViz 补加物体）的系统给出组合方案。★★★
    提示
    话题路径与人共享数据流、便于可视化调试；封装接口有确认、适合主控；服务路径居中。组合方案可以是"主控用封装接口管理程序化物体，操作员经 RViz 走同一条场景服务写入，两端统一命名规范与生效确认"。

小结

  • 碰撞世界是一张 id 到几何的映射表，标识唯一、位姿为快照、几何独立于机器人关节值。
  • 物体几何由两级位姿叠加表达：物体位姿放在参考系中，形状位姿放在物体内部；固定物体用 world，随动物体用 base_link。
  • 形状选择遵循代价谱系：解析形状优先，网格用于复杂轮廓并尽量保持凸性。
