第 017 章：规划请求参数与规划时间配置

本章建立完整的调参框架：规划时间、尝试次数、规划器标识与工作空间边界的作用链条，以及按失败模式分配预算的系统方法。

  • 主题：参数体系 / 规划请求调优
  • 关键机制：时间预算与尝试次数、规划器标识、工作空间边界
  • 预计学时：55 分钟
  • 前置章节：第 016 章

学习目标

  • 掌握规划请求层的参数全景：搜索参数、约束参数与后处理参数的分工。
  • 理解规划时间与尝试次数的语义关系，能评估两者乘积对任务周期的影响。
  • 理解规划器标识与管线配置的对应关系，知道名称错误的表现形式。
  • 会按失败模式建立调参顺序：先无解类、再超时类、最后质量类。
  • 能用重复实验的统计指标验证参数改动，拒绝依据单次运行下结论。

背景与动机

规划是随机搜索过程，同一目标两次规划的耗时与结果都可能不同，这给调参带来统计属性：单次结果不构成证据，需要重复实验。参数的影响也不独立：时间预算、尝试次数、规划器选择、工作空间边界各自作用于搜索的不同环节，改动一个参数往往改变另一个参数的边际效果。

本章的任务是把调参从试错变为工程方法：先测量基线，再按失败模式分类，然后对单参数做扫描实验，最后用统计指标固化配置。这套方法在第 018 章的验收指标与第三篇的规划器选型中会直接复用。调参的对象始终是"预算与约束的分配"，其成败由概率与统计规律决定。

核心原理

本节解释参数的分类与作用链条、时间与尝试的语义、规划器标识的机制，以及工作空间边界的影响。

1. 参数全景：四类参数，四个消费方

类别典型参数消费方影响阶段
搜索参数规划时间、尝试次数、规划器标识规划管线与采样规划器路径搜索
约束参数工作空间边界、目标容差请求适配器与规划器搜索空间裁剪与目标判定
后处理参数速度缩放、加速度缩放时间参数化轨迹时间轴
执行参数控制器选择执行组件轨迹下发

四类参数沿请求链路依次消费：请求进入管线后先经过适配器做约束与边界处理，再交给规划器搜索，成功后进入后处理，最后移交执行。排错时的第一条定位规则由这张表给出：先确定症状出现在哪一阶段（搜索失败、轨迹节奏不对、执行被拒），再检查对应类别的参数，避免把执行问题当搜索问题调。

2. 规划时间与尝试次数的语义

规划时间约束单次尝试的搜索时长；尝试次数让规划器以不同的随机序列重启。两者的组合决定了搜索的总预算：每次尝试独立获得时间预算，最坏情况下的总耗时接近两者乘积（具体叠加语义以对应版本的官方文档为准）。

总预算 ≈ 单次时间 × 尝试次数；成功率随预算增长但边际递减 任务周期允许的最大延迟决定了乘积的上限

两个旋钮的作用方式不同：提高时间让单次搜索走得更深，适合"路径存在但隐藏较深"的场景；提高尝试次数提供独立的重新开始，适合"搜索容易陷入坏随机序列"的场景。实践中的建议是先提高尝试次数（成本确定，收益稳定），当单次搜索确实需要更长时间推导时才提高单次时间。两者的乘积必须写入任务预算约束，防止难解目标把整条产线的节拍拖垮。

3. 规划器标识与管线配置

规划器标识是管线内部算法配置的名称：管线配置文件为每个算法定义参数块，请求通过标识选中其中一个。标识名称错误或未被管线定义时，请求会报无效规划器（部分版本行为是回退默认，需以文档为准）。不同规划器的特点属于第三篇主题，本章只建立"标识是配置的引用键"这一概念。

默认标识在管线配置的默认项中指定，接口层不设置时使用默认值。一个稳健做法是把可用标识清单与任务代码一起维护：排错时先用清单核对拼写，再考虑算法本身，这个顺序与第 002 章的"先接口后逻辑"一致。

4. 工作空间边界：搜索空间的裁剪

工作空间边界用矩形盒定义规划器采样与路径的有效区域。它有两类用途：一是缩小搜索范围，让采样集中在机器人实际工作的区域内；二是防错，避免仿真环境中规划出把手臂伸出工作站范围的结果。

边界过紧的失败模式需要重点记住：目标明明可达，请求却报无效或直接无解，因为目标点或路径上的必经点落在边界之外。边界应与工作台的实际尺寸加安全余量一致，扩大容易收紧难；每次调整边界后，把边缘区域的典型目标重新跑一遍回归，确认没有误伤。

5. 失败模式与调参顺序

规划失败先分类，后调参：

  1. 无解类（目标不可达、被碰撞包围）：调参无效，先修正目标或场景。
  2. 超时类（搜索未收敛）：提高尝试次数与时间，或更换规划器。
  3. 离群类（成功但轨迹怪异）：检查目标容差与工作空间裁剪，必要时更换规划器。
  4. 执行类（规划成功但执行失败）：属于第 014 章的范畴，不要在此处调搜索参数。

调参的统计纪律：同一配置重复运行不少于 30 次，报告成功率与耗时中位数，两个配置的对照要固定随机条件之外的一切变量。请求的随机序列通常不可复现，报告分布是唯一诚实的方式；中位数比均值更能抵抗偶发长尾的干扰。

实现思路与设计

调参按五步推进：基线、分类、扫描、交叉、固化。

  1. 基线测量：固定全部参数，重复 30 次记录成功率与耗时中位数。
  2. 失败分类：对失败样本按无解、超时、其他分类，确定主攻方向。
  3. 单参数扫描：一次只改一个参数，取 3 个水平形成对照。
  4. 交叉验证：把最优单参数组合起来复测，确认效果叠加。
  5. 固化配置：把参数写入配置文件并注明依据与测量数据。

参数建议起点作用何时提高

尝试次数10独立重启次数成功率受随机波动影响大

设计决策：为什么先调尝试次数再调单次时间？

尝试次数的收益曲线更稳定：独立重启避开了单次搜索陷入的坏路径，成本上每次尝试的时长有明确上限，总预算可控。单次时间的收益曲线更陡峭也更危险：简单场景中大部分时间被浪费，难解场景中又未必收敛。先在尝试次数上找到成功率的平台段，再对仍超时的目标动单次时间，最后才考虑更换规划算法。这个顺序在第 060 章的规划器选型实验中被验证会得到更一致的结论。

关键代码与解读

本节给出三段片段：接口层的参数设置、管线 YAML 中的规划器配置、以及基准测量脚本。

片段 1：接口层参数设置

// 搜索参数：时间与尝试的乘积构成最坏耗时，按任务周期设定
group.setPlanningTime(1.0);        // 单次尝试的时间预算（秒）
group.setNumPlanningAttempts(10);  // 独立重启次数

// 规划器标识：名称必须在管线配置中有对应定义
group.setPlannerId("RRTConnectkConfigDefault");

// 工作空间边界：按工作站尺寸加余量，约束采样区域
// 参数顺序为最小点与最大点的各三个坐标
group.setWorkspace(-0.8, -0.8, 0.0,    // xyz 最小
                    0.8,  0.8, 1.2);   // xyz 最大

// 目标容差：与第 012 章的约束容差互补，这里是请求级的兜底
group.setGoalJointTolerance(0.01);
group.setGoalPositionTolerance(0.005);
group.setGoalOrientationTolerance(0.01);
// 以上参数作用于随后的 plan() 调用，逐次设置逐次生效

解读：参数设置的作用域是下一次规划调用，逐次重设是安全习惯。（1）时间与尝试写成相邻两行，注释把两者的乘积关系显式化，评审配置时一眼可见最坏耗时。（2）规划器标识的注释强调"配置中有定义"这一前提，把拼写类错误挡在规划之前。（3）工作空间边界用最小最大点成对表达，坐标顺序写清楚，避免把范围与单点混填；目标容差与约束容差并存时的取舍规则以对应版本文档为准。

片段 2：管线 YAML 中的规划器配置

# ompl_planning.yaml 摘要：每个标识一个参数块，供请求按名选用
# 请求中的完整标识可能带参数化后缀（版本相关），实际名称用规划器参数查询核对
planner_configs:
  RRTConnect:
    type: geometric::RRTConnect
    # 连接尝试的步长：过大易跳过窄通道，过小探索慢
    range: 0.0
  RRTstar:
    type: geometric::RRTstar
    range: 0.0
    # 目标偏置概率：0.05 表示 5% 的采样直接瞄准目标附近
    goal_bias: 0.05

arm:
  # 组级默认：接口不设置标识时使用 default_planner_config
  default_planner_config: RRTConnect
  planner_configs:
    - RRTConnect
    - RRTstar
  # 最长有效段比例：碰撞检查密度的管线级默认值（请求显式设置时以请求为准）
  longest_valid_segment_fraction: 0.05

解读：YAML 定义了标识与算法参数的对应关系。（1）标识块与组配置分离：同一算法可以为不同组配不同参数，请求通过标识名引用。（2）注释解释参数语义：range 与 goal_bias 这类参数的行为描述帮助后来者按场景调整，名字复述只是冗余。（3）组级默认值是与接口设置的对接点：接口未设置时用默认，设置时以请求为准；两处配置的优先级关系应在任务文档中写清，避免"改了 YAML 却没生效"的困惑。

片段 3：基准测量脚本

import statistics
import time

def benchmark(plan_once, target_name, trials=30):
    """对同一目标重复规划：统计成功率与耗时中位数。

    plan_once: 可调用对象，执行一次规划并返回成功与否
    trials: 重复次数，30 次起步，样本过少会被随机波动主导
    """
    durations, successes = [], 0
    for i in range(trials):
        t0 = time.perf_counter()
        ok = plan_once(target_name)
        durations.append(time.perf_counter() - t0)
        successes += 1 if ok else 0
    rate = successes / trials
    # 中位数抵抗偶发长尾；均值会被少数超时样本拉高
    median = statistics.median(durations)
    p90 = sorted(durations)[int(0.9 * (trials - 1))]
    print(f"目标 {target_name}：成功率 {rate:.2f}，"
          f"中位耗时 {median:.3f} s，P90 耗时 {p90:.3f} s")
    return rate, median, p90

# 用法：同一目标在两组参数配置下各跑一轮，对照成功率与 P90
# 结论判据：成功率差大于随机波动范围，且 P90 在任务周期预算之内

解读：统计框架是把调参变成实验的基础设施。（1）成功率与耗时分开报告：两者回答不同问题，成功率决定可用性，耗时决定节拍。（2）中位数与 P90 并列：中位数描述典型体验，P90 描述必须在任务周期内兜住的尾部；只看均值会同时低估典型情况的稳定性和高估尾部的风险。（3）脚本把"重复 30 次"的纪律固化为默认参数，评审实验结论时先看样本量，再看指标。

常见坑

  • 只调时间不换方向：无解类失败被误判为超时，时间加到很大仍然失败。修复：先分类失败原因，无解类问题回到目标与场景层解决。
  • 忽略预算乘积：尝试次数提高后最坏耗时超出任务周期，产线节拍被个别难解目标拖垮。修复：把乘积写入预算上限并在基准测试中验证 P90。
  • 规划器标识拼写错误：报无效规划器，或落入默认配置使结果与预期不符。修复：标识名称从管线配置复制，不手工输入。
  • 工作空间边界过紧：可达目标被判无效，症状与目标不可达相似。修复：逐轴核对边界与工作站尺寸；边缘目标做回归验证。
  • 单次实验下结论：随机采样下两次运行差异不足以支撑调参决策。修复：重复 30 次以上，比较成功率与 P90 等分布指标，拒绝以单次耗时判定优劣。

练习与思考

  1. 对一条命名位姿目标做 30 次规划，记录成功率与耗时中位数、P90，形成本环境的基线数据。★
    提示
    基线数据要连配置一起记录：时间、尝试次数、规划器标识；没有配置上下文的数字无法用于后续对照。
  2. 把规划时间分别设为 0.2 s、1.0 s、5.0 s 各跑一轮基准，绘制"时间预算与成功率"的趋势，说明边际收益的变化。★★
    提示
    简单目标上三档差异很小，说明预算未成为瓶颈；若某目标在后两档才稳定成功，说明其搜索需要更深的探索。
  3. 预测实验：把工作空间边界从 ±0.8 m 收缩到 ±0.4 m，预测哪些目标类别的失败率上升，并说明失败信息的变化。★★
    提示
    边界外的目标与路径经过边界外的目标会集中失败；失败信息可能从"无解"变为"无效请求"或目标被裁剪后的无解。
  4. 设计题：为一条含 5 类典型目标的产线编写调参协议：基线测量方法、失败分类表、单参数扫描顺序、验收指标与配置固化格式。★★★
    提示
    协议要能被他人在新环境上重复执行；固化格式包含参数值、测量数据与生效范围，三者缺一不可。

小结

  • 规划参数沿链路分四类：搜索、约束、后处理、执行；排错先定位阶段再选参数。
  • 时间与尝试构成总预算，乘积受任务周期约束；先调尝试次数，再考虑单次时间。
  • 规划器标识是管线配置的引用键，名称与配置一致是前提。
  • 工作空间边界裁剪采样区域，过紧会制造"假不可达"。
  • 调参遵守统计纪律：重复 30 次以上，报告成功率与 P90，拒绝单次结论。
