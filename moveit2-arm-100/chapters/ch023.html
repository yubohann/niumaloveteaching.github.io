第二篇 · 规划场景与碰撞管理

第 023 章：移除与更新碰撞物体

场景内容是活的：工件被取走、托盘被搬移、工位重新布局。本章讲移除（REMOVE）、移动（MOVE）、追加（APPEND）的操作语义，两种更新策略的取舍，差分传播路径，以及避免"幽灵物体"堆积的一致性维护方法。

  • 主题：规划场景生命周期 / 物体更新与清理
  • 关键机制：操作语义、场景差分（Diff）传播、批量写入与对账清理
  • 预计学时：45 分钟
  • 前置章节：第 022 章

学习目标

  • 掌握碰撞物体的四种操作语义：添加（ADD）、移除（REMOVE）、移动（MOVE）、追加（APPEND），明确每种操作的输入要求与边界。
  • 能对比"移除再添加"与"原地移动"两种更新策略的代价与语义差异，并按物体变化频率做出选择。
  • 理解场景差分（Planning Scene Diff）的传播机制，知道更新为什么必须确认、确认什么。
  • 会设计场景内容的一致性维护（对账）流程，用固定标识集合防止失效物体堆积。
  • 能诊断"移除未生效""更新后规划仍按旧几何"两类典型故障。

背景与动机

第 022 章把碰撞物体写入规划场景，那只是生命周期的开始。真实工位上的物体不断变化：料箱被取空、工件被取走、托盘在传送带上移动、工装被重新摆放。规划场景中的几何若停留在旧状态，会产生两类后果。第一类是"幽灵障碍"：物体实际已经不在了，规划器仍然绕行它，路径质量下降甚至完全无解；第二类是"过期几何"：物体已经移动或变形，规划器按旧形状计算，生成的轨迹在真机上发生碰撞。

场景内容的正确性依赖两条纪律：更新要及时，移除要确认。本章把碰撞物体当作受生命周期约束的场景资源来讲解：先理清四种操作的语义边界，再讨论两种更新策略在代价上的差异，最后给出防堆积的一致性维护方法。第 024 章将继续下沉一层，解剖 CollisionObject 消息本身的字段设计。

核心原理

1. 四种操作的语义边界

对场景的每次写入都带一个操作字段，取值为 ADD、REMOVE、MOVE、APPEND 四者之一。它们的分工如下表：

操作取值需要的输入语义
ADD0id、参考系、几何、位姿把物体加入世界；对已存在的同名物体，几何数据如何合并属于实现细节，工程上不应依赖
REMOVE1id（几何可缺省）从世界移除同名物体，移除后该标识空闲可复用
APPEND2id、几何、位姿向已存在的物体追加几何形状，用于多形状组合
MOVE3id、参考系、位姿（几何可缺省）只更新已存在物体的位姿，几何保持不变

这张表里有三个容易被忽视的事实。（1）REMOVE 与 MOVE 只需要标识定位，几何数据不参与定位；给它们附带几何会被忽略，正确性取决于 id 是否与场景中的既有项一致。（2）APPEND 与 ADD 的区别在"合并还是新建"：需要在一个标识下表达多块几何（比如一张带四角支柱的工作台）时，APPEND 让改动指哪打哪，也避免重传既有几何。（3）重复 ADD 的行为在不同实现版本间存在差异，把它当作"覆盖写入"使用会在升级时埋下行为变化，显式使用 REMOVE 加 ADD 或 MOVE 才能让意图稳定。

2. 更新策略：移除再添加与原地移动

几何或位姿发生变化时，有两种标准更新路径，代价差别来自"几何是否需要重建"：

策略 A（通用）：REMOVE(id) 然后 ADD(id, 新几何, 新位姿)，几何与位姿都可变，代价含一次几何构建
策略 B（轻量）：MOVE(id, 新位姿)，只更新变换矩阵，代价不含几何重建

策略 A 的表达力完整：几何尺寸变了、换成另一种形状，都能通过这一条路径完成。策略 B 只对"刚性物体改变位置"有效，它的写入代价在上表中最低，因为碰撞世界内部只需要更新该物体的空间包围体，不必重建三角形与包围盒层次。选择准则是物体几何是否变化：几何不变而位置频繁变化（传送带、动态托盘、协作区人体占位盒），用 MOVE；几何本身变化（工件被切削、料箱被取空），用 REMOVE 加 ADD。对于每秒数十次的跟踪类更新，MOVE 通常是唯一现实的方案；对于每分钟几次的状态切换，策略 A 的清晰语义优先。

3. 差分传播：广播的是变化量

场景更新在系统内部的传递单位是差分（Diff）：一次写入产生一条"某个 id 发生了什么操作"的记录，通过场景话题与监视场景话题传播给订阅方。规划场景监视器把差分合并进本地场景副本，RViz 用它驱动显示。差分机制带来两个推论：

  • 更新与可见性之间存在时序间隙。写入接口返回成功，表示差分已经进入系统并被目标场景确认；其它订阅方的本地副本按各自的订阅节奏刷新，短暂的观察差异属于正常现象。
  • 差分可能被节流。监视场景话题常带发布频率限制，调试时用一次性订阅抓到的快照可能是旧内容。核对场景状态应优先走查询服务，或让程序查询物体清单，避免依赖对话题的肉眼观察。

这解释了一个常见困惑："代码明明执行了移除，规划还是绕行"：规划用的是规划场景监视器本地副本，若移除差分因路径故障未能送达，两者从此刻起永久分叉。写后确认是防止分叉的唯一手段。

4. 一致性维护：对账清理

长期运行的系统里，场景物体清单会缓慢偏离预期：任务被中断导致移除没执行、测试脚本留下了临时物体、感知节点反复用时间戳生成新标识。清理的通用方法是把场景内容当作集合来对账：

G = Snow - Sexpected Snow 为场景中当前全部 id 的集合，Sexpected 为本程序负责维护的 id 集合，G 为垃圾集合，逐项移除

执行对账的前提是程序始终使用固定、可枚举的标识集合，并在程序内部记录"我添加过哪些 id"。动态感知产生的物体走独立命名前缀（第 034 章展开），与任务物体的标识域分开维护，避免对账时误删其它来源的物体。标识域划分与固定集合，是场景长期稳定运行的两个支点。

实现思路与设计

把更新与移除工程化的六个步骤：

  1. 建立标识台账：程序内部维护"用途到 id"的固定映射，所有写入与移除都通过台账取值，消除散落的字符串字面量。
  2. 按变化频率选策略：几何不变的高频跟随用 MOVE；几何或形状变化用 REMOVE 加 ADD；批量场景切换用批量接口一次提交。
  3. 成对操作减少瞬态：同一 id 的替换尽量放进一次场景差分（多条操作一次提交），让订阅方看不到"缺项"的中间状态。
  4. 写后确认：每次批量更新后查询物体清单，核对标识集合与预期一致。
  5. 周期对账：按任务节拍执行垃圾集合计算与清理，清理动作同样走确认路径。
  6. 失败处理：移除不存在的 id 属于可容忍错误（记录并继续）；计划内物体缺失属于致命错误（中止任务并上报）。两类结果的判定依据来自清单查询。

场景变化内容推荐策略理由

关键代码与解读

片段 1：C++ 单个移除、批量移除与替换模式（接口以对应 ROS2 发行版与 MoveIt2 版本的官方文档为准）

// 单个移除：只需要 id 与参考系，几何数据不参与定位
moveit_msgs::msg::CollisionObject gone;
gone.header.frame_id = "world";
gone.id = "part_a";
gone.operation = moveit_msgs::msg::CollisionObject::REMOVE;
psi.applyCollisionObject(gone);   // 同步接口：提交差分并等待场景确认，返回后可查询

// 批量移除：一次往返处理一组标识，适合工位切换与测试收尾
std::vector<std::string> stale_ids = { "fixture_left", "bin_upper", "debris_1" };
psi.removeCollisionObjects(stale_ids);

// 几何变化的替换模式：REMOVE 与 ADD 之间场景短暂缺项
// 若执行体恰好在中间窗口读取快照，会看到"物体暂不存在"的瞬态
psi.removeCollisionObjects({ "part_a" });
// 随后按第 022 章的方式写入新几何的同名物体
// 需要原子替换时改用一次场景差分携带两条操作（见片段 3）

解读：（1）REMOVE 消息体是"轻"的，正确性完全落在 id 与参考系两个字段上：id 写错会移除失败或误伤同名单词，参考系字段保持与添加时一致是排错时的第一检查点。（2）批量接口减少与场景服务的往返次数，十个物体的清理从十次往返压缩为一次，在紧周期任务里有实际收益。（3）替换模式的两步之间存在瞬态窗口，注释点明了它的存在与规避方向：把两条操作放进同一次差分，是并发读取场景时的正确做法。

片段 2：Python 用 MOVE 跟踪动态托盘

def follow_pallet(self, x, y, z):
    """让场景中的托盘位姿跟随上位系统给出的实时位置。

    高频更新场景中只发 MOVE：几何数据保持不变，
    碰撞世界内部只更新该物体的包围体，避免每周期重传与重建网格。
    """
    obj = CollisionObject()
    obj.header.frame_id = "world"
    obj.id = "pallet_1"                # 必须与场景中已有物体完全一致
    obj.pose.position.x = x
    obj.pose.position.y = y
    obj.pose.position.z = z
    obj.pose.orientation.w = 1.0       # 单位旋转，托盘保持水平
    # 操作字段选择 MOVE；若误用 ADD，语义退化为未定义的合并行为
    obj.operation = CollisionObject.MOVE
    self.pub.publish(obj)

解读：（1）MOVE 的代价优势来自它跳过了几何构建：网格物体的三角形与包围盒层次保持原样，只替换变换。对 10 Hz 以上的跟踪更新，这一差异从"可用"变成"不可用"的分界线。（2）注释特意标注"不能误用 ADD"：ADD 遇到已存在 id 的合并行为属于实现细节，用它承载高频更新会在版本升级时出现不可预期行为。（3）位姿中的位置分量来自上位系统的实时数据，写入前应做量程与突变检查（例如单周期位移超过 0.3 m 时拒绝该帧），防止上游数据异常把障碍物写到错误位置。

片段 3：Python 用一次场景差分完成原子替换

import rclpy
from rclpy.node import Node
from moveit_msgs.msg import CollisionObject
from moveit_msgs.srv import ApplyPlanningScene

class SceneUpdater(Node):
    """用一次场景差分原子地完成"移除旧件 + 添加新件"。"""

    def __init__(self):
        super().__init__("scene_updater")
        # 同步服务路径：返回结果可判成败，适合替换这类关键写入
        self.cli = self.create_client(ApplyPlanningScene, "apply_planning_scene")
        while not self.cli.wait_for_service(timeout_sec=1.0):
            self.get_logger().info("等待场景服务可用")

    def replace(self, old_id, new_obj):
        req = ApplyPlanningScene.Request()
        remove = CollisionObject()
        remove.header.frame_id = "world"
        remove.id = old_id
        remove.operation = CollisionObject.REMOVE
        # 差分的多条操作在同一次场景更新中处理
        # 订阅方只会看到"旧的已去、新的已来"这一个结果状态
        req.scene.world.collision_objects = [remove, new_obj]
        future = self.cli.call_async(req)
        rclpy.spin_until_future_complete(self, future, timeout_sec=2.0)
        result = future.result()
        return result is not None and result.success

解读：（1）场景差分的处理是批量的：同一份 PlanningScene 消息里的操作序列在一次更新中生效，这为"替换"提供了原子性的实现手段，消除了片段 1 中两步替换的瞬态窗口。（2）服务调用带超时并检查 success，把"写失败"变成了可编程的返回值；主控流程据此决定重试或中止，避免盲目继续规划。（3）wait_for_service 放在构造阶段，替换逻辑保持纯粹；若放到每次调用里，服务重启会带来重复等待，拖长任务节拍。

常见坑

  • 把重复 ADD 当覆盖写：加载两个版本的场景脚本，第二个脚本对同名物体用 ADD，期望覆盖第一个。不同实现版本对几何合并的处理存在差异，升级后行为变化。修复是替换一律走 REMOVE 加 ADD 或 MOVE。
  • 移除无确认：话题路径发送 REMOVE 后直接进入下一次规划，差分未送达时规划仍按旧几何运行。症状是"偶然绕行消失的物体"。修复是主控流程改用完整服务路径并核对返回结果。
  • MOVE 承载了几何变化：工件被切削后尺寸改变，更新代码只发 MOVE。症状是新几何从未生效、检测仍按旧尺寸。修复是几何变化一律 REMOVE 加 ADD，MOVE 只用于刚性移动。
  • 标识域混用：任务物体与感知物体共用普通命名，对账清理时把感知生成的物体一并移除。症状是视觉噪音物体不断被删又不断重建。修复是给不同来源划分命名前缀（任务用 task_、感知用 sensed_），对账只处理自己的区域。
  • 垃圾堆积拖慢规划：每次任务生成带序号的新 id 却从不清除，场景物体数量随运行时长增长，包围体层次更新与碰撞检测候选对数量随之增加。修复是固定 id 集合加周期对账，把物体数量控制在常数级。

练习与思考

  1. 操作选择：一台传送带以 2 m 每分钟的速度搬运料箱，需让规划场景中的障碍物跟随真实料箱。应使用哪种操作？如果料箱中途被取走半箱物料导致几何变化，更新路径变成什么？★
    提示
    位置跟随用 MOVE；几何变化必须 REMOVE 加 ADD。两者可以共存：同一物体在稳定阶段高频 MOVE，内容变化时做一次替换。
  2. 参数预测：某个动态障碍以 20 Hz 更新。分别估算使用 MOVE 与使用 REMOVE 加 ADD 时，每秒的几何重建次数（网格约含 5000 个三角形）。这个差异对规划节拍意味着什么？★
    提示
    MOVE 方案每秒重建 0 次；REMOVE 加 ADD 方案每秒重建 20 次，即每秒重新处理约 10 万个三角形构成的空间结构。高频跟踪场景下前者通常是唯一可行的选择。
  3. 设计题：为一条多工位流水线设计场景对账流程，要求写出垃圾集合的判定规则、清理时机与失败处理，并说明如何与感知物体的命名域隔离。★★
    提示
    判定规则用本章公式 G = Snow - Sexpected；清理时机放在工位切换或任务收尾；失败处理区分"移除不存在"（可容忍）与"计划内物体缺失"（致命）。命名隔离用统一前缀。
  4. 诊断题：代码发送了 REMOVE，RViz 中物体消失，但规划仍绕行该区域。列出至少三种原因与验证方法。★★
    提示
    候选原因：规划场景监视器未收到差分（查询物体清单确认两端状态）；存在同名的第二个物体或附加物体仍在场景中（检查清单与附加物体列表）；规划使用了缓存的旧场景或旧目标（重发规划请求复测）。
  5. 分析题：从订阅方视角分析"REMOVE 与 ADD 分成两次写入"与"一次差分携带两条操作"的差异，说明原子替换在什么场景下是必要的，并给出一个不使用差分也能规避瞬态的替代方案。★★★
    提示
    两次写入之间存在中间态，若此时有执行体读取场景快照做碰撞判断，可能误判物体缺失；一次差分让所有订阅方只看到结果态。替代方案：先 ADD 新 id、确认生效后再 REMOVE 旧 id，用"双标识并存"的短暂重叠换取无缺项窗口，代价是两物体短时共存。

小结

  • 四种操作各有边界：ADD 建立、REMOVE 清除、MOVE 只改位姿、APPEND 追加几何；工程代码不应依赖重复 ADD 的合并行为。
  • 更新策略按几何是否变化选择：刚性移动用 MOVE，内容变化用 REMOVE 加 ADD，批量切换用批量接口。
  • 场景以差分传播，写入成功与订阅方可见之间存在时序间隙，写后确认是防止场景分叉的唯一手段。
  • 一致性维护用对账：固定标识台账加垃圾集合清理，标识域按来源划分。
  • 下一章深入消息本身：CollisionObject 的字段组织，理解每一层数据结构的设计意图。
