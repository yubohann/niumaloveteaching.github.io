第一篇 · 环境搭建与基础控制

第 001 章：MoveIt2 框架总览与生态定位

先建立全图：一个目标位姿如何经过构型空间搜索、碰撞校验与时间参数化，变成控制器能执行的关节轨迹，以及 MoveIt2 各组件在这条数据流上的分工。

  • 主题：框架架构 / 运动规划系统总览
  • 关键机制：move_group 中枢、规划管线（Planning Pipeline）、构型空间（Configuration Space）
  • 预计学时：55 分钟
  • 前置章节：无（本课程从这里开始）

学习目标

  • 建立 MoveIt2 的五层架构心智模型：用户接口层、规划核心层、算法插件层、场景层、机器人接口层。
  • 理解运动规划问题的形式化表述：构型空间（Configuration Space, C-space）、障碍映射 Cobs、路径与轨迹的区别。
  • 说清 move_group 节点为什么同时暴露 Action、Service、Topic 三类接口，以及每类接口适合的调用场景。
  • 掌握 MoveIt2 与 ROS2、ros2_control、RViz、OMPL、FCL 等组件的依赖关系与数据流向。
  • 能画出从目标位姿到关节执行指令的完整数据流，并指认每一步由哪个组件负责。

背景与动机

机械臂的控制问题可以浓缩成一句话：给定一个目标，求出关节空间中的一条可行运动。手工推导逆解只能应付结构简单的机械臂，一旦加入避障、关节限位、轨迹平滑度等要求，就需要一套完整的运动规划系统。

MoveIt2 是 ROS2 生态中的运动规划框架（Motion Planning Framework），它把采样规划、逆运动学（Inverse Kinematics, IK）、碰撞检测、场景管理、轨迹后处理这些子系统组织成一个可配置的整体。初学者常见的困难在于组件太多：move_group、PlanningScene、OMPL、ros2_control 各自是什么、边界在哪里。如果先动手配置却不清楚数据流，遇到规划失败时只能凭猜测调参数。

本章先给出全局视图，后续章节都在这个视图上逐块展开：环境与模型（002 至 005）、接口与状态表示（006 至 009）、关节空间与笛卡尔空间运动（010 至 012）、接口风格与轨迹执行（013 至 017）、阶段实践（018）、规划场景（019 至 020）。先看清系统边界，再深入每一个组件。

核心原理

本节的原理主线有两条：运动规划问题的数学形式，以及 MoveIt2 为求解该问题搭建的软件结构。

1. 运动规划问题的形式化

一个 n 自由度机械臂的位形（Configuration）可以用 n 个关节变量组成的向量 q 描述。全部合法 q 构成的空间称为构型空间 C。六轴机械臂的 C 是六维空间；加入夹爪的两个指关节后，系统维度上升为 8 维。空间中每个点对应机械臂的一个完整姿态，这个性质把"避障"翻译成了纯几何问题：环境中的障碍物映射到 C 中形成障碍区域 Cobs，其余部分称为自由空间 Cfree。

C = Cfree ∪ Cobs，规划输出为连续曲线 τ: [0, 1] → Cfree，τ(0) = qstart，τ(1) = qgoal 曲线 τ 是路径（Path）；给路径的每个点补上时间戳、速度后成为轨迹（Trajectory）

维度对问题的难度影响是根本性的。C 的栅格化描述随维数指数增长，六维空间即使每维只分 100 格也是 1012 个单元，穷举搜索不可行。采样规划（Sampling-based Planning）放弃完整枚举，改用随机采样加图搜索，把复杂度从维数指数降到与维数近似线性，这是 OMPL 类规划器的理论出发点。采样规划具有概率完备性（Probabilistic Completeness）：给定足够时间，只要解存在，找到解的概率趋近于 1。

2. 规划与执行分离的整体结构

运动规划的输出是一条关节空间轨迹，而机械臂执行需要控制器把轨迹转成伺服指令。MoveIt2 把这条链路分成三段：规划（Planning）在 C 空间求解，后处理（Time Parameterization）给路径补时间信息，执行（Execution）把轨迹交给控制器。三段之间通过标准消息传递，任意一段出问题都可以单独诊断。

层次职责典型对象出问题时的症状

排障顺序与传统多层系统一致：先确认机器人模型与 TF 正确，再确认场景与状态新鲜，再检查规划请求参数，最后才怀疑算法本身。越靠下的层错误越隐蔽，也越容易伪装成上层的"规划失败"。

3. move_group：一个节点，三类接口

move_group 是 MoveIt2 的主要执行节点，它聚合了规划管线、场景监视、IK 求解与执行转发。对外它同时提供三类通信接口：

  • Action（例如 MoveGroup action 与 ExecuteTrajectory action）：承载"规划并执行"这类长耗时、可取消、需要反馈的任务。目标（Goal）、反馈（Feedback）、结果（Result）三元组正好匹配规划过程的语义。
  • Service（例如获取规划场景、计算 IK/FK 的查询服务）：承载一问一答的短请求，延迟低，无中间状态。
  • Topic（例如关节状态、规划场景发布、显示用轨迹）：承载持续数据流，供 RViz 等观察者消费。

三类接口的选择依据是任务的时间尺度与交互模式：一次规划可能耗时 0.5 至 5 s，期间用户可能想取消，因此规划走 Action；查询当前末端位姿只需几毫秒，走 Service；关节状态以 100 Hz 持续发布，走 Topic。

4. 从目标到执行的数据流

把上述组件串起来，一次典型的规划请求经历七步：

  1. 用户接口把目标（命名位姿、关节角向量或末端位姿）封装为规划请求（MotionPlanRequest）。
  2. 规划请求经过适配器链（Request Adapters）预处理，例如修正起始状态、添加时间参数化。
  3. 规划管线调用采样规划器，在 C 空间中扩展搜索树或路线图。
  4. 每个候选状态都经过碰撞检测（FCL 库），确认机器人自身与场景无干涉。
  5. 求解成功后的路径经过时间参数化，得到带时间戳与速度的轨迹。
  6. 轨迹返回用户接口；选择执行时转发给控制器（例如关节轨迹控制器 Joint Trajectory Controller）。
  7. 控制器通过 ros2_control 驱动关节，完成物理运动。

数据流的关键分界在轨迹：规划阶段只对几何负责，执行阶段只对时间与动力学负责。理解这一点，才能理解为什么每次调参或排错都要先判断问题出在分界的哪一侧。

5. 生态定位

MoveIt2 处在 ROS2 机械臂软件栈的中层：上游依赖 URDF（Unified Robot Description Format）与 SRDF（Semantic Robot Description Format）提供模型与语义，下游依赖 ros2_control 与硬件驱动完成执行，周边集成 OMPL（Open Motion Planning Library）、FCL（Flexible Collision Library）、IK 插件、RViz 可视化插件。MoveIt2 的角色是调度者与标准制定者：它定义组件之间的接口，具体算法以插件形式接入。这一插件化设计意味着更换规划器或 IK 求解器通常只需修改 YAML 配置，不必改动上层调用代码。

实现思路与设计

理解框架之后，落地一个机械臂规划系统可以按固定顺序推进：先是模型，再是配置，然后是接口，最后是执行。本节给出这条路线与组件清单。

从零到可规划系统的六步路线

  1. 环境准备：安装与 ROS2 发行版匹配的 MoveIt2 二进制包，验证官方演示可运行（第 002 章）。
  2. 机器人建模：编写 URDF 或 Xacro 描述链接、关节、惯量与碰撞体（第 003 章）。
  3. 生成配置：用 Setup Assistant 把 URDF 加工成包含 SRDF、规划组、控制器参数的 MoveIt 配置包（第 004 章）。
  4. 可视化验证：在 RViz 的 MotionPlanning 插件中检查模型、规划组与交互式标记是否正确（第 005 章）。
  5. 代码接口：用 Python 或 C++ 接口发出第一个规划请求（第 006 至 008 章）。
  6. 目标与执行：区分关节空间与笛卡尔空间目标，配置规划参数，打通控制器执行（第 010 至 017 章）。

设计决策：为什么规划与执行分成两个 Action？

规划是纯计算过程，可在任意硬件上复现；执行涉及物理运动，有安全风险。把两者拆成独立的 Plan 与 Execute 两个阶段后，用户可以先检查轨迹（合法性、路径长度、是否接近奇异位形）再决定是否执行。这种"先看后执行"的模式是调试期安全性的基础。第 058 章会深入两个 Action 的消息结构，本课程 001 至 020 章使用的高层接口都建立在它们之上。

关键代码与解读

本节用三个片段展示同一件事在三种入口下的表达：Python 高层接口、C++ 高层接口、launch 启动编排。三者的调用对象都是 move_group，差别只在进程内还是进程外、静态语言还是脚本语言。

片段 1：Python 入口（moveit_py 高层接口）

import rclpy
from moveit.planning import MoveItPy          # 官方 Python 接口；模块路径随发行版演进

rclpy.init()
# MoveItPy 在进程内构建规划组件，省去与独立 move_group 进程的序列化开销
arm = MoveItPy(node_name="overview_demo")
group = arm.get_planning_component("arm")     # 规划组名称由 SRDF 定义，代码只引用名称

# 目标写成命名位姿：名称在 SRDF 的 group_state 中集中定义，避免硬编码关节角
group.set_goal_state(configuration_name="ready")

# plan() 内部走完整管线：请求适配、采样搜索、碰撞校验、时间参数化
plan = group.plan()
# execute() 把轨迹转交控制器；规划与执行分离，失败可分别定位
# 结果对象携带轨迹字段，成功时经 trajectory 属性取出
arm.execute(plan.trajectory, controllers=[])
rclpy.shutdown()

解读：这段代码浓缩了框架的调用范式。（1）规划组名称 "arm" 是配置期定义、运行期引用的符号，模型结构变化只影响配置包，不动调用代码。（2）set_goal_state 接受多种目标形式（命名位姿、关节值、位姿约束），本章先看命名位姿，第 012 章展开全部形式。（3）plan() 与 execute() 分离对应前文数据流分析：plan 只产出轨迹，execute 才触碰物理世界。旧版接口把两步合并为 plan_and_execute，能力等价，拆分形式更便于调试。

片段 2：C++ 入口（MoveGroupInterface 门面）

#include <rclcpp/rclcpp.hpp>
#include <moveit/move_group_interface/move_group_interface.h>   // 新版发行版中为 .hpp

int main(int argc, char** argv)
{
  rclcpp::init(argc, argv);
  auto node = std::make_shared<rclcpp::Node>("overview_demo");
  // MoveGroupInterface 是进程内门面：内部自动创建 action 与 service 客户端
  moveit::planning_interface::MoveGroupInterface group(node, "arm");
  group.setNamedTarget("ready");            // 命名位姿来自 SRDF，与 Python 入口语义一致
  moveit::planning_interface::MoveGroupInterface::Plan plan;
  // plan() 返回错误码：失败原因可通过错误码区分（超时、无解、无效请求），布尔返回值携带不了这些信息
  if (group.plan(plan) == moveit::core::MoveItErrorCode::SUCCESS) {
    group.execute(plan);                    // 执行同样经由控制器，需控制器在线
  }
  rclcpp::shutdown();
  return 0;
}

解读：C++ 入口与 Python 入口操作同一套底层机制。（1）MoveGroupInterface 承担门面（Facade）角色，把 Action 客户端、参数读取、结果解析封装成十几个方法，使调用者不必手写消息字段。（2）错误码设计值得注意：规划失败有十几种原因，布尔返回值会丢失信息，枚举错误码为排错保留线索。（3）该接口要求有执行器（Executor）为回调线程服务，第 008 章会专门处理多线程示例，直接照抄单线程示例到回调环境容易造成死锁。

片段 3：launch 编排（把系统拉起来）

# 启动文件定义了一个完整规划系统的最小进程组
from launch import LaunchDescription
from launch_ros.actions import Node
from moveit_configs_utils import MoveItConfigsBuilder


def generate_launch_description():
    # 从配置包读取 URDF、SRDF 与全部 YAML：规划参数集中管理，启动文件只做装配
    moveit_config = (
        MoveItConfigsBuilder("arm_robot", package_name="arm_robot_moveit_config")
        .to_moveit_configs()
    )
    # move_group 是规划服务核心节点，内部持有一份权威的规划场景
    move_group = Node(
        package="moveit_ros_move_group",
        executable="move_group",
        output="screen",
        parameters=[moveit_config.to_dict()],
    )
    # RViz 的 MotionPlanning 插件通过 action 与 service 与 move_group 通信
    rviz = Node(
        package="rviz2",
        executable="rviz2",
        arguments=["-d", str(moveit_config.package_path / "config/moveit.rviz")],
        parameters=[moveit_config.robot_description,
                    moveit_config.robot_description_semantic],
    )
    return LaunchDescription([move_group, rviz])

解读：启动编排体现两个设计原则。（1）参数集中：MoveItConfigsBuilder 把 URDF、SRDF、运动学、规划管线、控制器等配置汇聚成一个对象，所有节点共享同一来源，避免多处配置不一致。（2）进程自治：move_group 与 RViz 是独立进程，通过标准接口耦合，任一方重启不影响另一方内部的场景重建。这种松散耦合是多机与远程可视化场景的基础。

常见坑

  • 把 MoveIt2 当成控制器：规划成功但机械臂不动。原因在于 execute 阶段需要控制器在线；演示环境可用假控制器，实机需要 ros2_control 加载 Joint Trajectory Controller。修复：检查控制器列表与轨迹话题。
  • 规划组名称与配置不一致：代码引用 "arm"，SRDF 中定义的是 "manipulator"，move_group 返回"组不存在"。修复：用 ros2 param 或接口方法列出实际组名后再引用。
  • 场景状态过期：规划从旧的起始状态出发，生成的轨迹与当前姿态不符，执行时报起点不匹配。修复：确认 PlanningSceneMonitor 收到最新的关节状态，第 020 章展开。
  • 目标超出可达范围却反复调规划时间：工作空间边界之外的位姿，任何规划时间都得不出解。修复：先做正运动学（Forward Kinematics, FK）粗算目标点与基座的距离，再决定是否调整目标。
  • 忽略发行版差异照抄旧示例：Humble 与 Jazzy 的接口命名、头文件后缀、Python 模块路径均有演进。修复：以对应版本的官方文档为准，遇到编译或导入错误先核对版本。

练习与思考

  1. 一台六轴机械臂加两指夹爪（每个指关节 1 个自由度），构型空间维度是多少？如果末端需要同时约束位置与姿态，目标约束占几个维度？★
    提示
    关节总数为 8；末端位姿约束在笛卡尔空间占 6 维（位置 3 维加姿态 3 维），映射回构型空间时通常对应有限个离散解。
  2. 把本章数据流七步与五层架构对应起来：每一步的输入输出分别由哪一层组件持有？★
    提示
    前两步在规划核心层与用户接口层之间往返，中间三步在算法插件层与场景层之间交替，后两步跨到机器人接口层。画表比画图更容易暴露职责重叠。
  3. Plan 与 Execute 分离带来的好处之一是轨迹预检查。列举三项执行前值得检查的轨迹属性，并说明各自的检查依据。★★
    提示
    从时间维度（每段耗时是否合理）、空间维度（路径是否穿过障碍或奇异位形附近）、关节维度（速度、加速度是否在缩放因子允许范围内）展开。
  4. 预测实验：把规划时间参数从 1 s 调到 10 s，在障碍物稀少的场景中成功率与平均耗时分别如何变化？在障碍物密集的场景中呢？给出预测并说明依据。★★
    提示
    稀疏场景中首次尝试往往在最初 0.1 s 内就成功，余下时间被浪费；密集场景中成功在很大程度上依赖更多采样机会，成功率随规划时间上升，但边际收益递减。第 017 章用数据验证这个预测。
  5. 设计题：为一条 unbounded 的直线轨迹绘制"规划请求生命周期"状态图，标注正常路径、取消路径与超时路径三组转移，并指出每类转移由哪个接口机制支撑。★★★
    提示
    取消与超时都由 Action 的目标状态机支撑（CANCELING、ABORTED 等状态）；规划与执行的取消语义不同：规划取消即停止搜索，执行取消会触发控制器减速停止。

小结

  • 运动规划在 n 维构型空间中进行，障碍映射为 Cobs；采样规划以概率完备性把高维问题变成可解问题。
  • MoveIt2 分五层：用户接口、规划核心、算法插件、场景、机器人接口；排障自下而上，先模型与状态，后参数与算法。
  • move_group 以 Action、Service、Topic 三类接口对外服务，选择依据是任务的时间尺度与交互模式。
  • 规划与执行分离，轨迹是两者的分界：几何正确由规划负责，时间与动力学正确由执行负责。
