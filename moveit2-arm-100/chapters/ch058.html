第三篇 · 规划算法与求解器

第 058 章：PlanTrajectory Action 与 ExecuteTrajectory Action

动作接口把规划与执行从"一次函数调用"升级为带进度、可取消、可抢占的长时任务。本章拆解 MoveGroup action 的规划侧语义与 ExecuteTrajectory action 的执行侧语义，并说明"仅规划动作"在各版本中的承载方式。

  • 主题：动作接口 / 规划与执行的编排
  • 关键机制：goal 状态机、plan_only 选项、取消与抢占、执行监控
  • 预计学时：50 分钟
  • 前置章节：第 057 章

学习目标

  • 理解动作接口相对服务接口的三项增量：反馈、取消、抢占，以及它们对规划系统的意义。
  • 掌握 MoveGroup action 的字段结构：规划请求、规划选项与结果中的三条轨迹的区别。
  • 掌握 ExecuteTrajectory action 的字段结构与执行链路：从轨迹输入到控制器转发的监控过程。
  • 能解释"仅规划"需求的两种承载方式（服务与动作选项），并说明各发行版命名差异的处理方法。
  • 会编写带取消与并发保护的调用端代码，正确处理抢占、取消与失败三类结果。

背景与动机

规划的耗时从毫秒到秒级，执行从数百毫秒到数秒，两者都属于"长时任务"。服务接口的短板在此暴露：等待期间没有进度、无法取消、超时只能靠客户端断开。动作接口用目标状态机解决这三点，让"发起任务、观察进度、必要时取消"成为标准能力。

MoveIt 的动作层同时承担编排职责：规划与执行可以分两步走，也可以合并；执行可以被新的任务抢占。理解动作层的字段与状态转换，是构建可靠任务脚本的基础，也是第 088 章任务编排的接口前提。

核心原理

1. 动作接口的三项增量

能力服务接口动作接口规划系统中的意义
进度反馈无feedback 通道周期发布长规划与长执行期间的状态可观测
取消无（只能等待或断开）cancel 请求与确认流程任务切换、安全干预的必备能力
抢占无新 goal 替换旧 goal示教、遥控等高频指令场景的基础

动作服务器在同一时刻只处理一个 goal：新目标到达时旧目标被抢占，旧任务的调用端收到"被抢占"结果。这一"独占执行"模型决定了调用端必须处理并发：一次规划或执行尚未结束时再发新目标，旧任务即被终止。

2. MoveGroup action：规划侧与执行侧的合并

MoveGroup action 是规划与执行的主入口，字段结构分三段（以消息定义为准）：

段字段说明
goalrequest（MotionPlanRequest）第 057 章的全部请求字段
goalplanning_options（PlanningOptions）仅规划、重规划、感知重试等行为开关
resulterror_code、trajectory_start、planned_trajectory、executed_trajectory、planning_time规划结果与执行执行记录分开返回
feedbackstate（字符串）内部状态机的当前状态快照

规划选项中的关键开关：plan_only 表示只规划不执行；重规划相关选项让执行过程中检测到环境变化时可以重新规划；感知相关选项允许在感知数据更新后重试。"规划与执行解耦"的推荐调用方式就是设置 plan_only，拿到 planned_trajectory 后自行决定何时通过执行动作下发。

结果中的三条轨迹要分清：trajectory_start 是实际使用的起始状态；planned_trajectory 是规划输出；executed_trajectory 是执行过程的记录（含实际经过的路径点）。只有"仅规划"模式下 executed_trajectory 会为空，验证逻辑要按模式区分。

3. ExecuteTrajectory action：执行侧的门面

执行动作的结构简洁：

段字段说明
goaltrajectory（RobotTrajectory）待执行轨迹，通常来自规划结果
resulterror_code（MoveItErrorCodes）整体成败与失败原因
feedbackstate（字符串）执行状态机快照

执行链路：执行动作收到轨迹后转发给对应的控制器（控制器侧的 FollowJointTrajectory 动作，见第 014 章），并监控执行进展；取消请求会触发控制器减速停止；结果中的错误码区分执行失败、被取消与控制器拒绝。执行动作不做规划，也不修改轨迹：它下发的与收到的是同一份内容，检查"轨迹是否可执行"的责任在规划侧与调用侧。

4. "仅规划动作"的命名与版本差异

字段以发行版消息定义为准

在 moveit_msgs 的消息集合中，规划侧并没有名为 PlanTrajectory 的独立动作定义；"仅规划"能力由两种方式承载：其一，MoveGroup action 配合 plan_only 选项；其二，规划服务（GetMotionPlan，服务名常为 /plan_kinematic_path）直接返回响应消息。部分资料与口语把"规划侧动作"概念性地称为 PlanTrajectory。较新版本另有序列动作（MoveGroupSequence）承载多段规划。本章代码全部以消息定义中真实存在的动作与字段为准，迁移时先用接口自省确认动作清单。

实现思路与设计

调用模式选择表：

模式接口组合适用场景
合并规划与执行MoveGroup action 默认模式交互式操作、示教录制
先规划后执行MoveGroup action（plan_only）+ 执行动作执行前需要人工确认或安全校验
执行已有轨迹执行动作单独调用轨迹来自离线生成或记录（第 059 章）

调用端设计清单：

  1. 并发保护：维护"当前活动目标"句柄，发送新目标前检查旧目标状态；高频场景明确"抢占即取消"的语义。
  2. 结果归类：把"成功、被抢占、被取消、失败"四类结果分别处理，抢占与取消不计入故障统计（第 049 章）。
  3. 执行确认：执行动作发送前确认控制器已就绪、且没有其它调用端正在驱动同一控制器。
  4. 失败回退：执行失败后先读错误码，再决定重规划、重试或上报。
  5. 反馈消费：反馈只做心跳与状态展示，不解析成精确进度（进度细粒度在控制器反馈层）。

与第 057 章的衔接：动作的 goal 载荷就是请求消息，字段语义完全继承；本章新增的是"时间维度"：任务的发起、观察、取消与终止四件事。

关键代码与解读

片段 1：执行动作客户端（Python，含反馈与结果处理）

import rclpy
from rclpy.action import ActionClient
from rclpy.node import Node
from moveit_msgs.action import ExecuteTrajectory

class Executor(Node):
    """把一条已规划轨迹交给执行动作，并区分四类结果。"""
    def __init__(self):
        super().__init__("trajectory_executor")
        self.client = ActionClient(self, ExecuteTrajectory, "/execute_trajectory")
        self.active_goal = None                        # 并发保护：记录当前活动目标

    def send(self, robot_trajectory):
        if self.active_goal is not None:
            self.get_logger().warn("存在未完成的执行目标，先取消再发新目标")
            self.active_goal.cancel_goal_async()       # 抢占语义：旧目标被终止

        goal = ExecuteTrajectory.Goal()
        goal.trajectory = robot_trajectory             # 字段即 RobotTrajectory（第 057 章）
        self.client.wait_for_server(timeout_sec=2.0)
        future = self.client.send_goal_async(
            goal, feedback_callback=self.on_feedback)  # 反馈只做状态观测
        rclpy.spin_until_future_complete(self, future, timeout_sec=5.0)
        self.active_goal = future.result()
        return self.active_goal

    def on_feedback(self, feedback_msg):
        state = feedback_msg.feedback.state             # 状态机字符串快照
        self.get_logger().info(f"执行状态：{state}")

    def on_result(self, future):
        res = future.result().result
        if res.error_code.val == 1:                     # 成功
            self.get_logger().info("执行完成")
        else:
            self.get_logger().error(f"执行失败，错误码 {res.error_code.val}")
        self.active_goal = None                         # 释放句柄，允许下一任务

解读：三个设计点支撑可靠调用。其一，并发保护：活动句柄在发送前检查、在结果回调里释放，避免"新目标静默抢占旧目标"造成的状态错乱。其二，反馈语义：state 是状态机快照，用它做展示与心跳，进度判断交给控制器层。其三，结果归类：示例把非成功结果打印错误码，生产代码应把"被取消/被抢占"从故障计中分开（第 049 章语义表）。

片段 2：两阶段调用：规划与执行解耦（C++）

#include <moveit/planning_interface/planning_interface.h>

// 两阶段模式：先规划并检查，再决定是否执行；计划对象可在确认后再下发
bool plan_then_execute(moveit::planning_interface::MoveGroupInterface& mg,
                       const std::vector<double>& goal)
{
  mg.setJointValueTarget(goal);
  mg.setPlanningTime(1.0);
  mg.setNumPlanningAttempts(5);

  moveit::planning_interface::MoveGroupInterface::Plan plan;
  auto code = mg.plan(plan);                       // 阶段一：仅规划
  if (code != moveit::core::MoveItErrorCode::SUCCESS)
    return false;                                  // 失败：进入第 049 章诊断流程

  // 确认环节：此处可插入轨迹校验、人工确认或安全联锁检查
  // 例如：检查 plan.trajectory 的首点与当前状态一致、末点满足工艺位姿

  code = mg.execute(plan);                         // 阶段二：下发执行
  return code == moveit::core::MoveItErrorCode::SUCCESS;
}

解读：两阶段模式把"得到结果"与"执行结果"之间的窗口显式化，窗口内可以插入任意校验。C++ 接口的 plan() 走"仅规划"路径（底层经服务或动作实现，依发行版而定），execute(plan) 走执行动作。注意规划成功与执行成功是两个独立错误码：规划成功而执行失败（环境变化、控制器拒绝）在联调期很常见，必须分开上报。执行窗口越长，环境变化作废轨迹的概率越高；对动态环境应缩短窗口或启用重规划选项。

片段 3：取消的执行语义（Python 代码注释版）

import rclpy

def cancel_and_resync(executor, state_source):
    """取消执行后必须重新同步状态：控制器停在途中位置，模型状态随之过期。"""
    if executor.active_goal is None:
        return
    future = executor.active_goal.cancel_goal_async()   # 请求取消
    rclpy.spin_until_future_complete(executor, future, timeout_sec=2.0)
    # 取消确认后控制器会减速停止；停止位置介于轨迹中途，与起点、终点都不相同
    # 因此接下来必须：
    #   1) 等待状态源更新（第 021 章的当前状态监视机制）
    #   2) 以"停止位置"为新的起点重新规划，不要以原起点继续
    #   3) 若任务有工艺衔接要求，先把工具退到安全位姿再恢复任务
    stopped = state_source.get_current_joint_values()
    print("停在关节值：", [round(v, 3) for v in stopped])

解读：取消的执行语义是易被低估的工程点。取消不等于"回到起点"：控制器在减速过程中走完了部分轨迹，机器人停在轨迹中段；继续任务前必须以实际停止位置重建起点，否则规划出的轨迹与真实状态脱节，第一段就会产生跟踪误差。示例末尾打印停止关节值，生产代码应把它写回起点设置并触发状态同步等待，再进入重新规划流程。

常见坑

  • 把反馈当精确进度：执行反馈的 state 表示状态机快照，不含完成百分比；用它在 UI 上画进度条会长期停在中间状态。修复：进度展示接控制器反馈（第 014 章），动作反馈用于状态提示。
  • 结果错误码不检查：只等 future 完成就认为执行成功，失败被静默吞掉。修复：始终读取结果错误码并按四类归类处理。
  • 取消后立刻发新目标：控制器尚在减速停止，新目标到达被拒或造成状态错乱。修复：等取消确认与状态同步完成，再发起新目标。
  • plan_only 模式期待 executed_trajectory：仅规划模式下执行记录必然为空，校验逻辑误判失败。修复：按模式区分校验字段。
  • 多调用端共享执行动作：两个脚本同时向执行动作发目标，互相抢占。修复：执行权单点持有，或用命名空间为不同子系统隔离（第 089 章）。

练习与思考

  1. 列出"成功、被抢占、被取消、失败"四类结果的判定依据，并说明哪些不应计入故障统计。★
    提示
    依据错误码语义（第 049 章）；被抢占与被取消属于正常控制流，不计入故障，但要单独计数以观察调用端行为。
  2. 解释结果中 planned_trajectory 与 executed_trajectory 的差别，并设计一个使用二者差异做"跟踪质量检查"的方法。★
    提示
    计划轨迹是下发的目标，执行轨迹是实际经过的路径点；逐点比较关节偏差，统计最大偏差与时间滞后，作为跟踪质量指标。
  3. 设计一个"执行前校验窗口"：在两阶段调用中加入三项校验（起点一致、末点满足工艺位姿、轨迹时间戳单调），写出每项校验的通过判据。★★
    提示
    起点一致：轨迹首点与当前关节值之差小于阈值（如 0.02 rad）；末点：用 FK 算末端位姿与工艺目标比较；时间戳：相邻 time_from_start 严格递增且总时长在预期范围。
  4. 分析题：为什么动作服务器的"独占执行"模型对示教与遥控场景是优点，而对多任务并行场景是约束？给出各自的应对方式。★★★
    提示
    独占让新指令自然抢占旧任务，符合人工干预优先；并行需求靠多个受控机构（多组/多命名空间）承担，同一机构上的并行只会互相终止。应对：任务队列串行化，或按机构隔离动作服务器。

小结

  • 动作接口为长时任务提供反馈、取消与抢占；同一动作服务器同时只处理一个目标。
  • MoveGroup action 合并规划与执行，plan_only 选项提供"仅规划"模式；结果中的三条轨迹分别对应起点、计划与执行记录。
  • 执行动作以轨迹为输入，转发控制器并监控；它不修改轨迹，执行前校验由调用侧负责。
  • 规划侧没有名为 PlanTrajectory 的独立动作消息，"仅规划"由选项与服务承载，命名差异以发行版定义为准。
  • 取消的执行语义是"停在轨迹中段"，恢复任务前必须重建起点并同步状态。
  • 下一章把轨迹本身变成可保存、可复现的资产：轨迹记录与回放。
