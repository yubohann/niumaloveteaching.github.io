第 094 章：规划失败的恢复策略

把错误码变成行动：建立"分类、恢复、验证、升级"的恢复状态机，给出场景清理、状态重同步、预算扩展与规划器切换四类恢复手段的实现要点与边界。

  • 主题：可靠性设计 / 失败恢复
  • 关键机制：错误分类、恢复动作库、有界重试、升级路径、恢复度量
  • 预计学时：55 分钟
  • 前置章节：第 093 章

学习目标

  • 掌握失败分类框架：暂时性、配置性、环境性与资源性失败的特征与判别依据。
  • 会为常见错误码建立"原因判定到恢复动作"的映射表。
  • 理解恢复状态机的四个阶段：检测、分类、恢复、验证，以及升级路径的触发条件。
  • 会实现场景清理与状态重同步两类基础恢复动作，并保证其幂等性。
  • 会用恢复成功率与期望代价两个指标评估恢复策略的实际收益。

背景与动机

规划失败在真实系统中是常态：动态场景不断更新、目标偶尔不可达、传感器噪声让起始状态短暂处于碰撞检测的边界。恢复策略决定这些失败是"可自愈的扰动"还是"任务中断"，它是系统可用性的直接来源。

盲目重试与不重试同样有害：对配置性错误重试只会消耗算力并产生重试风暴；对暂时性错误直接放弃则频繁中断任务。本章的核心方法是对失败先分类再行动，让每一类失败对应成本最低、成功率最高的恢复手段。

第 088 章的任务状态机中预留了恢复状态，本章展开它的内部机制；第 082 章的错误码表在此获得行为语义。

核心原理

1. 失败分类框架

按可控性与可重复性把规划失败分为四类，另有执行类失败与抢占事件单独处理；分类结果直接决定恢复策略。判别依据是"重复同一请求是否稳定失败"与"失败位置是否集中在校验、求解或执行"。

类别特征典型错误码恢复策略
暂时性同请求重试有时成功PLANNING_FAILED、TIMED_OUT扩展预算、重试前刷新状态
配置性重复失败且与场景无关INVALID_GROUP_NAME、INVALID_GOAL_CONSTRAINTS终止并上报配置错误，不重试
环境性场景变化后成败改变START_STATE_IN_COLLISION、GOAL_IN_COLLISION清理场景、验证目标、重规划
资源性失败率随负载上升TIMED_OUT、PREEMPTED调整调度、串行化、提高优先级

2. 恢复状态机

恢复流程为四阶段：检测（捕获错误码与上下文）、分类（落到四类之一）、恢复（执行有界动作序列）、验证（重新检查前置条件）。验证阶段必须执行：恢复动作改变的是场景与状态，恢复后必须确认前置断言重新成立。

恢复流程 = 检测 → 分类 → 恢复（有界）→ 验证 → 升级或回到任务流 每一阶段的输出都是下一步的输入；分类缺失时恢复退化为盲试，验证缺失时失败原因被掩盖并可能在下一步放大

3. 恢复动作库

  • 场景清理：清空占用栅格数据、移除陈旧附着物体与过期检测对象。适用环境性失败，代价是丢失部分感知信息。
  • 状态重同步：重新获取关节状态与场景快照，确保起点可信。适用暂时性失败与状态过期。
  • 预算扩展：提高规划时间与尝试次数，或切换更适合窄通道的算法。适用暂时性失败中的求解困难。
  • 约束放宽：按梯度放宽容差或调整目标姿态，每次只放宽一个维度并记录放宽量。

四类动作按成本升序排列，恢复器沿序列逐级尝试，每级都设定上限。成本包括执行时长、信息损失与后续风险：场景清理会丢失感知信息，约束放宽会改变任务语义，因此排在序列后段。

4. 升级路径与有界性

恢复动作耗尽后进入升级：更换规划器、请求任务层重分解、降级服务或请求人工。升级同样是状态转移，需要明确定义触发条件与目标状态。有界性是恢复器的安全底线：所有重试次数、预算上限与升级层级都必须是常数，保证失败路径的终止性。

E[总代价] = c尝试 + (1 − p成功) · ( c恢复 + E下一级 ) p 为单次成功率；当 c恢复 远大于 c尝试 时，先做低成本重试再升级；恢复成功率低于某阈值时该级动作应从序列中移除

5. 恢复度量

恢复策略本身需要评估：恢复成功率（恢复后首次重试作为成功）、平均恢复代价（额外耗时与动作次数）、升级率（进入高成本层级的比例）。指标按失败类别分组统计，才能发现哪一类失败的恢复设计薄弱。

实现思路与设计

恢复设计按"映射、序列、上限、度量"四步落地。先把错误码映射到类别，再把类别展开为动作序列，然后为每级设置上限，最后接入度量。

1. 错误码映射表（节选）

错误码类别第一恢复动作第二恢复动作
START_STATE_IN_COLLISION (−10)环境性状态重同步清理过期物体后重试
GOAL_IN_COLLISION (−12)环境性复核目标点位调整目标姿态后重试
PLANNING_FAILED (−1)暂时性预算扩展后重试切换规划算法
TIMED_OUT (−6)暂时性/资源性预算扩展降低场景复杂度或串行化负载
INVALID_GOAL_CONSTRAINTS (−16)配置性终止并上报无（不重试）
CONTROL_FAILED (−4)执行类检查控制器状态复位后重发短轨迹

2. 恢复序列与参数

级别动作参数上限
1状态重同步状态新鲜度阈值 0.2 s2 次
2预算扩展时间乘 1.5、尝试次数加 102 次
3场景清理清占用栅格、移除陈旧物体1 次
4算法切换换用窄通道表现更稳的算法1 次
5约束放宽或升级容差按梯度放宽，或上报任务层1 次

3. 与任务状态机的接线

恢复器以函数形式被状态机的恢复状态调用，输入为失败上下文，输出为"已恢复待验证"或"进入终止"。恢复器的内部级别序列对状态机透明，状态机只感知一轮恢复的结果，保持职责边界清晰。

与上一章的差异点：第 093 章建立"不允许越过的数值边界"，本章处理边界内仍会发生的失败，把失败变成有界、可观测、可度量的恢复流程。

关键代码与解读

片段 1：错误分类与恢复序列

from dataclasses import dataclass

@dataclass
class Failure:
    code: int                     # 规划结果错误码
    context: dict                 # 触发时刻的请求与场景摘要

# 错误码到类别的映射：分类决定后续策略，未列出的码归入未知并升级
CATEGORY = {
    -1: "transient",    # PLANNING_FAILED
    -6: "transient",    # TIMED_OUT
    -7: "preempted",    # PREEMPTED：抢占事件，交由调度层重发
    -10: "environment", # START_STATE_IN_COLLISION
    -12: "environment", # GOAL_IN_COLLISION
    -15: "config",      # INVALID_GROUP_NAME
    -16: "config",      # INVALID_GOAL_CONSTRAINTS
    -4: "actuation",    # CONTROL_FAILED
}

# 恢复序列按成本升序：低成本动作在前，语义改动的动作在后
RECOVERY_LADDER = {
    "transient": ["resync", "extend_budget", "switch_planner"],
    "environment": ["resync", "clean_scene", "adjust_goal"],
    "config": [],                       # 配置性错误不重试
    "actuation": ["check_controller", "reset_and_resend"],
    "preempted": ["wait_for_schedule"], # 抢占不修复：等待调度层重发或撤销
}


def classify(failure: Failure) -> str:
    # 未知错误码保守升级：避免用错误的恢复动作放大问题
    return CATEGORY.get(failure.code, "unknown")

def recover(failure: Failure, actions: dict, budget_per_level=1):
    """按序列逐级恢复；每级有独立预算，成功即返回。"""
    for name in RECOVERY_LADDER.get(classify(failure), []):
        action = actions[name]
        for _ in range(budget_per_level):
            if action(failure.context):     # 动作内部幂等（见片段 2）
                return True, name
    return False, "exhausted"

解读：映射表与序列是恢复器的骨架。设计要点：（1）未知错误码归入"未知"并直接升级，宁可上报也不盲目恢复；（2）序列按成本升序，语义改动类动作排在最后；（3）PREEMPTED 归入独立的抢占类，序列只有等待调度一个动作（不执行修复动作），注释显式说明抢占的调度语义；（4）每级独立预算，总次数是序列长度乘预算，有界性可静态检查。

片段 2：两类基础恢复动作的实现

def make_resync(node, scene_client):
    def resync(context):
        """状态重同步：等待状态更新到阈值以内，再拉取场景快照。"""
        if not wait_state_fresh(node, max_age=0.2):
            return False                     # 状态链自身异常，交由升级处理
        snapshot = fetch_scene(scene_client)
        if snapshot is None:
            return False
        # 幂等：重复调用只是再取一次快照，不改变场景内容
        context["scene_stamp"] = snapshot.stamp
        return True
    return resync


def make_clean_scene(octomap_client, scene_client, protect_ids):
    """场景清理：只清占用数据与陈旧物体，保护当前任务相关对象。"""
    def clean_scene(context):
        called = octomap_client.call_clear()      # 清空占用栅格
        if not called:
            return False
        # 移除检测类物体，但保护白名单：任务物体与静态环境属于不可清理集合
        removed = remove_detected_objects(scene_client, protect_ids)
        context["cleaned"] = removed
        return True
    return clean_scene

解读：基础恢复动作的设计原则是"效果确定、重复安全"。设计要点：（1）重同步动作不修改场景，只刷新本地视图，天然幂等；（2）清理动作带白名单，避免把任务物体一并清掉造成更严重的状态损坏；（3）两个动作都以布尔返回值报告自身成败，恢复器据此决定是否升级；（4）上下文记录清理数量与场景时间戳，供恢复度量使用。清理动作排在重同步之后的原因：状态不一致优先用低成本手段解决，场景数据可信度问题才动用信息损失较大的清理。

片段 3：预算扩展与算法切换

class EscalatingPlanner:
    """预算扩展与算法切换：每级只改一个变量，便于归因。"""

    def __init__(self, base_request, ladder):
        # ladder 元素为 (时间倍数, 尝试次数增量, 算法名)
        self.request = base_request
        self.ladder = ladder
        self.level = 0

    def next_attempt(self):
        if self.level >= len(self.ladder):
            return None                        # 序列耗尽：调用方转入升级路径
        time_scale, attempt_bump, planner = self.ladder[self.level]
        self.level += 1
        # 在基础请求的副本上调整：不污染原始请求，重试之间相互独立
        candidate = copy_request(self.request)
        candidate.allowed_planning_time *= time_scale
        candidate.num_planning_attempts += attempt_bump
        candidate.planner_id = planner
        return candidate


# 序列示例：先扩预算（同算法），再换为窄通道更稳的算法
ladder = [(1.0, 10, "RRTConnect"),    # 第一级：加尝试次数
          (1.5, 10, "RRTConnect"),    # 第二级：再扩时间
          (1.5, 0, "RRTstar")]        # 第三级：换算法，预算保持不变

解读：逐级扩展把"调参"变成可归因的序列。设计要点：（1）每级只改一个维度，恢复成功时能直接读出有效变量；（2）在请求副本上修改，避免前一轮扩展泄漏到后续轮次；（3）算法切换放在最后一级，因为它的行为变化最大、归因成本最高。序列本身写入配置，现场可随工况调整顺序与上限。

常见坑

  • 对配置性错误重试：组名拼写错误被反复重试，占用算力并掩盖真实原因。修复：配置性错误直接终止并上报，映射表显式标记"不重试"。
  • 恢复动作破坏有效状态：清理动作把任务相关物体一并移除，后续规划基于残缺场景运行。修复：清理动作带白名单，清理前后记录场景差分供核对。
  • 恢复后不验证：恢复动作返回成功即重新规划，前置条件其实仍不成立，失败原因被掩盖并可能放大。修复：恢复流程以验证阶段收尾，前置断言重新成立才回到任务流。
  • 重试风暴：多任务并发时同时触发恢复，算力被重试占满，正常请求超时率上升。修复：重试串行化或限流，恢复动作共享互斥，观察负载指标后再提升并发。
  • 恢复度量缺失：恢复策略长期存在但从未评估，低收益级别持续消耗预算。修复：按失败类别统计恢复成功率与平均代价，低收益级别从序列中移除。

练习与思考

  1. 为错误码 −10、−1、−16 各写出类别、首选恢复动作与验证方式，并说明 −16 为何不进入重试序列。★
    提示
    −16 属配置性，约束消息无法被求解器解释，重复提交同一约束不会改变结果，修复位置在请求构造侧。
  2. 计算期望代价：单次尝试代价 1 个单位、恢复代价 3 个单位、单次成功率 0.6，恢复后成功率 0.8。求"先重试一次再恢复"与"直接恢复"两种策略的期望代价。★★
    提示
    先重试：1 + 0.4×(3 + 0.2×…) 约 1 + 1.2 = 2.2 个单位；直接恢复：3 + 0.2×… 约 3 个单位出头；低成本重试优先的结论与公式一致。
  3. 设计实验：人为注入三类失败（清除目标物体、遮挡起点、把组名改错），验证恢复器分别走哪条序列、在哪一级成功或升级。★★
    提示
    清除目标物体触发环境性序列；遮挡起点应被状态重同步或清理解决；组名错误直接升级，不发生任何重试。
  4. 改参数并预测：把预算扩展序列的时间倍数从 1.5 提高到 3.0，恢复成功率与平均恢复代价如何变化？给出选择依据。★★
    提示
    恢复成功率上升但失败样本的代价翻倍；选择依据是剩余截止时间与恢复收益的权衡，可用期望代价公式比较两档参数。
  5. 推导：说明为什么恢复动作必须幂等，给出一个非幂等动作的例子并改造为幂等版本。★★★
    提示
    非幂等例：每次调用都追加一个障碍物副本，重复恢复让场景持续膨胀；改造为"按标识更新或不存在才添加"，重复调用收敛到同一状态。

小结

  • 失败分四类：暂时性、配置性、环境性、资源性；分类决定恢复策略与是否重试。
  • 恢复状态机四阶段：检测、分类、恢复、验证；验证缺失会让失败原因被掩盖。
  • 恢复动作按成本升序排列：重同步、预算扩展、场景清理、算法切换、约束放宽与升级。
  • 所有重试次数与升级层级有界且可静态检查，恢复动作必须幂等。
  • 恢复策略按失败类别度量成功率与期望代价，低收益级别从序列中剔除。
