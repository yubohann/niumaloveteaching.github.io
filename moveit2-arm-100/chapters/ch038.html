第二篇 · 规划场景与碰撞管理

第 038 章：阶段实践：感知驱动的避障规划

把第二篇的全部组件接成一条闭环：状态同步、场景管理、感知写入、约束施加、规划验证与执行监控各就其位，用可量化的验收标准回答"这套系统现在可靠吗"。

  • 主题：阶段实践 / 感知驱动规划系统集成
  • 关键机制：就绪门、快照一致性、验证门与量化验收
  • 预计学时：60 分钟
  • 前置章节：第 037 章

学习目标

  • 能把第 019 至 037 章的组件组织成一条完整闭环：状态同步、场景维护、感知写入、约束施加、规划、验证、执行。
  • 掌握两道门禁的设计：场景就绪门（物体清单与数据新鲜度）与验证门（路径有效性与最小裕量），并理解它们各自拦截的错误类型。
  • 理解快照一致性的要求：规划与验证必须以同一份场景快照为依据，执行前再核对一次偏差。
  • 会为实践系统设定量化验收标准，并按标准定位失败环节。
  • 能根据失败症状在第二篇的章节间完成归因，形成可复用的排查路径。

背景与动机

第二篇前后二十章分别解决了场景监视、物体管理、载荷归属、碰撞判定、环境表示与约束表达。把这些组件逐个接对，与把它们接成一条可靠闭环，是两项不同的工作：单组件调用正确，系统仍可能因为时序、快照与门禁缺失而产生系统性故障：每个环节单独看都正常，串联起来偶发失败且难以复现。阶段实践的目的正在于此：用一条完整任务链把组件之间的接缝摊开，给每条接缝配上可判定的检查。

本章的实践场景选择"感知驱动的避障搬运"：工作台上存在已知工装（显式物体）与由深度相机感知的未知杂物，机械臂需要在带约束的前提下搬运工件并绕开两者。验收由三个量化条件定义：场景就绪（清单与新鲜度）、规划成功且验证通过（有效性加裕量）、执行期偏差在阈值内。完成本章后，第三篇将深入规划算法本身，理解"规划器内部究竟发生了什么"。

核心原理

1. 闭环的六个环节与责任划分

环节数据来源对应用章失效症状
状态同步关节状态话题第 021 章规划起点跳变或超时无解
场景维护规划场景差分与服务第 019、020、022 至 026 章幽灵障碍、载荷状态错误
感知写入点云与检测结果第 030 至 034 章地图陈旧、自障碍、幻影障碍
约束施加任务工艺参数第 035 至 037 章可行集为空、约束泄漏
规划与验证规划请求与场景快照第 028、029 章成功但不可执行、验证遗漏
执行与监控轨迹与实时状态第 014、029 章偏差积累、重规划触发过晚

责任划分的价值在失败归因：任何一次任务失败都先按症状落到表中的一行，再到对应章节的检查项里找根因。把"偶发失败"变成"表上的确定行"，是这套结构最重要的作用。

2. 两道门禁：就绪门与验证门

闭环上有两个最容易发生静默错误的接缝，各设一道门禁。就绪门位于规划之前，检查两件事：场景物体清单与预期一致（异步写入已经生效）、感知数据新鲜（点云年龄低于阈值）。它拦截的错误类型是"用错误的场景规划正确的目标"。验证门位于规划与执行之间，检查路径有效性与最小裕量（第 029 章的两类验证）。它拦截的错误类型是"规划与执行之间场景已变化"与"路径贴障碍过近"。

两道门禁有一个共同的设计要求：判定必须基于确定的快照，判定动作必须产生结构化结果（通过或拒绝加原因），拒绝后的处置路径必须预先定义。没有结构化结果的"检查"只是日志，无法构成门禁；没有处置定义的拒绝会让系统停在未定义状态。

3. 快照一致性：时序链的硬约束

闭环的时序链为：取状态快照、确认场景就绪、规划、验证、执行。其中一条硬约束是快照一致性：验证使用的场景快照不能比规划使用的快照更新一轮，也不能更旧一轮；理想情形是两者取自同一个只读锁视图。违反这条约束有两种表现：验证比规划旧时，验证在过期场景上放行，执行期发生场景变化未被察觉；验证比规划新时，规划结果可能在"验证观察到的新场景"中已经失效，却因验证实现基于路径重采样而看似通过。

快照一致性在实现上依赖场景监视器的只读锁视图：把"规划加验证"整个块放在同一份视图的生命周期内完成，随后再放行执行。执行前的最后核对（第 021 章的状态新鲜度加第 029 章的路径校验）覆盖"验证到执行"之间的窗口，形成两段式防护。

4. 量化验收标准

实践系统的验收用可测指标表达，建议基线如下表。指标的价值在于让回归可比较：任何配置变更（场景参数、感知频率、约束容差）后重跑同一批任务，指标与基线对照，变化可解释。没有基线的调参等于漂移。

指标建议基线测量方式
就绪门通过时间低于 2 s从上电到场景就绪
单次规划耗时0.5–2 s请求到结果的结构化耗时统计
路径最小裕量不低于 0.02 m距离查询逐路点审计
规划成功率不低于 95%（限时预算内）同目标重复 50 次统计
执行期偏差低于触发阈值的一半状态与轨迹的偏差监控

5. 失败分类与排查路径

把失败模式收敛成五类，每类给出首选检查项：

  1. 就绪门超时：先查点云新鲜度（传感器与变换链），再查物体清单（写入路径与命名）。
  2. 规划无解：先查场景内容是否与视觉一致（幽灵障碍），再查端点（起点碰撞、目标不可达），最后查约束（可行集是否为空）。
  3. 验证失败：查规划与验证的快照是否一致，再查场景是否在窗口内发生变化。
  4. 执行中止：查偏差触发时刻与场景更新时刻的对应关系，判断是感知激励还是机械跟随问题。
  5. 间歇复现失败：查异步写入与门禁的竞态（写入未确认就规划），这类失败在时序记录中表现为"失败总发生在场景变更之后的一两个周期内"。

实现思路与设计

实践系统的搭建顺序，每一步以验收标准收口：

  1. 链路自检：状态源、场景监视器、传感器插件、检测上报四路各自有"活着"指标（第 021、031、033 章的监测模式）。
  2. 场景初始化：写入工装显式物体并确认（第 022 章三要素核对），建立任务物与感知物的命名域。
  3. 感知联调：标准障碍放置与清除回归（第 030、031 章），确认地图位置、尺寸与清除时间。
  4. 约束标定：按工艺给出位置方向约束与关节窗口（第 035 至 037 章），分层验证可行集。
  5. 接入门禁：实现就绪门与验证门，拒绝路径结构化（原因码加日志），处置动作明确。
  6. 闭环回归：按验收指标表重复跑批，记录基线与回归曲线；变更参数后重跑。

片段 2：Python 就绪门实现

import rclpy
from rclpy.node import Node
from sensor_msgs.msg import PointCloud2
from moveit_msgs.srv import GetPlanningScene
from moveit_msgs.msg import PlanningSceneComponents

class PerceptionGate(Node):
    """就绪门：物体清单与点云新鲜度同时满足才放行规划。"""

    def __init__(self):
        super().__init__("perception_gate")
        self.cloud_stamp = None
        self.create_subscription(PointCloud2, "/camera/top/depth/points",
                                 self.on_cloud, 5)
        self.scene_cli = self.create_client(GetPlanningScene,
                                            "get_planning_scene")

    def on_cloud(self, msg):
        # 只记录到达时刻：门禁关心数据流是否活着，不做内容解析
        self.cloud_stamp = self.get_clock().now()

    def scene_ready(self, expected_ids, age_limit=0.5):
        if not self.scene_cli.wait_for_service(timeout_sec=1.0):
            self.get_logger().warn("场景服务不可用")
            return False
        req = GetPlanningScene.Request()
        req.components.components = PlanningSceneComponents.WORLD_OBJECT_GEOMETRY
        future = self.scene_cli.call_async(req)
        rclpy.spin_until_future_complete(self, future, timeout_sec=2.0)
        if future.result() is None:
            self.get_logger().warn("场景查询超时")
            return False
        ids = [o.id for o in future.result().scene.world.collision_objects]
        missing = [i for i in expected_ids if i not in ids]
        if missing:
            # 异步写入尚未生效或写入路径中断：两类故障都在这里汇聚
            self.get_logger().warn(f"场景缺物体: {missing}")
            return False
        if self.cloud_stamp is None:
            self.get_logger().warn("尚未收到点云")
            return False
        age = (self.get_clock().now() - self.cloud_stamp).nanoseconds / 1e9
        if age > age_limit:
            self.get_logger().warn(f"点云已 {age:.2f} s 未更新")
            return False
        return True

解读：（1）门禁把"清单核对"与"新鲜度"组合成一个布尔结果，任一不满足即拒绝；拒绝信息带缺失清单或年龄数值，直接指向写入路径或传感器链路。（2）清单核对走查询服务，不采用监视话题，后者带节流与差分语义（第 023 章），查询服务给出的是权威快照。（3）两个超时参数各司其职：服务可用性等待 1 s、查询响应 2 s，数值高于正常响应时间一个量级，避免把偶发抖动误判为故障。

片段 3：C++ 验证门实现（有效性加裕量）

// 验证门：路径有效性校验加最小裕量审计，两项都过才放行执行
bool validate_plan(const planning_scene::PlanningSceneConstPtr& scene,
                   const moveit::core::RobotState& start,
                   const moveit::core::RobotTrajectory& traj,
                   double clearance_required = 0.02)
{
  std::vector<std::size_t> invalid;
  if (!scene->isPathValid(start, traj, "arm_group", false, &invalid))
  {
    RCLCPP_WARN(rclcpp::get_logger("gate"), "路径校验失败，失效点索引 %zu",
                invalid.empty() ? 0 : invalid.front());
    return false;                          // 场景已变化：交回上层重规划
  }
  collision_detection::DistanceRequest dreq;
  dreq.group_name = "arm_group";
  collision_detection::DistanceResult dres;
  double min_d = std::numeric_limits<double>::infinity();
  for (std::size_t i = 0; i < traj.getWayPointCount(); ++i)
  {
    double d = scene->getCollisionEnv()->distanceRobot(
        dreq, dres, traj.getWayPoint(i));
    min_d = std::min(min_d, d);            // 记录全轨迹最贴近点
  }
  RCLCPP_INFO(rclcpp::get_logger("gate"), "最小裕量 %.4f m，阈值 %.3f",
              min_d, clearance_required);
  return min_d >= clearance_required;      // 裕量不足：拒绝并提示降速或换路径
}

解读：（1）验证门的两项检查对应两类风险：有效性回答"现在还能走吗"（场景变化会被捕捉），裕量回答"贴得多近"（执行抖动的前置防护）。（2）验证函数只做判定与汇报，不修改场景也不重规划；拒绝后的处置（重规划、降速、中止）由上层任务循环决定，职责边界清晰。（3）函数以常量场景指针为入参，强制调用方从确定的场景快照取得引用，配合第 3 小节的快照一致性要求：验证与规划共享同一视图时，该指针直接传入即可。

常见坑

  • 把规划成功当作任务成功：跳过验证门直接执行，场景在窗口内变化或裕量不足时现场故障。修复是把验证门设成执行接口的强制前置，任何调用路径都不可绕过。
  • 门禁基于不同快照：规划用一份场景副本，验证用另一份（或更旧/更新的一份），验证结论与规划结果脱节。修复是规划与验证共享同一只读视图，执行前再做一次轻量核验。
  • 就绪门只看点云不看清单：传感器活着但物体写入路径已断，规划在缺障碍的场景中进行。修复是按片段 2 把两者都纳入门禁。
  • 拒绝后无处置：门禁返回失败后任务停在未定义状态，或无限重试堆积请求。修复是为每类原因码定义处置：重试次数上限、降级动作、上报接口。
  • 回归指标未留基线：参数调整后无法判断成功率变化是否显著，凭感觉决定去留。修复是首次联调固化指标基线并纳入回归流程（第 4 小节表格）。

练习与思考

  1. 指标计算：同目标重复 50 次，规划成功 47 次，其中验证门拒绝 2 次。写出规划成功率与验收通过率，并说明两个指标分别反映什么。★
    提示
    规划成功率 47/50 = 94%，验收通过率 45/50 = 90%。前者反映规划器与场景表达，后者额外暴露"成功但不可交付"的路径（裕量不足或场景变化），两个指标一起看才能区分问题层面。
  2. 参数预测：验证门的裕量阈值从 0.02 m 提高到 0.05 m。在通道宽度约 0.15 m、机器人连杆退让 0.02 m 的工位上，预测验收通过率的变化与原因。★
    提示
    等效安全通道收窄约 6 cm，可行路径变少，验收通过率下降；若通过率跌破需求，应优先核对退让参数与路径自由度，再考虑放宽阈值到与执行抖动匹配的数值。
  3. 设计题：为"就绪门超时"设计完整的排查流程：从日志字段到三个检查点（传感器、变换链、写入路径），每步给出期望观测与超时预算。★★
    提示
    日志先看拒绝原因码（缺清单或点云年龄）；检查点一查点云话题频率；检查点二查 TF 链是否覆盖消息时间戳；检查点三用查询服务核对场景清单与写入日志的对应关系；每步超时预算取正常响应时间的两到三倍。
  4. 诊断题：任务在场景变更后的一两个周期内间歇失败，下一周期恢复正常。给出最可能的竞态来源与两种消除办法。★★
    提示
    竞态来源是异步写入与规划的先后顺序：写入未确认就规划。消除办法一是主控改为确认式写入（服务或封装接口）；办法二是把"清单核对"作为每轮规划的强制前置（就绪门常态化），让竞态窗口被门禁吸收。
  5. 分析题：把本章闭环扩展为"两个工位共享一台感知系统"的部署，说明新增的快照一致性与命名域问题，并给出场景划分与门禁调整方案。★★★
    提示
    共享感知意味着点云覆盖两工位，命名域需按工位细分；快照一致性扩展为"两工位任务各自持有一致视图"；门禁调整为按工位期望清单核对，并对跨工位的感知物体（人员、运输车）单独设域与保守策略。
