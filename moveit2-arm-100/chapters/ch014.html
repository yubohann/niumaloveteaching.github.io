第 014 章：轨迹执行与 FollowJointTrajectory Action

本章打通规划到运动的最后一段：轨迹如何经控制器动作下发、轨迹点各字段的语义、以及执行失败时按错误码定位问题的完整方法。

  • 主题：执行链路 / 控制器接口
  • 关键机制：FollowJointTrajectory 动作、轨迹点字段、时间与位置容差
  • 预计学时：60 分钟
  • 前置章节：第 013 章

学习目标

  • 理解 MoveIt2 的执行链路：规划结果经执行器转发到控制器动作的完整路径。
  • 掌握 FollowJointTrajectory 动作的目标结构：轨迹点序列与各类容差字段。
  • 理解轨迹点中位置、速度、加速度与力的字段语义，以及控制器如何消费它们。
  • 会用动作客户端直接向控制器发送轨迹，读取执行结果与错误码。
  • 能定位四类常见执行失败：起点不匹配、容差违规、控制器未激活、时间戳异常。

背景与动机

规划成功只意味着"存在一条可行的几何路径加时间信息"，机械臂真正运动起来还要经过执行链路：轨迹下发、控制器插值、伺服指令生成。这条链路由多个组件接力完成，任何一个环节的配置错误都会让机械臂"纹丝不动"或"动到一半停下"。

执行侧的问题有一个特点：症状相似而根因分散。机械臂不动的可能原因包括控制器未激活、动作端点名字不对、轨迹被控制器拒绝；动作到一半停下的原因包括容差违规、取消请求、通信中断。本章把执行链路的每个接口与字段展开，配合错误码表，把"不动的机械臂"变成一组可枚举的检查项。这也是与第四篇任务编程共享的基础设施。

核心原理

本节解释执行链路的组件接力、轨迹点字段语义、起点一致性检查与错误码体系。

1. 执行链路：三段接力

从规划结果到关节运动经过三段：

  1. 规划输出：规划管线产出机器人轨迹消息，内含起始状态与关节轨迹序列。
  2. 执行转发：MoveIt2 的执行组件读取轨迹，按控制器映射确定目标控制器，把关节轨迹以其动作目标的形式发送出去。
  3. 控制器执行：控制器接收轨迹，按时间戳在控制周期内插值生成指令，同时在每个周期比对实际状态与期望状态，超差即报错或停止。

三段之间的接口都是标准消息：机器人轨迹在链的前两段之间，关节轨迹在链的后两段之间。中间的执行转发层实现方式依配置而异（控制器管理插件或直连控制器动作），但对外表现一致。理解接力的意义在于排错：先确认第三段控制器活着，再确认第二段转发有配置，最后才怀疑第一段轨迹本身。

2. 轨迹点字段与控制器消费方式

字段含义控制器的使用方式
positions各关节目标位置（弧度或米）核心字段：控制器必须精确跟随
velocities各关节速度通常作为前馈或插值边界条件
accelerations各关节加速度部分控制器使用；缺失时由插值推导
effort力矩或力仅力矩接口的控制器使用，位置控制下留空
time_from_start相对轨迹起点的时间插值的时间轴：必须严格单调

控制器的插值行为是理解执行质量的关键：动作目标的采样点并不等于控制指令，控制器在两点之间按自身策略（常见为样条）插值，每个控制周期从插值曲线取一个点发给伺服。因此轨迹点稀疏是允许的，前提是时间戳与前后点的一致性好；相反，时间戳错误会直接破坏插值曲线，表现为抖动、超速或直接拒绝。

3. 起点一致性：执行前的第一道检查

控制器在开始执行前会把轨迹首点与当前关节状态比对，差异超过路径容差即报"起点不匹配"。这道检查保护的是物理安全：轨迹假设的起始姿态与实机不符时，直接执行会在第一帧产生位置跳变。

‖qtraj(0) − qcurrent‖ ≤ path tolerance，超差 → PATH_TOLERANCE_VIOLATED 规划与执行之间机器人若被手动拖动、或被其他程序驱动，起点就失效

起点失效的常见来源有三个：规划与执行之间隔了过长时间、调试期间手动拖动过关节、其它程序抢占控制。修复方式统一为"用当前状态重新规划"。任何"先规划、检查很久、再执行"的流程都应在执行前做一次起点核对，这一步在第 018 章的实践脚本中会固化为函数。

4. 错误码体系

结果错误码含义首要排查方向
SUCCESSFUL轨迹完整执行无
INVALID_GOAL目标轨迹不合法时间戳单调性、关节清单覆盖
INVALID_JOINTS关节名不被控制器识别控制器配置的关节清单与轨迹对照
OLD_HEADER_TIMESTAMP轨迹时间戳过期重新规划或刷新时间戳
PATH_TOLERANCE_VIOLATED执行中偏离过大速度缩放、控制器增益、负载突变
GOAL_TOLERANCE_VIOLATED终点未在容差内收住末端负载、摩擦、容差设置

错误码端点分散在两处：控制器的动作结果与 MoveIt 执行接口的返回值。两处都读，才能把"控制器拒绝了"与"执行组件转发失败"区分开。第 049 章会给出跨组件诊断的系统方法。

实现思路与设计

执行链路的打通按"控制器确认、轨迹检查、执行、结果判定"四步推进；调试期增加一条直发通道用于隔离变量。

  1. 控制器确认：枚举控制器动作端点，确认控制器已加载且处于激活状态。
  2. 轨迹检查：首点与当前状态核对、时间戳单调、关节清单一致。
  3. 执行：经执行接口下发；调试期可用直发通道只验证控制器。
  4. 结果判定：读取动作结果错误码；失败按错误码表分流。

控制器配置参数表（关节轨迹控制器）

参数建议值作用取值依据
joints组内全部关节控制器接管的关节清单与规划组关节一致，避免缺项
state_publish_rate50 Hz控制器状态发布频率与状态流频率匹配
constraints.goal_time0.5 s终点收敛的允许时间末端负载重的机型适当放宽
constraints.stopped_velocity_tolerance0.05 rad/s停止判定的速度阈值过高会掩盖未完全停止
constraints.goal 容差0.02 rad 量级终点位置容差与第 012 章关节容差同量级起步
设计决策：为什么调试期要保留"直发控制器"通道？

经执行接口下发时，一次失败可能来自规划、转发、控制器三层。直发通道绕过前两层，用一条手工轨迹直接考验控制器，把三层问题压缩成一层。联调新机型的标准顺序：直发通道验证控制器能精确跟随，再接入执行接口验证转发，最后走完整规划流程。每层单独验证后，后续任何失败都能快速归因。

关键代码与解读

本节给出三段片段：控制器映射配置、直发姿态轨迹的客户端、执行结果的判定分支。

片段 1：控制器映射配置

# moveit_controllers.yaml：规划组到控制器的映射
moveit_simple_controller_manager:
  controller_names:
    - arm_controller          # 执行组件按此清单查找控制器动作
  arm_controller:
    type: FollowJointTrajectory
    action_ns: follow_joint_trajectory
    # 控制器动作端点：/arm_controller/follow_joint_trajectory
    default: true
    joints:                   # 关节清单必须与规划组一致，多缺项都会导致拒绝
      - joint_1
      - joint_2

# ros2_control 侧：控制器的加载与参数（摘要）
arm_controller:
  ros__parameters:
    joints: [joint_1, joint_2]
    # 终点收敛时间：负载较大时适当放宽，避免 GOAL_TOLERANCE_VIOLATED
    constraints:
      goal_time: 0.5

解读：映射配置是把 MoveIt 与控制器接起来的第一份文档。（1）映射清单里的控制器名与动作命名空间决定执行组件往哪里发轨迹；名称错误的表现是执行阶段静默失败或报"找不到控制器"。（2）控制器关节清单与规划组必须一致：规划组多出的关节会导致控制器报关节不识别，缺项则让部分关节"不动"而规划却成功。（3）两侧配置常分属不同文件，修改任何一侧后都要核对另一侧，这是执行类问题最高频的来源。

片段 2：向控制器直发轨迹

from rclpy.action import ActionClient
from rclpy.node import Node
from control_msgs.action import FollowJointTrajectory
from trajectory_msgs.msg import JointTrajectory, JointTrajectoryPoint
from builtin_interfaces.msg import Duration

class DirectSender(Node):
    """调试通道：不经规划，直接向控制器发送两点轨迹。"""
    def __init__(self):
        super().__init__("direct_sender")
        self.client = ActionClient(
            self, FollowJointTrajectory,
            "/arm_controller/follow_joint_trajectory")   # 与映射配置一致
        self.client.wait_for_server(timeout_sec=3.0)

    def send(self, q_start, q_end):
        traj = JointTrajectory()
        traj.joints = ["joint_1", "joint_2"]     # 与控制器关节清单逐字一致
        # 首点与当前状态一致：控制器以此通过起点检查
        p0 = JointTrajectoryPoint()
        p0.positions = q_start
        p0.time_from_start = Duration(sec=0, nanosec=0)
        # 末点给出目标与时间：两点之间由控制器自行插值
        p1 = JointTrajectoryPoint()
        p1.positions = q_end
        p1.time_from_start = Duration(sec=2, nanosec=0)   # 2 s 走完
        traj.points = [p0, p1]

        goal = FollowJointTrajectory.Goal()
        goal.trajectory = traj
        # 同步等待结果：调试通道下逻辑简短，便于逐次观察
        result = self.client.send_goal(goal)     # 具体等待方式以对应实现为准
        self.get_logger().info(f"控制器结果：{result}")

def main():
    rclpy.init()
    node = DirectSender()
    node.send([0.0, -0.6], [0.1, -0.5])
    rclpy.shutdown()

解读：这段代码是隔离测试控制器的最小载体。（1）动作端点写法 /控制器名/follow_joint_trajectory 来自映射配置，两处对应关系是排查"发不出去"的第一检查点。（2）首点的两个要素：位置等于当前状态、时间戳为零；缺任意一个都会触发起点或时间戳相关的拒绝。（3）末点给出 2 s 的到达时间，控制器在两点间插值；若实际执行中报容差违规，缩短时间会加剧、放宽会缓解，这是验证时间与跟踪能力匹配关系的直接实验。

片段 3：执行结果判定分支

auto code = group.execute(plan);
if (code == moveit::core::MoveItErrorCode::SUCCESS) {
  RCLCPP_INFO(node->get_logger(), "执行完成");
} else if (code == moveit::core::MoveItErrorCode::CONTROL_FAILED) {
  // 转发或控制器层面的失败：先查控制器日志与动作端点
  RCLCPP_ERROR(node->get_logger(), "执行失败：检查控制器状态与映射配置");
} else if (code == moveit::core::MoveItErrorCode::TIMED_OUT) {
  // 执行超时：轨迹时长与控制器收敛时间的组合问题
  RCLCPP_ERROR(node->get_logger(), "执行超时：检查轨迹时长与控制器收敛参数");
} else {
  RCLCPP_ERROR(node->get_logger(), "执行未成功，错误码 %d", code.val);
}
// 无论成败，对照控制器结果错误码可以进一步区分根因（片段 2 的返回信息）

解读：结果判定是执行链路的收口。（1）错误码分流把"执行失败"拆成转发失败与超时两类，分别指向配置与参数；未分类分支保留原始值供深入分析。（2）最后一行的注释强调双端点检查：执行接口的错误码回答"哪一层失败"，控制器动作的结果回答"控制器认为失败原因是什么"，两者合起来才能完成归因。（3）该判定结构在第 018 章实践中会成为每次运动的固定收尾步骤。

常见坑

  • 首点与当前状态不符：控制器报起点不匹配或第一帧跳变。修复：执行前用当前状态重新规划，或核对"规划到执行"之间的机械臂是否被改动。
  • 控制器未加载或未激活：执行无任何动作，日志停在转发前。修复：枚举动作端点，检查控制器状态并从控制器管理器侧激活。
  • 关节清单缺项：部分关节不动而其余正常，规划却显示成功。修复：对照映射配置、控制器参数与规划组三方清单。
  • 时间戳异常：轨迹被拒或运动抖动。修复：检查时间戳从零起、严格单调、相邻间隔合理；重定时工具见第 015 章。
  • 假控制器掩盖的问题上线才暴露：演示一切正常，接真机执行失败。修复：接入真机前先走直发通道验证控制器，再恢复完整链路。

练习与思考

  1. 枚举控制器相关动作端点，读取控制器类型与状态，确认与映射配置中的名称一致。★
    提示
    用命令行工具列出动作端点与详情；名称比对要覆盖命名空间前缀，多机部署中前缀差异是常见错因。
  2. 用直发通道发送一条两点轨迹，先把首点故意设为错误的关节值，记录控制器返回的错误信息；改回当前状态后重发，对照两次结果。★★
    提示
    错误信息通常会明确指出起点偏差超差；该实验建立"起点检查是真实存在的硬门槛"的直接认知。
  3. 预测实验：把直发轨迹的到达时间从 2 s 缩到 0.3 s，预测控制器返回的结果类别，并说明若要安全提速应当先调整什么。★★
    提示
    时间压缩会提高所需速度与加速度，易触发跟踪容差违规；安全提速的前提是确认关节速度上限与控制器增益能力，再渐进压缩。
  4. 设计题：编写"执行前检查清单"的可执行版本：给定轨迹与当前状态，输出通过或具体的拒绝原因（起点、时间戳、关节清单、限位四项）。★★★
    提示
    参考第 010 章的轨迹速检与本章的起点检查，两项合并成一个函数；拒绝原因要带数值与关节名，便于直接修复。

小结

  • 执行链路三段接力：规划输出、执行转发、控制器插值；排错按链路从后向前。
  • 轨迹点核心字段是位置与时间戳；控制器按时间插值生成控制指令，稀疏路点可以，错误时间戳不行。
  • 起点一致性是物理安全门槛，超差即拒绝；执行前核对起点应固化为流程。
  • 错误码分两类端点：执行接口回答哪一层失败，控制器动作回答控制器视角的原因。
