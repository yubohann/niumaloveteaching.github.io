第三篇 · 规划算法与求解器

第 057 章：MotionPlanRequest 与 MotionPlanResponse 消息结构

所有高层接口最终都归结为两个消息：请求描述"要什么"，响应描述"得到什么"。本章逐字段讲解两者的结构与语义规则，包括约束的合取与析取、缩放因子的取值边界、轨迹消息的构成。

  • 主题：消息结构 / 规划请求与响应
  • 关键机制：约束语义、状态差分、轨迹消息、字段默认规则
  • 预计学时：55 分钟
  • 前置章节：第 056 章

学习目标

  • 掌握 MotionPlanRequest 的全字段结构，理解目标约束（goal constraints）数组与路径约束的语义差别。
  • 理解 RobotState 消息的差分（is_diff）语义与起始状态的处理规则。
  • 能解释缩放因子、笛卡尔速度字段的生效条件与边界取值规则。
  • 掌握 MotionPlanResponse 的字段与 RobotTrajectory 的两层结构，能解读轨迹点的时间戳语义。
  • 会手工构造请求并调用规划服务，从响应中提取规划时间、错误码与轨迹数据。

背景与动机

第 041 到 056 章用到的所有控制点，最终都落在两个消息的字段上：时间预算、尝试次数、管线与规划器标识、约束结构。接口层（MoveGroupInterface、moveit_py、命令行工具）只是构造消息的便捷方式；消息结构才是行为的最终定义。

理解字段级语义的价值在调试中最直接：阅读日志里的请求内容、构造最小复现请求、把高层接口的行为误差定位到具体字段，都要求对两个消息的结构了如指掌。本章也是第 058 章动作接口的基础。

核心原理

1. MotionPlanRequest：字段全览与语义

字段类型语义与注意点
workspace_parametersWorkspaceParameters界定规划空间的包围盒（min_corner 与 max_corner）；缺省由适配器填入默认值
start_stateRobotState起始状态；为空表示使用当前状态；支持差分更新（见下节）
goal_constraintsConstraints[]目标区域的数组，满足任意一个元素即可（析取语义）
path_constraintsConstraints轨迹上任意一点都不得违反（合取语义）
trajectory_constraintsTrajectoryConstraints对结果轨迹整体的约束集合，使用频率低
reference_trajectoriesGenericTrajectory[]参考轨迹，供优化型规划器作初值；不覆盖起止约束
pipeline_id / planner_idstring选择管线与规划器；空值表示使用配置默认
group_namestring规划组名，必须与 SRDF 定义一致
num_planning_attemptsint32尝试次数；多次计算时按最短解报告（与第 041 章的结论一致）
allowed_planning_timefloat64规划时间上限（秒），覆盖整个规划调用
max_velocity_scaling_factorfloat64速度缩放；取值在 (0, 1] 之外（含 0.0）时按 1.0 处理
max_acceleration_scaling_factorfloat64加速度缩放；边界规则同上
cartesian_speed_end_effector_linkstring笛卡尔速度限制作用的末端链路
max_cartesian_speedfloat64末端速度上限（m/s）；需要 SetMaxCartesianEndEffectorSpeed 适配器生效

两条最容易被忽略的规则：其一，目标约束数组是"或"，路径约束是"与"；其二，缩放因子的越界值（包括 0）会被内部重置为 1.0，把 0 当作"最慢"会得到相反的效果。

2. 约束消息族：目标区域的表达方式

Constraints 是容器，由四类约束组合而成：

  • JointConstraint：关节名、目标位置与上下容差（[position − tolerance_below, position + tolerance_above]）、权重。
  • PositionConstraint：链路名、链路系下的目标点偏置、约束区域（BoundingVolume）与权重。约束区域由解析形状或多边形网格列表构成，多个形状按并集解释。
  • OrientationConstraint：链路名、四元数目标姿态、三个轴向容差、误差参数化方式（默认欧拉角，另有旋转向量）与权重。
  • VisibilityConstraint：可见性约束（第 037 章），用于视线相关任务。

权重字段的含义是"相对重要性"，越接近 0 表示越不重要。结构性结论：位置约束定义的是"区域"；目标位姿通常由位置区域与姿态容差共同界定，把容差设为零并不会得到"精确解"，只会让约束退化难解。

3. RobotState 与差分语义

RobotState 消息包含关节状态（joint_state）、多自由度关节状态、附加碰撞物体列表与一个差分标志 is_diff。差分标志决定接收方如何合并这份状态：

  • is_diff = false：完整状态，替换目标对象的全部内容（包括清空附加物体）。
  • is_diff = true：增量更新，只覆盖消息中出现的关节与物体。

start_state 的使用纪律：给出完整状态（is_diff = false）最不容易产生歧义；若只关心少数关节，用差分会把其余关节留给接收方的当前值，行为依赖上下文。

4. MotionPlanResponse 与轨迹消息

响应结构包含五个字段：trajectory_start（实际使用的起始状态，可能已由适配器修复）、group_name、trajectory（RobotTrajectory）、planning_time（求解耗时）与 error_code。轨迹消息分两层：

  • joint_trajectory：关节名列表与路径点数组；每个路径点含位置、速度、加速度、力矩与 time_from_start。
  • multi_dof_joint_trajectory：多自由度关节（浮动基座等）轨迹，机械臂场景通常为空。

时间戳语义：time_from_start 表示相对轨迹起点的耗时，量纲为秒。执行前必须确认每个路径点的时间戳单调递增，且最后一点的时间与控制器预期匹配（第 059 章展开重放细节）。

实现思路与设计

两种构造路径与选择建议：

路径方式适用
高层接口设置目标与参数，由接口填充消息字段日常开发；字段覆盖必须核对接口文档
手工构造直接填充消息并调用服务或动作最小复现、跨系统集成、字段级控制

构造检查清单（手工路径）：

  1. group_name 与 SRDF 逐字核对；pipeline_id 与 planner_id 按第 039 到 046 章的命名填写或留空。
  2. start_state 选择完整状态；附加物体在带载任务中一并给出。
  3. 目标用约束表达：关节目标用 JointConstraint；位姿目标用位置区域加姿态容差。
  4. 预算字段显式写入；缩放因子避开 0 值陷阱。
  5. 响应解析顺序：先看 error_code（第 049 章），再看 planning_time 与 trajectory_start 是否与请求一致。

与第 058 章的衔接：本章的服务与消息是"一次函数调用"形态；动作接口在消息之上增加进度、取消与执行阶段，字段本身完全一致。

关键代码与解读

片段 1：手工构造请求并调用规划服务（Python）

import rclpy
from rclpy.node import Node
from moveit_msgs.srv import GetMotionPlan
from moveit_msgs.msg import (MotionPlanRequest, Constraints,
                             JointConstraint, WorkspaceParameters)

class PlanClient(Node):
    """最小请求构造：字段级控制是跨系统集成与最小复现的基础。"""
    def __init__(self):
        super().__init__("plan_client")
        self.client = self.create_client(GetMotionPlan, "/plan_kinematic_path")

    def make_request(self):
        req = MotionPlanRequest()
        req.group_name = "arm_group"                  # 与 SRDF 组名逐字一致
        req.num_planning_attempts = 5                 # 多次尝试重启，最短解被报告
        req.allowed_planning_time = 1.0               # 秒：覆盖整个调用
        req.max_velocity_scaling_factor = 0.3         # 注意：0 会被内部重置为 1.0
        req.max_acceleration_scaling_factor = 0.3

        wp = WorkspaceParameters()
        wp.min_corner.x, wp.min_corner.y, wp.min_corner.z = -1.0, -1.0, 0.0
        wp.max_corner.x, wp.max_corner.y, wp.max_corner.z = 1.0, 1.0, 1.5
        req.workspace_parameters = wp                  # 显式工作空间：限定采样范围

        goal = Constraints()                           # 单个目标区域
        for name, pos in zip(["joint1", "joint2", "joint3", "joint4", "joint5", "joint6"],
                             [0.4, -0.6, 0.8, -0.5, 0.6, 0.0]):
            jc = JointConstraint()
            jc.joint_name = name
            jc.position = pos
            jc.tolerance_above = 0.01                  # 目标区域：上下各 0.01 rad
            jc.tolerance_below = 0.01
            jc.weight = 1.0                            # 权重：1.0 表示硬性满足
            goal.joint_constraints.append(jc)
        req.goal_constraints.append(goal)              # 数组语义：满足任意一个即可
        return req

解读：这段代码把第 041 章的两个预算参数、第 036 章的目标区域思想、第 042 章的工作空间规则落实为具体字段。目标区域用上下容差表达：0.01 rad 的容差既保持精度又给采样留下命中空间；权重 1.0 表示该约束不可打折。工作空间六个数显式写出，避免依赖默认值。所有字段均有中文注释，可直接作为最小复现模板使用。

片段 2：响应解析（Python，接片段 1 的调用结果）

def inspect_response(res):
    """按固定顺序解析响应：错误码 -> 时间 -> 起始状态 -> 轨迹结构。"""
    mp = res.motion_plan_response                       # 服务响应的嵌套结构
    print(f"错误码 {mp.error_code.val}，规划耗时 {mp.planning_time:.3f} s")   # 第 049 章解读
    if mp.error_code.val != 1:                          # 1 为成功
        return None

    # 实际使用的起点可能与请求不同：适配器可能做过修复（第 042 章）
    start_positions = mp.trajectory_start.joint_state.position
    print(f"轨迹起点关节数 {len(start_positions)}，组名 {mp.group_name}")

    jt = mp.trajectory.joint_trajectory                 # 关节轨迹层
    print(f"关节名 {list(jt.joint_names)}，路径点 {len(jt.points)} 个")
    p0, pn = jt.points[0], jt.points[-1]
    print(f"首点 time_from_start {p0.time_from_start.sec}"
          f".{p0.time_from_start.nanosec:09d} s")
    print(f"末点 time_from_start {pn.time_from_start.sec}"
          f".{pn.time_from_start.nanosec:09d} s，"
          f"速度维度 {len(pn.velocities)}")
    return jt

解读：解析顺序对应三个诊断问题：成不成（错误码）、花多久（规划时间）、拿到什么（起始状态与轨迹）。重点观察两处容易踩空的细节：其一，trajectory_start 可能与请求的 start_state 不同，这是适配器修复的痕迹；其二，路径点的 time_from_start 是"相对起点的耗时"，末尾值即轨迹总时长，执行前应核对它与控制器预期一致。速度维度检查用于确认时间参数化确实执行（第 042 章）。

片段 3：用工具函数构造位姿目标约束（C++）

#include <moveit/kinematic_constraints/utils.h>

// 位姿目标的标准构造：位置区域 + 姿态容差；容差参数直接决定目标区域大小
void set_pose_goal(moveit_msgs::msg::MotionPlanRequest& req,
                   const geometry_msgs::msg::PoseStamped& pose,
                   const std::string& tip_link)
{
  // 位置容差 0.005 m、姿态容差 0.05 rad：贴合类任务收紧，搬运类可放宽
  moveit_msgs::msg::Constraints goal =
      kinematic_constraints::constructGoalConstraints(tip_link, pose, 0.005, 0.05);

  req.goal_constraints.clear();                       // 清空旧目标：避免多区域混叠
  req.goal_constraints.push_back(goal);               // 单区域目标：满足全部约束即可
}

解读：工具函数的两个容差参数是目标区域设计的最小抓手：位置容差生成一个包围目标点的小立方区域，姿态容差生成围绕目标四元数的锥形容差；两者共同决定"采样命中困难程度"。清空旧目标再追加，避免把上一任务的目标区域留在数组中造成析取歧义。若任务需要多个可选目标区域（如双手备选抓取位），向数组追加多个 Constraints 即可，数组的析取语义正是为这类需求设计。

常见坑

  • 把 0 当"最慢"：max_velocity_scaling_factor 置 0 会被内部重置为 1.0（见字段注释），实际以满速规划。修复：要保守就显式写 0.1 到 0.5。
  • 目标约束数组语义误用：把"必须同时满足的两个条件"分放两个数组元素，得到"满足其一即可"的宽松目标。修复：同一区域的约束放进同一个 Constraints；可选区域才拆数组。
  • 路径约束写成目标约束：期望"全程保持姿态"却只设置了 goal_constraints，中间段姿态不受约束。修复：姿态保持类需求放入 path_constraints。
  • 忽略 is_diff 语义：差分状态误用导致附加物体未清空或关节残留。修复：构造完整状态并显式设置 is_diff = false。
  • 直接使用 time_from_start 作绝对时间：把相对耗时当墙钟时间戳去对齐其它系统，产生数秒级偏差。修复：执行时以"轨迹启动时刻加 time_from_start"换算，见第 059 章。

练习与思考

  1. 写出"目标区域 A 或目标区域 B"与"目标区域 A 且姿态条件 P"两种语义的字段组织方式。★
    提示
    A 或 B：goal_constraints 数组中放两个元素；A 且 P：同一个 Constraints 里同时放位置类与姿态类约束。数组是析取、容器内是合取。
  2. 某请求缩放因子为 0.0，期望"最慢执行"，实际执行满速。解释原因并给出正确写法。★
    提示
    0.0 属于越界值，被重置为 1.0。正确写法是显式的正小值，如 0.05 到 0.2，并在响应轨迹上核对 time_from_start 末值是否相应变长。
  3. 设计一个"多备选目标"的抓取任务请求：同一工件有两个可行抓取位姿，任一可达即可。写出约束组织与验证方法。★★
    提示
    两个抓取位姿各自构造位置加姿态约束，放入 goal_constraints 两个元素；验证：统计多次规划的结果分别命中哪个区域，确认两者都被覆盖。
  4. 分析题：响应的 trajectory_start 与请求 start_state 不同，列出可能的两类原因与各自的确认方法。★★★
    提示
    原因一：起点碰撞修复适配器改写了起点（检查是否开启 FixStartStateCollision，对比差值幅度）；原因二：请求 start_state 为空时用了当前状态（检查是否显式设置起点）。确认方法：比较两者的关节向量与时间戳。

小结

  • MotionPlanRequest 的字段覆盖预算、标识、约束与状态四大类；高层接口只是构造它的便捷方式。
  • 目标约束数组是析取语义，容器内约束是合取语义；路径约束作用于全程。
  • 缩放因子越界（含 0）会重置为 1.0；笛卡尔速度字段依赖专用适配器生效。
  • RobotState 的 is_diff 决定替换与合并行为；完整状态最不易产生歧义。
  • 响应按"错误码、规划时间、起始状态、轨迹结构"顺序解析；time_from_start 是相对耗时。
