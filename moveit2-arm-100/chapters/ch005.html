第一篇 · 环境搭建与基础控制

第 005 章：加载机械臂到 RViz

本章在 RViz 的 MotionPlanning 插件中完成第一次端到端验证：显示模型与场景，设置起始与目标状态，规划并假执行一条轨迹。

  • 主题：可视化调试 / 交互式规划验证
  • 关键机制：MotionPlanning 插件、交互式标记、规划请求面板
  • 预计学时：50 分钟
  • 前置章节：第 004 章

学习目标

  • 理解 MotionPlanning 插件与 move_group 的客户端服务端关系，明确界面操作背后发生的通信。
  • 掌握三个显示面板的分工：场景机器人（Scene Robot）、规划请求（Planning Request）、规划轨迹（Planned Path）。
  • 会在 Planning 面板中设置起始与目标状态、发起规划、假执行，并用交互式标记直接拖动目标位姿。
  • 能从显示状态判断配置正确性：TF 是否完整、模型是否加载、规划组是否可选。
  • 能用程序化检查脚本核对界面所依赖的接口全部在线，为后续自动化测试打底。

背景与动机

配置包生成后，最经济的验证方式是在可视化环境中完成一次完整交互：模型出现在正确位置、关节能按预期运动、规划按钮产出轨迹。RViz 的 MotionPlanning 插件承担这个角色，它把规划请求的构造过程变成图形操作，把规划结果变成可见的轨迹与动画。

这个环节的价值在于及早暴露配置问题。TF 树缺一段、规划组未覆盖末端、虚拟关节方向错误这类问题，在纯文本配置里不易察觉，在三维视图中一目了然。把本章当作一次全面体检：界面上每一处异常都对应配置层的一个确定问题，修好之后才进入代码接口阶段。后续章节的自动脚本调试，实际上都在反复执行本章图形界面里完成过的动作。

核心原理

本节的原理主线是：插件如何与规划服务通信，界面上的每块显示由什么数据驱动，以及交互式操作对应的请求变换。

1. MotionPlanning 插件：RViz 内部的规划客户端

RViz 进程内加载 MotionPlanning 显示插件，插件内部持有一组客户端：向 move_group 的规划动作接口发送规划请求，向场景查询服务拉取最新规划场景，订阅监视场景话题获取增量更新。规划计算全部发生在 move_group 进程，RViz 只负责构造请求与绘制结果。

界面元素数据来源交互产生的请求
规划组下拉框SRDF 的组列表切换后续请求的组名参数
交互式标记当前起始状态的正运动学拖动标记改变目标位姿
Plan 按钮当前起始与目标设置规划动作目标（Plan 阶段）
Execute 按钮最近一次规划结果执行动作目标（Execute 阶段）
轨迹动画规划结果轨迹本地回放，无网络请求

理解这一点后，一条排错原则自然成立：界面上的任何异常，先判断数据来自哪个接口，再检查该接口的服务端状态。模型不显示查描述与 TF，轨迹不出现查规划动作，执行无动作查控制器。

2. 显示层次：当前状态、目标、轨迹

MotionPlanning 插件的显示分三层，对应规划问题的三要素：

  • 场景机器人（Scene Robot）：机器人当前状态，来自监视场景话题。半透明度设置让当前状态不遮挡目标状态，是并行观察两个姿态的关键。
  • 规划请求（Planning Request）：起始状态与目标状态的显示开关。起始状态与目标状态以不同着色区分显示，两者之间可以叠加碰撞高亮。拖动交互式标记时，目标状态实时更新。
  • 规划轨迹（Planned Path）：规划结果的可视化，支持一头播放与回放速度调节。轨迹的图层顺序与透明度决定观察效果，复杂场景中建议降低当前状态的透明度。

显示层之外还有状态反馈：机器人与场景物体干涉时，相关连杆按碰撞色高亮；规划失败时面板状态栏给出错误码。这些反馈与第 001 章的错误码体系对应，是调试的第一手线索。

3. 坐标系：Fixed Frame 与虚拟关节的一致性

RViz 全局选项中的 Fixed Frame 决定整个视图的基准坐标系。它与第 004 章定义的虚拟关节必须配合：虚拟关节把机器人锚定到 world，Fixed Frame 就应选 world 或与之固定连接的坐标系。

Fixed Frame = world（或 map），虚拟关节 parent = world，child = base_link 三者理顺后，场景物体与机器人才共享一个不变的参考系

把 Fixed Frame 选成随关节运动的链接，例如法兰，观察上似乎更方便，实际会让整个场景在视图中漂移，因为背景坐标系本身在运动。固定参考系的选择原则是"根系选根"。

4. 交互式标记的请求语义

拖动末端交互式标记会生成位姿目标，其内部经历逆运动学求解：标记位置映射到目标位姿，插件尝试求出一组关节角使末端到达该位姿。工作空间内的点通常有解，边界附近可能无解，标记会回弹或停在近似位置。

由此可以做一个有意义的观察实验：沿工作空间边缘拖动标记，观察哪些方向率先失去解。这个实验建立对机械臂工作空间的直觉，也为第 011 章笛卡尔空间运动的目标设计提供依据。标记拖动是检验 IK 配置的最短路径：若拖动任何位置都无法求解，问题多半在规划组划分或末端的运动学设置，而不在算法。

实现思路与设计

验证流程分界面准备、交互规划、结果检查三个阶段，每个阶段给出完成标准。

操作流程（界面步骤）

  1. 启动演示系统，等待 move_group 日志出现"规划管线就绪"类信息。
  2. 在 Global Options 中设置 Fixed Frame 为 world，确认机器人出现在工作台上方，位置合理；若停在原点半空，核对 TF 发布与 Fixed Frame 设置。
  3. 添加 MotionPlanning 显示，确认规划组下拉框能列出 arm 与 gripper 两组。
  4. 选择 arm 组，把 Scene Robot 的透明度调到 0.5，便于区分当前状态与目标状态。
  5. 在 Planning 标签页把起始状态设为"当前状态"，目标状态选择命名位姿 ready，点击 Plan。
  6. 观察轨迹生成后，勾选 Planned Path 显示，用回放滑条逐段检查关节运动。
  7. 点击 Execute，确认执行完成（演示环境由假控制器接管，无物理运动属预期）。
  8. 切换到交互式标记，拖动末端到桌面上方 0.3 m 附近，观察目标更新与规划结果变化。

设计决策：演示环境为什么用假控制器？

假控制器接收关节轨迹消息并立即报告执行完成，不做任何物理运动。它的作用是把"规划到执行"的接口链路完整打通并保持零风险。界面验证阶段区分两类目标：几何正确性（可用假控制器验证）与运动学正确性（需要真实或仿真控制器验证）。本章完成前者；真实控制器在第 014 章接入。

关键代码与解读

本节展示三类片段：RViz 配置文件的插件段、启动文件中 rviz 节点的参数装配、以及核对接口在线状态的自检脚本。

解读：配置文件把界面状态固化为文本，保证每次启动的观察条件一致。（1）Fixed Frame 与虚拟关节的配合是显示正确性的前提，两者不一致时机器人相对桌面漂移。（2）规划组名称是界面与服务端的连接键，拼写错误会让面板显示为空。（3）轨迹话题 /display_planned_path 是 move_group 输出规划结果的默认通道，订阅它可以脱离界面做程序化轨迹检查。（4）把查看配置纳入版本管理，团队内共享同一套观察条件，界面差异导致的口径不一随之消失。

片段 2：启动文件中 rviz 节点的装配

def generate_launch_description():
    # 允许命令行替换配置文件：调试时用检查清单专用配置，无需改代码
    declared = DeclareLaunchArgument("rviz_config", default_value="moveit.rviz")
    moveit_config = MoveItConfigsBuilder("arm_robot",
        package_name="arm_robot_moveit_config").to_moveit_configs()
    rviz = Node(
        package="rviz2",
        executable="rviz2",
        # 配置文件路径由参数拼出，避免绝对路径写死
        arguments=["-d", PathJoinSubstitution([
            FindPackageShare("arm_robot_moveit_config"), "config",
            LaunchConfiguration("rviz_config")])],
        # 描述类参数必须传给 rviz：插件凭它加载模型与运动学
        parameters=[
            moveit_config.robot_description,
            moveit_config.robot_description_semantic,
            moveit_config.robot_description_kinematics,
        ],
    )
    return LaunchDescription([declared, rviz])

解读：这段装配解决"界面看得见"的三个数据来源。（1）描述、语义、运动学三类参数缺一不可：缺描述则无模型，缺语义则无规划组，缺运动学则交互标记无法求解。（2）把配置文件做成启动参数，同一套系统可以在"演示界面"与"检查界面"之间快速切换。（3）路径通过包的查找机制拼接，配置包安装到任何前缀下都能定位，这与第 002 章的叠加机制直接相关。

片段 3：接口在线状态自检脚本

import rclpy
from rclpy.node import Node
from rclpy.action import ActionClient
from moveit_msgs.action import MoveGroup
from moveit_msgs.srv import GetPlanningScene

class InterfaceCheck(Node):
    """核对界面与脚本共同依赖的服务端接口是否在线。"""
    def __init__(self):
        super().__init__("interface_check")
        # 规划动作端点：Plan 与 Execute 按钮、脚本请求都走这里
        self.move_action = ActionClient(self, MoveGroup, "/move_action")
        # 场景查询服务：RViz 面板刷新场景时调用
        self.scene_srv = self.create_client(GetPlanningScene, "/get_planning_scene")

    def report(self):
        # 等待带超时：接口缺失时脚本在有限时间内给出明确结论
        action_ok = self.move_action.wait_for_server(timeout_sec=3.0)
        service_ok = self.scene_srv.wait_for_service(timeout_sec=3.0)
        self.get_logger().info(f"规划动作在线: {action_ok}")
        self.get_logger().info(f"场景服务在线: {service_ok}")
        return action_ok and service_ok

def main():
    rclpy.init()
    node = InterfaceCheck()
    ok = node.report()
    node.get_logger().info("接口自检" + ("通过" if ok else "失败"))
    node.destroy_node()
    rclpy.shutdown()

if __name__ == "__main__":
    main()

解读：把界面依赖的接口变成可编程断言。（1）两个接口覆盖两条关键链路：动作接口支撑规划与执行，场景服务支撑状态展示；两者同时在线说明 move_group 已完成初始化。（2）等待全部带超时，脚本在服务端缺席时会返回确定结论，适合纳入持续集成式的冒烟检查。（3）该脚本与 RViz 操作验证的是同一套服务端，界面排障时先跑脚本，能把"界面问题"与"服务端问题"快速分离。

常见坑

  • Fixed Frame 选错：机器人或场景在视图中漂移，拖动时尤其明显。修复：改为 world，并确认 TF 树中 world 到基座的链条完整。
  • 插件缺少描述参数：面板持续提示模型未加载。修复：检查 rviz 节点参数中描述、语义、运动学三项是否齐全，与片段 2 对照。
  • 规划组未选中导致交互标记缺失：连接成功后看不到可拖动的标记。修复：确认面板顶部已选中规划组，且该组的末端链条在 SRDF 中定义正确。
  • 把 Plan 成功当成执行成功：点击 Execute 无任何反馈。修复：确认控制器映射与假控制器状态；Plan 与 Execute 是两条独立链路，前者成功不蕴含后者可用。
  • 拖动目标无解后误判为系统故障：工作空间边缘 IK 失败，标记回弹。修复：向工作空间内部回拖，或检查该目标的姿态约束是否过严，第 011 章会系统处理这类问题。

练习与思考

  1. 完成一次 home 到 ready 的界面规划，记录面板显示的失败次数与 move_group 终端日志中的规划耗时，判断本次规划属于"一次命中"还是"多次尝试"。★
    提示
    日志会给出每次尝试的结果与总耗时；简单场景下的命名位姿切换通常一次命中，耗时在 0.1 s 量级以内。
  2. 比较两种目标设置方式：从下拉框选择命名位姿与拖动交互标记，分别对应规划请求里什么字段的差异？★
    提示
    命名位姿对应关节空间约束；交互标记对应末端位姿约束，服务端需要先做逆解。第 010 与 011 章将从接口层面展开这一区别。
  3. 预测实验：把 Scene Robot 的透明度从 0.5 调到 1.0 再规划同一目标，观察结果是否变化。再从 0.5 调到 0.1，解释画面上发生的变化及其原因。★★
    提示
    透明度只影响绘制，与规划计算无关；降低透明度让轨迹与目标状态更清晰，但当前状态本身更难辨认，需要注意观察次序。
  4. 设计题：为实验室的机械臂编写一份"RViz 验收清单"，覆盖模型显示、坐标系、规划组、命名位姿、规划与假执行六个环节，每项给出通过标准与失败时的第一检查点。★★★
    提示
    参考本章的参数与观察项对照表，把每项失败映射到配置层的责任文件；清单的价值在于把"看一眼"变成"查一处"。

小结

  • MotionPlanning 插件是运行在 RViz 内的规划客户端，规划计算全部发生在 move_group。
  • 显示分三层：当前状态、规划请求、规划轨迹；每层的异常指向不同的服务端接口。
  • Fixed Frame 与虚拟关节必须一致，参考系的选择原则是选根系而不用运动连杆。
  • Plan 与 Execute 是两条链路，假控制器让接口链路可测且零风险。
