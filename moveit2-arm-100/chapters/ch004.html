第 004 章：配置 MoveIt2 Setup Assistant

本章把 URDF 加工成 MoveIt2 可用的配置包：用自碰撞矩阵裁剪碰撞对，用规划组划分运动链，用命名位姿与末端执行器补充语义。

  • 主题：配置生成 / SRDF 语义建模
  • 关键机制：自碰撞矩阵采样、规划组划分、SRDF 生成
  • 预计学时：60 分钟
  • 前置章节：第 003 章

学习目标

  • 理解 SRDF（Semantic Robot Description Format）相对 URDF 增加的语义信息：规划组、命名位姿、末端执行器、碰撞豁免。
  • 掌握自碰撞矩阵（Self-Collision Matrix）的生成机制，能根据机械臂规模选择合理的采样密度。
  • 会用链（Chain）与关节集合（Joint Collection）两种方式定义规划组，并解释选择依据。
  • 能独立完成 Setup Assistant 全流程，生成包含 SRDF、运动学、规划与控制器配置的完整配置包。
  • 能在生成结果中核对关键配置项，识别"生成成功但语义错误"的隐性问题。

背景与动机

URDF 回答了"机械臂由哪些零件组成、怎么动"，但规划系统还关心另外一类问题：哪些关节应该一起规划、末端执行器在哪里、哪些连杆对永远不会碰撞、机器人的基座固定在世界何处。这些信息属于语义层，URDF 表达不了，MoveIt2 用 SRDF 承载，而 Setup Assistant 是生成这份语义描述的标准工具。

Setup Assistant 的操作界面友好，但每一步的选择都会固化为规划系统的行为：规划组划错会让某些目标永远无解，自碰撞矩阵生成得太粗会让危险碰撞被忽略，命名位姿定义不当会让演示脚本开局即失败。本章的重点在于理解每个步骤背后写入的内容，让图形界面的操作有据可依。配置包生成之后，第 005 章的 RViz 验证与后续全部章节都建立在这份语义描述之上。

核心原理

本节围绕 SRDF 的四类核心语义展开：规划组、碰撞豁免、命名位姿、末端执行器，随后解释自碰撞矩阵的生成算法。

1. SRDF：在几何之上补语义

MoveIt2 启动时同时加载 URDF 与 SRDF，合并为一个完整的机器人模型（RobotModel）。URDF 提供运动学与几何，SRDF 提供规划相关的语义约束。两份文件通过链接与关节的名字关联，任何一侧改名都必须同步另一侧，否则语义条目会静默失效或导致加载失败。

SRDF 条目作用缺失时的症状
规划组 group定义可规划的关节子集与链接口查询不到组名，无法发起规划
组状态 group_state保存命名关节位姿命名位姿引用失败
末端执行器 end_effector关联夹爪组与安装法兰抓取类功能无法识别工具
碰撞豁免 disable_collisions关闭永远不相碰的连杆对检测碰撞检测开销大，自碰撞误报多
虚拟关节 virtual_joint把机器人固定到世界坐标系基座悬空，场景中物体与机器人错位
被动关节 passive_joint声明不由控制器驱动的关节执行时报关节不匹配

2. 自碰撞矩阵：用采样换确定

自碰撞检测要枚举全部连杆对，但对数随链接数平方增长：14 个链接产生 91 对。其中相当一部分对在物理上永远不可能碰撞，例如相邻连杆（固定连接或共享关节）与对称的夹爪指。它们的存在只会增加每次碰撞查询的开销，还会因几何近似导致误报。

Setup Assistant 的生成流程如下：先自动豁免相邻与固定连接的对；对剩余对逐对采样。对每一对 (linki, linkj)，在随机关节状态下检测两者碰撞；若连续 k 次采样均无碰撞，则判定该对为"永不碰撞"并写入豁免列表。

采样密度 k（默认 10000）→ 若 k 次均无碰撞，则该对写入 disable_collisions k 越大越保守（更好抓出偶尔才碰撞的对），但采样过程更久；判定错误的方向必须是"宁可保留检测"

采样密度是唯一需要权衡的参数。密度过低时，两个实际上偶尔碰撞的连杆对被错误豁免，规划器会输出穿过自身的轨迹；密度过高时，生成过程变长，收益迅速衰减。经验判断：连杆几何关系简单的小型臂取几千次就能收敛；带复杂外壳与多指夹爪的模型建议保持默认的 10000 次。写出的豁免列表可以在 SRDF 中逐条审查，怀疑某对时将其删除即可恢复检测。

3. 规划组：链与关节集合

规划组是规划请求的最小单位，组的自由度决定采样空间的维度。两种定义方式对应两类结构：

  • 链（Chain）：指定起始链接与末端链接，中间路径上的所有关节自动纳入。六轴串联臂从基座到法兰的整条链用一次选择即可定义，模型改版增删中间关节时定义保持有效。
  • 关节集合（Joint Collection）：逐个选中关节，适合不构成链的平行结构。二指夹爪的两个滑动关节是典型例子，它们从腕部旁支伸出，链定义无法描述。

组名一旦确定就进入所有上层代码与配置文件，因此命名要在配置阶段一次定好：手臂用语义化的名称（如 arm 或 manipulator），夹爪用 gripper。第 016 章还会处理组的层级与末端执行器组，本章先建立最小可用的两组结构。

4. 命名位姿与末端执行器

命名位姿把常用的关节配置保存成符号（如 home、ready、vertical），让"回零"与"准备取物"成为一次名称引用。它的价值在于把调试好的姿态固化进配置，脚本与操作界面共享同一套姿态定义。命名位姿属于某个规划组，保存时记录该组全部关节的角度。

末端执行器条目把夹爪组与手臂组连接起来：记录安装法兰链接（parent_link）、手臂组名与夹爪组名。MoveIt2 的抓取功能通过这条关联确定工具的位姿与操作对象，姿态控制、附加物体等机制也依赖它定位抓手坐标系。法兰链接选错会导致末端位姿整体偏移一个连杆的变换，这类错误在纯运动测试中不显现，进入抓取任务后才集中暴露。

5. 虚拟关节与坐标系锚定

URDF 的运动学树没有"世界"概念，基座 link 的位姿悬空。虚拟关节（Virtual Joint）把基座 link 与一个外部坐标系（通常是 world）连接起来，类型选 fixed 表示固定安装，选 planar 或 floating 表示可移动基座。规划场景中的桌面、货架等物体通常定义在 world 坐标系下，虚拟关节就是机器人与场景坐标系的接缝，接缝错位会让机器人与桌子对不上，而规划本身可能仍然报成功。

实现思路与设计

Setup Assistant 流程按向导顺序推进，每步的产出都写入最终配置包，验证点也随步骤设置。

标准流程与逐步验证点

  1. 加载 URDF：确认链接与关节计数与第 003 章的设计一致，检查每个关节限位已读出。
  2. 生成自碰撞矩阵：采样密度取默认 10000；生成后抽查豁免列表，确认相邻对已自动豁免。
  3. 定义虚拟关节：名称 world，类型 fixed，parent 为 world，child 为 base_link。
  4. 创建规划组：arm 组用链，从 base_link 到法兰链接；gripper 组用关节集合，选中两个指关节；检查组的自由度显示。
  5. 保存命名位姿：在关节滑动条上摆出 home、ready、vertical 三个姿态并保存；保存前检查是否与桌面碰撞。
  6. 配置末端执行器：绑定 gripper 组到 arm 组的法兰链接，命名如 tool0。
  7. 配置控制器与作者信息：生成 ros2_control 控制器条目与规划管线参数，最后写入配置包目录。

设计决策：为什么先验证再微调数字？

配置包生成后，人工微调难以避免：改采样密度、补命名位姿、调关节缩放。直接手改生成文件会与后续重新生成的结果冲突。推荐策略是在首次生成时把语义结构（组、末端执行器、虚拟关节）定准，生成的数值参数再按章节需要微调，且在配置包内用注释标记改动点，保持"生成结果加补丁"的清晰边界。这是配置长期可维护的前提。

关键代码与解读

Setup Assistant 以图形界面操作，其产出是文本配置。本节展示三类产出文件的关键片段：SRDF、运动学配置、演示启动文件。

片段 1：SRDF 关键条目

<robot name="arm_robot">
  <!-- 规划组之一：手臂，用链定义，从基座到法兰的关节自动纳入 -->
  <group name="arm">
    <chain base_link="base_link" tip_link="flange"/>
  </group>

  <!-- 规划组之二：夹爪，平行指关节用关节集合定义 -->
  <group name="gripper">
    <joint name="finger_joint_1"/>
    <joint name="finger_joint_2"/>
  </group>

  <!-- 命名位姿：属于手臂组，记录该组全部关节角（弧度） -->
  <group_state name="home" group="arm">
    <joint name="joint_1" value="0"/>
    <joint name="joint_2" value="0"/>
    <joint name="joint_3" value="0"/>
    <joint name="joint_4" value="0"/>
    <joint name="joint_5" value="0"/>
    <joint name="joint_6" value="0"/>
  </group_state>

  <!-- 末端执行器条目：把夹爪组挂到手臂法兰上，供抓取功能定位工具 -->
  <end_effector name="gripper_tool" parent_link="flange"
                group="gripper" parent_group="arm"/>

  <!-- 碰撞豁免：采样判定为永不碰撞的连杆对，减少查询开销 -->
  <disable_collisions link1="link_2" link2="link_4" reason="Never"/>
  <!-- 相邻连杆对自动豁免，reason 标记来源便于审查 -->
  <disable_collisions link1="link_1" link2="link_2" reason="Adjacent"/>
</robot>

解读：这份 SRDF 是配置阶段的核心产出。（1）两个组用不同定义方式，对应手臂与夹爪两类结构；组的自由度决定后续采样空间的维度，arm 组为 6 维、gripper 组为 2 维。（2）group_state 记录的是该组全部关节的完整角度，保存时界面处于零位，但实际项目中一般摆到有意义的姿态再保存。（3）disable_collisions 的 reason 字段区分来源：Adjacent 来自自动豁免，Never 来自采样判定；手工审查时应重点核对 Never 条目。

片段 2：kinematics.yaml 中的 IK 配置

# 每个规划组可以绑定不同的 IK 求解器与参数；组名是连接键
arm:
  kinematics_solver: kdl_kinematics_plugin/KDLKinematicsPlugin
  # 搜索分辨率：数值越小越容易收敛，单次求解迭代也越多
  kinematics_solver_search_resolution: 0.005
  # 单次 IK 调用的时间上限，超时即判失败（单位：秒）
  kinematics_solver_timeout: 0.05
  # 同一目标用不同随机种子重试的次数：提高难点的求解成功率
  kinematics_solver_attempts: 3
# 夹爪组没有 IK 需求：平行指关节目标直接给关节值
gripper:
  kinematics_solver: kdl_kinematics_plugin/KDLKinematicsPlugin
  kinematics_solver_search_resolution: 0.005
  kinematics_solver_timeout: 0.05
  kinematics_solver_attempts: 3

解读：这份配置决定末端位姿目标的求解行为。（1）求解器按照组名绑定，多组可以搭配不同插件；第 050 章之后会横向对比各插件的能力差异。（2）timeout 与 attempts 构成两手策略：前者限制单次尝试的算力，后者提供多次机会；规划时间预算紧时应收缩 timeout，成功率不够时提高 attempts。（3）数值范围在本课程的示例中保持毫秒级到几十毫秒级，与规划总时间（0.5 至 5 s）相比占比很小，属于合理配置。

片段 3：生成的 demo.launch.py 结构

from launch import LaunchDescription
from launch_ros.actions import Node
from moveit_configs_utils import MoveItConfigsBuilder


def generate_launch_description():
    # 统一装载配置包：URDF、SRDF、运动学、规划管线、控制器一次到位
    moveit_config = MoveItConfigsBuilder("arm_robot",
        package_name="arm_robot_moveit_config").to_moveit_configs()
    # 演示用假控制器：不回读实际关节状态，仅校验轨迹接口
    # 真机部署时由 ros2_control 的真实控制器替换，配置结构不变
    fake_controller = Node(
        package="moveit_ros_planning",
        executable="fake_joint_trajectory_controller",
        parameters=[moveit_config.to_dict()],
    )
    # move_group 与 RViz 的装配与第 001 章一致，此处不再重复
    move_group = Node(package="moveit_ros_move_group", executable="move_group",
                      parameters=[moveit_config.to_dict()])
    rviz = Node(package="rviz2", executable="rviz2",
                arguments=["-d", str(moveit_config.package_path / "config/moveit.rviz")],
                parameters=[moveit_config.robot_description,
                            moveit_config.robot_description_semantic])
    return LaunchDescription([fake_controller, move_group, rviz])

解读：演示启动文件体现了配置包的自包含设计。（1）所有参数从同一配置包装载，MoveItConfigsBuilder 保证 URDF 与 SRDF 版本一致；手工拼各个 YAML 时最常见的错误就是两份描述不同步。（2）假控制器让"规划加执行"链路在无硬件条件下完整可测，是本课程前二十章的主推验证方式。（3）真机替换只发生在控制器一项上，这也解释了为什么配置阶段要把控制器映射放在独立的 YAML 文件里。

常见坑

  • 组定义遗漏关节：链条的 tip link 选在腕部，末三个关节没有纳入组，姿态目标全部无解。症状是位姿规划成功率极低而关节空间规划正常。修复：核对组自由度与设计值一致后再继续。
  • 采样密度过低导致碰撞豁免错误：低频碰撞对进入豁免列表，轨迹从自身穿过的现象偶发。修复：提高密度重新生成，或手工删除可疑的 Never 条目恢复检测。
  • 命名位姿保存在碰撞状态：home 姿态与桌面干涉，演示脚本每次启动都规划失败。修复：保存前在界面中检查碰撞指示，或把位姿抬高到安全区域。
  • 虚拟关节方向装反：parent 与 child 写反，整机位姿翻转到场景下方。修复：确认 parent 为 world、child 为基座链接。
  • 重新生成覆盖手工改动：在生成文件里手调参数后再次运行助手，改动丢失。修复：把手工改动挪到独立文件或记录补丁清单，生成流程只负责结构。

练习与思考

  1. 一台机械臂含 14 个链接。计算自碰撞检测需要评估的连杆对总数；若相邻与固定连接自动豁免了 15 对，采样过程实际处理多少对？★
    提示
    对数为 C(14, 2) = 91，减去自动豁免的 15 对，剩余 76 对进入采样判定。
  2. 解释链定义与关节集合定义各自的适用条件，并判断"腕部三轴"与"平行夹爪"分别应使用哪种定义。★
    提示
    腕部三轴随手臂链连续排列，纳入手臂链即可；平行夹爪从法兰旁支伸出，链结构无法覆盖，使用关节集合。
  3. 改参数预测：把自碰撞采样密度从 10000 降到 100，生成结果中 Never 条目数量与规划时自碰撞检出的灵敏度各会如何变化？说明推理过程。★★
    提示
    采样次数降低后，偶发碰撞更容易漏检，Never 条目偏多；规划期检出的碰撞事件减少，安全裕度下降。生成结果的条目数可以在两次生成间直接对比。
  4. 设计题：为一台带同步带传动的两指夹爪设计规划组方案：同步机构使两指位移存在定比例关系，规划时应把哪个关节纳入组、哪个关节应在仿真中忽略？说明理由。★★★
    提示
    考虑关节的被动（passive）属性：由机械耦合决定的从动关节标记为被动关节，避免执行器重复驱动导致接口不匹配。

小结

  • SRDF 在 URDF 之上补充语义：规划组、命名位姿、末端执行器、碰撞豁免、虚拟关节。
  • 自碰撞矩阵用采样换确定：相邻对自动豁免，其余对经采样判定；密度越高越保守，默认值适合常见模型。
  • 规划组用链定义串联结构、用关节集合定义平行结构；组名是上层全部接口的引用键。
  • 虚拟关节把基座锚定到 world，命名位姿把常用姿态固化为符号。
  • 下一章在 RViz 中验证整份配置：加载模型、检查规划组、完成第一次手动规划。
