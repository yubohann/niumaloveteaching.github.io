第 082 章：MoveGroup Action 详解

逐字段拆解 move_action 的动作定义与服务端处理流程，讲清规划请求（MotionPlanRequest）、规划选项（PlanningOptions）与结果错误码（Error Code）在"规划到执行"链条中的分工。

  • 主题：接口协议 / 规划请求与结果语义
  • 关键机制：MotionPlanRequest 字段语义、plan_only 与执行分离、错误码分类、缩放系数
  • 预计学时：55 分钟
  • 前置章节：第 081 章

学习目标

  • 掌握 move_action 动作定义的三段结构：目标（MotionPlanRequest 与 PlanningOptions）、反馈、结果（MoveGroupResult）。
  • 理解 MotionPlanRequest 关键字段的语义：起始状态、目标约束列表、路径约束、规划时间、尝试次数、缩放系数。
  • 会区分 plan_only 与"规划加执行"两种模式，并能设计"先规划、验证、再执行"的两段式流程。
  • 能读懂 MoveItErrorCodes 的分类规律，把常见错误码映射到具体原因。
  • 会使用命令行工具手动发送规划目标，用于接口联调与故障定位。

背景与动机

move_group 暴露的核心动作端点是 /move_action，消息类型为 moveit_msgs/action/MoveGroup。上层的 MoveGroupInterface、MoveItPy、RViz 插件最终都通过这个动作发起规划。理解它的字段语义，等于掌握了 MoveIt2 规划接口的公共语言。

实际故障多半出在请求语义上：目标约束写成"全部满足"导致无解、缩放系数留空导致全速运动、把规划失败误判为执行失败、起始状态过期导致规划起点与实际不符。这些问题在更高层封装中看不出来，只有拆到动作定义层面才能定位。

上一章讨论客户端如何调用，本章讨论调用的内容：请求里每个字段代表什么，服务端按什么顺序消费它们，结果里的错误码如何指导下一步动作。

核心原理

1. 动作定义的三段结构

MoveGroup 动作沿用标准三段式，字段分工如下。规划请求描述"从哪到哪、受什么约束"，规划选项描述"如何执行这次规划"，结果描述"发生了什么"。

段字段语义
目标request（MotionPlanRequest）规划任务本体：组名、起始状态、目标约束、时间预算、缩放系数
目标planning_options（PlanningOptions）调度选项：是否只规划（plan_only）、重规划开关、外观探索（look_around）等
结果result.error_code业务结果码，规划与执行成败的唯一权威判据
结果result.planning_time求解实际耗时，用于性能统计
结果result.planned_trajectory规划所得轨迹，供检查或二次执行
反馈state阶段状态字符串，用于进度观测

字段集合随发行版演进，以本地安装的消息定义为准；本节所述语义在 Humble 与 Jazzy 时期保持稳定。

2. 约束语义：列表取或、单体取与

目标约束字段 goal_constraints 是一个列表，含义是"满足任意一项即可"；而单个约束消息内部的多个约束分量之间是"与"关系。路径约束 path_constraints 只允许一个约束消息，轨迹全程必须满足。把多个可选目标写成一个约束消息，会把"或"变成"与"，直接制造无解。

目标可行 ⟺ ∃Gi ∈ goal_constraints，使 qgoal ⊨ Gi（列表取或）
单约束 G = C1 ∧ C2 ∧ … ∧ Cn（分量取与） 需要"位置或方向任选其一"时，应写成两个平行约束消息；在一个消息里放两个分量会被解读为两者同时满足

3. 服务端处理流程

目标被接受后，服务端按固定顺序处理：校验组名与请求合法性；解析起始状态（缺省时取当前状态并附带时间戳）；调用规划管线求解（适配器链加规划器）；若 plan_only 为假，进入执行链路（轨迹重采样、控制器分发、执行监视）；最终把结果写入动作结果。任一环节失败，错误码在结果中给出，反馈流随之结束。

规划成功概率随尝试次数累积：P(N) = 1 − (1 − p)N 单次成功概率 p = 0.3 时，10 次尝试的累积成功率约 97%；p 很小时提升尝试次数收益有限，应优先检查可达性与碰撞

尝试次数（num_planning_attempts）与规划时间（allowed_planning_time）是两种正交预算：前者约束采样重试次数，后者约束总耗时。窄通道场景提高尝试次数有效；求解器迭代型场景提高时间预算更直接。

4. 缩放系数的语义与生效位置

速度与加速度缩放系数（max_velocity_scaling_factor、max_acceleration_scaling_factor）取值区间为 (0, 1]，在时间参数化（Time Parameterization）阶段乘到轨迹速度与加速度上限上。缩放后的执行时长近似满足：

T执行 ≈ max(T路程 / sv, T加速段 / sa) 仅速度缩放为 0.5 时，匀速段时长加倍；若同时提高加速度缩放，加速段占比重构，总时长由两项中的更大者决定

缩放系数取 0 表示"未设置"，服务端按默认上限处理，不能把 0 当作静止。该字段作用于规划侧的时间参数化；控制器侧还有各自的速度限制，两层限制最终取更严格者。

实现思路与设计

构造一次高质量的规划请求，需要按"起始状态、目标约束、预算、限制、执行策略"五段填写。五段的顺序对应服务端的消费顺序，遗漏任何一段都可能在后续环节产生难以定位的失败。

1. 请求五段清单

段字段典型取值依据
起始状态start_state显式关节值离线规划与回放必须显式给出；在线任务可留空取当前状态
目标约束goal_constraints关节约束或位姿约束关节约束求解负担小；位姿约束需要 IK 参与
预算allowed_planning_time、num_planning_attempts1–5 s、10 次时间预算法则按"求解加余量"设置；尝试次数 10 次为常见起点
限制max_velocity_scaling_factor 等0.1–0.5调试阶段取低值，验证通过后逐步提高
执行策略planning_options.plan_onlytrue 或 false需要人工校验或二次分发时取 true

2. 两种调用模式

  1. 单目标模式：一个目标完成规划与执行，plan_only 为假。调用简洁，适合已验证的稳定任务。
  2. 两段式模式：先以 plan_only 为真规划并取回轨迹，做碰撞复检、速度审查或可视化确认，再单独通过 /execute_trajectory 执行。可插入验证与审批，也便于失败时区分规划与执行责任。
设计决策：何时使用两段式？

凡是有外部条件可能使规划失效的场合（场景动态更新、共享工作空间、需要人机确认），两段式能在执行前捕捉失效，代价是执行起点与规划起点之间可能出现状态差异，因此执行前必须校验当前状态与轨迹起点的一致性，偏差超过阈值时重新规划。

3. 错误码分类与处置

错误码值含义处置方向
SUCCESS1规划与执行成功记录耗时，进入下一步
PLANNING_FAILED−1求解器未找到解增加预算、换规划器、检查可达性
TIMED_OUT−6超时检查请求是否过于苛刻，评估求解器效率
PREEMPTED−7被新目标抢占确认抢占是否符合调度意图
START_STATE_IN_COLLISION−10起始状态处于碰撞清理场景或附加物体，检查状态来源
GOAL_IN_COLLISION−12目标状态处于碰撞校验目标位置与障碍物数据
INVALID_GROUP_NAME−15规划组名无效核对 SRDF 中的组名
INVALID_GOAL_CONSTRAINTS−16目标约束无法解释检查约束参考系与目标连杆名
CONTROL_FAILED−4执行阶段控制失败检查控制器状态与轨迹时间戳

错误码的排查顺序遵循"先校验区间（约 −10 至 −19），再过程区间（约 −1 至 −7）"的路径，因为校验类错误的修复成本最低、因果最明确。

与上一章的差异点：第 081 章解决"怎么发出去、怎么等回来"，本章解决"发什么、回来的是什么"，两章合起来覆盖动作接口的完整契约。

关键代码与解读

片段 1：构造带位姿目标的规划请求

from moveit_msgs.msg import MotionPlanRequest, Constraints
from moveit_msgs.msg import PositionConstraint, OrientationConstraint
from geometry_msgs.msg import PoseStamped, Vector3

def make_pose_goal(group: str, pose: PoseStamped, link: str):
    """把"末端到指定位姿"翻译成目标约束列表。"""
    req = MotionPlanRequest()
    req.group_name = group                    # 组名必须与 SRDF 定义一致
    # 时间预算覆盖适配器处理与求解，过小会在随机采样尚未收敛时超时
    req.allowed_planning_time = 2.0
    req.num_planning_attempts = 10            # 尝试次数与时间预算是正交资源
    req.max_velocity_scaling_factor = 0.3     # 调试阶段限速，验证后逐步提升
    req.max_acceleration_scaling_factor = 0.3
    # 位置约束：以一个小球区域表达容差，半径决定解的宽松程度
    pc = PositionConstraint()
    pc.header = pose.header                   # 约束参考系由消息头部声明
    pc.link_name = link                       # 被约束的连杆通常是工具端
    pc.target_point_offset = Vector3()        # 相对连杆原点无偏移
    # 约束区域用带位姿的几何体表达，球心即目标点
    from shape_msgs.msg import SolidPrimitive
    region = pc.constraint_region
    region.primitives.append(SolidPrimitive(
        type=SolidPrimitive.SPHERE, dimensions=[0.01]))   # 半径 1 cm 容差
    region.primitive_poses.append(pose.pose)
    region.header = pose.header
    # 方向约束：三个轴向分别给容差，比整体四元数约束更可解释
    oc = OrientationConstraint()
    oc.header = pose.header
    oc.link_name = link
    oc.orientation = pose.pose.orientation
    oc.absolute_x_axis_tolerance = 0.05       # 弧度级容差约 3 度
    oc.absolute_y_axis_tolerance = 0.05
    oc.absolute_z_axis_tolerance = 0.05
    oc.weight = 1.0                           # 权重进入约束代价，用于软约束
    goal = Constraints()
    goal.position_constraints.append(pc)
    goal.orientation_constraints.append(oc)
    # 约束消息内部各分量为"与"关系：位置与方向必须同时满足
    req.goal_constraints.append(goal)
    return req

解读：这段代码的核心是把几何意图翻译成约束区域的容差参数。设计意图有三处：（1）位置容差用球体半径显式表达，宽窄直接决定 IK 求解成功率；（2）方向容差按轴分解，便于按任务需求放宽容许度（例如近似竖直抓取允许绕竖直轴大范围旋转）；（3）整个约束放入一个 Constraints 消息，保证位置与方向同时成立。替代方案是使用关节空间目标，省去 IK 环节且求解更快，代价是目标点由逆解离线确定，灵活性下降。

片段 2：两段式流程，先规划后执行

from moveit_msgs.action import MoveGroup
from moveit_msgs.msg import PlanningOptions


def plan_only_goal(request):
    """把请求包装为只规划不执行的动作目标。"""
    goal = MoveGroup.Goal()
    goal.request = request
    # plan_only 为真时服务端在求解结束后返回，不触发执行链路
    goal.planning_options.plan_only = True
    return goal


def verify_trajectory(traj, joint_limits):
    """执行前校验：速度上限与时间戳单调性。"""
    prev_t = -1.0
    for point in traj.joint_trajectory.points:
        # 时间戳必须严格递增，否则控制器会在执行端报错
        t = point.time_from_start.sec + point.time_from_start.nanosec * 1e-9
        if t <= prev_t:
            return False
        prev_t = t
        # 逐关节检查速度是否越过模型限制（缩放后应更严格）
        for j, name in enumerate(traj.joint_trajectory.joint_names):
            if abs(point.velocities[j]) > joint_limits[name] + 1e-6:
                return False
    return True


def dispatch(result, executor):
    """两段式第二段：校验通过后单独触发执行。"""
    # 规划结果中已含错误码与轨迹，先判定规划成败
    if result.result.error_code.val != 1:
        raise RuntimeError(f"规划失败: {result.result.error_code.val}")
    if not verify_trajectory(result.result.planned_trajectory, LIMITS):
        raise RuntimeError("轨迹校验未通过")
    return executor.send(result.result.planned_trajectory)  # 走执行动作端点

解读：两段式的价值在于插入校验点。校验函数只做两类低成本检查：时间戳单调与速度越界，前者针对控制器兼容性，后者针对时间参数化后的实际输出。设计上把"规划结果判定"与"轨迹内容校验"分层，错误来源因此一眼可分：错误码异常说明规划环节，校验失败说明参数或缩放配置。执行端使用独立动作端点，便于在同一执行链路上复用到其它来源的轨迹。

片段 3：命令行发送目标用于联调

# 查看动作接口与当前可用端点
ros2 action list | grep move_action
ros2 action info /move_action

# 发送一个最小规划目标：仅指定组名，起始状态留空取当前状态
ros2 action send_goal /move_action moveit_msgs/action/MoveGroup \
  "{request: {group_name: arm, num_planning_attempts: 10, \
    allowed_planning_time: 2.0, max_velocity_scaling_factor: 0.2}, \
    planning_options: {plan_only: true}}" --feedback

# 结果中重点核对三个字段：错误码、规划时间、轨迹点数
# 错误码为负值时按"先校验类后求解类"的顺序排查（见正文错误码表）

解读：命令行方式绕过所有上层封装，直接检验服务端行为，是接口联调的第一件工具。先发 plan_only 目标确认求解链路，再放开执行能避免联调阶段误动作。反馈选项用于观察阶段状态字符串随时间的转换；结果中的轨迹路点（Waypoint）数量与规划时间可以做量级核对：典型 7 轴机械臂的轨迹路点数在几十到几百之间，规划时间落在 0.5 s 到 5 s 区间属于常见量级，明显偏离时应检查约束与场景设置。

常见坑

  • 把多个目标写成单个约束消息：需要"或"语义的多个候选目标被放进一个 Constraints，位置与方向分量全部强制满足，直接无解。修复：每个候选目标单独一个 Constraints，放入列表。
  • 缩放系数留 0 或留空：字段未设置时服务端按默认上限处理，调试阶段的限速意图落空。修复：显式写入 0.1–0.5 区间值，并在执行端核对实际关节速度。
  • 起始状态过期：请求留空起始状态时服务端取当前状态，从发出请求到实际求解之间机器人仍在运动，规划起点与执行起点不一致。修复：两段式流程中在执行前比较当前状态与轨迹首点，偏差超阈值即重新规划。
  • 把规划失败误判为执行失败：错误码为求解类负值却去检查控制器。先按错误码数值区间定位环节，再读日志细节，可以少走弯路。
  • 忽略规划时间与轨迹时长的区别：结果中的 planning_time 是求解耗时，轨迹时长由时间参数化决定，两者量纲相同但含义不同，性能统计时不可混用。

练习与思考

  1. 单次规划成功率 p = 0.6，尝试次数设为 5，计算累积成功率；若把尝试次数提高到 10，绝对提升多少个百分点？据此判断何时应该转向检查可达性。★
    提示
    P(5) = 1 − 0.4⁵ ≈ 99.0%，P(10) = 1 − 0.4¹⁰ ≈ 99.99%；p 高时增加尝试次数收益趋近饱和，瓶颈不在预算而在任务本身。
  2. 把速度缩放从 1.0 改为 0.25，加速度缩放保持 0.25，估计一条以匀速段为主的轨迹执行时长的变化，并说明加速段占比上升后结论如何修正。★★
    提示
    匀速段时长乘 4；加速段本身也受加速度缩放限制，当加速段占轨迹比例较大时，总时长由两项中的更大者决定，简单乘以 4 会低估。
  3. 设计"规划、校验、执行"两段式封装的状态机，覆盖规划失败、校验失败、执行失败三类路径，并说明每类失败后需要重新同步哪些状态。★★
    提示
    规划失败后同步场景与状态；校验失败后调整约束或缩放参数；执行失败后必须核对控制器状态与轨迹执行进度，再决定重发全轨迹或返回起点。
  4. 给定错误码 −10 与 −6 各一例，分别写出三条按成本排序的排查步骤，并说明两条路径为何在不同环节收束。★★
    提示
    −10 从场景与状态来源入手，涉及碰撞体与起始状态；−6 从请求苛刻度与求解器配置入手。前者属校验类，修复不涉及算法参数；后者属求解类，修复围绕预算与算法选择。
  5. 推导：说明为何"把路径约束写成两个约束消息"在消息层面无法表达，并给出用单个约束消息实现"某关节保持区间"的正确写法。★★★
    提示
    path_constraints 字段只容纳一个 Constraints 消息，多个条件应放入该消息的不同约束分量（关节约束列表），分量之间取"与"。

小结

  • MoveGroup 动作由"请求加选项、反馈、结果"三段构成，plan_only 决定是否触发执行链路。
  • 目标约束列表取或、约束消息内部取与，这一语义差异是构造请求时最易出错的点。
  • 时间预算与尝试次数是正交资源，按单次成功概率的累积公式估算收益。
  • 缩放系数在时间参数化阶段生效，0 表示未设置；执行端限制与控制端限制取更严格者。
  • 错误码按"校验、求解、执行"三区间分类处置，命令行联调是接口验证的基础手段。
