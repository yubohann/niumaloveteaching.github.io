第三篇 · 规划算法与求解器

第 048 章：规划性能分析 Profiling

规划慢、规划抖动、规划偶尔超时，问题出在适配器、碰撞检测、IK 还是规划器本体？本章给出分层测量方法与成本模型，把"时间去了哪里"从猜测变成实验结论。

  • 主题：性能分析 / 分项测量与瓶颈定位
  • 关键机制：成本模型、墙钟与求解时间差值、场景复杂度对照、系统级追踪
  • 预计学时：55 分钟
  • 前置章节：第 047 章

学习目标

  • 建立规划调用的成本模型：适配器、状态验证、碰撞检测、采样搜索、后处理各自的时间量级。
  • 掌握三个关键测量量：调用墙钟时间、响应中的求解时间、场景复杂度对照的结果差，并能用它们做瓶颈归因。
  • 会用系统级追踪工具获取节点级时间线，识别规划线程之外的干扰源。
  • 能按"先测量、后优化"的顺序处理性能问题，并用 Amdahl 型估算判断优化动作的上限收益。
  • 能针对碰撞检测、IK、场景规模三类热点给出具体优化动作与验证方法。

背景与动机

第 047 章的基准测试回答"哪个配置更好"，本章回答"时间为什么花掉"。性能问题在规划系统里很少是单一原因：同一条慢请求，可能是适配器在修复碰撞起点，可能是碰撞检测在网格场景上变慢，也可能是规划器采样空间本身复杂。不做分项测量就动手优化，常见的结局是把参数改乱、把结论归错因。

性能分析的价值还在于可预期性：真实的工程要求往往是"P90 小于 1 s"这类承诺，而动优化目标前，需要知道各项开销的占比与波动来源。

核心原理

1. 成本模型：一次规划调用的时间剖面

把一次规划调用拆成构成项：

T调用 = T适配器 + T规划器 + T后处理 + T传输与排队 规划器内部又可细分为采样、连接尝试、状态验证、距离查询、IK 调用

采样型规划器的核心成本近似为：

T规划器 ≈ N样本 × ( t状态验证 + t连接检测 ) + tIK × NIK 单次状态验证通常由若干对几何体的碰撞查询组成，量级在 0.1 到 1 ms；窄相检测单对查询在数十微秒量级

这组关系给出两个直接推论：第一，规划器时间对"每样本成本"与"样本数量"都敏感，场景变复杂会同时抬高两者；第二，笛卡尔路径类请求把 IK 调用数量放大，IK 插件效率成为独立热点。

2. 分项测量：三个关键量

测量量获取方式暴露的问题
调用墙钟时间调用侧计时对外响应的真实水平，含传输与排队
响应求解时间响应结构中的 planning_time 字段规划器本体的求解耗时
场景复杂度对照差同一请求在空场景与满载场景各测一轮碰撞检测在总时间中的权重

墙钟时间与求解时间的差值即适配器、后处理与传输开销的合计。差值显著（如超过总时间的三分之一）时，优先调查适配器行为：起点是否触发碰撞修复、约束投影是否反复重试。差值很小而求解时间大，则进入规划器内部找原因。

3. 场景复杂度对照：隔离碰撞检测的权重

碰撞检测的成本由场景对象数量、几何复杂度与查询结构决定。用同一请求在两类场景下各测 30 次：空场景（仅机器人自碰撞）与满载场景（工装、料箱、网格障碍全量加入）。两组成功率接近但时间差显著时，碰撞检测成为主导项；若成功率也显著下降，问题更可能出在采样空间的可通行性上。把"耗时增加"与"成功率下降"两个信号分开解读，是归因的关键分岔口。

4. 系统级追踪与干扰源

单进程测量看不见并行负载：场景更新（传感器点云插入、附加物体同步）、执行侧控制循环、日志输出都会与规划线程竞争 CPU。系统级追踪（如 Linux 上的 LTTng 结合 ROS2 的追踪工具链）给出线程级时间线，用于确认规划调用期间是否存在其它线程的密集活动。追踪工具的可用性随发行版与平台差异，使用前以对应工具文档为准；无追踪条件时，退而求其次的方法是在规划期间暂停感知更新并对比时间变化。

5. 优化动作的收益上限

用 Amdahl 型估算判断优化收益：若碰撞检测占 70% 的时间，把 IK 优化到零也只缩短 30%。优化动作应优先指向占比最大的分项。常见分项的优化方向：

  • 碰撞检测：用解析形状替代细网格、精简不必要的场景对象、配置允许碰撞矩阵（ACM）豁免确定不接触的几何对、收紧工作空间边界让检测结构更小。
  • IK：更换为解析解插件（第 054 章）或并行求解插件（第 052 章），减少迭代失败重试。
  • 适配器：保证起点合法以减少修复采样，路径约束的投影在请求构造阶段完成。
  • 传输：大轨迹与大场景的序列化成本，通过裁剪显示与减少附带数据降低。

实现思路与设计

性能问题的标准定位流程：

  1. 复现：在固定场景与请求上复现慢现象，连续 30 次记录墙钟与求解时间。
  2. 分层：计算墙钟减求解时间的差值，判断问题在适配器侧还是规划器侧。
  3. 对照：规划器侧的问题用空场景与满载场景对照，隔离碰撞检测权重。
  4. 追踪：仍有疑问时启用系统级追踪确认并行负载干扰。
  5. 优化与回归：按占比排序优化动作，改完后重复第 1 到 3 步验证，形成回归数据。

量级参考（用于判断异常）

分项健康量级异常信号
单次状态验证0.1 到 1 ms超过 5 ms 说明场景几何过重
自由空间规划总时长0.05 到 0.5 s超过 1 s 检查碰撞检测与适配器
适配器占比小于总时间三分之一更高时检查起点修复与约束投影
笛卡尔路径每点 IK0.1 到 2 ms更高时考虑解析解插件

与第 047 章的分工：基准测试产出"哪组配置更优"的结论，性能分析产出"为什么"的证据链；调优动作由 048 的证据支持，效果由 047 的口径验收。

关键代码与解读

片段 1：分项计时（墙钟减求解时间的差值法）

import time, statistics

def profile_plan(arm, goal, trials=30):
    """分别记录调用墙钟与响应求解时间，差值即适配器与后处理开销。"""
    walls, ok_walls, solves = [], [], []
    arm.set_joint_value_target(goal)
    for _ in range(trials):
        t0 = time.perf_counter()
        ok, plan, solve_time, err = arm.plan()   # 第三个返回值通常为求解耗时
        wall = time.perf_counter() - t0
        walls.append(wall)
        if ok:
            ok_walls.append(wall)
            solves.append(solve_time)
    overhead = [w - s for w, s in zip(ok_walls, solves)]
    stats = {
        "wall_median": statistics.median(walls),
        "solve_median": statistics.median(solves) if solves else None,
        "overhead_median": statistics.median(overhead) if overhead else None,
        "success": len(solves) / trials,
    }
    print(f"墙钟中位数 {stats['wall_median']:.3f} s，"
          f"求解中位数 {stats['solve_median']:.3f} s，"
          f"适配器与后处理中位数 {stats['overhead_median']:.3f} s")
    return stats

解读：差值法的前提是两侧统计同一批样本，用成功样本对齐。第三个返回值的语义是响应结构里的求解时间；接口不返回该字段时，可改由响应消息或管线日志获取。差值是有用的诊断信号：它大，说明请求在到达规划器之前或离开之后花了时间；它小，则把注意力收敛到求解器。每次测试前重设目标与起点，避免残留状态污染样本。

片段 2：场景复杂度对照实验（隔离碰撞检测权重）

def collision_weight_experiment(arm, scene_interface, goal, trials=30):
    """空场景与满载场景各测一轮：时间差暴露碰撞检测在总开销中的权重。"""
    empty_stats = profile_plan(arm, goal, trials)

    # 注入一组典型工装障碍：解析形状优先，网格其次（几何复杂度直接影响检测成本）
    obstacles = make_workcell_objects()          # 返回 CollisionObject 列表（第 022 章）
    scene_interface.apply_collision_objects(obstacles)
    loaded_stats = profile_plan(arm, goal, trials)

    # 对照结论的两个信号：耗时增量与成功率变化
    print("满载墙钟差：", loaded_stats["wall_median"] - empty_stats["wall_median"])
    print("空载成功率：", empty_stats["success"], " 满载成功率：", loaded_stats["success"])
    scene_interface.remove_collision_objects([o.id for o in obstacles])
    return empty_stats, loaded_stats

解读：实验设计的核心是"两组只差一个因素"。耗时差大而成功率基本不变，指向碰撞检测的算力成本；成功率显著下降，指向可通行性下降，此时优化方向是路径策略。障碍用解析形状不仅检测更快，也让实验更可控；真实网格模型可作为第二组对照，观察几何复杂度的增量。

ros2 run tracetools_analysis visualize_trace ~/.ros/tracing/plan_profile

# 无追踪工具时的替代对照：规划期间暂停感知更新线程，比较时间变化

解读：追踪回答单进程测量回答不了的问题：规划调用期间，场景更新、控制器反馈、日志线程是否在争抢 CPU。使用纪律是先录制带标注的短会话（一次慢请求即可），再与正常请求对照，确认差异出现在规划线程还是别处。工具名称与参数随发行版演进；条件受限时用"暂停感知对照法"获得同方向信息。

常见坑

  • 在调试构建上做性能测量：未开优化的构建使碰撞检测与采样循环慢数倍，结论失真。修复：确认使用发行配置构建，并记录版本信息。
  • 只测一次就归因：单次测量的波动足以覆盖分项差异。修复：每组分项重复 30 次，看中位数与分布。
  • 把传输与排队算进求解成本：跨进程调用包含序列化与排队延迟，直接与规划耗时相加会夸大求解器负担。修复：以响应字段与调用差值为界，分开陈述。
  • 忽略场景更新的旁路负载：传感器点云持续插入场景时，规划线程被后台更新干扰，表现为"同一请求时快时慢"。修复：用追踪确认干扰源，或把感知更新频率与规划节拍解耦。
  • 先改参数再测量：凭直觉调小采样范围、改变分辨率，问题可能只是被挪到别处，并未真正解决。修复：坚持"测量、归因、优化、回归"的顺序。

练习与思考

  1. 某请求总耗时 1.2 s，其中求解时间 0.4 s，差值 0.8 s。给出两个最可能的差值来源与各自的验证动作。★
    提示
    来源候选：起点碰撞修复的采样开销、路径约束投影或时间参数化。验证：把起点设为已知无碰撞状态再测差值；临时移除路径约束再测；对比差值变化定位。
  2. 碰撞检测占总时间 60%，IK 占 15%，优化 IK 到零的收益上限是多少？再回答"把碰撞检测成本减半"的收益上限。★
    提示
    IK 优化到零最多缩短 15%；碰撞检测减半缩短 30%。结论：按占比排序投入优化资源。
  3. 设计一个实验，区分"场景对象数量"与"单个对象几何复杂度"对碰撞检测的影响。写出两组对照与预期读数。★★
    提示
    第一组固定对象数变化几何（立方体对高密度网格）；第二组固定几何变化对象数（10 个对 50 个）。分别测单次状态验证时间，成本随对象的增长更接近线性，随几何密度的增长由窄相检测主导。
  4. 某系统在感知开启后规划 P90 从 0.6 s 升到 1.5 s，成功率不变。设计一个排查方案并给出两个最可能的机制。★★★
    提示
    机制一：场景更新线程与规划线程争抢 CPU（用追踪确认）；机制二：点云插入使碰撞结构重建频繁（观察 CPU 占用与更新频率）。方案：录制追踪会话、对比感知暂停前后的分项测量、检查更新频率与规划节拍的关系。

小结

  • 规划调用时间可分解为适配器、规划器、后处理与传输四部分，采样规划器内部再分为样本数乘单样本成本。
  • 墙钟与求解时间的差值暴露适配器与后处理开销；场景复杂度对照差隔离碰撞检测权重。
  • 耗时增大与成功率下降是两个不同信号：前者指向算力成本，后者指向可通行性。
  • 系统级追踪回答单进程测量看不到的并行干扰问题；无追踪条件时用感知暂停对照替代。
  • 优化动作按分项占比排序，用 Amdahl 型估算设定收益上限，改后用同一口径回归验证。
  • 下一章处理更硬的问题：规划直接失败时，如何用错误码与诊断工具定位失败原因。
