第 009 章：机器人状态表示：RobotState 与 RobotModel

本章解释规划系统内部的两类基础对象：RobotModel 描述机器人能怎么动，RobotState 记录此刻怎么动；规划请求的起始与目标状态都由它们支撑。

  • 主题：状态表示 / 模型对象与状态对象
  • 关键机制：运动学解析、关节值映射、状态更新（update）语义
  • 预计学时：55 分钟
  • 前置章节：第 008 章

学习目标

  • 理解 RobotModel 的构成：从描述文件解析出的链接、关节、规划组与运动学结构。
  • 理解 RobotState 的构成：关节变量数组、附加物体与派生变换缓存。
  • 掌握关节值的读写方式与更新语义，理解 update 调用为什么不可省略。
  • 会区分默认状态、随机状态、当前状态三类典型状态的用途与来源。
  • 能解释规划请求中的起始状态从哪里来，并以名称映射消除关节顺序假设。

背景与动机

规划系统的每一次计算都围绕"机器人现在什么样"与"机器人要去什么样"展开。这两个问题的答案由两类对象承载：不变的结构信息被解析成 RobotModel，随运行变化的数据被组织成 RobotState。前者来自 URDF 与 SRDF，进程内只存一份；后者每时每刻都在更新，规划、碰撞检测、显示模块各持所需的状态。

把这两类对象的关系理清，很多具体问题就有了解释：为什么设置关节角之后必须调用一次更新、为什么不同来源的关节角数组顺序可能不同、为什么修改状态时要考虑并发。本章的内容是后续所有接口章节的地基：第 010 章到第 017 章的目标与轨迹，最终都落到这两类对象的数据结构上。

核心原理

本节围绕"模型不可变、状态可变、更新触发派生计算"三条主线展开。

1. RobotModel：解析得到的结构视图

RobotModel 由描述加载器构造：读取 URDF 建立链接与关节的树结构，读取 SRDF 挂上语义信息，最终形成若干可查询的对象：链接模型（LinkModel）、关节模型（JointModel）、规划组（JointModelGroup）以及正逆运动学所需的链信息。

对象内容典型查询
RobotModel全树结构与组列表取规划组、取链接、取变量总数
JointModelGroup一个组的关节与变量集合组内变量数、变量名、末端链接
LinkModel单个链接的几何与视觉信息碰撞体、形状、网格资源
JointModel单个关节的类型与限位限位、轴向、自由度种类

模型对象的生命周期与进程一致，构造后不再改变。这一不可变特性带来两个好处：多线程可以放心共享模型；状态对象可以轻量地拷贝并各自演化。规划组对象是接口层最常引用的句柄：组内变量数决定规划维度，组内变量名是关节读写的索引表。

2. RobotState：变量数组加派生缓存

状态对象的核心是一个长度为 n 的浮点数组，n 为机器人全部变量的数量。数组的排布顺序由运动学树的遍历规则决定，属于模型的内部约定。除变量数组外，状态还携带附加物体集合（第 025 章展开）与派生量缓存。

派生量包括：各链接的全局变换矩阵、碰撞体的世界位置、雅可比矩阵等。这些量计算代价较高，系统采用惰性策略：修改关节值只把缓存标记为失效，真正的重算发生在显式更新调用时。

修改关节值 → 缓存标记失效；update() → 按需重算变换与碰撞体 连续多次修改只产生一次重算，批量赋值的正确做法是先改完再统一更新

忘记调用更新是状态编程的第一号错误：关节数组已经变了，但依赖缓存的查询（末端位姿、碰撞判定）仍返回旧值，症状是"数据改了、结果没变"。批量赋值的流程固定为"设置全部变量、调用一次更新、再查询"。

3. 三类典型状态与它们的使用场景

  • 当前状态：来自状态监视模块，与实机关节同步；规划默认从当前状态出发，执行前也用它做轨迹起点校验。
  • 默认状态：全部变量取默认值（通常为零位或有配置的初始角）；用于初始化与构造占位状态。
  • 随机状态：在限位范围内随机采样；采样规划器的内部工作状态就是随机状态序列，调试时会用它测试碰撞检测的覆盖率。

三者的选择决定规划的行为：用默认状态当起点，生成的是"从零位出发"的轨迹，与实机当前姿态无关；用当前状态作起点，轨迹才能与执行侧衔接。接口层默认使用当前状态，这正是"规划总能拿到合理起点"的原因；脚本中若显式替换起始状态，必须自行保证它来自真实数据。

4. 命名：跨系统的关节索引

关节值在不同系统间流动时，顺序假设是本可避免的错误源头：模型内部顺序、消息数组顺序、控制器配置顺序、诊断工具展示顺序各自独立。可靠的做法是以关节名称作为索引键，先建立名称到下标的位置映射，再按需要的顺序取数。

顺序假设的失败模式是静默的：数值仍在合法范围内，只是被赋给了错误的关节，规划结果看起来正常，执行时姿态与预期相差一个关节的错位。名称映射把这类错误显式化，缺失关节可以被立即发现并告警。

实现思路与设计

典型的状态编程分三步：取模型句柄、构造与操作状态、查询结果。本节给出步骤、参数与检查表。

  1. 取模型句柄：通过模型加载器获得全树对象，再取出目标规划组；完成标志是组的变量数与设计一致。
  2. 取当前状态：经接口对象或监视模块获得当前状态拷贝；完成标志是各关节值落在限位内且与实况一致。
  3. 构造测试状态：按需选择默认、随机或指定关节值；完成标志是赋值后显式更新。
  4. 查询派生量：读取末端变换、碰撞判定或雅可比；完成标志是数值与独立计算或可视化结果一致。

常用状态操作对照表

操作作用注意事项
setToDefaultValues置为默认状态默认值来自模型配置，未必是零位
setJointGroupPositions按组写入关节值数组长度必须等于组变量数
setVariablePosition按名称写单个变量名称拼写错误会被显式拒绝
update重算派生缓存写入后查询前必须调用

setToRandomPositions随机采样状态调试碰撞覆盖时使用
设计决策：为什么读取当前状态返回的是拷贝？

实机运行中，状态监视模块每秒接收几十帧新数据，读方与写方并发执行。若读方拿到内部对象的引用，写方在读取过程中更新数组，读方可能拼出"一半旧值、一半新值"的混合状态，据此规划出的轨迹必然错误。返回拷贝把数据一致性交给监视模块的锁来保证，读方获得的是某一时刻的完整快照。拷贝的代价（几百字节到几 KB 的内存复制）与一致性收益相比可以忽略。第 020 章会展开锁的细节。

关键代码与解读

本节给出三段片段：模型查询与当前状态打印、状态构造与更新语义、以及关节名称映射的 Python 实现。

片段 1：查询模型结构与打印当前状态

#include <moveit/robot_model_loader/robot_model_loader.h>
#include <moveit/robot_state/robot_state.h>

void inspectModel(const rclcpp::Node::SharedPtr& node)
{
  // 模型加载器读取描述参数并解析：参数缺失时构造即失败，问题定位在配置层
  robot_model_loader::RobotModelLoader loader(node);
  auto model = loader.getModel();

  // 取出规划组句柄：组成员与变量数是后续一切索引的依据
  const moveit::core::JointModelGroup* jmg = model->getJointModelGroup("arm");
  RCLCPP_INFO(node->get_logger(), "组 %s：变量数 %zu", jmg->getName().c_str(),
              jmg->getVariableCount());

  // 变量名按模型内部顺序输出：把它与消息里的关节顺序对照，差异即错位风险
  for (const auto& name : jmg->getVariableNames()) {
    RCLCPP_INFO(node->get_logger(), "变量：%s", name.c_str());
  }

  // 当前状态是拷贝：拿到的是一致性快照，不会被后台的连续更新干扰
  moveit::core::RobotStatePtr state = std::make_shared<moveit::core::RobotState>(model);
  state->setToDefaultValues();
  // 默认状态与实况无关，仅作占位；实机规划应以监视模块的当前状态为起点
  RCLCPP_INFO(node->get_logger(), "默认状态下末端 x=%.3f",
              state->getGlobalLinkTransform("flange").translation().x());
}

解读：这段代码展示模型与状态的第一种用法。（1）模型加载依靠描述参数，与第 006 章脚本的参数注入链路一致；参数问题在构造阶段暴露，便于与规划期问题分离。（2）组的变量名清单是一次性投入的检查工具：对照消息中的关节顺序，可以提前发现所有错位隐患。（3）默认状态用于占位与演示；代码注释明确指出它与实况的差别，避免阅读者把它当作"当前状态"使用。

片段 2：状态赋值与更新语义

void computeWithState(const moveit::core::RobotModelPtr& model,
                      const moveit::core::JointModelGroup* jmg)
{
  moveit::core::RobotState state(model);
  state.setToDefaultValues();

  // 批量赋值：先按组写入关节值，此时派生缓存尚未重算
  std::vector<double> q = {0.0, -0.5, 0.9, 0.0, 0.9, 0.0};
  state.setJointGroupPositions(jmg, q);

  // 显式更新：重算链接变换与碰撞体；省略调用则后续查询返回旧值
  state.update();

  // 更新后查询：变换矩阵的含义是"该链接坐标系到模型根坐标系"
  const Eigen::Isometry3d& tf = state.getGlobalLinkTransform("flange");
  RCLCPP_INFO(rclcpp::get_logger("state"), "法兰位置 (%.3f, %.3f, %.3f)",
              tf.translation().x(), tf.translation().y(), tf.translation().z());

  // 单个变量按名称改写：名称错误会被显式拒绝，比位置索引安全
  state.setVariablePosition("joint_2", -0.8);
  state.update();   // 第二次写入同样需要更新后才生效于查询
}

解读：更新的惰性策略在这段代码中完整呈现。（1）批量写完后一次更新，是最经济的用法：无论写入了几个关节，派生计算只发生一次。（2）第二次按名称改写演示了另一种写入口，注释点出它的安全性：名称错误直接报错，而数组下标错位不会。（3）变换查询放在更新之后，注释写明坐标系语义，避免把"全局"误解为世界坐标；模型根坐标系与世界坐标系的差异由虚拟关节衔接，第 004 章已建立这一概念。

片段 3：Python 侧的名称映射

import rclpy
from rclpy.node import Node
from sensor_msgs.msg import JointState

# 需要按模型顺序使用的关节清单（与上一节打印的变量名一致）
MODEL_ORDER = ["joint_1", "joint_2", "joint_3",
               "joint_4", "joint_5", "joint_6"]

class StateMapper(Node):
    """把消息中的关节数据映射到模型顺序，消除顺序假设。"""
    def __init__(self):
        super().__init__("state_mapper")
        self.sub = self.create_subscription(
            JointState, "/joint_states", self.on_state, 10)

    def on_state(self, msg):
        # 建立 名称到下标 的映射：消息顺序在此被彻底解耦
        index = {name: i for i, name in enumerate(msg.name)}
        ordered = []
        for name in MODEL_ORDER:
            if name not in index:
                # 缺失关节立即告警并放弃本帧：静默错位比缺数据更危险
                self.get_logger().warning(f"缺少关节 {name} 的数据，丢弃该帧")
                return
            ordered.append(msg.position[index[name]])
        # 至此 ordered 与模型变量顺序一致，可以安全送往后继计算
        self.get_logger().info(f"已映射 {len(ordered)} 个关节值")

def main():
    rclpy.init()
    node = StateMapper()
    rclpy.spin(node)
    rclpy.shutdown()

if __name__ == "__main__":
    main()

解读：名称映射是跨系统数据交换的通用纪律。（1）映射表在每帧构造，几微秒的成本换到的是顺序无关性；几十赫兹的状态流下开销可以忽略。（2）缺失关节选择"告警并丢弃整帧"；零值补齐会把错误状态伪装成合法状态，污染下游的碰撞与规划计算。（3）该工具在第 014 章执行链路与第 020 章状态监视中会被复用，本章先以最小形态建立习惯。

常见坑

  • 写完关节值忘记更新：查询结果与写入数据不符。修复：把"写入后更新"作为固定流程；批量写入只更新一次。
  • 把消息顺序当作模型顺序：关节值错位赋值，规划与执行姿态背离。修复：用名称映射重排，参照片段 3。
  • 用默认状态充当起始状态：规划轨迹从零位出发，与实机姿态脱节。修复：起始状态取当前状态快照；离线演练时才用默认或指定状态。
  • 在多个线程里共享并修改同一状态对象：数据竞争导致偶发错误结果。修复：状态对象按线程拷贝使用，共享读取经由监视模块的快照接口。
  • 忽略连续关节的角度绕行：跨越 ±π 的插值走了远路，轨迹耗时异常。修复：识别连续关节并对相邻目标做角度归一，第 015 章从插值层面展开。

练习与思考

  1. 打印 arm 组的变量名清单与数量，与 URDF 中的关节逐一对号；如果数量多出一个，说明可能的原因。★
    提示
    多出的变量通常来自把夹爪关节误纳入手臂链，或把末端固定件当作活动关节处理；对照组定义检查。
  2. 手算或程序验证：在默认状态下把 joint_2 从 0 改到 -0.5 rad，预测法兰位置的移动方向与量级，再运行片段 2 验证。★★
    提示
    joint_2 绕 Y 轴转动，末端位移近似为前臂加腕部长度乘转角；先估后测，偏差应在一个合理比例以内。
  3. 预测实验：注释片段 2 中的第一个 update 调用后运行，观察查询结果与写入数据的关系；再恢复调用对比。解释两次运行的差异根源。★★
    提示
    省略更新后查询读到默认状态的缓存；结果与写入值无关的现象正是"数据改了、结果没变"症状的复现。
  4. 设计题：为一段"从感知系统接收关节数据、校验后送入规划"的流程写状态一致性检查清单，至少覆盖顺序、缺失、越界、新鲜度四个维度。★★★
    提示
    顺序用名称映射解决；缺失逐关节告警；越界与限位表对照；新鲜度检查时间戳。清单在后续章节的状态来源讨论中会多次复用。

小结

  • RobotModel 是不可变的结构视图：链接、关节、规划组的全部查询都从它出发。
  • RobotState 是可变的变量数组加派生缓存；修改关节值后必须显式更新才生效于查询。
  • 当前、默认、随机三类状态各有用途；规划起始状态默认取当前状态快照。
  • 关节数据的跨系统交换以名称为索引，杜绝顺序假设带来的静默错位。
