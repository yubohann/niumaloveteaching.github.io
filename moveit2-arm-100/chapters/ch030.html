第二篇 · 规划场景与碰撞管理

第 030 章：使用 Octomap 表示环境

没有 CAD 图纸的障碍怎么进场景：本章讲八叉树占据地图（Octomap）的树结构与自适应内存、概率占据的对数几率更新模型、分辨率与内存的量化权衡，以及它在 MoveIt2 规划场景中的接入位置。

  • 主题：环境表示 / 概率占据地图
  • 关键机制：八叉树分层压缩、对数几率更新与钳制、分辨率与内存三次方关系
  • 预计学时：50 分钟
  • 前置章节：第 029 章

学习目标

  • 理解占据地图（Occupancy Map）解决的问题：在缺少先验模型时，用传感器采样表达任意形状的障碍。
  • 掌握八叉树（Octree）的分层结构：节点划分、叶子分辨率、均匀区域剪枝与自适应内存。
  • 会使用对数几率（Log-odds）更新公式，解释占据概率在多次观测下的收敛与钳制。
  • 能估算给定空间与分辨率下的栅格规模与内存量级，并解释八叉树实际占用远小于满栅格的原因。
  • 理解占据地图在 MoveIt2 中的接入位置：占据地图监视器的职责、参考系与分辨率参数、与显式物体的共存关系。

背景与动机

前几章的世界物体管理以"已知几何"为前提：工作台、料箱这些物体在部署阶段就有标称尺寸与位姿，可以用解析形状或网格精确描述。工作空间里还有另一类障碍没有图纸：操作员临时放置的工具、堆叠变形的物料、形状不规则的来料。它们的几何只能由传感器观测得到，观测形式是海量无序的空间点，无法直接变成少量解析形状。

八叉树占据地图（Octomap）为这类"采样几何"提供统一容器：把空间划分成小立方体（体素），每个体素记录"被占据的概率"，由传感器数据持续更新。它让规划器用同一套碰撞检测面对两种世界表示：显式物体负责已知精确几何，占据地图负责未知与动态几何。本章讲这种表示的数学与数据结构，第 031 章讲数据如何流入地图（点云管线），第 032 至 034 章讲传感器与融合。

核心原理

1. 占据表示：从"几何体"到"概率体素"

占据地图把空间离散为体素栅格，每个体素维护一个取值：被障碍占据的概率 p ∈ [0, 1]。传感器的一次观测提供局部证据：某个体素处收到回波（命中），它的占据概率上升；传感器的射线穿过某个体素而没有回波（未命中），该体素更可能是空的，概率下降。多个时刻的观测累积成对环境的稳定估计。

与显式物体相比，占据表示的取舍清晰：它能表达任意形状、无须先验模型、天然支持增量更新；代价是精度受分辨率限制、不携带语义（不知道"这是什么物体"）、内存随精度上升。工程中两种表示长期共存：料架、台面用显式物体，临时物料与人员活动区用占据地图。

2. 八叉树：分层压缩的栅格

三维满栅格的内存开销随分辨率立方增长，利用率却很低：工位里大多数区域要么全空、要么被少量表面占据。八叉树（Octree）用递归八分解决这个问题：一个立方体节点被均分为八个子节点，如此递归直到到达最小边长（叶子分辨率）。若一个节点的八个子节点状态一致（全空或全占），它们被"剪枝"合并为父节点单独表示。

结构性质带来三个工程后果。（1）自适应内存：大片均匀空域由少量高层节点覆盖，内存集中在表面附近的叶子上，实际占用远小于满栅格。（2）查询是层次下潜：定位一个点对应的体素只需沿树下行，深度为 log8(N)，单次查询代价与体素总数仅呈对数关系。（3）分辨率是唯一的精度旋钮：它同时决定最小可分辨障碍、叶子数量与更新代价，是本章最重要的设计参数。

3. 对数几率更新：概率的累加式表达

直接对概率做贝叶斯更新的乘法形式在观测序列很长时面临数值下溢。占据地图统一采用对数几率（Log-odds）表示，把乘法变为加法：

L(n) = log[ p(n) / (1 - p(n)) ]；更新：Lt = Lt-1 + Lhit/miss 典型传感器模型：命中概率 0.7，未命中概率 0.4；对应增量约 +0.85 与 -0.41

逆变换 p = 1 / (1 + e-L) 把对数几率还原为概率。两个工程细节值得记住。（1）钳制：对数几率被限制在上下限之内（常用区间对应概率 0.12 至 0.97），防止长期观测把概率压到 0 或 1 而失去对新证据的响应能力。（2）不对称更新是数帧收敛的：命中与未命中增量不对称（约 +0.85 与 -0.41），一条射线的命中需要约两次穿越观测才能抵消，这使表面估计对偶发噪声具有阻尼，同时让"去掉一个已消失的障碍"需要更多清除射线，动态场景中的迟滞正源于此。

4. 分辨率与内存的量化权衡

选分辨率之前先做算术。满栅格规模与内存的量级关系为：

体素数 N ≈ (Lx/r) × (Ly/r) × (Lz/r)；内存 M ≈ N × cleaf r 为分辨率（叶子边长），cleaf 为单个叶子节点的字节开销（占据概率加结构与指针，量级为数十字节）

以 4 m × 3 m × 2.5 m 的工位为例：分辨率 5 cm 时满栅格约 2.4 × 105 个体素，按数十字节量级折算为数 MB 到十几 MB；分辨率降到 2 cm，体素数放大约 16 倍，进入百 MB 量级；降到 1 cm 则接近 GB 量级，超出常规实时进程的预算。八叉树剪枝能显著低于满栅格数值，但剪枝效果取决于场景：表面多、噪声点多的场景叶子密布，实际内存向满栅格靠近。分辨率的选取因此是三步：先按内存公式圈定候选区间（工位场景常用 2 至 10 cm），再按"最小障碍尺寸"确定下限（分辨率应至少小于最小障碍的一半），最后用实测叶子数校准。

5. MoveIt2 中的接入位置

占据地图在 MoveIt2 中由规划场景监视器的占据地图监视器（Occupancy Map Monitor）管理：它持有八叉树实例，接收传感器插件（Sensor Plugin）写入的观测，并按配置的参考系（通常为 world）与分辨率维护地图。三个接入要点：

  • 参考系：八叉树附着在指定参考系上，传感器数据经坐标变换写入；参考系选择错误会让地图整体错位，表现为"障碍出现在机械臂另一侧"。
  • 碰撞检测：占据地图以整体身份参与机器人对世界的碰撞检查，检测器直接在树结构上做层次遍历，不需要先展开为大量显式物体。
  • 与显式物体共存：同一块几何不要同时以显式物体与占据体素两种形式进入场景（重复表示会让检测代价翻倍，也会在清除时留下矛盾）。已知几何优先走显式物体，占据地图只补未知部分。

占据地图监视器还有一条工程纪律值得单独强调：地图是"观测的累积"，只构成对真值的近似。传感器视角盲区里的障碍不会出现，已消失障碍的清除依赖射线观测。把地图当作与真值一致的完整环境使用，是感知类规划事故的常见根源。

实现思路与设计

启用占据地图的步骤与检查项：

  1. 确定参考系：选择工位中稳定的世界参考系，确认传感器到它的坐标变换链完整且稳定。
  2. 按公式选分辨率：从内存预算出发取候选区间，再按最小障碍尺度校验下限，初值常用 0.05 m。
  3. 配置传感器范围：设置最大观测距离，超出范围的数据不写入地图，控制误检与内存。
  4. 验证写入：在已知位置放标准障碍，核对地图中障碍的位置与尺寸；检查参考系与单位无差错。
  5. 检查内存与叶子数：长时间运行后观察进程内存与地图叶子规模，确认没有随运行时间单调增长。
  6. 与显式物体分工：列出哪些几何走显式物体、哪些留给占据地图，避免重复表示。

关键代码与解读

片段 1：规划场景的占据地图与传感器配置（参数组织以所用发行版的模板为准）

# 规划场景监视器的传感器配置：占据地图由这些插件写入
move_group:
  ros__parameters:
    sensors:
      - sensor_plugin: occupancy_map_monitor/PointCloudOctomapUpdater
        point_cloud_topic: /camera/depth/points   # 输入点云话题
        max_range: 3.5              # 超过该距离的点不写入地图，控制噪声与内存
        point_subsample: 4          # 每 4 个点取 1 个，直接决定更新开销
        padding_offset: 0.02        # 地图几何外附加的退让厚度
        padding_scale: 1.0          # 几何缩放，一般为 1
        filtered_cloud_topic: filtered_cloud      # 过滤后点云，供调试观察
    # 地图参考系与分辨率通常在占据地图监视器初始化处配置
    # 参数名与承载节点随发行版变化，以安装目录中的模板为准

解读：（1）配置分成两部分：sensor 列表中每项描述一路传感器的输入与写入参数；地图层面的参考系与分辨率在监视器初始化处设定，两者的组织位置在不同发行版间有差异，核对模板比记忆参数名可靠。（2）point_subsample 是最直接的性能杠杆：它按固定间隔抽稀输入点，更新代价近似线性下降，代价是细节损失；4 到 8 是常见起步值。（3）padding_offset 给写入地图的几何留出退让，与第 028 章的机器人退让距离配对使用，两侧共同构成安全裕量。

片段 2：Python 估算不同分辨率下的地图规模

def octomap_budget(length, depth, height, resolution):
    """估算占据地图的栅格规模与内存量级（最坏情况按满栅格计算）。"""
    nx = int(length / resolution)
    ny = int(depth / resolution)
    nz = int(height / resolution)
    voxels = nx * ny * nz
    # 八叉树对均匀区域剪枝，实际叶子数通常远小于满栅格；
    # 单叶子的结构与概率存储开销按数十字节量级估算
    worst_mb = voxels * 64 / (1024.0 * 1024.0)
    print(f"分辨率 {resolution * 100:4.1f} cm：满栅格 {voxels:>12,} 体素，"
          f"最坏内存量级 {worst_mb:7.1f} MB")
    return voxels

# 4 m x 3 m x 2.5 m 工位的三档分辨率对照
for r in (0.02, 0.05, 0.1):
    octomap_budget(4.0, 3.0, 2.5, r)

解读：（1）脚本刻意按满栅格计算，得到的数字是上界：真实占用取决于表面密度与剪枝效果，但上界能快速排除不可行方案（例如 1 cm 分辨率在这个工位直接超出内存预算）。（2）规模与分辨率的立方成反比，同一工位换一档分辨率就是数倍到十几倍的量级跳变，这正是"先算账再选参数"的原因；输出把三档并列，方便在设计讨论中现场对比。（3）单体素 64 字节是量级假设，用于方案比较，不作为精确计量；评审时以实测叶子数与进程内存为准。

片段 3：C++ 查询地图中某点的占据概率（octomap 库接口以所用版本为准）

// 从占据地图监视器取八叉树指针（访问接口随 MoveIt2 版本略有差异）
octomap::OcTree* tree = occupancy_monitor->getOcTreePtr();

// 在世界系中查询一个点：树按分辨率下潜，返回包含该点的最深节点
octomap::point3d query(0.45, 0.10, 0.62);
octomap::OcTreeNode* octree_node = tree->search(query);

if (octree_node != nullptr)
{
  // 节点概率由对数几率换算；数值在钳制区间内
  double prob = tree->getOccupancy(octree_node);
  RCLCPP_INFO(rclcpp::get_logger("octomap_probe"),
              "该点占据概率约 %.2f，分辨率 %.3f m",
              prob, tree->getResolution());
  // 注意：查询到节点只说明"该体素被观测覆盖"，概率中等时
  // 表示证据不足，不宜直接当作障碍或自由
}
else
{
  // 无节点意味着该区域从未被观测过：未知区域按策略处理
  RCLCPP_WARN(rclcpp::get_logger("octomap_probe"), "该点从未被观测");
}

解读：（1）search 返回包含查询点的最深节点，概率值即该体素的累积估计；用它在联调阶段核对"传感器看到的障碍有没有正确进入地图"，比只看可视化更精确。（2）概率中等（例如 0.4 到 0.6 之间）意味着证据不足：可能是掠射观测或噪声，工程策略上通常按"未占据但谨慎通过"处理，避免直接按确定障碍对待。（3）无节点代表未观测区域，与"已观测为空"有本质区别；把两者混为一谈（都按无障碍处理）会在盲区里产生撞击风险，这一区分是感知类规划的检查点之一。

常见坑

  • 分辨率贪高：为看清细小轮廓把分辨率设到厘米以下，内存与更新代价按数倍放大，长期运行后进程内存持续攀升。修复是按内存公式先定区间，再用最小障碍尺度校验下限。
  • 参考系选择错误：地图附着在会漂移的坐标系上，或与机器人基座链不一致，障碍整体错位。症状是规划绕行"空气"或撞向"空气"。修复是核对地图参考系与传感器变换链，用标准障碍做位置回归。
  • 把地图当真值使用：盲区中的障碍不在图中，把"地图里没有"当作"物理上没有"。修复是规划策略上保留盲区假设（按最坏情况评估），或用第二视角传感器覆盖。
  • 重复表示：同一几何既有显式物体又持续被传感器写入体素，检测代价上升且清除行为矛盾。修复是明确分工：已知物体加入传感器屏蔽区或从点云源剔除。
  • 忽视清除迟滞：障碍移走后地图仍长期保留其体素（清除需要足够的穿越观测），规划持续绕行已消失的障碍。修复是核对清除射线是否覆盖该区域，必要时对动态物体改用跟踪加显式物体表示。

练习与思考

  1. 计算练习：5 m × 4 m × 3 m 的空间，分辨率 5 cm 与 2 cm 的满栅格体素数各是多少？按每体素 64 字节估算内存，评论哪一档可以放进实时进程。★
    提示
    5 cm：100 × 80 × 60 = 48 万体素，约 29 MB；2 cm：250 × 200 × 150 = 750 万体素，约 458 MB。低分辨率档适合实时进程，高分辨率档需裁剪范围或稀疏存储。
  2. 更新预测：某体素连续被命中 3 次（增量 +0.85），随后连续被穿过 2 次（增量 -0.41），初值为 0。写出对数几率序列并换算首末概率，说明为什么动态障碍的清除比写入滞后的现象与增量不对称有关。★
    提示
    序列约为 0、0.85、1.70、2.55、2.14、1.73，换算概率从 0.5 升到约 0.93，再回落到约 0.85（钳制前）。命中增量约两倍于未命中增量，写入快、清除慢的不对称由此而来。
  3. 设计题：为"有人员往来的装配工位"设计占据地图参数方案：分辨率、观测范围、与显式物体的分工、动态物体处理策略，并给出验证用例。★★
    提示
    分辨率先取 0.05 m 并在窄通道复测；观测范围覆盖工位加 1 m 余量；台面料架走显式物体，人员区域交给占据地图；动态物体可配合清除观测或跟踪模块；验证用例用标准障碍核对位置与清除时间。
  4. 诊断题：地图中某个已移走的障碍长期不消失，列出至少三种原因与验证方法。★★
    提示
    候选原因：清除射线未覆盖该区域（传感器角度或遮挡）；清除观测不足未压过钳制下限（延长观测或用更强的清除模型）；该体素被其它传感器持续重新写入（核对多路传感器数据）。
  5. 分析题：从表达力、精度、语义、内存、更新代价五个维度比较"显式物体"与"占据地图"两种世界表示，给出一个混合系统里两类表示的分工准则。★★★
    提示
    分工准则：有先验模型且要求高精度或语义的几何走显式物体；无模型、动态、形状任意的几何走占据地图；同一几何只归一处维护，传感器输入与显式物体重叠处做屏蔽。

小结

  • 占据地图用概率体素表达任意形状障碍，弥补显式物体对先验模型的依赖，代价是精度受限与无语义。
