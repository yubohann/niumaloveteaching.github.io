第 084 章：日志系统与诊断方法

讲清 ROS2 日志机制（分级、命名、节流、运行时调级）与 MoveIt2 的诊断信号体系，给出"症状到观测手段"的排查路径，让日志成为可依赖的定位工具。

  • 主题：可观测性 / 日志与诊断
  • 关键机制：日志器层级与过滤、节流宏、运行时日志级别服务、诊断信号映射
  • 预计学时：50 分钟
  • 前置章节：第 083 章

学习目标

  • 理解 ROS2 日志管道：日志器（Logger）命名层级、严重级别过滤与输出处理器。
  • 掌握节流（Throttle）、一次性（Once）与跳过前若干条（Skip First）三种日志宏的语义与适用场景。
  • 会通过运行时服务调整指定节点与子日志器的级别，无需重启进程完成放大观测。
  • 能按症状选择观测手段：场景快照、动作状态、错误码、话题频率与日志文本。
  • 会设计规划节点的日志策略：正常路径低频、失败路径完整、恢复路径可追踪。

背景与动机

MoveIt2 的规划链路跨多个组件与线程，故障往往表现为静默失败：动作目标被拒绝、场景未同步、求解超时，这些事件在界面上未必可见。日志系统是成本最低的通用观测面，但默认配置下的日志既可能太少（缺关键状态），也可能太多（高频循环淹没信号）。

诊断能力的差别体现在两处：一是观测手段的覆盖，从文本日志扩展到快照、状态与频率检查；二是日志粒度可按需放大，正常运行时保持整洁，复现问题时临时提升子日志器级别。本章把这两件事的机制与方法固定下来。

上一章讨论了可视化观测，本章补齐文本与结构化观测，二者互为验证：界面显示与日志内容矛盾时，恰好指出数据通路中可疑的一段。

核心原理

1. 日志管道：从调用点到输出

一条日志从产生到落盘经过四级结构：调用点写入日志器；日志器按名称分层；过滤器按严重级别放行；处理器决定输出目标（控制台、文件或聚合话题）。级别过滤在日志器上执行，且支持继承：子日志器未设置级别时沿用父级设置。

级别语义规划系统中的典型用法
DEBUG高频细节每次迭代的代价取值、约束投影结果
INFO正常生命周期事件目标接收、规划开始、规划完成与耗时
WARN可恢复异常状态略旧、尝试次数用尽后仍继续、参数被夹取
ERROR本次任务失败规划失败、执行失败、场景应用被拒绝
FATAL组件不可用必需插件加载失败、模型初始化失败

节点默认日志器名为节点全名；组件通常再挂子日志器（例如规划、场景、轨迹执行等域），子日志器让"只放大规划域日志"成为可能，无需被迫接受全部组件的 DEBUG 洪流。

2. 节流语义与日志体量

控制循环中的日志若不节流，写入量随时间线性增长；节流（Throttle）把每个调用点限制为固定周期内最多一条。节流按调用点独立生效，不会合并不同来源的日志。一次性（Once）适合"首次发生"类事件；跳过前若干条（Skip First）适合"忽略预热阶段的常态警告"。

V ≈ min(N事件, T考察 / T节流) × L单条 500 Hz 状态回调、单条 120 字节：不节流约 3.6 MB/分钟；节流周期 1 s 后约 7 KB/分钟，量级差约三个数量级

节流代价是丢失事件密度信息：十秒内发生一次异常与十次异常在节流日志里难以区分。需要密度信息时，改用计数器汇总后再输出。

3. 运行时调级

每个节点暴露日志级别服务，接受"日志器名与级别"的列表，支持对父日志器与子日志器分别设置。调级在进程内部即时生效，用于复现问题时临时放大观测，问题定位后恢复原级别。调级状态不持久化：节点重启后回到初始级别，因此来源应以启动参数或环境变量记录，运行时服务只作为临时手段。

有效级别(日志器) = 显式设置值，若无则 = 有效级别(父日志器)，根默认 INFO 对 "moveit.planning" 调至 DEBUG 不影响兄弟域；对节点根日志器调级会波及所有未显式设置的子域

4. 诊断信号的分层映射

MoveIt2 暴露多类可观测信号，按"谁出的问题"分层：场景层看规划场景监视话题的内容与时间戳；接口层看动作列表、动作状态与参数快照；任务层看动作结果的错误码与耗时；进程层看日志文本与节点存活。排查顺序从任务层错误码入手定位环节，再下沉到场景层与接口层取证。

实现思路与设计

诊断设计分为两部分：日志策略（写什么）与排查路径（看什么）。前者决定问题发生时是否有证据，后者决定证据到手后能否快速收束。

1. 日志策略：三段式

  1. 正常路径低频：目标开始与结束各一条 INFO，包含组名、耗时、结果码；中间过程不输出或仅 DEBUG。
  2. 失败路径完整：失败日志必须包含错误码、请求摘要（组名、约束类型、时间预算）与场景版本信息，一次输出足以复现判断。
  3. 恢复路径可追踪：恢复动作（重试、取消、场景清理）以 WARN 记录原因与动作，便于统计恢复策略的实际收益。

2. 症状到观测手段的映射表

症状首选观测次选观测
规划返回失败但无细节结果错误码动作服务端日志的求解域子日志器
目标未被接受动作状态与参数快照服务端启动日志中的组名与插件加载记录
场景与预期不符场景快照话题回显场景应用服务的返回、可视化对照
执行阶段异常停止轨迹执行域日志控制器状态话题与错误码
偶发失败，概率随负载上升计划耗时分布与 CPU 占用节流日志中 WARN 的密度统计

3. 调级的操作纪律

调级遵循"最小范围、最短窗口、先记录后恢复"三条纪律：范围限定到出问题的子日志器；复现完成后立即恢复；调级前后把级别变更记录到问题复现说明中。调级的定位是临时仪器，长期配置应走启动参数，这样可以避免长期 DEBUG 运行带来的性能与存储代价。

与上一章的差异点：第 083 章的观测面是三维场景与交互面板，本章的观测面是文本与结构化信号；两者共享同一批数据源（场景、动作、状态），联调时应把两者交叉验证。

关键代码与解读

片段 1：C++ 侧的分域日志与节流

#include <rclcpp/rclcpp.hpp>

// 子日志器按域命名：调级时可以只放大本域，不波及全节点
static const rclcpp::Logger PLANNING_LOG = rclcpp::get_logger("moveit.planning");
static const rclcpp::Logger EXEC_LOG = rclcpp::get_logger("moveit.trajectory_execution");

void plan_cycle(std::size_t attempt, double cost, bool feasible) {
  // 单调时钟实例声明为静态：节流宏需要一个稳定的时间基准
  static rclcpp::Clock steady_clock(RCL_STEADY_TIME);
  // 高频迭代细节用 DEBUG：默认级别下零开销（过滤发生在写入前）
  RCLCPP_DEBUG(PLANNING_LOG, "attempt=%zu cost=%.4f", attempt, cost);
  if (!feasible) {
    // 可恢复异常用 WARN 并节流：0.5 秒窗口内最多一条，抑制刷屏
    RCLCPP_WARN_THROTTLE(PLANNING_LOG, steady_clock,
                         500, "采样未收敛（第 %zu 次尝试）", attempt);
  }
}

void finish(bool ok, double seconds, int code) {
  // 任务结束固定输出一条 INFO：耗时与结果码进入统计口径
  if (ok) {
    RCLCPP_INFO(PLANNING_LOG, "规划完成: %.3f s, code=%d", seconds, code);
  } else {
    // 失败信息一次给全：错误码、耗时与建议排查方向
    RCLCPP_ERROR(PLANNING_LOG, "规划失败: code=%d, %.3f s, 检查约束与场景", code, seconds);
  }
  // 执行域独立日志器：与控制域调级互不干扰
  RCLCPP_INFO_ONCE(EXEC_LOG, "轨迹执行链路已就绪");
}

解读：这段代码示范日志策略的三段式落地。设计要点：（1）域划分让日志可被独立放大，诊断时只提升规划域级别；（2）节流放在最靠近故障点的位置，WARN 保留"发生过"的事实而不保留全部频次；（3）结束日志携带耗时与错误码，使日志本身可用于统计，而不只是阅读。替代方案是统一使用节点根日志器，实现简单，代价是任何调级都会放大全部组件，信噪比失控。

片段 2：Python 侧运行时调级

import rclpy
from rclpy.node import Node
from rcl_interfaces.msg import LoggerLevel
from rcl_interfaces.srv import SetLoggerLevels

DEBUG_LEVEL = 10   # 严重级别的数值常量（随接口定义固定）
INFO_LEVEL = 20

class LogTuner(Node):
    def __init__(self):
        super().__init__("log_tuner")
        # 级别服务挂在目标节点下：服务名由目标节点全名决定
        self._client = self.create_client(
            SetLoggerLevels, "/move_group/set_logger_levels")

    def set_level(self, logger: str, level: int):
        if not self._client.wait_for_service(timeout_sec=1.0):
            self.get_logger().error("调级服务不可达，节点可能未运行")
            return False
        req = SetLoggerLevels.Request()
        entry = LoggerLevel()
        entry.name = logger          # 支持子日志器名，如 moveit.planning
        entry.level = level
        req.levels.append(entry)
        future = self._client.call_async(req)
        rclpy.spin_until_future_complete(self, future, timeout_sec=1.0)
        if not future.done():
            return False
        # 逐项检查返回的 success 标志，部分失败会出现在明细里
        return all(item.successful for item in future.result().results)

def reproduce_problem():
    rclpy.init()
    node = LogTuner()
    # 复现窗口内放大规划域观测，结束后恢复 INFO
    node.set_level("moveit.planning", DEBUG_LEVEL)
    run_reproduction_cycle(node)
    node.set_level("moveit.planning", INFO_LEVEL)
    node.destroy_node()
    rclpy.shutdown()

解读：运行时调级解决"默认安静、复现放大"的矛盾。关键行为：调级对象是日志器名（节点名不参与该设置），因此可以精确到域；服务调用失败时给出"节点可能未运行"的直接结论，把通信故障与业务故障分开；复现结束后恢复级别，避免长期 DEBUG 运行。注意调级不持久化，节点重启后回到启动参数设定的级别，所以长期策略仍应以启动参数配置为准。

片段 3：命令行诊断序列

# 第一步：确认节点与动作端点存在，排除"接口未加载"
ros2 node list | grep move_group
ros2 action list -t | grep move_action

# 第二步：核对场景数据新鲜度，排除"场景未同步"
ros2 topic hz /monitored_planning_scene
ros2 topic echo --once /monitored_planning_scene | head -n 20

# 第三步：放大规划域日志，复现一次失败请求
ros2 service call /move_group/set_logger_levels \
  rcl_interfaces/srv/SetLoggerLevels \
  "{levels: [{name: 'moveit.planning', level: 10}]}"

# 第四步：按错误码区间分类（校验类 / 过程类），确定修复方向
# 第五步：恢复日志级别，保持运行环境整洁
ros2 service call /move_group/set_logger_levels \
  rcl_interfaces/srv/SetLoggerLevels \
  "{levels: [{name: 'moveit.planning', level: 20}]}"

解读：这套序列体现"先存在性、再新鲜度、后细节"的排查顺序。先确认端点存在再怀疑数据，可以避免在接口未加载时深挖场景问题；场景话题的频率检查同时覆盖"未发布"与"发布停滞"两种故障；调级在复现之前执行，保证证据完整。命令行序列可以直接誊入复现手册，与程序内封装（片段 2）保持同一套接口。

常见坑

  • 高频日志不节流：控制循环每个周期打一条日志，写入量达 MB/分钟量级，故障信号被淹没且输出延迟上升。修复：对周期日志使用节流宏，密度信息用计数器汇总。
  • 严重级别随手选：把可恢复异常写成 ERROR，导致统计口径失真，运维告警对真实故障不敏感。修复：按表中的语义统一分配级别，失败才用 ERROR 及以上。
  • 调级找错对象：把节点名当成日志器名传参，返回成功但行为无变化。修复：先取回当前日志器列表（可通过参数或调级服务查询接口），核对子日志器全名再设置。
  • 调级后忘记恢复：长期 DEBUG 运行使输出量激增，DDS 聚合话题流量上升，影响发现与传输余量。修复：调级操作成对出现，复现结束立即恢复；长期需要时写入启动参数并评估代价。
  • 只看日志不核对快照：日志显示"场景已应用"，但应用的是过期差分。修复：把场景快照的时间戳与日志时间对照，必要时回显快照内容确认。

练习与思考

  1. 估算：某显示回调以 30 Hz 记录单条 150 字节的 DEBUG 日志，连续运行 10 分钟，日志总量约为多少？改为 5 秒节流后约为多少？★
    提示
    不节流约 2.7 MB；节流后约 18 KB。提示量级差异可用于说服把周期日志改到 DEBUG 级别。
  2. 为一段规划服务编写日志策略表：列出开始、迭代、失败、重试、成功五类事件各自的级别与包含字段，并说明每个字段进入统计口径的理由。★★
    提示
    开始与成功各一条 INFO 携带组名与耗时；迭代用 DEBUG 且节流；失败用 ERROR 携带错误码与请求摘要；重试用 WARN 记录触发原因。
  3. 设计实验区分"场景未发布"与"场景发布但内容陈旧"两类故障，写出使用的两条命令与判读规则。★★
    提示
    用频率工具看是否发布；用单次回显读头部时间戳并与当前时间比较，判断数据新鲜度。两者组合可区分发布缺失与更新停滞。
  4. 把节点根日志器整体调到 DEBUG 与只把规划域调到 DEBUG，两者在输出量与诊断价值上差异如何？给出一个只调子日志器即可定位问题的例子。★★
    提示
    根日志器调级波及全部域，输出量按域数量放大；子日志器调级把增益集中在怀疑域，信噪比高，适合"已锁定规划迭代"的场景。
  5. 推导日志体量与节流周期的关系式，说明在什么条件下节流会掩盖故障密度，并设计一个既能告警又能保留密度信息的输出方案。★★★
    提示
    输出条数为事件数与时间窗比值中的较小者；当事件密度超过窗口倒数时密度信息丢失。方案：节流告警加周期汇总统计（窗口内计数、最大值）。

小结

  • 日志四级结构：日志器分层、级别过滤、处理器输出；子日志器是"按域放大"的关键。
  • 节流把高频日志压到可读量级，代价是事件密度信息，需用计数器补偿。
  • 运行时调级服务支持针对子日志器即时生效，适合复现放大，不作为长期配置。
  • 诊断信号按场景层、接口层、任务层、进程层分层，排查从错误码走向证据快照。
  • 日志策略三段式：正常路径低频、失败路径完整、恢复路径可追踪。
