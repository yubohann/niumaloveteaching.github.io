第三篇 · 规划算法与求解器

第 042 章：规划请求适配器

请求到达规划器之前会被一条适配器链（request adapter chain）依次加工：解析约束坐标系、修复起点、校验工作空间，直到轨迹生成后补上时间参数。本章讲清链的顺序语义与每个适配器的职责，并给出自定义适配器的实现路径。

  • 主题：规划管线 / 请求预处理与后处理
  • 关键机制：适配器链式包裹、起点修复、时间参数化
  • 预计学时：50 分钟
  • 前置章节：第 041 章

学习目标

  • 理解规划请求适配器（Planning Request Adapter）的接口模型：adapt() 与 adaptAndPlan() 两个入口的分工。
  • 掌握链式包裹结构：请求侧修改按列表顺序执行，响应侧后处理按相反顺序执行，并解释该顺序为何重要。
  • 能说清默认适配器清单中每一项的职责与依赖关系，尤其是起点修复三件套与时间参数化。
  • 会阅读运行中 move_group 的适配器配置，判断"某一步没有被执行"是否由适配器链引起。
  • 能实现并注册一个自定义适配器，把领域规则（工作空间裁剪、轨迹后处理）接入管线。

背景与动机

第 039 章把规划管线拆成三段：适配器、规划器、后处理。很多"规划失败"的真实原因并不在规划器，而在请求本身：起点已经碰撞、目标约束的坐标系过期、工作空间未定义。适配器链就是管线为这些问题准备的自动处理层，它决定到达规划器的问题是否良定义。

同时，适配器也是规划结果的最后加工站：采样规划器产出的路径只是几何折线，必须经过时间参数化（time parameterization）补上速度、加速度与时间戳，控制器才能执行。理解这条链，是从"会调用规划"进阶到"能解释规划结果"的关键一步。

核心原理

1. 接口模型：两个入口，一个位置

每个适配器实现规划接口库（planning_interface）中的 PlanningRequestAdapter，具备两个入口：

  • adapt(scene, req)：只做请求侧的前置修改与校验，返回 false 会终止整条管线（适合硬校验）。
  • adaptAndPlan(planner_fn, scene, req, res)：包裹规划调用。planner_fn 是"链中下一环"，调用它得到响应后再加工。前置修改写在调用之前，响应后处理写在调用之后。

链的组成方式类似洋葱：列表中的第一个适配器在最外层，它先修改请求、最后处理响应；规划器位于最内层。因此，"请求修改按列表顺序执行、响应后处理按列表逆序执行"是同一事实的两种描述。

2. 默认适配器清单与职责

MoveIt2 各发行版的默认清单略有差异，职责划分稳定。以下为常见条目（名称以发行版配置为准）：

适配器阶段职责关键参数
ResolveConstraintFrames请求把约束引用的坐标系解析到规划坐标系，处理过期或延迟的 TF 帧无
FixWorkspaceBounds请求请求未定义工作空间时填入默认包围盒默认包围盒由 move_group 参数给出
FixStartStateBounds请求起点关节轻微越界时夹回限位start_state_max_bounds_error（常见默认 0.05 rad）
FixStartStateCollision请求起点处于碰撞时，在邻域采样寻找无碰撞副本start_state_max_dt、jiggle_fraction、max_sampling_attempts
FixStartStatePathConstraints请求起点违反路径约束时尝试投影到约束流形上依赖约束求解
AddTimeParameterization响应为轨迹补速度、加速度与时间戳随管线速度/加速度缩放因子
SetMaxCartesianEndEffectorSpeed响应按请求中的笛卡尔速度上限重新参数化请求字段 max_cartesian_speed
版本差异：时间参数化的挂载点

早期模板把 AddTimeParameterization 写在 request_adapters 列表中，依靠"外层包裹、后置执行"的洋葱结构在规划完成后生效；较新版本提供独立的 response_adapters 配置项，把它与请求链分离。两种挂载方式行为等价，语义更清晰的后者是迁移方向。修改配置前先确认当前发行版支持哪种写法。

3. 顺序为什么重要：依赖关系决定排列

适配器之间的顺序由数据依赖决定，随意打乱会引入隐性错误：

  • ResolveConstraintFrames 必须最先执行，后续对约束的检查与投影都依赖已解析到规划坐标系的表示。
  • FixStartStateBounds 必须早于碰撞检查：越界的关节值参与碰撞检查会得到无意义结果，先夹回限位再判定。
  • FixStartStateCollision 让起点可规划，FixStartStatePathConstraints 让起点满足路径约束，后者需要约束已解析，且应在碰撞修复之后提供兜底。
  • AddTimeParameterization 必须最后执行（即列表中最先声明的响应适配器，或请求链的逆序末端），否则其他适配器对轨迹的修改会破坏时间戳。

结论：适配器链的顺序由"数据依赖"决定，按"重要性"排布会引入隐性错误；调整顺序前先画依赖图。

4. 起点修复的语义与代价

FixStartStateCollision 属于语义最重的适配器：当起点碰撞时，它在当前状态邻域内做小幅采样（抖动幅度由 jiggle_fraction 控制），尝试找到一个无碰撞的近似起点。这带来两个后果：

  • 规划返回的轨迹起点与请求中的起点可能不同，调用方若假设"轨迹从当前状态出发"会与预期不符。
  • 采样过程消耗时间预算，起点越接近障碍，消耗越大，甚至耗尽预算导致规划器获得的时间极少。

工程上更稳妥的做法是在请求构造阶段就保证起点合法，把起点修复降级为兜底手段。第 049 章的失败诊断流程会先用状态有效性检查确认这一点。

实现思路与设计

操作适配器链的步骤：

  1. 确认现状：用 ros2 param dump /move_group 查看当前 request_adapters（及新版 response_adapters）列表，记录顺序。
  2. 小改优先：多数需求通过调参数解决（如 start_state_max_bounds_error），保持默认链不动。
  3. 增删条目：只在明确依赖关系时调整顺序；删除条目意味着把该职责转移给调用方。
  4. 自定义适配器：按接口实现类，用插件机制注册，再把插件名加入列表。
  5. 验证：构造针对性用例（如人为让起点轻微碰撞），确认适配器触发或不再触发。

与相邻章节的差异点

第 039 章关注管线的三段式结构，第 041 章关注预算参数，本章聚焦"请求进入规划器前的每一次改动"。读本章时把适配器理解为可观测的加工工序：每一道工序都应能回答"它改了什么、为什么改、代价多大"。

关键代码与解读

片段 1：适配器链配置（顺序即语义）

# 规划管线适配器配置（字段名与可用条目随发行版演进，以官方模板为准）
request_adapters: >-
  default_planner_request_adapters/ResolveConstraintFrames
  default_planner_request_adapters/FixWorkspaceBounds
  default_planner_request_adapters/FixStartStateBounds
  default_planner_request_adapters/FixStartStateCollision
  default_planner_request_adapters/FixStartStatePathConstraints
  my_adapters/WorkspaceClampAdapter
response_adapters: >-
  default_planner_request_adapters/AddTimeParameterization
# 注：早期模板把 AddTimeParameterization 写在 request_adapters 中，
# 依靠链式包裹在规划后执行；两种写法行为等价，迁移时以新写法为准。

解读：请求链按"解析坐标系 → 定义工作空间 → 修限位 → 修碰撞 → 修路径约束 → 领域规则"排列，每一环都能看到前一环修正后的请求；时间参数化单独放在响应链末尾。自定义适配器放在约束修复之后、规划器之前，保证它看到的是已经合法化的请求。若把 WorkspaceClampAdapter 放在 FixStartStateCollision 之前，起点修复阶段的采样可能越出自定义工作空间，属于典型的顺序错误。

片段 2：自定义适配器实现（C++）

#include <moveit/planning_interface/planning_request_adapter.h>

// 领域规则：把规划工作空间裁剪到工位安全盒内，防止规划器在无效空间采样
class WorkspaceClampAdapter : public planning_interface::PlanningRequestAdapter
{
public:
  std::string getDescription() const override
  {
    return "WorkspaceClampAdapter";
  }

  // 请求侧修改：在规划开始前调用，返回 false 会终止整条管线
  bool adapt(const planning_scene::PlanningSceneConstPtr& /*scene*/,
             planning_interface::MotionPlanRequest& req) const override
  {
    const double half = 0.8;  // 安全半边长（米），与工位护栏对应
    req.workspace_parameters.min_corner.x = -half;
    req.workspace_parameters.min_corner.y = -half;
    req.workspace_parameters.min_corner.z = -half;
    req.workspace_parameters.max_corner.x = half;
    req.workspace_parameters.max_corner.y = half;
    req.workspace_parameters.max_corner.z = half;
    return true;
  }

  // 包裹规划调用：planner 是链中下一环，不调用它则规划不会发生
  bool adaptAndPlan(const PlannerFn& planner,
                    const planning_scene::PlanningSceneConstPtr& scene,
                    planning_interface::MotionPlanRequest& req,
                    planning_interface::MotionPlanResponse& res,
                    std::vector<std::size_t>& /*added_state_indices*/) const override
  {
    return planner(scene, req, res);  // 本例只做前置修改，不介入响应
  }
};

解读：两个入口分工清晰，adapt() 负责"把请求改好"，adaptAndPlan() 负责"控制何时调用下一环"。关键设计点在最后一行：必须把 planner 透传调用，否则链在此处断掉。需要轨迹后处理时，在 planner() 返回后检查 res.trajectory 再修改。签名中的状态索引参数用于声明"适配器插入了哪些路径点"，供下游校验，以版本头文件为准。

片段 3：Python 侧让起点修复不必触发

import rclpy
from moveit_commander import MoveGroupCommander  # 接口以发行版为准

rclpy.init()
arm = MoveGroupCommander("arm_group")

# 显式把起点绑定到当前机器人状态：适配器链中的碰撞检查以此为准
arm.set_start_state_to_current_state()

# 若当前状态来自传感器且时间戳陈旧，应先确认 TF 与关节状态已更新，
# 再发起规划；否则 FixStartStateCollision 可能被触发并静默改写起点。
current = arm.get_current_joint_values()
print("起点关节值：", [round(v, 3) for v in current])

arm.set_joint_value_target([0.4, -0.6, 0.8, -0.5, 0.6, 0.0])
ok, plan, t, err = arm.plan()   # plan-only：把规划与执行分离，便于观察适配器行为
print(f"规划成功: {ok}，耗时 {t:.3f} s，错误码 {err.val}")

解读：配置层无法表达"起点此刻是否合法"，该判断属于调用侧职责。set_start_state_to_current_state() 把起点语义固定为"机器人当前状态"，配合状态新鲜度检查，可以让 FixStartStateCollision 保持静默。用 plan() 发起请求、把执行留给后续的 go()，是把适配器行为与执行器行为解耦的观察方式；错误码的解读方法见第 049 章。

常见坑

  • 起点被静默改写而不自知：FixStartStateCollision 找到近似无碰撞起点后，返回轨迹的首点与请求起点不同，上层若用"轨迹首点等于当前状态"做校验会误报。修复：先保证起点合法，或在验证逻辑中容忍适配器引入的偏差。
  • start_state_max_bounds_error 设置过大：超过 0.05 rad 量级的容差会让明显越界的状态被夹回，掩盖驱动层或标定的真实问题。修复：仅在已知存在少量关节零点偏差时使用稍大值，并记录原因。
  • 时间参数化缺失导致执行被拒：响应链中删除了 AddTimeParameterization 后，轨迹缺少速度与时间戳字段，控制器报轨迹无效。修复：始终保留该适配器，或在调用侧显式做时间参数化。
  • 自定义适配器未注册或未被加载：实现类编译通过但配置里写错插件名，启动时 move_group 报插件加载失败或静默忽略。修复：核对插件描述文件中的类名与配置字符串完全一致。
  • 改配置后未重启节点：适配器链在节点启动时装配，运行时改参数不影响已加载的链。修复：修改后重启 move_group，再验证。

练习与思考

  1. 适配器链顺序为 [A：夹回关节限位, B：检查并修复起点碰撞, C：解析约束坐标系]。指出错误并说明理由。★
    提示
    C 必须在最前，约束解析是一切约束相关操作的前提；A 应在 B 前，越界状态参与碰撞检查结果无意义。正确顺序为 C、A、B。
  2. 把 start_state_max_bounds_error 从 0.05 调到 0.2，预测两类任务（正常标定、存在关节零点偏差）的规划行为变化。★
    提示
    正常标定的任务：变化不大，偶尔把本应报错的越界输入放行；存在零点偏差的任务：成功率上升，但轨迹与真实状态的偏差被掩盖，应同步修正标定，避免长期依赖大容差。
  3. 设计一个自定义适配器：把规划结果中最大关节速度超过阈值的轨迹按比例拉伸时间戳，使其满足限制。写出它应挂在请求链还是响应链、以及前置修改与后处理分别放在哪个入口。★★
    提示
    属于轨迹后处理，挂响应链（或请求链的外层）。adapt() 可记录阈值来源；实际拉伸逻辑写在 adaptAndPlan() 中 planner 返回之后，遍历 res.trajectory 的路径点重写 time_from_start。
  4. 设计实验验证 FixStartStateCollision 的触发条件与代价：人为把起点设置到与桌面碰撞的姿态，测量规划成功率与耗时，对比三种处置（保留适配器、手动微调起点、禁用适配器）。★★★
    提示
    记录适配器触发时的耗时增量（墙钟时间与响应中 planning_time 的差值），以及规划返回轨迹的首点位置。禁用适配器组会稳定返回起点碰撞错误码，作为对照组。

小结

  • 适配器链在请求进入规划器前完成加工：解析坐标系、定义工作空间、修复起点、校验约束，并可在响应侧做后处理。
  • 接口有两个入口：adapt() 负责请求修改与硬校验，adaptAndPlan() 通过透传调用下一环实现链式包裹。
  • 请求修改按列表顺序、响应后处理按相反顺序执行；顺序由数据依赖决定，不可随意调整。
  • FixStartStateCollision 会静默改写起点并消耗预算，保证起点合法是调用侧的责任。
  • 时间参数化承担"让轨迹可执行"的最后一步，新版配置将其独立为响应适配器。
