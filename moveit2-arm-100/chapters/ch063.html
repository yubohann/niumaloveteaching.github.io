第四篇 · 抓取与操作任务

第 063 章：Pick Action 接口

把抓取作业封装为标准 action：Pickup 消息的目标、反馈与结果三部分语义，阶段状态的反馈设计，以及 MoveIt2 中该接口的提供方式与自建服务器的实现骨架。

  • 主题：任务接口 / Pick Action（Pickup Action）
  • 关键机制：action 三段结构 / 目标校验 / 阶段反馈与取消
  • 预计学时：50 分钟
  • 前置章节：第 062 章

学习目标

  • 理解 action 接口的三段结构（目标 Goal、反馈 Feedback、结果 Result）及其对长时任务的适配性，能对比话题与服务接口的适用边界。
  • 掌握 moveit_msgs/action/Pickup 的字段组成与语义，能把第 062 章管线的阶段参数映射到消息字段。
  • 理解 MoveIt2 中 Pick Action 的提供方式：消息定义保留在 moveit_msgs，move_group 默认能力不含 pick_place，接口由任务级服务器实现。
  • 会编写最小 Pick action 服务器：目标校验、阶段反馈、取消响应与结果错误码。
  • 能诊断三类接口级故障：目标被拒绝、执行中途取消、异常终态（abort）后的状态一致性。

背景与动机

第 062 章把抓取作业展开为阶段序列，但该序列若只存在于单个节点内部，上层任务系统就无法以标准方式请求、监控与中断它。作业级接口需要三件能力：携带完整的抓取意图（目标）、在长时执行中报告进度（反馈）、允许中途取消并区分终态原因（结果与错误码）。话题接口缺少请求与终态语义，服务接口在执行期间既无反馈也不可取消，action 接口恰好覆盖这三件能力。

moveit_msgs 中定义的 Pickup action 是抓取作业的标准化表达：抓取候选、目标物体、接近与回退参数、支撑面与可接触连杆列表都在目标字段中。需要特别说明版本差异：MoveIt1 的 move_group 内置 pick_place 能力插件直接提供该服务器，MoveIt2 的 move_group 默认不提供这一能力，常见做法是在任务层自建 action 服务器，或在 MoveIt Task Constructor 的作业描述之上封装接口层。接口字段以对应发行版的 moveit_msgs 定义与官方文档为准。

本章处于接口设计位置：上一章给出管线语义，本章把语义消息化；第 064 章的 Place Action 采用对称结构，第 065 章再逐字段剖析 Grasp 与 PlaceLocation 消息。

核心原理

1. action 三段结构与任务适配性

action 接口把一次远程过程调用拆成三个方向的数据流：客户端发送目标（Goal），服务器在两次终态之间周期发布反馈（Feedback），服务器在终态返回结果（Result）。终态包括成功（SUCCEEDED）、中止（ABORTED）与取消（CANCELED）三种，取消请求由客户端异步发起。

接口请求响应执行反馈中途取消适用对象
话题（Topic）无应答语义连续数据流无状态广播、传感器数据
服务（Service）同步应答无无短时查询与设置
动作（Action）目标与终态分离周期性反馈支持抓取、放置、导航等长时作业

抓取作业的持续时间由规划时间、直线段执行与手爪动作共同决定，通常在秒级到十秒级，且在任意时刻都可能需要人工干预或上层重规划，因此 action 是唯一合适的接口形态。

2. Pickup 目标的字段组成与语义

Pickup 目标（PickupGoal）的主要字段及其在第 062 章管线中的对应关系：

字段类型语义映射到管线
target_namestring目标物体在规划场景中的名称碰撞检查与附着操作的索引键
targetCollisionObject目标物体的碰撞几何服务器负责加入场景
possible_graspsGrasp[]抓取候选列表候选轮换顺序的来源
pre_grasp_approachGripperTranslation接近方向、期望退距与最小退距预抓取位姿与接近段参数
post_grasp_retreatGripperTranslation抓取后回退方向与距离回退段参数
support_surface_namestring支撑面名称碰撞矩阵放行与接近检查
allow_gripper_support_collisionbool是否允许手爪与支撑面接触桌面贴边抓取时的碰撞策略
attached_object_touch_linksstring[]允许与物体接触的连杆指尖与物体的碰撞放行

反馈字段承载当前推进到的阶段名称或状态字符串，结果字段携带运动规划错误码（MoveItErrorCodes）。目标字段与管线参数一一对应的设计让接口层无需理解实现细节，服务器更换实现（状态机或任务构造器）不影响客户端。字段列表随发行版演进，以 moveit_msgs/action/Pickup.action 的定义为准。

3. 提供方问题：MoveIt2 中谁来响应 /pickup

MoveIt1 的 move_group 通过 pick_place 能力插件加载抓取作业服务器，客户端向 move_group 发送 Pickup 目标即可。MoveIt2 中该能力未被移植进默认能力集，moveit_msgs 仅保留消息定义，实际部署形成两种架构：

  • 任务级 action 服务器：独立节点实现 Pickup 接口，内部复用第 062 章的阶段状态机，依赖 move_group 的规划服务与夹爪接口完成动作。接口层与实现层在同一进程内耦合度低，便于替换。
  • 基于任务构造器封装：以阶段与求解器描述作业，搜索可行解后执行，再在外部包一层 action 接口。适合候选多、需要解空间搜索的场景。

接口与实现分离是本节的核心结论：抓取任务的标准化发生在消息层，实现层保持自由，这也解释了为什么 MoveIt2 不急于内置作业管线。

4. 取消与终态语义

取消请求的响应分两个层次：接口层立即应答"接受取消"，实现层在安全点停止。安全点的定义是状态机可回退的边界：阶段之间的边界（尚未开始下一阶段）与阶段内部的轮询点（已完成的直线段不撤销，但停止继续推进）。

取消响应延迟 < 阶段轮询周期，建议轮询间隔 ≤ 0.2 s 轮询间隔决定取消的最大响应延迟；阶段内部不可中断的长动作（如整段直线执行）需拆分为可轮询的子段

异常终态的后果必须显式处理：中止（ABORTED）与取消（CANCELED）返回后，机械臂可能停在任意阶段，服务器有责任保证终态下场景与手爪状态一致（物体已附加则报告、未附加则在结果中标记），否则后续目标将在错误的世界模型上规划。

实现思路与设计

自建 Pick action 服务器的结构分四层：

  1. 接口层：ActionServer 声明目标、取消、执行三个回调；入口做目标校验（候选非空、frame 存在、物体几何有效）。
  2. 会话层：每个目标建立独立会话对象，持有所需的场景变更记录、手爪状态与阶段游标，支持回退。
  3. 阶段层：复用第 062 章的状态机，把阶段结果转换为反馈与错误码。
  4. 依赖层：move_group 规划服务客户端、夹爪接口客户端、规划场景服务客户端。

接口参数表

参数典型值作用取值依据
反馈周期0.2–1 s阶段推进的上报间隔兼顾可观测性与通信开销
阶段超时5–10 s单阶段时间上限覆盖规划与执行的最大预期时长
取消轮询间隔≤ 0.2 s取消请求的响应粒度安全响应的上限约束

与上一章的差异：第 062 章的管线是"实现"，本章的接口是"契约"；同一契约下可以替换状态机实现，也可以在前端增加调度系统做多目标排队。

关键代码与解读

片段 1：把抓取候选封装为 Pickup 目标

from moveit_msgs.action import Pickup

def make_goal(target_name, target_obj, grasps, approach_axis, d_approach, d_retreat):
    """把 062 章的抓取候选封装为 Pickup 目标：字段与管线阶段一一对应。"""
    goal = Pickup.Goal()
    goal.target_name = target_name   # 场景索引键：附着与碰撞检查都按此名查找
    goal.target = target_obj         # 碰撞几何：由服务器负责加入规划场景
    goal.possible_grasps = grasps    # 候选列表：服务器按序尝试，失败换下一个
    # 接近方向表达在 base_link 下：服务器据此把抓取位姿平移到预抓取位姿
    goal.pre_grasp_approach.direction.header.frame_id = "base_link"
    goal.pre_grasp_approach.direction.vector.x = approach_axis[0]
    goal.pre_grasp_approach.direction.vector.y = approach_axis[1]
    goal.pre_grasp_approach.direction.vector.z = approach_axis[2]
    goal.pre_grasp_approach.desired_distance = d_approach   # 期望退距 0.05 m
    goal.pre_grasp_approach.min_distance = 0.01             # 最小退距：避免贴住物体
    # 回退沿用接近方向的反向语义：方向取接近方向，语义由服务器解释
    goal.post_grasp_retreat.direction = goal.pre_grasp_approach.direction
    goal.post_grasp_retreat.desired_distance = d_retreat    # 回退距离 0.10 m
    goal.support_surface_name = "table"  # 支撑面：进入碰撞矩阵放行集合
    return goal

解读：（1）目标只描述"抓什么、从哪里接近、退多远"，不描述"怎么规划"：规划方式属于实现层，这种分工让接口在实现替换时保持稳定。（2）方向向量携带 frame_id，预抓取位姿的计算涉及坐标系变换，若缺省 frame 会产生方向歧义，这是接口层最常被忽视的字段。（3）desired_distance 与 min_distance 同时给出，服务器可在两者之间选取多档退距做尝试，增加成功率。（4）support_surface_name 让服务器知道桌面参与碰撞放行判断，贴边抓取时不至于把桌面判定为不可接近障碍。

片段 2：action 服务器骨架（校验、推进、取消）

import rclpy
from rclpy.action import ActionServer, CancelResponse, GoalResponse
from rclpy.node import Node
from rclpy.callback_groups import ReentrantCallbackGroup
from moveit_msgs.action import Pickup

class PickServer(Node):
    """Pickup 接口层：目标校验、阶段推进、取消与终态。"""
    def __init__(self):
        super().__init__("pick_action_server")
        # 执行回调内部要同步调用规划服务：独立回调组避免自我阻塞
        self.cb_group = ReentrantCallbackGroup()
        self.server = ActionServer(
            self, Pickup, "pickup", execute_callback=self.execute,
            goal_callback=self.on_goal, cancel_callback=self.on_cancel,
            callback_group=self.cb_group)
    def on_goal(self, goal_request):
        # 入口校验：候选为空直接拒绝，避免占用机械臂资源做无意义执行
        if len(goal_request.possible_grasps) == 0:
            self.get_logger().warn("拒绝目标：抓取候选为空")
            return GoalResponse.REJECT
        return GoalResponse.ACCEPT
    def on_cancel(self, goal_handle):
        # 接口层先应答接受，真正停止在阶段轮询点完成
        return CancelResponse.ACCEPT
    def execute(self, goal_handle):
        result = Pickup.Result()
        for stage in ("PRE_GRASP", "APPROACH", "CLOSE", "RETREAT", "LIFT"):
            if goal_handle.is_cancel_requested:
                self.rollback(stage)        # 取消也走回退：保证状态一致
                goal_handle.canceled()
                return result
            if not self.run_stage(stage, goal_handle.request):
                goal_handle.abort()         # 阶段失败：异常终态
                return result
            feedback = Pickup.Feedback()    # 反馈字段以实际消息定义为准
            feedback.state = stage          # 上报当前阶段，供上层监控
            goal_handle.publish_feedback(feedback)
        goal_handle.succeed()
        return result

解读：（1）三个回调的职责划分清晰：on_goal 只做校验表态，on_cancel 只应答接受，execute 承担全部推进，这让取消语义与执行逻辑互相独立。（2）取消检查放在阶段循环内的每个轮询点，取消响应延迟由该循环的粒度决定，长动作需细分为可轮询的子段。（3）回退在取消与失败两条路径上共用，回退的职责限定为"撤销未完成的场景变更与手爪动作"，已完成且一致的动作无需撤销。（4）反馈在每个阶段完成时发布，兼顾可观测性与通信开销；高频反馈应放在阶段内部按周期发布。片段中的 run_stage 与 rollback 属于实现层助手函数，分别承担单阶段执行与状态回退。

片段 3：终态错误码与结果填充

from moveit_msgs.msg import MoveItErrorCodes

def abort_with(result, goal_handle, code_value, reason):
    """终止目标并写入错误码：让客户端区分无解、碰撞与超时。"""
    result.error_code.val = code_value   # 结果字段承载规划错误码
    goal_handle.abort()                  # abort 与 succeed/canceled 互斥
    print(f"目标中止：{reason}（错误码 {code_value}）")
    return result

# 规划无解时返回 PLANNING_FAILED，碰撞问题时返回相应碰撞错误码
# 具体常量以 moveit_msgs/MoveItErrorCodes 定义为准

解读：（1）错误码把"失败"细分为可操作的原因：客户端据 PLANNING_FAILED 重发候选，据碰撞类错误码调整场景或退距，据超时缩短路径段长度。（2）终态调用互斥：abort、succeed、canceled 只能调用一次，框架对重复调用会报错，因此所有终止路径应集中在统一的辅助函数中，避免分支遗漏。（3）错误码常量随版本演进，使用时从 moveit_msgs 的定义导入而不硬编码数值。

常见坑

  • 按 MoveIt1 经验期待 move_group 内置 pickup 服务：客户端发送目标后长时间没有服务器响应。修复：先确认 action 服务器命名空间与可用性（列出 action 列表），再选择自建服务器或任务构造器封装。
  • 反馈只发一次或从不发送：上层看门狗把长阶段判定为卡死并强制取消。修复：阶段完成时发送，并叠加周期发送；反馈周期取 0.2–1 s。
  • 取消路径缺少回退：取消后物体仍处于已附加状态，下一个目标在污染的规划场景上规划。修复：把回退动作与失败路径共用，覆盖取消分支。
  • 目标校验缺失：候选为空、目标物体几何为空、frame 不存在等非法目标进入执行，占用机械臂并在中途以模糊错误失败。修复：入口统一校验并返回 REJECT，同时记录被拒绝原因。
  • 并发目标未管理：两条目标交错执行，直线段与手爪动作互相插入。修复：单臂作业采用资源独占策略，第二个目标返回拒绝或排队，并在反馈中体现排队状态。

练习与思考

  1. 从"执行时长、进度可见性、中途取消、错误原因区分"四个角度，说明抓取作业选择 action 接口的理由，并给出服务接口在各角度上的不足。★
    提示
    服务接口在等待应答期间既不返回进度也不接受取消，失败只能以单一异常上报；action 的三段结构分别解决进度的可观测与终止的可控。
  2. 把第 062 章参数表中的七个参数映射到 PickupGoal 字段，指出无法直接映射的参数与替代表达方式。★★
    提示
    接近退距与回退距离映射到两个 GripperTranslation 的 desired_distance；速度与步长属于执行层参数，不进目标字段，可由服务器参数或客户端配置承载；附着时序对应 attached_object_touch_links 与实现约定。
  3. 分析取消发生在三个不同位置的行为差异：阶段边界、直线段执行中、手爪闭合中。为每个位置说明安全停止方式与需要回退的内容。★★
    提示
    阶段边界可直接停止并保持状态；直线段执行中应先减速停在当前路点，再决定回退到起点或原地保持；手爪闭合中不可中途反开，应等闭合完成再决定张开或保留。
  4. 设计实验：把反馈周期从 1 s 调整到 10 Hz，测量反馈带宽占用、上层日志量与取消响应延迟的变化，给出适合本系统的取值与理由。★★★
    提示
    反馈消息较小，带宽通常不成瓶颈，主要代价在上层日志与回调压力；取消响应延迟主要由服务器的轮询间隔决定，与反馈频率只有间接关系。

小结

  • action 接口以目标、反馈、结果三段结构覆盖抓取作业在时长、进度与终止三方面的需求，终态分成功、中止、取消三类。
  • PickupGoal 的字段与管线阶段一一对应：候选列表、接近与回退参数、支撑面与可接触连杆列表各自承担明确语义。
  • MoveIt2 默认不提供 move_group 内置的 pickup 服务器，接口由任务层实现，消息定义保留在 moveit_msgs。
  • 取消响应延迟由阶段轮询粒度决定，终态必须保证场景与手爪状态一致，回退逻辑在失败与取消两条路径上共用。
