第二篇 · 规划场景与碰撞管理

第 019 章：规划场景组成与生命周期

第二篇开篇：规划场景是规划系统的世界模型，本章讲清它的组成字段、差分更新语义与从初始化到销毁的完整生命周期。

  • 主题：规划场景 / 世界模型与差分更新
  • 关键机制：PlanningScene 组成、is_diff 语义、服务与话题两条更新路径
  • 预计学时：60 分钟
  • 前置章节：第 018 章

学习目标

  • 说出规划场景的组成部分：机器人状态、世界碰撞物体、变换关系与碰撞豁免矩阵。
  • 理解完整场景与差分场景的语义差别，掌握 is_diff 标志的行为规则。
  • 掌握两条更新路径：服务调用与监视话题，能按任务形态选择。
  • 能描述场景从创建、初始化、运行期更新到销毁的生命周期，并处理其无持久化特性。
  • 会设计幂等的场景初始化流程，保证任务重复运行时不残留、不冲突。

背景与动机

前一篇的规划都发生在空旷世界里：机械臂只与自身和少数静态物体打交道。真实操作场景需要碰撞管理：桌面、料框、围栏、工件都必须进入规划系统的世界模型，规划器才能绕开它们。这个世界的载体就是规划场景（Planning Scene）。

场景问题的隐蔽性在于它的"半状态"属性：场景不写进任何持久文件，进程重启即重置；更新以差分消息流动，写错标志位可能悄悄清空或覆盖内容。本章先建立场景的静态结构与动态生命周期的完整认识，第 020 章再展开维护场景的监视器机制，第 022 至 026 章逐一处理物体的增删改与附着。

核心原理

本节解释场景的组成字段、两类消息语义、两条更新通道与生命周期模型。

1. 场景组成：状态、世界、规则、变换

组成部分内容来源
机器人状态全部关节变量、附加物体状态监视与前序任务
世界碰撞物体场景中的几何体集合任务初始化、感知系统
变换关系世界坐标系相关的静态变换描述文件与坐标广播
碰撞豁免矩阵被禁用检测的连杆对SRDF 与运行期增补

四项内容对应四类规划输入：机器人自身姿态、外部障碍、坐标基准、检测规则。规划器把这些合并后回答一个问题：某状态下哪些几何体互相干涉。场景中任何一项缺失或过期，碰撞判定就会失真：状态过期会漏检自身，物体缺失会漏检障碍，变换错位会让物体出现在错误位置，豁免错误会放过真实干涉。第 027 与 028 章将展开碰撞检测与距离查询的计算机制。

2. 消息语义：完整与差分

场景消息有一个关键标志位 is_diff。差分语义下，消息携带的是"变更指令"：物体列表中的每一项按操作类型（新增、删除、移动）叠加到既有场景；完整语义下，消息声明"这就是全部内容"，接收方以它替换场景的对应部分。

is_diff = true：场景 ← 场景 ⊕ 消息；is_diff = false：场景 ← 消息描述的完整内容 差分的接收方是"叠加"逻辑：变更顺序影响结果，多条差分按到达顺序生效

差分与完整的选择有明确的适用边界：流式更新必须用差分，否则每条消息都会清空上一次的内容；一次性快照可以用完整语义，但要明确覆盖范围。调试期最危险的组合是"想追加物体却发了完整消息"，表现为"每加一个物体，前一个就消失"。第 022 至 023 章会给出两类语义的具体操作序列。

3. 两条更新通道

通道行为适用场景
apply_planning_scene 服务同步调用，返回成功与否任务初始化、需要回执的变更
规划场景话题异步发布，无回执流式更新、可视化插件的界面操作
监视场景话题由场景维护方向外发布观察场景变化，不作为写入通道

服务通道的核心优势是回执：任务流程可以在"写入成功"之后再进入规划。话题通道的核心优势是解耦：发布者不需要知道谁在接收，可视化插件的物体拖动、感知管线的点云更新都通过它完成。任务关键路径上的场景变更选择服务通道；辅助与流式数据选择话题通道。混用时注意异步消息的到达顺序不保证，任务流程不应依赖"发布后立即生效"。

4. 生命周期：无持久化的世界

规划场景的生命周期与运行它的进程绑定，呈现四个阶段：

  1. 创建：随规划系统启动构建空场景，机器人状态来自描述与初始状态，世界为空。
  2. 初始化：写入任务所需的静态物体（工作台、料框等），建立碰撞豁免的补充条目。
  3. 运行期：物体的增删改、附加与分离、感知数据融合持续发生。
  4. 销毁：进程结束，场景消失；下一次启动从空场景重新初始化。

无持久化特性推出一条工程纪律：任务脚本必须假定"启动时世界是空的"，把初始化作为任务流程的第一步。依赖上一次运行残留物体的脚本在新进程里必然失败；反之，长期运行的进程里，历史任务遗留的物体也会干扰新任务，初始化流程需要能清理自己关心的命名空间。

实现思路与设计

场景管理按"清场、布置、校验、就绪"四步建立幂等初始化流程。

  1. 清场：按命名前缀删除本任务可能残留的物体，避免与历史状态冲突。
  2. 布置：以差分消息批量写入静态物体；同一消息内的多项按顺序生效。
  3. 校验：查询场景物体清单，核对数量与关键物体的位姿。
  4. 就绪门：校验通过才允许任务进入规划阶段，避免带着不完整场景开工。

场景消息关键字段表

字段内容填写要点
is_diff差分标志流式更新置真，语义理解到位再写
world.collision_objects世界物体列表每个物体的 id、几何、位姿、操作类型
robot_state机器人状态任务流程通常不覆盖，由监视器维护
allowed_collision_matrix碰撞豁免增补按需增补，不替代 SRDF 基础豁免
scene name / 时间戳场景标识多场景实例时用于区分，单机可留空
设计决策：为什么初始化流程选择"清场"、放弃"假定干净"？

长期运行的进程里，场景是多次任务叠加的结果：上一次任务删除物体失败、感知系统持续写入、人工通过界面拖动过物体，都会留下记录。清场步骤把"环境的过去"从任务逻辑中隔离出去，让每次任务从确定状态开始。清场按命名前缀执行，只清理本任务的命名空间，不影响共享物体。这是第 022 章物体命名规范的前置理由。

关键代码与解读

本节给出三段片段：差分场景的构造与服务写入、场景清单校验、场景对象的差分计算（C++ 视角）。

片段 1：构造差分场景并经服务写入

from moveit_msgs.msg import PlanningScene, CollisionObject
from moveit_msgs.srv import ApplyPlanningScene
from shape_msgs.msg import SolidPrimitive
from geometry_msgs.msg import Pose

def build_table_object():
    """构造工作台物体：几何、位姿、操作类型三要素齐全。"""
    obj = CollisionObject()
    obj.id = "table_01"                  # 命名带任务前缀：清场按前缀匹配
    obj.header.frame_id = "world"        # 位姿参考系：与虚拟关节父系一致
    box = SolidPrimitive()
    box.type = SolidPrimitive.BOX
    box.dimensions = [0.9, 0.6, 0.04]    # 长宽高，单位米
    obj.primitives.append(box)
    pose = Pose()
    pose.position.z = -0.02              # 台面中心的高度：厚度一半
    pose.orientation.w = 1.0             # 单位四元数：无旋转
    obj.primitive_poses.append(pose)
    obj.operation = CollisionObject.ADD
    return obj

def apply_diff(node, client, objects):
    """批量写入：一条差分消息承载全部变更，顺序生效。"""
    scene = PlanningScene()
    scene.is_diff = True                 # 差分语义：在现有场景上增量追加
    scene.world.collision_objects = objects
    request = ApplyPlanningScene.Request()
    request.scene = scene
    future = client.call_async(request)
    # 服务有回执：success 为真表示场景已接受全部变更
    return future

解读：这段代码把差分写入的四要素落实。（1）物体 id 带前缀，为清场与命名空间隔离做准备；参考系与虚拟关节一致，位姿才有确定语义。（2）几何尺寸与位姿按消息约定填写（全尺寸、单位四元数），第 024 章会系统展开 CollisionObject 的字段细节。（3）is_diff 与回执是这段代码的两个安全点：差分保证追加语义，服务回执让任务流程可以等待写入完成再规划。

片段 2：场景清单校验

import rclpy
from moveit_msgs.srv import GetPlanningScene
from moveit_msgs.msg import PlanningSceneComponents

def list_scene_objects(node, client, timeout_sec=2.0):
    """查询场景中的物体清单：初始化完成后核对内容。"""
    request = GetPlanningScene.Request()
    # 只请求世界物体部分：数据量最小，响应最快
    request.components.components = PlanningSceneComponents.WORLD_OBJECT_NAMES
    future = client.call_async(request)
    # 有限等待：服务端未就绪时给出确定结论，避免挂起
    rclpy.spin_until_future_complete(node, future, timeout_sec=timeout_sec)
    if not future.done():
        node.get_logger().warning("场景查询超时：确认服务端就绪")
        return None
    names = [obj.id for obj in future.result().scene.world.collision_objects]
    node.get_logger().info(f"场景物体：{names}")
    # 校验逻辑在上层：清单与预期不符则拒绝进入规划阶段
    return names

# 就绪门：数量与关键物体名都对上，才放行后续任务
names = list_scene_objects(node, scene_client)
if names is None or "table_01" not in names:
    raise RuntimeError("场景初始化未完成")

解读：校验步骤把"写过了"与"写对了"区分开。（1）查询只请求物体名清单，避免整场景消息的体积开销；需要位姿核对时再按物体名请求更细的部件。（2）等待带超时，服务端缺席时任务得到明确的失败信号；就绪门把校验结果与后续流程绑定，校验未通过就不进入规划。（3）该校验与片段 1 的写入构成"写后读"的确认模式，在第 018 章验收流程中可作为场景层的附加检查项。

片段 3：场景对象的差分视角（C++）

// 进程内的场景对象：模型加世界，与消息表示互转
planning_scene::PlanningScene scene(robot_model);

// 直接向世界添加几何体：几何指针与变换由世界容器持有
shapes::ShapeConstPtr box = std::make_shared<shapes::Box>(0.9, 0.6, 0.04);
Eigen::Isometry3d pose = Eigen::Isometry3d::Identity();
pose.translation().z() = -0.02f;
scene.getWorldNonConst()->addToObject("table_01", box, pose);

// 差分计算：相对"上次已发送状态"生成变更消息
// 监视器与客户端之间传递的正是这类差分（具体接口签名以对应版本为准）
moveit_msgs::msg::PlanningScene diff_msg;
scene.getPlanningSceneDiffMsg(diff_msg);
// 此消息经话题或服务送达客户端后，两边的场景重新一致

解读：C++ 视角揭示消息背后的对象模型。（1）场景对象由机器人模型构建，世界容器持有几何与位姿；消息只是这个对象在通信边界上的两种表示之一。（2）差分计算以"上次同步点"为基准，这解释了为什么差分消息依赖双方的状态一致性：任一方的场景偏离基准，差分传递的内容就会出现偏差。（3）该机制是第 020 章监视器"发布变更、订阅合成"循环的基础，本片段先建立对象与消息的对应关系。

常见坑

  • 非差分消息用于流式更新：每写一个物体就清掉之前的物体，场景"只剩最后一个"。修复：流式路径统一置 is_diff 为真，并理解覆盖范围。
  • 参考系与虚拟关节不一致：物体在界面上出现在错误位置，规划绕开"空气墙"。修复：核对物体 frame_id 与虚拟关节父系的一致性，位姿在正确参考系下解释。
  • 重复写入同 id 的语义误解：期望"新增第二个物体"，实际发生替换。修复：id 唯一性纳入物体命名规范，识别替换语义。
  • 依赖场景持久化：重启后任务因缺少物体失败。修复：初始化作为每次任务的第一步，脚本不假设历史状态。
  • 异步通道当成同步使用：发布后立刻规划，物体尚未生效。修复：关键路径用带回执的服务；话题路径在规划前做清单校验。

练习与思考

  1. 列出规划场景四项组成并写出每一项的来源与失效症状，形成场景体检表的初版。★
    提示
    状态来自监视器、物体来自任务与感知、变换来自描述、豁免来自 SRDF；每项的失效症状与规划失败模式对应。
  2. 在末段路径正下方写入一个 0.1 m 立方体障碍，规划同一位姿目标，观察轨迹绕行；删除物体后再规划，对照两次结果。★★
    提示
    障碍进入场景后，路径需要绕开或抬高；删除后路径恢复。两次对比是"场景参与规划"的最直接证据。
  3. 预测实验：把片段 1 的 is_diff 改为 false，连续写入两个物体，预测界面上物体的数量变化，并解释消息语义。★★
    提示
    第二次写入会覆盖第一次描述的范围，前一个物体消失；这正是差分标志必须理解后使用的原因。
  4. 设计题：为一条"上料、作业、下料"的任务流程设计场景初始化与清理方案：清场范围、物体清单、校验点与失败回退。★★★
    提示
    按任务前缀划分命名空间；校验点放在每类物体写入之后；回退策略包含重试写入与终止任务两级。

小结

  • 规划场景由机器人状态、世界物体、变换关系与碰撞豁免四部分组成，缺一或过期都会失真。
  • 差分与完整消息是两种语义；流式更新用差分，调试时先想清楚覆盖范围再写 is_diff。
  • 更新走两条通道：服务带回执适合关键路径，话题解耦适合流式与可视化。
  • 场景无持久化，初始化必须是每次任务的第一步；清场加校验构成幂等初始化的核心。
