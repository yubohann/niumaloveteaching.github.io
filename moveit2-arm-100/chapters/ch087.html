第 087 章：C++ 接口源码导读

建立 C++ 侧的层次地图：从核心库到规划管线再到接口封装与节点服务端，沿"动作路径"与"进程内路径"两条调用链读源码，补齐插件注册与编译依赖两块拼图。

  • 主题：接口实现 / 源码阅读方法
  • 关键机制：接口封装与动作路径、进程内规划管线、插件加载（pluginlib）、编译依赖组织
  • 预计学时：60 分钟
  • 前置章节：第 086 章

学习目标

  • 建立 C++ 侧四层结构地图：核心库、规划层、规划接口层、节点服务端，理解依赖方向。
  • 掌握接口封装类的本质：动作客户端加请求构造器，理解 plan 与 move 的调用链差异。
  • 会按场景选择直接使用规划管线，理解其与动作服务路径在状态来源上的区别。
  • 理解规划器、请求适配器与运动学求解器的插件注册机制与加载失败的表征。
  • 能根据故障症状确定需要阅读的代码层次，并组织编译与链接依赖。

背景与动机

C++ 接口是 MoveIt2 的原生形态：核心算法、规划管线与节点服务端都以 C++ 实现，Python 与命令行工具在其之上包装。阅读 C++ 源码的三个直接收益：接口行为有了权威解释；性能问题能定位到具体函数；扩展点（自定义规划器、适配器）有章可循。

与 Python 侧相比，C++ 侧多出两类需要掌握的内容：一是编译与链接的组织方式，决定"依赖哪个包、链接哪个库"；二是插件机制，规划算法与适配器都以动态插件形式装载，理解这条链路才能解释"配置里写了算法名却加载失败"这类问题。

上一章以 Python 视角走通了内部链路，本章用 C++ 视角检查同一条链路的两端实现，并把动作路径与进程内路径摆在一起对照。

核心原理

1. 四层结构地图

C++ 侧按依赖方向分为四层，上层可依赖下层，反向依赖不存在。读代码时先确定目标符号属于哪层，再看该层对外暴露的接口。

层包含内容特征
核心库机器人模型、状态、场景、碰撞、运动学抽象、轨迹处理不含节点与传输依赖，可独立测试
规划层规划场景监视、规划管线、规划器管理、请求适配器依赖核心库，持有插件加载逻辑
规划接口层接口封装类、场景接口类面向调用者的便捷封装，内部走动作客户端或直接调用
节点服务端move_group 节点及其动作与服务处理进程入口，把动作目标翻译为管线调用

2. 两条调用链

动作路径从接口封装类发出，请求经传输到达 move_group，再由服务端调用规划管线；进程内路径绕过节点，在调用方进程直接调用规划管线。两条路径共享规划管线这一内核，差别在状态来源与部署形态。

动作路径：封装类 → 动作客户端 → move_group → PlanningPipeline::generatePlan → 适配器链 → PlannerManager::getPlanningContext → PlanningContext::solve
进程内路径：调用方进程 → PlanningPipeline::generatePlan → 适配器链 → PlannerManager::getPlanningContext → PlanningContext::solve 适配器链负责工件化处理：起始状态修正、时间参数化、碰撞检查等；规划器只负责在图或约束空间中搜索

进程内路径的调用方必须自行提供规划场景对象；动作路径的场景由服务端维护。两条路径混用时，"场景谁权威"必须明确，否则规划结果与执行环境不一致。

3. 接口封装类的本质

接口封装类（MoveGroupInterface）在构造时解析参数获得组名与端点名，创建动作客户端与场景订阅；对外方法分为三类：目标构造（设置目标、约束、缩放）、查询（当前状态、命名状态）、执行（规划、移动、执行给定轨迹）。plan 与 move 的差别仅在是否顺带触发执行，请求构造部分完全共用。

4. 插件机制：三处可替换点

插件点接口基类注册方式
规划器管理规划接口层的规划器管理器基类插件描述文件加导出宏
请求适配器适配器基类同上，按参数顺序串成链
运动学求解器运动学基类同上，按组名在配置中指定

插件在运行时由类加载器按名称检索并实例化；实例化失败通常只留下日志而不会中止进程，表现为"算法名写了却没有对应行为"。排查插件问题的第一步是核对描述文件是否被安装到插件索引路径，第二步是核对配置中的插件名与描述文件声明是否逐字一致。

5. 编译依赖组织

依赖按层引入：使用接口封装类需要链接核心库、规划层与规划接口层；只做算法研究可仅依赖核心库与规划层。构建系统通过包描述声明依赖，编译单元按头文件路径引用。依赖最小化的收益是编译时间与部署体积下降，也能避免拖动不必要的运行期资源。

实现思路与设计

阅读 C++ 源码按"症状定位层、符号定位文件、调用点定位链"三步推进。每一步都缩小范围：先确定读哪层，再确定读哪个类，最后顺调用链读完整流程。

1. 症状到层次的对照表

症状需要阅读的层次查找起点
规划请求参数未生效规划接口层请求构造方法中每个字段的赋值位置
算法名无效或行为不符规划层规划器管理器的插件加载与实例化逻辑
起始状态与预期不符规划层与核心库场景监视器更新路径与状态获取函数
动作目标被拒绝节点服务端动作目标的校验分支
轨迹执行与规划不一致规划接口层与执行端执行方法的轨迹传递与控制器选择

2. 阅读路线

  1. 读公开头文件：接口方法清单与参数语义在头文件中即可获得，先建立调用面。
  2. 读构造体：构造过程创建了哪些客户端、订阅者与内部对象，决定运行期行为。
  3. 顺 plan 调用链：从请求构造到动作发送或管线调用，记录每层的数据变形。
  4. 读适配器链：管线在调用规划器前后做哪些修正，解释"配置生效位置"。
  5. 读插件加载：类加载器如何按参数检索插件，理解自定义算法的接入点。

3. 两种扩展的工程决策

验证新算法时，直接使用规划管线写成独立可执行程序，迭代速度最快；集成到既有系统时，把算法注册为插件，通过配置挂入管线。决策依据是"是否需要与系统内其它组件共享场景与状态"。需要共享时走插件与节点路径，纯验证时走独立程序路径。

与上一章的差异点：第 086 章关注对象装载与参数映射，本章关注实现层次与插件边界；两章结合后，同一条链路在两种语言视角下都有落点。

关键代码与解读

片段 1：接口封装类的标准用法

#include <rclcpp/rclcpp.hpp>
#include <moveit/move_group_interface/move_group_interface.h>

int main(int argc, char** argv) {
  rclcpp::init(argc, argv);
  // 接口封装类需要节点上下文：通常使用独立节点承载，便于线程与日志隔离
  auto node = rclcpp::Node::make_shared("move_group_demo");

  static const std::string GROUP = "arm";   // 组名来自 SRDF，全链路共用同一名称
  moveit::planning_interface::MoveGroupInterface group(node, GROUP);

  // 缩放设置在请求构造期写入：未设置时按默认上限处理（第 082 章）
  group.setMaxVelocityScalingFactor(0.3);
  group.setMaxAccelerationScalingFactor(0.3);
  // 命名状态目标：名称经机器人状态展开为关节值
  group.setNamedTarget("ready");

  // plan 只求解不解算执行；返回码是接口层的错误码类型，可直接判等
  moveit::planning_interface::MoveGroupInterface::Plan plan;
  const bool planned =
      (group.plan(plan) == moveit::core::MoveItErrorCode::SUCCESS);
  if (!planned) {
    RCLCPP_ERROR(node->get_logger(), "规划失败：检查目标与场景");
    rclcpp::shutdown();
    return 1;
  }

  // execute 在 plan 成功之后触发：请求构造逻辑与 plan 共用
  if (group.execute(plan) != moveit::core::MoveItErrorCode::SUCCESS) {
    RCLCPP_ERROR(node->get_logger(), "执行失败：检查控制器链路");
    rclcpp::shutdown();
    return 1;
  }
  rclcpp::shutdown();
  return 0;
}

解读：这段代码展示了封装类的调用面。设计要点：（1）组名是贯穿接口、SRDF 与配置的连接键；（2）缩放与目标设置在内部累积为请求字段，plan 时一次发出；（3）plan 与 execute 分离，便于插入校验（第 082 章两段式）；（4）错误码用类型化常量判等，可读性与编译期检查都优于裸整数。阻塞语义提醒：plan 与 execute 内部会等待动作结果，不得在单线程执行器的回调中调用，否则形成自锁（第 081 章）。

片段 2：直接使用规划管线（进程内路径）

#include <moveit/planning_pipeline/planning_pipeline.h>
#include <moveit/planning_interface/planning_interface.h>
#include <moveit_msgs/msg/joint_constraint.hpp>

void plan_in_process(const rclcpp::Node::SharedPtr& node,
                     const moveit::core::RobotModelConstPtr& model,
                     const planning_scene::PlanningSceneConstPtr& scene) {
  // 管线以插件名构造：名称为 pipeline 标识，决定适配器链与规划器集合
  auto pipeline = std::make_shared<planning_pipeline::PlanningPipeline>(
      model, node, "ompl");
  // 请求最小构成：组名、起始状态、目标约束、时间预算
  planning_interface::MotionPlanRequest request;
  request.group_name = "arm";
  request.allowed_planning_time = 2.0;
  request.num_planning_attempts = 10;
  // 起始状态显式取自调用方持有的场景，进程内路径没有服务端兜底
  moveit::core::RobotState start(scene->getCurrentState());
  start.update();
  moveit::core::robotStateToRobotStateMsg(start, request.start_state);
  // 目标约束与动作路径完全一致：约束消息是两路径的公共语言
  // 关节约束示例：锁定肘关节到给定角度，规避 IK 环节便于验证求解器
  moveit_msgs::msg::JointConstraint jc;
  jc.joint_name = "elbow_joint";
  jc.position = 0.5;
  jc.tolerance_above = 0.01;
  jc.tolerance_below = 0.01;
  jc.weight = 1.0;
  moveit_msgs::msg::Constraints goal;
  goal.joint_constraints.push_back(jc);
  request.goal_constraints.push_back(goal);

  planning_interface::MotionPlanResponse response;
  pipeline->generatePlan(scene, request, response);
  if (response.error_code.val != moveit::core::MoveItErrorCode::SUCCESS) {
    RCLCPP_ERROR(node->get_logger(), "管线求解失败: %d", response.error_code.val);
    return;
  }
  RCLCPP_INFO(node->get_logger(), "求解耗时 %.3f s，轨迹点数 %zu",
              response.planning_time, response.trajectory->getWayPointCount());
}

解读：进程内路径把管线当作库函数使用。关键差异：（1）场景对象由调用方提供，起始状态必须显式设置，服务端不会帮忙刷新；（2）请求与动作路径使用同一套约束消息，理解一次即可迁移；（3）响应携带耗时与轨迹，可直接用于离线对比实验。这条路径适合算法验证：固定场景与状态后，规划结果只随算法与参数变化，实验条件可控。

片段 3：自定义规划器的插件注册

// 实现类：继承规划器管理器基类，提供求解上下文与请求判定入口
namespace demo_planner {
class DemoPlannerManager : public planning_interface::PlannerManager {
 public:
  // initialize 接收模型、节点与参数命名空间，插件只取本插件关心的参数
  bool initialize(const moveit::core::RobotModelConstPtr& model,
                  const rclcpp::Node::SharedPtr& node,
                  const std::string& /*parameter_namespace*/) override {
    model_ = model;
    return true;
  }
  bool canServiceRequest(const planning_interface::MotionPlanRequest&) const override {
    return true;   // 简易实现：不区分请求类型，交给求解上下文检查
  }
  // 求解入口是规划上下文：上下文持有场景与请求，算法在其 solve 中实现
  planning_interface::PlanningContextPtr getPlanningContext(
      const planning_scene::PlanningSceneConstPtr& scene,
      const planning_interface::MotionPlanRequest& request,
      moveit_msgs::msg::MoveItErrorCodes& error_code) const override;
 private:
  moveit::core::RobotModelConstPtr model_;
};
}  // namespace demo_planner

// 导出宏把实现注册进插件系统：基类型决定被哪个加载器检索
PLUGINLIB_EXPORT_CLASS(demo_planner::DemoPlannerManager,
                       planning_interface::PlannerManager);

解读：插件注册分为实现与声明两段。设计要点：（1）初始化函数接收模型、节点与参数命名空间，插件自行解析参数，隔离各插件的配置域；（2）服务请求判定函数允许插件声明可处理的请求类型，精简实现可恒真而把校验放入求解上下文，真正的规划算法在上下文对象的 solve 中实现；（3）导出宏是插件可被发现的必要条件，漏写时类加载器找不到实现且仅在日志中提示。验证路径：编译安装后检查描述文件是否进入插件索引，再在配置中按插件名引用。

常见坑

  • 回调线程内调用阻塞接口：plan 与 execute 内部等待动作结果，在单线程执行器的回调中调用直接自锁。修复：调用放在独立线程或主流程，回调只做轻量处理。
  • 动作路径与进程内路径混用且场景未同步：两种路径各持场景快照，判断不一致。修复：明确场景权威方，混用前对比快照内容与时间戳。
  • 插件导出宏缺失或描述文件未安装：算法加载静默失败，配置写了算法名但行为仍是默认算法。修复：核对插件索引与日志中的加载提示，补齐导出宏与安装规则。
  • 依赖层次过深：纯算法验证程序链接了全部上层，编译时间与部署体积无谓增加，且易误用高层接口造成状态来源混乱。修复：按需要引入最底层依赖。
  • 在错误层定位问题：参数未生效却反复改规划器配置。修复：先按症状对照表确定层次，再从该层调用点顺链检查。

练习与思考

  1. 从 plan 方法出发画出动作路径的调用的层次清单，标注每一层接收与吐出的数据类型。★
    提示
    接口层构造请求，动作层传输请求消息，服务端解析请求，管线层生成响应，各层数据类型在"接口结构、消息、响应结构"之间转换。
  2. 改结构并预测：把进程内路径的起始状态改为"默认全零"（跳过场景当前状态），规划结果如何变化？说明这个改动在实验设计中的用途。★★
    提示
    全零状态可能处于碰撞或不可达，规划成功率下降；固定起始状态可消除状态随机性，适合算法对照实验。
  3. 为自定义规划器写出完整的接入清单：实现类、导出宏、描述文件、配置引用、验证步骤，并指出每一步失败时的表征。★★
    提示
    失败表征依次为编译错误、加载无提示、配置解析警告、算法行为不符；逐项核对描述文件安装位置与名称一致性。
  4. 解释适配器链放在规划器之前的工程意义，并列举两个真实适配器的职责。★★
    提示
    适配器在进入算法前统一修正请求与状态，避免每个规划器重复实现通用逻辑；例如起始状态修正与时间参数化。
  5. 设计一个对照实验：同一请求分别走动作路径与进程内路径，比较端到端耗时与规划时间，说明差值来源。★★★
    提示
    端到端差值含序列化、排队与回传；用结果中的规划时间做基线对照，两者接近说明求解占主导，差值大说明传输或排队显著。

小结

  • C++ 侧四层结构：核心库、规划层、规划接口层、节点服务端，依赖方向单向。
  • 动作路径与进程内路径共享规划管线内核，差别在状态来源与部署形态。
  • 接口封装类由动作客户端与请求构造器组成，plan 与 move 共用请求构造。
  • 规划器、适配器与运动学求解器都通过插件机制装载，名称一致与描述文件安装是加载成功的前提。
  • 按症状定位层次，再顺调用链阅读，是控制阅读范围的有效方法。
