第五篇 · 组件详解与系统集成

第 089 章：多机器人场景中的 MoveIt2 部署

从单臂单实例扩展到多臂多机：对比三种部署拓扑，梳理命名空间与变换前缀的完整隔离清单，给出跨臂碰撞检查与共享空间协调的两条技术路线。

  • 主题：系统集成 / 多机器人部署
  • 关键机制：命名空间隔离、变换前缀、跨臂碰撞镜像、共享空间互斥
  • 预计学时：60 分钟
  • 前置章节：第 088 章

学习目标

  • 理解多机器人部署的三种拓扑：独立实例、单体多组模型、独立实例加外部镜像，及其适用条件。
  • 掌握命名空间隔离的完整清单：描述参数、状态话题、场景话题、动作端点、控制器与变换前缀。
  • 理解跨臂碰撞检查的两条路线，以及镜像路线中时间错位与膨胀补偿的定量关系。
  • 会设计共享工作空间的协调规则：互斥、分区与统一调度。
  • 能按检查清单验证两套实例之间不存在话题串线与变换混叠。

背景与动机

双臂协作、多工位产线与移动操作平台让"多台机械臂共存"成为常态部署形态。多机器人不是把单臂方案复制多份：命名冲突、变换混叠、跨臂碰撞与共享空间竞争，都是单臂场景中不存在的问题。

最常见的故障是"串线"：第二套实例误订阅了第一套的关节状态，机器人模型在界面上重叠，规划结果朝错误目标运动。这类问题不会在启动时报错，只在行为上偏离，排查成本很高。另一类问题是跨臂碰撞：各实例的规划场景互不可见，两条臂在共享区域相撞。

上一章把单臂任务组织成可恢复流程，本章把编排扩展到多个规划实例与共享物理空间的系统级视角。

核心原理

1. 三种部署拓扑

拓扑选择由两个问题决定：是否需要跨臂碰撞检查、是否需要故障隔离。互碰撞检查要求两只臂位于同一规划场景，故障隔离要求各自独立进程。两者同时成立时，需要额外的同步机制。

拓扑结构互碰撞检查故障隔离适用
独立实例每臂一个节点实例，命名空间隔离无，需外部补充强工作空间分离的工位
单体多组单实例，一份模型含多臂，多个组有，天然统一场景弱双臂协作、强耦合任务
实例加镜像独立实例，把对方臂镜像为场景物体有（带时间错位）强需要隔离又要互检的产线

2. 命名空间隔离清单

隔离的目标是让每个实例只消费自己的数据、只响应自己的调用。漏掉清单中任何一项，都可能产生串线或资源竞争。

资源隔离手段漏配后果
机器人描述参数按命名空间各存一份两套模型加载同一描述，镜像错误
关节状态话题命名空间前缀实例 A 按 B 的状态规划
规划场景话题与服务命名空间前缀场景对象互相污染
动作端点命名空间前缀目标发到错误实例
控制器与执行端点命名空间前缀轨迹在错误硬件上执行
变换前缀发布前缀，引用一致两臂变换在同一坐标系下混叠

3. 变换前缀与坐标链

多台机器的变换树共享根参考系时，各机器人的连杆坐标系通过前缀区分。关节状态发布器接受前缀参数，规划实例发布与消费的坐标系必须携带一致的前缀，否则场景渲染与碰撞判定会落在错误位置。

T世界←臂N末端 = T世界←底座N ⊗ T底座N←末端（带前缀坐标系） 前缀不一致时，第二条链被解释在世界原点附近，渲染重叠且碰撞判断失真；这类错误在树结构检查工具中表现为重复坐标系名

4. 跨臂碰撞与镜像路线

镜像路线把对方臂当作动态碰撞体持续更新到本实例场景中。镜像存在时间错位：采样到对方状态、转换、写入场景之间存在延迟，对方在延迟窗口内继续运动，按旧位置检测会漏判。补偿方式是按最大关节速度乘延迟估计膨胀量：

r安全 ≥ v末端,max · δt镜像 + r余量 末端最大线速度 0.5 m/s、镜像延迟 0.1 s、余量 0.01 m 时，膨胀半径不小于 0.06 m；余量覆盖位姿估计与几何离散误差

镜像更新的几何表示有两种：按关节值展开的复制体（精确但计算量大），或按包络球近似（廉价但保守）。选择依据是共享区域的接近频率：偶发接近用包络近似，频繁交错用复制体。

5. 共享空间的协调

互碰撞检查只保证"规划时刻不碰撞"，不保证"执行时刻不碰撞"。共享区域的并发执行需要协调层：按区域划分互斥锁，进入共享区前加锁，离开后释放；或统一调度器串行化共享区动作。协调层的锁粒度按区域划分，避免无关工位互相阻塞。

实现思路与设计

多机器人部署按"拓扑选择、命名规划、启动编排、碰撞策略、协调规则"五步落地。顺序与单臂部署一致，新增的是每一步的多实例维度。

1. 命名规划表

项臂一臂二规则
实例命名空间/arm1/arm2小写短名，禁用数字开头与特殊符号
动作端点/arm1/move_action/arm2/move_action实例内相对名，天然跟随命名空间
场景话题/arm1/monitored_planning_scene/arm2/monitored_planning_scene观测与调试按实例分别进行
变换前缀arm1_arm2_与连杆名拼接，全链路一致

2. 启动编排

启动文件用循环生成实例节点，参数按实例注入：命名空间、变换前缀、描述参数路径、控制器配置。复用一个启动模板，扩展台数只改实例列表；实例间共享的共同节点（如静态世界变换）只启动一份。

3. 碰撞策略选择

  1. 工作空间分离：不检查跨臂碰撞，依赖物理分区与安全围栏。
  2. 共享区域且要求隔离：镜像路线加膨胀补偿，镜像频率不低于控制器状态频率的一半。
  3. 强耦合协作：单体多组模型，跨臂连杆对纳入检查，共享组用于协同动作。

4. 协调规则

协调层维护区域锁与优先级：进入共享区需要申请锁，锁的粒度约为一个技能动作；紧急任务允许抢占锁并触发对方退出共享区。协调层状态必须可观测：锁持有者、等待队列与超时次数都应可见。

与上一章的差异点：第 088 章的并发讨论停留在单实例内的任务互斥，本章把并发扩展到多实例共享物理空间，引入锁粒度与镜像补偿两个系统级机制。

关键代码与解读

片段 1：多实例启动编排（Python launch）

import os
from launch import LaunchDescription
from launch.substitutions import Command
from launch_ros.actions import Node
from launch.actions import GroupAction
from launch_ros.actions import PushRosNamespace
from ament_index_python.packages import get_package_share_directory

def robot_description(arm_id: str):
    """启动期用 xacro 实例化描述：前缀参数区分两套坐标系命名。"""
    xacro_file = os.path.join(get_package_share_directory("my_arm_description"),
                              "urdf", "arm.urdf.xacro")
    return Command(["xacro ", xacro_file, " prefix:=", f"{arm_id}_"])

def generate_launch_description():
    nodes = []
    for arm_id in ("arm1", "arm2"):
        # 每个实例整体压入命名空间：节点、参数、话题一次成型
        group = GroupAction([
            PushRosNamespace(arm_id),
            Node(
                package="my_arm_bringup",
                executable="move_group",
                name="move_group",
                # 描述参数按实例各放一份，避免两实例共用同一份而失去前缀区分
                parameters=[
                    {"robot_description": robot_description(arm_id)},
                    {"frame_prefix": f"{arm_id}_"},   # 变换前缀与连杆名拼接
                ],
                # 显式重映射关键话题：相对名自动带命名空间，绝对名需逐项改写
                remappings=[
                    ("joint_states", f"/{arm_id}/joint_states"),
                    ("monitored_planning_scene",
                     f"/{arm_id}/monitored_planning_scene"),
                ],
                output="screen",
            ),
        ])
        nodes.append(group)
    return LaunchDescription(nodes)

解读：启动编排是隔离的第一道闸门。设计要点：（1）用命名空间组统一压入，避免逐节点手工加前缀遗漏；（2）描述参数与变换前缀都按实例注入，模型坐标命名与变换链保持同一前缀约定；（3）话题重映射写成绝对名时逐项对应实例，相对名交给命名空间处理；（4）两套描述在启动期由同一份 xacro 源按前缀参数实例化，代码只有一份，差异集中在参数。共享的世界锚点与静态环境变换属于公共资源，只需在所有实例之外发布一份。验证方式：启动后逐实例列举话题与动作端点，核对命名空间前缀完整且互不重叠。

片段 2：把对方臂镜像为动态碰撞体

import rclpy
from rclpy.node import Node
from sensor_msgs.msg import JointState
from moveit_msgs.msg import CollisionObject, AttachedCollisionObject
from geometry_msgs.msg import Pose
from shape_msgs.msg import SolidPrimitive

class PeerMirror(Node):
    """订阅对方臂关节状态，用包络近似更新本实例场景中的动态碰撞体。"""

    def __init__(self):
        super().__init__("peer_mirror")
        # 镜像源：对方实例的关节状态；目标：本实例的场景应用服务
        self.create_subscription(
            JointState, "/arm2/joint_states", self.on_peer_state, 10)
        self.scene_pub = self.create_publisher(
            CollisionObject, "/arm1/collision_object", 10)
        # 包络半径含时间错位补偿：按对方末端最大速度乘镜像延迟估算（见正文）
        self.envelope_radius = 0.06

    def on_peer_state(self, msg: JointState):
        # 简化近似：以对方腕部关节位置为球心，用球体包络整段前臂
        if "wrist_3_joint" not in msg.name:
            return
        idx = msg.name.index("wrist_3_joint")
        # 关节位置是相对坐标，真实距离由变换查询获得；此处示意更新节拍
        obj = CollisionObject()
        obj.id = "arm2_envelope"
        obj.header.frame_id = "arm1_base_link"   # 统一到本实例参考系
        sphere = SolidPrimitive()
        sphere.type = SolidPrimitive.SPHERE
        sphere.dimensions = [self.envelope_radius]
        obj.primitives.append(sphere)
        pose = Pose()
        pose.position.x = float(msg.position[idx]) * 0.3   # 线性近似示意
        pose.orientation.w = 1.0
        obj.primitive_poses.append(pose)
        obj.operation = CollisionObject.ADD
        # 高频更新场景对象：接收端按差分应用，重复 ADD 表示覆盖位姿
        self.scene_pub.publish(obj)

解读：镜像节点的核心是"把对方状态持续翻译成本实例场景可消费的碰撞体"。设计要点：（1）镜像源与目标话题都带命名空间，方向明确（订阅 arm2，发布到 arm1 场景）；（2）包络半径显式携带时间错位补偿量，补偿依据是速度与延迟的乘积（见公式）；（3）发布采用场景对象差分话题，重复发送同一标识的对象等价于位姿覆盖，接收端无需先删后加。工程实现中该节点的几何计算应改为经由变换查询获得腕部真实位姿，示例中的线性近似仅用于说明更新节拍与消息结构。

片段 3：隔离性核验脚本

#!/usr/bin/env python3
"""启动后核验：每个实例的动作端点、场景话题与状态话题互不重叠。"""
import subprocess

EXPECTED = {
    "arm1": ["/arm1/move_action", "/arm1/monitored_planning_scene",
             "/arm1/joint_states"],
    "arm2": ["/arm2/move_action", "/arm2/monitored_planning_scene",
             "/arm2/joint_states"],
}


def list_interfaces(kind: str):
    # kind 取 action 或 topic：命令行输出按行拆分后取名称列
    out = subprocess.run(["ros2", kind, "list"],
                         capture_output=True, text=True).stdout
    return {line.split()[0] for line in out.splitlines() if line.strip()}


def verify():
    actions = list_interfaces("action")
    topics = list_interfaces("topic")
    problems = []
    for arm, names in EXPECTED.items():
        for name in names:
            pool = actions if "action" in name else topics
            if name not in pool:
                problems.append(f"缺失: {name}（{arm}）")
    # 串线检查：对方命名空间的动作端点不得出现在本实例的调用清单中
    for a, b in (("arm1", "arm2"), ("arm2", "arm1")):
        if f"/{b}/move_action" in actions and f"/{a}/move_action" not in actions:
            problems.append(f"疑似串线: {a} 只看到 {b} 的端点")
    print("核验通过" if not problems else "\n".join(problems))


if __name__ == "__main__":
    verify()

解读：核验脚本把"隔离是否成立"从人工检查变成可重复执行的自动化步骤。关键行为：（1）期望清单显式声明每个实例必须存在的端点，缺失即报；（2）互斥检查覆盖"自己的端点缺失"与"只看到对方端点"两种偏差；（3）脚本只读运行系统、不修改任何状态，可以在每次启动后无条件执行。扩展到更多实例时，只需扩充期望字典。

常见坑

  • 变换前缀不一致：关节状态发布带前缀而规划实例引用不带前缀（或相反），两臂在渲染中重叠、碰撞判断错位。修复：前缀作为部署参数集中管理，启动后用变换树检查工具核对坐标系命名。
  • 绝对话题名漏改：重映射里写了绝对名但只改了第一实例，第二实例仍指向前者。修复：绝对名重映射跟随实例循环生成，核验脚本按实例核对端点。
  • 场景对象互相污染：两实例共享同一场景对象话题，一方的放置物出现在另一方场景中。修复：场景话题全部命名空间化，共享场景只在单体多组拓扑中刻意为之。
  • 镜像延迟未补偿：跨臂接近时的碰撞判据按旧位置计算，实际执行中相撞。修复：按速度与延迟乘积估计膨胀半径并写入配置，镜像频率提升到状态频率的一半以上。
  • 共享区无协调：两条臂各自规划都无碰撞，同时进入共享区后相撞。修复：区域级互斥锁加统一调度，进入共享区前申请，离开后释放。

练习与思考

  1. 为"两臂工作空间完全分离"与"两臂频繁交错"两种场景各选一种拓扑，分别说明不选另一种拓扑的具体理由。★
    提示
    完全分离时跨臂检查无收益，独立实例的故障隔离更划算；频繁交错时镜像延迟的漏判风险高，单体多组的统一场景更可靠。
  2. 计算：对方末端最大线速度 0.8 m/s，镜像链路总延迟 0.15 s，几何离散误差 5 mm，求镜像包络的最小膨胀半径并说明各项含义。★★
    提示
    0.8 × 0.15 = 0.12 m，加 0.005 m 得约 0.125 m；第一项覆盖时间错位，第二项覆盖位姿估计与离散误差。
  3. 改配置并预测：把镜像更新频率减半，碰撞检测的误报率与漏报率分别如何变化？给出实验方案。★★
    提示
    频率减半使延迟加倍，需同步增大膨胀半径；半径增大则误报（把未接触判为接触）增加，不增大则漏报增加。实验固定轨迹速度，统计接近事件中的两类错误。
  4. 设计共享区协调协议：状态、申请、授予、释放、超时与抢占六要素，画出锁状态机并指出死锁预防规则。★★★
    提示
    锁按固定顺序申请可防环路等待；计时器保证锁不永久持有；抢占路径要求对方先退出共享区并确认安全，再移交锁。
  5. 把本章核验脚本扩展到四实例，给出期望清单的组织方式与一条新增的交叉检查规则。★★
    提示
    期望字典按实例循环生成；交叉检查可核对每个实例的场景话题订阅者只有一个权威发布者，防止多实例写入同一场景。

小结

  • 三种拓扑按"是否需要互碰撞检查、是否需要故障隔离"选择，两者同时成立时需要镜像或统一模型。
  • 命名空间隔离覆盖描述、状态、场景、动作、控制器与变换前缀六类资源，缺一即可能串线。
  • 镜像路线必须做时间错位补偿，膨胀半径由对方最大速度与镜像延迟的乘积决定。
  • 共享区协调采用区域级互斥与统一调度，进入前申请、离开后释放，并提供抢占路径。
  • 启动后核验脚本把隔离性从人工检查变为例行验证。
  • 下一章处理部署环境的另一半：从仿真到真机的迁移要点，把模型、控制器与安全性从仿真环境搬到物理现场。
