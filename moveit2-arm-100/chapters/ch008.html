第 008 章：使用 C++ MoveIt API 进行规划

本章用 C++ 的 MoveGroup 接口重写规划流程，重点讲清门面封装的机制、执行器与回调线程的配合，以及错误码驱动的结果处理。

  • 主题：C++ 接口 / 规划程序开发
  • 关键机制：MoveGroupInterface 门面、执行器线程模型、MoveItErrorCode
  • 预计学时：60 分钟
  • 前置章节：第 007 章

学习目标

  • 掌握 C++ MoveGroup 接口的初始化顺序与基本调用：取组、设目标、规划、执行。
  • 理解执行器（Executor）与回调线程模型，能正确安排 spin 线程与阻塞调用的配合。
  • 会解读规划错误码，按无解、超时、控制失败等类别分流处理。
  • 能编写构建文件把程序链接到 MoveIt2 库，理解依赖声明的作用。
  • 能对比 C++ 与 Python 两类接口的适用场景，做出有依据的选型。

背景与动机

机械臂应用的最终形态大多运行在 C++ 侧：控制器插件、实时性敏感的循环、与硬件驱动同进程的调度，都依赖静态类型与可预测的执行轨迹。Python 接口适合快速验证，C++ 接口承担交付形态，两者共享同一套底层库与消息定义，行为一致。

C++ 的代价在于两个额外的工程要求：程序的线程结构要自己安排，进程的生命周期要自己管理。常见的新手问题是把 Python 的直筒式写法照搬到 C++：在回调线程里调用阻塞方法，或在未启动 spin 的情况下等待动作结果，前者死锁，后者永远超时。本章把线程模型讲清楚，再给出可以逐行对照 Python 版本的完整程序。

核心原理

本节的原理主线是门面封装、线程模型、错误码体系三部分，它们共同决定 C++ 程序的结构。

1. MoveGroupInterface：进程内的组控制器

MoveGroup 接口对象围绕一个规划组构建，内部自动创建动作客户端、服务客户端与参数访问渠道。取组之后，调用者面对的是十来个语义明确的方法：设置各类目标、设置规划参数、规划、执行、查询当前状态。

这一设计是门面模式（Facade）的典型案例：把"构造复杂消息、发起通信、等待响应、解析结果"的序列封装成单次方法调用。门面的价值与代价同时存在：调用端的代码量降到最低，而调试粒度的默认值也变粗。需要观察请求细节时，要么借助日志，要么下沉到更底层的接口，后者在第五篇展开。

2. 执行器与回调线程：C++ 程序的骨架

ROS2 的 C++ 节点由执行器驱动：网络数据进入回调队列，执行器从队列取出并调用处理函数。动作客户端接收结果也属于回调。如果程序只在主线程里调用阻塞方法等待结果，主线程无法同时执行 spin，回调永不发生，等待必然超时；如果在回调内部再调用阻塞方法，单线程执行器会自锁死。

阻塞调用（plan/execute）+ 回调处理（动作结果）必须并行运行 标准解法：主线程发请求，独立 spin 线程消化回调；程序退出前先停执行器再回收线程

由此得到 C++ 程序的骨架顺序：初始化客户端库、创建节点与执行器、启动 spin 线程、构造组接口、执行规划与执行调用、结束时停止执行器并回收线程。顺序中任何一步调换都可能引入死锁或超时：先 spin 再发请求保证回调被及时处理，退出时先停 spin 再关闭库保证资源有序释放。

3. 错误码：失败分类的载体

规划接口返回错误码枚举、不返回布尔值，失败被分成多个类别。常见类别与处理策略如下：

错误码类别含义首要检查
SUCCESS规划成功无
PLANNING_FAILED搜索未找到可行路径目标可达性、碰撞状态、规划时间预算
TIMED_OUT超过时间预算仍未收敛提高预算、更换规划器、简化场景
INVALID_MOTION_PLAN请求本身无效组名、目标字段、起始状态
CONTROL_FAILED执行阶段控制器失败控制器在线状态与接口类型
FAILURE未分类失败查看服务端日志定位真实原因

错误码把"规划不行"的模糊判断细化为可执行的分流：无解改目标与场景，超时改预算与算法，控制失败查执行侧。程序在每个分支输出对应日志，一次运行即可圈定问题范围。

4. 构建与依赖声明

C++ 程序需要两处声明才能构建成功：包清单中的依赖项与构建脚本中的查找与链接。依赖声明不只为编译服务，还建立包之间的导出关系：MoveIt2 的库路径与头文件通过 ament 导出机制向依赖方暴露，构建脚本据此找到它们。漏声明的典型症状是本地目录编译通过、干净环境构建失败。以"任何新依赖都同时写进清单和构建脚本"为纪律可以避免这类环境差异。

实现思路与设计

程序按六步骨架组织，代码片段 1 给出完整实现；本节先给出设计决策与参数。

程序骨架

  1. 初始化客户端库：解析命令行参数，建立运行环境。
  2. 创建节点与执行器：节点承载配置参数，执行器负责回调调度。
  3. 启动 spin 线程：后台线程持续消化动作与服务回调。
  4. 构造组接口：绑定规划组名，读取组相关配置。
  5. 设目标并规划执行：命名位姿或关节目标先行，位姿目标在后续章节引入。
  6. 收尾：停止执行器、回收线程、关闭客户端库，返回退出码。

参数与检查表

参数建议值作用调整依据
规划时间1.0 s单次规划预算复杂场景提高，简单目标保持默认
尝试次数10独立重试次数失败率偏高时逐级提高
速度缩放0.2轨迹速度占上限比例首次运行保守，稳定后提高
目标容差0.01 rad（关节）到达判定的松弛量过紧导致难以收敛，过松影响精度
设计决策：为什么示例程序用单线程执行器加独立 spin 线程？

多线程执行器配合回调组能获得更高的并发上限，但回调组的划分与锁的边界需要仔细设计，首个 C++ 示例引入这些概念会丢失重点。单线程执行器加一个 spin 线程的模型最易懂：所有回调串行执行，业务线程只做阻塞调用，任何死锁都能用"谁在等谁"两句话解释清楚。并发模型升级放在第 092 章的实时性讨论中进行。

关键代码与解读

本节给出三段片段：完整规划程序、错误码分支与轨迹遍历、构建脚本。

片段 1：完整 C++ 规划程序

#include <thread>
#include <rclcpp/rclcpp.hpp>
// 头文件后缀随发行版演进：新版发行版中为 move_group_interface.hpp
#include <moveit/move_group_interface/move_group_interface.h>

int main(int argc, char** argv)
{
  rclcpp::init(argc, argv);
  // automatically_declare_parameters_from_overrides：启动文件注入的参数无需逐个声明
  auto node = std::make_shared<rclcpp::Node>(
      "cpp_moveit_demo", rclcpp::NodeOptions().automatically_declare_parameters_from_overrides(true));

  // 单线程执行器：所有回调串行处理，行为容易推理
  rclcpp::executors::SingleThreadedExecutor executor;
  executor.add_node(node);
  // 启动 spin 线程：动作结果、服务响应都在这里被处理
  std::thread spinner([&executor]() { executor.spin(); });

  // 门面对象绑定规划组；组名与 SRDF 一致，拼写错误在构造时报错
  moveit::planning_interface::MoveGroupInterface group(node, "arm");
  group.setMaxVelocityScalingFactor(0.2);   // 首次运行取保守速度
  group.setMaxAccelerationScalingFactor(0.2);
  group.setPlanningTime(1.0);               // 单位：秒
  group.setNumPlanningAttempts(10);         // 独立重试，提高成功率

  // 命名位姿目标：与第 005 章界面、第 006 章脚本使用同一份定义
  group.setNamedTarget("ready");

  moveit::planning_interface::MoveGroupInterface::Plan plan;
  // plan() 阻塞直到动作结果返回；期间回调由 spin 线程处理，互不阻塞
  if (group.plan(plan) == moveit::core::MoveItErrorCode::SUCCESS) {
    RCLCPP_INFO(node->get_logger(), "规划成功，路点数 %zu",
                plan.trajectory_.joint_trajectory.points.size());
    group.execute(plan);   // 执行同样阻塞等待控制器结果
  } else {
    RCLCPP_ERROR(node->get_logger(), "规划失败：检查目标与场景");
  }

  // 收尾顺序：先停执行器，唤醒并回收线程，最后关闭客户端库
  executor.cancel();
  spinner.join();
  rclcpp::shutdown();
  return 0;
}

解读：程序的每一段都在处理一个特定的机制。（1）节点参数自动声明选项让配置注入的参数可以被读取，启动文件直接复用第 006 章的注入方式。（2）spin 线程在组接口构造之前启动：门面构造时会进行参数与服务访问，需要回调通路已经就绪。（3）规划参数在设目标之前设置，参数作用域覆盖随后的规划调用。（4）收尾顺序与启动顺序镜像：先取消执行器再回收线程，避免线程在资源释放后访问已销毁对象。

片段 2：错误码分流与轨迹检查

// 把规划结果映射到处理策略：让日志直接指出下一步排查方向
// 先保存返回值再分支：规划是随机搜索，重复调用会改变结果且浪费时间
auto result = group.plan(plan);
if (result == moveit::core::MoveItErrorCode::SUCCESS) {
  // 成功路径继续向下执行
} else if (result == moveit::core::MoveItErrorCode::TIMED_OUT) {
  // 时间预算不足：提高预算或更换收敛更快的规划器（第 040 章展开）
  RCLCPP_WARN(node->get_logger(), "规划超时：考虑提高规划时间");
  return 2;
} else if (result == moveit::core::MoveItErrorCode::PLANNING_FAILED) {
  // 搜索失败：优先排查目标可达性与碰撞，第 049 章提供系统化诊断
  RCLCPP_WARN(node->get_logger(), "搜索失败：检查目标可达性与场景碰撞");
  return 3;
} else {
  RCLCPP_ERROR(node->get_logger(), "规划未成功，错误码 %d", result.val);
  return 4;
}

// 规划时间与路点规模是可观察的运行数据
const auto& jt = plan.trajectory_.joint_trajectory;
RCLCPP_INFO(node->get_logger(), "规划耗时 %.3f s，路点数 %zu", plan.planning_time_, jt.points.size());
// 抽查首末点时间：时间参数化已执行时，末点时间应大于零且单调递增
if (jt.points.size() > 1) {
  RCLCPP_INFO(node->get_logger(), "首末点时间 %.3f s 至 %.3f s",
              jt.points.front().time_from_start.sec + jt.points.front().time_from_start.nanosec * 1e-9,
              jt.points.back().time_from_start.sec + jt.points.back().time_from_start.nanosec * 1e-9);
}

解读：这段代码把第 001 章的接口分层落到了实现层。（1）分支链把错误码翻译为具体的下一步动作，日志从陈述事实升级为给出方向。（2）返回值先保存再分支：规划是随机搜索过程，每次调用都可能得到不同结果，逐次重算既浪费预算又破坏日志一致性；错误码数值通过 val 字段访问。（3）轨迹检查选择路点数与首末时间两个指标：路点数反映搜索规模，时间戳反映后处理是否生效；两者都异常时应回到规划管线配置检查。

解读：构建脚本的每一行都对应第 002 章的依赖解析机制。（1）find_package 与 ament_target_dependencies 成对出现：前者定位包，后者把编译与链接信息附着到目标。（2）依赖项需与包清单保持一致，清单服务构建顺序与依赖发布，构建脚本服务编译本身。（3）安装目标到包的库目录，随后可在任意加载该包的环境中直接运行，与第 002 章的叠加机制衔接。

常见坑

  • 未启动 spin 线程就调用阻塞方法：等待动作结果永远超时，且没有任何回调日志。修复：按片段 1 的顺序先启动执行器线程。
  • 在回调函数里调用阻塞规划：单线程执行器自锁，程序挂起。修复：把规划调用移出回调，或改用多线程执行器并划分回调组。
  • 退出顺序颠倒：先关闭客户端库再回收线程，偶发崩溃或资源告警。修复：取消执行器、回收线程、关闭库，严格按序执行。
  • 头文件后缀与发行版不符：编译报找不到头文件。修复：按对应发行版调整后缀（如 .h 与 .hpp），以官方文档为准。
  • 参数未注入导致规划管线缺失：组接口构造成功但规划失败，或启动即报参数缺失。修复：用启动文件注入配置包内容，与第 006 章的做法一致。

练习与思考

  1. 在片段 1 基础上增加一行代码，把规划时间改为 2.0 s、速度缩放改为 0.5，说明两处修改各自影响的阶段与预期现象。★
    提示
    规划时间影响搜索阶段的预算，影响失败率与耗时；速度缩放影响时间参数化后的轨迹速度，影响执行时长而不影响搜索。
  2. 解释为什么 spin 线程必须在构造组接口之前启动，如果交换顺序在什么情况下会永久超时。★
    提示
    门面构造期可能发起参数与服务访问；交换顺序后，构造阶段的回调无人处理，等待超时取决于各访问的超时设置。
  3. 预测实验：把错误码分支链中的 TIMED_OUT 分支删掉，让超时落入最后的兜底分支。失败日志的信息量发生什么变化？再把"先保存返回值"改成在每个分支内重新调用 plan()，又带来什么副作用？★★
    提示
    兜底分支只打印数字错误码，失去处理方向；重复调用会显著增加耗时，且规划是随机搜索，第二次结果可能与第一次不同，日志与行为都不稳定。
  4. 设计题：为一条"C++ 规划节点 + Python 监控脚本"的实验流程分工，说明哪些职责放在 C++ 侧、哪些放在 Python 侧，依据是什么。★★★
    提示
    实时路径与交付形态放 C++；数据统计、参数扫描、可视化脚本放 Python。依据是各自的部署成本与迭代速度，与语言偏好无关。

小结

  • MoveGroupInterface 是进程内门面：以方法调用封装动作、服务与参数访问。
  • C++ 程序的骨架是"执行器加 spin 线程"：回调与阻塞调用并行，顺序决定了程序会不会死锁。
  • 错误码把失败分类，让日志可以给出下一步排查方向；轨迹数据用路点数与时间戳速检。
  • 依赖声明分两处：包清单负责依赖发布，构建脚本负责编译链接，两者保持一致。
  • 下一章深入两类接口共同依赖的基础：机器人状态表示 RobotState 与 RobotModel，理解规划请求中的状态从哪来、到哪里去。
