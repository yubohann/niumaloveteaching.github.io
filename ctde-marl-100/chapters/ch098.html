第五篇 · 研究复现与系统集成

第 098 章：开源框架对比：PyMARL、MARLlib与RLlib

三套框架服务三种研究阶段：PyMARL 是值分解复现的起点，MARLlib 提供最广的算法与环境覆盖，RLlib 面向工程化与分布式伸缩。本章从六个维度横比，并给出选型与二次开发成本的评估方法。

  • 主题：训练框架（Training Framework）选型
  • 关键公式：策略映射 agent_id → policy_id、采样器-学习器吞吐比（样本吞吐与更新吞吐的匹配）
  • 预计学时：55 分钟
  • 前置章节：第 097 章

学习目标

  • 理解三套框架的架构定位与设计哲学差异，能概述各自的代码组织方式。
  • 掌握两个核心抽象：控制器-学习器分离与策略映射，理解它们对实验组织的影响。
  • 能从环境支持、算法覆盖、并行机制、扩展成本等维度建立框架选型矩阵。
  • 理解跨框架数字不可直接比较的原因，能设计跨框架对照的公平协议。
  • 能评估二次开发成本：新增算法、新增环境与日志评测对接的工作量结构。

背景与动机

前三章的方法论最终要落在代码基座上：复现第 092 至 094 章的算法需要正确的默认实现，跑动第 095 至 097 章的实验矩阵需要稳定的采样吞吐。选错基座的代价在项目中期才会显现：想扩到 32 个并行环境时发现框架只支持单进程，想换环境时发现算法与环境深度耦合。框架选型的本质是把研究问题映射到"环境支持、算法覆盖、并行能力、扩展成本"四个变量上的一次工程决策。

本章讨论的三套框架恰好覆盖三种典型诉求：PyMARL 代表"小而准"，围绕值分解与实时策略基准设计，代码量小、复现记录多；MARLlib 代表"全而统"，用统一接口覆盖大量算法与环境组合；RLlib 代表"稳而大"，把强化学习训练做成可伸缩的工程系统。理解它们的分工，比记住任何一个 API 都更有长期价值。

核心原理

1. 三框架定位

维度PyMARL 系（含 EPyMARL 扩展）MARLlibRLlib
设计目标值分解算法的高保真复现算法与环境的广覆盖可伸缩的通用训练系统
环境支持实时策略基准为主，扩展版接入粒子环境与 Gym 接口统一接口对接多类多智能体环境Gym 系接口加多智能体策略映射
算法覆盖VDN、QMIX、QTRAN、COMA 等值分解族覆盖值分解、策略梯度与通信类在内的广泛算法PPO、IMPALA、MADDPG 等通用族为主
并行机制单进程采样为主多进程采样工作器分布式采样工作器加可扩展学习器
扩展成本新增算法改动小、新增环境改动大新增环境走适配层，成本中等新增算法需要理解系统抽象，成本较高
复现生态社区复现数字最多，论文对照首选组合多、对照需注意实现差异以工程部署与规模化见长

三者的差异本质上是抽象层次差异：PyMARL 的抽象最少，从环境到损失函数路径最短；RLlib 的抽象最多，每个功能点都有可替换的组件。抽象层越多，规模化越容易、调试越需要理解框架；抽象层越少，复现越保真、扩展越依赖自己。

2. 核心抽象：控制器与学习器分离

PyMARL 系的骨架是控制器（Controller）与学习器（Learner）分离：控制器负责与环境交互、按探索调度产生动作、把完整回合写入回合级缓冲；学习器从缓冲采样批量、计算时间差分损失、执行参数更新。两个组件通过缓冲解耦，采样吞吐与更新吞吐互不阻塞。多智能体细节集中在两处：控制器调用的策略带逐智能体隐藏状态管理；学习器的时间差分目标用混合网络聚合个体价值。分离结构的调试优势是故障定位快：曲线不升先看缓冲内容的分布，再看待更新队列，最后才怀疑算法实现。

3. 核心抽象：策略映射

RLlib 系处理多智能体的方式是策略映射：系统维护一个策略字典，映射函数把 agent_id 指向 policy_id。参数共享就是"全部 agent_id 指向同一 policy_id"；异构智能体就是"不同 agent_id 指向不同策略"；课程式新增智能体只需扩展映射函数：

policy_id = mapping( agent_id )，参数共享 ⇔ 对所有 agent_id 有 mapping(agent_id) = 同一 policy_id 映射函数在执行期被调用，策略选择与算法逻辑解耦；共享是映射的特例，异构是映射的一般情形

映射抽象的副产品是异构智能体的低门槛：智能体类型差异（不同动作空间、不同观测维度）通过多策略表达，代价是每个策略维护独立的优化器与批处理逻辑。跨框架对照实验时要特别注意：RLlib 的"共享策略"与 PyMARL 的"参数共享"默认实现细节不同（批处理组织、归一化位置），数字不能直接互认。

4. 并行与分布式

三者的并行层级不同：PyMARL 系以单进程串行采样为默认（扩展版有并行采样选项）；MARLlib 支持多个采样工作器并行收集；RLlib 把采样与学习都做成可分布式组件，支持多机扩展。并行层级影响两件事：单位墙钟时间内收集的环境步数，以及相同环境步数下的更新次数（工作器越多、每工作器分配的更新越少）。报告实验时要给出并行度与更新次数，否则"相同环境步预算"的声明在跨框架对照中不成立。

数值算例（并行度与更新次数）。总预算 100 万环境步、采样批 8192 步一次迭代：8 个工作器时迭代约 122 次；工作器增到 32 而批量不变，迭代次数仍约 122 次，墙钟时间在理想并行下降到约四分之一；批量若随工作器同步放大到 32768 步，迭代次数降到约 30 次，更新次数随之减为四分之一（数值经程序核对）。同一环境步预算下两种做法产生不同的学习动力学，这正是跨框架对照必须声明"批量 × 工作器"组合的原因。

5. 二次开发成本结构

  • 新增算法：PyMARL 系继承学习器、实现损失函数即可，改动面小；MARLlib 在算法注册表中登记并复用接口；RLlib 需要按策略与算法两层的抽象实现，学习曲线最陡。
  • 新增环境：PyMARL 系需要侵入式改造环境包装；MARLlib 提供适配层，写环境包装器的工作量中等；RLlib 通过标准 Gym 接口与策略映射接入较顺。
  • 日志与评测对接：三者都要导出第 082 章格式的 JSONL；RLlib 自带日志与分析工具，另两套需要少量胶水代码。

实现思路与设计

选型按研究阶段分三步：

  1. 复现阶段：值分解与策略梯度复现选 PyMARL 系或 EPyMARL，理由是社区数字多、对照成本低。
  2. 扩展阶段：需要广算法组合或跨环境泛化实验时选 MARLlib，用统一接口降低环境适配成本。
  3. 规模化阶段：智能体数上探、需要分布式采样或多机训练时迁移 RLlib，并重新校准并行度与更新次数的对应关系。

与第 097 章的差异点：097 章选任务的供给方（基准），本章选代码的供给方（框架）；评测脚本的注册表设计在两章间通用，框架只是注册表背后被注册的实现。

设计决策：为什么跨框架数字不能直接比较？

框架对同一算法的默认实现存在系统性差异：批量的组织顺序、优势归一化的位置、探索调度的步数口径、RNN 序列预处理方式，每一项都能带来数个百分点到十余个百分点的曲线移动。跨框架比较必须先做"实现对齐"（按第 092 章的配置表逐项核对），或明确声明为"生态级对比"并附全部默认值差异清单。把框架默认值当算法性质，是文献间数字冲突的常见根源。

关键代码与解读

片段 1：策略映射配置（RLlib 风格）

def build_multi_agent_config(env_name, n_agents=4):
    """RLlib 风格配置：多智能体经策略映射共享一个策略。"""
    def policy_mapping_fn(agent_id, episode=None, **kwargs):
        # 映射函数在执行期调用：所有 agent_id 指向同一策略即参数共享
        return "shared"

    config = {
        "env": env_name,
        "env_config": {"n_agents": n_agents},
        "multiagent": {
            "policies": ["shared"],              # 策略表：此处只有一个共享策略
            "policy_mapping_fn": policy_mapping_fn,
        },
        "lr": 5e-4,
        "train_batch_size": 8192,                # 采样批步数：与并行工作器数共同决定更新频率
    }
    return config

# 异构改造示例：按智能体类型分流到不同策略
def type_based_mapping(agent_id, episode=None, **kwargs):
    return "scout" if str(agent_id).startswith("scout") else "carrier"

解读：（1）配置用普通字典构造，屏蔽了具体版本的链式 API 差异，读者可把字典字段映射到任一版本的配置对象上。（2）policy_mapping_fn 的签名保留 episode 参数：课程学习中映射可以随情节改变（例如前半段全共享、后半段分流），签名设计为将来的课程实验留了扩展点。（3）train_batch_size 命名为"采样批步数"，与并行工作器数相乘得到每次迭代的总步数；跨框架对照时要把该值换算成第 097 章的决策步口径。（4）异构示例按 agent_id 前缀分流：实际项目中智能体类型通常来自环境元数据，映射函数读元数据比字符串前缀更稳妥。

片段 2：控制器与学习器分离（PyMARL 风格骨架）

import torch

class Controller:
    """采样控制器：只产生经验，不接触梯度。"""
    def __init__(self, args, env, policy):
        self.args, self.env, self.policy = args, env, policy
        self.buffer = EpisodeBuffer(capacity=args.buffer_size)   # 5000 回合

    def run_episodes(self, n_episodes):
        for _ in range(n_episodes):
            obs, _ = self.env.reset()
            episode = []
            done = False
            while not done:
                # epsilon 由采样器管理：学习器不需要知道探索细节
                action, hidden = self.policy.act(obs, epsilon=self.args.eps)
                next_obs, rew, term, trunc, _ = self.env.step(action)
                episode.append((obs, action, rew, term, hidden))
                obs = next_obs
                done = all(term.values()) or all(trunc.values())
            self.buffer.push(episode)            # 回合级存储：保住 RNN 序列完整

class Learner:
    """学习器：从缓冲采样批量，执行一步时序差分更新。"""
    def __init__(self, args, agent, buffer):
        self.args, self.agent, self.buffer = args, agent, buffer
        self.optim = torch.optim.RMSprop(agent.parameters(), lr=args.lr)

    def step(self):
        batch = self.buffer.sample(self.args.batch_size)   # 32 个完整回合
        loss = self.agent.compute_td_loss(batch)
        self.optim.zero_grad()
        loss.backward()
        # 梯度裁剪：与第 027 章的稳定性手段一致
        torch.nn.utils.clip_grad_norm_(self.agent.parameters(), self.args.clip)
        self.optim.step()
        return float(loss.detach())

解读：（1）Controller 与 Learner 只共享缓冲，两者可以运行在不同进程或不同机器上；采样吞吐与更新吞吐的比例由调用方调度，不需要修改两个类的内部。（2）epsilon 属于采样器参数：把探索调度放在控制器侧，学习器看到的永远是"已按策略分布采集"的数据，off-policy 修正交给算法本身（如 Q 学习的目标构造）。（3）回合级缓冲保留完整序列，与第 093 章 on-policy 的序列完整性要求同源；片段里的 done 用术语与截断的并集，真实实现分别存储两个标志供 GAE 使用。（4）学习器返回损失标量供日志管道采集，与第 082 章诊断面板的 TD 损失字段直接对接。

常见坑

  • 把框架默认值当社区共识：不同框架对同一算法给了不同的默认批量与归一化，直接横向抄数字得到错误结论。修复：对照前先做实现对齐表。
  • 忽略并行度对更新次数的影响：相同环境步下工作器越多更新越少，学习速度差异被误认为算法差异。修复：报告并行度与更新次数。
  • 在单进程框架上硬扩规模：采样成为瓶颈后训练时间随智能体数平方增长。修复：按第 099 章的规模规划选择支持并行采样的框架。
  • 策略映射写成字符串前缀匹配：智能体命名规则变化后映射静默错配。修复：映射读环境元数据并加断言校验每个 agent_id 都有策略。
  • 缓冲与学习器生命周期不匹配：重置环境时缓冲未同步清空，跨运行数据混入。修复：每次 run 构造独立缓冲区并写入运行清单。

小结

  • 三框架对应三种诉求：PyMARL 系求准（复现）、MARLlib 求全（覆盖）、RLlib 求大（伸缩）。
  • 控制器-学习器分离把采样与更新解耦；策略映射把智能体到策略的指派变成配置。
  • 跨框架数字必须经过实现对齐才能比较，默认值差异是文献数字冲突的常见根源。
  • 二次开发成本按"新增算法、新增环境、日志对接"三笔账评估，抽象层越多单点成本越高、规模化成本越低。
  • 选型随研究阶段迁移，触发条件写成可测量阈值。
  • 下一章处理规模问题：大规模扩展：从十个到上百个智能体，讨论联合空间爆炸、平均场近似与局部化设计。
