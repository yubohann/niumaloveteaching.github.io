第 012 章：QoS匹配规则与策略选择

从"两条主策略"走向完整体系：兼容性矩阵逐条判定、预置 profile 的取舍、以及一套能背下来做评审的选型决策树。

  • 主题：通信基础 / 服务质量体系
  • 关键机制：兼容性判定规则、不匹配事件、预置 profile、deadline/liveliness/lifespan
  • 预计学时：55 分钟
  • 前置章节：第 011 章

学习目标

  • 掌握完整兼容性思路：每条策略的"要求 ≤ 提供"判定，能手工推算任意两端组合是否匹配。
  • 知道哪些 QoS 策略参与匹配、哪些只是本地资源设置（如 history 深度不参与兼容判定）。
  • 会捕获并解释不匹配事件：用事件处理器在运行期发现"合同谈崩"，无需事后猜。
  • 熟悉常用预置 profile（sensor data、services default 等）的正确用法：做起点、做基座、显式覆盖。
  • 会按决策树完成选型，并知道 deadline、liveliness、lifespan 三个进阶策略什么时候值得上场。

背景与动机

第 011 章讲透了可靠性与持久性两条主线策略。真实系统还需要回答更多问题：发布端承诺"至少每 100 ms 会有一条数据"，订阅端能不能把这条承诺变成告警（deadline）？探测到的旧指令要不要在中间件层直接作废（lifespan）？节点"还活着"除了应用层心跳，中间件层有没有声明（liveliness）？这些问题由 QoS 家族的其他成员回答。

更重要的是，多机器人系统里 QoS 配置的"人口密度"很高：20 台机器人 × 数十个话题 × 两端配置，任何一处两端的合同谈崩都会静默失联。本章的目标是让你具备三件能力：评审时一眼看出不兼容组合、运行时能捕获不匹配事件、选型时有章可循不拍脑袋，它们是第 013–015 章性能工程的前提：先保证连通正确，再谈延迟与带宽优化。

核心原理

1. 兼容性判定：一份逐条的矩阵

匹配的判定原则还是那句"订阅端的要求 ≤ 发布端的提供"，但对每条策略，"要求超标"的定义不同。下表是工程上最常撞到的组合：

策略订阅端"更强"的方向不匹配的典型组合不匹配的后果
Reliability要求 Reliable发布 Best-effort + 订阅 Reliable静默不连通
Durability要求 Transient-local发布 Volatile + 订阅 TL静默不连通
Deadline要求更短的周期（更快的更新）发布承诺 100 ms + 订阅要求 50 ms不匹配（要求快于承诺）
Liveliness要求更强的心跳模式发布 AUTOMATIC + 订阅 MANUAL_BY_TOPIC不匹配

反过来都匹配：发布 Reliable 满足订阅 Best-effort；发布 TL 满足订阅 Volatile；发布承诺 20 ms 满足订阅要求 100 ms；发布 MANUAL_BY_TOPIC 满足订阅 AUTOMATIC。记忆法：提供方"过剩"没关系，订阅方"要多了"才谈崩。各发行版与中间件在细散字段（如 liveliness 租约的毫秒级比较）上可能有实现差异，评审拿不准时以对应版本的官方文档为准。

还有一个关键区分：不参与匹配的策略。history（keep-last/keep-all）与 depth 是本地资源设置，两端深度不同不影响匹配，只影响各自的排队与补发行为；资源限制类策略同理。"对方 depth=1 我 depth=10 会不会不匹配"，不会；但对方只留 1 条历史时，你的晚到补发自然也只有 1 条，效果差异是数据层面的，不是连接层面的。

2. 队列深度与丢包：一条可以手算的关系

history 与 depth 不参与匹配，但它们决定"过载时丢什么"。以 keep-last 语义为例：发布端以速率 λ 生产，消费端以速率 μ 取用，积压以 (λ − μ) 的速率增长；当积压超过 depth，最旧的样本被覆盖丢弃。队列只能吸收突发，不能修复稳态失配：λ 持续大于 μ 时，无论 depth 取多大，稳态丢包率最终趋近 1 − μ/λ。

可吸收的突发时长 ≈ depth ÷ (λ − μ)（λ > μ 时成立）；稳态不丢条件：λ ≤ μ 算例：λ = 120 Hz、μ = 100 Hz、depth = 1 时积压速率为 20 条/秒，50 ms 内就会覆盖丢样；depth = 10 可吸收约 0.5 s 的突发。50 Hz 控制指令配 depth = 1 正是此理：只要最新，不要历史

这段算术推翻一个常见误解：有人把 depth 当"防丢包参数"，给 100 Hz 的感知流配 depth = 1 却疑惑"过载后数据为什么断崖"。正确顺序是先保证消费端处理能力（第 002 章的背压与降频），再用 depth 吸收网络与调度的短促抖动。队列深度的另一面是代价：depth 每加 1，晚加入者的补发量与内存占用随之增长，恢复瞬间的突刺也被放大（第 011 章），所以深度取值要有实测的抖动分布作依据，一律调大只会放大突刺。

3. 不匹配的生命周期：何时判定、如何发现

不匹配判定的时机在发现之后、匹配尝试之时：某个订阅端与某个发布端被放在一起比对合同，不通过则不建立通路。注意它对"多端点"话题的含义：一个话题有 3 个发布者、2 个订阅者，可能形成 6 组候选配对，其中若干组匹配、若干组不匹配，"看到数据"与"没看到数据"可以同时为真，取决于是哪一对。这就是为什么排障要看 --verbose 的端点级视图；只看话题名会漏掉配对级信息。

程序里的发现手段是 QoS 事件：发布端与订阅端都可以注册"不兼容 QoS"事件回调，当出现不匹配尝试时得到通知（对端 GUID、最后请求的 QoS 等）。把这件事做进系统监控里，等于给静默故障装了一盏灯，第 006 章的图巡检负责"端点数量对不对"，QoS 事件负责"端点对得上话没有"，两者拼全了连接健康的图景。

4. 预置 profile：用作起点，别当信仰

ROS2 客户端库提供若干预置统称 profile，覆盖常见实体类型：

预置要点典型用途
qos_profile_sensor_dataBest-effort、depth 5、Volatile传感器流默认档
qos_profile_services_defaultReliable、depth 10、Volatile服务/动作内部通信
qos_profile_parametersReliable + 较大 depth参数接口
qos_profile_system_default随实现而定的保守默认框架内部

正确姿势：把预置当"基座"，用显式覆盖表达你的特殊需求（如"我要 sensor data 的基调，但可靠性升级为 Reliable"）。两个纪律：（1）不要手写"半套配置"，自己拼一个缺失字段的 profile，其默认值随实现变化；（2）两端配置在同一处定义（如共享的 qos.py 模块），防止"发布端改了、订阅端忘了"。QoS 不匹配的根因十有八九是配置复制粘贴后的分叉，共享定义从源头上消灭它。

换到字段视角看预置之间的差别更直观（具体值以对应发行版实现为准）：

预置ReliabilityDurabilityHistory / Depth适合的对接对象
qos_profile_sensor_dataBest-effortVolatilekeep-last 5传感器流、可视化流
qos_profile_services_defaultReliableVolatilekeep-last 10服务与动作的请求应答
qos_profile_parametersReliableVolatile较大深度参数服务与参数事件
qos_profile_system_default依实现而定依实现而定依实现而定框架内部，业务不宜直接依赖

读表得到两条选型经验：系统默认档的字段值随版本可能变化，把它当业务接口的契约是不可靠的，关键话题一律显式写出策略；而 sensor data 档的 depth 5 恰好覆盖"单帧处理抖动"的量级，这就是它成为感知流默认档的原因，换成 depth 1 会让一帧的排队抖动直接变成丢帧。

5. 进阶三件套：deadline、liveliness、lifespan

当基础四象限不够用时，这三个策略值得认识：

  • deadline（截止时间）：发布端承诺"我至少每 D 时间发一条"；订阅端要求"我必须每 D 内收到一条"。违约时双方都收到事件，它把"数据新鲜度"的监控下沉到中间件层，不再需要每个应用自己写频率看门狗（那种看门狗测"到达频率"，deadline 测"更新承诺"，互补）。取值基座：正常周期的 2–3 倍，避免误报。
  • liveliness（活跃性）：声明"我怎么证明自己还活着"，AUTOMATIC（中间件代发心跳）到 MANUAL_BY_TOPIC（应用亲口声明）。泄漏/超时产生事件。适用面窄：应用层心跳（第 006 章）更灵活可控；只有当你想让中间件级别兜底"发布者半死"时才加。
  • lifespan（寿命）：给样本身份证有效期，超过 lifespan 还没送到的样本直接作废，不再投递。典型用途是"陈旧指令自动过期"：给 cmd_vel 配 200 ms lifespan，拥塞期间积压的旧指令会被中间件直接丢弃，延迟执行被阻断，把第 011 章"旧指令有害"的直觉变成机制。
deadline 起点 = 正常周期 + 抖动 p99，再留 1 倍余量；lifespan 上限 = 可接受陈旧位移 ÷ 运行速度 20 ms 周期加 15 ms 抖动 p99 得 35 ms，deadline 取 50 ms 量级；1 m/s 运行、允许 0.2 m 陈旧位移时，lifespan 取 200 ms。两式分别把"时效承诺"与"安全预算"翻译成参数

数值算例把两个策略的职责边界说透：同为 50 Hz 的话题，deadline 关注"发布端承诺的更新间隔是否被违反"，事件在违约瞬间触发；lifespan 关注"每条样本的保质期"，过期样本在进入投递前就被丢弃。前者管"会不会太久没说话"，后者管"说的话会不会太旧"；一个话题可以只配其中之一，也可以两者同配，各司其职。判断是否需要 deadline 的标准是"数据停更本身是否构成故障"；判断是否需要 lifespan 的标准是"陈旧数据是否比没有数据更危险"，两个问题都有明确的物理答案，不需要凭感觉。

三件套的共同气质：用声明代替代码。加它们之前先确认应用层没有更简单的实现；加了之后要在设计表里写明理由与参数依据，否则会变成下一任维护者的谜题。

6. 选型决策树

把整个章节压缩成五个问题，按顺序回答：

  1. 丢一条会破坏状态一致性吗？会 → Reliable；不会（下一帧更好）→ Best-effort。
  2. 晚加入的消费者需要当前值吗？需要 → Transient-local（+Reliable）；不需要 → Volatile。
  3. 历史要留几条？现状类 keep-last(1)；事件类按"消费者需要的上下文条数"；感知类 1–5 缓冲。
  4. 有没有"必须按时到"的承诺？有 → 加 deadline（按正常周期 2–3 倍设）。
  5. 有没有"过期即有害"的数据？有 → 加 lifespan（按物理安全预算设）。

五问走完，一条话题的 QoS 就定稿了。写进设计表时补上"为什么不选另一档"的一句理由，评审时真正被追问的是理由，答案只是落点。

实现思路与设计

用"多机器人监控系统"做一次全员 QoS 评审。角色不止生产/消费两端，还有两个特殊角色：录制端（rosbag 或自研记录器）与可视化端（遥控台面板）。它们的 QoS 请求决定"能不能看到"。

角色-QoS 对照表

角色话题请求的 QoS 要点理由
底盘（消费）/robotN/cmd_velReliable、Volatile、depth 1、lifespan 200 ms指令不丢；旧指令作废；旧样本不执行
遥控台（消费）/robotN/odomBest-effort 即可显示用：丢一帧无感，弱请求兼容一切发布端
地图服务（生产）/fleet/mapReliable + Transient-local + keep-last(1)晚加入要现状；见第 011 章的突刺预算
录制端（特殊）全部话题逐话题显式配置：sensor 档用 best_effort；地图类补 TL 会话记录器必须兼容两类发布端；默认 profile 会漏掉 TL 历史
健康监控（消费）/fleet/task_eventReliable + TL + depth 10事件不可丢；晚加入补上下文

评审检查清单：（1）每对端点是否过五问；（2）两端配置是否同源（共享定义）；（3）是否注册了不匹配事件回调；（4）特殊角色（录制/可视化）的请求是否被显式设计过；（5）Transient-local 话题是否进了"突刺预算表"。

设计决策：录制端为什么"默认配置"往往不够？

记录器的使命是"忠实复现"，它对 QoS 的诉求与其他消费者不同：它要尽量兼容所有发布端，还要尽量抓到历史。两个常见缺口：（1）用默认 profile 请求 Reliable，遇到 Best-effort 的传感器发布端直接不匹配，录像里大段空白；（2）不请求 Transient-local，开录时地图源早已在线，录像里永远缺"开局那一刻"的地图。解法：录制配置逐话题显式化，感知类用 Best-effort 请求、地图类叠加 TL 请求；录制端的 QoS 设计应该和录制话题清单一起评审；一个大一统默认会漏掉上述两类。回放时同理：回放器的发布 QoS 要与原始发布端一致，否则回放数据在订阅端眼里"形状不同"，复现实验就失去意义（第 037 章展开）。

关键代码与解读

片段 1：捕获不匹配事件，给静默故障装一盏灯

from rclpy.qos_event import PublisherEventCallbacks

class GuardedPublisher(Node):
    """发布端注册不匹配事件：任何订阅者合同谈崩，这里立刻知道。"""
    def __init__(self):
        super().__init__("map_pub")
        qos = QoSProfile(depth=1,
                         reliability=ReliabilityPolicy.RELIABLE,
                         durability=DurabilityPolicy.TRANSIENT_LOCAL)
        # 关键一步：创建发布端时注册不兼容 QoS 事件回调（事件容器与字段以发行版为准）
        self.pub = self.create_publisher(
            OccupancyGrid, "/fleet/map", qos,
            event_callbacks=PublisherEventCallbacks(incompatible_qos=self.on_incompatible))

    def on_incompatible(self, event):
        # event 携带冲突策略与计数（如 last_policy_kind / total_count，
        # 字段名以对应发行版文档为准）；生产系统应计数上报监控，仅打日志会丢失统计
        self.get_logger().error(
            f"存在不兼容订阅端：冲突策略={event.last_policy_kind}，"
            f"累计={event.total_count}（第 018 章接监控）")

解读：（1）不匹配是"静默"的，默认没有任何日志。注册这个回调后，静默故障变成显式告警：哪个话题、哪个策略谈崩、对端（通过事件信息）是谁。把这段代码抄进你所有"关键话题"的发布者，等于给系统装了合同审计员。（2）事件回调要短（第 002 章纪律），所以注释里写"计数并上报监控"，复杂处理留给监控侧。（3）注意事件 API 的形状随发行版有差异（事件容器的构造方式、info 字段结构），以对应版本文档为准；但"注册一个回调、拿到冲突策略、转为告警"这个流程是稳定的。

片段 2：预置基座 + 显式覆盖，控制通道的完整合同

class CommandPublisher(Node):
    """控制通道：以 services 档为基座，逐条覆盖出控制语义。"""
    def __init__(self, robot_id):
        super().__init__("cmd_bridge", namespace=f"robot{robot_id}")
        # 基座：以 qos_profile_services_default 的基调为参照（Reliable、较深历史）
        qos = QoSProfile(depth=10)
        qos.reliability = ReliabilityPolicy.RELIABLE
        qos.durability = DurabilityPolicy.VOLATILE
        qos.history = HistoryPolicy.KEEP_LAST
        qos.depth = 1                       # 覆盖基座 depth：控制只要最新一条
        # lifespan：旧指令在中间件层自动作废，拥塞时的"指令保质期"
        qos.lifespan = Duration(seconds=0.2)
        self.pub = self.create_publisher(Twist, "cmd_vel", qos)
        self.create_timer(0.01, self.tick)  # 100 Hz 控制流（第 002 章频率档）

    def tick(self):
        msg = Twist()
        msg.linear.x = 0.0                  # 简化示例：真实值来自上游决策模块
        self.pub.publish(msg)

解读：（1）这个片段展示"基座 + 覆盖"的写法：先取一个稳定起点，再把与业务语义相关的字段逐条显式化，每条覆盖在评审时都能被追问"为什么"，不留隐性默认。（2）lifespan=0.2 s 的推理链值得复述：控制周期 10 ms，物理上超过 200 ms 的旧指令执行起来已经危险（0.2 s × 1 m/s = 20 cm 位移差），所以中间件层直接作废，把第 011 章"旧指令有害"从设计直觉升级为机制保证。（3）同时注意 depth 与 lifespan 的层次差：depth 管"留几条"，lifespan 管"留多久"；两者对"陈旧数据"从不同维度设闸，可组合使用。

片段 3：CLI，合同核对与兼容性实验

ros2 topic list -t                    # 先确认话题名与类型，再谈 QoS 合同
# 端点级合同快照：每个发布者/订阅者的完整 QoS 逐行对照
ros2 topic info /robot1/cmd_vel --verbose
# 排障顺序提醒：先确认"发现了"（能用 node info 看到两端），再比对合同；
# 域/命名问题（第 007、010 章）不会有 QoS 层面任何线索
# 兼容性实验：故意制造一次不匹配，感受"静默"（对 Best-effort 话题用 Reliable 订阅）
ros2 topic echo /robot1/scan --qos-reliability reliable        # 什么都不会打印
ros2 topic echo /robot1/scan --qos-reliability best_effort     # 数据正常出现

解读：这组命令示范了"先发现、后合同"的排查顺序，QoS 是第二道门，别在门前排错队。两步兼容实验是本章最有教育意义的小练习：对 Best-effort 发布端用 Reliable 请求，echo 静默无输出且没有任何错误提示；换成 best_effort，数据立刻出现。亲手复现一次"静默"，以后在 20 台机器人的图里看到同样症状，你会直接去查合同，网络不再是第一嫌疑。

常见坑

  • 以为 history/depth 参与匹配：担心"两端 depth 不同会不匹配"而反复调参。事实：history 是本地资源，不参与兼容判定；晚到补发的条数差异是数据行为，不是连接问题。
  • CLI 工具 QoS 与话题不符：对 sensor data 类话题直接 echo 可能什么都看不到，误判"话题没数据"。修复：显式加 --qos-reliability best_effort；记住工具默认档不一定兼容你的端点。
  • 配置复制粘贴分叉：发布端改成 Reliable，订阅端还是两天前的副本。修复：两端共享同一份 QoS 定义模块（同一函数生成），变更单点化。
  • deadline 拍得过紧：把 deadline 设成等于标称周期（50 Hz 话题设 20 ms），网络每次抖动都触发违约事件，告警里全是噪声。修复：deadline = 正常周期 × 2–3，先测一周的真实抖动再收紧。
  • lifespan 设置后"数据丢了"的误诊：拥塞或接收端重启期间，旧样本被 lifespan 作废，验收脚本看到"缺口"以为丢包。修复：把 lifespan 写进设计表并让验收脚本感知，"缺口是设计行为"，但必须与真实丢失可区分（看 QoS 事件与统计）。

练习与思考

  1. 矩阵推演：判断匹配并说明方向，(a) 发布 Deadline 100 ms + 订阅要求 200 ms；(b) 发布 Deadline 200 ms + 订阅要求 100 ms；(c) 发布 MANUAL_BY_PARTICIPANT + 订阅 AUTOMATIC；(d) 发布 AUTOMATIC + 订阅 MANUAL_BY_TOPIC。★
    提示
    (a) 匹配（承诺比要求快）；(b) 不匹配；(c) 匹配（提供更强）；(d) 不匹配（订阅要求高于提供）。与可靠性/持久性同一套"要求 ≤ 提供"逻辑。
  2. 预测题：给 /robot1/scan（Best-effort 发布）写一个 Reliable 订阅者发布端不变。预测三件事：订阅者收不收到数据、发布端日志、ros2 topic info --verbose 里订阅者计数。然后给出两种修法。★
    提示
    收不到；双方默认无日志（除非注册了事件回调）；计数显示订阅者存在但不匹配。修法：订阅端降为 Best-effort，或发布端升为 Reliable（后者有带宽代价，慎用）。
  3. 设计题：给"地图话题 + 遥控面板"补全 QoS：面板偶尔会断开重连，要求重连后立刻看到当前地图；给出面板订阅端的 QoS 设计（含 depth 与理由），并说明为什么它必须请求 TL 而不能只靠发布端。 ★★
    提示
    面板请求 Reliable + TL + keep-last(1)：重连=晚加入，只有订阅端明确请求 TL，DDS 才会走历史补发流程；只配发布端 TL、订阅端 Volatile 时匹配虽成立，但"补发"不会发生。
  4. 推导题：某话题正常周期 20 ms、抖动 p99 为 15 ms。deadline 设多少能在"既不误报又能检测真故障"之间取平衡？若话题实际停更（发布端死了），多久后订阅端收到 deadline 事件？★★
    提示
    p99 抖动 15 ms 说明偶尔会有 ~35 ms 的到达间隔，deadline 取 2–3 倍周期即 40–60 ms；停更后事件在 deadline 时长（40–60 ms）后触发，比应用层心跳（秒级）快一个量级。
  5. 评审题：某团队给所有话题统一配了"Reliable + TL + depth 50"的"万能方案"，请从语义、内存、突刺、重传代价四个角度各写一条反对意见，并给出修正原则。★★★
    提示
    语义：控制指令不需要 TL（旧指令有害）；内存：每个话题常驻 50 条历史；突刺：晚加入者收 50 条历史；重传：感知流白白重传。修正原则：逐话题五问，禁止"一刀切"。

小结

  • 兼容判定统一为"要求 ≤ 提供"；Reliability/Durability/Deadline/Liveliness 都遵循此逻辑，细节差异查对应版本文档。
  • history/depth 是本地资源，不参与匹配；不匹配在"发现之后"判定，排查顺序是先发现、后合同。
  • 不匹配事件回调把静默故障变成显式告警；两端 QoS 定义共享同源，杜绝复制分叉。
  • 预置 profile 是基座不是信仰；选型用五问决策树：账本？晚到？几条？按时？过期？
  • 进阶三件套各有适用：deadline 管时效承诺、liveliness 管存活声明、lifespan 管陈旧作废，用声明代替代码，但要写清理由。
