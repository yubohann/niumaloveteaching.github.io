第二篇 · 数据分发与协同感知

第 039 章：系统级健康监测与告警

20 台机器人的系统里，最贵的故障是"某台悄悄掉线"。本章把"看一眼"升级为"持续盯着"：心跳看门狗、频率监测、分级状态机与可行动的告警。

  • 主题：系统工程 / 可观测性与告警
  • 关键机制：心跳看门狗、静默故障检测（频率/新鲜度）、诊断标准消息、状态机与去抖
  • 预计学时：55 分钟
  • 前置章节：第 038 章（通信可视化：rqt与Foxglove）

学习目标

  • 建立系统健康的六维清单：存活、数据流、新鲜度、资源、网络、业务进度。
  • 掌握看门狗设计：心跳频率与超时推导、分级状态机、去抖（迟滞）与恢复判定。
  • 会用 diagnostics 标准体系发布与消费健康状态，理解它与自定义看门狗的分工。
  • 掌握频域诊断：滑动窗口频率估计如何发现"节点活着但话题停了"的静默故障。
  • 能设计"可行动"的告警：分级、去重、抑制风暴、绑定处置动作，避免告警疲劳。

背景与动机

第 038 章的工具人能用，但人不能一直盯着，夜班、无人值守、多现场并行时，系统必须自己报告"我不对劲了"。多机器人系统里最危险的故障恰恰是最安静的：节点进程还在、话题不再更新（僵死）、某台机器人的定位悄悄漂移（数值全对但全错）、网络带宽悄悄被占满（一切都在，就是慢）。这些"静默故障"不会让系统崩溃，只会让它在错误的方向上稳定运行，直到撞上南墙。

健康监测（health monitoring）与告警（alerting）把它变成工程问题：定义指标 → 持续采集 → 状态判定 → 分级响应。本章沿用第 035/036 章的心跳与逻辑时钟等构件，但视角从"通信机制"切换到"系统运维"：目标是让任何一次异常都能在几十秒内变成一条明确、可处置的告警，并为第 040 章阶段项目的验收（掉线恢复）提供测量手段。

核心原理

1. 健康的六个维度

维度指标示例故障类型检测手段
存活心跳到达间隔进程挂死、断电、断网心跳看门狗（本机与跨机）
数据流话题频率、条目间隔僵尸节点（活着不发）频率监测（滑动窗口）
新鲜度数据时间戳与当前时间差时间源错、回放忘记切换时间差统计（第 030 章构件）
资源CPU/内存/磁盘/温度/电量泄漏、写满、过热系统探针 + 阈值
网络丢包率、RTT、带宽拥塞、干扰、分区链路监测（第 035/036 章构件）
业务任务进度、队形误差卡死、原地打转业务指标探针（应用层）

六个维度里，存活和数据流是根基，它们回答"最基本的通信是否成立"；业务维度则回答"通信成立但事情做成没有"。健康监测系统的设计顺序也照此：先把心跳与频率做扎实，再往上叠。

2. 看门狗：心跳频率与超时阈值的推导

看门狗（watchdog）是"定期喂狗、超时报警"的模式：被监测方周期性发心跳，监测方在超时窗口内未收到就判定异常。两个参数的推导：

心跳周期 T = 1–2 s；超时阈值 = T × 3 + 网络延迟上界 T × 3 给两次连续丢失的容忍；网络延迟上界（如 50 ms）加在最外层，阈值过紧会把抖动误判为故障

心跳消息应该极小（几十字节）且语义单纯（"我还活着"，不带业务数据），把业务数据的生死判断混进心跳，会让"心跳到了但数据是旧的"这种中间态失去表达。多机器人系统还有"跨机看门狗"的一层：每台机器人不仅要有本机看门狗（监测自己的节点），还要有车队看门狗（监测其他机器人的心跳），第 036 章的心跳分区检测器干的就是这件事，本章把它与"节点级看门狗"统一到同一套状态模型里。

心跳的带宽账顺手算掉：20 台机器人、每台 2 Hz、每条 80 B，车队心跳总流量 20 × 2 × 80 = 3.2 KB/s，完全可忽略；这也支持把心跳做成"人人可见的广播"（只报给中心的方案会在中心缺席时失明）：中心节点不在时，监测体系仍然成立，与第 034 章的星形路由形成互补关系。

3. 静默故障：频率与时新度的量化

僵尸节点不听不看不会报错，唯一的信号是"该来的数据没来"。两种检测器：

  • 频率监测（rate monitor）：用滑动窗口数消息数，估算实时频率；低于"期望频率 × 0.5"持续数秒 → 告警。为什么要连续数秒：频率是统计量，短窗波动是常态（调度抖动、突发丢包都会造成瞬时低谷），用"瞬时阈值"报警必然误报。
  • 时新度监测（freshness monitor）：检查消息时间戳与当前时间的差；超过"周期 × 3" → 数据已过期。它与频率监测互补：频率正常但数据时间戳不前进（例如驱动读了缓存）时，只有时新度能发现。

阈值设计的一个通用纪律：监测器的阈值必须与"业务能容忍的不良时长"挂钩；"消息周期"只决定采样与心跳的节奏。业务能容忍 5 秒无数据，就按 5 秒报；业务只能容忍 0.5 秒，那监测频率本身就要提速。

检测器捕捉什么漏掉什么典型参数
心跳看门狗进程死亡、断网进程活着但不干活1–2 Hz，阈值 3 周期加延迟上界
频率监测僵尸节点、停发、降频时间戳不前进（缓存复读）窗口 20 样本，低于期望 50% 判 ERROR
时新度监测数据陈旧、时间基异常频率极低但时间戳新鲜的部分失效流超过周期 × 3 判过期

4. 状态机与去抖：告警必须"稳"

每个被监测对象的健康状态用一个四级状态机表达：

状态含义典型触发响应
OK一切正常—无
WARN指标越界但功能可用频率 50%–90%、丢包 3%–10%记录 + 面板提示；准备降级
ERROR功能受损频率 < 50%、心跳 miss ≥ 3告警 + 触发降级（降频/隔离/切换）
STALE数据完全过期超时窗口 × 2 无数据强告警 + 安全策略（停止动作）

去抖（debounce）在两条边上都要有：升级条件（连续 N 次采样越界才升级，防瞬时脉冲）与降级条件（连续 M 次采样正常才降，防"刚恢复又断"的横跳）。与第 036 章分区检测的迟滞是同一个模式，信号越接近阈值，越需要用"持续时间"来确认真实性。

5. 数值算例：检测延迟与误报率的完整账

先算检测延迟。以片段 1 的参数为例：期望 50 Hz 的话题、窗口 20 个样本、评估周期 1 s、去抖需要连续 3 个异常窗口。窗口填满需要 20 ÷ 50 = 0.4 s，异常确认需要 3 × 1 = 3 s，合计约 3.4 s 从"停发"到"ERROR 告警"。心跳看门狗的账类似：心跳 1 Hz、阈值 3.05 s，检测延迟约 3 s。两类检测的延迟都在"秒级"，这正是与业务容忍度对齐后的结果：要求 1 秒内发现故障，就得把评估周期与去抖计数都压到亚秒级，误报率随之上升，两个参数是同一个预算的两面。

再算误报。频率是统计量，窗口越小噪声越大。对泊松式到达的事件流，用 N 个样本估计频率的相对标准差约为 1 ÷ √N：要在 3σ 置信下区分"正常"与"掉了 10%"两档，需要 N ≥ 900 个样本；而准周期的传感器流（定时器发布）抖动通常只有百分之几，20 个样本的窗口足够稳定。阈值 0.9 用在传感器流上安全，用在事件流上会频繁误报：工程做法是对事件流类话题放宽 WARN 档（如 0.5），或改用"长时间无消息"的时新度判据，别让统计噪声伪装成故障。

6. 失效模式与边界条件

失效模式表现根因修复
看门狗假活节点早已僵死，健康状态却是 OK心跳由别的进程代发，或心跳不含时间戳心跳携带测量时刻并检查时新度（片段 1）
阈值漂移上线数月后告警频发，无人处理阈值按上线初期的网络质量设定，环境变化后未复核定期复核阈值；把告警率本身作为被监控指标
静默窗口吞真警报抑制期间一个独立的新故障没有告警静默窗口只按时间屏蔽，未按对象区分静默只作用于同一根因组，新对象与新类别照常告警
恢复判定过松状态在 OK 与 ERROR 间反复横跳只要求一个正常窗口就恢复恢复需连续 M 个正常窗口，与升级对称的迟滞

还有两个设计边界要写进文档：监测系统自身也要被监测（聚合器心跳、告警通道连通性都要有独立探针，否则"没有告警"既可能是系统健康，也可能是监测已经死掉）；阈值不是越灵敏越好，告警系统的健康指标应包括告警率与误报率（例如目标每天不超过 5 条需要人工处理的告警），把"告警疲劳"当作可量化的工程指标来管理。指标的采集频率与保留时长也要写进配置，采集不是越多越好，存储与检索成本同样是运维预算的一部分。

实现思路与设计

  1. 定义指标清单：按六维列出监测点、期望值、阈值、响应动作，一页纸表格（下表示意）。
  2. 实现采集器：本机节点心跳（1–2 Hz）、话题频率与时新度监测（复用 diagnostics 或自建）。
  3. 实现聚合器：汇总全队状态，做状态机与去抖，产出"车队健康摘要"（每机一行 + 明细）。
  4. 接线响应：告警不只发消息，绑定动作：降频、切任务、退编队、安全停。（动作的编排见第 064 章行为树。）
  5. 防疲劳：告警去重（同一对象同一等级只在状态变化时发）、抑制风暴（全队大面积异常时只发一条"系统级"告警）、静默窗口。

告警通道本身要有冗余与降级：主通道（WebSocket 或消息总线）不可用时退到备用通道（邮件、短信、现场声光装置）；关键告警要求送达确认，普通告警允许尽力而为。把告警按"需要人立刻行动 / 需要人知晓 / 仅记录"三档分流，能让通道容量与人的注意力都用在正确的地方。

指标期望/阈值判定响应
节点心跳1–2 Hz；miss ≥ 3进程级 STALE重启节点（生命周期管理）/ 记 ERROR

关键代码与解读

片段 1：频率 + 时新度监测器（把静默故障变成信号）

import time
from collections import deque

class TopicHealth:
    """监测一个话题：频率（滑动窗口）与时新度（时间戳差），带去抖计数。"""
    def __init__(self, expected_hz, window=20, warn_ratio=0.9, err_ratio=0.5):
        self.period = 1.0 / expected_hz
        self.window = window                     # 最近 N 个到达间隔
        self.arrivals = deque(maxlen=window)
        self.warn_ratio, self.err_ratio = warn_ratio, err_ratio
        self.bad_windows = 0                     # 连续异常窗口计数（去抖）
        self.state = "OK"

    def on_msg(self, stamp_ns):
        now = time.monotonic()
        self.arrivals.append(now)
        # 时新度：消息时间戳与本地时钟的差（两机已做时间同步）
        age = now - stamp_ns * 1e-9 if stamp_ns > 0 else 0.0
        if age > self.period * 3:                # 数据已过期
            self.stale_now = True
        else:
            self.stale_now = False

    def evaluate(self):
        """周期性评估：用窗口内实际频率对比期望频率，输出状态。"""
        if len(self.arrivals) < 2:
            return self.state
        span = self.arrivals[-1] - self.arrivals[0]
        hz = (len(self.arrivals) - 1) / span if span > 0 else 0.0
        ratio = hz / (1.0 / self.period)
        if getattr(self, "stale_now", False) or ratio <= self.err_ratio:
            level = "ERROR"
        elif ratio <= self.warn_ratio:
            level = "WARN"
        else:
            level = "OK"
        # 去抖：连续 3 个评估窗异常才升级；连续 3 个正常才恢复
        self.bad_windows = self.bad_windows + 1 if level != "OK" else 0
        if self.bad_windows >= 3:
            self.state = "ERROR" if level == "ERROR" else "WARN"
        elif level == "OK" and self.bad_windows == 0:
            self.state = "OK"
        return self.state

解读：这个监测器把"看不见的停发"变成可判定的信号。（1）频率估计用"窗口内（到达数−1）÷ 时间跨度"；"1 ÷ 平均间隔"的写法对单次大间隔过于敏感（一个 500 ms 的空档会把平均间隔算歪），前者是真正的窗口速率。（2）时新度独立于频率：即使频率正常，时间戳不前进也判 ERROR，这捕捉"驱动读了缓存"之类的隐性异常。（3）去抖用"连续 3 个评估窗"：注意 bad_windows 在正常时清零、异常时累加，只有累计到 3 才升级；恢复需要 level == "OK" 且归零，升级与恢复都要求"持续证据"。（4）评估频率本身要合理：每 1–2 秒评估一次、窗口 20 个样本，意味着判定延迟在秒级，这就是"监测可以慢一点、误报必须少一点"的取舍。生产实现可直接采用 diagnostic_updater 的标准框架（片段 3），自建的价值在于理解每一层阈值与去抖的来路。

片段 2：车队聚合器，从"每台的状态"到"一条告警"

class FleetAggregator(Node):
    """汇总全队健康：状态机 + 去重 + 风暴抑制，产出可行动的车队摘要。"""
    def __init__(self, n_robots=20):
        super().__init__("fleet_aggregator")
        self.robots = {f"robot{r}": {"state": "OK", "since": 0.0} 
                       for r in range(1, n_robots + 1)}
        self.pub = self.create_publisher(FleetHealth, "/fleet/health", 10)
        self.create_timer(1.0, self.publish_summary)

    def on_robot_report(self, rid, level, reason):
        r = self.robots[rid]
        if level != r["state"]:
            # 只在状态"变化"时发告警：重复的相同告警是疲劳的来源
            r["state"], r["since"] = level, time.time()
            self.emit_alert(rid, level, reason)

    def publish_summary(self):
        msg = FleetHealth()
        msg.header.stamp = self.get_clock().now().to_msg()
        ok = sum(1 for r in self.robots.values() if r["state"] == "OK")
        msg.ok_count = ok
        msg.total = len(self.robots)
        # 风暴抑制：大面积异常时只发一条"系统级"告警，遮挡个体噪声
        if msg.total - ok >= 5:
            msg.summary = f"系统级异常：{msg.total - ok} 台受影响"
            self.pub.publish(msg)
            self.suppress_until = time.time() + 30.0    # 静默窗口 30 s
            return
        msg.summary = " | ".join(f"{k}:{v['state']}" for k, v in self.robots.items()
                                 if v["state"] != "OK") or "全部正常"
        self.pub.publish(msg)

    def emit_alert(self, rid, level, reason):
        # 告警 = 状态 + 对象 + 原因 + 建议动作：没有"动作"的告警不可行动
        self.get_logger().warn(f"[{level}] {rid}: {reason} -> 检查链路/定位/资源")

解读：聚合器的三个机制对应告警工程的三条戒律。（1）on_robot_report 里"状态变化才发"：告警系统最常见的设计错误是"每个周期重复播报同一异常"，运维在三天后就会把它当背景噪音，告警的正确语义是"状态迁移事件"，不是"状态轮询输出"。（2）风暴抑制：20 台里 6 台同时断，多半是共同原因（网关、交换机、频段干扰）；聚合器把个体告警折叠成一条系统级告警并进入 30 秒静默窗口，留时间给人处理共性原因，避免告警刷屏。（3）emit_alert 的格式（对象 + 原因 + 建议动作）是"可行动"的最小结构：只报"robot7 出错"无法处置，报"robot7 ERROR：心跳 miss 4 → 检查链路/定位/资源"才能把人引向正确的下一步。告警文案是被低估的工程资产，值得像 API 一样评审与版本管理。

片段 3：用标准 diagnostics 发布频率诊断（生态兼容做法）

from diagnostic_msgs.msg import DiagnosticStatus
from diagnostic_updater import Updater

class DiagNode(Node):
    """标准诊断栈：/diagnostics 话题 + rqt_runtime_monitor 面板直接可见。"""
    def __init__(self):
        super().__init__("diag_node")
        self.updater = Updater(self)             # 构造签名随发行版略有差异
        self.updater.setHardwareID("robot1")
        self.msg_count = 0
        self.create_subscription(MyState, "/robot1/state", self.on_state, 50)
        # 注册周期任务：每 2 秒自动汇总一次，发布 DiagnosticArray
        self.updater.add("state_rate", self.check_state_rate)

    def on_state(self, _msg):
        self.msg_count += 1                      # 只做计数，评估在任务里做

    def check_state_rate(self, stat):
        # 期望 50 Hz：用 2 秒窗口估算实际频率并写回诊断状态
        hz = self.msg_count / 2.0
        self.msg_count = 0
        stat.add("expected_hz", 50.0)            # 诊断项做成键值对：可查询可绘图
        stat.add("actual_hz", f"{hz:.1f}")
        if hz < 10.0:
            stat.summary(DiagnosticStatus.ERROR, "状态流几乎停发")
        elif hz < 40.0:
            stat.summary(DiagnosticStatus.WARN, "状态流频率不足")
        else:
            stat.summary(DiagnosticStatus.OK, "正常")
        return stat

解读：标准诊断栈的价值在"生态"：/diagnostics 是 ROS 生态约定的健康话题，任何符合约定的监控面板（rqt_runtime_monitor、Foxglove、车队面板）都能直接消费，不必为每套自研监测再写一个前端。（1）stat.add 的键值对既是展示也是数据源：把 expected/actual 都写进去，下游可以做曲线与报表，比只发一个 OK/ERROR 布尔值信息量大得多。（2）任务函数里"计数换频率"的模式：回调只做 O(1) 的计数，评估放在低频任务里，避免在消息回调里做统计计算（回调是热路径）。（3）阈值分层与自建监测器一致（ERROR < 10、WARN < 40、OK 其余）：无论用哪套框架，"分级 + 迟滞"的判定逻辑没有捷径。（4）Python 侧 Updater 的构造参数（是否显式传周期等）在各发行版间有差异，以对应版本文档为准，这是本章第二处版本提示，因为诊断 API 正是随发行版演进而来的。

常见坑

  • 只看节点在不在，不看话题动没动：僵尸节点被漏检。修复：频率 + 时新度监测（片段 1）。
  • 阈值拍得太紧：网络抖动即告警，三天后全员无视告警。修复：迟滞 + 连续证据（升级/恢复都要持续条件）；阈值与业务容忍度挂钩。
  • 告警不绑定动作：告警只发不处置，等于多了一堆噪音。修复：每条告警配"预期处置"，能自动化的自动化（降频、隔离、回充）。
  • 用"收到消息"判定心跳，但没看消息时间戳：回放或重复消息让看门狗"假活"。修复：心跳判定基于消息时间戳与本地时钟差（时新度），杜绝单纯按"收到消息"判定。
  • 告警风暴没有抑制：共同原因触发 20 条告警，处理人被淹没。修复：聚合器做折叠与静默窗口（片段 2），把"根因级的少数告警"暴露给处理人。

练习与思考

  1. 推导：心跳周期 1 s、网络延迟上界 50 ms。超时阈值应取多少？如果业务能容忍的最长"沉默"是 2 s，你的参数该如何调整？★
    提示
    阈值 ≈ 3 × 1 s + 50 ms = 3.05 s；若业务最多容忍 2 s，则心跳周期要降到约 0.6 s（3T + 0.05 ≤ 2）。
  2. 把频率监测的"连续 3 窗"改到"连续 1 窗"，预测正常网络下误报率与故障检测延迟的变化，并给出你的折中。★★
    提示
    1 窗判定让任意一个低谷直接报警；3 窗需要约 3 秒持续异常才报。误报代价高（告警疲劳）时用更长窗口；安全关键链路可以更灵敏并配合快速恢复。
  3. 设计实验：人为让一个话题"僵尸化"（进程还在、停发数据），测量从停发到 ERROR 告警的时间，与设计值对比。★★
    提示
    预期检测时间 ≈ 窗口样本数 ÷ 期望频率 + 评估周期 × 去抖计数；若实测更长，检查评估周期与窗口大小。
  4. 设计题：为第 040 章阶段项目设计"健康监测清单"：十个以内指标、各自阈值与响应动作、谁负责采集、告警文案。★★★
    提示
    从六维各取 1–2 个关键指标即可起步；响应动作力求自动化（降频/隔离/回充），文案含对象+原因+建议。
  5. 思考：为什么说"没有动作的告警是技术债"？举一个你系统中"告警响过但没人知道该干嘛"的例子，写出它的处置动作。★★★
    提示
    告警的消费端是人或自动化流程；若两者都没有对应动作，告警只会消耗信任。处置动作可以是巡检命令、自动降级、或明确的"忽略并记录"（后者也应写明）。

小结

  • 健康六维：存活、数据流、新鲜度、资源、网络、业务；先做扎实存活与数据流，再向上叠加。
  • 看门狗参数推导：心跳 1–2 Hz、阈值 = 3 个周期 + 网络延迟上界；心跳消息保持极小且语义单纯。
  • 静默故障靠频率 + 时新度两条腿：窗口速率防毛刺、时间戳差抓隐性异常；判定一律加去抖。
  • 状态机四级（OK/WARN/ERROR/STALE）+ 双向迟滞；告警是"状态迁移事件"，可行动是底线要求。
  • 下一章把第二篇的所有机制拧成一个系统：阶段项目：协同建图与状态共享，完整架构、集成步骤与可量化的验收指标。
