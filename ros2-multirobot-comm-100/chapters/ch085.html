第四篇 · 系统集成与工程化

第 085 章：阶段项目：带故障恢复的任务系统

第四篇闭环：把任务池、心跳监视、租约重分配、降级模式焊成一个 4 台机器人的任务系统，并用故障注入实验逐项验收，完成率、恢复时间、零重复执行。

  • 主题：系统集成与工程化（第四篇阶段项目）
  • 关键机制：任务生命周期、心跳检测、租约重分配、幂等执行、降级模式
  • 预计学时：90 分钟（含动手）
  • 前置章节：第 084 章

学习目标

  • 把第四篇的各机制（任务分配、优先级、故障检测、动态重构、配置管理）集成为一个可运行的 4 机器人任务系统。
  • 掌握"租约（lease）+ 心跳（heartbeat）"的故障恢复组合：为什么心跳负责"发现"，租约负责"收回"，两者职责不能混淆。
  • 会为任务生命周期设计状态机与幂等执行，杜绝"重分配导致同一任务被做两遍"。
  • 能设计并执行故障注入实验矩阵（三种故障 × 三个时机 × 多次重复），产出可信的验收数据。
  • 交出一份含量化指标的验收报告：完成率、故障检出时间、重分配时间、重复执行率、降级切换时延、makespan 劣化。

背景与动机

单点技术你已经分别练过了：任务分配（第 066 章）、优先级（第 068 章）、故障检测与恢复（第 074 章）、动态重构（第 075 章）、版本与配置（第 081 章）。但工程系统的难点从来都在把它们接起来之后冒出来的新问题，单项技术本身早已分别练过：重分配时任务会不会被做两遍？监视器误判一次会不会引发全队抢单大战？机器人复联后它的旧状态会不会污染新任务？

本项目就是把这些"接缝问题"暴露出来并逐一定刑。场景设定：4 台差速轮式机器人在 10 m × 10 m 的仿真场地里执行 20 个取送任务（取货点 → 卸货点），任务池统一派单，任意一台机器人可能在任意时刻"失联"（进程崩溃、网络中断或急停），系统必须在几秒内把它的未完成任务转交他人，且不乱、不重、不停摆。

本项目同时是第四篇的验收门槛：过不了本章的指标，说明前面某章的机制只停留在"能跑 demo"，没有到"能交付"。

核心原理

1. 任务生命周期：状态机是第一件设计

系统中每个任务在任何时刻必须处于且仅处于一个状态：待派（PENDING）→ 已派（ASSIGNED）→ 执行中（EXECUTING）→ 完成（DONE），加上两个异常终态：失败（FAILED，执行了但没成功）与撤销（ABORTED，执行前被收回）。状态迁移只能沿箭头走，每条迁移都要有触发者与凭据（谁能把 ASSIGNED 改成 EXECUTING？只有持租约的机器人）。状态机的价值在于：分布式系统的混乱几乎都能追到"某个对象的状态没有单一权威"，任务状态由任务池统一维护，机器人只上报事实，不自行宣布任务完成后的去向。

完成率 = DONE / 总任务数；重复执行率 = 被两个不同机器人执行过的任务数 / 总任务数 重复执行率必须是 0，这是重分配机制是否设计正确的试金石

2. 心跳：负责"发现"；租约：负责"收回"

职责分离是本项目最重要的一个设计决策。心跳（heartbeat）是周期性的"我还活着"消息（建议 2 Hz，32 字节级），监视器若 timeout = 2.0 s 没收到某机器人心跳，判定其"疑似死亡"。为什么 timeout 取 4 个心跳周期？取 1 个会怎样？因为无线网络偶发丢几拍是常态：timeout 约等于周期时误报率极高，一次误报就可能触发全队抢单。检测时延与误报率是一对矛盾：

检出时延 ∈ [timeout − 周期, timeout]；误报率 ≈ P(连续 k 拍心跳丢失)，k = timeout / 周期 周期 0.5 s、timeout 2.0 s → 检出时延 1.5–2.0 s；连续 4 拍全丢在稳定 WiFi 上概率约 10⁻⁶ 量级（工程按 10⁻⁴ 估算留余量）

但"发现死亡"不等于"敢收回任务"，如果监视器一发话就把任务转给别人，而原机器人其实只是网络卡了一下，它复活后就会和别人抢着做同一个任务。解法是租约：任务被机器人领取时，任务池给出一个到期时间（如 10 s），持有者必须周期性续租（如每 2 s 一次），租约到期不续，任务自动回到可派状态。租约把"谁拥有任务"的裁决权放在任务池的时间轴上；若改为依赖各机器人对故障判断的一致，就需要共识，昂贵且缓慢。

3. 幂等执行：对抗"至少一次"语义的必然产物

重分配机制的天然语义是"至少一次"（at-least-once）：任务可能被原持有者做完但上报丢包、也可能被新持有者重做。要保证业务语义上是"恰好一次"，标准手法是幂等执行：每个任务有唯一 task_id，执行端记录"已完成的 task_id 集合"；任务池收到 DONE 上报时，若该任务已被标记完成，则忽略重复上报。真正危险的是两边都真的执行了（重复上报无害），所以执行端还有一个纪律：上报前检查任务是否仍属于自己（租约是否还有效），租约被收回则立刻停手并回滚到安全状态。角度差一点点：宁可让任务多花几秒被别人重新做一遍，也不能让两台机器人同时做同一取送动作。

4. 降级模式：分区时的保守行为

当机器人发现自己与任务池失联（连续未收到任务池广播或服务调用超时），不能傻站在那儿等：进入降级模式，停止接受新任务、完成当前任务后原地待命、速度上限减半、保留本地避障。降级模式的三条原则：行为可预测（别人知道你会干什么）、安全优先（慢即安全）、可恢复（保持重连尝试并上报回归）。恢复连接后由任务池下发全量状态快照；分区期间双方的状态都可能变过，增量同步的基准已不可信。

实现思路与设计

系统由四个逻辑组件组成，全部挂在同一个 ROS2 域与命名空间约定下（/fleet/... 车队级，/robotN/... 机器人级）。

组件所在职责接口（话题/服务）
任务池 task_pool中心（可兼任）任务队列、租约发放与过期回收/fleet/claim(服务)、/fleet/renew(服务)
执行端 executor每台机器人心跳、领任务、幂等执行、状态上报/fleet/heartbeat(话题 2 Hz)、/fleet/status(事件)
监视器 supervisor中心或任一机心跳超时判定、触发提醒订阅心跳、发布 /fleet/alerts
指标记录器 metrics中心事件打点：领取/完成/超时/重分配订阅状态与告警，落盘 CSV

接口设计的三个决定及其理由：（1）领取与续租用服务（不用话题），它们是"请求-应答"语义，必须知道成功与否，且天然串行化（任务池单点串行处理，避免并发抢单竞态）。（2）心跳用 Best-effort + 小消息，丢一两拍没关系（下一拍 0.5 s 后到），用可靠重传反而在拥塞时加剧拥塞。（3）状态上报用事件驱动，只在状态迁移时发，别做成周期流：一天 20 个任务不该产生上万条状态消息。

关键代码与解读

片段 1：带租约的任务池，领取、续租、到期回收

class LeaseTaskPool:
    """任务池：任务以租约形式"被租用"：租约到期自动回到可派状态。"""
    def __init__(self, lease_sec=10.0):
        self.lease_sec = lease_sec         # = 5 倍心跳超时（2 s）：容忍连续多拍丢失
        self.pending = {}                  # task_id -> payload（未完成任务）
        self.leases = {}                   # task_id -> (robot_id, expire_at)

    def is_available(self, tid, now):
        holder = self.leases.get(tid)
        # 无租约或租约已过期 → 可派；过期即回收，无需任何"死亡确认"流程
        return holder is None or holder[1] < now

    def claim(self, robot_id, now):
        for tid in sorted(self.pending):   # 排序保证高速并发下派单顺序确定
            if self.is_available(tid, now):
                self.leases[tid] = (robot_id, now + self.lease_sec)
                return tid, self.pending[tid]
        return None, None

    def renew(self, tid, robot_id, now):
        holder = self.leases.get(tid)
        if holder and holder[0] == robot_id:   # 只有现持有者能续租，防抢单
            self.leases[tid] = (robot_id, now + self.lease_sec)
            return True
        return False

    def finish(self, tid):
        self.leases.pop(tid, None)         # 完成后立即释放租约并从队列移除
        self.pending.pop(tid, None)

解读：claim 只在租约过期后允许领取，这条规则把"重分配"从特殊流程降级成普通流程：新机器人根本不需要知道前任死没死，它只是在租约过期后正常领单。这就是租约机制最优雅的地方：把分布式故障问题转化成了本地时间问题。sorted(self.pending) 让派单顺序可复现（调试与验收都要求确定性）。finish 在收到 DONE 时调用；如果原持有者其实还活着但租约被别人拿走（网络分区过长），它下一次 renew 会失败（holder 已换人），必须立刻停手，这条协议写在了执行端（片段 3）。

片段 2：心跳监视，超时判定与"只报一次"

class HeartbeatMonitor:
    """心跳监视器：记录每台机器人的最近到达时刻，超时则报告。"""
    def __init__(self, timeout=2.0):
        self.timeout = timeout             # 4 个心跳周期：权衡检出时延与误报
        self.last_seen = {}                # robot_id -> 本地接收时刻

    def on_heartbeat(self, robot_id, now):
        # 用"本地接收时刻"，不用消息里的发送时间戳：
        # 发送端时钟可疑（甚至它卡死后时间戳不再前进）时更稳健
        self.last_seen[robot_id] = now

    def check(self, now):
        dead = []
        for rid, t0 in list(self.last_seen.items()):
            if now - t0 > self.timeout:
                dead.append(rid)
                del self.last_seen[rid]    # 移除：同一故障只报警一次
        return dead

解读：两个工程细节。（1）用本地接收时刻：如果用心跳消息里的发送端时间戳，"时钟不同步"和"机器人卡死"会难以区分；用本地钟只看"有没有按时到达"，判据单一且不依赖对端时钟。（2）报警即移除记录：防止每个检查周期重复报同一台死亡机器人（报警风暴）。移除后若该机器人恢复心跳（复联），on_heartbeat 会重新登记它，监视器不需要"复活"特殊逻辑。注意监视器只负责发现并广播信息，不直接改任务状态：任务状态只有任务池能动，避免多脑决策。

片段 3：执行端主循环，心跳、续租、幂等、让手

class RobotExecutor:
    """执行端：一条主循环把"活着、持有、干活、上报"四件事串起来。"""
    def __init__(self, robot_id, pool, hb_pub, status_pub):
        self.rid, self.pool = robot_id, pool
        self.hb_pub, self.status_pub = hb_pub, status_pub
        self.done_tasks = set()            # 已完成 task_id：幂等去重的依据
        self.current = None                # (task_id, payload)

    def tick(self, now):
        self.hb_pub.publish(heartbeat_msg(self.rid))          # 2 Hz 心跳
        if self.current is None:
            tid, payload = self.pool.claim(self.rid, now)
            if tid is not None:
                self.current = (tid, payload)
                self.status_pub.publish(status_msg(tid, "EXECUTING"))
            return
        tid, _ = self.current
        if not self.pool.renew(tid, self.rid, now):
            # 续租失败 = 租约已被收回（自己曾被判死）：立即让手，不许继续
            self.current = None
            return
        if self.task_input_missing():
            # 急停/卡死类故障：执行超时后任务池也会回收，这里主动放弃更干净
            self.status_pub.publish(status_msg(tid, "ABORTED"))
            self.current = None
            return
        if self.is_finished(tid):
            if tid not in self.done_tasks:     # 幂等：重复完成只上报一次
                self.status_pub.publish(status_msg(tid, "DONE"))
                self.done_tasks.add(tid)
            self.pool.finish(tid)
            self.current = None

解读：主循环的四个动作对应四条设计原则。心跳先行：任何情况下心跳优先发出，它是全系统判断"我还活着"的唯一凭据。续租即时校验：renew 失败是"我曾被判定失联、任务已被/将被他人接手"的最早信号，立刻清空 current，保证物理执行动作在此刻停止（安全语义优先于任务完成语义）。幂等上报：done_tasks 保证同一任务在本机的重复完成判定只产生一次 DONE 消息。主动放弃：与其等任务池超时回收，执行端在确认无法继续时主动报 ABORTED，让重分配提前发生，两条路径终点相同，主动上报让恢复更快、指标更好看（但正确性不依赖它：即使 ABORTED 消息丢失，租约与执行超时仍然兜底）。

常见坑

  • 心跳超时设得太短：timeout = 1 个周期，误报频发，网络抖动一次全队抢单。修复：timeout ≥ 4 个周期，并把误报率按连续丢拍概率估算进设计文档。
  • 没有幂等设计导致任务被做两遍：验收时发现某个取货点被两台机器人先后到达（重复执行率 > 0）。修复：done_tasks 集合 + 任务池端"完成去重"双保险；验收报告必须单独列这一项。
  • 重分配风暴：监视器判定机器人死亡后直接改任务状态，多台机器人同时被通知去抢同一任务。修复：状态只由任务池在租约过期时释放，所有机器人通过正常 claim 竞争，租约天然串行化。
  • 时钟不一致污染租约：任务池用各机器人上报的时间戳算租约过期，机器间时钟差几秒，租约时长形同虚设。修复：租约的到期时刻一律用任务池自己的单调钟计算（本项目的 lease_sec 相加都在接收方本地完成）。
  • 降级模式没定义清楚：失联机器人继续全速执行旧计划，复联时状态与任务池期望完全不符。修复：降级行为写进配置并测试，停接新任务、完成当前任务、速度减半、周期重连、复联后全量快照对齐。

练习与思考

  1. 算一算：心跳周期 0.5 s、timeout 2.0 s 时，故障检出时延的范围是多少？若把 timeout 改为 0.6 s，连续丢几拍就会误报？按 WiFi 单拍丢包率 1% 估算误报概率的量级。★
    提示
    时延范围 = timeout − 周期 到 timeout，即 1.5–2.0 s。timeout 0.6 s 只需连续丢约 1–2 拍即误报；单拍丢 1% 时连续 2 拍 ≈ 10⁻⁴，每台机器人每天误报多次，不可接受。
  2. 改配置并预测结果：把租约从 10 s 缩短到 3 s（心跳周期仍 0.5 s）。预测对"任务被误收回并重分配"的概率和"真故障后重分配速度"的影响，各给一个方向性结论。★
    提示
    租约 3 s 意味着续租消息连续丢失两轮（按每 2 s 一次续租、心跳 0.5 s，约 4–5 拍）就会被收回，误收回概率上升；真故障后的回收等待变短，恢复更快。经验法则：租约 ≥ 5 倍心跳超时（本设计 10 s = 5 × 2.0 s），且大于最坏续租往返时延的 3 倍。
  3. 设计：为本章系统补一个"任务执行超时"机制（应对"心跳在但卡死"），写出：超时时长怎么定、由谁判定、判定后任务状态如何迁移、如何避免与租约机制互相打架。★★
    提示
    超时 = 任务预计时长 × 2（按任务类型查表）；由任务池判定（它有全部时间信息）；触发后把任务租约强制置为过期并重入队列；与租约的兼容点是统一走"过期即回收"的通道，不要另建一套状态。
  4. 推导：设任务池每 0.2 s 处理一轮派单，某任务被原持有者完成但 DONE 消息丢失的概率为 p。证明：在"租约到期回收 + 幂等上报"机制下，任务最终完成且只有一次物理执行的充分条件是什么，并指出哪个环节失效会打破该条件。★★
    提示
    充分条件：任一时刻至多一台机器人持有有效租约（由任务池单点串行派发保证）且执行端在上报前校验租约。若执行端在租约失效后仍继续物理执行（片段 3 的 renew 检查被删掉），条件被打破，这就是"让手"检查不可省的原因。
  5. 完整验收：按本章验收表跑 5 次基线 + 9 个注入场景（3 故障 × 3 时机），生成一页验收报告：指标表（目标 vs 实测）、3 个最差案例的现象与根因、2 条"下个迭代要修"的问题清单。★★★
    提示
    报告要点：最差案例要写清楚时间线（注入 → 检出 → 重分配 → 完成）；根因分析指向机制缺口（如执行超时缺失）；问题清单按"影响 × 修复成本"排序，别按发现的先后堆。

小结

  • 第四篇项目闭环：任务状态机 + 心跳发现 + 租约回收 + 幂等执行 + 降级模式，五个机制合起来才构成"可交付"的任务系统。
  • 职责分离是设计灵魂：心跳负责发现（本地钟判超时、只报一次），租约负责收回（时间轴裁决、无需共识），执行超时兜底"活着但卡死"。
  • 幂等是重分配机制的孪生兄弟：done_tasks 去重 + 执行前校验租约，双重保证重复执行率为 0。
  • 验收必须量化且可复现：完成率 ≥ 95%、检出 ≤ 2.5 s、重分配 ≤ 1.0 s、降级 ≤ 3 s、重复执行 = 0、makespan 劣化 ≤ 30%。
  • 故障注入矩阵（3 故障 × 3 时机 × 5 重复）是验收报告的证据链，也是下一轮迭代的问题输入。
