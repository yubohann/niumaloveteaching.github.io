第一篇 · 通信基础与系统搭建

第 017 章：多机器人仿真环境搭建

在虚拟世界里先跑通全部通信：一个世界、N 台机器人、统一仿真时钟、桥接传感器，以及"仿真验证不了什么"的诚实边界。

  • 主题：通信基础 / 仿真试验台
  • 关键机制：单世界多模型、仿真时钟与 /clock、仿真-ROS 桥接、TF 前缀
  • 预计学时：55 分钟
  • 前置章节：第 007 章、第 009 章

学习目标

  • 理解多机器人仿真与单机仿真的本质差异：单世界多模型带来的互相影响、命名空间隔离与时钟统一。
  • 掌握仿真时间体系：为什么必须全队 use_sim_time=true、/clock 由谁发布、实时因子（RTF）意味着什么。
  • 会搭建"世界 → 生成多台机器人 → 桥接传感器与时钟 → 命名空间隔离"的完整链路。
  • 掌握仿真中的 TF 纪律：frame 命名冲突的根源与解决（前缀约定），避免"两棵树打架"。
  • 能诚实划出验证边界：哪些问题仿真能抓（命名、QoS、编排、状态机），哪些必须真机才能暴露（无线、时钟、带宽）。

背景与动机

多机器人开发最贵的资源不是算力，是"另一台机器人"。20 台规模的系统如果只能靠真机联调，迭代速度会被硬件与场地卡死；而仿真让你在笔记本上拥有无限次的"擦掉重来"，成本几乎为零。更关键的是：前 16 章所有内容，命名空间、参数、发现、QoS、延迟、中间件，都可以在仿真里先跑一遍"逻辑正确性"，把大量愚蠢错误挡在真机之前。

但多机器人仿真是有门槛的：一个世界里的两台机器人会共享物理（互相碰撞、雷达互相看见）；时钟必须整体统一（否则 TF 立刻分裂）；同一套 frame 名（base_link）会打架；仿真与 ROS 之间还有一座"桥"要按正确的方向与 QoS 搭。本章把这些做成一份可执行的搭建清单，并明确一条纪律：仿真过了不等于真机过了，它证明"逻辑对"，不证明"网络好"。这份认知会帮你把第 013–015 章的网络测试严格留在真机侧。

核心原理

1. 单世界多模型：共享物理，隔离逻辑

多机器人仿真的基本形态是一个仿真世界（world）里放入 N 个机器人模型。这一步的选择决定了仿真的"真实性等级"：

  • 共享物理：两台机器人在同一物理世界里，会碰撞、会互相遮挡激光（一台挡住另一台的视野），这是"多机器人"最本质的仿真，单机分期仿真是替代不了的。
  • 隔离逻辑：软件层面每台机器人仍是独立实例，独立的命名空间、独立的参数、独立的话题。这正是第 007 章"实例化复用"在仿真里的复刻：一台机器人一份命名空间，不许省略。

由此得出两条搭建纪律：（1）机器人模型在 world 里的初始位姿互不重叠（生成位置要显式给，避免出生即碰撞）；（2）每台机器人的模型实体名、命名空间、话题前缀三者使用同一编号约定（robot1/robot2…），从源头杜绝第 007 章的命名事故。仿真环境是演练命名规范最便宜的场地。

2. 仿真时间：全队唯一的时钟

仿真世界里时间由仿真器驱动：仿真器发布 /clock，每个 ROS 节点把 use_sim_time 设为 true，用节点时钟读取仿真时间（第 009 章的时间纪律在仿真侧的落地）。三个必须理解的事实：

  • 时钟停摆的诊断：忘开 use_sim_time 的节点（或忘了桥接 /clock），它的时间戳与仿真世界错位，表现为 TF 报"找不到指定时间的变换"、回放工具时间轴怪异。检查方法：看 /clock 是否在发布、看目标节点参数是否为 true。
  • 实时因子（RTF）：仿真时间前进速度与墙上时间的比值。RTF = 1.0 表示"仿真里的 1 秒 = 真实 1 秒"；CPU 吃紧时 RTF 掉到 0.5，仿真"变慢放"，协同逻辑的时序观察会被拉长，测频率/时序类指标前，先确认 RTF 稳定。
  • 确定性：仿真的一大价值是可复现。用固定初始位姿、固定种子（若有随机组件）、固定仿真步长，"每次跑出来都不一样"的仿真不是试验台，是抽奖机。
仿真时间前进量 = 真实时间 × RTF；控制环的"10 ms"由仿真时间度量 RTF 波动应记录在测试报告里：RTF 0.6 下测得的话题频率仍可真实，但"端到端延迟"的墙钟数值会被放大

算例：RTF 0.4 会把报告里的数字怎么改写？仿真里测得单程 5 ms 的控制延迟，换算成墙钟是 5 ÷ 0.4 = 12.5 ms；设定 10 Hz 的话题，墙钟观察频率约 10 × 0.4 = 4 Hz。两个换算方向要分清：频率类指标乘 RTF（墙钟 = 仿真 × RTF），延迟类指标除 RTF（墙钟 = 仿真 ÷ RTF）。所以测试报告必须记录 RTF 区间，否则同一份数据换台机器就复现不了。物理步长与 RTF 的关系同样直观：步长 1 ms、每步实际计算耗时 2 ms 时，RTF 上限约 0.5，这就是"仿真变慢"最直接的来源。

仿真时钟还有一个特有行为要记住：仿真暂停（暂停或逐步执行）时 /clock 停止前进，所有基于节点时钟的定时器、超时、看门狗一并冻结。排查"定时器不触发"时先看仿真器是不是停着，这是仿真环境独有的假故障；同理，重启仿真让时钟回到起点时，任何记录"上次时间戳"的节点都要能处理时间回退（第 009 章的跳变检测在这里依旧适用）。

3. 桥接：仿真器与 ROS 之间的海关

仿真器（Gazebo 等）与 ROS 是两个世界，需要桥接（bridge）进程转运数据：传感器（激光、相机、IMU）从仿真世界流向 ROS；控制指令从 ROS 流回仿真世界；/clock 从仿真器流向全队。搭桥的三个关键点：

  • 方向：每条桥都是单向声明（仿真→ROS 或 ROS→仿真），方向错了表现为"单边数据"（能看不能控）。
  • QoS：桥接端点有各自默认 QoS，与你的话题 QoS 不匹配时静默丢失（第 011/012 章的知识在这里复用）。高频感知桥用 Best-effort 侧出。以桥工具的对应版本文档为准，忽略细节会造成"桥接了但收不到"。
  • 话题名与命名空间：桥接配置里的话题名要与第 4 节的命名约定一致（/robotN/scan 等），别让桥引入第二套命名。

4. TF 与 frame：两台机器人不能同名

TF（坐标变换树）是仿真里最先爆炸的东西。单机仿真时 base_link 全局唯一；两台机器人各自发布 odom → base_link 时，两棵树同名打架，TF 里会出现两个发布者争抢同一条边。解决手段（按推荐顺序）：

  1. frame 前缀化：机器人 1 的 frame 叫 robot1/base_link、robot1/odom，所有与这台机器相关的 frame 带前缀（生成时把前缀注入 URDF/模型，或命名约定写进描述文件）。
  2. 独立 TF 树 + 静态桥接：每台机器人维护自己的树，再用一条静态变换把各树的"根"连接到世界坐标（world），世界系是唯一的连接点，这也是多机器人 TF 的标准做法（第 024 章展开）。

纪律一句话：凡是被两台机器人各自发布的 frame，就必须带身份前缀；只有 world 这类全局唯一的 frame 不带。

数量级有助于理解 TF 的负担：单台机器人典型有 5–15 个 frame，静态变换一次性发布、动态变换按 30–100 Hz 刷新；4 台仿真就是 4 条同时刷新的树，外加 4 条 world 静态桥。TF 检查就是把这些"边"逐一核对发布者唯一性：同一条边出现两个不同父级的发布者，就是前缀漏配的信号，越早发现越便宜。

5. 仿真能验证什么、不能验证什么

诚实划界（这决定了你的测试策略）：

项目仿真能否验证原因
话题/服务的命名与隔离能计算图与真机同构（第 007 章）
QoS 组合与匹配行为能发现与匹配走真实中间件栈
启动编排、生命周期、状态机能（前提 RTF 稳定）时序逻辑与代码一致
无线延迟、丢包、带宽瓶颈不能仿真内通信走本机回环，无物理无线效应
时钟漂移与同步质量不能仿真只有一个时钟源
多播/发现协议在真实网络的失效不能回环网络永远"最理想"

结论：仿真把"逻辑类"问题拦在真机之前；"物理网络类"问题必须靠第 013–015 章的真机测试台。把两类测试分开安排，是团队从"演示项目"走向"系统项目"的标志。

把边界再量化一处：发现时间是仿真与真机差距最大的项目之一。仿真内各进程走回环与共享内存，发现近乎瞬时；真机上 20 台规模的冷启动发现按第 010 章的口径是秒级到十几秒，依赖发现时序的启动编排（"等全部成员可见再开协同"）必须在真机复测一遍。同理，QoS 匹配在仿真里几乎"秒配"，真机上受发现延迟与网络抖动影响，重连行为与超时阈值也只有在真机才能定版。

实现思路与设计

给出可执行的搭建流程（以 Gazebo 系仿真器为主线，命令以对应 ROS2/仿真发行版为准）：

  1. 定世界：选一个空白/平地 world 起步，写清初始位姿表（4 台机器人各占一角）；先让世界跑起来（无机器人）确认仿真器本身可用。
  2. 生成 N 台：用一个循环生成 4 台，模型名、命名空间、初始位姿全部来自同一张"车队列配置表"。
  3. 桥接：桥接 /clock 与每台机器人的传感器/指令话题；话题名带命名空间；感知类桥接注意 QoS。
  4. 全队时间纪律：所有 ROS 节点 use_sim_time=true（launch 统一注入）。
  5. 验证清单：图检查（每台机器人节点/话题存在、前缀正确）；/clock 频率；TF 树每台独立且前缀正确；把一台机器人的电量话题停掉，确认监控报警（第 006 章）。

给仿真的计算开销留一份预算思维：RTF 的主要消耗者是物理步进、传感器渲染与桥接进程。常用手段包括按需关闭暂时用不到的相机（渲染通常是最大头）、降低非关键传感器的更新率、给 RTF 设一个可接受下限（例如 ≥ 0.7）并由测试脚本自动记录。当"加第 5 台机器人"把 RTF 从 0.9 拉到 0.5 时，先优化世界配置，急着继续加台数只会得到一份时序失真的"成功"报告。另外，出生点的间距校验要写成规则：任两台机器人的外接圆半径之和再加约 0.5 m 的安全余量，避免"出生即碰撞"。

仿真元素真机对应物差异/注意

设计决策：为什么"先通信、后算法"要在仿真里执行一遍？

因为多机器人算法的联调环境里混合着两类错误：通信类（命名错、QoS 不匹配、参数没注入）与算法类（控制逻辑、协同策略）。如果直接上真机联调，两类错误会互相伪装，算法不动，你怀疑网络；网络排查完没错，回头再翻算法，时间就这样烧掉了。仿真是"通信干净"的世界：回环网络没有丢包与延迟，所有"通信类"问题在这里都是纯粹的逻辑问题（名字对不对、连没连上），可以被快速消灭。等仿真里图检查与编排清单全绿，再把算法带进真机，你的调试焦点就只剩物理与网络，这是把问题分而治之的最优排期。

关键代码与解读

片段 1：世界与多机器人生成，一张配置表驱动 N 台

from launch import LaunchDescription
from launch.actions import IncludeLaunchDescription
from launch.launch_description_sources import PythonLaunchDescriptionSource
from launch_ros.actions import Node, SetParameter

FLEET = [                                   # 唯一事实来源：车队列配置表
    {"id": 1, "x": -2.0, "y": 0.0},
    {"id": 2, "x": 2.0, "y": 0.0},
    {"id": 3, "x": 0.0, "y": -2.0},
    {"id": 4, "x": 0.0, "y": 2.0},
]

def generate_launch_description():
    actions = [
        # 所有节点统一仿真时间：漏一个都会造成时间轴错位（第 009 章）
        SetParameter("use_sim_time", True),
        # 启动仿真世界（以对应 gazebo/ros_gz 发行版的启动文件为准）
        IncludeLaunchDescription(PythonLaunchDescriptionSource(
            "/opt/ros/share/ros_gz_sim/launch/gz_sim.launch.py")),
    ]
    for r in FLEET:
        actions.append(Node(                # 生成这台机器人：名字、位姿、主题都带编号
            package="ros_gz_sim", executable="create",
            arguments=["-name", f"robot{r['id']}",
                       "-topic", "robot_description",
                       "-x", str(r["x"]), "-y", str(r["y"])],
            namespace=f"robot{r['id']}",    # 逻辑隔离：与话题前缀一致
        ))
    return LaunchDescription(actions)

解读：（1）生成序列由 FLEET 表驱动，无需手写四遍，扩展到 20 台只是表变长，这与真机部署的 launch 写法（第 007 章）刻意保持一致：仿真与真机的机器人"实例化方式"同构，迁移代码才不用重学。（2）初始位姿（x/y）显式给定，互不重叠：把"出生点"当作标定来对待，避免第一帧就碰撞，这是多机器人仿真"第一号小坑"。（3）命令与路径以对应发行版为准（Gazebo 经典版与新版的包名/参数不同）：姿态上要记住的是结构，单表驱动、命名与命名空间一致、位姿显式，不同发行版只换命令壳。

片段 2：桥接配置，时钟、传感器与指令的三向海关

from launch import LaunchDescription
from launch_ros.actions import Node

def generate_launch_description():
    # 桥接进程：仿真世界 <-> ROS 的搬运工；每条桥的方向都必须显式声明
    bridges = []
    for rid in (1, 2, 3, 4):
        bridges += [
            # 传感器上行：仿真 -> ROS（scan/imu/odom 按需补全）
            f"/robot{rid}/scan@sensor_msgs/msg/LaserScan[gz.msgs.LaserScan",
            # 指令下行：ROS -> 仿真（方向反了就是"能看不能控"）
            f"/robot{rid}/cmd_vel@geometry_msgs/msg/Twist]gz.msgs.Twist",
        ]
    return LaunchDescription([
        Node(package="ros_gz_bridge", executable="parameter_bridge",
             arguments=["/clock@rosgraph_msgs/msg/Clock[gz.msgs.Clock"] + bridges,
             # 时钟桥必须最先健康：没有 /clock，全队时间停摆
             output="screen"),
    ])

解读：（1）每条桥的方括号是方向语法：[ 表示仿真→ROS、] 表示 ROS→仿真（以对应桥工具文档为准）。方向错误是本片段的第一教训：上行传感器写成下行，现象是"图里有话题但永远安静"。（2）/clock 桥是唯一的"全队生命线"：它先于一切；排障顺序里"看 /clock 在不在"永远排第一。（3）话题名全部带 /robotN/ 前缀，与命名空间约定一致，桥是"传感器驱动"在仿真里的替身，驱动不会乱起名字，桥也不应该。

片段 3：仿真试验台的验收清单（CLI）

ros2 topic hz /clock                 # 仿真时钟在流动；停=仿真世界没起或桥没通
ros2 topic hz /robot1/scan           # 传感器桥健康：频率应稳定在仿真设定值
ros2 node list | grep robot          # 期望看到 4 台机器人各自的一组节点
ros2 topic list | grep "^/robot1"    # 单台前缀分簇：命名空间隔离生效（第 007 章）
ros2 param get /robot1/odom_pub use_sim_time   # 应为 true：时间纪律逐台核对
ros2 run tf2_tools view_frames       # 生成 TF 树：确认每台帧带前缀、根接 world
# 故障演练：停掉 robot3 的桥接或生成节点，观察监控（第 006 章）是否按预期报警
# 记录 RTF：仿真窗口/日志中的实时因子，测试报告必须随附（时序类结论的前提）

解读：这份清单按依赖顺序排列：时钟 → 节点 → 命名 → 参数 → TF → 故障演练，任何一步红掉都不要往下走（后面都是它的下游）。TF 检查是清单里最容易被跳过、后果最严重的一项：view_frames 产出的树图要肉眼确认"4 个前缀、4 棵子树、world 为根"。最后两行把仿真试验台与监控系统接在一起：能在仿真里演练"某台机器人掉线"并验证告警，说明你的监控体系是活的，这一条演练会在第 018、020 章反复用到。

常见坑

  • 部分节点忘开 use_sim_time：TF 报"extrapolation into the future"、话题时间戳与仿真世界错位。修复：launch 层统一注入（片段 1 的做法）；验收清单加参数核对。
  • /clock 没桥接：全队时间停在 0（或系统时间），定时器行为诡异，TF 全乱。修复：时钟桥最先检查；把它当作仿真环境的"总电源"。
  • frame 名冲突：两台机器人各自发布 odom → base_link，TF 树打架，map 端出现"随机漂移"。修复：frame 前缀化 + 独立树 + 静态桥接到 world（本章第 4 节两步）。
  • 桥接方向或 QoS 错误：传感器能看不能控（方向）、或桥接了却收不到（QoS 不匹配，第 012 章）。修复：每条桥过一遍"方向 + QoS"评审；用 topic info --verbose 核对桥端点。
  • 忽略 RTF 就下时序结论：笔记本上跑 4 台机器人 + 相机渲染，RTF 掉到 0.4，却拿"话题 10 Hz"和"延迟 5 ms"去写报告。修复：测试脚本记录 RTF；RTF 明显低于 1 时只做功能结论，性能结论留给真机/降载环境。
  • 仿真出生点重叠：多台机器人生成在同一位置，第一帧互相弹飞，日志全是莫名其妙的碰撞。修复：位姿表显式给定并加"最小间距"校验。

  1. 预测题：把片段 1 中的 SetParameter("use_sim_time", True) 删掉，列出至少三种可观察的异常现象（TF、频率统计、日志时间戳各一），并给出检查步骤。★
    提示
    TF 查询不到指定仿真时刻的变换；话题时间戳落在 1970 或系统时间轴；ros2 topic hz 显示正常但下游按时间戳的行为错乱。检查：param get use_sim_time 逐台核对。
  2. 改配置并预测：把桥接中的 cmd_vel 桥方向从 ]（ROS→仿真）改成 [（仿真→ROS），预测系统行为的变化与排查时你会看到的图状态。★
    提示

  3. 设计题：为 4 台机器人写一份"TF 命名方案"：列出每台机器人的 frame（至少 5 个/台）、静态桥接的位置与理由，并说明如何用 CLI 验证"没有同名的争抢发布者"。★★

  4. 边界题：为下列问题选择测试环境（仿真/真机/两者都行）并说明理由：话题前缀错、QoS 静默不匹配、WiFi 漫游导致的发现中断、启动顺序竞态、20 台规模的发现时间、参数版本配错。★★★

小结

  • 多机器人仿真 = 单世界多模型：物理共享（会互撞互遮挡）、逻辑隔离（每台命名空间与参数独立）。
  • 时间纪律：全队 use_sim_time=true、/clock 桥最先健康；RTF 不稳时只做功能结论，不做性能结论。
  • 桥接三要素：方向、QoS、命名；"能看不能控"查方向，"桥了却收不到"查 QoS。
  • TF 纪律：凡两台各自发布的 frame 必须带身份前缀；各树经静态变换接到 world。
  • 边界诚实：仿真抓逻辑类问题（命名/QoS/编排/竞态），无线与时钟类问题留给真机测试台。
  • 下一章为试验台装上仪表盘：日志聚合与监控，让 N 台机器人的日志与指标汇到一处。
