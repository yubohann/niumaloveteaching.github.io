第 016 章：通信中间件对比：DDS、Zenoh与共享内存

RMW 是 ROS2 的"可换发动机"：车间局域网用 DDS、同机大数据走共享内存、跨网桥接交给 Zenoh，选型靠场景分解，不靠信仰。

  • 主题：通信基础 / 中间件选型
  • 关键机制：RMW 抽象、Zero-Copy 共享内存、Zenoh 路由与桥接
  • 预计学时：55 分钟
  • 前置章节：第 010 章、第 013 章

学习目标

  • 理解 RMW 抽象层的作用：ROS2 之上换中间件不需要改应用代码，但换来的行为差异必须重新验收。
  • 说出 DDS 家族（Fast DDS / Cyclone DDS 等）的实现差异会如何影响发现、QoS 与性能，掌握"实测优先"的选择方法。
  • 理解共享内存（Zero-Copy）的机制与边界：同机、大数据有效，跨主机退化为网络路径。
  • 认识 Zenoh 的定位：会话式路由、可跑 TCP/QUIC、跨网络桥接（zenoh-bridge-dds），适合广域与受限网络场景。
  • 会做混合中间件部署的分层设计：哪些子系统用什么、边界在哪、如何验收与排障。

背景与动机

本书前面 15 章都建立在"默认中间件"之上：你说话题、QoS、发现，ROS2 背后的 DDS 替你完成。但多机器人系统的部署面远比单机复杂：同一台机器人上有图像大数据的进程间传输，车间里有 20 台设备的局域网，还有跨楼宇、跨网络的远程监控与桥接。一种中间件包打天下的时代正在结束，是时候认识"可替换的发动机"了。

ROS2 通过 RMW（ROS Middleware）接口支持多种中间件实现，并允许在同一系统中按主机部署不同实现（桥接处打通）。本章不评比"谁最好"（那是一场没有赢家的争论），直接给你一把场景分解的尺子：同机大数据、局域网实时控制、跨广域桥接三类任务，各自的瓶颈不同，发动机也就不同。本章也是第 022 章（共享内存与零拷贝）、第 023 章（大消息传输）的直接前置。

核心原理

1. RMW：ROS2 的中间件插槽

ROS2 架构从下到上：操作系统网络 → RMW 接口 → 中间件实现（DDS/Zenoh/…）→ rcl/rclpy 客户端库 → 你的节点。RMW 层定义了"发布、订阅、服务、动作、QoS"的抽象语义，由具体实现翻译成各自的协议与配置。换 RMW 通常只需一致的镜像与环境变量，但请记住第 010 章的教训：发现行为、QoS 细节在不同实现里并不完全一致，换发动机后"原来的调优"与"原来的验收"都要重做一轮。

实现定位典型优势需要留意的点
rmw_fastrtps_cpp（Fast DDS）默认实现之一，生态成熟文档与工具完善，发现服务器与安全机制齐全高级调优项多，需要专门配置才出最佳表现
rmw_cyclonedds_cpp（Cyclone DDS）轻量实现内存占用小、发现行为可预测部分高级 QoS/安全组合需查对应文档
rmw_zenoh_cpp（Zenoh）路由式中间件NAT 穿透、广域桥接、会话模型清晰成熟度与工具链随发行版演进，需实测

选型纪律：（1）全队统一或显式桥接，不同 RMW 之间默认不互通，同一域里"混装"会让一半设备互相看不见；（2）实测优于传闻，发现时间、延迟分布、大消息吞吐在你们的具体网络上跑一遍，比任何对比榜单都可信；（3）变更即回归，RMW 是车队级配置（第 010 章），改动需要重跑发现、延迟、带宽三张验收表。

把版本也当成配置的一部分：中间件的参数名、默认值、已知问题随版本变化，"同型号不同版本"同样会制造不对等的行为。部署仓库里要记录 RMW_IMPLEMENTATION 与具体版本号，升级走与"换实现"相同的回归表，"小版本升级不会有事"的假设在通信底座上尤其危险。

2. 共享内存 / Zero-Copy：把拷贝降到零

同机进程通信的默认路径是"用户态序列化 → 内核拷贝 → 对端内核 → 对端用户态"，一条图像要拷贝好几遍，还要多次进出内核。Zero-Copy 的机制是：发送端把消息放进共享内存段，接收端只拿到一个"引用"（句柄 + 引用计数），数据零拷贝共享。成熟实现（如 iceoryx 及其与中间件的集成）用"专属共享段 + 引用计数 + 无锁队列"，大负载（图像、点云、大日志包）收益最明显。

同机 1 MB 消息的默认路径拷贝成本 ≈ 数次内存拷贝；Zero-Copy ≈ 0 次 消息越大收益越大；10 KB 的小消息收益有限，反而增加配置复杂度，"该不该上"先看消息尺度

边界务必分清：（1）仅同一主机有效，跨主机时共享内存无从共享，中间件会退回网络路径（配置不当的表现是"跨机大消息突然变慢"）；（2）参与者要"接入共享段"，实现通常有进程白名单/开关，漏配的进程静默退化为拷贝路径；（3）生命周期语义更严格，借用/归还模型约束了"消息被多处长期持有"的用法，深度队列的语义在大消息上也要重新想（第 022 章展开）。

还有一个常被混淆的档位问题："走共享内存传输"与"零拷贝 API"是两档配置。前者把数据路径从内核往返换成共享段内的 1–2 次拷贝，收益已经可观；后者需要节点使用"借用消息（loan）"接口，把序列化一并省掉、数据原地共享，才是字面意义的零拷贝。验收时要写清采用哪一档：只开了共享段而没有改用借用模式的代码，拿到的只是部分收益。粗算一笔账：2 MB 图像在拷贝路径上每级流程做 4 次搬运，合计约 8 MB，按 10 GB/s 内存带宽估算约 0.8 ms，单流看不大；但"相机→检测→融合→可视化"的流水线上每级都复制数次，CPU 与内存带宽占用会叠加，调度抖动也会被拷贝放大，所以大消息链路的收益更多体现在系统抖动下降，平均延迟只少几毫秒。

3. Zenoh：把"发现与路由"独立成层

DDS 的世界是"域内对等发现 + 直连传输"，穿透 NAT 与跨网段一直是痛点（第 010 章的单播列表与发现服务器都是在打补丁）。Zenoh 的思路不同：节点先与 Zenoh 节点（router/peer）建立会话，发布/订阅/查询通过会话内的路由层转发，像"消息总线网络"，与"互相喊话"的直连模式不同。它带来的能力：

  • 网络友好：可跑在 TCP/TLS/QUIC 上，天然穿透 NAT；跨网络（车间 ↔ 办公网 ↔ 云）不需要组播。
  • 模型丰富：除 pub/sub 外还有 query（请求-应答会合点）与可组合的存储/路由插件。
  • 桥接生态：通过 zenoh-bridge-dds 把 DDS 世界的 ROS 图与 Zenoh 网络互连，"跨网络两段式部署"的现成桥。

使用建议：把 Zenoh 用在"网络环境复杂/需要跨域"的那一段；为了新鲜感替换整个车队不划算，DDS 在局域网内的成熟度与工具链（topic info --verbose 这类日常工具）仍是多机器人开发的主场。桥接处要额外验收：QoS 映射、延迟叠加、以及"桥不转发什么"（工具话题、大消息策略）都要过设计评审。

给桥接段的延迟建一个量级预期：同机内 DDS 与 Zenoh router 之间的桥接，附加处理通常在亚毫秒到数毫秒级；跨网络时主体延迟由链路决定（同城专线数毫秒、公网 20–50 ms 起），桥转发本身通常不是大头。真正要写进设计表的是三件事：QoS 映射（可靠性、持久性如何翻译，哪些组合会被降级）、大消息策略（是否分片、分片大小与重组超时）、主题白名单（允许哪些话题过桥，防止图像与工具话题把窄链路淹掉）。这三条各有对应的验收项，桥接不是"配个地址就完事"的透明代理。

4. 场景分解表：三类任务的发动机

任务特征推荐理由
同机大数据（相机→检测→融合）MB 级、主机内、毫秒敏感共享内存 / Zero-Copy消灭拷贝与内核往返；消息越大收益越大
车间局域网控制与状态KB 级、20 台、低延迟DDS（默认实现）成熟、工具链完整、QoS 语义丰富
跨楼宇/跨网段监控与桥接带宽受限、NAT、长链路Zenoh（或经桥接）会话式路由穿透网络边界
车队级统一项发现信标、默认 QoS保持一种实现为主混装的排障成本远超单点收益

"混合部署"正是主流答案，与妥协无关：每台机器人内部一个共享内存域；机器人之间一张 DDS 局域网；车队与外部世界之间一座 Zenoh 桥。三层之间的边界各有明确的验收与责任人，故障域互不牵连，这正是架构设计追求的效果。

5. 切换与对比的方法论

最后给"换/不换"一个可执行流程：（1）写清目标指标（发现时间、p99 延迟、大消息吞吐、CPU/内存占用里选两三个）；（2）搭最小对比环境（两台机、固定网络、统一负载脚本）；（3）各实现跑同一组基准，记录配置（配置本身就是结果的一部分）；（4）回归验收：发现、QoS 事件、延迟、带宽四张表（第 006/010/012/015 章）。全部过线才切换；没过线就把结论写进文档，"我们验证过不换"与"我们换过"一样是有价值的工程结论。

实现思路与设计

以"机器人实验车队（4 台）+ 远端监控中心"为对象做中间件分层设计：

  1. 画边界：机内（进程间大数据）→ 共享内存；车间（机器人 ↔ 边缘服务器）→ DDS；车队 ↔ 远端（跨 Internet）→ Zenoh 桥接段。
  2. 定统一项：车间段全队统一 RMW 与环境模板（域号、发现配置）；机内段启用共享内存并把大消息进程加入清单；桥接段单独部署 router 与 bridge 进程。
  3. 定验收：每段独立三张表，发现时间、延迟 p99、大消息吞吐；再做跨段回归（远端能订阅到车队主题、桥接延迟叠加在预算内）。
  4. 定运维：RMW/共享内存/桥接配置全部进部署仓库（第 081 章）；每段配降级预案（桥断则本地记录续传；共享内存失效回退拷贝路径，功能不断但必须告警）。

分段配置表

段机制关键配置验收指标
机内大数据共享内存（Zero-Copy）共享段开关 + 进程接入清单图像链路 CPU 占用下降 ≥ 40%
车间局域网DDS（全队统一）域号、发现模式、RMW 版本发现 ≤ 5 s；控制 p99 ≤ 15 ms
跨网络桥接Zenoh + zenoh-bridge-ddsrouter 地址、TLS、主题白名单跨段 p99 ≤ 200 ms；桥进程可观测
设计决策：为什么"全队保持一种 RMW"是默认答案，混合只在边界处发生？

混装中间件的成本藏在三处：（1）发现不通，不同实现互不可见，每对"跨实现通信"都要额外桥接；（2）工具失灵，ros2 topic info --verbose 这类排障工具在混合环境里只能给出片段信息，团队要在两套心智模型间切换；（3）验收翻倍，每次升级都要跑两套回归。所以分工是"段内统一、段间显式桥接"：车间一段一个实现，机内共享内存只影响本机进程（不算跨段混装），跨网段用 Zenoh 桥。桥接点少而明确，责任清晰，故障域隔离，比"每个子系统挑一个最爱的中间件"便宜得多。

关键代码与解读

片段 1：统一 RMW 的部署，launch 注入与环境自检

from launch import LaunchDescription
from launch.actions import SetEnvironmentVariable

def generate_launch_description():
    # 车间段全队统一：RMW 与发现在同一处定义，避免"部分机器换了发动机"
    return LaunchDescription([
        SetEnvironmentVariable("RMW_IMPLEMENTATION", "rmw_fastrtps_cpp"),
        SetEnvironmentVariable("ROS_DOMAIN_ID", "42"),
    ])

# 部署自检：任何一台机器人的 RMW 偏离约定，立即告警（对第 006 章巡检的扩展）
def check_rmw_consistency(env, expected="rmw_fastrtps_cpp"):
    got = env.get("RMW_IMPLEMENTATION", "rmw_fastrtps_cpp")  # 未设置=发行版默认
    if got != expected:
        return f"RMW 不一致：{got} != {expected}（会导致跨机静默不通）"
    return None

解读：（1）RMW 的"切换点"就是环境变量加下发的节点进程，这段 launch 演示"全队定义在一处"的纪律；（2）自检函数的细节值得注意：未设置时按"发行版默认"处理再比较，大量实现差异事故正是"一台没配、其他都配了"造成的；（3）检查结果应接入第 006 章的巡检上报，靠人记迟早会漏。把"发动机型号"和域号、发现配置并列为车队级配置项，是本章最想让读者带走的工程习惯。

片段 2：共享内存开关（示意），让同机大消息走快路径

<!-- 共享内存配置示意：字段名与开关以对应中间件版本官方文档为准 -->
<!-- 思路：开启共享段传输；把"会发大消息的进程"加入参与者清单 -->
<dds>
  <profiles>
    <transport_descriptors>
      <transport_descriptor>
        <transport_id>shm</transport_id>
        <type>SHM</type>
        <!-- 段大小按最大消息 + 额度估算：图像 2 MB 级别留足余量 -->
        <segment_size>33554432</segment_size>   <!-- 32 MB -->
      </transport_descriptor>
    </transport_descriptors>
  </profiles>
</dds>
<!-- 注意：进程不在清单里=走拷贝路径（功能正常、性能打折）；
     跨主机参与者=自动回退网络路径（这不是错误，是边界） -->

解读：（1）配置的核心只有两件事：开"共享段"、把大消息进程纳入清单，其余交给中间件自动选择传输路径（同机走 SHM、跨机走网络）。（2）segment_size 的取法按"最大消息 × 并发缓冲数"估，注释给的是图像 2 MB 级的 32 MB 档；太小会频繁创建/回收段（性能抖动），太大则浪费内存，上线前用实际消息尺寸复核一次。（3）最后两条注释是本章的"边界宣言"：共享内存失败会静默退化为拷贝路径（功能不受影响），所以验收必须测 CPU/吞吐；"功能是否可用"永远通过，性能收益才是这项配置的全部意义。

片段 3：切换对比的基准脚本框架

# 对比流程：每次只换一个变量（RMW 实现），其余配置与负载保持一致
export RMW_IMPLEMENTATION=rmw_fastrtps_cpp
ros2 launch fleet_bench latency_bench.launch.py   # 统一负载脚本：定频话题 + 探针

ros2 topic delay /robot1/odom | tail -5            # 记录 p 分位与最坏值
# 换发动机再跑一遍（记得同步重启两端进程，避免混装）
export RMW_IMPLEMENTATION=rmw_cyclonedds_cpp
ros2 launch fleet_bench latency_bench.launch.py
sleep 60
# 结论文档要写三样：配置（含版本）、负载说明、四张验收表的数字
# 反例：只贴一句"XX 更快"，配置与负载不明，结论不可复现

解读：（1）这段脚本强调的是"控制变量"：一次只换 RMW，负载脚本、网络、消息大小全部固定，中间件对比最大的敌人是"顺手也调了别的"。（2）换实现时必须同步重启两端进程（不能一端 Fast DDS、一端 Cyclone），否则测出的是混装故障，混入的信号会掩盖性能差异，注释专门提醒。（3）最后一行是方法论落点：结论必须携带配置、负载、数字三要素；第 015 章"空载数字没有意义"在这里升级为"不可复现的数字没有意义"。

常见坑

  • 车队混装 RMW：一半 Fast DDS、一半 Cyclone，两组各自健康、互不相识。症状与域号不一致极像。修复：部署自检（片段 1）+ 车队级配置统一变更。
  • 以为 Zenoh 与 DDS 天然互通：直接换一半设备的 RMW 指望无缝。实际需要桥接进程（zenoh-bridge-dds）。修复：桥接作为独立组件纳入设计与验收，别把它当"配置细节"。
  • 共享内存期待跨机生效：给全车队开了共享内存配置，跨机大消息毫无改善（本来就该走网络）。修复：分清"同机优化"与"跨机传输"是两件事；跨机大消息见第 023 章。
  • 配置了共享内存但进程没入清单：功能正常、CPU 依旧高企，验收"通过"了功能测试却没收成性能。修复：验收指标锁定 CPU/吞吐；对"性能收益"做前后对比报警。
  • 切换 RMW 不做回归：发现行为、QoS 默认值、调优参数的语义在小版本间有差异，换完直接上线，几天后出现"偶发收不到"。修复：发现、QoS、延迟、带宽四张表全量回归后再切。

    提示
    (a) 共享内存（同机大数据）；(b) DDS（局域网、低延迟、成熟）；(c) Zenoh 桥接（跨网络、NAT）；(d) 后台类流量，机制与限速并重（第 014 章），网络段仍可走 DDS/桥接，但要错峰。
  2. 预测题：给同机图像链路开共享内存前后，预测四个指标的变化方向：功能正确性、CPU 占用、消息延迟、内存使用。哪个指标"不会变"？为什么功能测试无法证明收益？★
    提示
    功能不变（灰路径兜底）；CPU 与延迟下降；内存占用上升（共享段常驻）。功能测试测"对不对"，收益要测"省多少"，验收指标必须另立。
  3. 设计题：设计"桥接段"的验收方案：至少列出五项检查（含 QoS 映射、主题白名单、延迟叠加、桥进程健康、断连行为），并说明断连时车队侧应保持什么行为。★★
    提示
    断开时：本地协同必须继续（桥不是关键路径）；远端数据走本地缓存待续传；桥的健康由第 006 章式心跳监控。白名单防止工具话题/大消息涌过桥。
  4. 推导题：某图像流 2 MB/帧、10 Hz，同机链路默认路径有 4 次拷贝，每次拷贝按 10 GB/s 带宽估算。计算默认路径的拷贝耗时与占每帧预算的比例；再算 Zero-Copy 后的变化。★★★
    提示
    每帧 2 MB、4 次搬运合计约 8 MB；按 10 GB/s 内存带宽估算约 0.8 ms，占 100 ms 帧预算不到 1%，单流不致命，但多级流水与非借用模式下的序列化开销叠加会放大；Zero-Copy 把这部分省掉并释放内存带宽。
  5. 论证题："既然 Zenoh 更现代，我们应该立刻把全车队换过去。"给出支持与反对各两条，并写一个可执行的分阶段方案。★★★
    提示
    支持：跨网络友好、统一会话；反对：工具链与成熟度需实测、全队回归成本高。分阶段：先桥接段试点（新网络段用 Zenoh）→ 沉淀基准与运维经验 → 再评估替换，先换边界，后换心脏。

小结

  • RMW 是中间件插槽：换发动机不改应用，但发现、QoS、性能行为要重新验收；全队统一是默认纪律。
  • DDS 家族各有性格（Fast DDS 生态全、Cyclone 轻量可预测），选择靠实测与回归，不靠传闻。
  • 共享内存消灭同机大消息的拷贝（消息越大越划算），边界是"仅同机"；失效会静默退化，验收要盯 CPU/吞吐。
  • Zenoh 用会话式路由穿透网络边界，配 zenoh-bridge-dds 做跨段桥接；桥接点要独立验收。
  • 主流形态是分层：机内共享内存、车间 DDS、跨网 Zenoh 桥，段内统一、段间显式、故障域隔离；选型结论要带配置与负载，才可复现。
