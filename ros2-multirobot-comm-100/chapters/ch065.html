第三篇 · 协同控制与任务协同

第 065 章：阶段项目：协同搬运与围捕演练

把前二十四章的能力焊成一个可验收的系统：三台机器人协同搬运货箱穿过门洞，再对闯入目标完成合围，从场景设计、架构分层、消息表到验收指标与评分表，一次完整的工程闭环。

  • 主题：阶段项目 / 系统集成演练
  • 关键机制：指挥树编排、虚拟结构搬运、包围几何、指标采集与验收
  • 预计学时：90 分钟
  • 前置章节：第 064 章（并综合第 041–063 章能力）

学习目标

  • 独立完成一个"多机器人协同演练"的场景分解：把故事性需求翻译成可测量、可验收的技术指标。
  • 设计演练系统的四层架构与全部关键话题/QoS 契约，并解释每一处取舍。
  • 用行为树/状态机编排"检测→分配→编队→搬运/合围→回收"的完整任务流。
  • 实现指标采集节点：时间戳对齐、成功率统计、评分表自动生成。
  • 写出一份别人可复现的演练运行手册（Runbook）：环境、步骤、判据、故障处置。

背景与动机

第三篇从编队（041）一路走到行为树决策（064），每个单点能力都能单独演示，但系统性问题只有在组合时才会暴露：端到端时延把合围拖慢半秒就围不住目标；任务分配与编队的坐标系不一致，搬运队形当场扭成麻花；指标口径没统一，"实验成功"只能靠肉眼。

本阶段项目选择两个互补的演练：协同搬运考察强耦合协同（多机必须保持刚体约束、时序严格），协同围捕考察动态博弈协同（目标会跑、需要持续调整包围圈）。两者共用同一套通信底座与决策框架，正好检验你的架构是否"可组合、可复用"。完成本章后，你会带着一套完整的验收模板进入第四篇（066 章起）的工程化内容。

核心原理

1. 演练场景定义

演练 A（协同搬运）：仓库区有一台货箱（0.8 m × 0.6 m，15 kg），三台差速轮式机器人需在 180 秒内把它搬出仓库，穿过 1.2 m 宽门洞，送到 25 m 外的卸货区，允许 ±0.5 m 的落点误差。货箱无轮，被抬起后只能靠三台机器人保持相对位置同步推进，这是"虚拟结构"式协同。

演练 B（协同围捕）：随机时刻，扮演"入侵者"的机器人从园区边界进入限制区，以 ≤ 1.0 m/s 逃逸；四台巡逻机器人需在其进入后 60 秒内形成合围：所有机器人到目标距离 ∈ [1.2 m, 2.0 m]，且相邻包围者最大角间隙 ≤ 90°；持续保持 10 秒即判定成功。

两个演练之间共享：导航栈、坐标系、任务分配器、指挥树框架、监控与记录设施。只替换"任务级子树"，这是检验架构解耦程度的试金石。

2. 搬运的协同约束：虚拟结构与队形保持

三台机器人围绕货箱质心呈 120° 分布，共同维持一个虚拟刚体（virtual structure）。设机器人 i 的目标位姿为 pid = pcargo + R(θcargo)·di，其中 di 是货箱坐标系下的固定抓取点偏移。控制律的经典形式是"编队误差 + 队形协调项"：

ui = kp(pid − pi) + kf(pcargo − p̄robots) + kv(vd − vi) kf 项让所有机器人共享同一个"货箱牵引量"：单人偏离会被队形拉回，不会把货箱扯歪（第 056/057 章的力协调思路）

关键工程数值：货箱位姿由三台机器人的观测融合得到（至少两台同时可见，否则货箱状态不可信）；队形误差超过 0.15 m 即减速，超过 0.3 m 即停车重对齐，宁可慢，不可把货箱摔了。穿越门洞时队形切换为"纵队"（前后 1.2 m），过门后恢复"品字"，这是第 043 章编队变换的直接应用。

3. 围捕的几何与时间账

N 台机器人合围的稳态构型是围绕目标半径 R 的正 N 边形，期望相位 θid = θ0 + 2πi/N。持续包围的可行性有一条直观的时间账：目标的机动能力必须被包围圈的收缩速度压制。目标以 ve 逃逸、最近两台包围者的角速度能力为 ω，则包围圈不破的条件约为

R·ω ≥ ve·(1 + ε) R = 1.6 m、ve = 1.0 m/s、ε = 0.3 → 每台角速度需 ≥ 0.81 rad/s；差速轮的极限角速度要留 30% 余量，否则会在目标急转时被甩开

围捕成败的另一半在通信时延：各机器人看到的目标位置来自共享话题，若端到端时延 200 ms、目标 1 m/s，位置偏差就是 0.2 m，接近包围环容差 0.8 m 的四分之一。因此围捕演练要求：目标位姿话题 ≥ 10 Hz、端到端时延（含融合）≤ 200 ms、时间同步偏差 ≤ 20 ms（否则带时间戳的融合形同虚设）。

4. 验收指标：把"成功"变成数字

5. 数值算例：合围几何的余量与时间预算

先把"最大角间隙 ≤ 90°"这条验收线的数学含义算清楚。四台机器人围绕目标，相邻包围者的角间隙之和恒为 360°；要求每段都 ≤ 90°，等于要求四段全部恰好等于 90°，余量为零。目标一个急转，某台机器人相对其余台的相位偏移 Δ，必然让一侧间隙变成 90° + Δ、另一侧变成 90° − Δ，最大值立即越线。换句话说，这个判据在 4 台配置下只有"完美正四边形"一个合格点，实际运动中几乎不可持续。两条修正路线各有代价：改用 5 台，理想间隙降到 72°，允许 18° 的扰动余量（相对余量 25%），代价是多一台机器人；或把判据放宽到 100°，给 4 台配置留 10° 余量，代价是包围圈在目标高速变向时更容易被穿出。验收线写进文档前，先做这道算术，避免把"理论上存在合格点"当成"工程上可稳定达成"。

时间预算同样可以逐段核算。最不利情形是目标从园区边角进入、最远一台机器人相距约 40 m：以 1.0 m/s 巡逻速度赶路需 40 s，加上到位后的包围整形与速度匹配约 10–15 s，总耗时 50–55 s，落在 60 s 验收线内但余量不足 20%；若最远距离升到 45 m，预算恰好击穿（45 + 15 = 60 s）。这给出两个可执行结论：围捕区的预置点位要保证"任一点到最近机器人 ≤ 40 m"，或者把段内巡航速度提高到 1.2 m/s（40/1.2 + 15 ≈ 48 s）。持圈能力用角速度账校验：R = 1.6 m、目标 1.0 m/s、安全系数 1.3，单机角速度至少 0.81 rad/s；轮距 0.5 m 的差速机器人在左右轮 ±0.5 m/s 差速下可提供 (0.5 − (−0.5))/0.5 = 2 rad/s 的角速度上限，余量约 2.4 倍，说明"围得住"的瓶颈在时间预算与通信时延，不在底盘机动能力。

6. 数值算例：搬运演练的时间预算分解

把 180 s 的验收线拆成可解释的账单：接近与对准 20 s、直线推进 25 m ÷ 0.5 m/s = 50 s、门洞纵队切换与减速 15 s、落位与确认 15 s，合计 100 s，留出 80 s 给队形修正与重对齐。满载后实际巡航速度若掉到 0.35 m/s，直线段变成 71 s，总预算升到 121 s，余量仍有 59 s，说明 180 s 的验收线对速度波动有韧性；反过来，任何一段实测耗时超过预算 30%，例如对准用了 30 s，都应记录为"结构性超支"，在下一轮参数整定中优先处理；靠最后的直线段加速去补会掩盖问题。这份分解也是验收报告里"总耗时 ≤ 180 s（中位数）"这一条的支撑材料：评审用同一张分解表逐段对数，任何超支都有归属。

货箱位姿的融合精度同样可以核算。两台机器人同时观测货箱，若观测方向的标定误差约 1°、观测基线 1.2 m，三角定位的横向误差约 1.2 × tan(1°) ≈ 0.021 m，远小于队形误差预算 0.15 m；只剩单台观测时，相机测距的相对误差 5%、距离 3 m 对应深度误差 0.15 m，恰好吃光整个误差预算。这就是"至少两台同时可见，否则货箱状态不可信"的量化依据，也解释了为什么监控要把"可见机器人数"做成在线指标：从两台降到一台的瞬间，位姿误差预算从 2 cm 级跳到 15 cm 级，队形应立刻降速甚至停车重对齐。

围捕对通信时延的敏感度也可以量化：目标以 1.0 m/s 机动，各机器人看到的目标位姿若平均滞后 200 ms，等效位置偏差就是 0.2 m；包围环容差是 [1.2 m, 2.0 m] 的 0.8 m 带宽，0.2 m 已占其四分之一，再叠加目标转向造成的真实位置差，很容易把某一侧的间距压到环外，判据随即失败。反过来给预算：希望时延贡献的偏差不超过环带宽的 10%（0.08 m），在 1.0 m/s 下对应端到端时延不超过 80 ms。这就是围捕验收把"端到端 ≤ 200 ms"写成底线、把"≤ 100 ms"作为优化目标的由来；也解释了目标位姿话题取 10 Hz 的原因：周期 500 ms 的 2 Hz 方案本身就让新鲜度输掉一半。

实现思路与设计

系统分四层，各层的职责与失败隔离边界要写清楚：

层内容部署失败影响
感知层目标检测（围捕）、货箱位姿融合（搬运）各机本机 + 一次融合检测丢失 → 演练暂停，回退到搜索/重对齐
决策层指挥树（阶段编排）、分配器、黑板车队主机（单点，演练期可接受）指挥失联 → 各机保持当前位置待命（安全默认）
控制层编队/虚拟结构控制器、合围控制器各机本机，100 Hz控制器接管失败 → 单机停车，队形降级
通信层话题/服务/动作 + QoS 表 + 监控统一域 42依据 QoS 表逐话题降级

指挥流程（两演练共用骨架）

  1. READY：自检（定位、电量、话题连通性），向 /fleet/drill_state 广播就绪。
  2. START：裁判发布开始信号；指挥树进入 ACTIVE。
  3. ACQUIRE：搬运=确认货箱位姿；围捕=等待入侵者进入检测区。最长等待 120 s，超时判"环境未就绪"。
  4. EXECUTE：分配角色 → 编队/包围 → 执行（搬运推进/围捕保持）。
  5. FINISH：满足验收条件 → 广播结果 → 各机返回集结位。
  6. ABORT：任何时刻急停或裁判叫停 → 全部停车、货箱若有则安全放下。
设计决策：为什么决策层允许单点，而控制层必须分布？

演练场景中指挥节点故障的概率低、影响可观测（状态广播停更即发现），用单点换来编排逻辑清晰、调试成本低，工程上优先选"可测的简单系统"。但控制层是 100 Hz 闭环，一旦依赖网络指令就会把无线时延引入环路，必死无疑；所以编队与合围控制器必须本机运行。原则：慢决策可以集中，快控制必须分布。这也为第四篇 074/075 章的容错与重构埋下伏笔。

片段 1：指挥树，阶段编排

class DrillCommander(Node):
    """演练指挥：用阶段机（等价于行为树的记忆型 Sequence）编排两条演练流。"""
    PHASES = ("READY", "ACQUIRE", "ASSIGN", "EXECUTE", "FINISH", "ABORT")

    def __init__(self):
        super().__init__("drill_commander")
        self.declare_parameter("scenario", "transport")   # transport | capture
        self.phase = "READY"
        self.t0 = None                                     # 阶段起始时刻，用于超时
        self.create_timer(0.1, self.tick)                  # 10 Hz 与行为树同频
        self.state_pub = self.create_publisher(DrillState,
            "/fleet/drill_state", qos_transient_reliable())

    def tick(self):
        handler = getattr(self, f"phase_{self.phase.lower()}")
        handler()                                          # 每个阶段一个 handler
        self.broadcast_state()

    def phase_acquire(self):
        if self.scenario_ready():                          # 子类/分支实现：货箱可见 or 目标进入
            self.advance("ASSIGN")
        elif self.elapsed() > 120.0:
            self.advance("ABORT")                          # 环境未就绪不能被无限等待

    def phase_execute(self):
        if self.acceptance_met():                          # 指标判定交给独立评估器
            self.advance("FINISH")
        elif self.elapsed() > self.time_limit():           # 180 s / 60 s 来自验收线
            self.abort("timeout")

    def advance(self, nxt):
        self.get_logger().info(f"阶段 {self.phase} -> {nxt}")
        self.phase = nxt
        self.t0 = self.now_s()                             # 每次迁移刷新计时基准

解读：把行为树的"记忆型 Sequence"降维成显式阶段机，是阶段项目里最务实的折中，编排骨架简单到可以一张纸画完，复杂逻辑都在各阶段 handler 里。三个值得学的细节：每次 advance 重置 t0，让超时判据以阶段为单位（全局计时无法反映单阶段是否超支）；ACQUIRE 阶段自带 120 秒环境超时，防止"演练开始但货箱不在视野"时系统傻等；指标判定由独立评估器（片段 2）负责，指挥只关心"是否满足"，不关心"怎么算"，判定逻辑可单独测试与复算。

片段 2：指标采集与评分

class DrillScorer(Node):
    """根据验收口径实时评估：搬运看落点与队形，围捕看包围几何与保持时长。"""
    def __init__(self):
        super().__init__("drill_scorer")
        self.fc = []            # 合围成立/失效的时间区间
        self.form_err = []      # 队形误差采样
        self.create_subscription(RobotStates, "/fleet/robot_states", self.on_states, 10)

    def on_states(self, msg):
        t = self.stamp(msg)     # 使用统一时间源（第 009 章同步后的时钟）
        if self.scenario == "transport":
            e = max(dist(r.pose, self.expected_grasp(r.id)) for r in msg.robots)
            self.form_err.append((t, e))
        else:
            gaps = self.angular_gaps(msg.robots, msg.target)
            in_range = all(1.2 <= r.range_to_target <= 2.0 for r in msg.robots)
            ok = in_range and max(gaps) <= radians(90)
            if ok and (not self.fc or not self.fc[-1][1]):
                self.fc.append([t, None])       # 包围成立：开区间
            elif not ok and self.fc and self.fc[-1][1] is None:
                self.fc[-1][1] = t              # 包围失效：闭区间

    def report(self):
        p95 = percentile([e for _, e in self.form_err], 95)
        held = max((b - a) for a, b in self.fc if b)     # 最长持续包围
        return {"form_p95": p95, "hold_s": held}

    def score(self):
        r = self.report()
        # 评分表：指标→分数映射写在一处，任何人复算结果一致
        return 60 * (r["hold_s"] >= 10) + 40 * (r.get("form_p95", 1.0) <= 0.20)

解读：评估器只订阅一个状态话题（各机汇聚后的 robot_states），保证所有指标基于同一份数据快照计算，如果队形误差用本机自估、包围几何用指挥端融合，两边口径不一致，复算时必然打架。合围用"开/闭区间"记录成立区间，可以同时回答"是否成功"和"保持了多久"；评分公式把指标与分数写在一个函数里，评审或复现时只跑 score() 就能核对。注意 t 取自消息内的时间戳，不用接收时刻：接收时刻会把网络抖动计入指标；时间戳在同步时钟下才是物理真值（前提是第 009 章的同步真的做对了）。

    scenario = LaunchConfiguration("scenario").perform(context)
    nodes = [
        Node(package="fleet_drill", executable="drill_commander",
             parameters=[{"scenario": scenario, "time_limit": 180.0}]),
        Node(package="fleet_drill", executable="drill_scorer",
             parameters=[{"scenario": scenario}]),
        Node(package="fleet_drill", executable="fleet_recorder"),  # 记录 bag 供复算
    ]
    # 名字里带场景参数：一次运行一个目录，10 次实验互不覆盖，满足统计需求
    return nodes

def generate_launch_description():
    return LaunchDescription([
        DeclareLaunchArgument("scenario", default_value="transport",
                              description="transport | capture"),
        DeclareLaunchArgument("rosbag_uri", default_value="drill_00"),
        OpaqueFunction(function=launch_drill),
    ])

解读：launch 里用 OpaqueFunction 让参数在启动时真正参与构造；把 LaunchConfiguration 的延迟求值直接塞进静态 nodes 列表会踩到拼接类型的坑，这是 Python launch 最常见的报错来源。scenario 参数化让两条演练共用一套启动脚本；fleet_recorder 无条件随仓启动，把"记录"变成演练的默认行为，避免"事后补做"式的丢现场，10 次实验里任何一次失败的现场都是改架构的第一手证据。参数里预留 rosbag_uri，你可以在上层脚本里按实验编号循环调用这个 launch，自动完成"跑一次—存档一次"的统计流程。

常见坑

  • 用接收时刻做指标时间基准：不同机器人的"接收时刻"受网络抖动影响，合围时延忽大忽小，无法复现。修复：统一时间源 + 消息内时间戳；实验前用 ros2 run tf2_tools view_frames 与时钟对比脚本验证同步偏差 ≤ 20 ms。
  • 把"演练开始"定义成人按按钮的时刻：从按键到系统真正进入 ACQUIRE 还有启动延迟，10 次计时基准漂移。修复：计时基准取 /fleet/drill_state 的 START 消息时间戳，人工动作只负责触发该消息。
  • 队形误差只在稳态采一次：拍一张"好看的照片"当验收，穿越门洞时的瞬时大幅误差被掩盖。修复：全程采样取 P95，并单独报告门洞姿态切换段的最大值。
  • 围捕期间目标话题降频保带宽：目标位姿从 10 Hz 降到 2 Hz"省带宽"，包围圈像放幻灯片，判定窗口根本围不住。修复：先算清预算，10 Hz 的目标消息（约 100 字节）总共 1 KB/s，围捕的瓶颈从来都在端到端时延，带宽有的是余量。
  • 失败的实验不记录：只保存成功场次，出错原因全靠回忆。修复：记录器对所有场次无条件生效；评分表对超时/碰撞/货箱落地分别编码，方便事后分类统计。

练习与思考

  1. 为"穿越 1.2 m 门洞"设计纵队队形：机器人宽 0.45 m，货箱宽 0.6 m，给出前后间距与进入门洞前的减速策略，并写出队形切换成功的判据（位置误差、航向误差）。★
    提示
    纵队轴线间距 ≥ 货箱半长 + 安全余量（约 1.2 m）；切换判据建议：三机到期望位姿误差均 ≤ 0.15 m、航向误差 ≤ 10°、速度 ≤ 0.3 m/s 且保持 1 s，才允许过门。
  2. 按公式 R·ω ≥ ve(1+ε) 计算：R = 1.6 m、目标 0.8 m/s、ε 取 0.3，单机角速度能力至少多少？如果差速轮在 0.5 m/s 线速度下的角速度上限是 1.0 rad/s，这个配置围得住吗？★★
    提示
    需 ω ≥ 0.8×1.3/1.6 = 0.65 rad/s，能力 1.0 rad/s 有余量但不多；注意线速度越快差速轮的极限角速度越小，应把包围环线速度限制在 0.6–0.8 m/s 区间校验。
  3. 把片段 2 的评分表改成"时间加权"版本：合围时延越短分越高（60 s 对应 0 分、10 s 对应满分），写出公式并说明如何避免"只追求快而忽略保持稳定性"的退化策略。★★
    提示
    可用线性映射分 = 100×(1 − (t−10)/50) 再加"保持时长"门限（未满 10 s 直接判负）；单看速度会导致机器人挤成一团凑几何判据，用角间隙指标与最小间距下限约束堵住。
  4. 为演练写一页 Runbook：列出场地标定（参考点、坐标系）、赛前检查单（电量、时间同步、QoS 连通性、急停测试）、开始信号、失败处置（超时/急停/货箱落地）、数据归档命名规则。★★★
    提示
    检查单必须可勾选可证伪（例如"ros2 topic hz /fleet/target_pose 输出稳定在 10±1 Hz"）；归档命名含日期-场景-场次-结论四段，让 10 次实验能直接按名排序统计。

小结

  • 阶段项目把"故事"翻译成数字：搬运成功率 9/10、围捕 8/10、合围时延 ≤ 60 s、队形误差 P95 ≤ 0.20 m，每条指标都有唯一口径与测法。
  • 搬运的核心是虚拟结构协同：编队误差 + 队形协调项，宁可慢不可摔；围捕的核心是时间账与通信时延：R·ω ≥ ve(1+ε)，端到端 ≤ 200 ms。
  • 架构原则：慢决策可集中、快控制必分布；两个演练只替换任务级子树，共用通信与评估设施。
  • 评估器订阅同一份状态快照、用消息时间戳、全程采样取分位数；记录器无条件生效，失败场次同样是资产。
  • 第三篇到此收束，从编队、覆盖、巡逻到决策与演练。进入第四篇，先把"给任务找人"的分配问题讲透：多机器人任务分配。
