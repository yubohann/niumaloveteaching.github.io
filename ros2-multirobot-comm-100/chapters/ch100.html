第五篇 · 科研进阶与协同机制

第 100 章：多机器人综合作品设计与发布

全课收官：从选题四问到里程碑路线、验收演示脚本、仓库发布清单与答辩叙事，把 99 章的知识焊成一个"能展示、能被追问、能被复现"的完整作品，并回顾整门课程。

  • 主题：综合作品设计与发布（课程收官）
  • 关键机制：选题四问、里程碑与风险、发布闸门、演示脚本化、答辩叙事
  • 预计学时：60 分钟
  • 前置章节：第 099 章

学习目标

  • 会用"选题四问"（场景、差异化、边界、证据）把一个模糊的兴趣收敛成可交付的作品定义。
  • 能制定四段里程碑（可跑 → 机制 → 实验 → 发布）与配套风险表，懂得"控制范围"比"堆功能"更重要。
  • 会写脚本化的验收演示：正常场景 / 故障降级场景 / 极限场景三段演示，全程无人为摆位、可重复执行。
  • 掌握发布工程：仓库结构、README 叙事、版本与 license、验收闸门脚本，把"作品"变成"可被别人复现的资产"。
  • 能设计 7 分钟答辩叙事与高危提问准备，把九十九个章节学到的机制讲成一条完整故事线。

背景与动机

这是全课程最后一章。前 99 章给了你一座机制库：DDS 与 QoS、状态同步、编队与避障、任务拍卖与调度、学习与安全保证、实验设计与论文复现。但机制库本身不是作品，作品是"带场景的问题 + 有取舍的系统 + 有数据的结果 + 可复现的交付物"四件东西的合体。竞赛评委、奖学金与项目的评审、未来的导师，都不会按章节清单考核你，他们只问三句话：你解决了什么问题？凭什么说解决了？我能不能自己验证？

本章把这三句话翻译成工程流程：选题四问让"解决什么问题"有边界；里程碑与验收闸门让"凭什么"有数据；发布清单让"能不能验证"有答案。同时，本章的小结承担收官任务：把五篇一百章的课程地图完整回顾一遍，帮你把散落的机制挂回体系，也为课程结束后的继续深耕留下路线。

核心原理

1. 选题四问：把兴趣收敛成"可交付的作品"

初做作品最常见的失败出在定义太宽，很少是技术不行："我要做一个多机器人协同平台"，这是一句愿望，不是作品。选题四问把它逼细：

问题要写出什么合格标准
场景：谁在什么条件下遇到什么问题？一句场景声明（如：仓库断电检修时，4 台 AMR 需在退化通信下完成 20 个转运任务）包含数字与约束，能画出一张场景图
差异化：与现有方案比，差异在哪根轴上？指名对比对象（某开源栈/某论文），并选定一根轴：更省通信 / 更强鲁棒 / 更优指标"在 X 轴上前进 Y%，代价是 Z"，完整句式
边界：不做什么？明确排除项（不做真机全自主、不做视觉感知、不做 20 台以上）每个排除项写明理由（时间/设备/依赖）
证据：用什么指标证明？指标清单与验收阈值（第 098 章口径）每个指标有测量方法、重复次数与阈值

四问的互锁关系值得体会：差异化决定机制选型，边界决定工作量，证据决定实验设计，四问写完，你的作品其实已经被"倒推"出来了，剩下的只是执行。这也是对第 086 章"设计五问"的作品级复用：一个管机制，一个管作品，逻辑同源。

2. 系统架构收束：五篇课程如何映射到一个作品

回顾全课的五层结构，一个成熟作品在每个层上都应该"有话可说"，但只需有一两层是"亮点"：

层（对应篇）作品里要交代的事可选的亮点层
通信底座（第一篇）域/命名空间、QoS 策略、发现与时间同步方案通信机制选型对比数据
数据协同（第二篇）状态同步协议、坐标系、压缩与带宽账本低带宽状态同步（如第 087 章的增量 + gossip）
协同层（第三篇）编队/避障/任务/规划用了哪些机制、参数何来自研机制（第五篇第 088–097 章任选其一深化）
系统层（第四篇）故障恢复、监控、配置管理、部署流程故障注入验收数据（第 085 章模板）
研究层（第五篇）实验设计、指标口径、复现基准、边界分析实验方法学本身（对照组、CI、敏感性分析）

务实建议：一个作品通常只需要一个通信级亮点 + 一个协同级亮点（例如"低带宽状态协议" + "带安全保证的互惠避障"），其余层用成熟方案"守规矩"即可。层数堆满、每层都半成品，是参赛作品最典型的失败形态。三种常见作品形态的取舍可以放到同一张表里比较：

作品形态亮点分布主要风险证据强度答辩表现
平台型（多亮点并列）通信、协同、系统层各一点范围失控，样样半成品面广但每点浅演示热闹，追问容易失守
机制型（单亮点深挖）集中在一层，纵向到底场景过窄，故事单薄深且可复现追问稳，需要讲清普适性
复现型（复现加改进）公开基线加一处增量增量不明显对照强，有公开基线可查可信度高，创新叙事偏弱

选择依据与你的资源、时间、导师方向三点匹配：能动用的机器人与场地多，选平台型但把实验压在两个亮点上；单机资源也能做但追求理论深度，选机制型；想快速建立可信度并接上后续研究，选复现型再叠一处增量。三种形态并不互斥，但主线只能有一条，其余内容降为支撑材料。

3. 里程碑与风险：四段交付与三条风险线

里程碑不看"完成了多少代码"，看"能演示什么"：

  • M1 可跑（2–3 周）：2 台机器人在最小场景端到端跑通（含一条关键数据流），先证明骨架成立。
  • M2 机制（3–6 周）：核心创新机制接入并单点可测（该机制的指标可复现地测出）。
  • M3 实验（2–4 周）：按第 098 章跑完因子实验，对照基准（第 099 章复现）出数据与图表。
  • M4 发布（1–2 周）：演示视频、仓库、文档、答辩材料齐备；验收闸门全绿。

风险表三条线各自配降级预案：硬件线（实机坏了 → 全部实验切高保真仿真，视频补真机片段）；依赖线（某库/服务不可用 → 提前锁定版本并把关键路径写在本项目内，别把"能交付"押在第三方计划上）；时间线（M2 超期两周 → 砍范围不砍质量：从两个亮点砍到一个，实验规模从 12 格砍到 6 格，但实验方法与验收闸门不砍）。降级预案必须在 M1 结束时写好，超期的那一刻才想"砍什么"，往往砍错地方。

里程碑关键路径 = M1 + M2 + M3 + M4，另留约 20% 缓冲；样本量减半时，比较用的置信区间宽度约放大 √2 ≈ 1.41 倍 四段给定区间相加为 8–15 周，计入缓冲约 10–18 周；实验格数从 12 砍到 6 时总运行次数减半，每个因子的统计分辨率下降，误差棒的宽度约增加四成。这就是"砍范围不砍质量"要守住方法与口径的量化理由

数值算例提醒砍范围的正确切法：把 12 格实验砍到 6 格，样本量减半，同一指标的标准误放大 1.41 倍，如果你的效应量本来只有 2σ 的显著度，砍完就掉到不显著，主张无法成立；反过来，砍"第二个亮点机制"不伤害主实验的统计结构，只是把系统层从双亮点收缩为单亮点加成熟方案。所以降级顺序是先砍并列亮点、再砍实验格数，且砍格数时必须复核每个因子的效应量还能不能撑住结论。

4. 演示脚本化：三段演示代替一次性表演

演示环节的最大坑是"靠人工摆位、靠现场运气"。作品演示应该像测试用例一样脚本化，固定三段：

  1. 正常场景（60–90 s）：任务下达 → 全队协同完成 → 指标实时显示（完成率、通信量、时间）。要点：把"指标显示"做进演示界面，评委亲眼看到数字，比事后幻灯片可信。
  2. 故障降级（60 s）：在中途注入故障（杀进程/断网，第 085 章机制），展示检出 → 重分配 → 恢复的完整时间线（屏幕角落可显示恢复计时）。要点：这是绝大多数作品没有的段落，差异化最直观。
  3. 极限场景（30–60 s）：把因素推到边界（延迟拉高、机器人数加到一个上限）展示性能曲线与边界行为，主动展示边界比被评委追问出边界强。

三段各录一条"备份视频"（含指标水印），现场演示失败时无缝切视频。演练纪律：每次完整跑三段，连续三次全绿才算"演示就绪"，一次成功是运气，连续三次是能力。

实现思路与设计

发布工程四件套与对应清单：

交付物内容要求验收标准
仓库src/ 按包分层、configurations 独立、依赖清单（rosdep 风格）、一键启动脚本新机器按 README 三步内跑起最小 demo
README一段话简介 + 演示动图 + 安装 + 运行 demo + 指标摘要表 + 引用格式不识项目的人 10 分钟内能复现演示
发布版本tag（v1.0.0）、LICENSE（如 Apache-2.0，注明第三方构件许可）、CHANGELOG发布闸门脚本全绿（见代码片段 1）
数据与视频实验原始 CSV + 分析脚本 + 三段演示视频图中每个数字可追到 CSV 某行（第 098 章口径）

README 的叙事顺序决定第一印象，推荐五段式：① 一句话（做什么、亮点是什么）；② 演示动图（10 秒看完）；③ 快速开始（复制三条命令能跑）；④ 数据摘要表（3–5 个关键指标 + 口径注明）；⑤ 结构与引用。常见错误是把 README 写成开发笔记（先讲目录再讲功能），读者不关心你的目录，只关心"这能不能用、有多好、怎么跑"。

答辩叙事（7 分钟版骨架）

段落时长内容
问题与场景1 min场景声明 + 一张图；点出"现有方案在 X 轴的不足"
现场演示2 min三段演示（或视频），指标实时可见
机制解释1.5 min只讲两个亮点机制的原理与取舍（对应系统架构收束的两个亮点层）
数据与证据1.5 min对照实验 + CI + 故障注入结果；一句话边界声明
展望与边界1 min明确"不做什么"与"下一步做什么"，展示工程判断力

高危提问预演（每题准备 30 秒答案）："和 XX 开源方案比怎么样？"（拿对照数据答）、"多台时会不会崩？"（拿极限场景曲线答）、"实验重复了几次、有没有置信区间？"（第 098 章口径答）、"如果评委现在改一个参数会怎样？"（现场改演示参数跑一格的胆量来自脚本化演示）。这四个问题回答稳了，答辩基本盘就稳了。

关键代码与解读

片段 1：发布闸门，每个检查项一行断言

import subprocess, sys

def sh(cmd):
    """执行命令并返回标准输出（strip 便于比较）。以对应环境为准。"""
    return subprocess.run(cmd, shell=True, capture_output=True,
                          text=True).stdout.strip()

def release_gate(tag="v1.0.0"):
    """发布闸门：全部通过才允许打 tag。自动化的"发布纪律"。"""
    checks = [
        ("工作区干净", sh("git status --porcelain") == ""),
        ("测试全过", "failed" not in sh("python -m pytest -q").lower()),
        ("版本一致", tag.lstrip("v") in sh("cat setup.py")),
        ("许可存在", sh("ls LICENSE") != ""),
        ("README 含演示入口", "demo" in sh("cat README.md").lower()),
        ("演示视频存在", sh("ls docs/demo_*.mp4") != ""),
    ]
    failed = [name for name, ok in checks if not ok]
    if failed:
        print("发布被拒：", "、".join(failed))
        return False
    print(f"发布检查通过：可打 tag {tag}")
    subprocess.run(["git", "tag", "-a", tag, "-m", f"Release {tag}"])
    return True

release_gate()

解读：闸门脚本把"发布"从仪式变成流程，六个检查项覆盖了发布最常见的疏漏（改了没提交、测试挂了、版本没升、忘了 license、README 不会用、视频没录）。两个工程思路值得迁移：（1）检查项用"人类可读的名字 + 布尔"组织，失败时打印的是"许可存在"这样的检查名，非工程队友也能看懂哪里没准备好（一串报错码做不到这一点）；（2）通过即打 tag，把"打标签"与"检查通过"绑定，防止"先打 tag 再补检查"的自我欺骗。注意 pytest 与 setup.py 的写法以你的实际项目为准（ROS2 项目可能是 colcon 与 package.xml），骨架不变。

片段 2：演示脚本化，launch 里把"场景"变成参数

from launch import LaunchDescription
from launch.actions import DeclareLaunchArgument
from launch.substitutions import LaunchConfiguration
from launch_ros.actions import Node

def generate_launch_description():
    # 场景（normal / fault / stress）是参数：演示与实验用同一份编排
    scenario = DeclareLaunchArgument("scenario", default_value="normal")
    robots = [
        Node(package="fleet_demo", executable="robot", namespace=f"robot{r}",
             parameters=[{"robot_id": r, "scenario": LaunchConfiguration("scenario")}])
        for r in (1, 2, 3, 4)
    ]
    manager = Node(package="fleet_demo", executable="fleet_manager",
                   parameters=[{"scenario": LaunchConfiguration("scenario")}])
    # 故障注入器只在 fault 场景下工作（自身判断参数后决定是否行动）
    injector = Node(package="fleet_demo", executable="fault_injector",
                    parameters=[{"scenario": LaunchConfiguration("scenario")}])
    return LaunchDescription([scenario, *robots, manager, injector])

解读：脚本化演示的秘密全在"同一份编排、不同参数"：演示与实验共用这套 launch，意味着演示跑的就是实验的系统，评委问"演示和论文数据是一套系统吗"，答案是"同一套代码、不同的启动参数"。故障注入器作为常驻节点、由场景参数决定行为，比"演示时手工 kill 进程"高级的地方在于：注入时刻精确（可复现）、注入类型可配（进程死亡/网络分区/急停三种，第 085 章矩阵）、且注入事件自动打点进指标记录器（恢复时间自动测量）。这四个机器人 + 管理 + 注入器的编排结构可以直接作为你作品的骨架。

片段 3：验收闸门，把发布条件写成可执行阈值

def acceptance_gate(metrics, spec):
    """作品验收闸门：指标脱靶就不允许发布（阈值在开发前写死）。"""
    results = [
        ("任务完成率",      metrics["completion_rate"] >= spec["completion_min"]),
        ("P95 恢复时间",    metrics["recovery_p95_s"] <= spec["recovery_p95_max"]),
        ("重复执行率",      metrics["dup_rate"] <= spec["dup_rate_max"]),
        ("通信负载",        metrics["bytes_per_robot_s"] <= spec["bw_max"]),
        ("极限场景完成率",  metrics["stress_completion"] >= spec["stress_min"]),
    ]
    failed = [name for name, ok in results if not ok]
    for name, ok in results:                    # 逐项打印：报告与录像都引用这行
        print(f"[{'PASS' if ok else 'FAIL'}] {name}")
    if failed:
        print("验收未通过：", "、".join(failed))
        return False
    print("验收通过：允许发布")
    return True

# 阈值示例（开发前与导师/队友对齐后写死）：
SPEC = {"completion_min": 0.95, "recovery_p95_max": 4.0, "dup_rate_max": 0.0,
        "bw_max": 3000, "stress_min": 0.80}

解读：这段代码是第 085 章验收表与第 098 章指标口径的最终合体。三个细节：（1）阈值写死在配置（SPEC）里且在开发前确定，防止"跑出来多少就以多少为合格"的目标漂移，这与第 098 章"预注册指标"是同一条纪律的作品级执行；（2）逐项打印 PASS/FAIL 行，演示视频与答辩材料可以直接引用终端输出，成为"证据链"的一环；（3）极限场景单独列为闸门项，正常场景达标容易，把"压力下限"也放进发布条件，保证作品在评委加码提问时不会崩。指标名（如 completion_rate）与你的记录器对齐，整个闸门就是三个文件的协作：配置、指标 CSV、本函数。

常见坑

  • 范围失控：想做的事越来越多（加视觉、加机械臂、加真机），到最后没有一个场景能完整演示。修复：选题四问的"边界"先写死；任何新增都用降级预案的"砍范围不砍质量"原则处理。
  • 演示依赖人工摆位：机器人起始位置手摆、任务手工下、时间点靠喊，换个评委跑第二遍结果就变了。修复：launch 参数化场景 + 脚本化任务流 + 连续三次全绿才算就绪。
  • 只有代码没有文档、LICENSE 与版本：评委想看"怎么用"却只能听你现场讲二十分钟；仓库没有 license 别人不能用；改了代码没打 tag 复现对不上版。修复：README 五段式加十分钟原则（陌生人十分钟跑起 demo）；发布闸门脚本把 license 与打 tag 自动化，缺一不可。
  • 实验数据没有可追溯链：PPT 上一个 95%，问"哪测的"翻不出来。修复：图表 → 分析脚本 → 原始 CSV → 运行 run_id 的链条完整（第 098/099 章的产物规范）。
  • 答辩只讲技术细节：七分钟里六分钟讲公式，评委不知道你解决了什么问题。修复：按七分钟骨架排练，把"问题—演示—机制—数据—边界"的叙事顺序立在第一位；技术细节留给提问环节。

练习与思考

  1. 写一页"选题四问"：用一个你真实感兴趣的多机器人场景，逐问作答（各 3–5 句）。自检标准：场景里有数字、差异化是完整句式（"在 X 轴上 Y%，代价 Z"）、边界至少三条、指标至少三条带阈值。★
    提示
    退化测试：把这一页给完全不懂的同学看，如果他能复述"你做什么、凭什么、做到什么程度算完成"，四问就算合格；如果他说"听起来很厉害但不知道你要干嘛"，回去重写"场景"与"证据"两栏。
  2. 改配置并预测结果：你的演示总时长预算 3 分钟，正常/故障/极限三段各分配多少？如果现场只剩 90 秒，你砍哪一段、保留哪个指标必须露脸？先写下预测，之后用真实排练验证节奏。★
    提示
    预算示例：90/60/30 秒。仅剩 90 秒时保留"故障降级段"或"正常段的指标展示"，评委对"别人没做的部分"（故障恢复）记忆最深；极限段改为一句口播数据。核心判断：演示的目标是"被记住一个差异点"，不是"展示全部功能"。
  3. 设计：为你的作品写里程碑计划（M1–M4）与风险表：每条风险配触发信号与降级动作（硬件、依赖、时间三线各至少一条）。★★
    提示
    触发信号要"可观察"：如"M2 过半时机制单测仍未通过"、"实机连续两次在演示序列中掉线"。降级动作要"可执行"：切换仿真、砍亮点数、缩实验格数，每条都注明代价（哪项指标/视频素材会受损）。
  4. 设计：写出你的三段演示脚本（场景名、启动命令、预期时间线、显示哪些指标、注入什么故障、验收观察点），要求每一段都能被队友在无人指导下重复执行。★★
    提示
    脚本要素照抄本章"演示脚本化"一节；故障段的时间线写成表（T+0 启动、T+20 s 注入、T+22 s 预期检出、T+30 s 预期重分配完成）；验收观察点给出数字阈值，演示结束后 30 秒内能判"过还是不过"。
  5. 综合：完成一次"模拟发布"，用片段 1 的闸门脚本（改造成你的项目）、README 五段式初稿、七分钟答辩稿大纲 + 四个高危问题的 30 秒答案。找一位同学扮演评委完整走一遍，记录被问倒的问题并修复。★★★
    提示
    评委彩排的关键是"真问真答"：让扮演者随意挖坑（参数、边界、口径、对比），仔细记录你卡壳的位置，每个卡壳点都是一份待办。彩排后把修复内容合并进仓库与讲稿，再跑一次闸门脚本。

小结

  • 作品 = 场景问题 + 有取舍的系统 + 有数据的结果 + 可复现的交付物；选题四问（场景/差异化/边界/证据）是全部工作的收敛器。
  • 里程碑四段：可跑 → 机制 → 实验 → 发布；风险三线（硬件/依赖/时间）在 M1 结束就配好降级预案，超期时"砍范围不砍质量"。
  • 演示三段脚本化：正常（指标可见）、故障降级（别人没做的差异点）、极限（主动亮边界）；连续三次全绿才算就绪，备份视频兜底。
  • 发布四件套：仓库（十分钟复现）、README 五段式、tag + LICENSE + CHANGELOG、数据与视频证据链；发布闸门与验收闸门用脚本说话。
  • 答辩七分钟：问题 → 演示 → 机制 → 数据 → 边界；四个高危问题（对比、规模、统计、现场变参数）提前备好 30 秒答案。

全课程回顾：五篇一百章的一张地图

  • 第一篇 通信基础（001–020）：DDS 发现、Domain 与命名空间、QoS 合同、带宽与延迟预算、仿真与编排，一切协同的物理与中间件底座；核心心法是"排障自下而上，预算按峰值算"。
  • 第二篇 · 数据分发与协同感知：状态同步、零拷贝与压缩、统一坐标与时间对齐、协同建图与融合、网络分区下的一致性，多机器人共享世界观的建立；核心心法是"语义决定通道，口径决定精度"。
  • 第三篇 · 协同控制与任务协同：编队、避障、规划、探索搜索、搬运围捕、行为树决策，从"各自为战"到"整体行动"的机制库；核心心法是"拓扑即算法，仲裁与平滑保执行"。
  • 第四篇 · 系统集成与工程化：任务分配与调度、QoS 保障与安全通信、故障检测与动态重构、基准测试与故障注入、仿真到真机、运维与版本、协同学习与运动规划入门，把机制变成可交付系统；核心心法是"验收指标说话，故障恢复成对设计"。
  • 第五篇 · 科研进阶与协同机制：机制设计方法论统领，十一个机制专题各攻一个系统视角（通信协议、感知、决策、学习、控制、导航、避障、编队、博弈、调度、路径），再以实验设计、论文复现、综合作品三连收口；核心心法是"三轴权衡（最优性-通信-鲁棒性）与三层对齐（问题-方法-结果）"。
  • 课程到此结束，但你的系统才刚开始：选一个场景，走完一次"四问 → 四里程碑 → 三段演示 → 发布闸门"的完整循环，你在第一百章之后收获的是一件能拿得出手的作品；课程知识清单只是它的原料。感谢同行一百章，祝你的车队一路绿灯。
