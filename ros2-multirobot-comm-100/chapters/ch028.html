第二篇 · 数据分发与协同感知

第 028 章：多机器人SLAM协同

每台机器人各自 SLAM 只能看到局部；本章讲它们的地图与轨迹如何"互相纠正"，位姿图的弹簧直觉、会合约束的形成、以及分布式优化需要交换什么、不需要交换什么。

  • 主题：地图协同 / 同时定位与建图
  • 关键机制：位姿图优化、机器人际回环（rendezvous 约束）、集中式与分布式协同架构
  • 预计学时：60 分钟
  • 前置章节：第 027 章（动态地图更新共享）

学习目标

  • 理解位姿图的构成与优化目标：节点、边、信息矩阵与"弹簧网络"的直觉。
  • 掌握多机器人 SLAM 的两类架构：集中式全局优化与分布式增量优化，及其通信量差异。
  • 理解机器人际回环（inter-robot loop closure）从会合检测到约束生成的全过程。
  • 知道协同 SLAM 里该交换什么（约束、锚点、摘要），以及哪些东西不必交换（稠密点云、原始扫描）。
  • 能判断你的系统需要"真协同"还是"各扫各的最后合并"，两者成本差一个量级。

背景与动机

第 026、027 章把"已经建好的局部地图"拼起来，但那只是后处理：每台机器人的轨迹误差已经在各自地图里"固化"了，如果机器人 A 的长走廊漂移了 30 cm，合并后的全局地图就带着这 30 cm 的错位。真正的协同 SLAM 不止于拼图，其核心是让机器人们在建图过程中互相提供约束：B 在会合点看到的 A 的旧地图特征，可以反过来修正 A 的轨迹，就像单机 SLAM 里"回到起点"的回路闭合一样，只不过这次闭合发生在两台机器人之间。

这也是分布式机器人系统里最优雅的一类问题：用极少的通信量（相对位姿约束只有几十到几百字节）换取全局地图质量。对比之下，交换原始激光/点云动辄每秒数 MB。理解"传约束不传数据"的分寸感，是本章最重要的工程收获。它与第 029 章的分工：本章管"地图与轨迹的联合优化"，第 029 章管"实时位姿估计的融合"。

核心原理

1. 位姿图：用"弹簧网络"理解 SLAM 后端

单机 SLAM 的后端通常归结为一个位姿图（pose graph）：节点是机器人各时刻的位姿 x1, x2, …（位置 + 朝向），边是两条位姿之间的相对变换观测，连续位姿之间来自里程计的"短边"，回路闭合时的"长边"来自扫描匹配。每条边带一个信息矩阵 Ω（测量越可靠，Ω 越大）。优化目标是最小二乘：

min Σ(i,j)∈E eijt Ωij eij，eij = (xi−1xj) ⊖ zij zij 是观测到的相对变换；⊖ 表示变换之差（平移差 + 角度差）

把它想象成一张弹簧网：每个节点是一个珠子，每条边是一根弹簧，弹簧的自然长度等于"观测到的相对位姿"。优化过程就是让整张网的总弹性势能最小，某一根弹簧的拉伸，会通过网传递到很远处的节点。这正是远端回环能修正整条轨迹的原理，也是多机器人协同的立足点：机器人之间新增一根弹簧（会合约束），两侧的整段轨迹就会互相"拉齐"。

2. 两类协同架构：集中式 vs 分布式

架构做法通信量优点风险
集中式各机上传位姿图/子图摘要到服务器，全局优化后下发修正每机每轮几十 KB 级实现简单，全局最优性好单点依赖、链路中断即停
分布式各机只与通信半径内邻居交换位姿/子图锚点，本地迭代求解随邻居数线性增长，常为 KB 级无中心、容错好收敛慢、需处理拓扑变化

选择的判断标准：有稳定的车队网关（如车间里的基站）→ 集中式省事；无中心、机器人群漂移作业（如野外编队）→ 分布式必需。两者可以混合：平时分布式运行，回到基地后集中式做一次"全量精修"。

3. 机器人际回环：会合检测与约束生成

协同 SLAM 的关键原料是跨机器人约束。它通常这样产生：

  1. 会合发现：两机距离足够近（基于各自上报的全局位姿粗判，第 029 章的定位输出），或观测到对方的视觉标记/共享地理特征；
  2. 相对观测：用激光互扫、共享地标匹配或视觉标定板，估计出两机之间的相对位姿 zAB（含不确定度）；
  3. 约束入图：把 (A 的某时刻位姿, B 的某时刻位姿, zAB, Ω) 作为一条边加入双方的位姿图；
  4. 时间对齐：两个位姿节点的时间戳必须对应同一物理时刻（第 030 章），否则"会合时的相对位姿"张冠李戴。

注意信息矩阵的估计：一个仅凭一次 UWB 测距的约束应该 Ω 很小（弱约束），一次高质量的点云匹配可以有强 Ω。Ω 的诚实程度决定优化的可信度，虚高的 Ω 会让地图被噪声"拽跑"。

4. 分布式优化：为什么以及怎么收敛

分布式求解的思路是"各扫门前雪 + 轮流对齐公共变量"。常见两类协议：

  • 分布式高斯-赛德尔：每个机器人只优化自己的位姿节点，但把邻居共享节点的最新值当作固定量；一轮一轮交替进行下去。直觉：两个工匠轮流对齐各自半张拼图，直到接缝不再变化。
  • ADMM 类对偶分解：把"共享变量必须一致"做成惩罚项，子问题并行求解 + 对偶变量更新。收敛理论更完整，但需要调罚参数。

收敛速度取决于通信拓扑：链式拓扑收敛最慢（信息要沿链传播），全连接最快；还有一个常被忽略的量化事实，每次迭代的通信量很小（几十个节点位姿 × 每项几十字节），所以"多迭代几轮"通常在带宽预算内，真正稀缺的是"两机什么时候能见面通信"。这与第 041 章一致性协议的直觉相通：连接性（connectivity）是分布式算法的第一前提。

设计决策：协同 SLAM 交换什么？

交换顺序按"信息密度 × 实时性"排：① 跨机约束（首选项）：几十字节，直击优化目标；② 子图锚点与摘要：位姿 + 边界特征，几百字节到几 KB，用于地图拼接与匹配；③ 压缩特征/描述子：KB–MB 级，需要时按需拉取；④ 原始扫描/点云：几乎不交换（除本机本地）。把这张优先级表贴在架构文档里，能省下很多"要不要传点云"的争论。

5. 数值算例：一条会合约束拉齐两侧轨迹

用一条最简的轨迹链看清"弹簧"的作用。机器人 A 与 B 各自的位姿图都是一条 10 节点的链（节点间距 1 m，共 10 m 路程），两机起点锚定在同一参考系、误差为零；走完一圈后各自漂移：A 的末端估计位置比真实位置多出 30 cm，B 少 10 cm。一次会合观测到的相对位姿与当前估计相差 40 cm。

把这条约束当作一根强弹簧加入两张图。由于两链的起点被锚定、弹簧刚度相同，修正量在两条链之间对半分配：每条链的末端被拉回 20 cm。拉力沿链均匀摊开，链上第 k 个节点的修正量约为 0.2 m × k ÷ 10，即首端 2 cm、中点 10 cm、末端 20 cm，沿链线性过渡。这就是"远端回环修正整条轨迹"的定量版本：修正的手段是把误差分摊到全链，末端并不做一次性对齐；单个节点的位姿跳变因此很小（本例每步 2 cm），轨迹形状保持连续。

算例还给出三条实现纪律。第一，锚点必须有。去掉两端的全局锚定后，40 cm 的错位在两张自由链之间分配时，整体平移分量无人约束，弹簧网可以整体平移而不改变任何一个弹簧的拉伸；这对应真实系统里"world 基准由标定锁定，优化器不能移动它"。第二，相对一致与绝对正确是两码事。修正后 A、B 末端都停在 +10 cm，两机之间的相对几何已经正确，共同的 10 cm 残余偏移需要绝对观测（回到已知点、卫星定位或高质量回环）才能消掉。第三，修正量要全链更新。只把会合点末端拉 20 cm、链上其余节点不动，等于让最后一根弹簧独自拉伸，下一次优化会把这份拉伸弹回去，系统在两套解之间来回震荡；正确做法是解算全链、批量更新所有位姿，再同步重投影地图（片段 3）。

6. 失效模式与边界条件

  • 修正阶跃冲击控制环：map → odom 一步跳 20 cm，依赖 map 系的高频控制器会看到位置突变。边界动作：对修正做限速平滑（如每秒不超过 5 cm 与 2°），大跳变单独打日志并复核约束来源。
  • 位姿图规模无界：长时间运行后节点数万，每次优化成本与内存持续上升。边界动作：滑窗边缘化旧节点或按子图裁剪，但必须保留仍被回环引用的地标与锚点，裁剪策略要与约束生命周期一起设计。
  • 有偏的会合观测：自遮挡、标定板角度过大或时钟残留使相对位姿带系统偏差，强 Ω 会把两侧地图整体拽歪。对策：Ω 按残差估计、配合鲁棒核函数与卡方检验剔除离群约束。
  • 对称拉锯：分布式的 A、B 同时更新共享变量且步长为 1 时，强耦合约束下可能互相过冲。对策：小步长（如 0.5）、确定性更新顺序（按 id 轮流主导），并监控相邻两轮修正量的衰减。
  • 通信量误估：约束消息本身只有约 250 B，但一轮迭代要交换最多 50 个共享位姿（约 600 B），几十轮下来约 30 KB，仍远小于交换一帧 3 万点扫描的 480 KB（约 1900 倍差距）。边界：真正稀缺的是"两机物理接近"的窗口，迭代的字节数可以忽略。

实现思路与设计

搭建协同 SLAM 的六步：

  1. 现状盘点：先明确单机 SLAM 的输出（位姿话题、地图话题、子图结构），确定协同插入点，通常挂在"位姿图后端"外侧，不动前端。
  2. 选架构：按上表判断集中式/分布式/混合；集中式先跑通，再谈分布式。
  3. 定义交换消息：PoseGraphEdge（两端节点、相对位姿、Ω、时间戳）、SubmapAnchor（子图 id、锚点位姿、覆盖范围）。消息要小、要带不确定度。
  4. 会合流程：近邻检测 → 相对观测 → 约束生成 → 双方各自入图 →（集中式时）上传服务器。
  5. 优化循环：本地位姿图按固定周期（如 1 Hz）优化；优化后把修正量作用到地图与 TF（map → odom 修正，第 024 章的边）。
  6. 验收：两机重叠区对齐误差（第 026 章冲突率或专门的对齐评估）、协同后轨迹相对单机的改善量、会合约束的数量与质量和运行中的收敛震荡。
参数起点值依据
会合判定距离3–5 m保证相对观测质量；过远观测噪声大
优化周期1 Hz（本地）地图与轨迹是慢变量；控制环另走高速通道
约束频率上限每个会合事件 1 条重复约束会让同一证据被多次计入

关键代码与解读

片段 1：会合检测与跨机约束生成

def detect_rendezvous(pose_self, pose_other, stamp, min_gap=3.0, max_gap=5.0):
    """基于双方上报的全局位姿粗判会合：距离进入 [min_gap, max_gap] 才值得观测。"""
    dx = pose_other[0] - pose_self[0]
    dy = pose_other[1] - pose_self[1]
    dist = (dx * dx + dy * dy) ** 0.5
    if dist < min_gap:
        return None                     # 太近：可能互相遮挡，观测质量差
    if dist > max_gap:
        return None                     # 太远：测距/匹配噪声主导，不生成约束
    # 相对观测 z：这里示意为"基于共享特征匹配的相对位姿"（鲁棒估计后）
    z, omega = estimate_relative_pose(self_id, other_id, stamp)
    edge = PoseGraphEdge()
    # 节点命名 = 机器人 + 时刻：优化器必须能精确定位"谁的哪个位姿"
    edge.node_a = f"/{self_id}/pose_{stamp.sec}"
    edge.node_b = f"/{other_id}/pose_{stamp.sec}"
    edge.dx, edge.dy, edge.dtheta = z          # 相对平移与相对航向
    edge.info = omega                          # 信息矩阵：由匹配残差估计
    edge.stamp = stamp                         # 同一时刻，约束才有物理意义
    return edge

解读：这段"会合检测"代码体现了约束生成的三条纪律。（1）距离窗口是双边的：太近（< 3 m）时两机可能互相遮挡、激光互扫变成"面对面"的死角；太远（> 5 m）时相对观测的不确定度快速膨胀。（2）节点命名直接编码"机器人 + 时刻"：优化器需要精确定位"哪个时刻的哪个位姿"，模糊的节点引用是分布式优化最阴险的 bug 来源。（3）约束必须携带信息矩阵与时间戳：前者告诉优化器"这条观测有多可信"，后者保证两端位姿对应同一物理时刻，缺了时间戳，两机时间差会被当成真实位移吃掉。工程实现里，会合判定还应有去抖和"同一会合事件只生成一条约束"的判据，防止重复计数。

片段 2：分布式优化的"直觉版"，Gauss-Seidel 式交替松弛

def relax_once(pos, edges, anchor=0, step=0.5):
    """一轮松弛：对每条边把两端位姿互相拉向"观测相对位姿"。
    pos: (N, 3) 数组（x, y, theta）；edges: (i, j, dx, dy, dtheta, w)。
    这是分布式高斯-赛德尔的极简直觉版：生产系统请用 GTSAM/Ceres 等库。"""
    import numpy as np
    pos = pos.copy()
    for (i, j, dx, dy, dtheta, w) in edges:
        if i == anchor or j == anchor:
            continue                      # 锚点固定：全局基准不可动
        # 当前两节点的相对位姿与观测的偏差（旋转按小角度近似处理）
        ex = (pos[j, 0] - pos[i, 0]) - dx
        ey = (pos[j, 1] - pos[i, 1]) - dy
        eth = (pos[j, 2] - pos[i, 2]) - dtheta
        # 每端各承担一半修正，按权重 w（信息矩阵的标量简化）缩放
        pos[i] += step * np.array([ex, ey, eth]) * w * 0.5
        pos[j] -= step * np.array([ex, ey, eth]) * w * 0.5
    return pos

def run_until_stable(pos, edges, iters=50, tol=1e-4):
    """交替迭代直到最大修正量小于阈值：分布式协议的收敛判据。"""
    for k in range(iters):
        new = relax_once(pos, edges)
        delta = float(abs(new - pos).max())
        pos = new                          # 本地求解后广播共享节点的新值
        if delta < tol:                    # 收敛：接缝不再变化
            return pos, k
    return pos, iters

解读：这段代码是"位姿图优化"的玩具版本，但它的结构映射了真实分布式协议的全部要素。（1）锚点固定：没有锚点的弹簧网会整体漂移到无穷，全局基准（第一台机器人初始位姿或 world 原点）必须锁定，对应真实系统里"world 原点由标定确定，不可被优化移动"。（2）两条边对两端的拉拽是对称的（各承担一半）：这正是共识协议的味道，信息通过边的传递让两端慢慢达成一致，与第 041 章的拉普拉斯共识同构。（3）tol 与迭代上限是分布式算法的必备控制项：通信中断时外部循环会停在那里反复重试，本地的一轮迭代必须有界。（4）注释里说明"生产用 GTSAM/Ceres"是诚实的做法：真实的位姿图优化要处理旋转流形、稀疏 Cholesky、鲁棒核函数，玩具代码的价值只在于把算法骨架和通信模式讲清楚。

片段 3：修正落地，把优化结果变成 TF 与地图更新

def apply_correction(self, map_to_odom_delta):
    """优化产生的修正作用在 map->odom 边上：位姿立刻生效，历史地图同步平移。
    map_to_odom_delta: (dx, dy, dtheta)，即优化前后该机器人位姿的差值。"""
    # 只在"慢通道"上更新：map->odom 允许跳变，odom->base_link 绝不动
    self.correction[0] += map_to_odom_delta[0]
    self.correction[1] += map_to_odom_delta[1]
    self.correction[2] += map_to_odom_delta[2]
    self.publish_map_to_odom(self.correction)   # 50 Hz 动态广播（第 024 章）
    # 地图是被优化的对象之一：子图/栅格按同一变换重投影，保持与位姿一致
    self.remap_existing_map(map_to_odom_delta)
    self.get_logger().info(
        f"应用协同修正 dx={map_to_odom_delta[0]:.3f} "
        f"dy={map_to_odom_delta[1]:.3f} dth={map_to_odom_delta[2]:.3f}",
        throttle_duration_sec=5.0)

解读：优化结果必须"落地"才有效，而落地方式直接决定系统是否稳定。（1）修正施加在 map → odom 这条边上，是因为它在 REP-105 语义里就是"全局一致性与局部连续性之间的接缝"，跳变被允许、且不会破坏控制环依赖的平滑性。（2）地图与位姿必须同步修正：只改位姿不改地图，旧栅格会与新位姿不对齐，表现为"地图整块错位"；只改地图不改位姿，导航轨迹会漂移。（3）日志节流（5 秒一条）在协同运行中很实际：优化修正高频出现时，日志本身也会成为性能负担。

常见坑

  • 没有统一时间基就生成会合约束：两机时间差 100 ms、各以 1 m/s 运动，约束里混入 10–20 cm 假位移，优化越"努力"地图越歪。修复：时间同步（第 009 章）后再生约束。
  • 信息矩阵虚高：给一次低质量匹配也填大 Ω，噪声获得"权威"，把好轨迹拽跑。修复：Ω 由匹配残差/特征数量估计，宁可保守。
  • 重复约束：两机会合 10 秒内生成了 200 条约束，等价于把同一证据重复计入 200 次。修复：每次会合事件最多一条；不同事件要求位姿差异足够大再生成。
  • 优化后忘记重投影地图：位姿与栅格脱节，导航用旧地图"撞墙"。修复：apply_correction 里地图与位姿同步更新（片段 3）。
  • 分布式迭代无超时：邻居离线后本地循环等待响应，整个协同停摆。修复：每轮外部迭代设置超时与降级（无邻居时用上一次的解继续本地运行）。

练习与思考

  1. 用 4 个节点、3 条边的手工位姿图（其中一个节点位置故意偏 0.5 m）跑片段 2 的松弛，观察需要多少轮收敛、锚点选择对结果的影响。★
    提示
    误差会按权重"摊"到各边上；锚点不动时其余节点向其对齐。改变锚点会整体平移解，这解释了为什么全局基准必须外部指定。
  2. 把会合约束的信息矩阵权重从 1.0 改成 10，预测优化后地图对齐误差与轨迹形状的变化。★★
    提示
    高权重让两机被"强拉"到会合观测上；若观测有偏，轨迹被带斜。可与第 029 章的加权融合呼应：权重的意义是信任度。
  3. 设计对比实验：同一段数据，(a) 各机独立 SLAM + 最后合并；(b) 协同 SLAM（会合约束入图）。量化两者在重叠区的对齐误差、走廊末端的漂移差异。★★
    提示
    关键控制变量：相同数据、相同标定。预期 (b) 在远端回环受益明显（漂移被约束"拉回"），但要注意会合观测质量差时 (b) 也可能变差。
  4. 设计题：为 3 台机器人设计分布式协同 SLAM 的"会合协议"：谁发起、如何互认、约束如何生成与去重、断连后如何继续。★★★
    提示
    发起可用距离阈值 + 随机延迟防碰撞；互认用各自全局位姿粗对齐；去重靠"已配对事件表"；断连后本地优化继续，恢复后再交换增量约束。
  5. 思考：为什么说"多迭代几轮"在协同 SLAM 里通常不算成本，而"见面通信"才是稀缺资源？把你的系统的通信机会画在时间轴上再看一遍。★★★
    提示
    约束消息只有几十字节，迭代几十轮也就是几 KB；但机器人要物理接近才能产生高质量观测，机会窗口以分钟计。

小结

  • SLAM 后端 = 位姿图的弹簧网络；多机协同 = 在两张网之间加"会合弹簧"，让远端轨迹互相拉齐。
  • 架构选择看基础设施：有稳定网关用集中式，无中心场景用分布式；混合方案是现实工程的常态。
  • 跨机约束 = 相对位姿 + 信息矩阵 + 时间戳；Ω 要诚实，重复约束必须去重。
  • 协同交换的优先级：约束 ≫ 锚点/摘要 ≫ 特征 ≫ 原始数据；"传约束不传点云"是核心纪律。
