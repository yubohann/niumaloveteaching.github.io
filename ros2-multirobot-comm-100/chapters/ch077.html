第四篇 · 系统集成与工程化

第 077 章：通信压测与故障注入

把系统推下悬崖看看它会不会飞：用阶梯/脉冲负载找到容量"膝盖点"，用受控的故障注入（丢包、延迟、杀进程、断分区）验证降级与恢复路径，每一步都可回滚、可判据、可复盘。

  • 主题：系统集成 / 压力测试与混沌工程
  • 关键机制：负载曲线、故障注入分类、场景编排、自动回滚与判据前置
  • 预计学时：60 分钟
  • 前置章节：第 076 章

学习目标

  • 区分基准测试与压测的目标：基准测稳态质量，压测找容量上限、验证退化行为。
  • 掌握负载模型设计：阶梯、斜坡、脉冲三类曲线的用途，以及合成负载与 bag 回放的取舍。
  • 会按五类故障（资源、网络、节点、数据、时钟）设计注入方案，并预写"预期系统反应"。
  • 能写出"判据前置 + 自动回滚 + 全程观测"的压测场景脚本，杜绝"测完连不上"的事故。
  • 会用注入结果反推容量线与改进项，把结论落到架构决策（分域、限流、降级阈值）。

背景与动机

第 076 章的基准告诉我们"平静水面下系统跑多快"，但生产环境的常态是风浪：WiFi 信道被占、某台机器人突然回传一帧未压缩图像、交换机过热丢包、系统里混进一个不听指挥的节点。这些情况平时没有，出事时集中爆发，只测过"稳态"的系统等于只考了开卷题。

压测与故障注入是把系统的容错设计（072 降级、074 恢复、075 重构）拿出来"实战验货"的过程。核心原则与测试工程一致：先声明预期（注入发生时应触发哪个降级档、多久恢复），再看实际，最后对比差距。没有预写判据的注入只会产生"感觉还行"的结论，等于白测。

核心原理

1. 负载曲线：三种推法找不同答案

曲线形态回答的问题注意
阶梯（step）每 2 min 抬一档负载（如 5→10→20 台等效）容量"膝盖点"在哪；哪一档开始超时每档要稳态够长（≥ 90 s）
斜坡（ramp）负载线性上升到超过容量越界后的退化是"缓慢恶化"还是"断崖"适合找脆弱阈值
脉冲（spike）短时突发（3–10 s 峰值）突发缓冲与恢复速度；队列能否泄洪考验内存与 QoS 深度设置

合成负载（脚本按参数发消息）胜在可控可重复；bag 回放（第 037 章）胜在真实，真实消息的大小分布、突发模式、话题交织都是合成的简化模型抓不到的。工程顺序：先用合成负载定容量的量级，再用真实 bag 回放验证"实际业务形态下膝盖点是否提前"。回放注意时钟：ros2 bag play 的倍速播放会把负载压缩，测出的时延不真实；回放要按 1.0 倍速，且记录回放时的系统资源占用（回放器本身也是负载）。

2. 故障注入五分类与预期反应

故障类型注入手段预期系统反应（预写判据）
资源限制 CPU 配额、占用内存、限制带宽（cgroup / tc / 应用内限速）发布频率下降 → DEADLINE 报警 → 降级档 L1/L2
网络丢包率、延迟+抖动、带宽限制、分区（tc netem；无 root 时用转发代理）P95 越线 → QoS 降级 / 保命流不受损
节点kill 进程、SIGSTOP 挂起（模拟"假活"）、伪造心跳心跳超时 → SUSPECT → FAILED → 任务接管 ≤ 15 s
数据发布坏消息（NaN 位姿）、时间戳回退、重复消息风暴消费端校验拒绝；重复去重；无崩溃
时钟注入 200 ms–2 s 时钟偏移（chrony 打偏或容器时钟）TF/融合告警；同步修复后自愈

每类注入都要先写"预期反应"再执行：这条纪律来自混沌工程方法论，作用是防"事后合理化"，没有预期时，任何结果都会被解释成"符合预期"。预期要可度量，例如"L2 在注入后 5 s 内触发、控制 P95 < 30 ms、注入结束后 30 s 内回 L0"；笼统的"系统应该还能工作"无法充当判据。

3. 无 root 的注入：转发代理模式

实验室里修改内核网络（tc netem）最真实，但很多开发环境没有权限。等价效果可用转发代理实现：拦截一个话题，以"订阅→按策略处理→重新发布"的方式模拟网络劣化，按概率丢、按分布延迟、按上限截带宽。被测端看到的与真实链路故障同构（消息晚到、缺失、乱序），且注入时间精度与回滚粒度都更细，能做到按消息生效与回滚。它测不了真实网卡与协议栈的细节（重传、拥塞控制），用于功能级验证够了；性能级验证还是要在真实网络（或 netem）上做。

注入强度换算示例：丢包 p、平均时延 μ、抖动 σ → 有效吞吐 ≈ (1−p) × 理论吞吐；重传加剧时进一步按 (1−p)² 衰减 p = 3% 时吞吐损失仅 ~3%，但 P99 时延可能上升 3–5 倍，丢包的伤害主要在尾部，不在均值

4. 场景编排：五段式剧本与安全保障

一个标准压测场景脚本分五段：基线（30 s）→ 爬坡（到目标负载/注入加码）→ 持压（保持 60–180 s）→ 卸载（停止负载/撤销注入）→ 恢复观察（60 s）。观测贯穿全程，判据在基线段就采集好（对比需要 before/after）。

安全保障三条铁律：（1）熔断开关，脚本进程被杀、超时、异常时必须自动撤销注入（try/finally + 看门狗进程双保险）；（2）注入器自身超时，任何注入的最大持续时间硬编码（如 300 s），到点自动回滚；（3）隔离边界，压测只在自己的域/频段/网络内进行，绝不波及他人系统（域隔离第 001 章的再次兑现）。历史上大量"故障注入事故"都是注入没回滚、netem 规则留在网卡上，第二天整个实验室都在丢包。

实现思路与设计

压测系统四个组件（都跑在测试域里）：

  1. 负载生成器：参数化发布节点组（台数、大小、频率、曲线类型）；支持"等效 N 台机器人"的负载放大（一台机器发 N 份）。
  2. 注入器（injector）：转发代理与进程级注入的集合，每个注入有 start(id)/stop(id) 两个显式命令与内置 TTL。
  3. 观测器：复用 076 章探针 + task_event 统计 + 系统资源采样；输出统一时间线。
  4. 编排器：读场景 YAML（步骤、时长、判据），按五段式执行，产出"通过/失败 + 偏差证据"的报告。

场景规格与判据示例

场景注入/负载判据（通过线）
S1 带宽劣化受限带宽 2 MB/s，持续 120 s视频自动降帧；控制 P95 ≤ 20 ms；日志无丢单
S2 高丢包丢包 5%，120 s降级 ≤ L2；任务接管 0 次（不误判）；恢复 ≤ 30 s
S3 节点猝死kill 调度器进程备份接管 ≤ 15 s；任务零重复；领导纪元 +1
S4 消息风暴重复消息 ×50、1 min去重生效；CPU < 70%；无队列溢出
S5 时钟偏移+500 ms告警触发；修复后 TF 自愈；任务时间戳校正
注意：判据里必须包含"无副作用"一条

压测常见的自欺是只看"关键指标没超线"，忘了查副作用：注入结束后有没有残留订阅、有没有机器人卡在降级档、有没有任务的账本状态没回正。每个场景的判据都要附"系统回稳"检查（节点图与基线一致、所有任务事件闭合、降级档回 L0），否则测出的"通过"可能是带伤通过。

关键代码与解读

片段 1：阶梯负载生成器

class LoadGenerator(Node):
    """按阶梯曲线放大负载：等效 N 台机器人的合成流量。"""
    STEPS = [(1, 30), (4, 30), (10, 30), (20, 30)]   # (等效台数, 持续秒数)
    def __init__(self):
        super().__init__("load_generator")
        self.pub = self.create_publisher(ProbeMsg, "/bench/load", 100)
        self.step = 0
        self.t_step = self.now_s()
        self.create_timer(0.01, self.tick)           # 统一 100 Hz 基础节拍

    def tick(self):
        n, dur = self.STEPS[self.step]
        if self.now_s() - self.t_step > dur:
            self.step = min(self.step + 1, len(self.STEPS) - 1)
            self.t_step = self.now_s()
            self.get_logger().info(f"负载档位 → {self.STEPS[self.step][0]} 台等效")
        # 一个节拍内模拟 n 台的流量：每台 10 Hz → 每 10 个 tick 全发一轮
        if self.tick_count() % 10 == 0:
            for i in range(n):
                msg = self.make_probe(robot=i)       # 消息带来源编号，便于按机统计
                self.pub.publish(msg)

解读：负载生成器用"单进程放大"替代真实机器人（实验室里没法真开 20 台），三个设计点保证放大后的负载在统计意义上等价：消息大小与频率与真实业务一致（消息类型取真实业务，空消息测不出序列化与大小分布的影响）；每台的消息带来源编号，接收端可以按"等效机器人"分解统计（能看出是哪一档开始出问题）；节拍驱动，不给每台各开一个定时器：后者在 20 台时会引入 20 个定时器回调的额外开销，污染负载本身。注意 depth=100 是大负载下的必要配置：小深度会让发送队列频繁阻塞，测出来的"时延"其实是生成器的自旋等待。阶梯切换点的日志很重要，压测报告的时间线要与它对齐。

片段 2：无 root 故障注入，转发代理

import random

class NetFaultProxy(Node):
    """转发代理：在订阅与重发布之间按策略注入延迟与丢包。
    被测节点只需把该话题重映射到本代理的入口即可（不改代码）。"""
    def __init__(self):
        super().__init__("net_fault_proxy")
        self.drop = 0.0            # 丢包率 0–1（由注入命令调整）
        self.delay_ms = 0.0        # 固定延迟
        self.jitter_ms = 0.0       # 抖动（正态）
        self.ttl_until = None      # 注入 TTL：到点必须自动恢复（安全铁律）
        self.declare_parameter("input_topic", "/bench/load_raw")
        self.declare_parameter("output_topic", "/bench/load")
        self.pub = self.create_publisher(ProbeMsg, "/bench/load", 100)
        self.create_subscription(ProbeMsg, "/bench/load_raw", self.on_msg, 100)
        self.create_timer(1.0, self.safety_check)

    def on_msg(self, msg):
        if self.now_s() > (self.ttl_until or float("inf")):
            self.pub.publish(msg)          # TTL 过期：透明转发（自动恢复）
            return
        if random.random() < self.drop:
            return                         # 丢掉：模拟链路丢包
        delay = max(0.0, self.delay_ms + random.gauss(0, self.jitter_ms)) / 1000.0
        if delay > 0.001:
            # 简单实现：起一个一次性定时器延迟重发（生产中用最小堆调度）
            threading.Timer(delay, self.pub.publish, args=(msg,)).start()
        else:
            self.pub.publish(msg)

    def safety_check(self):
        if self.ttl_until and self.now_s() > self.ttl_until:
            self.get_logger().warn("注入 TTL 到期，自动恢复透明转发")
            self.ttl_until = None

解读：转发代理是"无根权限环境下的 netem"，它的工程价值在于注入粒度与回滚精度：可以只对某话题、某来源、某时间段注入，TTL 到点自动恢复。三个细节：ttl_until 双保险（消息路径检查 + 1 Hz 定时检查），高楼上的测试别指望有人记得手动关注入；延迟重发用一次性定时器（简化版），生产级实现应改为最小堆统一调度，每消息一线程在 1 kHz 负载下会直接压爆系统；TTL 过期后走"透明转发"，停发会让下游把"注入结束"误判为"故障升级"。注意这个代理只能模拟延迟/丢包/乱序这类行为级故障，测不了 TCP 重传与拥塞窗口，性能压测仍要在真实网络或 netem 上做。

片段 3：场景编排，判据前置与 finally 回滚

SCENARIOS = {
    "S2_lossy_link": {
        "baseline_s": 30, "hold_s": 120, "recover_s": 60,
        "inject": {"kind": "proxy", "drop": 0.05, "ttl_s": 150},
        "expect": {                        # 判据在运行前写死：防事后合理化
            "degrade_max_level": 2,        # 降级不超过 L2
            "control_p95_ms": 30.0,        # 控制 P95 上限
            "task_takeover_count": 0,      # 不应误判故障
            "recover_s": 30,               # 卸载后 30 s 内回稳
        },
    },
}

def run_scenario(name, harness):
    spec = SCENARIOS[name]
    obs = harness.start_observers()          # 观测先于一切：没有数据就没有结论
    try:
        harness.wait(spec["baseline_s"])     # 五段式：基线
        baseline = obs.snapshot()             # 基线数值：判据的对照物
        harness.inject(spec["inject"])       # 注入（带 TTL 自动回收）
        harness.wait(spec["hold_s"])         # 持压
        harness.stop_inject()                # 卸载
        harness.wait(spec["recover_s"])      # 恢复观察
        verdict = obs.evaluate(spec["expect"], baseline)
    finally:
        # 无论成功失败异常：撤销注入 + 停负载 + 等回稳（安全铁律第一）
        harness.force_cleanup()
    harness.write_report(name, verdict)

解读：编排器的骨架是"判据前置 + 观测先行 + finally 兜底"。判据写进 expect 字典的那一刻就冻结了，哪怕测出来"系统扛住了 5% 丢包但降级到了 L3"，也不能回头说"L3 也算合理"，偏差就是要记录的事实（可能意味着降级阈值需要重调）。baseline 快照让判据里可以写相对量（"恢复后 P95 不超过基线的 1.2 倍"），比绝对阈值更抗环境差异。finally 里的 force_cleanup 是人身安全级的要求：任何异常路径都必须撤销注入、停止负载、恢复系统，压测脚本的第一用户是明天的你自己。报告要包含时间线（注入开始/结束、降级切换、判据越线时刻），它是后续调参和复盘的全部证据。

常见坑

  • 注入没有自动回滚：测试中断后 netem 规则留在网卡、代理继续丢包，第二天整个环境"亚健康"。修复：注入 TTL 硬编码 + 清理脚本 + 编排器 finally 三保险。
  • 判据事后补写：测完看着结果定标准，"通过"是自我安慰。修复：场景 YAML 里写死 expect；CI 流水线校验场景文件存在判据才允许执行。
  • 压测域与生产域混用：故障注入打到真实车队，造成真实事故。修复：独立域 ID + 独立频段 + 注入器白名单目标；第 001 章的域隔离在此成为安全边界。
  • 回放倍速播放：bag play -r 5 把 5 分钟的负载压进 1 分钟，测出来的"容量"毫无意义。修复：1.0 倍速回放，记录回放器自身资源占用。
  • 只测不修：压测发现膝盖点在 8 台，报告存档后无人行动，上线直接 20 台。修复：把"容量线 → 行动"写进流程（扩容、分域、限流、降级阈值调整），并在下一轮压测验证行动效果。

练习与思考

  1. 设计 S1 带宽劣化的完整场景规格：负载形态（等效台数、消息构成）、注入参数（带宽上限、时长）、五段式时长、四条判据（含一条"无副作用"检查）。★
    提示
    参考 S2 规格的字段结构；无副作用检查例："卸载后 60 s，节点列表与基线一致且降级档 = L0"；判据给相对量（P95 ≤ 基线×1.5）抗环境漂移。
  2. 用片段 1 的阶梯负载跑到"10 台档 P95 = 40 ms、4 台档 = 18 ms"，估算膝盖点位置，并给出三种扩容/缓解选项（分域、限流、降级）各自的适用条件。★★
    提示
    膝盖在 4–10 台之间（近似 6–8 台：40/18 ≈ 2.2 倍跃升）。分域适合"可分组"的机器人；限流适合"总量受限但个体可降质"；降级适合"保命流可定义"的实时系统。
  3. 给"网络分区"设计一个无 root 注入方案：如何让被你测试的机器人 A 与其他所有成员互相看不见，但 A 的进程照常运行？写出代理拓扑与预期系统反应（两侧各自的判定与动作）。★★
    提示
    在 A 侧部署出站/入站双向代理：所有出向流量丢弃 + 所有入向不转发。预期：监控端判 A 疑似→确诊；A 侧检测与指挥端失联 → 10 s 安全停车；恢复后重入验收发现任务疑似重复 → 对账解决。
  4. 写一份"压测回滚检查单"：列出压测开始前、注入期间、结束后各要核对的事项（域、开关、TTL、观测在线、清理命令），并解释为什么"清理命令"要在开始前就准备好。★★★
    提示
    开始前：域正确、熔断开关就位、清理命令可执行、观测已录；期间：TTL 倒计时、观测数据连续；结束：注入撤销、负载停止、系统回稳、报告落盘。清理命令提前准备的原因：出事时人最慌，现找命令必然耽搁。

小结

  • 压测找容量与退化行为：阶梯找膝盖、斜坡看恶化形态、脉冲验缓冲；合成定量级，bag 回放验真实（1.0 倍速）。
  • 故障注入五分类（资源/网络/节点/数据/时钟），每类先写可度量的预期反应，再执行，判据前置是纪律。
  • 无 root 用转发代理做行为级注入；性能级验证上真实网络或 netem；注入必须有 TTL 与双保险自动恢复。
  • 场景五段式：基线→注入→持压→卸载→恢复观察；finally 清理与"无副作用"检查是报告的一部分。
