第一篇 · 通信基础与系统搭建

第 001 章：ROS2多机器人系统架构总览

先看全图再动手：一台机器人的 ROS2 图怎么变成 N 台机器人的"网络化系统"，以及 DDS、域 ID、命名空间这三件基础设施各自管什么。

  • 主题：系统架构 / 通信基础设施总览
  • 关键机制：DDS 发现、Domain ID、命名空间隔离、QoS 合同
  • 预计学时：50 分钟
  • 前置章节：无（本课程从这里开始）

学习目标

  • 建立 ROS2 多机器人系统的四层架构心智模型：网络层 → 中间件层（DDS）→ 计算图层（节点/话题/服务/动作）→ 协同层。
  • 理解 DDS 的发现机制为什么能取代 ROS1 的中心 master，以及它在无线网络上的软肋。
  • 掌握多机器人隔离的两把钥匙：Domain ID（域隔离）与命名空间（图内隔离），知道什么时候用哪把。
  • 会做带宽预算：用"消息大小 × 频率 × 台数"估算链路需求，找出带宽大户。
  • 能画出双机器人系统的最小计算图，并解释每一条数据流的用途与 QoS。

背景与动机

单机器人的 ROS2 系统很好理解：几十个节点挂在一张计算图上，话题互相连接。但当你把第二台、第五台、第二十台机器人接入同一个系统时，通信问题会以新的方式集中爆发：谁和谁应该连通？怎么保证不串线？无线网络撑不撑得住？一台掉线了怎么办？这些问题都不是"多写几个节点"能解决的，它们属于系统架构层面。

ROS2 相对 ROS1 最大的变化，是把通信底座从"中心化的 master + TCPROS"换成了基于 DDS（Data Distribution Service）的去中心化中间件，这正适合多机器人场景：任何一台机器人加入/退出都不影响其他成员，发现与传输完全分布式。代价是配置项变多（域、QoS、发现策略），不搞清架构就会陷入"节点都启动了却收不到消息"的泥潭。

本章先建立全图。后面 99 章都是在图上"填零件"：消息怎么发（002–004）、隔离怎么做（007–012）、数据怎么协同（021–040）、系统怎么工程化（066–085）。

核心原理

1. 四层架构：从线缆到协同

层职责典型对象出问题时的症状
应用/协同层任务分配、编队决策、调度协同算法、行为树行为逻辑错，通信本身正常
计算图层节点与接口：话题/服务/动作/参数rclpy 节点、msg 定义接口不匹配、命名冲突
中间件层（DDS）发现、序列化、QoS、传输Domain、QoS、RMW静默不通、丢消息、发现慢
物理网络层以太网 / WiFi / 5G 承载交换机、AP、频段延迟抖动、丢包、带宽打满

排障的顺序应该自下而上：先确认网络通、再确认发现成、再确认 QoS 匹配、最后才怀疑算法，反着来会浪费大量时间。

2. DDS 发现：没有 master 的"通讯录"

DDS 用两级发现建立通信：(1) SPDP，参与者（participant）之间互相打招呼，交换存在信息；(2) SEDP，已认识的参与者之间交换各自的发布/订阅端点细节，然后匹配同名话题、协商 QoS。

发现的开销随节点数平方增长：M 个端点最坏要建立 O(M²) 对匹配关系。20 台机器人、每台 20 个端点时，就是 400 个端点、约 8 万对潜在匹配，这也是大规模系统要控制"信标流量"、按需分域的原因。

发现规模 ≈ M²/2 对（M 为域内端点总数） 一台机器人 20 个端点 × 20 台 = 400 端点 → 约 8 万对；划小域可把它降回可控范围

工程直觉：多播像"广播喊话"，单播像"逐个打电话"。有线网络通常允许多播，喊一声大家都收到；但很多 WiFi 路由器会抑制多播，导致"有线能发现、无线发现不了"。生产系统常用单播发现列表或 Discovery Server 来绕开这个坑（第 010 章展开）。

对比项ROS1（master + TCPROS）ROS2（DDS 发现）
中心依赖roscore 是单点，进程退出全系统瘫痪无中心，任何节点退出不影响其他参与者
发现方式节点向 master 注册与查询，由 master 撮合SPDP 多播心跳加 SEDP 端点配对，参与者之间直接完成
跨网段能力配置 master URI 即可跨网段多播难以跨网段，需要单播列表或 Discovery Server
规模特性负载集中在 master，节点多时它是瓶颈负载均摊到各参与者，但发现量随端点数平方增长

2.1 域号如何变成端口：网络分区的算术

不同域彼此不可见，其机制是一组固定的端口映射公式：RTPS 在 UDP 上把域号线性映射到一段 250 个端口的窗口，域与域的端口块互不重叠，因此即使接在同一台交换机上，它们连对方的发现心跳都收不到。

PB = 7400 + 250 × 域号
发现多播端口 = PB；用户多播端口 = PB + 1
单播端口基线 = PB + 10 + 2 × 参与者编号 单播基线与基线 + 1 各占一个端口，分别承载发现元流量与用户数据；公式是 RTPS-over-UDP 的通用约定

代入三个代表性域号：域 0 的窗口是 7400–7649；域 42 从 17900 起；域 101 从 32650 起。ROS 2 默认把可用域号限制在 0–101，原因在操作系统一侧：Linux 的临时端口区间从 32768 开始，域号再往上加，DDS 端口块会与系统随机分配的外连端口大面积重叠，产生偶发且难定位的异常。

算例：域 42、编号 3 的参与者占哪些端口？

PB = 7400 + 250 × 42 = 17900。发现多播 17900，用户多播 17901；单播基线 17900 + 10 + 2×3 = 17916，连同 17917 共两个端口。相邻编号差 2 个端口，编号最大 119 的参与者用 18148、18149，正好把 17910–18149 的窗口用满。由此得到两条硬边界：同域参与者上限 120 个，超编参与者无法分配端口、节点创建直接失败；域号是硬切分，跨域通信必须显式部署桥接节点，没有任何自动兜底。

2.2 发现流量的量级：心跳轻、配对重

SPDP 是"轻而慢"的心跳：每个参与者周期性向发现多播端口发一条存在公告（数百字节量级、周期秒级，具体默认值以实现文档为准），租约到期未续则被判离线。稳定态公告流量近似 M×S/T，其中 M 为参与者数、S 为公告字节数、T 为公告周期：30 台机器人、500 字节、3 秒周期时仅约 5 KB/s，稳态心跳并不贵。

真正贵的是 SEDP 的配对交换，它随端点数平方增长。每对新认识的参与者要互相交换端点清单（每个端点描述约 0.5–1 KB）：M = 30、每台 15 个端点时，一次性交换总量约 30 × 29 × 15 × 0.5 KB ≈ 6.5 MB。参与者从 30 台增到 40 台，交换量按 M×(M−1) 变化，比值 40×39 ÷ (30×29) ≈ 1.79，规模上升约 79%。这个突发在千兆有线上几秒内完成；切到 WiFi 后，多播被抑制、单播重传排队，同样规模可能拖到十几秒以上。由此得到三条工程惯例：分域降低 M、砍掉无用端点、无线环境改用单播发现或 Discovery Server。

2.3 隔离手段对比与消息开销

带宽公式里"协议开销系数"为什么小消息要取大值？把线上真实占用拆开看：以太网/IP/UDP 头 42 B + RTPS 头 20 B + 时间戳与 Data 子报文头约 36 B，合计约 98 B 固定开销。一条 20 B 的状态消息，线上实占约 118 B，是负载的约 6 倍；而 10 KB 的消息图，固定开销占比约 1%，系数 1.05 足够。这解释了为什么小高频消息宜合并发送（批处理、自定义聚合消息）：每项数据各开一个话题，固定开销会按话题数逐条累计。

3. 隔离的两把钥匙：Domain ID 与命名空间

ROS2 提供两级隔离，它们作用在不同层面：

  • Domain ID（DDS 层）：不同域 = 完全不同的通信平面，互相不可见，甚至不互相"打招呼"。适合隔离独立系统（例如两台机器人的调试系统与产线系统）。域的底层实现是端口偏移：端口 = 7400 + 250×域 + 偏移，所以域号本质上是"网络分区号"。域号范围 0–101（安全域另有约定），不同域之间没有任何兜底连通手段。
  • 命名空间（ROS 层）：同一个域内，话题前缀化为 /robot1/、/robot2/，避免同名话题互相串。命名空间只是名字约定，DDS 层面仍然可见，所以它防"串线"，不防"监听"。

选择标准一句话：需要网络级隔离（不同系统、安全边界）用 Domain；需要同一系统内多实例共存用命名空间。两者可以叠加：同域 + 命名空间是多机器人产线的默认配置。

4. QoS 合同与带宽预算

DDS 的 QoS（可靠性、持久性、历史深度等）是端到端合同：发布端声明"可靠传输 + 保留最后一条"，订阅端也必须接受这个组合，否则匹配失败，而且失败是静默的，没有弹窗报错。QoS 的细节在第 011、012 章展开，本章先记住"合同"这个词。

带宽预算是架构设计的第一道算术题：

链路需求 ≈ Σ（消息大小 × 发布频率）× 机器人台数 ×（1 + 协议开销系数） 开销系数随消息小、频率高而上升；10 KB 以上的消息可近似取 1.05–1.2

算两个例子：激光扫描 720 点/圈（4 字节/点）、10 Hz、4 台机器人 ， 约 0.1 MB/s，轻松。而未压缩彩色图 1280×720×3 字节、15 Hz、单台 ， 约 40 MB/s，四台就压垮千兆网。所以多机器人系统里"图像必须压缩或不上网"是条铁律。

实现思路与设计

搭一个多机器人系统的标准六步（后续章节逐项展开）：

  1. 规模与拓扑：几台机器人、有线还是无线、是否经过交换机/AP。无线场景先标记"多播是否可用"。
  2. 域与命名规划：系统级一个 Domain（例如 42，避开默认 0 与别人的域）；每台机器人一个命名空间 /robotN；预留 /fleet 作为车队级话题（任务、调度）。
  3. 频率与带宽预算：为每类数据确定频率档位，状态 50 Hz、感知 10–30 Hz、控制 100–500 Hz、地图/大消息事件驱动或低频。逐项过一遍上面的带宽公式。
  4. QoS 策略表：给每个话题选可靠性/持久性/深度（下表给了起点模板）。
  5. Launch 编排：同一份节点代码用命名空间 + 参数复用到每台机器人，避免"复制粘贴 N 份代码"。
  6. 监控与日志：节点图监控、关键话题频率/延迟告警、统一日志聚合（第 018、038、039 章）。

话题 QoS 起点模板（双机器人系统）

话题典型频率可靠性持久性理由

/robotN/joint_states50 HzReliableVolatile状态同步要完整
/robotN/scan10 HzBest-effortVolatile丢一帧扫描没有致命影响，宁要新数据不要旧补发

设计决策：为什么控制与感知用不同的可靠性？

可靠传输意味着"丢了要重传"，重传需要时间，在 100 Hz 的控制环里，一帧 10 ms 前重传到的旧指令毫无价值，还挤占带宽。感知数据同理：对激光扫描而言"最新的"永远比"补全的"更重要，Best-effort 让系统自动挑最新数据。反过来，指令类消息绝不能丢。这个"按消息语义选可靠性"的思路会贯穿全课程。

域号落地的三条检查

域号选错属于"全系统静默"级事故，部署前过三条检查。其一，避开域 0：任何未配置的开发机都默认落在域 0，你的系统若也在域 0，陌生节点会混进图里，带来同名话题串线与额外发现流量。其二，全链路统一下发：ROS_DOMAIN_ID 是环境变量，机器人本体、地面站、容器与回放环境必须同一取值；容器默认 bridge 网络还会拦截多播，需切 host 网络或显式映射端口。其三，写入部署文档并预留下限：写明"为什么选这个域、周围哪些域已被占用"，并给未来子系统留至少一个空闲域号，避免上线后再改域，引发全系统重新联调。

关键代码与解读

片段 1：带命名空间与 QoS 的桥接节点

import rclpy
from rclpy.node import Node
from rclpy.qos import QoSProfile, ReliabilityPolicy, DurabilityPolicy
from geometry_msgs.msg import Twist

class FleetBridge(Node):
    """把一个机器人的速度指令转发给另一个机器人（命名空间隔离示例）。"""
    def __init__(self):
        # 节点全名为 /robot2/bridge：命名空间让同名节点在不同机器人上共存
        super().__init__("bridge", namespace="robot2")
        # QoS 是"合同"：与对端不匹配时会静默不连通（没有报错）
        qos = QoSProfile(depth=10)
        qos.reliability = ReliabilityPolicy.RELIABLE    # 控制指令：不丢
        qos.durability = DurabilityPolicy.VOLATILE      # 只要最新值，不补历史
        # 相对话题名"cmd_vel"自动展开为 /robot2/cmd_vel
        self.pub = self.create_publisher(Twist, "cmd_vel", qos)
        # 绝对话题名"/robot1/cmd_vel"不受本节点命名空间影响
        self.sub = self.create_subscription(
            Twist, "/robot1/cmd_vel", self.on_cmd, qos)

    def on_cmd(self, msg):
        # 多机器人系统的"衔接节点"：转发/转换/汇聚是它最常见的三种职责
        self.pub.publish(msg)

解读：这段代码里藏着两个关键区分。（1）相对话题名 "cmd_vel" 会带上节点自身的命名空间（/robot2/cmd_vel），而绝对名 "/robot1/cmd_vel" 忽略命名空间，在跨机器人传递数据时，绝对名是明确指向的写法。选相对还是绝对，取决于你希望话题"跟随节点"还是"固定指向"。

（2）QoS 配置的双端匹配：如果对面的发布端只提供 Best-effort，而这里的订阅端要求 Reliable，DDS 匹配会失败且不弹错。调试时用 ros2 topic info --verbose 查看每个端点的 QoS，这是发现"静默不连通"的第一把工具。

片段 2：Launch 编排，一份代码拉起 N 台机器人

# launch 文件是系统的"编排层"：用循环与参数复用拉起 N 台；复制 N 份启动脚本会带来维护泥潭
from launch import LaunchDescription
from launch_ros.actions import Node

def generate_launch_description():
    nodes = []
    for rid in (1, 2):                      # 扩展到 20 台也只是改这里
        nodes.append(Node(
            package="fleet_bringup",
            executable="robot_node",
            namespace=f"robot{rid}",        # 命名空间：话题自动前缀 /robotN/
            parameters=[{"robot_id": rid}], # 参数区分实例：同一程序跑出不同身份
            remappings=[("odom", "odom_raw")],  # 话题重映射的示意（第 008 章展开）
        ))
    return LaunchDescription(nodes)

解读：多机器人代码的第一原则是"实例化复用"，节点代码里不写死 robot1 这种身份信息，一切通过命名空间与参数注入。这样从 2 台扩到 20 台，改动只有循环里的列表。remappings 则用来在"外部约定的话题名"与"节点内部实现名"之间做适配，实现接口解耦。

片段 3：带宽预算小工具

def link_budget(n_robots=4, img_px=1280*720, img_bpp=3, img_hz=15,
                scan_pts=720, scan_hz=10, compressed=True):
    """估算多机器人下行链路带宽：逐类数据求和，单位 MB/s。"""
    img_bytes = img_px * img_bpp
    if compressed:                      # 压缩比是量级差异：~50 倍
        img_bytes /= 50
    # /8 是把 bit 换 byte；再乘台数得到系统总量
    img_mb = img_bytes * img_hz * n_robots / 1e6
    scan_mb = scan_pts * 4 * scan_hz * n_robots / 1e6   # 每点按 4 字节估
    print(f"图像 {img_mb:6.1f} MB/s + 扫描 {scan_mb:5.2f} MB/s = {img_mb+scan_mb:6.1f} MB/s")
    return img_mb + scan_mb

link_budget(compressed=False)   # 未压缩：约 165 MB/s，千兆网直接占满
link_budget(compressed=True)    # 压缩后：约 3.3 MB/s，余量充足

解读：写这段脚本的目的是把"带宽会不会爆"变成一行可执行的判断，精度无须达到计费级。算术结论很残酷：未压缩图像的带宽需求是压缩的 50 倍左右，这是数量级差异，所以多机器人视觉系统的第一决策永远是"图先在边缘压缩（或用压缩话题），再上网"。参数留成函数入参，方便在架构评审时现场改数字演示。

常见坑

  • 把 Domain 当命名空间用：不同 Domain 的节点"物理上不通"，连看到对方都做不到，需要在系统部署前就规划好域号并写进部署文档；反过来，同域忘记加命名空间，两台机器人同名话题直接串线（/cmd_vel 互相抢）。
  • 无线环境多播被抑制：有线调试一切正常，上 WiFi 后节点互相发现不了。症状是 ros2 node list 只能看到本机。修复：配置单播发现列表，或部署 Discovery Server（第 010 章）。
  • QoS 不匹配静默失败：日志里没有任何错误，就是收不到数据。检查 ros2 topic info --verbose 里两端的 QoS 组合是否"兼容"（Reliable 发布端可以兼容 Best-effort 订阅端，反方向不行）。
  • 带宽按"平均值"算不按峰值算：地图保存、日志上传这类突发流量平时不出现，上线时把网络打满，控制指令的时延瞬间恶化。预算要按"最坏 1 秒"估算。
  • 时间源不统一就启动协同：多台机器人的墙上时钟不同步，TF 与消息时间戳错乱，表现为"轨迹跳变、地图错位"。开工前先做时间同步（第 009 章），再谈协同。

练习与思考

  1. 算一算：3 台机器人，每台以 30 Hz 发布 1080p 压缩图（约 200 KB/帧）。网络每秒需要多少 MB/s？如果 AP 实测吞吐 80 MB/s，还剩多少余量给控制与感知？★
    提示
    200 KB × 30 Hz × 3 = 18 MB/s，约占吞吐 22%。别忘了 DDS 开销与重传会把实测值再抬高一截，评估时留 30% 余量。
  2. 画出双机器人最小计算图：两台机器人各自的 /robotN/cmd_vel、/robotN/odom，加上一个车队的 /fleet/task。标出每条边的方向与 QoS 类型（可靠/尽力）。★
    提示
    先画两个命名空间盒子，再画机器人内数据流（cmd→执行→odom），最后画跨机器人的边（调度节点→/fleet/task→各机器人）。跨机器人的控制指令一律 Reliable。
  3. 比较四种隔离方案：(a) 系统 A 域 0+无命名空间；(b) 同域+命名空间；(c) 各自独立域；(d) 同域+命名空间+各自 QoS 隔离。给出各自适用场景与一种失效模式。★★
    提示
    (a) 撞车现场；(b) 标准做法；(c) 适合"产线系统 vs 调试系统"，但车队级话题要跨域，需要桥接；(d) QoS 隔离不是安全边界，只影响连接行为，不能当权限用。
  4. 设计实验：在 WiFi 上从 2 台逐步加到 8 台机器人（每台 20 个端点），测量 ros2 node list 的发现时间与误发现率，观察发现流量随 N 的增长曲线，并与 M²/2 的估算对照。★★★
    提示
    用 ros2 daemon 关闭本机缓存后计时；观察多播模式下 5 台以内较快、继续加台后发现时间非线性上升；这正是分域/单播发现的动因。
  5. 给你的多机器人项目写一份"域与命名规范"半页纸：域号选择理由、命名空间分层（车队/机器人/子系统）、预留话题清单与 QoS 起点表。★★★
    提示
    参考本章六步法第 2、4 步与 QoS 模板表；写清"新增一类数据往哪挂命名空间"的规则，比列一堆具体名字更有价值。

小结

  • 多机器人系统的四层架构（网络 → DDS → 计算图 → 协同），排障务必自下而上；域号经 7400 + 250×域 映射为端口窗口，同域参与者上限 120 个。
  • DDS 靠 SPDP/SEDP 两级发现实现去中心化，发现规模 O(M²)；多播在 WiFi 上常不可用是头号部署坑。
  • 隔离两把钥匙：Domain = 网络级隔离，命名空间 = 图内隔离；产线默认"单域 + 每机命名空间"。
  • QoS 是端到端合同，"按消息语义选可靠性"；带宽预算按峰值算，图像类数据优先压缩，小高频消息要留意约 98 字节的固定协议开销。
  • 下一章进入最基础的通信原语：话题通信，发布/订阅模型在多机器人场景下的命名、频率与常见误用。
