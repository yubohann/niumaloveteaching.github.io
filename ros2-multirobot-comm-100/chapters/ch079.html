第四篇 · 系统集成与工程化

第 079 章：多机器人真机实验设计

真机实验是稀缺资源：场地、电量、人力都以小时计费。用实验设计的纪律，假设、变量、对照、重复、盲化与预注册，把每次上场地都变成能进论文和验收报告的有效数据，避免"又跑了一遍"式的浪费。

  • 主题：系统集成 / 实验方法论
  • 关键机制：变量与控制、运行矩阵、安全规程、元数据与预注册
  • 预计学时：60 分钟
  • 前置章节：第 078 章

学习目标

  • 会为真机实验写规范的实验方案：研究问题、假设、自变量/因变量/控制变量、对照与重复策略。
  • 掌握在资源受限下提高数据效力的手段：分块设计、配对比较、运行顺序随机化。
  • 能设计包含安全规程的 Runbook：前置检查、中止判据、急停演练、角色分工。
  • 会搭建"每次运行必带元数据"的记录规范，杜绝数据孤儿与幸存者偏差。
  • 理解预注册与协议冻结的意义，能把结论表达为"效果量 + 置信区间"；单个数字不足以支撑决策。

背景与动机

仿真实验可以跑一千遍，真机实验一晚可能只有 20 个有效场次：场地要清场、电池要轮换、每跑一次要人盯、出错一次可能要修半小时。资源稀缺放大了两个常见错误：（1）设计粗糙，同时改了三个参数，最后说不清哪个起了作用；（2）记录随意，只留下"成功的好像还行"的印象，失败场次与现场条件全部遗失。

本章与 076（基准方法学）是姊妹篇：076 管"怎么测"（指标与统计），079 管"怎么排实验"（变量、顺序、安全、记录），077 提供"恶劣条件"的注入手段。掌握这套方法论，你的真机数据才经得起评审、复现与论文级追问。

核心原理

1. 从问题到假设：实验的七个要素

一份可执行的实验方案包含七个要素，缺一项都会让数据分析阶段抓瞎：

要素示例（比较两种任务分配策略）
研究问题拍卖式分配是否比集中式分配在 6 台真机下更快完成任务批次？
假设H1：拍卖式的 batch makespan 中位数低于集中式 ≥ 10%
自变量分配策略 ∈ {集中式, 拍卖式}（唯一被操纵的变量）
因变量makespan、空驶里程、任务成功率（测量口径固定）
控制变量机器人 6 台同型、同一场地布局、任务集相同、电量 ≥ 60%、同一 WiFi
对照集中式作为对照；两策略在同一批任务集上配对比较
重复每种策略 15 次（配对：同一任务集跑 A 再跑 B）

变量纪律的核心一句话：一次实验只操纵你想回答的那个变量。想同时看"策略"和"任务数"的影响，就把任务数做成分层（每层内配对比较）；把两个变量混在一个大矩阵里随缘跑，结论会归因不清。

2. 资源受限下的设计技巧

  • 配对比较（pairing）：同一任务集先跑 A 后跑 B（或顺序随机），环境漂移（温度、电量、时段）在两策略间共同发生，比较的是差，比独立两组节省一半以上样本。
  • 顺序随机化：A→B 与 B→A 各半，抵消"后跑的沾光/吃亏"（电量下降、跑熟场地）。
  • 分块（blocking）：按电量档位、时段分块，块内条件一致；分析时块间差异被单独吃掉。
  • 运行队列预排：开跑前生成整晚的运行清单（含随机化后的顺序）并打印张贴，禁止现场"临时改主意"，那会引入选择偏差。
配对设计样本量感：需分辨 10% 差异、配对差 σd ≈ 15% → n ≈ (1.96+0.84)² × (15/10)² ≈ 18 对 一个通宵 6 h、每对 15 min → 24 对，可行；先算再做，避免"跑完发现不够"

3. 安全规程：不可谈判的先决条件

真机实验的安全设计依靠硬性结构，"小心一点"这样的口头提醒不构成防护：

  • 急停演练：每次实验开始前，全队急停测试 1 次（物理急停 + 软件急停两条链）；测试未过不准开跑。
  • 中止判据前置：写明"出现什么立即停"，越界、碰撞、冒烟、通信全断、某机姿态异常、观察者判断不安全。中止权属于现场任何一个人，不需要请示。
  • 场地边界与限速：物理围栏/警戒带；真机首日的速度上限取平时的 50–70%（078 章安全配置）。
  • 角色分工：至少三人，操作（起停、监控）、安全（盯机器人本身，不碰电脑）、记录（标注事件时间点）；一人多角是事故的温床。
  • 风险清单：列出本次实验的 Top 5 风险（撞击、失联、跌倒、电池、人员误入）与对应处置，张贴在现场。

4. 元数据与预注册：让数据可复现

真机实验的数据集 = 测量数据（bag/日志）+ 元数据（条件与环境）+ 协议（方案版本），三者缺一不可复现。元数据最低集合：运行编号、条件编码、方案版本、时间戳、操作员、机器人列表与固件版本、电量区间、场地布局版本、天气/温湿度（室外）、异常事件标注。记录规范的关键是"每次运行都记录，包括失败的"，失败数据恰恰是论文里最有价值的部分（"在 X 条件下成功率下降"），也是防止幸存者偏差的唯一办法。

预注册（pre-registration）在这里的工程对应物是"协议冻结"：开跑前把实验方案（含判据、分析脚本）存成一个版本号，运行期间只允许"附录式"修改（记录变更与原因），分析只按冻结版执行。没有冻结协议，分析阶段会不自觉地挑选好看的判据（p-hacking），结论的可信度归零。毕业论文与学术评审里，"我们事先声明了判据"这句话的含金量极高。

实现思路与设计

一次实验日的时间线（6 小时示例）：

  1. 布置（45 min）：场地布置、标定复核（< 3 cm）、时间同步检查、急停演练、网络实测（发现时间/丢包）。
  2. 试跑（30 min）：每条件的第一次运行视作试跑（数据保留但单独标注），暴露流程问题。
  3. 正式运行（4 h）：按预排队列执行；每 30 min 强制休息与电量轮换；每运行一次记录元数据并快速核对（数据是否录上）。
  4. 收尾（30 min）：数据双备份（本地 + 异地）、现场照片、异常回顾、次日队列预排。

运行矩阵与记录字段

字段示例用途
run_id2026-09-30_A_07主键；与 bag 文件名一致
conditionauction / centralized自变量编码
order_slot第 7 位（随机序）顺序效应分析
battery_block60–80% 档分块变量
protocol_versionprereg_v3协议冻结版本
anomalynone / human_intrusion / reset剔除与归因依据
注意："事后剔除"必须有规则，且写进协议

哪些运行可以剔除（数据未录上、人为误操作、设备故障）必须在协议里定义清楚，并在分析脚本里以显式规则实现。不能看着结果决定丢掉哪几次，那是最常见的 p-hacking 变体。剔除的运行要在报告里列出清单与理由，"剔除了 2/24 对"是透明，而"用了 22 对"含糊其辞就是不可信。

关键代码与解读

片段 1：实验运行器，队列驱动 + 元数据 + 安全确认

import csv, time, random

def build_queue(conditions, repeats):
    """生成随机化运行队列：配对条件在块内交替，顺序随机。"""
    queue = []
    for r in range(repeats):
        block = conditions[:]                 # 每块内两种条件各一次（配对）
        random.shuffle(block)                 # 顺序随机：抵消先后效应
        for cond in block:
            queue.append({"repeat": r, "condition": cond})
    random.shuffle(queue)                     # 块间也打散（不同批任务集归块）
    return queue

def run_experiment(queue, scenario_start, rec_start, meta_writer):
    for i, run in enumerate(queue, 1):
        print(f"[{i}/{len(queue)}] 条件={run['condition']}")
        input("检查场地/急停就位后回车开始（超时 120s 自动中止）...")
        meta = collect_meta(run)              # 电量、固件、协议版本快照
        rec_start(f"run_{i:02d}_{run['condition']}")   # 先开录：数据从第一秒进入
        try:
            result = scenario_start(run["condition"])
            meta["result"] = result.status    # 成功/失败都记录，绝不挑着存
        finally:
            rec_stop_and_flush()              # 无论成败：封包、落盘、双备份
            meta_writer.writerow(meta)        # 元数据与 bag 同名入库
        time.sleep(60)                        # 冷却：让机器人回到同一初始态

解读：运行器把"人的随意"压到最低。三个设计点：（1）配对与随机化在 build_queue 里一次完成，进入 run_experiment 后没有人再决定"今天跑哪个"；（2）先开录再执行，数据录制在场景启动之前，避免漏掉开局阶段（很多关键事件发生在最初 10 秒）；（3）finally 里封包 + 元数据落盘，失败运行的数据同样入库。最后的 60 秒冷却是被低估的细节：不做冷却，后一次运行会继承"上次结束位置、电机温度、日志堆积"等状态，配对比较的前提（同起点）就被破坏。真实场景还会把 collect_meta 接上电池管理接口与 git 版本查询，让元数据半自动生成，手工填表一定会漂。

片段 2：结果分析骨架，配对差 + 置信区间

import numpy as np

def paired_analysis(runs, metric="makespan_s"):
    """配对比较两条件：输出每对差值、效应量与 95% 置信区间。"""
    by_repeat = {}
    for r in runs:
        by_repeat.setdefault(r["repeat"], {})[r["condition"]] = r[metric]
    diffs, ctrl = [], []
    for rep, pair in sorted(by_repeat.items()):
        if "centralized" in pair and "auction" in pair:
            # 只看同一重复内两条件齐全的配对（剔除规则在协议里已冻结）
            diffs.append(pair["auction"] - pair["centralized"])
            ctrl.append(pair["centralized"])
    d = np.array(diffs)
    n = len(d)
    mean_d, sd = d.mean(), d.std(ddof=1)
    half = 1.96 * sd / np.sqrt(n)             # 95% 置信半宽
    effect = mean_d / np.mean(ctrl)           # 相对效应：平均差/对照均值
    return {"n_pairs": n, "mean_diff": mean_d, "ci95": (mean_d - half, mean_d + half),
            "rel_effect": effect,
            "verdict": "支持 H1" if mean_d + half < 0 else "证据不足"}

解读：分析只能回答"协议里写好的问题"，这从代码结构上强制了预注册纪律。paired_analysis 用配对差做比较（不用两组均值对比）：配对的方差远小于独立组（环境漂移被差掉），同样样本下结论更稳。关键统计概念：结论用置信区间表达，区间告诉你不只"有差异"，还有"差异有多大"（效应量），这才是工程决策需要的。判定逻辑 mean_d + half < 0 表示"连最保守的估计都是拍卖更快"；若区间跨 0，结论写"证据不足"；样本不够时写"没有差异"属于过度解读。verdict 建议直接回填到实验报告模板，避免手工转录出错。

常见坑

  • 变量混改：一次实验同时换策略和换任务集，"更快"归因不清。修复：自变量唯一化；其他变化放到后续实验或有计划的分层。
  • 只存成功数据：失败场次不录、不标，报告只剩"平均成功率 95%"。修复：失败运行同样入库并带异常标注；报告呈现失败清单。
  • 现场改协议：跑到一半"加一个条件试试"。修复：协议冻结版本 + 变更附录；新增条件作为下一次实验，不污染本期数据。
  • 顺序效应未控制：总是先跑 A 再跑 B，B 沾了"场地热、熟悉流程"的光。修复：随机化 + 记录 order_slot + 分析时可检查顺序效应。
  • 没有中止判据的"安全"：写了"注意安全"但没写"什么情况停"。修复：中止判据逐条列出（越界 0.5 m、姿态倾斜 > 30°、通信断 10 s……），贴在现场，任何人可执行。

练习与思考

  1. 把"围捕控制器的两种参数组谁更好"写成七要素实验方案（问题、假设、变量、对照、重复数），并计算在配对差 σd ≈ 20%、要分辨 15% 差异时的最小样本量。★
    提示
    n ≈ (1.96+0.84)² × (20/15)² ≈ 14 对；因变量选"合围时延 + 保持成功率"两个口径；假设写成"B 组合围时延中位数低 ≥ 15%"，可证伪。
  2. 设计你实验的中止判据清单（≥ 6 条），并为每条写出"谁执行、执行动作、如何记录"。★★
    提示
    示例：机器人越出警戒线 → 任一在场者按物理急停 → 记录时刻与坐标；通信中断 > 10 s → 操作员软停 + 安全员就位；任何碰撞 → 全场停。核心是"不请示、动作明确、事后可查"。
  3. 审查这个实验描述的问题："我们跑了 10 次拍卖法和 3 次集中法，拍卖法平均快 12%。"列出至少 4 个方法学缺陷并给出修正。★★
    提示
    缺陷：样本不平衡且都太少；未配对/未随机化顺序；未报告分位数与置信区间；"平均快 12%"未定义测量口径；缺失败场次。修正：配对 15+ 对、随机顺序、协议冻结、报告 CI 与失败清单。
  4. 为你的下一次实验日排一份 6 小时运行队列：起止时间、每个环节时长、电量轮换点、休息点、收尾备份步骤，并说明"试跑数据"如何标注与使用。★★★
    提示
    参考本章时间线；试跑数据保留但打 pilot=true 标签，不进主分析但可用于估计方差、修订样本量；队列留 15% 缓冲吸收故障修复时间。

小结

  • 真机实验七要素：问题、假设、自变量、因变量、控制变量、对照、重复；一次只操纵一个自变量。
  • 资源受限靠配对、随机化、分块与预排队列提效；样本量先算后跑，别等跑完才发现不够。
  • 安全是结构不是口号：急停演练、中止判据前置、三人分工、限速与围栏；任何人有权随时中止。
  • 数据 = 测量 + 元数据 + 冻结协议；失败与异常运行同样入库；剔除规则先定义后执行。
  • 下一章从单次实验走向长期运行：把车队当基础设施来管，多机器人系统运维工具链。
