第一篇 · 通信基础与系统搭建

第 005 章：参数服务器共享配置

配置也是"通信"：本节讲清 ROS2 的参数模型为什么不是一块共享黑板，以及多机器人车队的配置如何做到"一处定义、按机覆盖、运行时可审计"。

  • 主题：通信基础 / 配置管理
  • 关键机制：节点级参数、声明与校验、YAML 注入、运行时参数事件
  • 预计学时：50 分钟
  • 前置章节：第 002 章

学习目标

  • 理解 ROS2 参数的本质：节点级键值配置，与 ROS1 式的全局参数服务器有本质区别，清楚这与"共享配置"需求的差距。
  • 掌握参数的声明、读取、来源优先级（默认 → 文件 → 命令行 → launch），会做"默认值 + 覆盖"的分层设计。
  • 会用 on_set_parameters 回调做运行时校验与拒绝，理解参数事件对配置审计的价值。
  • 掌握多机器人配置的三种模式：launch 集中注入、配置话题广播、配置服务拉取，能给项目选型。
  • 能为车队设计配置版本号与启动自检，任一台机器人配置失配都能被立刻发现。

背景与动机

多机器人系统的第一行工程代码往往是配置，算法还在其次：每台机器人叫什么、在哪个域、最大速度是多少、协同周期多长。20 台机器人如果各自"手改代码里的常量"，一周后没人说得清 17 号机器人的参数是什么。配置管理的目标有三层：一致（车队共用一套基线）、差异可控（每台只解冻它必须个性化的少数项）、可审计（任何时候能回答"谁在什么时候改了什么"）。

ROS2 的参数机制常被误用：有人把它当 ROS1 的全局参数服务器用，让机器人 A 去读机器人 B 的参数；有人改了参数却没生效，因为节点根本没重新读。这些问题的根源都是没分清"节点级配置"与"车队级共享数据"的区别。本章把参数讲透之后，给出多机器人场景的三种配置分发模式，它是第 007 章命名空间、第 019 章启动编排的直接前驱，也是第 020 章阶段项目的配置骨架。

核心原理

1. 参数的本质：每个节点自己的"旋钮面板"

ROS2 的参数（parameter）是节点级的键值对：每个节点持有自己的一小张参数表，外部通过参数服务（ROS2 用服务接口实现参数的列出/读取/设置）来操作它。它与 ROS1 的全局参数服务器有三个根本区别：

  • 归属：参数属于节点实例。20 台机器人各有一个 /robotN/pid_controller，就有 20 份独立的参数表，天然支持"同一程序、不同配置"。
  • 声明机制：参数要被使用，必须先声明（declare）。未声明的参数无法读取，这是防拼写错误的护栏，也意味着"我以为我配置了"和"节点实际读到了"是两回事。
  • 类型锁定：声明时确定的类型（整数/浮点/字符串/布尔/数组）就是契约。YAML 里把本应是 double 的写成字符串，轻则在启动时报错，重则被静默忽略，这类失配是多机器人配置事故的高发区。

心智图景：参数是每台仪器面前的旋钮面板，各自独立，没有一块公共黑板。想"共享"，你要自己拉一条线（话题或服务）把旋钮值送过去，本章第 5 节整节讲这件事。

2. 参数的四种来源与优先级

一个参数最终生效的值由四层叠出来，后者覆盖前者：

  1. 代码默认值：declare_parameter("max_speed", 0.5)。写好默认值的意义是"缺配置也能安全启动"，默认值应当取保守值（慢速、小范围）。
  2. 参数文件（YAML）：部署期注入，机器人车队通常一份基线文件 + 每机覆盖。
  3. 命令行：--ros-args -p max_speed:=0.3，调试单机时最快的手段。
  4. launch 参数：正式系统的统一入口，同一份节点代码由 launch 按命名空间实例化，并注入差异化参数（第 007 章展开）。

这个优先级设计的方向是"越靠近具体部署，话语权越大"：默认值最泛，launch 最具体。把不常变的放默认值与文件，把稳定性差、经常现场调的放 launch 与命令行，是有依据的分层；随手乱放会让"配置到底在哪生效"变成玄学。

3. 运行时变更：on_set_parameters 与参数事件

参数可以在节点运行时被修改（ros2 param set 或程序调用）。修改到达时，节点有两种态度：

  • 拒绝或纠正：在 on_set_parameters 回调里检查新值是否合法。比如把速度上限设成 5.0 m/s 超过安全设计值，直接返回拒绝（REJECT），并把原因放进回调结果；或纠正为上限值（SET_AS_INTENDED 的替代语义，由你实现）。
  • 接受并生效：回调里校验通过后，把新值同步到节点内部使用它的变量（比如周期间隔、限速值），然后返回成功。

所有参数变化都会在参数事件话题上广播。这对多机器人车队很有价值：一个"配置审计节点"订阅全车队的参数事件，任何一次运行时改参都会留下日志，"谁在凌晨两点把 3 号机器人的速度上限改成了 2 m/s"，这类事故只需要翻参数事件流就能定位。

把参数接口的通信行为展开看，你会更清楚"改参为什么不必重启"：客户端库为每个节点提供一组参数服务端点（列出参数、查询描述、读取、设置等），ros2 param set 与程序内 set_parameters 走的是同一条服务调用路径；无论成功与否，节点都会在参数事件话题上发布事件消息。由此得到两条可以量化的管理结论。

参数写路径时延 ≈ 服务请求往返 + 校验回调耗时（同机常为毫秒量级） 审计流量 = 事件条数 × 单条字节数 × 台数。20 台每天 10 次变更、每次按 2 条事件、单条约 120 B 估算：20 × 10 × 2 × 120 B ≈ 48 KB/天，长期归档的成本可以忽略

数值算例说明审计的性价比：某车队 20 台机器人，运维每天调整限速与编队间距约 10 次，变更事件按每条约 120 B 计入结构化日志，一天的审计流不足 50 KB，保留 90 天的累计量仍不足 5 MB。这个体量换来的是"任何一次参数改动都能还原出时间、机器人、旧值与新值"的能力。反过来，如果配置只靠 param set 且无人订阅事件，这类追问只能靠记忆回答，配置审计等于不存在。

4. 多机器人配置的三种共享模式

参数机制本身是"本机配置"，而车队需要"共享"。给三种模式与适用场景：

模式机制适用代价
A. Launch 集中注入一份基线 YAML + 按命名空间覆盖，部署时下发绝大多数静态配置改配置需重启节点
B. 配置话题广播配置节点把车队参数发布到 /fleet/config（必要时 Transient-local），各机器人订阅热更新需运行中统一调整的参数（限速、编队间距）要自己处理一致性与时序（第 011 章 QoS）
C. 配置服务拉取机器人启动时调用 /fleet/get_config，按 robot_id 拉取自己的配置大规模、配置由中央库管理的场景服务端成为启动链路的单点

选择标准：静的多（A）、动的少（B）、中央强运营（C）。生产系统常组合使用：A 做基线，B 做运行时微调，但同一项参数不要同时由 A 和 B 管，否则"谁说了算"会陷入持久的争议。

5. 分发模式的量化对比

把三种模式放到同一张表里逐维度对比，选型就不再靠感觉：

维度A. Launch 集中注入B. 配置话题广播C. 配置服务拉取
20 台全队变更的操作步数改 1 份文件 + 重启 20 台（或分批重启）1 次发布服务端改 1 处，各机下次启动生效
生效时延一次重启窗口，分钟量级广播周期加处理，亚秒级由下次启动时刻决定
一致性机制版本库加重启幂等config_version 单调递增服务端版本号加拉取校验
运行中可变否是否（除非另配轮询刷新）
单点风险无（文件随部署分发）无（发布者只是数据源）服务端成为启动链路的单点
适合的变更频率低，随发布节奏中高频，运行中需要统一调整低，随启动节奏

读表要点：B 在操作步数与生效时延上全面占优，代价是你要自己实现版本守门与一致性巡检；C 的优势在大规模与中央运营，代价是单点风险；A 简单可靠，但每一次变更都要付出重启窗口。三者对应同一份配置生命周期的不同阶段，可以并存：A 定基线，B 管运行期微调，C 管大规模下发。选型时逐项对照"你的变更频率、对停机的容忍度、是否需要审计"，答案自然浮现。

6. 配置的版本与自检

20 台机器人的配置一致性不能靠"我们都记得改"来保证。两个廉价而有效的机制：

  • 配置版本号：在 YAML 里放一个 config_version: 7，机器人启动时同时打印版本号与配置文件的内容校验码。发布新配置（版本号 +1）后扫描全车队日志，谁还是 6 一目了然。
  • 启动自检：启动时校验关键参数的关系约束（如 max_speed <= hard_limit），不满足就拒绝进入工作状态，与其带着坏配置干活，不如当场停机报警。这条会在第 019 章生命周期节点里升级成标准玩法。

实现思路与设计

以"4 台机器人巡逻车队"为例，走一遍配置层设计：

  1. 列配置清单并分域：车队级（域 ID、协同周期、安全限速、编队间距）、单机级（robot_id、初始位姿、命名空间）、调试级（日志级别、可视化开关）。分域是设计配置的第一步，它决定了后面用哪种分发模式。
  2. 选分发模式：域 ID、命名空间、初始位姿 → 模式 A（launch 注入）；安全限速 → A 定基线 + B 做运行时调整；日志级别 → A，调试时命令行覆盖。
  3. 写基线 YAML + 覆盖表：车队共用一份基线，按 robotN 覆盖差异项。覆盖表要短，覆盖超过 5 项的机器人，说明分域没分好。
  4. 节点内校验：声明时给保守默认值；on_set_parameters 拒绝越界值；启动自检打印版本号并检查约束。
  5. 审计与回滚：配置审计节点订阅参数事件流；YAML 进版本库，回滚 = 换回上一个版本号重启。

配置分域表（巡逻车队）

配置项域来源运行时可变校验规则
domain_id车队环境变量/launch否0–101 且与调试域隔离
robot_id单机launch否全车队唯一
max_speed车队基线 YAML + 配置话题是0.1–1.5 m/s（安全上限）
formation_gap车队配置话题是1.0–5.0 m
log_level调试launch/命令行是枚举值
设计决策：为什么车队级动态参数选"配置话题"、不选"远程 param set"？

技术上你可以用 ros2 param set /robot3/controller max_speed 0.8 一台台改，但这有三个问题：改 20 台是 20 次单点操作（中途失败就是不一致状态）；绕过节点校验时行为依赖实现（有的节点没写回调，有的写）；操作不留统一记录（审计节点只能被动收事件）。而配置话题是一次发布、全体接收、版本对齐（消息里带 config_version），天然解决这三件事。原则：批量、一致性要求高的改动走广播；单台临时调试才用 param set。

关键代码与解读

片段 1：参数声明、校验与生效，节点侧的标准骨架

from rcl_interfaces.msg import SetParametersResult

class SpeedController(Node):
    """速度控制节点：参数全部"先声明、后校验、再生效"。"""
    def __init__(self, robot_id):
        super().__init__("speed_ctrl", namespace=f"robot{robot_id}")
        # 默认值取保守值：即使配置文件缺失，节点也以最安全的方式能跑
        self.declare_parameter("max_speed", 0.5)      # double，单位 m/s
        self.declare_parameter("config_version", 1)   # 整数：用于车队配置一致性检查
        # 启动即读取一次：这是参数的"初始快照"
        self.max_speed = self.get_parameter("max_speed").value
        # 注册变更回调：后续任何运行时修改都先经过这里（校验闸门）
        self.add_on_set_parameters_callback(self.on_param_change)
        self.get_logger().info(
            f"config_version={self.get_parameter('config_version').value}, "
            f"max_speed={self.max_speed}")

    def on_param_change(self, params):
        # 逐项校验：不合法就整体拒绝，返回原因供 ros2 param set 显示
        for p in params:
            if p.name == "max_speed" and not 0.1 <= p.value <= 1.5:
                return SetParametersResult(
                    successful=False,
                    reason="max_speed 必须在 [0.1, 1.5] m/s（安全设计上限）")
        # 校验全过后再把新值"接进"内部变量：生效与存储是两件事
        for p in params:
            if p.name == "max_speed":
                self.max_speed = p.value              # 热更新：控制器下一步就用新值
        return SetParametersResult(successful=True)

解读：（1）"声明 → 读取快照 → 注册回调"三步是参数使用的完整闭环。只声明不读，参数就是摆设；读了不注册回调，运行时修改不会生效，"改了没用"九成是缺了闭环的某一环。（2）默认值取 0.5 m/s（保守值）：配置系统出任何问题时，机器人以最慢速度运行仍然安全，这比"没配置就崩溃"更符合机器人系统的失效哲学。（3）校验回调把范围检查集中到一处：无论是 ros2 param set 还是程序修改，都过同一道闸门，参数的合法性不依赖调用者的自觉。

片段 2：YAML 基线 + 覆盖，一份文件管住车队

# fleet_params.yaml：基线 + 单机覆盖的写法（节点名用命名空间限定）
/speed_ctrl:                    # 谨慎使用：不带命名空间会匹配所有同名节点
  ros__parameters:
    max_speed: 0.6              # 车队基线：默认限速
    config_version: 7           # 配置版本号：每次改动 +1（审计用）

/robot1/speed_ctrl:             # 单机覆盖：只列与基线不同的项
  ros__parameters:
    max_speed: 0.4              # 1 号机器人负载重，单独降速

/robot2/speed_ctrl:
  ros__parameters:
    max_speed: 0.8              # 2 号底盘状态好，可以稍快（仍在安全上限内）
# 为什么覆盖表这么短：超过 5 项的"个性化"说明配置分域出了问题
# launch 中就把 YAML 接进去：启动的同一入口，避免"手动跑文件"式部署
def generate_launch_description():
    params_file = PathJoinSubstitution([FindPackageShare("fleet_bringup"), "config", "fleet_params.yaml"])
    nodes = []
    for rid in (1, 2, 3, 4):
        nodes.append(Node(
            package="fleet_control",
            executable="speed_ctrl",
            namespace=f"robot{rid}",                 # 与 YAML 里的键一一对应
            parameters=[params_file, {"robot_id": rid}],  # 文件 + 显式覆盖：后者优先级更高
        ))
    return LaunchDescription(nodes)

解读：（1）YAML 的键必须与"命名空间 + 节点名"精确对上，/robot2/speed_ctrl 只有 2 号机器人的那个节点会读到，写错前缀是"配置没生效"的头号原因，部署后务必用 ros2 param dump 逐台验证。（2）基线 + 覆盖的结构让"车队规则"与"单机差异"在同一文件里各自可见：改车队基线影响所有人，改覆盖只影响一台，评审时一眼能看出这次改动的影响面。（3）launch 里 parameters 列表的顺序表达了优先级：后写的字典覆盖先写的文件，所以 robot_id 这类强身份参数放在列表尾部、由 launch 注入，不给 YAML 留出错的机会。

片段 3：配置话题，运行时统一调整车队参数

class FleetConfigSubscriber(Node):
    """订阅车队配置广播：收到新配置后走与本地 param set 相同的校验路径。"""
    def __init__(self, robot_id, speed_ctrl):
        super().__init__("fleet_config", namespace=f"robot{robot_id}")
        self.speed_ctrl = speed_ctrl                 # 复用同一个节点内的校验回调
        qos = QoSProfile(depth=1,
                         reliability=ReliabilityPolicy.RELIABLE,
                         durability=DurabilityPolicy.TRANSIENT_LOCAL)
        # Transient-local：晚启动的机器人一连上就能收到"当前有效配置"
        self.sub = self.create_subscription(FleetConfig, "/fleet/config", self.on_config, qos)

    def on_config(self, msg):
        # 版本守门：只接受比本地新的配置，防止乱序消息把配置"回滚"
        local_ver = self.speed_ctrl.get_parameter("config_version").value
        if msg.config_version <= local_ver:
            return
        # 通过参数接口更新成员变量：让校验与审计走同一条路，直接改会绕开校验闸门
        from rclpy.parameter import Parameter
        result = self.speed_ctrl.set_parameters([
            Parameter("max_speed", value=float(msg.max_speed))])
        if not result[0].successful:
            self.get_logger().error("reject fleet config: 校验未通过")

解读：（1）这段代码的核心设计是"所有配置变更都走参数接口"（set_parameters），直接改内部变量会绕开校验与事件流。这样广播配置与命令行改参共享同一套校验与事件流，审计节点不需要关心配置从哪来。（2）版本守门（msg.config_version <= local_ver 就丢弃）解决的是乱序问题：广播网络不保证消息先后，没有版本比较，一台延迟的旧配置就能把全队的配置改回去。（3）Transient-local 语义让"晚加入者"拿到当前配置，避免空手启动，这正是第 011 章持久性策略在多机器人配置场景的典型应用。

运维侧配套四条命令：ros2 param list 看清节点声明了什么，ros2 param get 核对当前值，ros2 param set 做单点修改（会被校验回调拦截非法值），ros2 param dump/load 做快照与回滚。记住两次操作纪律：动手改配置前先 dump 备份；param set 不改变 YAML 基线，重启后仍以文件为准。要"永久"修改必须更新 YAML 再重启，这条纪律能让车队配置不随时间腐化。

常见坑

  • 读未声明的参数：get_parameter("mpax_speed") 直接抛异常（ParameterNotDeclaredException），节点带病启动。修复：坚持"先声明后读取"；对需要宽松读写的调试节点才开 allow_undeclared_parameters，并明白它放弃了拼写保护。
  • 类型失配静默生效或静默丢：YAML 里 max_speed: "0.5"（字符串）与声明的 double 不符。修复：部署后逐台 ros2 param get 核对类型与数值；CI 里加一段"加载 YAML 并断言关键参数类型"的检查。
  • YAML 键前缀写错：/robot1/speed_ctrl 写成 speed_ctrl，或把命名空间写成 robot_1。症状：节点用默认值静静运行，配置"改了没反应"。修复：启动日志里打印全部关键参数的最终值；用 ros2 param dump 抽查。
  • 全队 robot_id 相同：覆盖节写漏导致 4 台机器人 robot_id 全是 1，话题前缀却按命名空间展开，日志箱、任务分配全乱。修复：启动自检阶段让每台广播一次身份，中央节点做唯一性校验。
  • 把 param set 当配置管理：运行时改了 3 号机器人的参数，没记档、没同步、重启丢失，排查事故时无从复原。修复：运行时变更走配置话题并进审计日志；临时调试的改动记入值班记录，收班前恢复。

练习与思考

  1. 把片段 2 的 YAML 里 max_speed: 0.6 改成字符串 "0.6"，预测三件事：节点能否启动、ros2 param get 显示什么、实际限速是多少。解释你的推理链。★
    提示
    取决于版本与严格性设置：可能启动时报类型错误，也可能忽略覆盖退回默认值 0.5，无论哪种，"配置了 0.6 实际跑 0.5"而不自知都是事故。所以部署后必须逐台 verify。
  2. 给片段 1 增加参数 watchdog_timeout：默认 0.5 s，合法范围 [0.1, 2.0]，写下校验回调的改动，并预测 ros2 param set /robot1/speed_ctrl watchdog_timeout 5.0 的输出。★
    提示
    回调里加同名分支与范围判断；越界时成功返回 failed + reason，CLI 会显示失败原因，配置保持不变。这验证了"校验闸门对所有入口生效"。
  3. 推导题：20 台机器人、每台 8 个车队级参数。方案一：SSH 逐台手改（20 台逐一操作，单次修改出错率 5%）；方案二：配置话题广播（一次发布，全队生效）。比较两个方案的操作量与"至少一台出错"的概率，并说明广播方案的残余风险。★★
    提示
    手改：每轮 20 台逐一操作，至少一台错 ≈ 1−0.95²⁰ ≈ 64%；广播：一次发布即可完成，残余风险是"没连上的机器人静默落后"，需要 config_version 一致性巡检来兜底。
  4. 设计配置审计系统：订阅全车队的参数事件流，把"时间、机器人、参数名、旧值、新值"写入结构化日志，并对"安全关键参数被改"实时告警。写出拓扑（谁订阅谁）与至少三条告警规则。★★★
    提示
    审计节点按命名空间订阅各机器人的 parameter_events；告警规则如"max_speed 超出 [0.1,1.5]""非维护窗口的变更""同一参数 10 秒内被改超过 3 次"。参考第 018 章日志聚合。
  5. 给你的项目写一份"配置分域表"：列出至少 10 个配置项，每项标注域（车队/单机/调试）、来源（默认/YAML/launch/配置话题）、是否运行时可变与校验规则，并指出其中一项选择动态广播、不选静态注入的理由。★★★
    提示
    参考本章分域表模板；动态广播的理由通常落在"运行中需要统一调整且频率高于重启频率"，比如限速、编队间距、日志级别。

小结

  • ROS2 参数是节点级键值配置：先声明、后读取、类型锁定；它不是共享黑板，跨机共享要自己设计机制。
  • 来源优先级：代码默认 → YAML → 命令行 → launch；默认值取保守值，保证缺配置也能安全启动。
  • on_set_parameters 是唯一的合法性闸门；参数事件流提供免费的配置审计。
  • 多机器人配置三模式：launch 集中注入（静）、配置话题广播（动、带版本号）、配置服务拉取（中央运营）；同一参数只由一个模式管辖。
  • config_version + 启动自检让"配置失配"从隐蔽事故变成一行告警。
