第 020 章：阶段项目：双机器人通信与遥控

把第一篇的全部零件组装成一台可验收的系统：遥控 1 号、镜像到 2 号，安全链本地兜底，每项指标都有数字、每个故障都有演练。

  • 主题：阶段项目 / 系统集成验收
  • 关键机制：安全混合与看门狗、指令镜像、一键编排、故障注入验收
  • 预计学时：70 分钟
  • 前置章节：第 002–019 章（第一篇全部）

学习目标

  • 把第一篇的机制（命名、QoS、发现、心跳、编排、日志）兑现成一台完整系统的接口契约表与部署清单。
  • 掌握安全链设计：本地看门狗、急停服务、使能信号与指令时效，理解"安全最终兜底必须在机器人本机"。
  • 会设计指令镜像：跨机转发、缩放与使能门控，以及镜像链上的每一道本地防线。
  • 掌握验收指标的分层写法：功能性、性能、健壮性，每项给出测量方法与通过阈值。
  • 会组织故障注入演练：断链路、杀节点、断网恢复，用实测数据评审系统"够不够硬"。

背景与动机

第一篇从第 002 章的单条话题走到了第 019 章的启动编排，每个机制单独看都懂了，但"系统能力"不是机制之和，它是机制之间的接口、时序与兜底关系。本章用一个最小的多机器人系统把这些关系落成实物：遥控台控制 1 号机器人，1 号把遥控指令镜像给 2 号，两台机器人各自拥有独立的本地安全层，整车队拥有一套启动编排、心跳监控与日志。

这个系统小到两台机器人就够，却覆盖了第一篇全部关键决策：命名空间怎么分、QoS 怎么签、跨机依赖怎么接、断链怎么办、启动怎么排、验收怎么量化。完成它之后，你会拥有一份"可复制的系统模板"，后面三篇的编队、协同建图、任务调度，都是在这份模板上增加数据流与算法，基础设施无需重造。

核心原理

1. 系统定义与数据流蓝图

需求：遥控台（键盘/摇杆）以 100 Hz 输出速度指令；1 号机器人执行，并把(经安全层过滤后的)指令镜像到 /robot1/cmd_mirror；2 号机器人以 0.8 倍速度镜像执行；两台机器人都有急停与本地看门狗；全队统一域、统一命名、统一启动流程、统一日志。数据流蓝图（含归属与 QoS 决策的出处）：

2. 安全链：三道防线，各管一段

遥控系统最危险的失效是"链路死了，机器人还在以最后一个指令狂奔"。安全设计的核心原则：失效兜底必须在机器人本机，不能在链路对面。三道防线：

  1. 指令时效防线（中间件层）：控制指令配 lifespan=200 ms，拥塞时旧指令自动作废，防止"延迟执行的幽灵指令"（第 012 章）。
  2. 本地看门狗（应用层）：安全混合器（safety_mux）记录"最后一次收到遥控指令/心跳的时刻"，超过 500 ms 未刷新即输出零速。这条是全部兜底的最终防线：无论节点崩、网络断、遥控台关机，机器人都会在 0.6 秒量级内完成停车（含底盘执行时延）。
  3. 急停服务（操作层）：任何已授权的调用方能通过服务触发急停；急停是幂等设置式操作，重复触发同样结果（第 003 章的幂等纪律）。

时长设计有依据：看门狗 500 ms 取"遥控人的感知阈值"（0.5 s 的失控可被容忍与纠正）× "链路抖动 p99"（WiFi 数百毫秒）之间的平衡；如果现场 WiFi 更差，上调到 800 ms-1 s，但要同步调整验收指标。每个参数背后都有一条推导链，这是验收会能站住脚的唯一方式。

停车时间上界 T_stop ≈ watchdog_timeout + 发布周期 + 底盘执行时延 0.5 s + 0.01 s + 约 0.1 s ≈ 0.61 s；验收表里"断链后 ≤ 700 ms 双机零速"的阈值就来自这条推导（留约 15% 余量，吸收链路抖动与底盘差异）。看门狗上调到 1 s，验收阈值必须同步上调并写明理由

数值算例给出了验收阈值的来源：验收表里 700 ms 的来历是推导，看门狗、发布周期与底盘响应三项相加得出。这个套路可以推广到全部安全参数：先把"最坏情况时间线"写出来，再把它折进阈值，最后在故障注入时用时间戳验证。时间线在文档里，阈值在脚本里，证据在日志里，三者对齐，验收会就没有争议空间。

3. 指令镜像：跨机依赖的三层门控

2 号镜像 1 号不是"复制话题"那么简单，它需要三层门控才能安全：

  • 使能门：只有 1 号处于遥控模式时，2 号才允许镜像，用一条 Transient-local 的使能事件表达，2 号晚启动也能拿到当前状态（第 011 章）。1 号退出遥控/急停，使能立即置假。
  • 时效门：镜像指令超过 500 ms 未更新，2 号视为失效并输出零速，与本地看门狗同构的第二道时效判断。
  • 强度门：镜像时按比例缩放（本例 0.8），让跟随机器人的动作比主控保守，协同速度不同步时，保守的一方是安全的一方。

注意架构细节：2 号的镜像节点把指令写入自己的 cmd_vel_in，仍然经过 2 号的安全混合器，镜像路径不绕过任何本地防线。如果哪条数据流开了"安全后门"（直连底盘），整个安全设计就白做了。

带宽账本让"安全机制会不会拖累系统"这个问题有个定量答案：Twist 消息约 48 B，加序列化与传输头约 60 B，100 Hz 下镜像流约 6 KB/s；原遥控指令与镜像指令合计不到 12 KB/s，全队心跳按 1 Hz、100 B 计也在 KB/s 量级。安全链与镜像链的开销在总预算里可以忽略，真正的大头留给感知与地图（第 013/022 章）；这条结论本身就反驳了"为了性能砍掉安全设计"的做法。

镜像拓扑跳数与端到端时延失效传播缩放误差扩展评估
串联链 A→B→C每跳叠加一段网络，3 台接近 150 ms中间节点故障即击穿下游0.8 × 0.8 = 0.64，逐级复合差，链越长越脆
星型 A→其余一跳，约 60 ms故障局限在单条链路统一 0.8，可控好，镜像源由 A 的安全层兜底
广播式镜像一跳，无定向确认各接收端自行判定时效各接收端独立配置中，需要接收端纪律来兜底

拓扑选择的结论：镜像拓扑优先星型或广播，避免串联中继。串联链的问题不只是时延叠加，更在于故障与缩放误差都会沿链传播；星型让每台跟随机器人都直接面对 1 号的已决策指令，"谁跟随谁"的关系一图可查。扩到第三、第四台时，只增加源侧的一条订阅配置，不改变任何现有关系。

4. 启动与就绪：一键、有序、可重试

整系统一键启动按第 019 章的方法组织：本机节点按依赖顺序起；两台机器人的安全层先于驱动就绪；遥控台与镜像节点最后接入；每台机器人就绪后向 /fleet/ready 上报（带 boot_id）。验收时的启动标准：从执行启动命令到双机就绪上报齐全，≤ 60 s；其中任何一台失败不阻塞另一台的本地启动（故障局部化）。

5. 验收指标：三层写全

实现思路与设计

实施路径分四步，每步都有产物：

  1. 接口契约表：把"数据流蓝图"细化成话题/服务清单（名字、类型、频率、方向、QoS、生产者、消费者），本项目的对外契约，评审通过后冻结。
  2. 安全参数表：看门狗 500 ms、lifespan 200 ms、急停 100 ms、镜像缩放 0.8、时效门 500 ms，每个参数写推导依据与调整边界。
  3. 部署清单：域名 42、RMW 统一、命名空间 robot1/robot2、launch 一键、日志聚合开关、就绪上报（boot_id）。
  4. 验收脚本与报告模板：把"三层指标表"变成可执行的检查项（本章片段 4），跑完生成带数据的报告。
设计决策：为什么 2 号的镜像要"复制 1 号安全层之后的指令"？

镜像点选在安全层之后（cmd_mirror 由 1 号的安全混合器发出）有三层含义：（1）语义正确，镜像的是"1 号真正执行的指令"，包括看门狗过滤与限幅后的结果，2 号跟随的是"事实"层（已决策指令），（2）失效传播一致，1 号本地看门狗停车时，镜像流同步变为零速，2 号不需要额外判断就跟着停；（3）安全噪声不扩散，遥控台侧的网络抖动被 1 号的安全层消化过一轮，2 号收到的是相对干净的数据流。反过来（镜像原始遥控指令）会让 2 号直接暴露在遥控链路的全部抖动之下，还可能出现"1 号停了、2 号还在跑"的撕裂缝隙。镜像点的选择体现了分布式系统的一条通用原则：向下游复制"已决策"的状态，把"意图"留在上游。

关键代码与解读

片段 1：安全混合器，三道防线的代码形态

class SafetyMux(Node):
    """机器人本地的最后防线：混合指令、看门狗超时停车、急停服务。"""
    def __init__(self, robot_id):
        super().__init__("safety_mux", namespace=f"robot{robot_id}")
        self.declare_parameter("watchdog_timeout", 0.5)   # 500 ms：感知与抖动的平衡
        self.cmd, self.last_rx, self.estop = Twist(), None, False
        # 输出：本机 cmd_vel。lifespan 让拥塞期的旧指令自动作废（第 012 章）
        qos = QoSProfile(depth=1, reliability=ReliabilityPolicy.RELIABLE,
                         durability=DurabilityPolicy.VOLATILE)
        qos.lifespan = Duration(seconds=0.2)
        self.pub = self.create_publisher(Twist, "cmd_vel", qos)
        # 遥控输入与车队心跳都刷新"链路活着"；前者按契约用 Reliable，后者用 Best-effort
        self.create_subscription(Twist, "cmd_vel_in", self.on_cmd,
                                 QoSProfile(depth=1,
                                            reliability=ReliabilityPolicy.RELIABLE))
        self.create_subscription(Heartbeat, "/fleet/heartbeat", self.on_beat,
                                 QoSProfile(depth=1,
                                            reliability=ReliabilityPolicy.BEST_EFFORT))
        # 镜像出口：发"安全层之后"的指令（设计决策），供 2 号跟随
        self.mirror = self.create_publisher(Twist, "cmd_mirror", qos)
        self.create_service(Trigger, "~/estop", self.on_estop)  # 幂等急停
        self.create_timer(0.1, self.tick)                  # 100 Hz 发布
    def on_cmd(self, msg):
        self.cmd = msg                                     # 只存最新（depth=1 语义）
        self.last_rx = self.get_clock().now()

    def on_beat(self, _msg):
        self.last_rx = self.get_clock().now()              # 心跳也算"链路活着"
    def on_estop(self, _req, resp):
        self.estop = True                                  # 设置式：重复触发同结果
        resp.success = True
        self.get_logger().error("[ESTOP] 急停已执行 robot local")
        return resp

    def tick(self):
        timeout = self.get_parameter("watchdog_timeout").value
        gap = 1e9 if self.last_rx is None else \
            (self.get_clock().now() - self.last_rx).nanoseconds
        safe = self.estop or gap > timeout * 1e9
        out = Twist() if safe else self.cmd                # 超时/急停 → 零速安全默认
        self.pub.publish(out)
        self.mirror.publish(out)                           # 停机时镜像也归零

解读：（1）这段代码是三道防线里第二道的完整实现：tick 每 100 Hz 检查"最后接收时刻"，超时即零速。它的鲁棒性来自极简，不依赖任何远端协议，网络、遥控台、任何上游节点全灭，它照常运转。（2）注意 mirror 发布的是与 cmd_vel 相同的 out：1 号停车时镜像同步归零，2 号不需要额外判断就跟随停止（设计决策的落点）。（3）last_rx is None（从未收到任何输入）也按超时处理：机器人启动后没有被遥控过，就应该静止，把"没有数据"与"数据过期"统一成同一种安全语义，是看门狗代码里最容易被写错的分支。

片段 2：指令镜像，使能、时效、缩放三层门控

class CommandMirror(Node):
    """2 号机器人：镜像 1 号的已决策指令，缩放后送入本机安全层。"""
    def __init__(self, leader_id, scale=0.8):
        super().__init__("mirror", namespace="robot2")
        self.declare_parameter("scale", scale)     # 强度门：跟随速度比例
        self.enabled = False                       # 使能门：1 号 teleop 才为真
        self.cmd, self.stamp = None, None
        # 跨机订阅 leader 的安全后指令：绝对名明确指向（第 007 章）
        self.create_subscription(Twist, f"/robot{leader_id}/cmd_mirror",
                                 self.on_leader, QoSProfile(depth=1,
                                 reliability=ReliabilityPolicy.RELIABLE))
        # 使能事件用 TL：2 号晚启动也能拿到当前遥控状态（第 011 章）
        self.create_subscription(Bool, f"/robot{leader_id}/teleop_enabled",
                                 self.on_enable, QoSProfile(depth=1,
                                 durability=DurabilityPolicy.TRANSIENT_LOCAL))
        self.pub = self.create_publisher(Twist, "cmd_vel_in", QoSProfile(depth=1))
        self.create_timer(0.1, self.tick)

    def on_leader(self, msg):
        self.cmd = msg                             # 只缓存最新：镜像语义
        self.stamp = self.get_clock().now()

    def on_enable(self, msg):
        self.enabled = msg.data

    def tick(self):
        dt = None if self.stamp is None else \
            (self.get_clock().now() - self.stamp).nanoseconds / 1e9
        out = Twist()                              # 默认零速：不满足门控就静止
        if self.enabled and dt is not None and 0.0 <= dt < 0.5:
            s = self.get_parameter("scale").value
            # 缩放只写进输出值，绝不修改缓存的原指令，否则会逐周期复利相乘
            out.linear.x = self.cmd.linear.x * s
            out.angular.z = self.cmd.angular.z * s
        self.pub.publish(out)                      # 仍然经过本机 safety_mux，无后门

解读：（1）tick 里的默认输出是零速 Twist，安全输出的写法原则："先假定必须停，再论证可以动"，与"先默认能动、出问题再停"的写法是生与死的区别。（2）使能信号用 Transient-local：2 号比 1 号晚上线 10 秒，也能立刻收到"现在是否处于遥控模式"，避免"晚加入者默认失能、直到下一次事件才恢复"的体验断档。（3）输出写入 cmd_vel_in（本机相对名），2 号的镜像链路完整经过自己的 safety_mux；代码里那句注释"无后门"是架构纪律，review 时应该逐条链路检查有没有人图方便直连底盘。

        # 每台机器人"控制栈"：安全层 + 驱动，复用同一份代码与命名空间模式
        actions += [
            Node(package="fleet_base", executable="safety_mux",
                 namespace=f"robot{rid}"),
            Node(package="fleet_base", executable="base_driver",
                 namespace=f"robot{rid}"),
        ]
    # 遥控台在根命名空间工作：内部名 cmd_vel_raw 重映射到 1 号输入（第 008 章）
    actions.append(Node(package="fleet_teleop", executable="keyboard_teleop",
                        remappings=[("cmd_vel_raw", "/robot1/cmd_vel_in")]))
    # 2 号镜像节点：leader_id 与 scale 都是参数（第 005 章）
    actions.append(Node(package="fleet_follow", executable="mirror",
                        parameters=[{"leader_id": 1, "scale": 0.8}]))
    # 就绪上报与心跳（第 006/019 章）：启动完成的收尾节点
    actions.append(Node(package="fleet_ops", executable="ready_reporter"))
    return LaunchDescription(actions)

解读：（1）整份 launch 是"接口契约表"的可执行版本：两台机器人同构部署、遥控台单向接线、镜像节点参数化，每一行都能指回前 19 章的某个机制。（2）重映射出现在遥控台（内部名到外部契约）而两台机器人内部零重映射：第 008 章的边界经验，重映射只出现在"连接两个不同命名世界"的地方。（3）把域号/RMW 统一放最顶上，取代每台设备手工设置：这份文件就是"车队级配置的单一事实来源"，对应第 010 章的"三统一"。生产版本再按第 019 章升级为事件驱动编排（本示例为便于阅读保持平铺）。

片段 4：验收脚本，故障注入的时间戳才是证据

# 顺序执行；每项记录"时间戳 + 观测值 + 判定"，汇总成验收报告
ros2 topic hz /robot1/odom              # 性能：50 Hz ±5%（基线）
ros2 topic delay /robot1/odom           # 前提：时间同步已过第 009 章验收
ros2 param get /robot1/safety_mux watchdog_timeout    # 安全参数在位（0.5 s）
# 故障注入 1：拔掉遥控台网线或 kill 遥控进程 → 期望 ≤ 700 ms 双机零速
#  证据：safety_mux 日志出现 [WATCHDOG] + odom 静止时刻戳
# 故障注入 2：kill -9 2 号的 mirror 节点 → 期望心跳看门狗 ≤ 3.5 s 告警
# 故障注入 3：断 2 号网络 60 s 再恢复 → 期望 ≤ 60 s 重新就绪（/fleet/ready）
ros2 service call /robot2/safety_mux/estop std_srvs/srv/Trigger "{}"  # ≤ 100 ms
# 全部通过后：把日志聚合检索一遍，验证"故障后 5 分钟重建时间线"（第 018 章）

解读：验收脚本的精髓在注释里的"证据"二字：性能测试看数字，健壮性测试看时间戳，"拔线后停了"不算通过，"拔线后 0.42 s 停、日志时间戳与动作记录吻合"才算。四条故障注入覆盖了链路失效（1）、节点失效（2）、网络分区与恢复（3）、主动安全（4），正好对应安全链与编排机制的每个承诺。最后的日志重建检查是"可观测"指标的落地：能把一次演练复盘成一条分钟级时间线，这套系统才配称为"工程系统"，与"演示系统"彻底拉开差距。

常见坑

  • 安全只做在遥控台：遥控台判断"该停车了"再发停车指令，链路一断，指令永远到不了。修复：安全兜底必须在本机（看门狗 + 零速默认），遥控台侧的保护只是"锦上添花"。
  • 镜像路径绕过本地安全层：2 号的镜像节点图省事直接发底盘驱动，2 号失去本地兜底。修复：全部控制输入统一入口（cmd_vel_in → safety_mux），review 检查"没有任何节点直连底盘"。
  • 使能信号只在事件时发一次：2 号晚启动收不到使能，或 1 号急停后 2 号不知情继续跑。修复：使能走 Transient-local（晚加入可见）+ 退出遥控/急停必发置假；镜像端加时效门。
  • 验收只测顺利路径：正常遥控跑通就签字，上线第一天被拔网线教育。修复：故障注入是验收的必选项；四项注入（断链、杀节点、断网恢复、急停）缺一不可。
  • WiFi 部署跳过发现配置：开发用有线一切正常，现场换 WiFi 后偶发"看不见遥控台"，被当成"软件不稳定"。修复：按第 010 章先验收发现（单播列表/服务器），再谈遥控性能。

练习与思考

  1. 计算题：遥控链路预算 50 ms：遥控台采集 2 ms、网络 15 ms、1 号接收排队 5 ms、安全层 1 ms、底盘接口 5 ms，剩余是控制计算与余量。若实测网络段 p99 变成 28 ms，预算应该如何调整？给出两个方案并说明代价。★
    提示
    方案一：压缩控制计算与余量（技术债）；方案二：优化网络段，分流/信道/重传策略（第 013/014 章）。严肃系统应选择"预算不变、修根因"，把指标让位给网络属于饮鸩止渴。
  2. 改配置并预测：把 safety_mux 的 watchdog_timeout 从 0.5 s 改成 2.0 s，列出至少三个可观察变化（安全性、体验、误停率），并给出你所在场景的取值论证。★
    提示
    停车延迟上限变长（危险 ↑）；WiFi 抖动不易误停（体验 ↑）；急停前"失控窗口"变长。取值=感知容忍 × 链路 p99 抖动，两者都要报告在验收文档里。
  3. 设计题：给系统增加第三个机器人，跟随 2 号（串联镜像链 robot1→robot2→robot3）。画出数据流与门控，指出至少两个新增风险（时延叠加、失效传播）与缓解手段。★★
    提示
    时延叠加：每跳 50→100 ms，缩放再降（0.8→0.64）；失效传播：2 号挂掉 3 号直接失源，建议镜像源统一来自 1 号的 cmd_mirror 广播，放弃串联中继。串联链的每个节点故障都会击穿下游，星型镜像更稳。
  4. 推导题：全队 4 台、每台心跳 1 Hz、100 B/条，主备两个监控端各订阅全部心跳。计算心跳总带宽与"监控端漏检一台"的概率影响（假设单包丢失率 5%，连续 3 次才判定）。★★★
    提示
    带宽极小（~3 KB/s）；单包丢失 5% 时，连续 3 次全丢概率 0.05³=0.0125% 每次判定，几乎不误报，这就是"连续判定"的量化收益。主备双端使"监控自身失联"同样被覆盖。
  5. 综合评审题：写一页"上线前评审清单"：把本章三层验收指标、安全参数表、部署清单、故障注入项合成检查表，并注明每项的负责人与证据留存方式。★★★
    提示
    参考片段 4 的结构：每个检查项 = 动作 + 判据 + 证据（时间戳/截图/日志链接）+ 负责人。评审会带着这份表逐项过，拒绝"应该没问题"这类口头结论。

小结

  • 系统能力 = 机制间的接口、时序与兜底关系；本项目把第一篇的命名、QoS、发现、心跳、编排、日志组装成可验收实例。
  • 安全三道防线：lifespan（中间件）、本地看门狗（500 ms 零速）、急停服务；兜底必须在机器人本机。
  • 指令镜像三层门控：使能（TL）、时效（500 ms）、缩放（0.8）；镜像已决策状态，且不绕过任何本地安全层。
  • 一键启动 = 契约表的可执行版本；车队级配置单一来源；就绪上报带 boot_id。
  • 验收三层写全：功能性、性能（p99）、健壮性（四项故障注入）；证据 = 数字 + 时间戳 + 负载说明；可观测是第七项指标。
  • 第一篇到此完整收官。下一章进入第二篇：多机器人状态同步，从双机遥控走向 N 台机器人的状态汇聚与共享。
