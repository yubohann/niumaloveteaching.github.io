第四篇 · 系统集成与工程化

第 078 章：多机器人仿真到真机部署

仿真里跑得通，真机上满地坑：同一套上层代码，如何靠硬件抽象层、配置分层与时钟纪律平滑迁移，再用分阶段灰度与"仿真-真机差距"度量，把部署从跳崖变成走台阶。

  • 主题：系统集成 / 仿真到真机迁移
  • 关键机制：硬件抽象层（HAL）、use_sim_time、配置分层、分阶段灰度
  • 预计学时：60 分钟
  • 前置章节：第 077 章

学习目标

  • 列出仿真与真机的差异清单（动力学、传感、时间、通信、坐标系），知道哪些差异会直接让协同逻辑失效。
  • 会设计硬件抽象层：上层算法不感知仿真/真机，切换发生在驱动与配置层。
  • 掌握 use_sim_time 的规则与踩坑方式：时间源、TF 时间戳、暂停与倍速对协同系统的影响。
  • 会设计"仿真→单机→双机→全队"的分阶段灰度与每阶段验收门。
  • 能度量"仿真-真机差距"：同一场景两处运行，比较关键指标并解释偏差来源。

背景与动机

前 77 章的努力大多在仿真里完成：编队、调度、故障恢复在虚拟世界里调得又快又好。但客户和评审只认真机。迁移过程藏着多机器人特有的陷阱：仿真里 20 台机器人的通信是"本机环回"，零丢包零延迟；真机上 WiFi 一开，发现时间、时延、丢包全部进入动力学回路。仿真隐藏的恰恰是多机器人最脆弱的部分，通信。

本章的目标是建立一套迁移纪律：代码一份、配置分层、时钟讲清、逐级放行，覆盖"怎么点启动按钮"之上的全部环节。它把第 001–077 章的所有能力（命名空间、QoS、时间同步、基准测试）在真机环境里再兑现一遍，也为 079 章的"真机实验设计"与 080 章的运维体系铺路。

核心原理

1. 差异清单：仿真漏掉了什么

维度仿真世界真机世界协同逻辑的受害点
时间仿真时钟可暂停/倍速墙上时间不可控，只可同步带时间戳的融合与调度全乱
通信本机 DDS 环回，零丢包、时延微秒级WiFi：丢包、抖动、盲区、漫游编队几何、围捕、抢占判定误判
动力学理想模型（无滑移、无延迟执行）打滑、惯性、执行延迟 50–200 ms控制器增益失稳、轨迹超调
传感器理想噪声参数与完美视野污渍、反光、盲区、标定误差定位漂移、目标检测漏检
坐标系常被简化（忽略安装误差）标定偏差累积到米级TF 树错位、共享地图错层

优先级最高的三项是时间、通信、标定：它们不会让系统"跑不动"，只会让系统"慢慢跑错"。真机部署的第一个检查项永远是时间同步（第 009 章），第二个是通信质量实测（第 076 章：发现时间、P95 时延、丢包率），第三是标定复核（第 025 章：TF 与地图对齐）。这三项没达标之前，任何协同算法的调试都是在错误的地基上刷墙。

2. 硬件抽象层：一份代码，两种后端

迁移的第一原则：算法层节点不知道自己在哪儿跑。实现手段是把"数据从哪来"抽象成稳定接口：

  • 接口一致：无论仿真还是真机，上层订阅的都是 /robotN/odom、/robotN/scan、/robotN/cmd_vel（第 001 章的命名空间模板），话题名与消息类型是合同。
  • 驱动可替换：仿真时由仿真桥发布同样的话题（虚拟传感/执行）；真机时由硬件驱动发布。切换只发生在"生产话题的那一端"。
  • 配置分层：同一份节点代码，参数来自"基础层 + 环境层"的合并，环境层（sim/real）提供增益、限速、传感器配置等差异。

这种结构让第 070–075 章的调度与恢复逻辑可以原样运行：它们只依赖"robot_status、task_event 这些业务话题"，根本不关心下面的轮子是真转还是虚拟转。抽象层的验收标准很干脆：把环境开关从 sim 切到 real，上层代码 diff 为 0。

3. use_sim_time：小开关，大事故

use_sim_time 让节点用 /clock 话题（仿真时钟）作为时间源，替代系统的默认时钟。规则简单，后果凶险：

  • 必须全队一致：一个节点用仿真钟、另一个用墙上钟，两者时间戳相差可达数小时，TF 直接报"外推失败"，消息 TTL/DEADLINE 判定全乱。开关要么全开要么全关，没有中间态。
  • 仿真时钟暂停时，所有定时器停摆：仿真器暂停（或时间只推进 0.1 倍速），基于 clock 的定时器不触发、看门狗不出警，仿真里看似"稳定"，其实是没在走路。
  • 真机上严禁开着它：没有 /clock 发布者的真机节点开着 use_sim_time，等于把一个永远不走的时钟当表用，系统会"死得安静"。
时间戳一致性约束：日志/融合/调度用到的所有时间必须来自同一时间源 仿真：/clock（全队开 use_sim_time）；真机：同步后的系统钟（全队关；chrony/PTP 偏差 < 1 ms）

4. 分阶段灰度与差距度量

迁移不能一步到位，要像药物试验一样分层放行：

阶段环境验收门（全部通过才进入下一阶段）
G0 仿真全量大规模虚拟车队功能与判据全绿；性能有基准数据（076）
G1 单机真机1 台真机 + 隔离场地时间同步 < 1 ms；单机任务闭环；急停验证
G2 双机真机2 台真机通信实测（发现 < 10 s、丢包 < 1%）；编队/避障不互撞
G3 全队小场景N 台 + 降级判据协同任务成功率 ≥ 80%；072 降级被触发且正确
G4 全量生产真实场地/满规模077 压测场景通过；有回滚预案

"差距度量"是每阶段门的量化输入：同一场景（同一脚本、同一判据）在仿真与真机各跑一遍，比较关键指标，例如编队误差 P95 仿真 0.05 m vs 真机 0.18 m，就得到了"动力学+标定"的综合差距；端到端时延仿真 4 ms vs 真机 22 ms，得到通信差距。差距不必然是问题，但必须被知道：控制在仿真里调得好好的参数，到真机可能要整体放缓 30%，这种调整要以数据为依据；"真机要保守一点"式的随手调低不构成依据。

实现思路与设计

工程落地分四步：

  1. 定义接口清单：列出"仿真桥与真机驱动都要提供"的话题/服务/动作（含消息类型与 QoS）。这份清单就是 HAL 的规格书，双向可查。
  2. 配置分层：config/base.yaml（通信契约、任务参数）+ config/sim.yaml / config/real.yaml（环境差异）；launch 按参数选择并合并，节点代码只读合并后的参数。
  3. 启动切换：sim:=true/false 一个开关决定"跑哪套驱动 + 用哪层配置 + use_sim_time 的值"。开关逻辑集中在一个 launch 文件里，禁止散落。
  4. 验收门自动化：每阶段的检查项脚本化（时间同步检查、话题连通性、P95 时延、任务闭环），跑起来给出"放行/拦截"结论，人工打勾必然会漏。

差异参数表（同一节点在两种环境的典型差异）

参数仿真值真机值为什么差
编队控制增益 kp1.20.8真机执行延迟与惯性；高增益会在真机震荡
最大线速度1.5 m/s0.8 m/s打滑与制动距离；场地安全冗余
感知降级阈值宽松收紧真机丢包率天然高于仿真环回

设计决策：为什么"差距度量"要跑同一脚本同一判据？

如果仿真用 A 判据、真机用 B 判据，两边的数字不可比，"差距"就无从谈起，更没法回答"是环境差异还是这次调参搞坏了"。统一脚本与判据后，所有偏差都能归因到两个已知源：环境差异（可接受、可记录）或实现缺陷（要修）。把这两者混在一起，是仿真到真机迁移最大的效率黑洞。

关键代码与解读

片段 1：一个开关切换仿真/真机的 launch

from launch import LaunchDescription
from launch.actions import DeclareLaunchArgument, OpaqueFunction
from launch.substitutions import LaunchConfiguration
from launch_ros.actions import Node

def bringup(context, *args, **kwargs):
    sim = LaunchConfiguration("sim").perform(context).lower() == "true"
    cfg = "config/sim.yaml" if sim else "config/real.yaml"   # 环境层配置
    base = "config/base.yaml"                                # 契约层配置
    nodes = [
        # 驱动层：环境相关的唯一分叉点
        (Node(package="fleet_sim", executable="sim_bridge",
              parameters=[base, cfg]) if sim else
         Node(package="fleet_hw", executable="hw_driver",
              parameters=[base, cfg])),
        # 算法层：无论端侧是什么，代码与参数出生地都不变
        Node(package="fleet_ctrl", executable="formation_ctrl",
             parameters=[base, cfg, {"use_sim_time": sim}]),  # 时钟源随环境
        Node(package="fleet_app", executable="patrol_node",
             parameters=[base, cfg, {"use_sim_time": sim}]),
    ]
    return nodes

def generate_launch_description():
    return LaunchDescription([
        DeclareLaunchArgument("sim", default_value="true"),
        OpaqueFunction(function=bringup),
    ])

解读：这个 launch 把"迁移"的全部不确定性压缩到了一个布尔值。三个结构要点：（1）驱动层是唯一分叉点，仿真桥与硬件驱动提供同一套话题接口，这是 HAL 的落地形态；（2）参数分层合并（base + 环境层 + 运行时开关），算法节点不需要知道自己在哪跑；（3）use_sim_time 与 sim 开关绑定，从机制上消除"忘改时间源"事故，这比在文档里写"记得改"可靠一万倍。用 OpaqueFunction 是为了在启动时解析 sim 参数再构造节点（静态列表里做不变量分叉会踩替换类型的坑，071 章同款注意事项）。

片段 2：仿真-真机差距报告器

def gap_report(sim_metrics, real_metrics, keys, tolerances):
    """对比同场景两环境指标：超出容忍的标记为待归因项。"""
    report = []
    for k in keys:
        s, r = sim_metrics[k], real_metrics[k]
        rel = (r - s) / s if s != 0 else float("inf")
        status = "OK" if abs(rel) <= tolerances.get(k, 0.3) else "GAP"
        report.append({"metric": k, "sim": s, "real": r,
                       "rel_diff": round(rel, 3), "status": status})
    return report

# 用法：跑完 G1/G2 场景后对比，例：
#   latency_p95_ms:   4.0 → 22.0   (+450%, GAP：通信差距，预期内但需记录)
#   formation_err_p95:0.05 → 0.18  (+260%, GAP：增益需再降或标定需复核)
#   task_success:     1.0  → 0.9   (-10%,  OK：首轮真机可接受)

解读：差距报告器是迁移期的"体检单"。指标选择要紧贴协同链路（时延、编队误差、任务成功率、恢复时间）；泛泛的 CPU/内存指标对迁移验收帮助有限。容忍度按指标分设（时延差距 300% 都算预期，任务成功率差 10% 就要警惕），"预期内的差距"和"需要行动的差距"必须用数字区分，否则每次评审都在争论"这算不算正常"。带 status 的报告进入第二阶段验收门：所有 GAP 项要么给出归因（环境差异，记录在案），要么进入修复队列（实现缺陷），不允许"知道但不处理"。注意这段代码需要一个可复用的场景脚本（076/077 章资产）：迁移不只是换后端，测量资产也要跟着搬过去。

常见坑

  • use_sim_time 不一致：一个节点开、一个关，TF 外推失败、DEADLINE 全炸。修复：开关与 sim 参数绑定进 launch；上线自检脚本断言"全队时间源一致"（用 topic hz 检查 /clock 存在性 + 节点参数抽查）。
  • 直接把仿真增益搬到真机：高增益在理想动力学里稳定，真机执行延迟让它震荡。修复：真机首跑用"降增益 + 降速"安全配置；按阶段门逐步回复，用差距报告做依据。
  • 仿真里验证通信逻辑：本机环回零丢包，把 072 的降级阈值调到"理想值"，真机一跑全误报。修复：通信相关阈值以真机实测数据重标；仿真只验流程是否触发。
  • 标定误差没复核：仿真里 TF 是"设定值"，真机多机标定误差累积，编队/地图全错位。修复：G1/G2 阶段门包含标定复核（静态目标位姿误差 < 3 cm）；每次场地变更后重标定。
  • 真机验收没有回滚预案：全队一起上，出事只能人工抱机器。修复：分阶段灰度 + 每阶段有急停与"退回仿真/单机模式"的配置开关；G3 起必须先在 077 场景里压过。

练习与思考

  1. 列出你的系统 HAL 接口清单（话题/服务/动作 + 消息类型 + QoS），标注哪些由仿真桥提供、哪些由真机驱动提供、哪些两者都要实现。★
    提示
    从第 001 章计算图出发：/odom、/scan、/cmd_vel、/robot_status、task 动作是两面都要有的合同项；仿真桥可能额外提供"作弊通道"（直接读真值），必须与真实驱动接口分开、且只在 sim 配置里启用。
  2. 写一份 use_sim_time 事故复盘：假设真机测试时某个传感器驱动忘了关 use_sim_time，描述你会观察到的三个症状、根因链与修复动作。★★
    提示
    症状：该话题时间戳停在 0/僵死、TF 报时间外推、依赖其时间戳的融合输出跳变或静默；根因：无 /clock 发布者，仿真时钟不前进；修复：参数由 launch 统管 + 启动自检断言。预案里再加一条"关键话题时间戳新鲜度"告警。
  3. 你的编队误差在仿真里 P95 = 0.06 m、真机 = 0.22 m。设计一个两步归因实验：先分离"动力学/增益"与"定位/标定"两类来源，再给出各自的修复动作。★★
    提示
    步骤一：真机原地重放静态编队（低速 0.2 m/s，只依赖定位）→ 若误差仍大，定位/标定为疑；步骤二：低速动态轨迹扫一遍增益表（0.4/0.6/0.8），看误差-增益曲线是否在仿真曲线上平移。修复：前者重标定+融合复检；后者按曲线选增益。
  4. 为你的项目写"迁移放行单"模板：G1–G4 每阶段的必检项、判据、负责人、不通过时的处置（回退到哪一阶段、修复后如何复验）。★★★
    提示
    必检项从本章两表里选并加"环境快照"（固件版本、标定日期、AP 分布）；不通过处置默认"回退一格 + 差距报告更新 + 修复项进入队列"；复验要求"原场景重跑 + 新增回归场景"，防止修 A 坏 B。

小结

  • 仿真与真机的五大差异（时间、通信、动力学、传感、标定）中，时间/通信/标定是协同逻辑的第一杀手，先达标再调算法。
  • HAL 的验收标准：切换环境开关后上层代码 diff 为 0；驱动层是唯一分叉点，参数走"基础+环境"分层合并。
  • use_sim_time 全队一致、与 sim 开关绑定；仿真时钟可暂停/倍速的特性要防"看似稳定其实没走"。
  • 分阶段灰度 G0→G4，每阶段有可脚本化的验收门；差距度量用同一脚本同一判据，把偏差归因到"环境差异"或"实现缺陷"。
