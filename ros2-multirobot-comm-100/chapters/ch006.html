第 006 章：节点发现与计算图监控

20 台机器人上线后，第一句话应该是"谁在线、谁和谁连着、谁在偷偷死亡"。本章把计算图变成可查询、可巡检、可告警的对象。

  • 主题：通信基础 / 系统可观测性
  • 关键机制：图发现 API、看门狗心跳、分层监控、滑动窗口频率检测
  • 预计学时：55 分钟
  • 前置章节：第 002 章

学习目标

  • 理解 ROS2 计算图的动态属性：节点与端点的出现、匹配、消失都在运行中发生，监控必须"活"着做。
  • 掌握图查询 API 与 CLI 的关系：get_node_names、count_publishers 等能直接问出"发现状态"，不依赖外部工具。
  • 会设计分层监控：进程层、图层、应用层各自解决什么问题，为什么要三层都建。
  • 掌握心跳（heartbeat）与看门狗（watchdog）的定量设计：周期、超时、误报与漏报的权衡。
  • 能写一个图巡检节点：对照"预期节点清单"检测缺失、静默话题与端点异常，并输出可行动的告警。

背景与动机

多机器人系统代价最高的故障是静默死亡，它比显式崩溃更隐蔽：3 号机器人的定位节点因为一次异常退出了，进程管理器不知道，遥控台不知道，其他机器人照常发协同消息但永远等不到它的状态。没有监控的系统里，这类问题往往是在任务失败数小时后靠"人肉发现"暴露的。

ROS2 的一大优势是：通信底座（DDS）本来就在持续交换"谁存在、有哪些端点"的信息，ROS 又把它们暴露成了图查询接口，监控不需要额外协议，只需要把这些已有的信息读出来、对照预期、及时告警。本章讲清计算图监控的三个层次与两个核心工具（图巡检、心跳看门狗），它们将在第 018 章（日志与监控）、第 039 章（系统级健康监测）中升级成完整体系，是阶段项目验收指标里"谁掉线多久被发现"的直接答案。

核心原理

1. 计算图是"活"的：监控的对象是变化

ROS2 的计算图（computation graph）由节点（node）与各类端点（话题、服务、动作、参数）组成。与静态配置文件不同，它是运行时持续变化的场景：机器人接入网络 → 它的节点被其他成员发现；某节点退出 → 它的端点从图中消失；QoS 匹配成功 → 一条数据通路"点亮"。监控的第一个认知是：监控的对象是"图的变化与预期之间的偏差"，静态的"一张图"没有意义。

DDS 的发现机制（第 010 章详述）让每个参与者天然掌握"域内有哪些成员"。ROS 客户端库把这些信息整理成图查询 API 和 CLI：

问题API / CLI说明
有哪些节点？get_node_names() / ros2 node list节点全名列表，含命名空间
某话题有几个发/收端点？count_publishers/subscribers() / ros2 topic info端点计数：匹配失败时数字会不对
端点细节（QoS/类型）？get_publishers_info_by_topic() / --verbose排障静默不匹配的最终依据
图中有什么话题/服务？get_topic_names_and_types() 等用于自动巡检与文档生成

一个实践细节：CLI 的图查询走本机守护进程（daemon）的缓存，追求"打字快"；程序里直接调用图 API 拿到的是客户端库视角的实时数据。发现"CLI 与程序看到的不一致"时，ros2 daemon stop 重启守护进程往往能解决，但更本质的原因是发现本身有时间差，任何图快照都只是"此刻的近似"。

2. 三层监控：进程活着 ≠ 节点活着 ≠ 数据流动

很多团队只装了一层监控（进程守护），然后在故障复盘时才发现盲区。三层各自的职责：

  • 进程层：操作系统视角，进程在不在、CPU/内存多少。工具是 systemd、supervisor 或容器健康检查。它能发现"整个进程死了"，但发现不了"进程活着、里面的节点早退出了"。
  • 图层：ROS 视角，节点是否注册、关键端点的发布者/订阅者计数是否符合预期。这一层能发现"节点半死""发现没完成""QoS 静默不匹配"（计数与预期不符）。
  • 应用层：业务视角，话题频率、心跳、端到端延迟。图层说"数据通路存在"，应用层才回答"数据真的在流"。一个订阅者匹配上了但发布者卡死，只有应用层能发现。

三层是递进的推理链：进程死了 → 图里节点消失；节点崩了但进程还在 → 图里缺节点；图正常但数据不流 → 应用层频率掉零。故障定位的效率完全取决于你把探测点放在哪一层。探测点放置还有一条原则：探测要能代表被测对象，又不能被它的失效一并带走。本机体检放在同一台机器上的独立节点里，生产节点崩了它还在，取数也不经过网络；中心看门狗只看心跳流，业务流量再乱也不影响它对"在不在"的判断。反例是把频率统计写死在业务节点自身：节点一崩，指标与节点一起消失，监控看到的最后一条数据永远是"正常"。

3. 心跳与看门狗：把"活着"变成数字

应用层最通用、成本最低的机制是心跳：每个机器人周期发布一条极小的心跳消息（标识 + 时间戳 + 关键状态），监控端记录"最后一次收到的时间"。若超过 超时阈值 = 心跳周期 × N 没收到，判定失联。参数量化：

检测时间上限 ≈ 心跳周期 × N；稳态带宽 = 心跳大小 × 频率 × 台数 1 Hz 心跳、N=3：最坏 3 s 发现失联，稳态带宽 20 台 × 64 B ≈ 1.3 KB/s，廉价的可靠性保险

周期与阈值直接决定两种错误的比例：阈值太紧（比如周期 100 ms、阈值 150 ms），网络抖动就会疯狂误报"失联"（误报），值班员很快对它脱敏；阈值太松（阈值 30 s），真失联半小时才发现（漏报）。合理起点：心跳 1–2 Hz、阈值 3–5 个周期，并要求"连续 K 次超时"才升级为告警，用连续判定滤掉偶发丢包。

算例：连续 N 次判定把误报压到多少？设单次心跳丢失概率为 p 且各次相互独立，连续 N 次全丢的概率为 pN。1 Hz 心跳、p = 5% 时，N=3 的误报概率 1.25×10⁻⁴，按一天 86400 次判定计，每台机器人每天约 11 次误报，值班员必然脱敏；把 N 提到 5，误报降到约 37 天一次。三档对比：

单次丢包率 pN=3：误报频率N=5：误报频率取值建议
1%约 12 天一次数百年一次N=3 已够用
5%每台每天约 11 次约 37 天一次必须 N=5
10%每台每天约 86 次约 1.2 天一次先修网络，再谈阈值

换算成设计规则：若目标是"每台机器人每月不超过 1 次误报"，在 p = 1%、5%、10% 三档下分别需要 N ≥ 4、5、7。注意上表假设各次丢失独立；真实无线网络的丢包常成串出现（漫游、干扰突发），连带丢失会让误报率高于估值，所以 N 要按"实测网络最差时段"来定。顺带把心跳计入带宽表：64 B 载荷经 UDP/IP/RTPS 封装后线上约 162 B，20 台 1 Hz 共约 3.2 KB/s，相对控制流量可以忽略，但写进预算就不会在扩容时被忘掉。

还有一个拓扑问题："谁监视谁"。两种基本结构：中心监控（一个监控节点收全队心跳，简单、有全局视图，但监控端是单点）与去中心互相监视（每台机器人监视邻居，无单点、但全局视图要靠聚合）。工程折中很常见：中心监控做全局视图 + 每台机器人本地看门狗（监视遥控/调度链路），互相兜底。

4. 图巡检：把"预期拓扑"文档化并自动对照

监控要回答"图对不对"，前提是有"标准答案"。做法是把预期拓扑写成清单：每台机器人应有哪些节点、每个关键话题应有几个发布者/订阅者。巡检节点周期（如每 5 s）扫描图，逐项对照：

  • 预期节点缺失 → 节点没起来或崩了（线索交给进程层与日志）；
  • 话题发布者数 = 0 而预期 ≥ 1 → 发布端异常；订阅者数为 0 而预期 ≥ 1 → 消费端异常或命名/匹配问题；
  • 发现超过阈值时间仍不达标 → 可能是发现故障（对比第 010 章的排查）。

巡检与心跳互补：巡检回答"结构对不对"（可以在数据静默前就发现端点消失），心跳回答"数据流是否活着"。两者叠加，才能覆盖"静默死亡"的全部形态。

维度图巡检心跳看门狗
回答的问题结构对不对：节点与端点是否齐全数据流是否活着
时间尺度秒到十几秒，跟随发现收敛秒级：心跳周期 × N
运行开销查询图 API，接近零流量每台持续发送一条极小消息
发现不了的故障端点都在、数据不流（发布者卡死）单个子节点退出但整机心跳照常
误报来源发现尚未收敛、预期清单过期网络抖动、丢包成群

实现思路与设计

以 20 台机器人车队设计监控系统，按"清单 → 分层 → 拓扑 → 告警"四步：

  1. 写监控清单：把"系统健康的定义"落成表格，检查项、方法、阈值、动作。没有清单的监控会退化成"凭感觉加告警"。
  2. 分层落点：进程层交给部署工具（systemd 自动重启 + 日志）；图层与应用层由本章的巡检节点与本地体检节点承担。
  3. 定拓扑：每台机器人跑"本地体检"（测自己的话题频率，本机测量不受网络影响）；中央"车队监控"节点订阅各机的体检报告与心跳，做全局状态聚合与告警。
  4. 设计告警策略：分级（INFO/WARN/CRITICAL）、连续判定（连续 3 次异常才告警）、恢复通知（失联恢复也要发一条）。

监控清单（节选）

检查项层方法阈值/条件动作
节点进程存活进程systemd/容器状态退出即事件自动重启 + 记日志
预期节点在图中图图巡检对照清单缺失 > 10 sWARN→CRITICAL
关键话题端点计数图count_publishers/subscribers与预期不符 > 10 s告警（疑发现或 QoS 问题）
里程计话题频率应用本机滑动窗口< 45 Hz（预期 50）本机告警 + 上报
心跳应用中心看门狗连续 3 周期未收到CRITICAL：失联
设计决策：为什么频率检测要放在每台机器人的本地体检节点里，中央监控端行不行？

如果中央监控跨网络订阅 20 台机器人的话题来测频率，测出的数字混入了网络损耗与调度抖动，一台 WiFi 信号差的机器人会被误判为"话题异常"，而问题根源在网络，不在发布端。把频率检测放在生产数据的本机（甚至直接在发布者的定时器里统计），得到的是"系统真实产出率"；网络层的损耗另外由心跳与延迟指标衡量。让每一层只回答自己能回答的问题，是监控系统可信度的来源。

关键代码与解读

片段 1：图巡检节点，对照清单检查节点与端点

class GraphInspector(Node):
    """每 5 秒对照"预期清单"巡检计算图：缺节点、端点计数异常都要报。"""
    def __init__(self):
        super().__init__("graph_inspector")
        # 预期清单：图中"必须存在"的节点与"最小端点计数"，应由部署配置生成
        self.expected_nodes = {f"/robot{r}/odom_pub" for r in range(1, 5)}
        self.expected_edges = {                 # 话题 -> (最少发布者, 最少订阅者)
            "/robot1/cmd_vel": (1, 1),
            "/fleet/battery_min": (0, 1),
        }
        self.create_timer(5.0, self.inspect)    # 巡检周期：与发现时间尺度匹配

    def inspect(self):
        live = set(self.get_node_names())       # 实时图查询：不需要额外协议
        for n in self.expected_nodes - live:    # 预期存在但图中没有：缺失告警
            self.get_logger().error(f"节点缺失: {n}")
        for topic, (min_pub, min_sub) in self.expected_edges.items():
            npub = self.count_publishers(topic)
            nsub = self.count_subscribers(topic)
            # 端点计数不符时，可能是节点问题，也可能是发现/QoS 匹配问题
            if npub < min_pub or nsub < min_sub:
                self.get_logger().warn(
                    f"{topic}: pub={npub}(>={min_pub}), sub={nsub}(>={min_sub})")

解读：（1）巡检的价值在于"对照"，没有预期清单，图上有什么都不算异常。清单应该由部署配置（launch 里的机器人列表）自动生成；在监控代码里手抄一份会导致每次扩编都要改两处。（2）节点缺失与端点计数分开报：前者通常是进程问题，后者也可能是发现或 QoS 问题（第 010、012 章的排查工具在这里被程序化）。（3）巡检周期 5 s 是刻意的：小于发现收敛时间会误报（图还没稳定），太长则故障发现慢；与心跳的秒级检测配合，覆盖不同时间尺度。

片段 2：本地体检，滑动窗口频率检测与心跳

class HealthReporter(Node):
    """本机体检：测关键话题的真实频率，同时向车队广播心跳。"""
    def __init__(self, robot_id, watch_topics):
        super().__init__("health", namespace=f"robot{robot_id}")
        self.robot_id = robot_id
        self.stamps = {t: deque(maxlen=100) for t in watch_topics}   # 每话题的到达时刻窗口
        for t in watch_topics:
            # 用与生产者一致的 QoS 订阅，才能测到"真实"频率，避免被过滤后测出假象
            self.create_subscription(Header, t, partial(self.on_msg, t), QoSProfile(depth=50))
        # 心跳：1 Hz、极小载荷；失联检测的原料
        self.hb_pub = self.create_publisher(Heartbeat, f"/robot{robot_id}/heartbeat",
                                            QoSProfile(depth=1))
        self.create_timer(1.0, self.beat)
        self.create_timer(5.0, self.report)

    def on_msg(self, topic, _msg):
        self.stamps[topic].append(self.get_clock().now().nanoseconds)  # 只记录时刻

    def beat(self):
        msg = Heartbeat()
        msg.robot_id = self.robot_id
        msg.stamp = self.get_clock().now().to_msg()
        msg.state = "active"
        self.hb_pub.publish(msg)                # 心跳语义：我还活着（内容从简）

    def report(self):
        for t, q in self.stamps.items():
            if len(q) < 2:
                self.get_logger().warn(f"{t} 无数据")
                continue
            # 窗口频率 = (样本数-1) / 时间跨度：跨过"窗口里到底几个"的歧义
            span = max(q[-1] - q[0], 1)
            hz = (len(q) - 1) / (span / 1e9)
            if hz < 45.0:                       # 预期 50 Hz：低于 90% 即告警
                self.get_logger().warn(f"{t} 频率异常: {hz:.1f} Hz")

解读：（1）频率用"滑动窗口"测：窗口太短（如 1 秒）量化误差大，50 Hz 的期望在 1 秒窗里天然是 ±2% 抖动；deque(maxlen=100) 让窗口兼顾"长到能平均"与"短到能及时发现"。（2）体检节点用自己的 QoS 订阅被测话题，注意注释：若生产者是 Best-effort、体检端用 Reliable，匹配不上会测出"零频率"的假象，所以 QoS 要对齐（第 012 章会给完整规则）。（3）心跳与告警分离：心跳走极简负载（失联检测只需要"到达"这件事），频率等细节走 5 s 一次的本地报告，把"我在"和"我好"分成两条信息，各自用合适的频率，避免心跳被大报文拖累。

片段 3：中心看门狗，连续判定防误报

class FleetWatchdog(Node):
    """中心看门狗：收敛全队心跳，连续缺失才判失联，恢复也要报。"""
    def __init__(self, robot_ids, period=1.0, miss_limit=3):
        super().__init__("fleet_watchdog")
        self.last_seen = {}                      # rid -> 最近一次心跳的本地时刻
        self.missed = {r: 0 for r in robot_ids}  # 连续未收到次数
        self.down = {r: False for r in robot_ids}
        for rid in robot_ids:
            # 心跳用绝对名订阅；参数与调度器共用一份"失联阈值"配置（第 005 章）
            self.create_subscription(Heartbeat, f"/robot{rid}/heartbeat",
                                     partial(self.on_beat, rid), QoSProfile(depth=1))
        self.create_timer(period, self.check)

    def on_beat(self, rid, _msg):
        self.missed[rid] = 0                     # 任何一次到达都清零：连续判定
        self.last_seen[rid] = self.get_clock().now()

    def check(self):
        now = self.get_clock().now()
        if not self.last_seen:                   # 还没有任何首跳：由图巡检盯启动，不在此误报
            return
        for rid, t0 in list(self.last_seen.items()):
            gap = (now - t0).nanoseconds / 1e9
            if gap > 1.5:                        # 一个周期 1 s，1.5 s 未见记一次
                self.missed[rid] += 1
                # 连续 3 次（≈3.5 s）才升级为失联：滤掉偶发丢包与抖动
                if self.missed[rid] >= 3 and not self.down[rid]:
                    self.down[rid] = True
                    self.get_logger().error(f"robot{rid} 失联（连续 {self.missed[rid]} 次）")
            elif self.down[rid]:                  # 恢复也是事件：值班界面要看到"康复"
                self.down[rid] = False
                self.get_logger().info(f"robot{rid} 已恢复心跳")

解读：（1）核心是连续判定：任何一次心跳到达就清零计数，只有连续 3 个检查周期都没有心跳才判失联，"心跳阈值 ×N"的工程化实现，把偶发丢包与真实失联区分开。（2）注意代码里一个细节：check 遍历 last_seen，从不"假设刚启动时所有机器人都该有心跳"（那些机器人还没有首跳记录，不该立刻炸出 20 条告警），首次心跳缺失是启动问题，交给图巡检的清单去管。这种"两种监控各管一件事"的分工让告警更可解释。（3）恢复通知（已恢复心跳）与告警同等重要：如果只有故障没有恢复，值班员无法确认状态回稳，也无法统计"失联持续了多久"，而后者恰是第 020 章验收指标里的量化项。

常见坑

  • 信任 CLI 的第一眼：刚启动就 ros2 node list 看不到全部节点就断言"发现坏了"，其实是发现尚未收敛（秒级到十几秒，规模越大越久）。修复：给巡检加"连续 N 次不达标才告警"的时间窗；单点判断会被发现收敛期的正常波动触发。
  • 只监控进程不监控图：systemd 显示 20 个进程全部 active，但其中 3 个节点的主循环早就崩在回调里（进程靠残留线程活着）。修复：图巡检 + 心跳，把"节点级活着"与"业务级活着"补上。
  • 心跳阈值拍脑袋：设成 100 ms 一次、200 ms 判失联，WiFi 一次漫游就全队报失联。修复：按"检测目标 × 网络 p99 抖动"反推（例如要求 3 s 内发现，就取 1 Hz + 连续 3 次）；先在真实网络测一周再收紧。
  • 中心监控自己失联没人知道：全舰队依赖一个监控节点，它死了，整个面板"全绿"（因为没有数据被显示成"没有异常"）。修复：监控节点也要心跳；面板对"数据源断流"要显示为显式告警，静默等于掩盖。
  • 告警风暴与脱敏并行：一次网络抖动引发 40 条重复告警，值班员开始忽略所有告警，真正的事故来了也没人看。修复：分级 + 聚合（同一故障只报一次+计数）、连续判定、恢复通知，让每条告警都携带"该做什么"。

练习与思考

  1. 把片段 3 的心跳周期从 1 s 改为 0.2 s，同时保持"连续 3 次"判定。预测：检测时间、带宽、误报率各如何变化？给出你为巡检场景选择周期的理由。★
    提示
    检测时间从 3 s 缩到 0.6 s；带宽 ×5（仍很小）；但 0.2 s 粒度会暴露更多网络抖动，误报率上升，公共卫生级巡检 1 Hz 足够，只有安全联锁场景才需要亚秒级。
  2. 推导题：滑动窗口长度 W 秒、真实频率 f，窗口内计数的量化误差最大是多少？若 f=50 Hz，要求频率判读误差 < 5%，W 至少要多少？★★
    提示
    计数误差 ±1 帧，频率误差 ≈ 1/W Hz；要求 1/W < 2.5 Hz → W ≥ 0.4 s。但还要覆盖抖动，实践取 1–2 s 窗口再平滑。
  3. 给一个双机器人 Demo 设计监控方案：列出至少 8 个检查项，标注层次（进程/图/应用）、检测方法与阈值，并说明哪一项能在"遥控链路断开"时最先触发。★★
    提示
    遥控链路断开：心跳（应用层）最先触发；cmd_vel 订阅者计数（图层）其次；若机器人侧有本地看门狗，它会先自停并用日志记录。参考本章清单模板。
  4. 模拟三种故障，(a) 杀掉一个节点进程；(b) 节点活着但发布者为 0；(c) 节点与发布者都在但没有数据，写出你的监控栈分别靠哪一层、哪条规则发现，并给出修复动作。★★★
    提示
    (a) 图巡检缺节点 + 进程层事件；(b) 端点计数告警；(c) 只有应用层频率/心跳能发现，这就是三层都要建的理由。
  5. 设计"监控面板信息架构"：为 20 台机器人车队画一屏（草图）：全局健康分、失联清单、频率异常榜、最近 10 条告警流。说明每个元素的数据来源与刷新率。★★★
    提示
    全局分=心跳在线率；失联清单来自看门狗；频率异常来自各机体检报告（5 s 上报）；告警流来自分级告警总线。刷新率从 1 s（心跳）到 5 s（体检）分层。

小结

  • 计算图是活的：监控对象是"图与预期的偏差"，不是静态截图；图查询 API 让你不写新协议就能巡检。
  • 三层监控缺一不可：进程层看存活、图层看端点与匹配、应用层看数据真的在流动。
  • 心跳设计 = 周期 × 连续判定：1 Hz + 连续 3 次是通用起点；误报与漏报由这两个参数直接决定。
  • 频率检测放在数据产生的本机做；跨网络测频率会把网络问题误记为话题问题。
  • 告警要分级、聚合并携带动作建议；恢复通知与故障通知同等重要。
