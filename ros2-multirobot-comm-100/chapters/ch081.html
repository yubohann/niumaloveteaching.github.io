第四篇 · 系统集成与工程化

第 081 章：多机器人系统版本管理与配置

车队里最危险的是"说不清哪台跑哪个版本"，版本老旧只是表面问题：用不可变构建物、配置分层与内容标识、接口版本握手、分批滚动升级，把变更从"现场玄学"变成受控流程。

  • 主题：系统集成 / 版本与配置治理
  • 关键机制：不可变构建物、配置分层、接口版本握手、滚动升级与回滚
  • 预计学时：60 分钟
  • 前置章节：第 080 章

学习目标

  • 区分软件版本、配置版本与接口版本三个维度，理解各自的变化频率与治理方式。
  • 掌握接口兼容性规则：哪些消息修改是兼容的、哪些是破坏性的，如何用版本握手在启动时快速失败。
  • 会设计配置分层与校验：base/site/robot 三层合并、schema 校验、配置内容标识进心跳供漂移检测。
  • 会执行"一次构建、多次部署"与分批滚动升级：金丝雀→小批→全量，健康门与回滚点齐备。
  • 能定义配置漂移的检测与处置流程，把"有人在机器人上改了参数"从隐患变成可发现事件。

背景与动机

前二十章把系统做得越来越"能打"，但战斗力的第一步是知道自己手里的部队是什么状态。真实车队最常见的灾难性混乱是：A 机器人上周改过参数没人记、B 机器人还在跑半年前的镜像、升级到一半断电导致半新半旧、两台机器人对同一消息结构的理解不一致却没人报错。等你需要复盘时，连"当时跑的是什么"都答不上来。

版本与配置治理就是给系统建立"可追溯、可复现、可回滚"三条底线：任何时刻能回答"谁在跑什么"（第 080 章清单的深化）、任意一版能原样重建、任何一次变更能安全撤回。它是第四篇工程化弧线的收口，前面所有机制（QoS、调度、恢复、重构、运维）只有在受控的版本与配置基础上才谈得上"稳定"。

核心原理

1. 三个版本维度，三种变化节奏

维度载体变化频率治理方式
软件版本ROS 包、依赖、固件、镜像天/周级不可变构建物 + 语义化版本 + 容器/镜像固化
配置版本参数 YAML、地图、标定文件小时/天级Git 管理 + 分层合并 + 内容标识审计
接口版本.msg/.srv/.action 定义、协议月级（动了就是大事）兼容性规则 + 启动握手 + 版本拒连

三者必须分开管理、统一审计：把配置混进代码仓库一起发（改个阈值要重新构建镜像）太笨重；把接口定义当普通配置随时改（不升包版本）则会产生"两台机器人消息结构不同却互相发现"的幽灵故障。正确姿势：软件版本号（如 fleet_core 2.4.1）、配置内容标识（如 cfg:a1b2c3）、接口版本（如 iface:3）三个值都出现在心跳与状态清单里，任何运维决策的第一步都是先看这三个值。

2. 接口兼容性规则：什么改动会炸车队

接口改动性质为什么
新增字段并带默认值兼容（前向+后向）旧消费端忽略新字段；旧发布端缺字段取默认
重命名字段/话题破坏性旧端直接匹配失败（话题级）或字段读取异常
修改字段类型或语义破坏性序列化不兼容；语义错位比崩溃更隐蔽
改变单位（如 mm→m）破坏性且最阴险类型没变，值差 1000 倍，静默出错
删除字段破坏性旧端读取失败或取默认；行为悄悄变化
新增可选服务/动作兼容旧端不调用即无感知

铁律：接口定义一旦进入车队运行，只增不改；语义变化必须伴随版本号升级与握手校验。为了防止"有人在消息里悄悄改单位"，把接口版本放进"启动握手"：新节点启动时与车队互报 interface_version，不匹配就拒绝启动并给出明确日志，运行几分钟后才暴露的玄学偏差代价更高。滚动升级期间允许新旧并存，条件是**接口版本落在兼容窗口内**（例如 iface 3 与 4 声明为互操作，5 及以上不兼容），兼容窗口是显式声明的数据，不是口头约定。

3. 配置分层：合并规则与校验

配置按三层组织：base（全队契约：话题名、QoS、任务模板骨架）、site（场地级：地图路径、AP 布局、限速区域）、robot（个体：标定参数、轮径、增益微调）。合并顺序固定（后层覆盖前层），合并结果计算内容标识。三条纪律：

  • 所有配置进 Git，现场禁改，发现现场直改的文件，视为事故处理（至少是流程逃逸）。
  • schema 校验：键名白名单、类型、范围（限速 ∈ [0, 2.0] m/s）；校验失败的配置不允许进入部署环节。
  • 敏感信息分离：密码、口令、私钥不进配置仓库，引用外部密钥管理，配置里只放引用标识。
配置身份 = hash(base ⊕ site ⊕ robot)，随心跳上报 聚合端发现"同组机器人内容标识不一致"即配置漂移；漂移按事件上报，级别高于普通警告，要进审计流（080 章）

4. 一次构建，多次部署：滚动升级与回滚

发布流程的黄金法则：构建产物不可变，CI 里构建一次、打内容标识、存制品库；部署只是"把同一制品复制到 N 台机器人"，绝不在机器人上重新构建（不同编译器/依赖版本会造出行为差异）。发布节奏按"环（ring）"推进：

环范围观察窗进入下一环的条件
R0 金丝雀1 台试验机（或仿真）≥ 24 hSLO 无劣化、任务成功率不降
R1 小批10% 机器人≥ 48 h关键指标 P95 无恶化；无新增告警类型
R2 全量其余机器人持续观察版本身份写入清单；旧版制品保留 N 版备回滚

回滚能力要在升级前就位：镜像用 A/B 分区或容器镜像 tag 双份，配置回滚就是 Git revert + 重新下发。判据仍是"数据说话"：R0/R1 的观察窗里拿基线（076）对比，超出容忍即回滚并冻结该版本。没有回滚方案的升级不算升级，叫赌博。此外，配置更新与镜像更新要分开走：调一个阈值不必动镜像（秒级下发、秒级回滚），动接口或依赖才走完整镜像流程（重、但少），频率错配是变更管理混乱的常见源头。

实现思路与设计

治理体系落地的四件套：

  1. 制品库 + 内容标识：镜像/包/配置文件全部内容寻址（以内容标识为名）；部署清单记录"机器人 → 制品内容标识"。
  2. 配置流水线：Git 提交 → schema 校验 → 分层合并 → 生成每机器人配置包 + 内容标识 → 下发（带签名）。
  3. 启动握手：节点启动时校验接口版本与配置完整性；不通过即拒绝进入工作状态（快速失败优于带病运行）。
  4. 清单与漂移检测：心跳携带三个版本值；聚合端比对基线，漂移生成事件并联动 080 章告警。

版本身份三件套在心跳中的字段设计

字段示例用途
pkg_versionfleet_core 2.4.1软件溯源；回滚目标定位
config_hashcfg:a1b2c3配置漂移检测；"同组不一致"告警
iface_versioniface:4（兼容窗口 [2,4]）混合版本期间的安全边界
设计决策：为什么接口版本要"快速失败"？"尽力兼容"的代价是什么？

"尽力兼容"（遇到不认识的字段就忽略、缺字段就补默认）在 UI 场景是美德，在机器人控制里是灾难：忽略的字段可能是"安全限速"，补的默认可能是"最大速度"。控制系统的哲学是"不确定即拒绝"：握手不通过时节点停在安全状态并持续告警，让人来决定；让消息悄悄降级会埋下更隐蔽的故障。这也符合第 073/074 章的总体安全观，宁可停，不可猜。

关键代码与解读

片段 1：配置分层合并 + schema 校验

import hashlib, yaml

SCHEMA = {                          # 白名单式 schema：只允许已知键
    "max_speed": (float, 0.0, 2.0),
    "patrol_period_s": (float, 30.0, 600.0),
    "map_version": (str, None, None),
}

def load_layered(robot_id, base_p, site_p, robot_p):
    """三层合并：base -> site -> robot，后层覆盖前层；输出配置与内容标识。"""
    cfg = {}
    for path in (base_p, site_p, robot_p):
        with open(path, encoding="utf-8") as f:
            cfg.update(yaml.safe_load(f) or {})     # 浅合并够用：键不嵌套过深
    for key, (typ, lo, hi) in SCHEMA.items():
        if key in cfg:
            v = cfg[key]
            ok = isinstance(v, typ) and (lo is None or lo <= v <= hi)
            if not ok:                               # 校验失败即拒绝：不带病上线
                raise ValueError(f"配置非法：{robot_id} {key}={v!r}")
    blob = yaml.safe_dump(cfg, sort_keys=True).encode()
    cfg["_hash"] = "cfg:" + hashlib.sha256(blob).hexdigest()[:8]
    return cfg

解读：20 行的合并器守住了配置治理的入口。三个要点：（1）白名单 schema，未知键直接忽略还是报错？这里选择"只校验已知键、未知键允许但归档"，实践中更推荐把未知键也警告出来（配置写错键名等于没配置，静默忽略是经典事故）；（2）内容标识只算"纯配置"（排序后序列化），保证"相同语义的配置得到相同标识"，顺序不同、注释不同不该造成漂移告警；（3）校验失败即时抛错：部署流水线里配置包生成失败会直接拦住发布，这比"机器人启动后才发现在载重超速"便宜三个数量级。_hash 字段最终随心跳上报，把"配置版本"变成组织可观测性的一部分。

片段 2：启动接口版本握手

COMPAT_WINDOW = (2, 4)      # 本节点可互操作的接口版本区间（显式声明）

class CompatCheck(Node):
    """启动握手：与车队确认接口版本；不兼容则拒绝进入工作状态。"""
    def __init__(self):
        super().__init__("compat_check")
        self.iface_version = 4                  # 本节点实现的接口版本
        self.cli = self.create_client(Handshake, "/fleet/handshake")

    def verify_or_die(self, timeout=8.0):
        if not self.cli.wait_for_service(timeout_sec=timeout):
            self.get_logger().error("握手服务不可达：车队未就绪，保持安全态")
            return False                         # 停车等待，不猜
        req = Handshake.Request()
        req.iface_version = self.iface_version
        req.pkg_version = self.pkg_version()     # 软件版本也一并上报（清单用）
        fut = self.cli.call_async(req)
        rclpy.spin_until_future_complete(self, fut, timeout_sec=timeout)
        ok = fut.result() and fut.result().accepted
        if not ok:
            self.get_logger().error(
                f"接口版本 {self.iface_version} 超出车队兼容窗口 {COMPAT_WINDOW}，"
                "拒绝启动（快速失败优于带病运行）")
        return ok

解读：握手的价值在于把"混合版本的灾难"提前到启动的 8 秒内暴露。三个设计点：（1）兼容窗口是显式数据，服务端知道全队当前支持的区间（滚动升级期动态放宽），客户端只上报自己；（2）失败动作是"停在安全态"：退出进程会被监督器（080 章 systemd）当成崩溃反复拉起，停在安全态并告警才是可控行为；（3）软件版本搭车上报，让清单顺手更新，不用另设注册流程。注意 spin_until_future_complete 在启动阶段可用，但绝不能在业务回调里用（071 章的死锁教训），启动期是唯一允许同步等待的窗口，且必须带超时。

片段 3：分批滚动升级脚本（示意）

RINGS = [("canary", ["robot1"]), ("small", ["robot2", "robot3"]),
         ("full", ["robot4", "robot5", "robot6"])]

def rolling_upgrade(artifact_hash, health_gate, per_ring_wait_s=1800):
    """一次构建、多次部署：按环推进，健康门通过才继续；否则整体回滚。"""
    deployed = []
    try:
        for ring, robots in RINGS:
            print(f"== 部署环 {ring}：{robots}")
            push_artifact(artifact_hash, robots)      # 只复制既定制品，不重构建
            restart_services(robots)                  # systemd 重启；A/B 分区原子切换
            for r in robots:
                if not health_gate(r, timeout=per_ring_wait_s):
                    raise RuntimeError(f"{r} 健康门未通过")
            deployed += robots
            print(f"环 {ring} 通过，观察期后继续")
    except Exception as e:
        print(f"升级失败：{e}，开始回滚已部署批次")
        rollback(deployed)                            # 回滚到上一稳定制品标识
        raise
    freeze_manifest(artifact_hash, deployed)          # 清单固化：谁在跑什么，永久记录

解读：真正的运维脚本，精彩处不在"推"，而在"停"和"退"。health_gate 是每台机器人在观察窗内的验收函数（心跳、SLO 指标、任务成功率，全部有基线可对比）；任何一台不过门，异常直接抛出，rollback 把所有已升级机器人退回上一稳定版，宁可整体回退，也不留半队新半队旧的僵局。脚本最后把"制品标识 → 机器人清单"固化进清单库：一周后有人问"上周三 robot3 跑的是什么"，答案是查得到的。生产级实现还要加上：升级窗口避开任务高峰、电池电量门槛（升级中断电是很现实的场景）、每台升级后的启动握手校验（片段 2 的服务端视角），以及把每一步写进审计日志（080 章）。

常见坑

  • 现场手改配置：有人为了"临时提高速度"在机器人上 vim 了一把，两周后无人记得。修复：配置全量 Git 化 + 心跳带配置内容标识 + 漂移事件自动上报；现场修改列为流程违纪。
  • 接口改动不升版本：消息结构加字段、改单位都不通知，混合版本期间静默出错。修复：接口只增不改；语义变更升 iface 版本并握手拒连；CI 校验接口文件 diff。
  • 每台机器人各自构建：编译环境不同导致行为差异，问题永远无法复现。修复：CI 一次构建、内容寻址制品、部署只做复制。
  • 升级无回滚点：新版本出问题只能连夜修补。修复：A/B 分区或镜像双 tag；发布流程把"回滚演练"列为上线前置项。
  • 敏感信息入库：WiFi 密码、证书私钥混进 YAML 提交到 Git。修复：密钥/口令走外部引用；仓库加 secret 扫描钩子（此类事故一旦发生必须轮换全部泄露凭据）。

练习与思考

  1. 判断以下接口改动的兼容性并说明理由：(a) 给消息加字段（带默认）；(b) 字段单位从 mm 改 m 但类型不变；(c) 话题改名 robot1/cmd_vel → robot1/velocity；(d) 新增一个可选服务。★
    提示
    (a) 兼容；(b) 破坏且最阴险，类型相同、数值差 1000 倍，必须升 iface 版本并握手；(c) 破坏，话题名是合同；(d) 兼容。
  2. 为你的项目写配置分层方案：列出 base/site/robot 三层各放什么，至少 8 个键的归属与一个 schema 范围约束，并说明哪些内容绝不能进仓库。★★
    提示
    base：话题名、QoS、任务模板骨架；site：地图路径、限速区、AP 参数；robot：标定、轮径、个体增益。禁入：密码、私钥、证书，只放引用。
  3. 模拟混合版本事故：iface 3 的机器人订阅 iface 4 的调度器话题，字段 order 的语义从"编号"变成"优先级"。描述错误会在何时、以什么方式暴露，并给出握手方案如何把它变成启动即失败。★★
    提示
    暴露方式：序列化可能成功，语义错位表现为"任务执行顺序诡异"，运行数小时后才被发现，最贵的故障形态。握手方案：调度器上报 iface 4，机器人区间 [2,4] 内但不含 4 的互操作声明 → 拒绝连接并告警，人工决定升级节奏。
  4. 设计一次完整的版本发布演练：从 CI 构建到 R2 全量、含一次 R1 阶段的人为回滚。写出每个环节的检查项、观察窗指标（用 076 基线）、回滚触发条件与回滚后验证清单。★★★
    提示
    要点：构建内容标识入库→金丝雀 24 h→小批 48 h（对比 P95/任务成功率/SLO）→人为制造 R1 失败 → 触发整体回滚 → 验证"版本三件套"回退到位、无残留半新进程、清单已冻结回滚记录。演练本身的价值在于把回滚路径跑熟。

小结

  • 三个版本维度分开管理、统一审计：软件版本、配置内容标识、接口版本全部进心跳与清单。
  • 接口只增不改：新增带默认字段兼容，改名/改类型/改单位都是破坏性的；语义变更升版本并用启动握手快速失败。
  • 配置三层合并 + schema 校验 + 内容标识漂移检测；配置进 Git，现场禁改，密钥不入库。
  • 一次构建多次部署：不可变制品、金丝雀→小批→全量、健康门与回滚点齐备；没有回滚的升级是赌博。
  • 第四篇到此收束，工程化底座（分配、调度、保障、安全、容错、运维、版本）全部就位。下一章开启第五篇的科研进阶：多机器人协同学习入门。
