第四篇 · 系统集成与工程化

第 080 章：多机器人系统运维工具链

上线只是开始：把 20 台机器人当作一套长期运行的基础设施来管，用可观测性四件套（指标、日志、事件、状态清单）搭出车队健康视图，用"带持续时间的告警规则"盯住 SLO，用自动重启与远程运维守住 MTTR。

  • 主题：系统集成 / 运维与可观测性
  • 关键机制：SLO 与错误预算、指标聚合、日志与事件、告警规则引擎、进程监督
  • 预计学时：60 分钟
  • 前置章节：第 079 章

学习目标

  • 会用 SLO 语言定义车队健康目标（可用率、任务成功率、告警响应时延），理解错误预算的作用。
  • 掌握 ROS2 可观测性四件套：指标、日志、事件流、状态清单，各自的数据来源与采样策略。
  • 会设计告警规则：阈值 + 持续时间 + 分级 + 去重 + 运行手册链接，避免告警疲劳。
  • 能搭出最小可用运维工具链：健康聚合节点、指标导出、日志收集、进程监督与远程诊断。
  • 理解远程运维的安全边界：认证通道、命令审计、与 SROS2 的配合。

背景与动机

第 074 章的故障恢复解决"坏了自动救"，但运维要回答的是更长期的问题：车队过去一周健康吗？哪台机器人在慢性劣化？凌晨三点报警响了，值班的人能不能在五分钟内定位？版本升级后为什么这台机器人的启动慢了 8 秒？没有工具链，这些问题的答案只有"要去现场看看"。

运维工具链的价值是把"人的经验"变成"系统的例行公事"：指标告诉你趋势，日志告诉细节，事件流给出时间线，状态清单回答"现在到底有哪些东西在跑"。它是第 071–075 章所有机制（账本、事件、对账、故障）在时间维度上的汇总出口，也是 081 章版本管理与配置治理的观测基础。能观测的系统才敢改，能自动恢复的系统才养得起。

核心原理

1. SLO：把"健康"写成可计算的目标

SLI（指标）SLO（目标）数据来源
机器人可用率（心跳可见时间占比）≥ 99%（月度）/fleet/heartbeat 聚合
任务成功率≥ 95%（周度）task_event 统计
关键告警承认时延≤ 5 min（P90）告警系统自身日志
控制链路时延 P95≤ 30 ms（至 90% 运行时段）探针/监控节点（076 章）
故障恢复时间 MTTR≤ 15 min（P75）fault_event 与恢复日志配对

SLO 是运维的"验收线"：它让"系统最近怎么样"变成一个可以在晨会上回答的数字。配套概念是错误预算：99% 可用率意味着每月允许 7.2 小时的不可用，预算没用完可以适度激进（多实验、快迭代），预算烧得快就要冻结变更先修稳定性。没有错误预算，团队会在"天天报警但没人管"和"为了稳定什么都不敢动"两个极端间摇摆。

2. 可观测性四件套（机器人版三支柱 + 一）

通用软件可观测性是三支柱（指标、日志、链路追踪）；多机器人系统要加"状态清单（inventory）"这第四件，因为机器人的"存在"本身（哪台在场、跑哪个版本、在哪片区域）是物理事实，必须单列。

  • 指标（metrics）：可聚合的数值时间序列，每话题频率与到达间隔、端到端时延分位数、CPU/内存/网络、电量、任务队列长度。采样 1 Hz 起步；指标不是日志，别把自由文本塞进指标系统。
  • 日志（logs）：结构化文本事件（第 018 章的日志聚合），带节点名、严重级、时间戳；集中收集，本地滚动，禁止把图像/点云写日志。
  • 事件流（events）：语义化的状态变迁，任务生命周期（task_event）、故障与恢复（fault_event）、降级切换（degrade_level）、重构（reconfiguration）。事件流是复盘时间线的骨架，比日志高一层。
  • 状态清单（inventory）：当前在场的机器人与其运行版本、配置内容标识、角色分配、地图版本。清单由"注册+心跳"维护，任何时刻要能回答"谁在跑、跑的是什么"。
MTTR = 检测时间 + 定位时间 + 修复时间；告警系统只压缩前两项，自动恢复压缩第三项 例：检测 10 s（074 章心跳）+ 定位 5 min（工具链）+ 修复 2 min = MTTR ≈ 7.2 min；换人工跑现场修复则再加 30 min

3. 告警规则：阈值只是起点

一条能用的告警规则至少有五个字段：指标、比较、阈值、持续时间（for）、级别与处置链接。缺"持续时间"是新手最常犯的错，"CPU > 90%"瞬时颤动毫无意义，"CPU > 90% 持续 5 分钟"才是问题。规则示例：

规则条件级别处置
机器人失联心跳缺失 > 10 sP1Runbook：分区分诊 → 074 章恢复流程
控制时延劣化P95 > 30 ms 持续 60 sP2检查 072 降级档位与链路负载
任务积压队列长度 > 20 持续 5 minP2查看分配器日志与机器人忙闲
电量爬坡异常充电桩占用 > 90 minP3检查充电流程与桩状态
启动风暴同一节点 10 min 内重启 ≥ 3 次P1锁定重启，收集核心转储

告警治理两条纪律：去重与聚合（同一根源的告警合并成一条"事件"，20 台机器人失联不要发 20 条，应合并为一条"车队级：5 台失联"）；每条告警绑定 Runbook，没有处置指引的告警是在把焦虑转给值班员。定期审计"误报率"：误报 > 30% 的规则要么调参要么删除，否则值班员会学会忽略一切。

4. 进程监督与远程运维

运维的自动化底线是进程监督：关键节点进程崩溃后自动拉起，进程假死（心跳停但进程在）被看门狗击杀重启。Linux 上用 systemd 最省事：Restart=on-failure + WatchdogSec（应用定时喂狗，超时杀进程）；应用层再配合 074 章的"重启风暴保护"，防止重启—崩溃循环。

远程运维（Remote Operations）要守住三条线：通道（经 VPN/跳板机；DDS 的发现是广播式的，把 DDS 直接暴露到公网即招攻击）；审计（所有远程命令记录"谁、何时、对谁、做了什么、结果"）；最小权限（值班员能重启节点与拉日志，配置变更与升级走 081 章的受控流程）。配合第 073 章：远程通道自身用证书认证，与车队内部的 SROS2 信任链复用同一套 CA 管理体系最省心。

健康聚合节点挂了、告警引擎挂了、日志上传断了，这些故障最危险，因为它们让所有其他故障"隐形"。给每个运维组件配一个最原始的存活信号（如 systemd 心跳 + 一个"健康节点每分钟发一条车队级存活消息"的哑通道），并让"健康聚合 > 60 s 未更新"本身成为一条 P1 告警。监控自己不被监控，等于没有监控。

关键代码与解读

片段 1：车队健康聚合节点

class FleetHealth(Node):
    """把分散信号聚成一部车队的健康分与结构化指标。"""
    def __init__(self):
        super().__init__("fleet_health")
        self.hb = {}              # rid -> 最近心跳时刻
        self.lat = {}             # rid -> 时延样本队列（来自监控探针汇总）
        self.create_subscription(Heartbeat, "/fleet/heartbeat", self.on_hb, 10)
        self.create_subscription(LatencyStat, "/fleet/latency_stat", self.on_lat, 10)
        self.metrics_pub = self.create_publisher(FleetMetrics,
                                                 "/fleet/metrics", 10)
        self.health_pub = self.create_publisher(FleetHealth, "/fleet/health", 10)
        self.create_timer(2.0, self.publish_health)       # 0.5 Hz：给人看的节奏

    def on_hb(self, msg):
        self.hb[msg.robot_id] = self.now_s()

    def publish_health(self):
        now = self.now_s()
        alive = sum(1 for t in self.hb.values() if now - t < 10.0)
        m = FleetMetrics()                                # 结构化指标：可被桥接导出
        m.robots_alive = alive
        m.robots_total = len(self.hb)
        m.latency_p95_ms = self.p95_of_all(self.lat)
        # 健康分：简单加权（可用率 60% + 时延达标 40%），口径写死可复算
        avail = alive / max(1, len(self.hb))
        lat_ok = 1.0 if m.latency_p95_ms < 30.0 else 0.0
        h = FleetHealth()
        h.score = round(60.0 * avail + 40.0 * lat_ok, 1)
        h.updated_at = now
        self.metrics_pub.publish(m)                       # 机器读
        self.health_pub.publish(h)                        # 人读（大屏/仪表盘）

解读：健康聚合的价值是"有唯一口径"。两个设计点：（1）健康分公式写死在代码里并公开（可用率 60% 权重 + 时延 40%），任何人拿到原始指标都能复算，分数可解释比分数精确更重要，没人相信的黑盒分数等于没有分数；（2）发布两条流：/fleet/metrics 面向机器（字段化、可桥接导出到时序库），/fleet/health 面向人（一个带时间戳的分数）。publish_health 用 0.5 Hz 的独立节拍，不在每条心跳上计算：聚合是给人做决策的，过高频率只会制造无意义的抖动曲线。注意存活判定用了 10 s 窗口（与 074 章的 t2 对齐），运维视图与故障检测视图必须用同一套时间常数，否则大屏显示"19 台在线"而告警说 5 台失联，值班员会先怀疑系统，耽搁真正的修复动作。

片段 2：告警规则引擎，阈值 + 持续时间 + 去重

RULES = [
    {"name": "robot_lost",     "expr": lambda m: m.loss_seconds,
     "gt": 10.0,  "for_s": 0,    "level": "P1", "runbook": "rb/robot_lost.md"},
    {"name": "latency_bad",    "expr": lambda m: m.latency_p95_ms,
     "gt": 30.0,  "for_s": 60,   "level": "P2", "runbook": "rb/latency.md"},
    {"name": "queue_backlog",  "expr": lambda m: m.queue_len,
     "gt": 20.0,  "for_s": 300,  "level": "P2", "runbook": "rb/backlog.md"},
]

class AlertEngine(Node):
    """规则评估：越线计时（for_s）、恢复清除、同规则去重冷却。"""
    def __init__(self):
        super().__init__("alert_engine")
        self.since = {}            # rule_name -> 首次越线时刻
        self.firing = set()        # 正在报警的规则
        self.cooldown_until = {}   # 规则级冷却：防抖动风暴
        self.create_subscription(FleetMetrics, "/fleet/metrics", self.eval, 10)
        self.alert_pub = self.create_publisher(Alert, "/fleet/alert", 10)

    def eval(self, m):
        now = self.now_s()
        for r in RULES:
            val = r["expr"](m)
            over = val > r["gt"]
            if over and self.since.get(r["name"]) is None:
                self.since[r["name"]] = now          # 起计时：for_s 从这里算
            if not over:
                self.since.pop(r["name"], None)      # 恢复：计时清零
                self.firing.discard(r["name"])
                continue
            if (now - self.since[r["name"]] >= r["for_s"]
                    and r["name"] not in self.firing
                    and now >= self.cooldown_until.get(r["name"], 0)):
                self.fire(r, val)                    # 触发
                self.firing.add(r["name"])
                self.cooldown_until[r["name"]] = now + 600.0   # 10 min 冷却

    def fire(self, rule, val):
        a = Alert()
        a.name = rule["name"]
        a.level = rule["level"]
        a.message = f"{rule['name']} 越线：{val:.1f} > {rule['gt']}"
        a.runbook = rule["runbook"]                  # 告警必须带处置指引
        self.alert_pub.publish(a)

解读：规则引擎把"什么时候烦人"设计成状态机。for_s 计时：越线即起计时，未满 for_s 不报、恢复即清零，这让 1 秒的尖峰永远不会打扰人；firing 集合保证一条规则在一个持续事件里只报一次（否则 10 s 评估周期会每轮发一条）；冷却窗在恢复后 10 分钟内不再报，给修复留时间，也防"越线—恢复—越线"的抖动刷屏。规则与处置文章（runbook）一一绑定：收到的每条告警都能一键跳到"怎么办"，这是告警系统从"噪音源"变成"生产力工具"的分水岭。RULES 用数据结构组织（散落的 if 无法统一测试）：新增规则不改引擎代码，还能被单元测试逐一验证触发逻辑（构造边界指标断言是否在恰当时刻触发）。

片段 3：进程监督，systemd 单元示例

# /etc/systemd/system/robot-core.service
[Unit]
Description=Robot core stack (bringup + control + app)
After=network-online.target
Wants=network-online.target

[Service]
Type=notify
# 应用需通过 sd_notify 定期喂狗；超时未喂 → systemd 视为假死并重启
WatchdogSec=15
Restart=on-failure
RestartSec=5
# 重启风暴保护：5 分钟内最多 3 次，再多则进入 failed 状态等人介入
StartLimitIntervalSec=300
StartLimitBurst=3
Environment=ROS_DOMAIN_ID=42
ExecStart=/opt/fleet/run_robot.sh
# 核心转储：崩溃后别丢现场（复盘第一素材）
LimitCORE=infinity

[Install]
WantedBy=multi-user.target

解读：这份单元文件把 074 章的"自愈"接到了操作系统层。WatchdogSec=15 处理"假死"，进程活着但心跳不发，systemd 直接击杀重启（前提是应用里的 watchdog 喂狗线程绑在业务主循环上，独立线程喂狗等于没喂，参见 074 章）；StartLimitBurst=3 是重启风暴的硬闸，崩溃循环时停在 failed 状态并触发人工告警，避免无限重启把 SD 卡写坏；LimitCORE 保留核心转储供事后分析。部署侧的配合：这套单元随镜像固化，升级走 081 章的受控流程（现场 vim 编辑属于流程违纪）；run_robot.sh 负责选择 sim/real 配置并启动 ROS2 launch，systemd 只管进程生命周期，不管 ROS2 内部结构，职责边界清晰。

常见坑

  • 告警风暴：一次路由器故障让 20 台机器人同时失联，发出 20 条 P1，值班群炸锅。修复：告警聚合（按根因合并为"车队级事件"）+ 分级 + 冷却；阈值型告警配 for_duration。
  • 监控盲区：运维组件自己挂了没人知道（心跳停了一切照旧，直到出事才发现数据断了三天）。修复：运维组件互监 + "健康数据超过 60 s 未更新"作为独立 P1。
  • 日志无时间基准：各机器人时钟不同步，事故时间线拼不起来。修复：时间同步是运维前置项（第 009 章），日志带同步后时间戳与节点名。
  • 远程入口裸奔：为看图方便把 DDS 端口映射到公网，任何人可订阅与发布。修复：远程一律经 VPN/跳板 + 证书认证；命令审计；与 SROS2 体系复用同一 CA。
  • 告警没有 Runbook：收到告警的值班员不知道下一步做什么，每次都要找原作者。修复：每条规则绑定处置文档链接；上线新规则前先写 Runbook，写不出来说明规则本身没想清楚。

练习与思考

  1. 为你的车队定义 4 条 SLO（含指标口径、目标值、统计周期），并解释如果月度错误预算用掉 70% 时你会暂停哪类变更。★
    提示
    参考示例表；错误预算烧到 70% 时典型动作：冻结"非修复类"的版本升级与参数实验，把资源转向稳定性修复，直到预算回落到 50% 以下再放开。
  2. 给"控制时延劣化"设计完整告警规则四件套：指标口径、阈值、for 时长、分级与 Runbook 提纲，并说明为什么 for 时长不能设 0。★★
    提示
    P95 > 30 ms 持续 60 s → P2；for=0 会被单次统计窗口噪声持续触发；Runbook 提纲：查降级档（072）→ 查链路丢包（077 探针）→ 查 AP/信道占用 → 必要时临时限流。
  3. 复盘一个事故时间线：03:12 某机器人开始丢心跳、03:14 恢复、03:40 又断、04:05 人工重启后正常。用"误报率与 MTTR"的视角评论：告警系统应该报几次？值班员应在哪一步介入？★★
    提示
    应报 2 次（两次中断各一次），第二次升级注意"30 分钟内重复故障"模式；03:40 时应把该机器人标记为"反复故障嫌疑"，MTTR 从第一次断到 04:05 = 53 min，其中检测 2 min、定位靠人工，这就是需要聚合历史与 Runbook 的典型场景。
  4. 设计远程运维的最小权限矩阵：列出"值班员/运维工程师/开发"三类角色分别可以做的 5 项操作（看状态、拉日志、重启节点、改参数、升级版本），并为每项写审计字段。★★★
    提示
    价值取向：值班员只读 + 重启；运维工程师可改参数（走受控配置流程）；开发可升级版本（走 081 章发布流程）。审计字段：who/when/target/action/params_hash/result/ticket_id，缺 ticket 的高危操作直接拒绝。

小结

  • 用 SLO/错误预算管理运维：可用率、任务成功率、告警承认时延、MTTR，都有口径与周期，预算烧得快就冻结变更。
  • 可观测性四件套：指标（机器读）、日志（细节）、事件流（时间线）、状态清单（谁在跑什么）；四者缺一不可。
  • 告警规则五要素：指标、阈值、持续时间、级别、Runbook；聚合去重与误报审计是防疲劳的关键。
  • 进程监督压实自动化底线：WatchdogSec 治假死、StartLimit 防风暴、核心转储保现场；监控系统自身必须被监控。
