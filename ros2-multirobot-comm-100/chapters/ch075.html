第四篇 · 系统集成与工程化

第 075 章：多机器人动态重构

机器人走了、任务换了、通道窄了，系统不能"推倒重来"，而要换一副骨架继续跑：用四层配置（角色/拓扑/控制/任务）描述当前形态，用两阶段提交与屏障同步完成原子切换，用迟滞与回滚压住重构本身的代价。

  • 主题：系统集成 / 变结构协同
  • 关键机制：配置四层模型、两阶段提交、屏障同步（barrier）、渐进重构与回滚
  • 预计学时：65 分钟
  • 前置章节：第 074 章

学习目标

  • 区分"故障恢复"与"动态重构"：前者修复一个元素，后者让整个系统迁移到一个新的正常态。
  • 掌握配置四层模型（角色、拓扑、控制、任务）与"过渡态必须安全"的设计原则。
  • 会用两阶段提交（提议→收集→提交）与屏障同步实现全体一致的原子切换，理解版本号/纪元的角色。
  • 会设计重构抑制：收益阈值、稳定窗、冷却期，避免系统在两种构型间来回跳。
  • 能实现一个带渐进执行与回滚的重构管理器，并为它定义验收指标。

背景与动机

上一章的恢复处理"单点坏了怎么办"；本章处理更宏观的一类变化：系统的"正常态"本身变了。四台机器人巡逻，一台电池告罄主动返航，不是故障，但巡逻段的划分、相遇点、盯着关键点的角色都要重新安排；任务从"搬运"切换到"安检"，编队形态、控制增益、通信拓扑全都要换一副面孔。

没有重构能力的系统只有两个选项：要么僵死在初始配置上（减员即失效），要么被人工重启（停机即事故）。动态重构的目标是让系统在运行中平稳地换骨架：切换过程本身安全、切换结果全队一致、切换失败能退回去。它是多机器人从"演示系统"走向"生产系统"的关键一步，也直接服务第 085 章"带故障恢复的任务系统"阶段项目。

核心原理

1. 配置是可序列化的四层数据结构

"当前形态"不能用散落各处的参数表达，而要收敛成一份可版本化、可下发、可比对的配置对象，分四层：

层内容示例变更影响面
角色层leader/follower、searcher/guard、负责区段决策与任务权限
拓扑层谁监听谁的状态、控制链路的邻接图通信负载分布、发现关系
控制层编队几何（间距、相位）、控制增益、速度上限运动行为
任务层任务归属与顺序（第 066–071 章的结果）任务完成度

把配置建模成数据结构（例如一个 JSON/YAML 对象，每台机器人持有它的副本）带来三个能力：版本化（配置号 v17 → v18，出问题能知道"哪一版引入的"）、差异最小化（切换时只重启变化的子系统，未变部分不动）、可预演（新配置先在影子模式里校验合法性，如"无重复槽位、无资源互斥冲突"再提交）。

2. 过渡态安全：重构不是瞬移，是搬家具

从构型 A 到构型 B，物理世界必须经过一个过渡态：编队从三角变纵队，机器人要先散开再成列，中间有几十秒"既不是 A 也不是 B"的状态。设计铁律：过渡态的每一刻都必须是安全的（满足最小间距、不占同一资源、随时可停）。三条衍生规则：

  • 不允许"无主"或"双主"窗口：角色交接瞬间必须定义谁说了算，典型做法是保留旧 leader 直到新 leader 的屏障确认，再降级旧 leader。
  • 过渡走安全走廊：编队变换的中间形态选择"有序让位路径"（例如先全部减速到 0.3 m/s，再按序拉开间距）；各自奔新位置是碰撞的温床。
  • 过渡可中断：任何时刻收到急停或新重构指令，系统能停在一个"合法但未完成"的状态，之后要么继续、要么回滚。所以过渡态要设计成可枚举的中间检查点，一段黑盒动画无法在中途安全中止。

3. 两阶段提交与屏障：让全队换到同一页

单机切换配置很简单，难的是"全队在同一时刻切换到同一版本"。借鉴分布式事务的两阶段提交（2PC）：

  1. 提议（propose）：重构管理器算出候选配置 v18（含新的角色/编队/任务表）与生效条件，广播 ReconfigProposal（配置全文或差异 + 校验和）。
  2. 准备（prepare/ack）：各机器人校验自己能否满足新配置（电量够不够、位姿是否支持新角色、资源是否可用），回 ack(ready / reject+reason)。
  3. 提交（commit）：全部 ready（或达到法定人数）后，管理器广播 ReconfigCommit(v18, epoch)；各机器人切换到 v18 并进入过渡态执行器，过渡完成回报 transition_done。
  4. 稳定（stabilize）：管理器在稳定窗内（如 30 s）观察指标，通过则宣布 v18 稳定；若期间出现异常或某机长时间未完成过渡 → 触发回滚。

版本号（version）与纪元号（epoch）分工不同：version 标识配置内容（v17 和 v18 的差异可 diff）；epoch 标识"哪一次变更具有权威"（防止旧版指令在回滚/二次重构时复活）。两者都放进每条控制消息里，接收端校验"版本兼容 + 纪元最新"才执行。

4. 重构抑制与渐进执行

重构是有成本的（过渡期效率降低、通信翻倍、风险窗口），所以"要不要重构"本身要用经济学判断：

重构收益 = 新构型的预测完成时间收益 + 安全收益 − 过渡成本（≈ 过渡时长 × 全队效率损失 + 风险溢价） 例如巡逻从 4 台减为 3 台，idleness 从 6.25 min 升到 8.33 min（仍在 10 min 约束线内，重构理由明确），过渡只需 20–40 s，值得；若只是某扇门临时关闭，绕行即可，别重构

抑制机制三件套：收益阈值（预测改进 < 15% 不动）、稳定窗（一次重构完成后 60 s 内不再发起新的）、冷却与滞环（触发条件与撤销条件用不同阈值，例如电量 20% 触发返航、充电到 60% 才允许回归）。渐进执行则把大重构拆成有序的小步：先加入新成员、观察一窗、再撤销旧角色，每一步都可独立验收与回滚。大爆炸式切换（全员同时换）只在低风险配置（如仅改速度参数）时使用。

5. 数值算例：一次减员重构的收益账

用 063 章的回路口径算一遍减员重构。回路总负载 25 min（行驶 24 min + 12 点驻留 1 min），等时切分下 idleness = 25/n min：4 台时 6.25 min，减为 3 台时 8.33 min。按 12 小时班次换算总访问次数：720/6.25 ≈ 115 次，对照 720/8.33 ≈ 86 次，减少 25%。同一条曲线继续往下算：3 台减到 2 台，idleness 12.5 min、访问次数降到 57.6 次，再减 33%；2 台减到 1 台直接腰斩到 28.8 次。这组数给出重构决策的量化模板：减员的代价随规模缩小而放大，而过渡成本（约 20–40 s 的一次性切换）相对班次级收益可以忽略。所以当电池告罄、维修离场这类事件发生时，及时重构几乎总是正收益；真正需要抑制的是"为了鸡毛蒜皮的效率改进"频繁重构，那才是收益阈值 15% 与稳定窗 60 s 要拦住的对象。

但减员不是免费的：若任务有"每点 10 min 必访"的硬约束，3 台配置的 8.33 min 已经贴着线，任何一次告警抢占都会让某些点短暂超标。重构规划器应该在提交前把这类约束当成 PREPARE 阶段的校验项（类似 074 章重入检查的"能不能满足"投票），算不过就拒绝本轮，并给出"需要替换成 4 台或放宽约束"的具体理由。这就是四层配置模型的价值：约束与配置分离，切换前可以用同一份配置数据做静态校核，把不可行方案拦在过渡态之外。

6. 数值算例：法定人数与 2PC 的失败模式账

先把法定人数具体化：3 台机器人时简单多数是 2，4 台时是 3；按"关键成员全体 + 总数 ≥ ⌈2n/3⌉"的加权规则，4 台配置要求关键集合（新领导、唯一覆盖某防区者、持资源者）全部 ready 且总 ready 数 ≥ 3。举例：4 台中 3 台已 ready，但唯一覆盖北门的那台 reject（电量不足），即使人数达标也要取消本轮；否则新构型"形式上成立、功能上残缺"，北门出现无人覆盖的空窗。把 2PC 的四类失败对齐到处置动作，重构管理器就完整了：PREPARE 期间成员掉线 → 超时按 reject 处理，本轮取消；部分成员没收到 COMMIT → 按纪元判断，重发 COMMIT，靠"epoch 更新"补齐；过渡超时或稳定窗指标恶化 30% → 回滚到上一稳定配置并升纪元；回滚本身再失败（成员大面积离线）→ 全员安全停车并锁定重构，转人工。每类失败都要求"有确定终态"，绝不允许系统停在"既不是 A 也不是 B 且没人知道"的中间态。

重构的可观测指标要在上线时就定好：过渡时长（P50/P95）、回滚发生率、稳定窗内的指标漂移、以及"预测收益与实测收益"的偏差。校准例子：预测 idleness 从 6.25 升到 8.33 min，实测 60 个通知点的平均空置 9.1 min，比预测高 9%；把这个系统性偏差折进预测器，多轮之后收益评估会越来越准。没有这组指标的团队只能凭感觉判断"这次切换值不值"，而数据本身不贵：全部从已有的状态上报与事件日志里算得出来，观测器模块顺手输出即可。

实现思路与设计

重构管理器的结构：一个状态机 + 三个接口。

  1. 触发器：汇总四类输入，成员变化（074 章的上线/离线事件）、任务变化（调度器事件）、环境变化（禁区/通道宽度）、性能退化（idleness/能耗监控）。所有输入先归一成"重构理由"对象再评估。
  2. 规划器：生成候选配置。角色/槽位分配复用 066 章的匹配思想，代价里加重"切换平稳项"（保持原角色的机器人代价为 0，换角色加固定切换罚金），让重构尽量少动人。
  3. 执行器：2PC 协议 + 屏障；维护"当前稳定配置"与"上一稳定配置"两个版本以备回滚。
  4. 观测器：过渡时长、失败率、回滚次数、重构收益实测值；这些数字是下一轮阈值调参的依据。

关键参数表

参数建议值依据
重构收益阈值15%过渡成本与预测误差的量级；低于此噪声占主导
稳定窗60 s过渡后指标（idleness/编队误差）需要时间回到稳态
ack 超时3 s与 066 章派发确认同量级；超时视为 reject
过渡超时90 s编队变换典型 20–40 s 的两倍余量
回滚触发过渡超时或稳定窗内指标恶化 30%回滚是安全网，宁可回到旧构型也不带病前进
冷却期120 s回滚后的系统需要时间清账，禁止连环重构
设计决策：为什么回滚目标固定为"上一稳定配置"？现场重算新配置的代价在哪里？

回滚的目标是确定性：回滚发生时系统往往已经在异常态（指标恶化、成员缺失），此时再运行规划器可能算出一个"看起来更好的第三配置"，但它的实际表现未经验证，是把一次故障叠加成两次。回滚必须回到"已知能跑"的状态（上一稳定版），然后再重新规划、重新走 2PC。这也解释了为什么"当前稳定配置"在运行时不能删，它是系统的锚。

关键代码与解读

片段 1：角色/槽位重分配，把"少动人"写进代价

SWITCH_PENALTY = 40.0     # 换角色的等效秒数：磨合成本 + 重定位成本

def assign_roles(robots, slots, travel, current_role_of):
    """给机器人分配角色槽位：代价 = 到位时间 + 换角色罚金，最大化保持原角色。"""
    C = np.zeros((len(robots), len(slots)))
    for i, r in enumerate(robots):
        for j, s in enumerate(slots):
            eta = travel(r.pose, s.pose) / r.speed
            # 关键：原本就是此角色的机器人不加罚金，重构倾向于“微调”
            penalty = 0.0 if current_role_of.get(r.id) == s.id else SWITCH_PENALTY
            C[i, j] = eta + penalty
    rows, cols = linear_sum_assignment(C)
    return [(robots[i].id, slots[j].id) for i, j in zip(rows, cols)]

def should_reconfigure(old_pred, new_pred, transition_cost, threshold=0.15):
    """重构收益评估：改进必须显著超过过渡成本，且越过收益阈值才动手。"""
    improvement = (old_pred.makespan - new_pred.makespan) / old_pred.makespan
    net = improvement * old_pred.makespan - transition_cost
    return improvement >= threshold and net > 0.0

解读：规划器复用 066 章的匹配算法，但代价项多了一维"切换平稳项"。没有它，算法会为了 3 秒的到位时间差把整队角色洗牌，每个换角色的人都付出磨合与重定位的隐性成本（40 秒量级）。加了罚金后，只有当新构型在"省下的时间"上明显胜出时，才会推倒现有分工。should_reconfigure 是重构的"财务门槛"：先算替换收益，再减过渡成本，最后还要越过 15% 阈值，三重闸门把"为 1 秒优化折腾全队"的可能性彻底掐掉。参数建议写进配置文件随车队规模调整：机器人越多，切换罚金应越大（一次洗牌的绝对成本更高）。

片段 2：两阶段提交，提议、收集、提交

class ReconfigManager(Node):
    """重构管理器：2PC 执行全队一致的配置切换，带屏障与回滚。"""
    def __init__(self):
        super().__init__("reconfig_manager")
        self.stable = load_config()            # 当前稳定配置（回滚锚点）
        self.epoch = 1
        self.phase = "IDLE"
        self.acks = {}                         # robot_id -> True/False/reason
        self.create_timer(0.5, self.tick)
        self.cmd_pub = self.create_publisher(ReconfigCommand, "/fleet/reconfig", 10)

    def propose(self, candidate):
        self.phase = "PREPARE"
        self.candidate = candidate
        self.acks.clear()
        cmd = ReconfigCommand()
        cmd.action = "PREPARE"                 # 携带全文 + 校验和：接收端先校验再回执
        cmd.config = candidate.serialize()
        cmd.epoch = self.epoch
        self.cmd_pub.publish(cmd)

    def on_ack(self, msg):
        if self.phase == "PREPARE":
            self.acks[msg.robot_id] = msg.ready   # False 时 msg.reason 一并记录

    def tick(self):
        if self.phase == "PREPARE" and self.all_acked_or_timeout():
            if self.majority_ready():
                self.epoch += 1                   # 提交前升纪元：新旧指令永不混淆
                cmd = ReconfigCommand()
                cmd.action = "COMMIT"
                cmd.config = self.candidate.serialize()
                cmd.epoch = self.epoch
                self.cmd_pub.publish(cmd)
                self.phase = "TRANSITION"
            else:
                self.get_logger().warn(f"准备失败：{self.reasons()}")
                self.phase = "IDLE"               # 未达条件：本轮重构取消
        elif self.phase == "TRANSITION" and self.transition_timeout():
            self.rollback()

    def rollback(self):
        self.epoch += 1
        cmd = ReconfigCommand()
        cmd.action = "COMMIT"
        cmd.config = self.stable.serialize()     # 回到“已知能跑”的上一稳定版
        cmd.epoch = self.epoch
        self.cmd_pub.publish(cmd)
        self.phase = "IDLE"

解读：2PC 的每一步都对应一个失败模式。PREPARE 阶段收集"能不能做"，机器人按自己的实况（电量、位姿、资源占用）投票，任何一个 reject 都附带理由，管理器据此决定取消还是换方案；COMMIT 前升 epoch，保证从这一刻起旧纪元的任何指令（包括回滚前的残留消息）都不再有效；TRANSITION 阶段超时即回滚，回滚目标固定为 self.stable（不是重新规划）。细节：majority_ready() 允许在非关键成员失联时仍推进重构（法定人数思想，074 章同源）；stable 只在稳定窗结束后才被替换为新配置，把"宣布稳定"做成显式动作，"提交了就算成功"是很多实现省略的一步。生产实现里还要给 COMMIT 消息加重发（接收端可能没收到），并用 ack 编号去重。

片段 3：机器人侧的渐进过渡执行器

class TransitionExecutor(Node):
    """接收 COMMIT 后在本地执行带检查点的过渡，任何异常都可安全中止。"""
    CHECKPOINTS = ("slow_down", "clear_zone", "take_slot", "formation_lock")

    def on_commit(self, msg):
        if msg.epoch <= self.epoch:            # 旧纪元（乱序/重放）：直接忽略
            return
        self.epoch = msg.epoch
        self.target = parse_config(msg.config)
        self.step = 0
        self.active = True                     # 进入过渡态：以安全速度执行

    def tick(self):
        if not self.active:
            return
        phase = self.CHECKPOINTS[self.step]
        done = {
            "slow_down": self.set_speed(0.3),           # 先降速：所有让位动作的前提
            "clear_zone": self.leave_shared_resources(),# 释放窄道/工位（069 章租约）
            "take_slot": self.goto_new_slot(),          # 按“有序让位”路径到位
            "formation_lock": self.check_formation(),
        }[phase]()
        if done:
            self.step += 1
            self.report("transition_checkpoint", self.step)
            if self.step >= len(self.CHECKPOINTS):
                self.active = False                     # 过渡完成
                self.report("transition_done", None)

    def abort(self, reason):
        # 中止时停在当前检查点：位置本就合法（每个检查点后都安全）
        self.active = False
        self.hold_position()
        self.report("transition_aborted", reason)

解读：过渡执行器的精髓是把"换队形"拆成四个有序检查点，一条从旧位置到新位置的直线路径是中途无法安全中止的黑盒。四个检查点的顺序是安全逻辑的体现：先 slow_down（速度是所有让位动作的前提）、再 clear_zone（释放共享资源，避免带资源换位引发 069 章的死锁）、然后 take_slot（按有序让位路径进场）、最后 formation_lock（全队校验新编队误差达标）。每个检查点完成后立即上报，管理器的过渡超时判据以"最慢检查点"为界，全队统一一个时间点会掩盖卡住的位置。回滚/中止时 hold_position 保证系统停在合法状态：因为每个检查点后都是安全态，中止永远不需要"倒带"。这就是"过渡态可枚举"的实际收益。

常见坑

  • 构型震荡：指标在阈值附近时系统在两种构型间反复切换，每次切换期间效率更差。修复：进入/退出用不同阈值（滞环）+ 稳定窗 + 冷却期；重构收益阈值 15%。
  • 部分成员切换到新配置、部分滞留旧配置：没有 2PC 与屏障，消息丢失就让全队裂成两半。修复：PREPARE/COMMIT 两阶段 + ack 重发 + 纪元校验；滞留者按 OBSERVE_ONLY 降级等重入。
  • 过渡路径撞上资源冲突：编队变换经过窄道时两台机器人同时申请通行权，重构卡死。修复：过渡检查点包含"释放共享资源"步骤；变换路径预先做资源冲突检查（与 069 章的预约系统联动）。
  • 不留回滚点：新配置一提交就把旧配置覆盖，出问题只能"向前修"。修复：稳定窗结束前保留上一稳定版；回滚是广播旧版 + 升纪元，不重算。
  • 重构期间不冻结任务：编制变了但调度器还在按旧表派任务，机器人收到两套指令。修复：重构期调度器暂停派发（冻结窗），过渡完成后按新配置一次性重派。

小结

  • 重构 = 系统迁移到新正常态；配置要作为四层可版本化对象管理，规划代价里包含"少动人"的切换罚金。
  • 过渡态每一刻都必须安全：有序让位路径、检查点化、可中断；无主/双主窗口一律禁止。
  • 2PC + 屏障保证全队一致切换：PREPARE 收集能力，COMMIT 升纪元执行，稳定窗后才宣布成功；失败回滚到上一稳定配置。
  • 重构抑制三件套：15% 收益阈值、60 s 稳定窗、冷却与滞环；渐进执行优于大爆炸。
