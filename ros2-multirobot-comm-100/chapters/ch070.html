第四篇 · 系统集成与工程化

第 070 章：多机器人协同调度

分配回答"谁做"，调度回答"何时做、按什么顺序做、谁和谁可以并行"：用任务图刻画先后约束，用关键路径定下总工期下界，再用表调度把任务压到各机器人的时间轴上。

  • 主题：系统集成 / 时间与顺序调度
  • 关键机制：任务图（DAG）、关键路径、表调度启发式、makespan 下界
  • 预计学时：65 分钟
  • 前置章节：第 069 章

学习目标

  • 区分分配（assignment）与调度（scheduling）的问题层次，会为一批任务写出带前后约束的任务图。
  • 掌握关键路径法（CPM）：用拓扑排序 + 动态规划求总工期下界，并识别哪些任务"一分钟都不能拖"。
  • 会用表调度（list scheduling）启发式把任务排到多机器人时间轴，理解"关键路径优先"的构造逻辑。
  • 会计算 makespan 下界（关键路径长 vs 总工作量/台数）并评估自己调度结果与下界的差距。
  • 能为调度器设计"重排策略"：何时重排、如何保证调度稳定性。

背景与动机

066 章把任务分给了机器人，但每个机器人手里的任务还是"一袋散装的活"。真实任务之间常有先后关系：先扫码核对再搬箱、先建图再巡逻、先取货再送货；同一台机器人执行带依赖的任务时，顺序错了就根本做不了，而不只是慢一点。同时，车队是一条流水线：A 的交付物可能是 B 的输入，谁先动手直接决定整批活什么时候干完。

调度层要回答三个问题：顺序（哪些任务必须先后串行）、时间（每个任务什么时候开始）、并行（哪些任务可以同时压在多台机器人上）。它上接 066–069 的分配与资源约束，下启 071 章的 ROS2 工程实现；任务图与关键路径这两件工具，也是第 096 章科研级"调度机制与优化建模"的工程起点。

核心原理

1. 从分配到调度：多出来的两个维度

维度066 分配问题070 调度问题
决策变量xij：谁做哪个每个任务的开始时间 sj 与执行机
约束一对一匹配先后顺序（先 A 后 B）、资源容量、机器人可用时间段
目标总代价最小总工期最短（makespan）、或交付延迟最小
复杂度多项式（O(n³)）含顺序约束的调度是 NP-hard

复杂度跳变的原因：分配问题里任务相互独立，调度问题里任务通过先后关系织成一张网，可行排法的数量随任务数阶乘级增长。好消息是工程上不需要最优解，只需要"接近下界且稳定可解释"的解，表调度加关键路径优先的经典组合就够了。

2. 任务图与关键路径

把任务画成有向无环图（Directed Acyclic Graph, DAG）：顶点是任务（带时长 dj），边 j → k 表示"k 必须在 j 完成后开始"（数据依赖或物理依赖）。对每个任务定义最早开始时间：

EST(k) = maxj→k [EST(j) + dj]，EST(无前驱) = 0；makespan 下界 = maxk [EST(k) + dk] 沿拓扑序一遍动态规划即可；最长的那条"任务链"就是关键路径，链上任何一秒延误都会等量推后总工期

关键路径给两个工程信号：（1）总工期不可能小于关键路径长；（2）资源要向关键路径倾斜，给非关键路径上的任务加机器人，makespan 纹丝不动，这是调度评审时最常见的误区。另一个下界来自工作量守恒：总工期不可能小于"总工作量 / 机器人数"，两个下界取更紧的那个（更大者）才是有效下界。

这里有个多机器人特有的坑：任务之间的"边"不只是数据依赖，还有行驶时间。机器人做完任务 A 再去做 B，中间必须加上 A→B 的空驶时间，它是与顺序相关的准备时间（sequence-dependent setup time）。把它漏掉，调度表会乐观得离谱：一个 20 任务的调度表可能低估 30% 的工期。

3. 表调度：一行行把任务"压"上时间轴

表调度的流程像模拟执行：把所有任务按优先级排成一个待派表；反复取出当前"就绪"（前驱全部完成）且优先级最高的任务，分配给能最早开工的机器人（开工时刻 = max(机器人空闲时刻 + 行驶时间, 前驱完成时刻)），更新该机器人的空闲时刻。优先级怎么定，决定调度质量：

  • CP 优先（关键路径优先）：优先级 = 从该任务出发到终止的最长剩余路径（"尾长"）。尾长越长越先排，留给它的时间余量最少。这是 LPT 思想在带依赖场景下的推广，也是工程默认。
  • LPT（最长处理时间优先）：无依赖、纯并行机场景下，先排长任务能把 makespan 压到不超过最优的 4/3 倍，经典结论，直觉是"大石头先装桶，碎石填缝"。
  • EDF/优先级修正：叠加 068 章的截止时间与关键度，作为 CP 优先的前置过滤（过期任务强制先排）。

表调度的价值不在最优性（通常比下界差 5–15%），而在可解释、可增量更新、计算快：20 个任务、6 台机器人微秒级完成，几乎可以"每来一波新任务就重排一次"。它也天然支持"重排"：任务完成后从当前状态继续推进，而不用推翻历史。

4. 重排策略：稳定压倒最优

任务完成、失败、新任务到达都会让旧调度失效，但频繁重排会把系统变成布朗运动，机器人刚按新表启动又接到新表。三个抑制手段：

  • 事件触发 + 节流：任务完成触发局部推进（把后续任务前移），只有"结构性事件"（新任务到达、机器人离线、任务失败）才全量重排，且全量重排最小间隔 5 s。
  • 冻结窗：已经开始执行或 10 s 内即将开始的任务冻结在时间轴上，重排只动其后部分。
  • 稳定性罚金：重排目标改为"新 makespan + β × 变动任务数"，β 取 5–15 s/任务，让调度器对无关紧要的改进保持懒惰。

5. 数值算例：五任务 DAG 的关键路径与表调度全解

给一个可以完整手算的任务图：A(8 s) → C(6 s)、B(5 s) → C、B → D(3 s)、C → E(4 s)、D → E。正向动态规划求最早完成时间：eft(A) = 8、eft(B) = 5、eft(C) = max(8, 5) + 6 = 14、eft(D) = 5 + 3 = 8、eft(E) = max(14, 8) + 4 = 18。反向求尾长：tail(E) = 4、tail(C) = 6 + 4 = 10、tail(D) = 3 + 4 = 7、tail(A) = 8 + 10 = 18、tail(B) = 5 + max(10, 7) = 15。关键路径是 A → C → E，长度 18 s；工作量守恒下界 = 总时长 26/2 台 = 13 s，取更紧者，makespan 下界为 18 s。用两台机器人按尾长优先跑表调度：就绪任务 A 与 B，tail(A) = 18 > tail(B) = 15，先排 A 到机器人 1（0–8 s）；B 到机器人 2（0–5 s）；随后 C 就绪（tail 10）排在机器人 1（8–14 s），D 就绪（tail 7）排在机器人 2（5–8 s）；E 需等 C 与 D，二者都完成于 14 s，排在 14–18 s。最终 makespan 恰好 18 s，与下界相等，ratio = 1.0。这个例子说明：当关键路径长于工作量下界时，把机器人 2 的余量浪费掉也无妨，因为工期由关键链决定，这也再次印证"资源要往关键路径倾斜"。

6. 数值算例：短任务优先的反例

再看一个能暴露优先级选择错误的最小反例：任务 A(6 s) → Z(5 s) 构成一条关键链，另有 J1、J2 两个 2 s 的独立小任务，两台机器人。按尾长优先（CP 策略）：A 排机器人 1（0–6 s），Z 就绪后接着排机器人 1（6–11 s），J1、J2 由机器人 2 填缝（0–2 s、2–4 s），makespan = 11 s。换成"短任务优先"：两个 2 s 的任务先把两台机器人都占住（0–2 s），A 只能从 2 s 开始（2–8 s），Z 再从 8–13 s，makespan 变成 13 s，比 CP 策略差约 18%，而且在所有平局处理方式下结论都一样。原因直接写在数字里：短任务优先在"最关键任务即将开始"的时刻占用了全部机器，把整条关键链平移了 2 s，尾部任务全部顺延。这就是为什么带依赖的场景不能照搬 LPT 的"大石头先装桶"：LPT 的 4/3 近似界只对相互独立的任务成立，一旦有先后约束，优先级必须挂在"从这里到终止的最长剩余路径"（尾长）上，让稀缺的机器时间为关键链让路。

7. 数值算例：两个下界谁在主导

下界比值是调度评审的第一读数，用两个极端场景建立直觉。长链型：就是上一节的五任务图，关键路径 18 s、工作量下界 26/2 = 13 s，lb = 18 s，关键路径主导，比值 18/13 ≈ 1.38；此时增加机器人对 makespan 毫无帮助（该例已经是 18 s 达成），正确的优化方向是拆解或并行化关键链上的任务。并行型：8 个互不相关的 5 s 任务、2 台机器人，关键路径只有 5 s，工作量下界 40/2 = 20 s，lb = 20 s，工作量主导；加一台机器人下界降到 40/3 ≈ 13.3 s，收益近似线性。两条读数线放在一张表里，就能在评审现场回答"该加机器还是改结构"。

情形关键路径长工作量/台数有效下界主导项加一台机器的收益
长链型（A→C→E 等）18 s13 s18 s关键路径几乎为零
并行型（8×5 s 独立任务）5 s20 s20 s工作量近似线性（≈ 13.3 s）

使用方法是先算两个数、再做决策：若有效下界等于关键路径长，任何资源都买不回工期，先看依赖结构能不能改（把长链里的串行段转成可并行子任务，或者把数据依赖改成流水线）；若有效下界由工作量给出，扩张产能立竿见影。调度报告里同时给出"结果 / 有效下界"的比值，评审的讨论焦点会从"这张表排得好不好"转向"下界本身合不合理"，后者才是更有价值的问题。

重排与关键路径是正交的两件事，验收指标要分开列：关键路径与 ratio 衡量"调度质量"，重排次数与变动任务数衡量"执行稳定性"。把两者混在一个数字里，出问题就无法归因。变动控制的门槛也可以验算：一次重排预计变动 5 个任务、稳定性罚金 8 s/任务，等效门槛 40 s；在百秒量级的 makespan 上，这意味着只有结构性变化（大批新任务、机器人离线）才能省出超过 40 s，琐碎优化会被罚金自动挡下。

实现思路与设计

调度器的工程结构分四件套：

  1. 任务图构建：任务模板自带依赖声明（例如"送货"依赖"取货"），实例化时生成 DAG；入图前做环检测，发现环立即拒绝并报警（依赖配错是上游录入问题，不要让调度器背锅）。
  2. 时长估计：每类任务用历史 P75 时长（调度要留余量；均值会被长尾拖低），行驶时间用路网矩阵 + 0.9 折速度系数。
  3. 调度生成：表调度 + CP 优先，输出"机器人 → (任务, 开始时刻) 列表"；同时算两个下界，把"调度长度 / 下界"作为调度质量指标输出。
  4. 下发与跟踪：调度表按机器人切片下发；执行中每个任务结束上报，触发局部推进；偏差超过阈值（任务超时 20% 以上）触发全量重排。

调度结果输出成每台机器人一条泳道、每个任务一个色块的甘特图（可以让监控节点以文本或 CSV 形式发布），评审时一眼看出：哪台机器人是瓶颈（泳道排满）、关键路径在哪（红色链）、有多少空隙（橙色等待）。调度器如果只能输出"已下发"三个字，团队永远不会相信它，可视化是调度系统获得信任的最短路径。

关键代码与解读

片段 1：关键路径，拓扑序 + 尾长动态规划

def critical_paths(tasks, durations, notify=0.0):
    """tasks: {id: set(前驱)}；durations: {id: 秒}。
    返回 (每个任务的最早完成时间 eft, 从任务出发的最长尾长 tail)。"""
    order = topo_sort(tasks)                     # 拓扑序：前驱一定排在前面
    eft = {}
    for t in order:                              # 正向扫：求最早完成时间
        est = max([eft[p] for p in tasks[t]] or [0.0])
        eft[t] = est + durations[t]
    tail = {}
    succ = invert_edges(tasks)                   # 后继表：反向扫用
    for t in reversed(order):                    # 反向扫：求尾长（剩余关键长度）
        tail[t] = durations[t] + max([tail[s] for s in succ[t]] or [0.0])
    cp_len = max(tail.values()) if tail else 0.0
    return eft, tail, cp_len 
    # cp_len 即 makespan 下界之一：任何调度都不可能快过关键路径

解读：两个方向的动态规划把关键路径问题一网打尽。正向的 eft 告诉你每个任务"最早什么时候能完"，用于判断可行性，如果某任务的截止时间早于它的 eft，这个调度目标从一开始就不可达，应该立刻上报停机，让求解器空转只是浪费算力。反向的 tail（尾长）就是表调度的优先级：尾长最大的任务在关键路径上，先排它。代码里 or [0.0] 处理无前驱/无后继的边界；topo_sort 必须先做环检测，有环的图不产生拓扑序，直接抛错比让 DP 静默算错强。注意这段逻辑与 068 章的紧急度是不同坐标：紧急度管"谁先被满足"，尾长管"谁最拖后腿"，重排时两者相乘或分级使用。

片段 2：表调度，按尾长优先贪心压轴

def list_schedule(tasks, durations, tail, robots, travel, ready=None):
    """表调度：反复派"就绪且尾长最大"的任务给最早能开工的机器人。
    travel(a, b) 为路网行驶时间；返回 {robot: [(task, start, end), ...]}。"""
    finish_of = {}                       # task -> 预计完成时刻
    free_at = {r.id: 0.0 for r in robots}      # 各机器人空闲时刻
    pos = {r.id: r.pose for r in robots}       # 各机器人当时位置（算行驶时间）
    plan = {r.id: [] for r in robots}
    remaining = set(tasks)
    while remaining:
        ready_tasks = [t for t in remaining
                       if all(p in finish_of for p in tasks[t])]   # 前驱已完成
        t = max(ready_tasks, key=lambda x: tail[x])                # 尾长优先
        options = []
        for r in robots:
            est_ready = max(free_at[r.id],
                            max([finish_of[p] for p in tasks[t]] or [0.0]))
            arrival = est_ready + travel(pos[r.id], t.pose)        # 空驶时间
            options.append((arrival + durations[t], arrival, r))
        end, start, r = min(options, key=lambda o: o[0])           # 最早完工者
        plan[r.id].append((t, start, end))
        finish_of[t] = end
        free_at[r.id] = end
        pos[r.id] = t.pose                # 该机器人到了任务点：位置更新
        remaining.remove(t)
    return plan

解读：这段代码就是"把任务压上时间轴"的仿真。四个关键行：就绪筛选保证前驱完成后才能排（顺序约束的兑现）；尾长优先把稀缺资源让给关键任务；开工时刻取三者最大，机器人空闲时刻、前驱完成时刻、（再加行驶时间），这是所有带依赖调度器通用的"就绪时间"公式，漏任何一项都会排出物理上不可能的表；选最早完工者（按"空闲最久"来选会把任务塞给一台"闲但远"的机器人），避免无谓的空驶。复杂度 O(m×n²)，20 任务 × 6 机器人瞬间完成。别忘了 pos 的更新：机器人做完任务的落点是下一个任务行驶时间的起点，这一行就是 070 章反复强调的"顺序相关准备时间"的代码形态。

片段 3：下界评估与调度质量

def evaluate(plan, cp_len, durations, n_robots):
    """产出调度质量报告：makespan、两个下界、与下界的差距、关键任务标记。"""
    makespan = max(end for lanes in plan.values() for (_, _, end) in lanes)
    work_bound = sum(durations.values()) / n_robots      # 工作量守恒下界
    lb = max(cp_len, work_bound)                         # 取更紧的下界
    ratio = makespan / lb if lb > 0 else float("inf")
    report = {
        "makespan": round(makespan, 1),
        "lower_bound": round(lb, 1),
        "ratio": round(ratio, 3),                        # 目标 ≤ 1.15
        "lanes": {rid: len(lanes) for rid, lanes in plan.items()},
    }
    # 机器人的"负载最大者"通常是瓶颈：下一轮加机/调权重的依据
    report["bottleneck"] = max(report["lanes"], key=report["lanes"].get)
    return report

解读：评估函数回答两个问题："调度好不好"（ratio 与下界的差距）与"瓶颈在哪里"（最忙的泳道）。ratio 要设验收线（如 ≤ 1.15）：超过就说明启发式太粗糙或参数失真（最常见的是行驶速度折减不够）。两个下界的取大逻辑值得记住：纯串行任务链的机器（cp_len 占主导）无论加多少机器人都救不了；纯并行任务堆的机器（work_bound 占主导）加机器人立竿见影，先看哪个下界在主导，再决定加机器还是改依赖结构。报告建议随调度表一起存档，三周后当有人问"为什么那次任务拖了"，你能用数据回答，无需依赖回忆。

常见坑

  • 行驶时间不计入依赖边：任务 B 依赖 A 的数据，但机器人从 A 点到 B 点还要 20 s，调度表按"零切换"排，实际全程晚 20 s。修复：所有顺序约束边至少携带两任务间的行驶时间，或统一在就绪时间公式里加。
  • 用平均时长估计：长尾任务（偶发绕路）把整个表带崩。修复：用 P75 或 P90 时长；调度质量用 ratio 衡量，绝对时间会随任务规模漂移。
  • 给非关键路径加资源：调度超时后机械加机器人，makespan 巍然不动。修复：先输出关键路径标记，资源优化只针对关键路径上的任务。
  • 每次任务完成都全量重排：机器人收到 5 秒内第三张调度表，启动又取消。修复：局部推进 + 全量重排节流 + 冻结窗 + 稳定性罚金。
  • 依赖图有环：上游配错依赖（A 等 B、B 等 A），调度器卡死在"无就绪任务"循环。修复：入图时拓扑排序检测环，发现即拒绝整批并点名冲突任务对，让上游修数据。

  2. 上题用 2 台机器人、行驶时间忽略，分别按"关键路径优先"与"短任务优先"跑表调度，比较 makespan。解释为什么短任务优先会变差。★★
    提示
    CP 优先：一台做 A(8)→C(6)→E(4) = 18 s，另一台做 B→D = 8 s，makespan 18；短任务优先可能先派 B、D，把 A 压到后面导致 C 等到 13 s。短任务优先先消耗了机器人的时间片，关键链被推迟。
  3. 给片段 2 的表调度加上"顺序相关准备时间"的增强：机器人完成前一任务的位置到下一任务位置的路网时间必须计入。写出改动点，并用一个 3 任务 2 机器人的小例子说明改动前后的 makespan 差异。★★

    提示
    预期：立即重排 makespan 最接近重排后的新下界，但变动次数最多、启动延迟最高；冻结窗居中；稳定性罚金牺牲少量 makespan（3–8%）换取最低变动。结论应写成"什么场景选什么策略"的决策表。

小结

  • 分配管"谁"，调度管"何时、何序、哪些并行"；顺序约束把问题推入 NP-hard，工程上用启发式求"接近下界"的解。
  • 任务图 + 关键路径：正向算 eft 判可行性，反向算尾长作优先级；makespan 下界 = max(关键路径长, 总工作量/台数)。
  • 表调度三要素：就绪时间公式（含行驶准备时间）、尾长优先、最早完工分配；复杂度低到可以"边执行边重排"。
  • 重排求稳定不求最优：事件节流、冻结窗、稳定性罚金；Gantt 输出是调度系统获得信任的最低配置。
