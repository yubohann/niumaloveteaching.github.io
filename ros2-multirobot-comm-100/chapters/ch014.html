第 014 章：网络带宽管理与流量整形

预算告诉你网络够不够用，策略决定谁先用：关键流优先、大流限速、后台流让路，从应用层到网卡的三级工具箱。

  • 主题：通信基础 / 流量管理
  • 关键机制：流量分类、令牌桶限流、优先级调度、闭环降载
  • 预计学时：55 分钟
  • 前置章节：第 013 章

学习目标

  • 理解流量管理的目标是"保护关键流、约束贪婪流"，不追求"平均分配"：会做三级分类（关键/尽力/后台）。
  • 掌握令牌桶的原理与参数含义（速率与突发额度），会为一条数据流设定合理的限速参数。
  • 认识三级工具箱：应用层节流、网络层整形（tc/DSCP）、无线层优先级（WMM），知道每级该做什么、边界在哪。
  • 会给系统设计"闭环降载"：拥塞时向上游反馈，让数据源主动降频，网络被挤爆的局面由上游化解。
  • 能识别整形的常见反模式：只限速不分类、把 Reliable 流限到低于重传需求、出口方向搞错。

背景与动机

第 013 章的预算算出了瓶颈与余量，但系统上线后流量并不会"自觉守规矩"：日志上传想多大就多大，图像节点想发多快就发多快，地图上传想起来就发。结果是一个经典的公地悲剧，关键的控制指令和贪婪的后台流量在同一个队列里排队，前者被后者拖垮。

流量整形（traffic shaping）要解决的就是这个结构性问题：给流量分类、给贪婪流设上限、给关键流留通道。它是"网络公民教育"：让每条流拿到"配得上它重要性"的服务，这比单纯放大总带宽有效得多。本章给的三级工具箱（应用层、网络层、无线层）各有车道，组合使用才能既保护控制流、又不让后台任务彻底饿死。

核心原理

1. 先分类，再行动：关键 / 尽力 / 后台

整形的第一步永远是分类。多机器人系统里三条车道：

类别典型流量特征策略
关键流控制指令、状态、心跳、安全事件小、持续、延迟敏感优先通行；限速余量充足（含重传）
尽力流感知数据、可视化、协同感知中大、可降级按配额通行；拥塞时降频降质
后台流日志上传、录像回传、地图同步、软件更新大、可延迟、可断点严格限速；低优先级；预约错峰窗口

分类依据是"延迟敏感度 × 可降级性"这个二维判据，"谁重要"这类模糊感觉不作数：控制指令既敏感又不能降级，进关键车道；日志不敏感可降级，进后台车道；图像介于之间。没有分类的限速是破坏性的，如果把所有流量"平等"限到配额，关键流会被后台流挤成受害者。分类 → 配额 → 手段，这个顺序不能乱。

2. 令牌桶：限速的基本零件

限速的实现几乎都用令牌桶（token bucket）：桶以恒定速率 r 注入令牌，桶容量为 b（突发额度）；发一个字节消耗一个令牌；桶空时必须等，长期平均速率被压到 r，短期可以透支到 b 的突发。

长期平均速率 ≤ r；最大突发量 ≈ b r 决定"稳态多快"，b 决定"憋多久能一次性冲多少"：地图上传需要大 b，控制流要小 b

参数选择很讲究：r 按业务预算设（如日志每台 2 Mbps）；b 按"合理的瞬时爆发"设，太小会把正常突发切成碎片（一个 3 MB 地图上传被 2 Mbps + 小 b 限成几十秒，失去意义）；太大则失去平滑作用（突发照旧冲击网络）。经验起点：b ≈ r × 0.5–2 秒，再按实际场景调整。注意桶是在发送端就地执行的：先在源头限，再谈网络层。

算例：一个 3 MB 文件穿过 r = 2 Mbps、b = 1 MB 的桶要多久？桶满时先放 1 MB（瞬时），剩余 2 MB 按 2 Mbps = 0.25 MB/s 注入，耗时 2 ÷ 0.25 = 8 s；若桶恰好空着，还要先等 1 MB 的令牌积攒（4 s），最坏 12 s。公式化：单次传输耗时 ≈ (S − b) ÷ r，桶空时再加 b ÷ r（S 为消息大小）。再反推一遍 b 的取值哲学：如果这个 3 MB 是必须整体送达的归档，b 至少给到 1 MB 量级才能让传输"不被打断两次以上"；而一条 100 Hz 的控制流，b 应该小到只覆盖几个周期的抖动，防止积压转化为延迟。

机制超额报文的处理是否引入延迟适用场景
监管（policing）直接丢弃或降级标记不缓冲，延迟不变防滥用、保护池；丢不影响语义的流
整形（shaping）放入缓冲排队，平滑后发出引入排队延迟后台大流；需要"完整送达"的传输

区分这两个词很重要：监管是"超了就丢"，整形是"超了就等"。对控制与感知流用监管（丢一帧无所谓，等一帧反而有害），对日志与归档用整形（宁可慢，不可残）。把需要整形的流做成监管，会得到"文件传一半断掉"的故障；把该监管的流做成整形，则给控制流加上了排队延迟，两头都错。

3. 三级工具箱各管什么

层手段管什么边界
应用层（ROS 内）发布降频、消息降采样、令牌桶节流、数据差分/压缩该发多少、什么时候发需要改代码；对第三方节点力不能及
网络层（主机）tc 整形/调度、DSCP 标记、HTB 分层配额怎么排队、谁先走只对出口方向有效；需部署与持久化
无线层（AP）WMM 四类优先级、SSID/频段分离、每客户端限速空口资源的分配依赖 AP 能力与配置，端到端可见性差

选择标准：能应用层做就应用层做（最可控、语义最清楚，你知道这是"图像"而网络只看到字节）；网络层做兜底（防止"漏网流量"破坏全局）；无线层做结构（分离与优先级）。一个实操细节：Linux 的 tc 只管出口（egress），所以要限制"机器人上传"，限制规则要加在机器人自己身上；加在服务器侧就装反了方向，是新手常见错误。

无线层的优先级值得再拆一层：WMM 把流量分入四个接入类别，靠不同的信道竞争参数（AIFSN 越小越早抢到信道、CWmin 越小退避窗口越短）形成优先次序。典型默认档位如下（具体以实现配置为准）：

接入类别典型流量AIFSNCWmin相对优先级
语音类（VO）急停、安全事件23最高
视频类（VI）控制指令、状态流27高
尽力类（BE）图像、感知数据315中
背景类（BK）日志、软件更新715最低

WMM 有一个常被误解的边界：它管不住多播与广播。多播帧没有 ACK、没有接入类别队列，通常还按最低基础速率发送，因此发现信标与任何走多播的数据流量都得不到优先级保护，往往最慢、最不可靠。这也从无线层侧面解释了三条老结论：关键流量尽量单播；多播发现要谨慎；大流量不要靠多播省事。

4. 闭环降载：让拥塞变成反馈

静态配额有个软肋：网络状况是动态的（有人走近 AP、信道干扰突增、20 台同时开工）。闭环降载把"网络拥塞"变成上游可感知的信号：

  • 信号来源：AP/交换机计数器（队列丢弃）、QoS deadline 事件（第 012 章）、应用层观测（发送队列积压、重传率上升）。
  • 反馈通道：一条低带宽的"预算指令"话题（如 /fleet/bw_budget，Reliable + Transient-local，1 Hz），或简单粗暴的"降载等级"枚举。
  • 执行方：图像节点收到"降到 5 fps"就降，有语义的执行（降分辨率/降帧率）远好于网络层一刀切（丢帧不挑内容）。

这是"自适应"的最小可用形态，不需要花哨算法：监测 → 广播等级 → 节点按等级调整。设计要点是滞后与稳定：反馈周期不能太短（会震荡），降载要分级（如 100%/70%/40% 三档），恢复要慢于降级（经典的非对称策略，坏了立刻降，好了慢慢升）。

5. 反模式清单

最后固化几条"别这么干"：（1）只限速不分类，关键流被平等地伤害；（2）把 Reliable 流限到低于它的重传需求，丢包→重传→更堵的死循环（限速值要包含重传余量，无线环境加倍）；（3）出口方向搞反，在服务器限"下行"却想治机器人的"上行"；（4）突发额度抠到零，正常业务被切碎，团队转头怪"网络不稳定"；（5）限了带宽不限队列，整形器自己的缓冲过大，延迟照样膨胀（多机器人场景 buffer bloat 同样致命）。

整形也有三条边界，写进设计文档以免过度承诺：（1）物理层太差时它无能为力：弱信号导致的低速率与重传发生在整形器之下，应用层降载只能少发，修好介质仍然是第一优先级；（2）它不创造带宽：总需求超过容量时，整形只决定谁挨饿，必须配合"减量"；（3）端到端可见性有限：主机整形管不到别人的设备与骨干段，AP 侧排队对主机不可见，所以要保留应用层闭环降载作为跨层兜底。

实现思路与设计

回到 20 台 AGV 车间（第 013 章的账）：每 AP 稳态 ρ≈0.56、最坏秒 1.36。给出一份完整的流量管理方案：

  1. 分类落表：控制/状态 → 关键；图像/激光 → 尽力；日志/地图/录像 → 后台。
  2. 配额分配（按每台机器人、每 AP 预算倒推）：关键流不限（天然小）；图像按 AP 均分（例：每台 12 Mbps 上限）；后台合计 ≤ 15% 的 AP 容量，且只能走"错峰窗口"。
  3. 手段组合：应用层给日志与图像加令牌桶；机器人主机加 DSCP 标记；AP 启用 WMM 并把后台映射到低优先级类。
  4. 闭环兜底：监测节点每 5 s 评估每 AP 利用率，>0.75 发"降载 L1"（图像 10→6 fps）、>0.9 发 L2（→3 fps + 日志暂停）。
  5. 验证：基线测试（限流前）、限流后主题 bw 对比、拥塞注入测试（人为打满 + 控制延迟不劣化）。

设计决策：为什么"在发送端应用层限流"优先于"在网络设备限流"？

四个理由叠加。（1）语义可见：应用层知道这是"图像"，可以优雅降级（降分辨率），而网络层只会按字节丢弃（丢掉半张图反而更糟）。（2）省的是全程：源头不发，从机器人到 AP、到骨干、到服务器的每一段都省下；网络层限速只省限速点之后的链路。（3）避免无效重传：网络层丢 Reliable 流会触发重传，等于"限速又倒贴带宽"；源头降频没有重传。（4）可观测：发送端能把"我发了多少、被限了多少"写进日志与监控；交换机的匿名丢弃只会表现为"别人莫名其妙的抖动"。结论：应用层配额是第一道闸，网络层整形是兜底的第二道闸，两道都有，但顺序别反。

关键代码与解读

片段 1：应用层令牌桶，图像上传的限速闸门

class RateLimitedImageSender(Node):
    """压缩图上传：用令牌桶把长稳速率压到预算内，同时容忍短突发。"""
    def __init__(self, rate_mbps=12.0, burst_mb=3.0):
        super().__init__("image_up")
        self.rate_bps = rate_mbps * 1e6 / 8.0        # MB/s 口径的填充速率
        self.burst = burst_mb * 1e6                  # 突发额度：约 2 秒的量
        self.tokens = self.burst                     # 初始满桶：允许开局爆发
        self.last = self.get_clock().now()
        self.pub = self.create_publisher(CompressedImage, "camera/compressed",
                                         qos_profile_sensor_data)

    def try_publish(self, msg):
        now = self.get_clock().now()
        dt = (now - self.last).nanoseconds / 1e9
        self.last = now
        self.tokens = min(self.burst, self.tokens + dt * self.rate_bps)
        cost = len(msg.data)                         # 令牌消耗按字节算
        if self.tokens < cost:
            return False                             # 桶空：这一帧放弃（可降级为跳帧）
        self.tokens -= cost
        self.pub.publish(msg)
        return True

解读：（1）令牌桶放在发布路径的函数里（try_publish），不另起线程：调用方对"发不出去"有知情权，可以选择跳帧、降质量、或累计告警；限流器返回布尔值，把决定权留给业务，默默阻塞是反模式。（2）burst = 3 MB 的取法：约等于 2 秒的稳态量，让"刚上线时补发几帧"这类正常突发得以通过，同时把持续超速稳稳压住。（3）桶空时选"丢帧"：图像是新闻类数据（第 011 章），排队只会制造延迟；丢弃最新帧、等桶回暖才是正确语义。若换成日志上传（后台、可延后），同样的桶只需把"返回 False"改成"入队稍后重试"。

片段 2：网络层整形，tc 给后台流设专用通道

# 在机器人主机上为"日志出口"建立限速类（HTB），对上行流量生效
# 前提：DSCP 标记已由应用或 iptables 打在日志流上（示意）
tc qdisc add dev wlan0 root handle 1: htb default 30
# 1:10 关键流：大额保底 + 高优先级，保证控制与状态永不受限
tc class add dev wlan0 parent 1: classid 1:10 htb rate 50mbit ceil 80mbit prio 0
# 1:20 尽力流（图像）：稳态 12mbit，空闲时可借用（ceil 给到 40）
tc class add dev wlan0 parent 1: classid 1:20 htb rate 12mbit ceil 40mbit prio 1
# 1:30 后台流（日志）：稳态 2mbit，上限锁死，不许借别人的额度
tc class add dev wlan0 parent 1: classid 1:30 htb rate 2mbit ceil 2mbit prio 2
# 用 fq_codel 作为叶子队列：主动管理缓冲，压制 bufferbloat 式延迟
tc qdisc add dev wlan0 parent 1:10 fq_codel
tc qdisc add dev wlan0 parent 1:30 fq_codel
# 过滤规则：按 DSCP 把流量分到类（语法以你的 tc 版本为准）

解读：（1）这段配置的结构是"保底 + 可借 + 锁死"三种策略并存：关键流保底 50、上限 80（借空闲）；图像保底 12、可借到 40；日志锁死 2/2（不许借）。保底保证"再挤也有你的份"，ceil 保证"再空也不许你独占"，HTB 的价值就在于这套双层语义。（2）prio 决定同一时刻的出队次序：关键流永远排在图像与日志前面。（3）最后挂 fq_codel 是针对多机器人场景的深水细节：整形器不管理缓冲的后果是"限了带宽、没限延迟"，fq_codel 主动丢弃并公平排队，把排队延迟压住，限速的目标从来是延迟可控，不是数字好看。

片段 3：闭环降载，把拥塞变成一条指令

class BandwidthGovernor(Node):
    """预算治理器：评估每 AP 利用率，向图像节点广播降载等级。"""
    def __init__(self):
        super().__init__("bw_governor")
        qos = QoSProfile(depth=1, reliability=ReliabilityPolicy.RELIABLE,
                         durability=DurabilityPolicy.TRANSIENT_LOCAL)
        # 1 Hz 广播当前等级：新加入的节点立刻拿到（TL 语义，第 011 章）
        self.pub = self.create_publisher(LoadLevel, "/fleet/bw_level", qos)
        self.level = 0
        self.create_timer(5.0, self.evaluate)     # 评估周期：防震荡的第一道闸

    def evaluate(self):
        util = self.measure_ap_utilization()      # 来自 AP 计数器或本地统计
        if util > 0.9:
            want = 2                              # L2：图像 →3 fps，日志暂停
        elif util > 0.75:
            want = 1                              # L1：图像 →6 fps
        else:
            want = 0
        if want > self.level:                     # 坏消息立刻执行：降载不迟疑
            self.level = want
        elif want < self.level and self.stable_for(30.0):
            self.level = want                     # 好消息慢慢来：稳定 30 s 才回升
        msg = LoadLevel()
        msg.level = self.level
        self.pub.publish(msg)

解读：（1）这段代码实现的是第 4 节说的"非对称策略"：if want > self.level 立刻升级降载，恢复则要求 stable_for(30.0)，坏消息快、好消息慢，是控制回路的通用防震荡手法（与第 006 章看门狗的连续判定同源）。（2）用 Transient-local 发等级：图像节点万一中途重启，也立刻知道"现在还在 L1"，不会满速复活把网络再点着。（3）评估周期 5 s、恢复观察 30 s，这两个数字常被质疑"太慢"，但降载不是安全联锁（那个由本地看门狗秒级兜底），它是资源治理，稳定性比速度重要；参数应写进设计表并预留现场调整位。

常见坑

  • 限速方向装反：想在服务器侧限制机器人上行，结果 tc 只管出口（服务器下行），毫无效果。修复：上行流量在机器人主机上整形；把"谁的出口"写进配置注释。
  • 把 Reliable 流卡到重传红线以下：给图像限 10 Mbps，但丢包重传让实际需求 12 Mbps，限速→丢→重传→更拥塞的死亡螺旋。修复：限速值含 20–50% 重传余量；或干脆让该流 Best-effort（第 011 章）。
  • 突发额度抠成 0：令牌桶 burst 设得极小，正常的一次脉冲突发（上传一帧地图）被切成几十段，业务超时连环失败。修复：burst ≈ 0.5–2 秒的稳态量；"平滑"不等于"禁突发"。
  • 只限带宽不限缓冲：整形器缓冲偏大，利用率是低了，但排队延迟高企（bufferbloat），控制流照样迟到。修复：叶子队列用 fq_codel 类主动队列管理；给关键流单独挂小缓冲队列。
  • 配置不持久化：tc 规则手工执行，设备重启即失效。部署脚本/网络管理器统一下发并加"配置自检"（第 006 章图层巡检的思路）。

练习与思考

  1. 参数题：日志上传令牌桶 r=2 Mbps、b=1 MB。一次 3 MB 的归档上传最快需要多久（含突发额度）？如果把 b 改到 0.2 MB 会变成多久？说明两个配置各自适合什么场景。★
    提示
    桶满起步时 b=1MB 约 8 s（先冲 1 MB，余 2 MB 按 2 Mbps=0.25 MB/s 再 8 s）、b=0.2MB 约 11.2 s；桶空起步再各加满桶等待（4 s / 0.8 s）。小 b 全程平滑但更慢，适合持续小流量；大 b 适合偶发归档。
  2. 预测题：给图像流把 HTB 的 ceil 从 40mbit 改成 12mbit（与 rate 相同），在"网络空闲"与"网络拥挤"两种状态下分别预测图像节点的实际体验变化。★
    提示
    空闲时失去借用能力（本来能冲到 40 的机会没了），图像可能卡在 12；拥挤时行为不变（本来就接近 12）。结论：ceil 是"空闲红利"的阀门，关掉它等于放弃机会性吞吐。
  3. 设计题：为"软件更新分发"（每台 200 MB，一个月一次）设计流量方案：分类、限速参数、执行窗口、对 ρ 的影响，以及"更新中断续传"的考虑。★★
    提示
    后台类 + 深夜错峰窗口 + 令牌桶 r=5 Mbps/b=10 MB；200 MB 约 6 分钟/台；更新服务器与主业务分流（频段/SSID）；务必支持断点续传（别让 90% 的下载因窗口结束而作废）。
  4. 推导题：给一条 100 Hz 的 cmd_vel 流（每帧 80 B）设计 DSCP/WMM 映射与队列参数：说明它需要的最小带宽（含 30% 余量）、为什么必须走小缓冲队列、以及 bufferbloat 对它的危害量化（0.1 s 缓冲 = 多少米的控制滞后，按 1 m/s）。★★★
    提示
    80 B×100 Hz≈64 kbps×1.3≈85 kbps；小缓冲队列（如 20 ms）使最坏排队延迟 20 ms=2 cm 位移误差；若共用 0.1 s 大缓冲，1 m/s 下 10 cm，控制类流量必须"专属小队列"是量化结论，不是偏执。
  5. 方案评审：某方案给"图像、激光、日志"统一限到每台 8 Mbps，理由是"公平"。列出至少三条反对理由，并给出替代设计（含关键流的处理）。★★★
    提示
    反对：激光本来就远小于 8（被限制没意义）、日志在窗口外应可让路、公平限速在拥塞时同时伤害关键流（无优先级）。替代：三级分类 + 关键流优先队列 + 尽力/后台各自配额 + 闭环降载兜底。

小结

  • 整形目标是保护关键流、约束贪婪流：先分类（关键/尽力/后台），再配额，再选手段。
  • 令牌桶 = 速率 r + 突发额度 b：r 定稳态、b 定瞬时爆发；"丢帧、排队、稍后重试"按数据语义选。
  • 三级工具箱：应用层（语义化降级，第一道闸）→ 网络层（tc/HTB/fq_codel 兜底与优先级）→ 无线层（WMM/分频/分 SSID）。
  • 闭环降载：监测利用率 → 广播等级（TL 语义）→ 节点按级降帧；坏消息快、好消息慢，防震荡。
  • 反模式：限速不分类、把 Reliable 流卡到重传红线以下、方向反了、禁绝突发、只管带宽不管缓冲；物理层不达标时先修介质，再谈策略。
