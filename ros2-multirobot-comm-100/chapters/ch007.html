第 007 章：分布式命名空间隔离

20 台机器人共用一个域，凭什么不串线？答案是 ROS 名字系统：相对名、私有名、绝对名各自展开到哪里，命名空间怎么分层，本章全部讲透。

  • 主题：通信基础 / 名字系统与隔离
  • 关键机制：名字解析规则、命名空间分层、名字冲突检测
  • 预计学时：50 分钟
  • 前置章节：第 002 章

学习目标

  • 彻底掌握 ROS2 三类名字（相对名、私有名、绝对名）的展开规则，能手算任意节点里任意名字的最终全名。
  • 理解命名空间与 Domain ID 的分工：一个在图层防串线，一个在网络层隔离系统，能说清各自管什么。
  • 会给多机器人系统设计命名分层（机器人 → 子系统 → 资源），控制层级深度并保持可读性。
  • 会写"零硬编码"的节点代码：内部只使用相对名与私有名，一切前缀由 launch 注入。
  • 掌握部署后的命名自检：查同名端点、查前缀一致性、查真机上名字是否与设计一致。

背景与动机

第 001 章说过：同一域内，所有节点共享一张计算图。4 台机器人如果都发布 /odom、都订阅 /cmd_vel，DDS 的匹配是 N:M 的，它们不会报错，只会把数据混在一起：遥控台想让 2 号前进，结果四台机器人一起动；定位数学上收到四份"自己的里程计"。这就是命名空间要解决的第一个问题：在同一张图上给每台机器人划出自己的名字领地。

命名空间不只是"话题加前缀"。它作用于节点持有的全部名字，话题、服务、动作、参数全都按同一套规则展开。这意味着命名空间设计错了，排障会扩散到系统每个角落；设计对了，则"一份代码部署 20 台"成为自然结果。本章把名字规则讲到底，它是下一章重映射（008）的前置知识（重映射本质上是对已展开名字的改写），也是第 020 章双机系统骨架的一半。

核心原理

1. 名字的三种写法与展开规则

ROS2 中一个名字最终指向哪里，由"节点的命名空间 + 节点名 + 名字本身的写法"共同决定。三类写法：

写法示例（节点 /robot3/scanner）展开结果语义
相对名scan/robot3/scan跟随节点命名空间：最常用的跨组件接口名
私有名（~ 前缀）~/debug/robot3/scanner/debug挂在节点名下：节点"自己的"资源，天然防重名
绝对名/fleet/map/fleet/map无视命名空间：跨机器人共享与明确的系统级接口

记忆规则一句话：相对名"随大流"（跟命名空间），私有名"回自己家"（跟节点），绝对名"报全地址"（谁也不跟）。这个展开发生在节点创建发布者/订阅者/服务的时候，展开后的全名才是 DDS 层匹配的依据，两台机器人的同名相对话题之所以不串线，就是因为展开结果不同。

全名展开三式：相对名 → 命名空间 + "/" + 名字；私有名 → 命名空间 + "/" + 节点名 + "/" + 名字；绝对名 → 原样保留 例：节点 /fleet/robot7/planner 里写 path、~/goal、/fleet/task，展开为 /fleet/robot7/path、/fleet/robot7/planner/goal、/fleet/task。展开是匹配前的最后一步，你手算得出的全名就是 DDS 看到的全名

数量算例能让你看清"不隔离"的代价：4 台机器人若都不加命名空间，各自发布 /odom 又各自订阅 /cmd_vel，计算图上每个名字形成 4 个发布者乘 4 个订阅者共 16 组候选配对，DDS 会把它们全部匹配上；加上 /robotN 前缀后，同一份代码展开出 4 个不同的名字，每个名字只剩 1 乘 1 共 1 组配对，4 台合计 4 组。把数字放大到 20 台：不隔离时每个名字 400 组配对，隔离后 20 组。配对数的除法关系正是"隔离"的数学形态；同时要记住一个反直觉的边界：命名空间只改变名字与配对关系，并不会减少发现流量本身（发现流量由参与者数量与端点数决定），要把发现流量也压下来，必须用 Domain 隔离或发现服务器（第 010 章）。

三条边界规则常被问起，一并说清。（1）相对名可以自带子路径：debug/log 展开为 /robot3/debug/log，其中 debug 只是名字里的路径段，不构成独立的命名空间分区。（2）节点在根命名空间（namespace 为空）时，相对名展开为 /name，私有名展开为 /节点名/name；单机调试里常见，在多机器人系统里则意味着没有隔离，自检脚本应把它们标为异常。（3）话题、服务、动作共享同一套展开规则；参数走另一条规则：私有参数 ~/rate 的全名是"节点全名 + /rate"，YAML 用节点全名寻址（第 005 章），命名规范对参数同样生效。

混合使用的正确姿势：节点内部接口用相对名，节点内部私有资源用私有名，跨机器人引用用绝对名。反过来在本应通用的组件里写绝对名（如 create_publisher(Twist, "/cmd_vel")），等于把"这台机器人的领地"焊进了代码，第二台机器人复用同一份代码时就会直接串线。

2. 命名空间 vs Domain ID：两级隔离的分工

回顾第 001 章的"两把钥匙"，现在可以更精确地对比：

维度Domain ID命名空间
作用层DDS 网络层（端口级隔离）ROS 图层（名字前缀）
可见性互相完全不可见，发现都不发生同图可见：能看到、能订阅、能操作
切换成本需配置/环境变量，通常写死在部署里launch 一行参数，随实例注入
典型用途隔离独立系统（产线 vs 调试）、安全边界同一系统内多机器人实例共存

关键工程事实：命名空间不是安全边界，它防"误连"，不防"恶意或好奇的访问"。任何同域节点都可以用绝对名订阅别人的话题。真正需要隔离请用 Domain（或 DDS 安全机制，第 073 章）。设计口诀：系统边界用 Domain，系统内分工用命名空间。

3. 分层设计：给 20 台机器人一个不乱的名字世界

命名空间可以嵌套，形成层级。多机器人系统的常见分层是：/车队域别/机器人编号/子系统，例如 /fleet/robot12/lidar/scan。设计要点：

  • 从左到右从大到小：帮助人和工具按前缀分组（ros2 topic list 天然按字典序聚簇）。
  • 深度控制在 3–4 层：每多一层，CLI 输入更长、人更容易写错；超过 4 层通常意味着该用私有名或话题命名来区分；继续深挖命名空间只会让输入与阅读更累。
  • 机器人编号对齐：robot1..robot20（两位补零或严格递增），保证字典序与物理编号一致，扫日志时不会出现 robot10 夹在 robot1 和 robot2 之间。
  • 车队级话题独立成支：共享资源的命名空间 /fleet 应与机器人支并列；藏在某台机器人下会让共享数据的归属含糊。

4. 命名分层方案对比

同样的隔离目标有多种编码方式，选错不致命但会长期磨损可维护性：

方案示例隔离效果CLI 与日志可读性跨机引用成本扩展评估
扁平单层前缀/robot3/scan好中：同一机器人资源分散排列短20 台可接受，编号需补零
分层两级/fleet/robot03/lidar/scan好好：前缀分簇，子系统归属一眼可见稍长但可用补全20 台以上推荐
子系统在前/lidar/robot03/scan好差：按子系统聚合，定位某台机器人费劲别扭不推荐
无前缀绝对名/scan无差不可控仅限单机调试

选择依据只有一条：让阅读者的检索路径与系统的物理结构一致。人查问题时先想"哪台机器人"，再想"哪个子系统"，所以机器人编号在前、子系统在后；反过来写，你的正则与人工扫描都要多做一次变换。方案定了就写进规范表并配自检脚本（本节末），规范与工具对齐后，风格漂移才拦得住。

5. 命名空间如何"传播"到所有资源

命名空间在节点构造时确定，之后节点创建的每一个相对名资源都会自动前缀化：话题 scan、服务 self_test、动作 navigate 全部跟随。参数也不例外，参数存在节点的全名下（/robot3/scanner 的参数表），所以 YAML 里按"命名空间 + 节点名"精确寻址（第 005 章）。

有一个常被忽略的推论：同名节点的合并语义。ROS2 允许两个节点取同一个全名，图里会显示为一个名字下多个节点，它们的同名端点会合并成 N:M 关系。命名空间设计混乱（比如 4 台机器人共用一个 /robot1 前缀）时，这种"合并"会让问题非常隐蔽；部署自检必须能发现"全名重复"。给一个可观察的算例：两台同名节点各以 50 Hz 发布 odom，合并后订阅端看到的是 100 Hz 的混合流，频率"翻倍"看似健康，数值却在两套坐标系之间交替跳变，这种故障既不容易被频率监控抓住，也无法从单条消息上直接认出。

6. 与重映射的叠加顺序

命名空间展开与重映射（remap，下一章主题）存在顺序关系：名字先按节点环境展开为全名，重映射规则再对全名做改写。理解叠加顺序的意义在于排障：ros2 node info 显示的端点是两轮加工后的最终结果，如果最终名字不对，你要先判断错在"展开"（命名空间/节点名配置问题）还是"改写"（重映射规则问题）。下一章会用具体案例演示这条链路。

实现思路与设计

给"4 台机器人 + 调度台"的巡逻系统设计命名规范，四步：

  1. 定顶层分区：/fleet 放跨机器人共享（任务、地图、编队参数），/robotN 放各机内部。每个名字在出生时就要面对灵魂提问："它属于一台机器人，还是属于整个车队？"
  2. 定子系统层级：机器人内部按传感器/决策/控制分：/robotN/lidar、/robotN/planner、/robotN/base。原则是"按消费边界分组"，不是按代码仓库结构分组。
  3. 约定代码纪律：组件代码只用相对名与私有名；不允许出现 /robotN 字面量（代码评审规则）；跨机器人引用集中在一小撮"桥接节点"里（用绝对名，下一章用重映射优雅解决）。
  4. 部署即自检：起系统后跑一次命名检查，列出全部节点/话题全名，与规范表比对；对重复全名、规范外前缀、孤立命名空间（没有节点注册）报错。

命名规范表（节选）

名字类别写法理由
/robotN/lidar/scan话题相对名注入命名空间机内私有，随身份展开
/robotN/base/cmd_vel话题相对名机内私有，供安全层写入
/fleet/task话题绝对名车队共享，调度台发布
/robotN/scanner/self_test服务私有名 ~/self_test节点自己的维护接口
/fleet/map话题绝对名 + Transient-local后加入机器人也要拿到
设计决策：为什么机器人编号从 1 开始、且严格与命名空间一致？

因为机器人系统里的编号会扩散到命名空间、参数、日志箱、设备序列号、监控面板，任何一处用 0 起始、另一处用 1 起始，都会产出"差一"的事故（机器人 1 的配置发给了 0 号）。把"物理编号 = 命名空间编号 = 参数编号"当成不可协商的约定写进规范，比事后对表便宜得多。补零（robot01）只在编号会超过 9 台时使用，避免字典序错乱。

关键代码与解读

片段 1：名字展开的可视化，用 API 亲眼看一遍

class NameDemo(Node):
    """把三类名字的展开结果打印出来：排查命名问题的第一课。"""
    def __init__(self):
        super().__init__("scanner", namespace="robot3")   # 节点全名 /robot3/scanner
        # resolve_topic_name 用的是与创建端点完全相同的解析规则
        self.get_logger().info(self.resolve_topic_name("scan"))
        # 输出 /robot3/scan：相对名跟随命名空间
        self.get_logger().info(self.resolve_topic_name("~/debug"))
        # 输出 /robot3/scanner/debug：私有名挂在节点名之下
        self.get_logger().info(self.resolve_topic_name("/fleet/map"))
        # 输出 /fleet/map：绝对名不受命名空间影响
        self.get_logger().info(f"namespace={self.get_namespace()}")

解读：这段 8 行的小工具值得放进你的调试工具箱。名字问题（"为什么收不到"）最常见的判断是"它到底展开了没有、展成什么"，用 resolve_topic_name 打印两侧端点名，比猜快得多。注意 resolve_topic_name 与真正创建发布者时使用同一套解析，打印结果即事实本身，不存在近似。类似地有 resolve_service_name（服务与动作同理）。

片段 2：节点代码，零硬编码的名字纪律

class LidarNode(Node):
    """雷达节点：全部资源用相对名/私有名，代码里不出现任何 robotN 字面量。"""
    def __init__(self, robot_id):
        # 身份只进两处：命名空间与参数；其余名字全部随身份自动展开
        super().__init__("lidar", namespace=f"robot{robot_id}")
        self.declare_parameter("publish_rate", 10.0)      # 私有参数：挂在 /robotN/lidar 下
        rate = self.get_parameter("publish_rate").value
        # 相对名 "scan"：在 robot1 上展开 /robot1/scan，robot2 上 /robot2/scan
        self.pub = self.create_publisher(LaserScan, "scan", QoSProfile(depth=5))
        # 私有名 ~/self_test：展开为 /robotN/lidar/self_test，天然防跨机重名
        self.srv = self.create_service(Trigger, "~/self_test", self.on_self_test)
        self.timer = self.create_timer(1.0 / rate, self.tick)

    def tick(self):
        msg = LaserScan()
        msg.header.stamp = self.get_clock().now().to_msg()   # 时间戳：对接下游融合
        self.pub.publish(msg)                                # 数据流保持最薄

    def on_self_test(self, _req, resp):
        resp.success = True                # 真实实现里在此执行诊断并填充 message
        return resp

解读：（1）整个类里唯一出现身份的地方是构造函数的 namespace，这是"实例化复用"原则的代码形态：20 台机器人的部署差异全部由 launch 注入，代码零分支。（2）自检服务用私有名 ~/self_test，相对名 self_test 会把"这台雷达的自检"暴露成公共资源，与同命名空间里其他"self_test"合并成多对多；私有名把它挂在节点名下，语义与结构一致。（3）参数 publish_rate 声明但由 YAML/launch 覆盖（第 005 章），节点内不写死环境相关的值，这条纪律让同一份镜像能配置出不同机器人。

片段 3：launch，一份代码、四台机器人、一次编写

from launch import LaunchDescription
from launch_ros.actions import Node

def generate_launch_description():
    nodes = []
    for rid in (1, 2, 3, 4):
        # 命名空间是"整个实例"的总开关：话题/服务/参数一起前缀化
        nodes.append(Node(
            package="fleet_sensing",
            executable="lidar_node",
            namespace=f"robot{rid}",              # 展开所有相对名：/robotN/...
            parameters=[{"robot_id": rid,         # 身份参数：供节点内部业务使用
                         "publish_rate": 10.0}],
        ))
        # 机内"安全写入者"同命名空间：它订阅的 cmd_vel 也自动是本机的
        nodes.append(Node(
            package="fleet_base",
            executable="safety_mux",
            namespace=f"robot{rid}",
            remappings=[("cmd_vel_in", "cmd_vel")],  # 内部名到对外名的适配（第 008 章）
        ))
    # 车队级调度台：故意不加命名空间，它工作在 /fleet/... 与各 /robotN/...
    nodes.append(Node(package="fleet_ops", executable="dispatcher"))
    return LaunchDescription(nodes)

解读：（1）循环里每个 robotN 实例收到同一份代码、不同的命名空间与参数，这就是"1 份代码 → N 台机器人"的机制本体。扩到 20 台只是把元组写长，无需复制 20 个文件。（2）调度台节点故意不设命名空间：它要跨机器人工作，让它工作在根命名空间下、用绝对名/重映射表达跨机引用，语义最清晰，"谁在哪一层工作"本身就是架构的一部分。（3）remappings 出现在这里预告了下一章：安全选择器内部叫 cmd_vel_in，对外期望接受标准 cmd_vel，重映射把"内部实现名"与"外部契约名"解耦。

片段 4：CLI，按命名空间盯着看

# 命名空间的验证工具：从节点全名到话题前缀，逐个确认"展成什么了"
ros2 node list                       # 应看到 /robot1/lidar ... /robot4/safety_mux
ros2 node info /robot1/lidar         # 检查该节点实际持有的端点全名（展开后的）
ros2 topic list | grep "^/robot1"    # 按前缀分簇阅读：一台机器人的全部话题
ros2 topic list | grep -v "robot"    # 非机器人前缀的"漏网"话题：排查未隔离资源
# 关键验证：任意两台机器人的同名话题必须展开为不同全名
ros2 topic info /robot1/scan --verbose   # 发布者应为 /robot1/lidar，出现别的发布者即异常
ros2 node list | sort | uniq -d          # 重复全名检测：同一名字出现两次即冲突嫌疑

解读：这段命令是部署后的"命名验收"。node info 看单个实例、topic list 加前缀过滤看全局分簇：如果 grep -v robot 输出里出现 /cmd_vel 这样没有前缀的话题，基本可以断定某个节点漏了命名空间（或写死了绝对名），未隔离资源在多机器人系统里是定时炸弹，因为第二台机器人上线时它的同名话题会与之合并。把这条检查写进上线清单，能拦住大量"一上线就串线"的事故。

常见坑

  • 组件代码写死绝对名：create_publisher(Twist, "/cmd_vel") 在单机测试一切正常，部署第二台机器人时两台互抢指令。修复：通用组件只用相对名；跨机引用集中管理（桥接节点或重映射）。
  • 漏设命名空间导致话题合并：两台机器人的 /drive 话题同名，订阅者收到两家混合数据（表现为"里程计闪变、控制抖动"）。修复：部署后跑"重复全名自检"；把命名空间注入写进 launch 模板，手工敲迟早会漏。
  • 私有名与相对名混用错位：想给节点自己的调试流用 debug（相对名），结果和同命名空间另一个节点的 /robot1/debug 撞名。修复：节点私有资源一律 ~/xxx。
  • 命名风格不统一：robot_1、Robot1、robot1 混用，CLI 过滤与脚本扫描全失效。修复：写进规范的"唯一写法"（本章规范表），评审时查。
  • 把命名空间当权限用：以为加了前缀就"别人访问不了"。事实上同域任何节点都可订阅。需要真隔离请用 Domain 或 DDS 安全（第 073 章）。

练习与思考

  1. 手算展开：节点 planner 的命名空间是 /fleet/robot7，写出以下名字的展开结果：path、~/goal_marker、/fleet/task、debug/log。再写出节点全名。★
    提示
    /fleet/robot7/path；/fleet/robot7/planner/goal_marker；/fleet/task；/fleet/robot7/debug/log。节点全名 /fleet/robot7/planner，私有名和相对名都以"节点视角"展开，只是挂载点不同。
  2. 把片段 3 的调度台节点也加上 namespace="fleet_ops"，预测哪些链路会断、哪些不受影响，并解释为什么"跨机组件不设命名空间"是更省心的约定。★
    提示
    调度台内部的相对名全部前缀化为 /fleet_ops/...，跨机订阅若用绝对名不受影响、若用相对名全部找不到。约定：跨机组件在根命名空间工作，用绝对名表达目标。
  3. 设计题：为"3 台机器人 + 1 个中央调度台 + 1 个日志汇聚节点"写一份完整命名规范（至少 12 个名字：话题/服务/动作各类都有），并指出其中哪些必须用绝对名、为什么。★★
    提示
    机器人私有的一律相对名；调度台发布的 /fleet/task、/fleet/map 用绝对名（跨机共享）；日志汇聚依赖各机的 /rosout 与体检话题（第 018 章）。绝对名的判断标准只有一个：消费方不是"本机"。
  4. 推演事故：4 台机器人忘了加命名空间，全部发布 /odom 并全部控制话题 /cmd_vel。写出至少三种可观察的异常现象（从遥控台视角与机器人视角），并说明为什么"日志里没有报错"。★★★
    提示
    遥控台发一条指令四台齐动；监控端 odom 话题频率 ×4 且位置跳变；融合算法漂移。DDS 的 N:M 匹配是"合法操作"，不是错误，这正是静默故障的含义。
  5. 设计"命名自检脚本"：扫描当前计算图，检查 (a) 每个节点是否在预期前缀下；(b) 是否存在重复全名；(c) 是否有未隔离的"裸名字"。写出检查项、误报来源与处理顺序。★★★
    提示
    用 get_node_names 与 get_topic_names_and_types 遍历；"裸名字"白名单要包含 /rosout、/parameter_events、/clock 等系统话题，否则误报漫天。顺序：重复名 > 越界前缀 > 裸名字。

小结

  • 三类名字：相对名跟随命名空间、私有名挂节点、绝对名无视环境；展开后的全名才是匹配依据。
  • 代码纪律：组件内零身份硬编码，只用相对名与私有名；身份由 launch 的命名空间与参数注入。
  • 命名空间防串线不防访问：系统边界用 Domain，系统内分工用命名空间。
  • 分层 3–4 层为宜，编号与物理机器人严格一致，车队级资源独立成 /fleet 支。
  • 部署后必查：重复全名、越界前缀、未隔离裸名字，三类问题各对应一类经典事故。
  • 下一章深入"改写"机制：话题重映射，让内部实现名与外部契约名彻底解耦。
