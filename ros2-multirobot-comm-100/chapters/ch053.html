第三篇 · 协同控制与任务协同

第 053 章：多机器人协同搜索与救援

发现目标只是第一步：用双确认过滤误报、按存活价值衰减排救援优先级、把有限的中继机器人放到最需要信号的位置，把搜索升级成一条会调度、会取舍的救援流水线。

  • 主题：任务协同 / 搜索救援（SAR）
  • 关键机制：双确认、价值衰减调度、能力匹配、通信中继选址
  • 预计学时：65 分钟
  • 前置章节：第 052 章

学习目标

  • 理解搜索救援的任务栈：搜索、确认、救援执行、通信中继四类任务的差异与依赖关系。
  • 掌握价值衰减模型 V(t) = V0·e−t/τ 与"边际价值/时间"贪心调度，理解它与静态任务分配的区别。
  • 会设计双确认机制：确认者规则、确认超时、误报处理与状态机迁移。
  • 能实现异构能力匹配：任务需求（requires）与机器人能力（caps）的集合判定，以及"确认对"的互斥约束。
  • 会用贪心覆盖法做通信中继选址，并说清中继资源与搜救资源之间的权衡。

背景与动机

052 章的搜索结果是一张概率地图和一个"疑似发现"的事件。搜救任务到此才刚开场：一个传感器告警可能是真人，也可能是一只塑料袋；真目标需要按紧急程度排序；幸存者需要物资投送或引导；废墟里的通信黑区让所有协调都蒙上一层阴影。把这几步串起来的系统，才配得上"救援"二字。

本章与 052 的区别在于"从信息到行动"：052 优化的是发现时间，本章优化的是行动的价值，同样的队伍、同样的地图，谁先被救、怎么确认、中继放哪里，决定了救援行动的成败。这套"任务生成 → 排序 → 匹配 → 执行 → 回报"的流水线，与 066–070 章的任务分配体系直接衔接，本章是它的第一个完整实例。

核心原理

1. 任务栈：四类任务，四个依赖层

搜救场景里的"任务"不是一种：搜索任务由 052 章的信念地图驱动；确认任务在疑似发现处生成，要求第二名机器人到场核实；救援任务在确认后升级，需要对应能力（载重、担架、机械臂）；中继任务属于通信基础设施，服务于以上所有任务。依赖关系是一条链：搜索 → 疑似 → 确认 → 救援，同时中继任务可以被视为"持续服务型任务"（没有终点，只有位置）。调度器要处理的正是这条链上的资源分配：谁去确认、谁去救援、派几台去做中继。

2. 价值衰减：搜救与普通任务分配的本质差别

普通任务分配（066 章）的收益是静态的：送到货、巡检完，早 5 分钟晚 5 分钟差别不大。搜救不同：目标的价值随时间衰减，被困者的生存概率、泄漏源的扩散速度，都让"晚到的救援"价值大打折扣。用指数模型刻画：

Vi(t) = Vi,0 · e−(t − ti,0)/τi ti,0 为任务生成时刻，τi 为特征时间（示例：人员 τ = 300 s，设备 τ = 1800 s）

调度目标变为最大化"期望收获价值"：Σ Vi(完成时刻)。贪心的排序键是边际价值 / 预计耗时：单位时间能挽回多少价值，比单看"价值"或"距离"更完整。τ 越小（越紧急）的任务越优先；离得近的任务也因为"损耗少"而获得加权。这个键的另一个好处是自然处理溢出：当所有任务都来不及救时，队伍会自动集中到少数价值最高的任务上，平均撒开在排序里自然出局，这正是有限资源下最理性的行为。

3. 双确认：把误报挡在执行之前

传感器告警的误报率在废墟环境中可以高达 30%：热源、反光、运动尘埃都会触发。直接按告警派救援队，等于把稀缺资源扔进赌局。双确认机制是行业标配：

  • 确认者必须是另一台机器人：发现者自己复看无意义（传感器故障往往系统性发生、具有重复性）。
  • 两次独立检测才升级：两台的传感器类型、视角不同，联合误报率是单台误报率的乘积量级（0.3 × 0.3 = 0.09），但前提是两次检测独立，因此不要用同型号机器人在同一位置的复检。
  • 确认超时兜底：长时间无人确认的疑似点不能消失，要重排队列（可能所有机器人都忙）；反之确认任务超时 3 分钟未派出的疑似点应降权（大概率误报或已漂移）。

确认任务本身也消耗资源：一台机器人从搜索切到确认，意味着搜索力量变少。所以确认半径要小（只派最近的一台）、确认动作要快（到点拍照 15 s 级）。是否值得双确认取决于误报代价与资源紧张度的比值，这是可以算的：误报一次的代价（浪费的救援时长 × 队伍价值）对比确认一次的代价（15 s 的搜索损失 + 路程）。

4. 能力匹配与任务认领唯一性

救援任务带能力需求：requires = {载重 ≥ 2 kg} ∪ {机械臂} 之类；机器人带上能力集合 caps，承接条件是 requires ⊆ caps。这是集合判定：能力不满足即硬性出局，再近也不能派。确认任务则多一条互斥约束：确认者不能是发现者；如果用两台机器人各确认一次，两台之间也要互不相同。硬约束与软目标（价值、距离）混在同一优化里时，工程上的标准做法是"先筛可行集，再对可行集排序"：把硬约束做实，贪心只在可行集中工作。

任务认领的唯一性用 050 章的同样机制：任务带 assignees 列表与 TTL，收到认领即写入，重复认领按"先认领者优先 + 距离平局"仲裁；任务完成后广播 done 供全队关闭。

5. 通信中继：把"信号覆盖"当成一种救援物资

废墟结构的信号衰减通常是非均匀的：某些区域完全黑区、某些区域勉强可用。中继机器人的作用是放大覆盖，它的选址是一个覆盖问题，与 061 章的覆盖规划同源：给定"需求点集合"（各搜救小队的常用路径、指挥点、疑似目标点）和候选放置位置（通道口、楼梯间），选 k 个位置最大化被覆盖的需求权重。贪心算法每轮选"覆盖未满足需求最多"的位置，简单且近似最优（覆盖函数是子模的，贪心有 1−1/e 的经典近似保证）。

真实系统里中继资源还要和搜救资源竞争：派一台机器人去做中继，等于少一个搜索者。常见策略是"中继优先、但要最省"：先用固定的中继机（专用设备）覆盖主干道，机动中继只补黑区；黑区持续存在才动用搜救机器人兼职。这个取舍没有普适答案，但必须显式建模，把中继任务与搜救任务放进同一个调度器，用统一的边际价值/时间键排序，让"谁去做中继"交给数字决定，取消默认指派。

6. 数值算例：调度排序、确认成本与中继覆盖

排序计算：三个任务分别是人员（V0=100、τ=300 s、已过期 120 s）、设备（V0=80、τ=1800 s、已过期 300 s）、物资（V0=60、τ=600 s、已过期 60 s），耗时估计 60/90/40 s。实时价值：100·e−0.4 = 67.0、80·e−1/6 = 67.7、60·e−0.1 = 54.3；边际价值/时间分别为 67.0/60 = 1.12、67.7/90 = 0.75、54.3/40 = 1.36。绝对值最低的物资任务排到第一，因为它的单位时间收获率最高；设备任务价值还很高（67.7），但 90 s 的长耗时把它压到末位。这个例子说明"按价值排序"与"按价值/时间排序"会给出完全不同的执行顺序，稀缺资源应该跟随后者。

确认成本计算：设一次误报派单的损失为 120 当量、一次确认的成本为 30 当量（路程 + 作业 + 搜索力量损失）、单台误报率 30% 且独立。确认者数量为 k 时的总损失近似为 0.3k × 120 + 30k：k = 1 时 36 + 30 = 66；k = 2 时 10.8 + 60 = 70.8；k = 3 时 3.24 + 90 = 93.2。这组参数下双确认与单确认的总损失接近（70.8 对 66.0），双确认把误报通过率从 30% 压到 9%：再加一层的收益（误报损失再降约 8 个当量）不足以支付第三台机器人的路程成本。你的现场参数不同，结论可能不同，但这张表的算法可以直接套用；把两类成本做成可配置参数，比争论"该确认几次"有效。

中继覆盖计算：走廊长 100 m、每 10 m 一个需求点共 11 个（权重各 1），候选点位在 20 m、60 m、90 m 三处，覆盖半径 30 m。贪心第一轮：20 m 候选覆盖 0–50 m（6 点）、60 m 候选覆盖 30–90 m（7 点）、90 m 候选覆盖 60–100 m（5 点），选 60 m；第二轮把已覆盖点清零后，20 m 剩 3 点、90 m 剩 1 点，选 20 m。贪心解覆盖 10 个点，100 m 处的末端需求没人覆盖；最优解选 20 m + 90 m，覆盖全部 11 个点。贪心覆盖不保证最优（1−1/e 的近似比对应最坏情况约 63%），本例差距是 91% 对 100%；实际做法是贪心起步，再用小规模穷举对候选点少于 10 个的场景做精确校验。

时间压力还有一个乘数：人员目标的 τ = 300 s 意味着每多等 5 分钟，价值只剩 36.8%（e−1）；设备目标同类但衰减慢得多。定期用现场标定更新 τ，把这组曲线挂上调度器监控面板，值班人员能直观看到"救援窗口还剩多少"，比一串原始分数更利于跨岗位沟通。

边界与失效：价值衰减模型最怕"低估任务真实紧迫度"。若所有任务都按同一 τ 处理，紧急任务会被平均化淹没；工程上把 τ 做成按任务类型查表（人员、设备、物资三档起步），并允许指挥端对个别任务手动加大衰减（等价于"插队"），两条通道的动作都记录下来供事后复盘。反过来，插队滥用会让调度器失去量化意义，规定"插队必须填原因码"是便宜的约束。

实现思路与设计

  1. 任务消息：SarTask（task_id、type、pose、value0、tau、t0、requires[]、status、assignees[]、stamp），事件触发 + 1 Hz 重播，Reliable + Transient-local。
  2. 状态机：SEARCH → REPORT（疑似）→ VERIFY（确认中）→ CONFIRMED → DISPATCH（救援执行）→ DONE；误报走 DISMISSED；每个状态有超时与回收规则。
  3. 调度循环：1 Hz 重算；对每个"未满员"任务 × 每台空闲机器人算分数（能力硬筛 + 边际价值/时间），贪心配对；已派出任务不再重复派单。
  4. 中继任务：作为 TYPE_RELAY 任务参与调度，值由"覆盖增益 × 权重"给出；放置候选来自通道拓扑（预先标定的 5–10 个点位）。
  5. 执行与回报：承接后机器人用 046–049 的规划执行；到达、作业、完成各广播事件；任务有最大作业时长（确认 60 s、投送 180 s）防挂死。
  6. 验收：3 台机器人、仿真废墟、12 个目标（含 4 个误报点）：误报派单率（对误报点派出救援的比例）小于 5%；平均确认延迟小于 90 s；价值加权救援完成率大于 80%；中继黑区覆盖率提升大于 60%。

关键代码与解读

片段 1：边际价值/时间贪心派单

import math

def task_score(task, robot, travel_time, now):
    """边际价值/时间；能力不满足是硬约束，直接淘汰。"""
    if not set(task["requires"]).issubset(robot["caps"]):
        return -1.0                            # 能力硬筛：再近也不能派
    value = task["value0"] * math.exp(-(now - task["t0"]) / task["tau"])
    cost = max(travel_time + task["work_time"], 1.0)     # 防除零
    return value / cost

def dispatch(tasks, robots, dist_fn, now):
    """贪心派单：每轮选全局分数最高的 (任务, 机器人) 配对。"""
    assigns = []
    free = {r["id"]: r for r in robots}
    pending = [t for t in tasks if t["status"] == "pending"]
    while pending and free:
        best_t, best_r, best_s = None, None, 0.0
        for t in pending:
            for rid, r in free.items():
                tt = dist_fn(r["pose"], t["pose"]) / max(r["v_max"], 0.1)
                s = task_score(t, r, tt, now)
                if s > best_s:
                    best_t, best_r, best_s = t, rid, s
        if best_t is None:
            break                              # 剩余组合都不可行
        assigns.append((best_t["id"], best_r))
        free.pop(best_r)
        pending = [t for t in pending if t is not best_t]
    return assigns

解读：这段代码有三个值得放大的设计。(1) 分数是比值不是加权和：加权和需要手工平衡"价值"与"时间"的量纲，而比值（单位时间的价值收获）物理意义明确、无需调参，且天然实现"紧急任务优先"。(2) cost 把作业时长 work_time 一并计入，单算路程会低估：一个 15 s 的确认任务与一个 180 s 的投送任务，若不把作业时长算入成本，调度器会误判后者"更快完成"。(3) 贪心每轮重新全局扫描：任务价值随时间衰减，配对顺序随时间变化，这是一个持续重评估的滚动过程，"先到先服务"在这里不成立。计算量 O(任务 × 机器人) 在几十个量级完全可忽略。

片段 2：双确认任务状态机

def step_task(task, event, robot_id):
    """任务状态机：SEARCH -> REPORT -> VERIFY -> CONFIRMED -> DISPATCH -> DONE。"""
    st = task["status"]
    if st == "SEARCH" and event == "detected":
        task["reporter"] = robot_id
        task["status"] = "REPORT"              # 疑似：等待第二方核实
    elif st == "REPORT" and event == "confirm":
        if robot_id == task["reporter"]:
            return task                         # 发现者本人不能充当确认者
        if robot_id not in task["confirmers"]:
            task["confirmers"].append(robot_id)
        if len(task["confirmers"]) >= 2:         # 两次独立确认才升级
            task["status"] = "CONFIRMED"
    elif st == "REPORT" and event == "dismiss":
        task["status"] = "DISMISSED"            # 核实为误报：关闭并记录
    elif st == "CONFIRMED" and event == "assigned":
        task["status"] = "DISPATCH"
    elif st == "DISPATCH" and event == "done":
        task["status"] = "DONE"
    return task

解读：状态机刻意把"确认"做成计数器：confirmers 列表要求两台不同的机器人（含 not in 去重），"发现者排除"写死在迁移条件里。这些微小约束对应真实的失效模式：同一台机器人的传感器重复告警、或发现者绕一圈回来"确认自己"，都会让误报过滤形同虚设。DISMISSED 状态不要直接删除任务，保留记录用于统计误报率与"哪个区域容易出误报"（例如果断区域反光严重，可以调整检测灵敏度）。超时逻辑放在调用方（每个状态配超时表），状态机本身保持纯函数，任何输入不产生异常，这种"无副作用迁移"让仿真回放与单元测试都容易得多。

片段 3：中继选址贪心

import numpy as np

def place_relays(needs, candidates, radius=30.0, k=1):
    """中继选址：每轮选覆盖未满足需求权重最大的候选点。"""
    needs = np.array(needs, dtype=float)       # (x, y, weight) 需求点
    chosen = []
    for _ in range(k):
        best, best_gain = None, -1.0
        for cx, cy in candidates:
            d = np.hypot(needs[:, 0] - cx, needs[:, 1] - cy)
            gain = float(needs[d <= radius, 2].sum())      # 覆盖需求权重
            if gain > best_gain:
                best, best_gain = (cx, cy), gain
        if best is None:
            break
        chosen.append(best)
        d = np.hypot(needs[:, 0] - best[0], needs[:, 1] - best[1])
        needs[d <= radius, 2] = 0.0            # 已覆盖需求清零，下一轮补死角
    return chosen

解读：中继链路遵循"两跳质量减半"的粗略规律（每跳吞吐与延迟都恶化），所以半径 30 m 是宁小勿大的工程值，覆盖判据用的是保守值，实际链路余量留给墙体衰减。贪心的正确性依赖覆盖函数的子模性（加一个中继的边际收益随已选中继增多而递减），它保证贪心解不差于最优解的 63%（1−1/e），对工程来说完全够用。真实系统里候选点不是任意的：中继要放在有电源、有净空、在通路上方便机器人到达的位置，所以候选集合来自预先勘定的点位清单，贪心只负责"选哪几个"。

常见坑

  • 假阳性直接派救援：一个热源误报让整队扑空，真正的目标延迟被救。修复：双确认（且确认者与发现者不同源）；把误报率做成指标长期观测。
  • 价值模型不衰减：调度器把一小时前的旧任务与刚生成的任务当同等价值，资源被历史任务拖住。修复：价值随 t 衰减（τ 分类型）；旧任务超过特征时间自然沉到队尾。
  • 中继机器人被顺手派去搜救：角色冲突导致黑区扩大。修复：中继任务与搜救任务进同一调度器但用独立资源池；兼职中继的任务加锁定期（做完中继 5 分钟不能转岗）。
  • 任务重复认领：两台机器人奔赴同一目标，另一目标无人认领。修复：唯一认领 + TTL 回收；认领冲突用"先到 + 距离"确定性仲裁（复用 050 章机制）。
  • 断连任务无回收：执行中的机器人失联，任务永久挂起。修复：任务带心跳（执行者 5 s 上报进度），15 s 无进度即视为失败并重新入队；同时把失联本身作为"疑似新目标"提醒其他机器人留意。

练习与思考

  1. 三个任务：人员（V0=100，τ=300 s，生成于 120 s 前）、设备（V0=80，τ=1800 s，生成于 300 s 前）、物资（V0=60，τ=600 s，生成于 60 s 前）。当前时刻各自的实时价值是多少？按"价值/耗时"（耗时分别 60/90/40 s）排序，与按纯价值排序有何不同？★
    提示
    实时价值：100e−0.4≈67、80e−0.167≈68、60e−0.1≈54。比值：1.12 / 0.75 / 1.36，物资任务因耗时可观而反超，说明调度要同时看紧迫与代价。
  2. 把确认者数量从 2 降为 1、或升为 3，分别计算误报通过率（设单台误报率 30%，独立）与确认开销（团队搜索时间损失）；给出让决策最小化"总损失"的判据式。★★
    提示
    1 台：0.3；2 台：0.09；3 台：0.027。开销随确认次数线性上升。判据式：误报通过率 × 误报成本 + 确认次数 × 确认成本，取最小值。
  3. 设计一个"确认任务与搜索任务抢资源"的仿真：2 台机器人、1 个疑似点 + 持续搜索流。观察确认优先策略与搜索优先策略下的加权完成率，给出你的策略阈值。★★
    提示
    确认优先在疑似点真实性高时收益大；搜索优先适合误报极多的场景。用"疑似点真实率"做敏感度扫描，找到策略翻转点。
  4. 中继贪心的近似比是 1−1/e。构造一个覆盖问题实例，说明贪心为什么不是最优；再说明什么条件下贪心恰好最优。★★★
    提示
    经典反例：一个大覆盖集合与多个小集合交错，贪心先选大集合后剩余收益低；当集合互不相交（覆盖不重叠）时贪心最优。
  5. 为 6 台异构机器人（2 台带机械臂、2 台高续航、2 台中继）写完整的 SAR 运行手册：任务类型与状态、调度键、确认与超时、断连回收、验收指标。要求给出至少三个"角色冲突"场景及处置。★★★
    提示
    角色冲突例：机械臂机器人被派中继、中继被派确认、全员扑向同一确认点。处置核心是分组资源池 + 任务类型白名单。

小结

  • SAR 任务栈：搜索、确认、救援、中继四类任务；依赖链搜索 → 确认 → 救援，中继提供服务型支撑。
  • 价值指数衰减改写了调度：排序键用"边际价值/时间"，紧急与近的距离都自动加权，溢出时自然集中资源。
  • 双确认把误报挡在执行前：确认者必须独立于发现者，联合误报率是乘积量级；确认任务本身也要调度与超时。
  • 能力匹配是硬约束、认领需要唯一性与 TTL；中继选址用贪心覆盖（子模近似保证 1−1/e）。
  • 下一章处理会动的目标：多机器人目标跟踪，估计、融合与观察者站位，让队伍盯住一个移动目标。
