第 008 章：话题重映射实现机器人间通信

不改一行代码，让第三方遥控节点把指令发到 2 号机器人、让跟随节点去读 1 号机器人的里程计：重映射就是部署期的"电话转接"。

  • 主题：通信基础 / 部署编织
  • 关键机制：重映射规则、按展开名匹配、运行时重映射、与桥接节点的分工
  • 预计学时：50 分钟
  • 前置章节：第 007 章

学习目标

  • 理解重映射（remap）的本质：对"已展开名字"的改写，让节点内部实现名与对外契约名彻底解耦。
  • 掌握三种施加渠道：launch 的 remappings、命令行 --ros-args -r、以及代码内建（了解代价，少用）。
  • 会算"匹配语义"：相对名/绝对名写在规则两侧时如何按节点环境展开，判断一条规则为什么生效或为什么不生效。
  • 会用重映射完成典型多机器人接线：第三方节点的输出定向到指定机器人、跨机订阅用本机名字访问、标准动作改名。
  • 能分清新三件事的边界：命名空间（批量前缀）、重映射（名字改写）、桥接节点（数据加工），该用哪个就用哪个。

背景与动机

多机器人工程里反复出现同一类需求："这个节点不在我手里（第三方包/公司共用组件），但我要让它和我的机器人对话"。比如键盘遥控节点只发布 /cmd_vel，而你的 2 号机器人只认 /robot2/cmd_vel；再比如一个跟随控制器订阅的文章名叫 leader_odom，你想让它读 1 号机器人的里程计。改代码当然可以，但改第三方代码意味着维护一个分叉版本；写桥接节点又要多一个进程、多一份 QoS 与生命周期管理。

重映射提供了第三条路：不改代码，在部署层把名字"转接"掉。它解决的是"接线"问题；数据原样流过，只是换了名字，"加工"不在它的职责内。理解它，你就能把"机器人间通信"这件事从"谁订阅谁"的硬编码，变成 launch 里一份显式、可审计的接线表；也应知道它的边界：只换名字，不换内容。

核心原理

1. 重映射是什么：名字的转接规则

一条重映射规则形如 from:=to：当这个节点要使用名字 from 时，实际使用 to。规则是节点级的，每个节点持有自己的一小张转接表，节点 A 的规则不影响节点 B。图景：给每个进程配一个接线员，凡是它喊出的名字、它要拨的号，接线员都按表转接。

与第 007 章的知识拼起来看：名字先按"命名空间 + 节点名"展开成全名，重映射规则再在这条链路上做改写。规则两侧的名字也按节点的环境展开，写 cmd_vel:=/robot2/cmd_vel 的节点在 /robot2 命名空间下，左侧其实指 /robot2/cmd_vel，结果两侧同指一名、规则空转；而同样一条规则放到无命名空间的遥控节点里，左侧是 /cmd_vel、右侧是 /robot2/cmd_vel，转接成立。这就是"为什么我的 remap 没生效"的第一类答案：规则对不对，取决于它在哪个节点身上、以什么环境展开。

名字处理链：最终名字 = 重映射(展开(命名空间, 节点名, 原始名))；规则两侧同样先展开、后比较、再改写 规则是节点级的，只作用于声明它的那个节点；匹配为精确相等，没有通配符。手算顺序永远是"先展开、后比对"，跳过展开这一步就会得出错误的生效判断

数值算例把处理链走一遍：遥控节点在 /robot2 命名空间下、规则写 cmd_vel:=/robot2/cmd_vel，左侧展开为 /robot2/cmd_vel，与右侧相等，改写后仍是原地名，规则空转，节点发布的数据留在本机；同一个遥控节点去掉命名空间后，左侧展开为 /cmd_vel，改写迁移到 /robot2/cmd_vel，定向成立。判断一条规则是否有效，只需要两次展开加一次比较；部署评审时逐条手算，比上线后发现"接线静默失效"便宜得多。

2. 匹配语义：精确名字，没有通配符

ROS2 的重映射是精确匹配：一条规则替换一个名字。/robot*/odom 这类通配写法来自 ROS1 的习惯，在 ROS2 中不会展开成任何东西，它只是一个"永远不匹配的名字"（静默失效）。需要多个名字转接就写多条规则；需要"一族名字"的批量改写，那正是命名空间与参数化 launch 的职责。

规则对三类原语统一生效：话题、服务、动作都走同一套名字系统，所以 -r set_mode:=/robot2/set_mode 可以为服务改名，动作同理。还有个特殊规则体系用于"节点自身"：__node:=新名 改节点名、__ns:=/新命名空间 改命名空间，它们等效于 launch 的 namespace= 参数，适合在命令行里快速给节点"换身份"。

边界需要说清：重映射只改名字，不改消息类型、不改 QoS、也不改发现身份。两端改名后全名相等、类型一致、QoS 兼容，连接才会建立；改名本身永远无法创造一次本不该发生的匹配，也无法阻止一次本该发生的匹配。排障顺序由此确定：先做名字层面的展开比对（本节的计算），再看端点合同（第 011/012 章的判定矩阵），最后才怀疑网络与中间件。

3. 多机器人场景的四种典型接线

  • 输出定向：第三方发布者只发 /cmd_vel，重映射到 /robot2/cmd_vel，让"标准名字的输出"落到指定机器人的领地里。
  • 跨机读取：机器人 2 上的跟随节点订阅相对名 leader_odom，重映射为绝对名 /robot1/odom，本机代码保持"不知道 leader 是谁"，部署时注入指向。跟随 1 号还是 3 号，只改 launch。
  • 接口适配：内部实现名（cmd_vel_in）与对外契约名（cmd_vel）不一致时，用重映射把契约名接进来，不改组件代码。
  • 动作/服务改名：把通用动作名 navigate 定向到 /robot3/navigate（动作名替换会作用于它内部的全部端点，验证时看 ros2 action info）。

这四种接线的共同点：数据不需要加工。一旦需要改内容（单位换算、坐标系变换、降频、过滤），重映射就无能为力了，那是桥接节点的领域，本章最后一节给判断树。

接线的规模算例：把一台遥控端的输出定向到指定机器人，星型接法只需 1 条规则；若要用重映射把 N 台机器人接成两两可达的直连，则需 N × (N − 1) 条定向规则，4 台为 12 条、20 台为 380 条，管理成本随台数平方增长。跨机拓扑要收敛成星型或经桥接节点转发：星型 20 台只需 19 条规则，每条的含义一眼可查，新增一台也只加 1 条。

全互联定向规则数 = N × (N − 1)；星型定向规则数 = N − 1 4 台：12 条对 3 条；20 台：380 条对 19 条。平方增长是拓扑设计的硬约束，也是"重映射管接线、拓扑管规模"的分工来源

4. 施加渠道与"隐形的代价"

重映射可写在三个地方：launch 的 remappings=[]（推荐：与部署绑定、可评审）、命令行 --ros-args -r from:=to（调试快、不持久）、代码内建（Node(..., remappings=[...]) 构造参数，写进代码就丧失了灵活性，除封装内部自用外不推荐）。

重映射最大的代价是隐形：打开节点源码，你看到 cmd_vel；打开计算图，数据却流在别处。跳两层工具才能对上。因此有两条纪律：（1）全部重映射集中在 launch 文件里，随部署文档评审；（2）上线后必须用 ros2 node info 看"实际端点全名"做验收；"规则应该生效"只是假设。

施加渠道生效范围持久性可审计性适用场景
launch 的 remappings被编排的该类节点实例进版本库，长期有效好：随部署评审可见正式接线，默认选择
命令行 --ros-args -r仅本次启动的进程进程退出即消失差：需要另行记录现场急救、临时验证
代码内建 remappings该程序编译出的所有实例随版本固化差：隐藏在实现里封装库内部的特殊需要，常规系统避免

5. 与命名空间、桥接节点的分工

工具改什么典型场景不做的事
命名空间节点全部相对名的前缀同构组件的批量实例化不改单个名字、不做跨机定向
重映射单个名字（含服务/动作）接线与适配、跨机指向不加工数据、无通配
桥接节点数据本身换算、过滤、聚流、协议转换费用高：多一个进程与生命周期

选择顺序：能用命名空间解决就不写重映射；能用重映射解决就不写桥接节点；非做数据加工不可才上桥接。这个"代价递增"的顺序能让系统里的活动部件最少。

桥接的代价可以定量看：每转发一条消息要经历反序列化、加工、再序列化与一次重新发布，同机进程间直转通常在 0.1–1 ms 量级，跨机转发还要再加一个网络单程；同时多出一个进程、一份 QoS 配置与一套生命周期管理。对比重映射的零额外数据路径（只改名字、不碰数据），"能用重映射绝不上桥接"就有了数字依据，不再是风格偏好。

实现思路与设计

以"双机跟随 + 键盘遥控"demo 为例，需求与解法对照：

需求手段规则/机制为什么不用别的
键盘节点（第三方）的 /cmd_vel 只发给 2 号重映射teleop: /cmd_vel:=/robot2/cmd_vel改第三方代码要维护分叉；桥接节点纯属浪费
2 号的跟随节点读 1 号的里程计重映射follow: leader_odom:=/robot1/odom让"跟随谁"从代码常量变成部署参数
同一键盘节点也要能直接驱动单机 demo重映射另一份 launch：/cmd_vel:=/robot1/cmd_vel同一份代码、两套接线：重映射把差异收进部署层
2 号的估计位移与 1 号的监控数据，频率一致、单位一致无需处理直接引用数据间无加工：重映射足够
1 号里程计的坐标系要转到 2 号的框架桥接节点坐标变换 + 转发重映射不做加工，必须上有逻辑的进程（第 024 章）

部署验收三件事：（1）launch 评审看见全部接线；（2）上线后逐节点 node info 核对实际端点；（3）断连演练，把 1 号机器人的 odom 停掉，确认 2 号跟随节点正确进入"无数据"处理，僵尸等待是缺陷。

接线评审清单三项，逐条写进部署文档：每条规则在目标节点的环境下手工展开，确认左名与右名不相等（不等才可能生效）；每条规则写明"为什么用重映射，而不用命名空间、也不使用桥接节点"的一句话理由；全部规则只出现在 launch 文件中，命令行与代码内建保持为零。清单过一遍的成本很低，拦下的却是空转规则、方向写反、以及"改了发布端忘了订阅端"这几类最常见的静默事故。

设计决策：为什么"跟随对象"用重映射注入，参数拼接不好吗？

用参数也能做：给跟随节点传 leader_id=1，代码里拼出 /robot{leader_id}/odom 再订阅。问题在于拼接发生在代码里，名字的完整链路（第 007 章）与 QoS、类型校验都藏在运行时；而重映射让"2 号的跟随节点连接到 /robot1/odom"这件事在图上是可见、可检查的显式事实。用重映射的判据：凡是"整条查询/数据流指向另一个实体"的，优先让它在部署层显式可见；参数更适合"数值型、会影响逻辑判断"的配置（限速、周期、阈值）。

关键代码与解读

片段 1：launch 接线表，双机跟随与遥控的全部转接

from launch import LaunchDescription
from launch_ros.actions import Node

def generate_launch_description():
    # 键盘遥控（第三方节点）：输出定向，它只知道 /cmd_vel
    teleop = Node(
        package="teleop_twist_keyboard",
        executable="teleop_twist_keyboard",
        name="teleop",
        # 左侧相对名在根命名空间展开为 /cmd_vel，右侧绝对名指向 2 号机器人
        remappings=[("/cmd_vel", "/robot2/cmd_vel")],
    )
    # 2 号的跟随节点：跨机读取，leader 是谁由这条规则注入
    follower = Node(
        package="fleet_follow",
        executable="follow_node",
        namespace="robot2",                       # 瞬时话题自动变成 /robot2/...
        parameters=[{"gap": 1.5}],                # 数值型配置走参数（第 005 章）
        # 内部契约名 leader_odom 重映射到 1 号的绝对话题：部署注入依赖关系
        remappings=[("leader_odom", "/robot1/odom")],
    )
    return LaunchDescription([teleop, follower])

解读：（1）两条规则的"方向感"值得咂摸：遥控节点把"大家通用的名字"定向到具体机器人（收束），跟随节点把"角色名"指到具体机器人（注入依赖）。（2）注意 teleop 没有命名空间，它刚要发布 /cmd_vel，这条相对名在根环境下展开，规则正好命中；若给它加了 namespace="robot2"，它会先变成 /robot2/cmd_vel，规则就该写成匹配这个全名，第 1 节的"规则在谁身上展开"在此落成实例。（3）parameters=[{"gap": 1.5}] 与重映射的分工同框展示：数值配置走参数、名字接线走重映射，两者各归其位。

片段 2：节点代码，为被重映射而设计

class FollowNode(Node):
    """跟随控制：名字全部用"角色名"，具体指向留给部署注入。"""
    def __init__(self):
        super().__init__("follow")                # 命名空间由 launch 注入：/robot2/follow
        self.declare_parameter("gap", 1.5)
        # 角色名 leader_odom：单机 demo 里可以简单重映射到 /robot1/odom，
        # 也可以一步指向仿真话题；代码不知道也不关心 leader 是谁，这是关键设计
        self.sub = self.create_subscription(
            Odometry, "leader_odom", self.on_leader, QoSProfile(depth=5))
        # 自己的速度指令：相对名 cmd_vel 展开为 /robot2/cmd_vel，天然发给本机底盘
        self.pub = self.create_publisher(Twist, "cmd_vel", QoSProfile(depth=5))
        self.leader = None

    def on_leader(self, msg):
        self.leader = msg                         # 只缓存最新的 leader 状态
        self.tick()                               # 演示用：真实系统应由定时器驱动

    def tick(self):
        if self.leader is None:
            return                                # 无 leader 数据：保持静止（安全默认）
        err = self.leader.pose.pose.position.x - self.get_parameter("gap").value
        cmd = Twist()
        cmd.linear.x = max(min(0.6 * err, 0.5), -0.3)   # 简单比例限幅控制
        self.pub.publish(cmd)

解读：（1）不少团队先在代码里写死"订阅 /leader/odom"，之后每换一个 leader 就改一次代码、发一次版本，这段代码示范了正确的姿势：代码里只有"角色"，"演员"在 launch 里指定。这一条原则会一路贯穿到第三篇的编队控制，那时"跟随对象"由任务分配动态决定。（2）处理逻辑放在 tick()，订阅回调只做缓存，延续第 002 章的"数据面短"原则，也便于以后把回调换成定时器驱动。（3）无数据时保持静止是"失效安全"的默认：多机器人系统里，"没收到 leader 就默认直行"是最经典的送命设计。

片段 3：命令行重映射，调试与快速试验

# 不给机器人 2 写任何 launch：直接把键盘遥控接到 /robot2/cmd_vel
ros2 run teleop_twist_keyboard teleop_twist_keyboard --ros-args -r /cmd_vel:=/robot2/cmd_vel
# 用 __ns 给节点换"住址"：它所有的相对名瞬间变成 /robot3/...
ros2 run fleet_sensing lidar_node --ros-args -r __ns:=/robot3 -p publish_rate:=20.0
# 动作也能重映射：把通用名 navigate 指向 3 号机器人的动作
ros2 run fleet_ops dispatcher --ros-args -r navigate:=/robot3/navigate
# 验证：节点实际持有的端点全名才是事实，规则表只是预期
ros2 node info /teleop
# 若规则没生效：先看两边全名是否真的相等（相对名/绝对名展开问题）

解读：命令行重映射是"应急接线"的理想工具：远程 SSH 进去，五秒钟把遥控接对，不用动仓库。__ns 与 __node 这两个特殊规则值得记住，它们让"给节点换住址/换名字"变得像改一行参数。但注意最后两条注释的纪律：命令行改动随进程消失、不留痕迹，只适合调试；最终接线必须回到 launch。ros2 node info 是唯一的验收标准，重映射错了不会报错，只会"端点是别的名字"。

常见坑

  • 规则两侧展开后同指一名：在 /robot2 命名空间的节点上写 cmd_vel:=/robot2/cmd_vel，左侧也展开成 /robot2/cmd_vel，规则空转，行为与没写一样。修复：先问"这个节点在哪一层"，再决定左右两侧怎么写（或统一用绝对名写规则）。
  • 从 ROS1 带来通配符习惯：写 /robot*/odom:=odom 期望批量匹配，ROS2 精确匹配，规则静默失效。修复：一条一个名字；"一族名字"用命名空间机制。
  • 只改一侧：把发布端重映射到 /robot2/cmd_vel，却没确认订阅端（安全层）订阅的就是这个名字。修复：上线前跑"发布者视角 + 订阅者视角"双向核对（topic info --verbose 看两端）。
  • 重映射藏在代码里：某节点构造函数里写死 remappings=[("cmd_vel","/robot2/cmd_vel")]，部署到 robot1 后行为诡异，而 launch 里看不到任何线索。修复：纪律，重映射只允许出现在 launch（与部署评审同源）。
  • 用重映射做数据加工：把单位不同的两个话题"接起来"（如 deg 与 rad），数据能流但控制全错。修复：认清边界，内容加工属于桥接节点；重映射只换名字。

    不生效：左侧展开为 /robot2/cmd_vel 与右侧相同，空转。修法一：去掉规则（本来就对了）；修法二：改左侧为匹配展开后的名字并把右侧指向别处。
  2. 快答题：下列需求各用什么机制，(a) 把 4 台机器人的雷达帧统一改名；(b) 让跟随角色动态指向任意 robotN；(c) 把 2 号相机的图像从 BGR 转 RGB 再转发；(d) 给一组同构节点加统一前缀。★
    提示
    (a) 逐条重映射（或统一改用命名空间）；(b) 重映射由 launch/参数化注入；(c) 桥接节点（数据加工）；(d) 命名空间。
  3. 设计题：用重映射实现"一键切换跟随对象"：写一份 launch，通过一个 launcher 参数 leader_id（取 1–4）生成 leader_odom:=/robotN/odom 的规则。说明为什么用重映射比用参数拼接好。★★
    提示
    launch 里用 Python 字符串拼规则即可（launch 本身是代码）；好与更好：重映射让图上的连接显式可查、类型与 QoS 校验在连接层完成；参数拼接的错误只能在运行时暴露。
  4. 排障题：遥控键盘发出 /cmd_vel，但 2 号底盘毫无反应。topic info /cmd_vel 显示发布者 1、订阅者 0；topic info /robot2/cmd_vel 显示订阅者 1、发布者 0。定位问题并写出修复规则。★★
    提示
    重映射缺失：发布端从未改道。加 teleop 的 remapping（或反之把订阅端重映射到 /cmd_vel），注意两端只能改一边，同时改两边又会绕回原点。
  5. 论证题：团队要把"雷达节点的话题改名"写进节点代码（硬编码新名字），放弃 launch 重映射方案。列出至少三条反对理由与一条可能支持的场景。★★★
    提示
    反对：复用性破坏（第 007 章纪律）、接线不可见、单元测试与部署耦合；支持场景：封装库内部确实需要稳定私名时用私有名，那也不是"硬编码绝对名"的理由。

小结

  • 重映射 = 对已展开名字的节点级改写；规则两侧都按该节点的命名空间展开，这决定了它生效与否。
  • 精确匹配、无通配符；话题、服务、动作统一适用；__ns/__node 是改身份的特殊规则。
  • 四种接线：输出定向、跨机读取、接口适配、动作改名；共同前提是"不做数据加工"。
  • 接线集中放 launch、随部署评审；上线验收以 node info 的实际端点为唯一事实。
  • 代价递增顺序：命名空间 → 重映射 → 桥接节点；能用前面的绝不用后面的。
  • 下一章把"通信的基础设施"补齐最后一块：时间同步，没有统一时钟，所有跨机数据对齐都是空谈。
