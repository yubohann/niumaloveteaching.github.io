第二篇 · 数据分发与协同感知

第 040 章：阶段项目：协同建图与状态共享

把第二篇的全部机制拧成一个可运行、可验收的系统：3 台机器人共享坐标系与时间轴、协同建图、实时分享状态，并用一组量化指标证明"它真的成了"。

  • 主题：阶段项目 / 系统集成
  • 关键机制：统一坐标与时间、增量地图合并、状态共享、健康监测、验收指标
  • 预计学时：90 分钟（含集成与验收）
  • 前置章节：第 039 章（系统级健康监测与告警）

学习目标

  • 把第 021–039 章的分散机制组织成一张端到端的数据流：谁生产、谁加工、谁消费、用什么 QoS。
  • 完成 3 机器人协同建图系统的集成：统一 world 框架、时间同步、增量地图、状态共享、监控告警。
  • 掌握验收指标的测量方法：地图对齐冲突率、覆盖率增益、状态端到端延迟、带宽与掉线恢复时间。
  • 会运行"故障注入"验收：拔掉一台机器人的网络，验证系统降级与恢复行为。
  • 产出可复现的项目报告：架构图、指标实测表、失败模式清单与改进项。

背景与动机

第二篇从"状态同步"出发，走过大消息传输、坐标与时间、地图、SLAM、感知与融合，最后落到链路可靠性与一致性；第 039 章又把这些机制的状态汇总成了可观测的告警，现在是收网的时候。真实的工程能力不在"懂每个机制"，而在"把它们装进一个系统还让指标达标"：QoS 要在集成时全部对齐、时间基准要统一、地图要增量流动、掉线要能恢复、带宽不能被更新流量打爆。这些只有在系统级才会暴露的问题，正是本阶段项目的训练目标。

项目场景：一个约 40 m × 20 m 的厂房（含办公区走廊），3 台差速轮式机器人，每台带 2D 激光与轮式里程计，同域（Domain 42）、同网段 WiFi，中央有一台网关机运行汇聚与监控。目标：三机协同探索并建立一张全局一致的栅格地图，实时共享状态，全程可监控，且通过量化验收。

核心原理

1. 系统架构：三层数据流

层模块（机器人侧）模块（车队/网关侧）关键数据流
感知与本地估计激光驱动、里程计、本地 SLAM—scan → 本地地图块（第 033 章）
协同层位姿共享（第 021/029 章）、检测共享（第 031/032 章）地图合并/对账（第 027/036 章）、任务状态pose/obs/地图增量（数十 KB/s 量级）
系统层健康探针（第 039 章）、录制（第 037 章）健康聚合、可视化信道（第 038 章）健康摘要（1 Hz）、/viz（5 Hz）

三层各自独立演进：感知层换算法不该影响协同层协议；协同层的对账机制（第 036 章）复用第 027 章的块协议；系统层对前两层"只观察不干预"（除了告警触发的降级动作）。分层的目的是让故障可定位，出问题时先问"哪一层"，再进对应章节的排障手段。

用一次典型故障走一遍分层定位：2 号机器人的位姿在融合视图里突然跳变。感知与本地估计层先自查（里程计与本地 SLAM 是否丢帧、重定位是否触发）；协同层的证据是接收侧的时间戳与来源检查（第 030/031 章）；系统层的证据是同刻的网络丢包与时间同步告警（第 039 章）。各层给出的证据把猜测空间收敛到一层，这就是分层的全部价值；若平时不做分层监控，事故现场就要在三层之间同时猜，复盘时间成倍拉长。

2. 坐标系与时间轴：全系统的两条基准线

项目开始前必须固化的两份"契约"：

  • 坐标契约（第 024/025 章）：world 为唯一根；每台机器人内部沿用 map/odom/base_link 原生名 + robotN/ 前缀；world → robotN/map 桥接来自场地标定（残差 RMS ≤ 3 cm）。地图、检测、位姿分享一律在 world 系输出。
  • 时间契约（第 009/030 章）：统一时钟源（网关 NTP + 各机同步）；所有消息打"测量时刻"戳；跨机对齐容差 50 ms；验收时抽查任意两机的消息时间差分布。

两条基准线的任何一处破裂，都会在本项目的指标上显形：坐标错 → 冲突率超标；时间错 → 状态延迟虚高、融合抖动。先验收基准线，再验收功能，这是验收流程的基本纪律。

整图字节数 =（宽 ÷ 分辨率）×（高 ÷ 分辨率）× 每格字节数；增量带宽 ≈ 块字节 × 每秒变化块数 × 叠加机器数；快照突刺 = 整图字节 × 同时加入成员数 40 m × 20 m、5 cm 分辨率：800 × 400 = 32 万格，int8 栅格约 0.31 MB/幅；两台新成员同时拉快照是 0.62 MB 突刺；增量按 100 B/块、50 块/s、3 机叠加约 15 KB/s，与 2 MB/s 的带宽预算相差两个数量级

覆盖率算例把 10 分钟的验收窗口也算清楚：3 台机器人有效观测幅宽各 3 m、速度 0.5 m/s，理论清扫率为 3 × 3 × 0.5 = 4.5 m²/s；场地 40 m × 20 m = 800 m²，理想情况约 180 s 覆盖一遍。真实系统再乘 2–3 的效率折损（路径重叠、转弯、避障、地图合流等待），落入 6–9 分钟，正好压进 10 分钟窗口。把速度降到 0.3 m/s，理论时间升到约 300 s，折损后可能越过验收线；参数与指标之间的因果链由此显形，任何收紧阈值的决定都要先回到这张算术里。

标定残差预算 3 cm 同样是推导出来的：栅格分辨率 5 cm 时，半格为 2.5 cm，两机地图里同一面墙的位置若相差超过半格，就会落在相邻格上并被统计为冲突。把标定残差压在 3 cm 以内，冲突率小于 3% 的目标才有物理余量；残差升到 5 cm 以上，即便算法正确，冲突率也会被几何误差顶上去，此时应当先修复标定，再谈融合参数调整。

指标设计的两个要点：（1）每条指标都有"测量方法"栏，没有测量方法的指标只是愿望；（2）指标要成组，单看覆盖率可能"虚高"（机器人乱撞也覆盖），所以要配冲突率与恢复能力一起判。

指标运行的配套纪律有三条：每次验收运行分配一个 run_id，所有图表与 bag 都以它归档；每条指标记录时间戳与当时的负载说明（谁在可视化、是否在录包、网络信道状态）；同一指标至少重复三次，报告里给出中位数与波动范围。没有这三条，指标只能证明"某一次曾经好过"；有了这三条，指标才能作为回归基线（第 037/039 章的体系在此汇合）。

"协同相对单机提速 ≥ 40%"的门槛同样来自算术：单机有效清扫率 1.5 m²/s、三机 4.5 m²/s，理想加速比是 3 倍；折损因子在单机与协同上同时存在（路径重叠、转弯、避障、地图合流等待），协同侧的折损通常更重，真实加速比落在 1.8–2.4 倍。取 40%（即 1.4 倍）作为门槛，既留出"协同调度不完美"的余量，又能把"三台各跑各的、几乎没有协同收益"的失败形态筛出来；若把门槛提到 2 倍以上，先要解决探索调度与地图合流等待，再去验收现场看数据。

4. 失败模式预演：集成系统会怎么坏

  • QoS 集成错配：模块各自测试都好，拼起来收不到数据（第 011 章），集成时逐话题对比两端 QoS。
  • 更新风暴：三机同时发布全量地图/大更新，峰值打满链路，控制流受损，整流 + 增量 + 限速（第 027/034 章）。
  • 时间基准分裂：部分节点忘记 use_sim_time 或时钟未同步，基准线验收拦截。
  • 恢复路径从未演练：断网恢复逻辑只在 PPT 里存在，故障注入是验收的必选项。
  • 监控本身成为负载：/viz 与录制全量数据把磁盘与带宽吃掉，第 037/038 章的预算纪律。

5. 地图同步策略对比

地图怎么在车队里流动，直接决定带宽曲线的形状。四种策略放同一尺度下对比：

同步策略稳态带宽新成员可见延迟峰值特性实现复杂度
周期全量快照0.31 MB × 频率 × 3 机，秒级重复即达 MB/s 量级快，但重复传输无新增信息持续高位，无突刺最低
事件驱动全量无变化时为零取决于下一次地图事件每次变化全量重传，突刺大低
增量块加整流约 15 KB/s（本例规模）受整流周期上界约束（约 0.5 s）小幅可控中
增量块加订阅半径随机器数与半径增长，但局部性最好本地块即时，远端靠快照补齐大规模下曲线最平滑高（第 033 章机制）

本项目（3 台）选"增量块加整流"，理由有两个：整流周期 0.5 s 直接支撑"地图更新端到端延迟 p95 ≤ 2 s"的验收指标，并为晚加入者保留一条快照通道；订阅半径机制留到扩到 8 台以上时再引入（练习 4）。策略选择完成后，把每条流写回接口表：生产者、消费者、频率、QoS、带宽预算，与状态流共用同一张表，评审时一次性核对。

实现思路与设计

集成按"自下而上、先单机后协同"的八步走：

  1. 基准线先行：部署时间同步与坐标标定，跑验收脚本确认"时间差分布 + 标定残差"达标。
  2. 单机闭环：一台机器人跑通 传感器 → 本地 SLAM → 地图块发布 → 状态话题（其余两台先关机）。
  3. 双机协同：接入第二台，验证位姿共享、地图合并、冲突率与更新延迟。
  4. 三机扩容：第三台加入，观察带宽增长（应近似线性；超线性增长说明瓶颈已经出现）与地图增量流量。
  5. 状态共享：位姿/目标/任务状态统一到 /fleet/state 与各机话题；测量端到端延迟。
  6. 监控接线：健康聚合器 + 告警落日志/面板；/viz 信道开通并控频。
  7. 故障注入验收：依次注入停话题、断网、高水位，核对告警时间与恢复时间。
  8. 录制与报告：全程 bag（白名单压缩），导出指标实测表与失败模式清单。

关键代码与解读

片段 1：顶层集成 launch，一份编排拉起全队

from launch import LaunchDescription
from launch_ros.actions import Node

def robot_bringup(rid):
    """每台机器人的标准装配：命名空间 + 参数 + 重映射一次写清。"""
    return [
        Node(package="fleet_slam", executable="local_slam",
             namespace=f"robot{rid}", parameters=[{"robot_id": rid}],
             output="screen"),
        Node(package="fleet_state", executable="pose_sharer",
             namespace=f"robot{rid}", parameters=[{"robot_id": rid}],
             output="screen"),
        Node(package="fleet_health", executable="probe",
             namespace=f"robot{rid}", parameters=[{"robot_id": rid}],
             output="screen"),
    ]

def generate_launch_description():
    nodes = []
    for rid in (1, 2, 3):                    # 扩到 20 台也只改这一行列表
        nodes += robot_bringup(rid)
    # 网关侧：合并器、健康聚合、可视化桥（第 034/038/039 章模块）
    nodes.append(Node(package="fleet_map", executable="merger",
                      parameters=[{"robots": [1, 2, 3]}], output="screen"))
    nodes.append(Node(package="fleet_health", executable="aggregator",
                      parameters=[{"robots": [1, 2, 3]}], output="screen"))
    return LaunchDescription(nodes)

解读：集成 launch 是"系统即代码"的直接体现。（1）机器人装配被抽成 robot_bringup(rid) 函数：同一份代码复用到 N 台，扩容的唯一代价是改列表，第 001 章"实例化复用"原则在项目级的兑现。（2）每个节点都显式带 namespace 与 robot_id 参数：身份信息绝不硬编码在节点内部，这与第 021–039 章所有模块的设计保持一致。（3）网关模块单列：合并器、聚合器、桥都是"全队级"组件，与机器人级模块的启动时机、升级节奏不同，混在一起会让部署脚本难以维护。（4）真实部署时这里还要叠加环境变量（RMW、SHM，第 022 章）与 QoS 覆盖配置文件，把所有"系统级约定"集中在顶层 launch，是新成员理解系统的第一入口。

片段 2：状态共享 + 地图合并的核心节点（网关侧）

class FleetMerger(Node):
    """网关核心：聚合三机状态与地图增量，输出车队视图与全局地图。"""
    def __init__(self, robots):
        super().__init__("fleet_merger")
        self.robots = robots
        self.poses = dict()                  # rid -> (stamp, x, y, theta)
        # 地图增量：Reliable 保内容，volatile 只对"此刻在场"的订阅者有意义
        self.tiles = dict()                  # (bx,by) -> (version, block)
        for rid in robots:
            self.create_subscription(RobotState, f"/robot{rid}/state",
                                     lambda m, r=rid: self.on_state(r, m), 10)
            self.create_subscription(MapTile, f"/robot{rid}/map_updates",
                                     self.on_tile, 50)
        snap_qos = QoSProfile(depth=1)       # 快照：晚加入者可取的完整地图
        snap_qos.reliability = ReliabilityPolicy.RELIABLE
        snap_qos.durability = DurabilityPolicy.TRANSIENT_LOCAL
        self.map_pub = self.create_publisher(OccupancyGrid, "/fleet/map", snap_qos)
        self.state_pub = self.create_publisher(FleetState, "/fleet/state", 10)
        self.create_timer(0.5, self.publish_fleet_state)   # 聚合状态 2 Hz

    def on_state(self, rid, msg):
        cur = self.poses.get(rid)
        # 新鲜度守卫：旧状态不得覆盖新状态，先比较再写入（第 021 章同步纪律）
        if cur is not None and msg.stamp < cur[0]:
            return
        self.poses[rid] = (msg.stamp, msg.x, msg.y, msg.theta)

    def on_tile(self, msg):
        key = (msg.tx, msg.ty)
        cur = self.tiles.get(key)
        if cur is not None and msg.version <= cur[0]:
            return                           # 块级版本守卫（第 027 章）
        self.tiles[key] = (msg.version, np.frombuffer(msg.data, dtype=np.int8))

    def publish_fleet_state(self):
        out = FleetState()
        out.header.stamp = self.get_clock().now().to_msg()
        out.robots = [self.to_msg(rid, *v) for rid, v in self.poses.items()]
        self.state_pub.publish(out)          # 队友可用：/fleet/state 即"共享视图"

解读：网关节点的四个细节都是前文机制的项目级复用。（1）状态聚合里也有版本/新鲜度守卫：守卫必须发生在写入之前，先比较、后赋值；若先赋值再比较，旧包会把新状态"覆盖一下再判断"，产生瞬时回退。审阅集成代码时，这类顺序错误是高发点。（2）块级版本守卫与第 027 章完全一致：项目里的每个合流点（网关、订阅增量图的每个节点）都必须执行同样的规则，协议的一致性体现在"处处执行"，只在文档里写下的规则等于没有落地。（3）两种 QoS 的分工：增量用 Reliable、快照用 Reliable + transient_local，状态型与事件型数据的语义差异在新项目里第一次被完整使用。（4）聚合成 /fleet/state 以 2 Hz 发布：它同时服务于监控（第 039 章）、可视化（第 038 章）和需要"全队一瞥"的算法；单机细节仍可从各机话题获取，聚合视图与原始视图并存，前者是后者的补充。

片段 3：验收测量脚本，三个核心指标的自动判定

def acceptance_report(fleet_map, ref_free_mask, conflicts, latencies_ms):
    """把三项验收指标算成"通过/不通过"，输出可直接贴进报告的表。"""
    # 指标 1：重叠区冲突率（第 026 章工具；示例传入已统计的冲突对数）
    overlap_known = sum(conflicts["known_pairs"]) or 1
    rate = conflicts["conflict_pairs"] / overlap_known
    ok_conflict = rate < 0.03

    # 指标 2：覆盖率：合并地图已知格中处于"参考可通行区域"的比例
    known = fleet_map != -1
    covered = (known & ref_free_mask).sum() / max(ref_free_mask.sum(), 1)
    ok_coverage = covered >= 0.95

    # 指标 3：状态共享延迟 p95（第 030 章的双时间戳统计）
    lat = sorted(latencies_ms)
    p95 = lat[int(0.95 * (len(lat) - 1))] if lat else float("inf")
    ok_latency = p95 <= 50.0

    rows = [("冲突率", f"{rate:.2%}", "< 3%", ok_conflict),
            ("覆盖率", f"{covered:.1%}", "≥ 95%", ok_coverage),
            ("状态延迟 p95", f"{p95:.1f} ms", "≤ 50 ms", ok_latency)]
    for name, val, target, ok in rows:
        print(f"{name:12s} 实测 {val:>10s} 目标 {target:>8s} "
              f"{'通过' if ok else '不通过'}")
    return all(ok for _, _, _, ok in rows)

解读：验收脚本把"感觉不错"变成"表格说话"，三个设计点值得强调。（1）三个指标的判据分别来自不同的测量源：冲突率来自地图对（第 026 章工具）、覆盖率需要"参考可通行区域掩码"（来自平面图或人工标注的 ground truth）、延迟来自双时间戳统计（第 030 章），验收体系的质量取决于测量源的独立性，用系统自己产生的地图来判系统没有意义。（2）判据选 p95：平均值会把偶发的大延迟稀释掉，而协同系统的"体感"由尾部决定，这与第 035 章关注 p99 的纪律一致。（3）返回布尔值让脚本能进 CI/流水线：每次集成后自动跑一遍，把"系统是否还达标"变成回归项，这正是第 037 章回放体系与本章验收体系的汇合点。注意示例中把目标值写成字符串时用了 &lt; 等转义（HTML 展示需要），真实脚本里应是普通比较运算符。

常见坑

  • 模块单测全过、集成就哑：QoS/命名空间/时间基准在拼接处错配。修复：集成第一课就是"逐话题核对两端 QoS"，并在启动脚本里输出检查清单。
  • 三机同发的更新风暴：全量快照周期性重复发布，峰值带宽打满。修复：增量为主、快照事件驱动、整流 + 限速（第 027/034 章）。
  • 恢复路径没演练：断网恢复只在文档里。修复：故障注入作为验收必选项（断网 30 s、停话题、高水位）。
  • 验收指标没有 ground truth：用系统输出验证系统，指标永远"好看"。修复：独立的参考掩码/参考轨迹；至少用录包离线核对一次。
  • 监控与录制反噬：/viz 与全量 bag 把资源吃掉，指标集体劣化。修复：/viz 专用信道（第 038 章）、bag 白名单 + 压缩（第 037 章）、监控进预算表。

练习与思考

  1. 设计你自己场地的"参考可通行区域掩码"制作流程（3 步以内），并说明它与合并地图的比对方法。★
    提示
    如：平面图栅格化 → 人工修边 → 导出分辨率对齐的布尔掩码；比对即掩码内已探索比例与掩码外误占比例两个数。
  2. 把地图更新延迟目标从 p95 ≤ 2 s 收紧到 ≤ 500 ms，预测需要调整哪些参数（整流周期、发布频率、带宽），代价是什么。★★
    提示
    整流周期从 0.5 s 缩到 0.1 s、提高更新 QoS 深度；代价是流量峰值与 CPU 上升，先确认带宽预算能容纳再动。
  3. 设计并执行一次故障注入："让 robot2 断网 30 秒"。写出注入步骤、预期行为（告警时间、地图状态、任务状态）与恢复判定。★★
    提示
    注入：防火墙丢包或断开 AP；预期：10 s 内健康告警、robot2 进入本地模式；恢复后走第 036 章对账，60 s 内冲突率回到阈值内。
  4. 设计题：把本项目扩展到 8 台机器人，列出需要改动的三件事与可能的新瓶颈（拓扑、带宽、发现、合并器负载），并给出各自的应对方向。★★★
    提示
    ①发现规模：分域或路由器（第 034 章）；②带宽：订阅半径收窄（第 033 章）；③合并器：多实例分区聚合或分层。
  5. 思考：如果把验收指标里的"覆盖率 ≥ 95%"换成"三机协同比单机快 ≥ 40%"，测量的公平性需要哪些控制条件？★★★
    提示
    相同场地、相同起始点分布、相同速度与感知范围、相同时间预算；单机对照至少跑 3 次取中位数；避免"协同组有更好开局"这类系统性偏差。

小结

  • 阶段项目的核心是"集成与验收"：三层架构 + 两条基准线（坐标、时间）+ 一组可测指标。
  • 集成顺序：基准线 → 单机 → 双机 → 三机 → 监控 → 故障注入 → 录制报告。
  • 验收指标七项之外，最重要的是"测量方法"与"独立 ground truth"；统计口径用 p95，均值会稀释尾部延迟。
  • 协议纪律在集成点的复用：版本守卫、QoS 语义、整流限速、告警可行动，一条都不能只在文档里。
  • 第二篇至此收官；第三篇从这里出发：编队控制基础，让多台机器人从"知道彼此在哪"走向"保持队形协同运动"。
