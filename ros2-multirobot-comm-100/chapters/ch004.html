第 004 章：动作通信执行复杂任务

返航、导航、搬运这类"要跑一会儿"的任务，需要三种能力：能看进度、能喊停、有始有终。动作（action）把这三件事打包成一个标准协议。

  • 主题：通信基础 / 长任务交互原语
  • 关键机制：目标状态机、反馈流、协作式取消、抢占策略
  • 预计学时：55 分钟
  • 前置章节：第 003 章

学习目标

  • 说清动作解决的三件事：进度反馈、可取消、结构化结果；理解它与话题/服务的能力分工。
  • 掌握动作目标（goal）的状态机：从发出到最终态的全部中间状态，能预判每个状态上客户端该做什么。
  • 会设计反馈流：频率、内容、与带宽的关系；知道"反馈不是日志"这条铁律。
  • 理解协作式取消的语义与响应时间，会设置合理的取消检查点频率。
  • 能写出服务端与客户端的标准骨架：执行循环、并发处理取消、两级 future 的结果获取。

背景与动机

上一章的服务适合"几毫秒办完"的操作，但多机器人系统里最重的活都是长任务：导航到 40 米外的充电桩、搬运货架回库、按航点巡航一圈。这类任务有三个服务给不了的东西：进度（还要多久）、取消（情况变了，别去了）、与任务时长匹配的生命周期（几十秒到几分钟，中途失败也要有结构化结果）。

硬拿服务做长任务，客户端要么阻塞几十秒，要么就得自己发明"轮询进度"的土办法；硬拿话题做，请求与结果的对齐、取消的传达又全部要手搓。ROS2 的动作原语就是把这些模式固化成协议：一个目标、一路反馈、一个结果。本章把动作拆开讲清楚，理解它的内部构造，你在排障时才知道去哪个话题、哪个服务里找线索；理解它的状态机，你在做任务调度（第三、四篇反复出现）时才能正确表达"抢占"与"取消"。

核心原理

1. 动作 = 长任务协议：目标 + 反馈流 + 结果

动作是在服务与话题之上组装出的协议模板，传输层仍复用既有原语，没有独立的第四种传输机制。一次完整的动作交互包含：

  • 目标请求（服务）：客户端说"去 2 号充电桩，速度上限 0.5 m/s"；服务端回答"接受 / 拒绝"。
  • 反馈流（话题）：任务执行期间，服务端以固定频率发布进度（剩余距离、当前阶段）。
  • 结果（服务）：任务结束时返回终局（成功/失败/被取消 + 细节数据）。
  • 取消请求（服务）与状态流（话题）：前者让客户端喊停，后者让任何观察者知道"某个目标现在处于什么状态"。

在 ROS2 的实现里，一个动作会展开成五条内部端点（三个服务 + 两个话题），它们都挂在动作名之下的 _action 子路径里。这个事实有两个用途：排障时你可以分别检查它们（第 4 节 CLI 演示）；设计时你可以问自己"我真的需要全套吗"，如果不需要进度和取消，退回服务（003）会更轻。五条端点的清单如下，值得背下来：

内部端点形式作用丢得起吗
_action/send_goal服务提交目标请求，取回"接受 / 拒绝"丢不起，可靠传输
_action/cancel_goal服务请求取消某个在途目标丢不起，可靠传输
_action/get_result服务获取最终结果与终态丢不起，可靠传输
_action/feedback话题过程读数（剩余距离、阶段）丢得起，按仪表盘语义
_action/status话题所有目标的状态，供任意观察者查询重要，晚到者应补到当前状态

这张表解释了动作的三类故障为什么表现不同：send_goal 不通是"接不了单"，feedback 停滞是"过程看不见"，get_result 不出是"没有终局"。三者分属不同端点，排障时逐个验证，比笼统地说"动作坏了"高效得多。

2. 目标状态机：把"任务在流程中的位置"说清楚

每个目标（goal）都有一条生命周期：客户端发出后先处于等待裁决；服务端接受后进入执行中；客户端请求取消且服务端同意后进入取消中；最终三选一：成功、中止、已取消。这台状态机是动作的核心价值，它把"任务现在到底怎么样了"变成一个任何组件都能查询的显式事实。

两类典型竞态它都能防住：（1）客户端在服务端还没裁决时若直接发下一个目标，旧目标可能还在排队执行，状态机禁止未决目标未清理就发新目标（或由服务端的抢占策略处理）。（2）服务端在"执行中"收到取消，必须先进入"取消中"并在安全点停下；对取消视而不见会让客户端陷入状态错位。

状态含义客户端该做什么
等待裁决目标已送达，服务端尚未答复等第一级 future，不要重复发送同一目标
执行中服务端已接受，正在推进消费反馈，启动任务级看门狗
取消中取消已被同意，任务正在收尾等结果 future 到达终态，不切换到下一个任务
成功 / 中止 / 已取消三个终态，互斥且不可再变记录结果与耗时，清理句柄后再接新任务

3. 反馈流：设计的是"仪表盘"，不是"日志"

反馈通道存在的意义是让客户端和操作员能判断"要不要干预"：剩余距离 12 m 变成 3 m，说明正常；十分钟没变，说明卡住了。由此得出设计规则：

  • 频率 1–10 Hz 足够。反馈来自任务循环的天然节拍（每步推进发一条）；以 50 Hz 刷反馈，带宽与 CPU 全是浪费，人眼也消费不了。
  • 内容要机器可判断：剩余完成度、阶段枚举、当前位姿。字符串日志塞进反馈是反模式，文本无法被遥控台程序化消费，还会把每条反馈撑到几百字节，20 台机器人的反馈流足以挤占控制带宽。
  • 反馈可以丢：它是"仪表读数"，不是账本。丢失一帧只是少刷一次屏，下一帧立刻补上，反馈订阅侧天然按 Best-effort 语义理解即可。
反馈带宽 ≈ 单条反馈大小 × 频率 × 并发任务数 200 B × 5 Hz × 20 台 ≈ 20 KB/s：健康；若把 2 KB 日志文本按 20 Hz 发，则是 800 KB/s 的灾难

4. 协作式取消：为什么"停"不是立即发生的

动作的取消是协作式的：客户端发出取消请求 → 服务端裁决（同意/拒绝）→ 处于执行循环中的任务在下一个检查点发现取消已被请求 → 收尾、进入"已取消"终态。这意味着取消的响应时间取决于检查点间隔：一个每秒检查一次的循环，最坏要等 1 秒才停。

检查点该多密？用"安全预算"倒推：如果"继续跑 0.5 秒"会造成明显危险或浪费（例如即将撞上动态障碍），检查点必须远快于 0.5 秒；如果任务是慢慢扫地，1 秒的停止延迟无所谓。注意服务端也可以拒绝取消（CancelResponse.REJECT）：比如"正在下坡，停不下来"的物理约束下，拒绝并让任务跑完往往更安全。

T检查点 ≤ 安全间距 ÷ 当前速度 例：速度 1 m/s、最小安全间距 0.3 m，则检查点不能慢于 0.3 s；速度提到 1.5 m/s，要求收紧到 0.2 s。约束随速度变化，不能一次定死

算例：0.5 s 的检查点差在哪？1 m/s 的机器人在同意取消后最坏再前进 0.5 m；若任务场景的最小安全间距是 0.3 m，这半米就足以把"及时喊停"变成"擦碰"。把检查点改为 0.2 s，停止距离压到 0.2 m 以内；代价是循环开销与反馈发布次数增加，按 2 Hz 反馈、0.2 s 检查的设计，一个 30 s 任务多执行约 90 次轻量检查，CPU 增量可以忽略。可见"取消粒度"是一个物理安全参数，取值依据来自场地与速度，不来自代码习惯。

5. 抢占：多机器人里"新任务挤掉旧任务"的显式表达

单机器人场景，一个目标跑到底就行。多机器人协同里，抢占（preemption）是常态：调度器决定让 5 号机器人从"巡逻"转去做"应急支援"，这需要打断进行中的巡逻。动作把这变成显式选项：服务端对新目标可以接受并替换旧目标（先让旧目标收到取消、再按新目标执行），或者拒绝新目标。关键设计问题是"替换的原子性"：必须先确认旧任务停在安全状态，再启动新任务，否则机器人会同时执行两套控制逻辑，这是"动作抢占"最典型的事故场景。这个主题将在第三篇的任务协同里反复出现，本章先把机制打牢。

实现思路与设计

以"返航充电"任务为例走一遍完整设计：

  1. 先做原语判断：任务时长约 30 秒（长）、需要显示进度（要反馈）、遥控台可能要求中止（要取消），三条都满足，用动作。只要有一条明显不需要，就往下退：服务（短且无进度）或话题（高频流）。
  2. 定义 .action 三块：goal（速度上限、目标桩号）、result（成功标志、中止时剩余距离）、feedback（剩余距离、阶段）。字段最小集原则：能推算的不重复发。
  3. 服务端三段式：goal_callback 只做快速裁决（是否已有任务、电量是否够）；execute 循环"推进任务 + 检查取消 + 发反馈"三件事交错；结束时给出终态。
  4. 客户端两级 future：第一级等"目标是否被接受"，第二级等"最终结果"；反馈回调独立更新界面缓存。取消按钮调用 cancel_goal_async。
  5. 超时与兜底：任务级看门狗，客户端对"结果"设置总时长上限（如预期 30 s，上限 60 s）；超时则发取消；通信中断时的最终兜底由机器人本地看门狗负责（呼应第 003 章的"沉默保险"）。

参数取值依据

结果超时60 s预期时长 30 s 的 2 倍，容忍慢速与绕行

结果超时值的推导（可复核）：距离 15 m、限速 0.5 m/s，纯行驶时间 30 s；按绕行系数 1.5 估最坏 45 s；60 s 的结果超时留有约 33% 余量。这条推导演示了参数的敏感性：若场地安全策略把限速下调到 0.3 m/s，最坏时间变成 15 ÷ 0.3 × 1.5 = 75 s，60 s 的超时会在任务完成前误触发，客户端发出一次不必要的取消。限速、绕行系数、超时三者必须联动维护，改了任何一个都要重算，否则超时值就从"兜底"变成了"干扰源"。

设计决策：为什么 execute 循环里"发反馈、查取消"要和任务推进交错进行？

因为动作服务端的执行回调是独占长跑的：它一旦在里面写个 time.sleep(30)，取消请求根本没有机会被处理（单线程执行器下连收都收不到），反馈也发不出去。正确结构是"小步推进"：每步推一下任务、查一次取消、发一次反馈，用循环把三者编织起来。这也是为什么 execute 回调的效率问题会直接表现为"取消失灵、反馈停滞"两类症状。

关键代码与解读

片段 1：.action 接口定义，三块字段各司其职

# ReturnHome.action：长任务的标准三块字段（以自定义接口包为准）
float32 speed          # goal：返航速度上限（m/s），须为正数（0 或负值会被拒绝）
int32 dock_id          # goal：目标充电桩编号（多机器人共享场地的寻址键）
---
bool success           # result：是否成功到达并停机
float32 distance_left  # result：终止时的剩余距离（失败/取消时供诊断）
---
float32 distance_left  # feedback：实时剩余距离
string stage           # feedback：阶段枚举 traveling / docking / settling

解读：注意三段字段的职责划分。goal 是"我要什么"（期望），result 是"实际发生了什么"（事实），feedback 是"现在到哪一步了"（过程）。容易犯的错是把过程信息也塞进 result、或把"期望"塞进 feedback。字段设计还有一条实用性原则：result 的 distance_left 在成功时是 0、失败时是"卡在哪"，同一个字段服务两种诊断场景，不需要为失败再造一组字段，结果越好解析，上层调度越好写。

片段 2：动作服务端，三段式骨架与协作式取消

from rclpy.action import ActionServer, GoalResponse, CancelResponse
from rclpy.callback_groups import ReentrantCallbackGroup

class ReturnHomeServer(Node):
    """返航动作服务端：长任务 + 进度反馈 + 可取消的标准骨架。"""
    def __init__(self, robot_id):
        super().__init__("return_home", namespace=f"robot{robot_id}")
        # 取消/新目标请求要与执行循环并发处理：用可重入回调组，且必须配多线程执行器
        self.srv = ActionServer(
            self, ReturnHome, "return_home",
            execute_callback=self.execute,
            goal_callback=self.on_goal,      # 新目标到达时的快速裁决
            cancel_callback=self.on_cancel,  # 取消请求到达时的快速裁决
            callback_group=ReentrantCallbackGroup())

    def on_goal(self, goal_request):
        if goal_request.speed <= 0.0:
            return GoalResponse.REJECT       # 参数非法：直接拒绝，绝不接进来再失败
        return GoalResponse.ACCEPT         # 快速校验：耗时操作一律留到 execute

    def on_cancel(self, goal_handle):
        return CancelResponse.ACCEPT         # 同意取消：真正停止在 execute 下一个检查点
    def execute(self, goal_handle):
        result = ReturnHome.Result()
        dist = goal_handle.request.dock_id * 2.0    # 简化的距离模型：桩号×2 米
        while dist > 0.1:
            # 检查点：每步开头先查取消，停止延迟 ≤ 一个步长
            if goal_handle.is_cancel_requested:
                goal_handle.canceled()              # 进入终态"已取消"
                result.success, result.distance_left = False, dist
                return result
            dist -= goal_handle.request.speed * 0.5     # 每步推进 0.5 s 的行程
            fb = ReturnHome.Feedback()
            fb.distance_left = max(dist, 0.0)           # 反馈：仪表盘读数
            fb.stage = "traveling"
            goal_handle.publish_feedback(fb)            # 反馈走独立话题流
            self.get_clock().sleep_for(0.5)             # 步长 0.5 s：兼作取消粒度
        goal_handle.succeed()                           # 进入终态"成功"
        result.success, result.distance_left = True, 0.0
        return result

解读：（1）三个回调的职责被明确切开：on_goal/on_cancel 是"快速裁决"（回答是/否），execute 是"执行现场"。把裁决逻辑写进 execute 是本末倒置，裁决必须快到不占用执行器。（2）检查取消放在循环每一步的开头：这样最坏停止延迟就是一个步长（0.5 s），而且取消检查的频率和反馈频率、推进步长是同一个参数，设计时它们本来就该一起定。（3）注意注释里点名的执行器前提：零拷贝式地照抄这段代码进单线程执行器的进程，取消会"失灵"，其根源是请求排不进执行线程，与回调是否写对无关。这属于动作服务端最隐蔽的一类坑。

片段 3：动作客户端，两级 future 与反馈回调

from rclpy.action import ActionClient

class HomeClient(Node):
    """遥控台侧：发送返航目标、展示进度、支持取消。"""
    def __init__(self, target_id):
        super().__init__("home_cmd")
        # 绝对动作名跨机器人指向：/robotN/return_home（内部含 5 条端点）
        self.ac = ActionClient(self, ReturnHome, f"/robot{target_id}/return_home")
        self.handle = None

    def send(self, dock_id=1, speed=0.5):
        # 等动作服务端就绪：本质是等它内部的 3 服务 2 话题都发现完成
        if not self.ac.wait_for_server(timeout_sec=2.0):
            self.get_logger().warn("return_home 服务端未就绪")
            return
        goal = ReturnHome.Goal()
        goal.dock_id = dock_id
        goal.speed = speed
        # 第一级 future：目标本身是否被接受（rejected 也是有效答复）
        self.ac.send_goal_async(goal, feedback_callback=self.on_feedback).add_done_callback(self.on_goal_resp)

    def on_feedback(self, fb_msg):
        # 反馈回调：频率由服务端决定（这里 2 Hz），只更新界面缓存即可
        self.last_left = fb_msg.feedback.distance_left

    def on_goal_resp(self, future):
        self.handle = future.result()
        if not self.handle.accepted:
            self.get_logger().info("目标被拒绝：机器人可能电量不足或正在执行任务")
            return
        # 第二级 future：等最终结果；任务期间本节点照常处理其他消息
        self.handle.get_result_async().add_done_callback(self.on_result)

    def cancel(self):
        # 取消按钮：发请求后仍要等结果 future，取消的终态也要走状态机
        if self.handle is not None:
            self.handle.cancel_goal_async()

解读：（1）"两级 future"是动作客户端的心智模型：send_goal_async 的 future 表示"接单成功没有"，get_result_async 的 future 表示"活干完了没有"，两者之间隔着整个任务时长。把两者混在一起等待，会把"被拒绝"错误地当成"执行失败"。（2）反馈回调只更新缓存：它与结果回调、其他话题共享执行器线程，任何耗时操作都会拖慢所有通信，回到第 002 章"数据面短、逻辑面慢"的通用原则。（3）取消后不要立刻销毁 handle：真实系统里等结果回调确认"已取消"再清理，否则界面状态与机器人实际状态可能脱节。

# 动作排障：先看整体，再拆到内部端点（话题名以发行版实际为准）
ros2 action list -t                                    # 列出动作与类型，确认 /robotN 前缀
ros2 action info /robot1/return_home                   # 看动作的客户端/服务端计数是否正常
ros2 action send_goal /robot1/return_home robot_interfaces/action/ReturnHome \
  "{speed: 0.5, dock_id: 1}" --feedback                # 手动发一个目标并观察反馈
ros2 topic echo /robot1/return_home/_action/feedback --once   # 反馈话题的原始内容
ros2 topic hz /robot1/return_home/_action/feedback            # 实测反馈频率是否符合设计
ros2 service list | grep return_home                   # 内部三个服务是否都在
# 常见乱象：action send_goal 卡住 = 服务端 execute 阻塞无响应

解读：这段 CLI 演示了"协议思维"的实用性，动作出问题时，你可以逐层验证：动作层（list/info）、消息层（echo 反馈）、频率层（hz）、服务层（send_goal 手动触发）。send_goal --feedback 是最有价值的排障工具：它绕开遥控台，独立验证"服务端能不能接受目标、推不推反馈、给不给结果"，一步把问题范围切两半。最后一行的经验值得记住：手动发目标卡住，几乎总是服务端 execute 在同步阻塞。

常见坑

  • 把日志当反馈发：反馈里塞文本日志、以 20 Hz 推送，一条 2 KB，全网一天就是约 70 GB 流量，外加卡顿的遥控界面。修复：反馈只放机器可判断的数字与枚举，频率 1–10 Hz。
  • 取消响应慢或完全失灵：执行循环里长阻塞（time.sleep(5)），或单线程执行器导致取消请求排不进队。症状：点了取消，机器人还在走。修复：小步循环 + 每步检查 + 多线程执行器与可重入回调组。
  • 不处理"目标被拒绝"：把 accepted == False 当异常丢掉，界面一直显示"执行中"。修复：拒绝是业务语义（电量不足、已有任务），要显示原因并让调度器重排。
  • 反馈频率与带宽预算脱钩：设计时忘了反馈也是网络流量，20 台 × 5 Hz 反馈看似小，25 台巡视编队 + 图像时就是压垮 WiFi 的最后一根稻草。修复：架构阶段把反馈列入带宽表。
  • 抢占时旧任务没停就启动新任务：调度器直接发新目标，服务端"接受并替换"却没等旧任务收尾，两套运动指令同时作用于底盘。修复：替换协议 = 先确认旧目标到达终态（取消或完成），再执行新目标；必要时用单一"当前任务"状态字段做守卫。

练习与思考

  1. 把片段 2 的反馈频率从 2 Hz（每步 0.5 s）改为 20 Hz（每步 0.05 s），预测反馈带宽、取消响应时间与 CPU 占用的变化；再说明在什么任务里 20 Hz 反馈才合理。★
    提示
    带宽 ×10，取消响应从 0.5 s 缩到 0.05 s；只有精密对接（厘米级纠偏，需要高频遥测）才值得 20 Hz，普通返航 2 Hz 足够。
  2. 用"三问法"给下列任务选择原语：读取电池电压（毫秒级）、清扫 100 m² 区域（几分钟）、以 100 Hz 上报关节角、切换传感器量程、编队巡航两小时。★
    提示
    读电压=服务；清扫=动作（进度+取消）；关节角=话题；切换量程=服务；巡航=动作（且需要抢占策略与看门狗）。
  3. 推导：一个"按航点列表巡航"的服务端每 2 s 检查一次取消。如果机器人巡航速度 1 m/s、障碍物最小间距 0.3 m，这个取消粒度安全吗？给出一个更合适的设计并说明代价。★★
    提示
    2 s 内前进 2 m，远大于 0.3 m，不安全。改为每 0.1–0.2 s 检查（或由避障层独立兜底），代价是循环开销略增；关键认知：取消粒度要跟"物理世界留给你的时间"对齐，代码写起来方不方便是次要考量。
  4. 设计"抢占式巡逻"的动作交互：调度器把 5 号机器人从巡逻切到应急支援。画出状态转换（旧目标被取消 → 新目标执行），写出服务端对"执行中收到新目标"的策略分支与每条理由。★★★
    提示
    策略分支至少三类：空闲则直接接单；执行中且新目标优先级更高则"取消旧+接新"，并等待旧目标终态；正在不可中断阶段（对接中）则拒绝。每个分支都要给调度器一个可重试的明确答复。
  5. 设计实验：对一个 30 s 的返航动作做三次测试，(a) 正常跑完；(b) 第 5 秒发取消；(c) 第 5 秒杀掉执行机器人进程。记录结果回调的状态、耗时与客户端表现，解释三者差异。★★★
    提示
    (a) SUCCEEDED；(b) 应在约一个检查点粒度内 CANCELED；(c) 结果 future 永不完成，这才是需要"任务级看门狗"的原因，也是第 020 章验收指标里的必测项。

小结

  • 动作 = 目标 + 反馈流 + 结果 + 取消，本质是"服务+话题"组装出的长任务协议；不需要进度或取消时用服务更轻。
  • 目标状态机：等待裁决 → 执行中 → （取消中）→ 成功/中止/已取消；两级 future 分别对应"接单"与"完工"。
  • 反馈是仪表盘不是日志：1–10 Hz、机器可判读、计入带宽预算。
  • 取消是协作式的：响应时间由检查点决定；检查粒度用"物理安全预算"倒推。
  • 抢占要先停旧再启新，用单一"当前任务"状态做守卫；动作服务端要用多线程执行器 + 可重入回调组。
