第四篇 · 系统集成与工程化

第 069 章：多机器人资源竞争管理

充电桩只有一个、窄道只容一车、电梯载重有限：用租约、预约窗口与全局资源排序，把多机器人对物理资源的争抢从"抢"变成"排"，安全、无死锁、可恢复。

  • 主题：系统集成 / 资源共享与互斥
  • 关键机制：租约（lease）、预约窗口、全局资源序、超时回退
  • 预计学时：60 分钟
  • 前置章节：第 068 章

学习目标

  • 会区分资源类型：独占/容量受限、可重用/一次性、可抢占/不可抢占，并据类型选择管理机制。
  • 理解租约（lease）机制如何同时满足互斥安全与"持有者崩溃后系统可恢复"的活性要求。
  • 掌握窄道、电梯这类"时空资源"的预约窗口算法，会由通行时间推导入场条件。
  • 能识别多机器人系统中的死锁四条件，并用全局资源序或回退重试做规避。
  • 会实现一个资源管理器节点：注册、租约获取/续租/释放、过期清扫与冲突审计。

背景与动机

前两章分配的是"任务"，任务可以并行、可以排队重排；本章面对的是"物理资源"，充电桩插头只有一个、1 米宽的窄道同一时刻只能过一台车、货梯载重 200 kg 塞不下三台机器人。任务冲突的代价是变慢，资源冲突的代价是相撞。

多机器人系统里资源竞争是事故率最高的环节之一：两台机器人在对向窄道里顶牛、四台全灭电量挤一个充电桩、一台卡在门洞里导致整队瘫痪。这些问题在单机时代不存在，本质是分布式互斥问题，计算机科学里的老问题，但套上了"会动、会坏、时钟会漂"的物理外壳。本章给出工程上真正能落地的三种机制：租约、预约窗口、资源排序。

核心原理

1. 资源分类与管理策略

类型例子关键性质推荐机制
独占可重用充电桩、窄道、单工位同一时刻至多一个持有者租约（带过期时间的互斥锁）
容量受限N 口充电站、载重电梯同时最多 k 个持有者计数信号量（租约 + 名额）
时空窗口十字路口、对向窄道冲突发生在时间窗内，不是全时段预约窗口（申请未来一段时间）
一次性充电时段、托盘位使用后消耗/占用队列 + 先进先出 + 优先级修正

分类决定协议：把十字路口按"独占可重用"管理会让吞吐惨不忍睹（同一时刻整条路只准一台车）；按"时空窗口"管理才能允许多台车在不相交的时间窗里依次通过。先给资源定类型，再选机制，反过来做，协议一定过度保守或不足。

2. 租约：会过期的锁

普通互斥锁有两个致命问题：持有者崩溃后锁永不释放（死锁）；没接到锁的机器人不知道要等多久。租约（lease）用"带时限的授权"解决两者：请求者申请资源，管理器授予一段租期 T；到期前持有者必须续租，否则资源自动回收。

Tlease = Ttask + Trenew_margin，回收延迟 ≈ Tlease（最坏） 窄道通行 24 s → 租期取 35–40 s、续租周期 10 s；崩溃后最多 40 s 资源自动可用，这就是"活性的最坏等待上界"

租约的安全性依赖两个条件：（1）持有者必须"自律"，租期一过即使人还活着也要主动停止使用资源（本地看门狗实现）；（2）管理器与持有者的时钟不能漂太多（第 009 章的同步在这里兑现价值）。如果做不到这两点，只能把租期设得更保守，用效率换安全。窄道场景还有一条硬规矩：必须在物理离开资源后才能释放；释放依据取入口/出口的传感器或里程计双重确认，本地"我认为走完了"的判定不足以作为凭据。

3. 时空资源的预约窗口

十字路口与对向窄道的冲突是"我到达资源的那段时间里资源必须为我保留"。申请时不能只报"我要用"，而要报"我将在 [t1, t2] 占用"，其中 t1 是从当前位置到资源入口的预计到达时间、t2 = t1 + 通行时间。管理器的裁决规则：

  • 同向无冲突：若新申请的窗口与已有窗口不重叠且方向相同，直接批准，单向车流可以流水线化，吞吐提升数倍。
  • 对向必须错峰：对向窗口之间强制插入安全间隔（车辆通过后再留 2–3 s），防止"擦肩"时的避让抖动。
  • 迟到作废：持有窗口的机器人若在 t1 + 宽限（如 10 s）仍未进入资源，窗口作废并重新申请，否则"幽灵预约"会把资源锁死。

任何涉及"预计到达时间"的机制都怕估计失准：导航绕路、被他人挡路都会让 ETA 漂移。工程惯例是把窗口留 20–30% 余量，并在接近资源时（如 5 m 内）发起一次"最终确认"，确认失败则退避重试。

4. 死锁：四个条件与两种规避

死锁的四个必要条件（互斥、持有并等待、不可剥夺、循环等待）在机器人场景里都能凑齐：机器人 A 握着充电桩想进窄道，机器人 B 占了窄道想充电，循环等待，双方永停。规避手段有两类：

  • 破坏"循环等待"，全局资源序：给所有资源编号，任何机器人必须按编号从小到大申请。上面的例子中若窄道编号 3、充电桩编号 7，A 会先申请窄道再申请充电桩，B 先申请... B 持有窄道（3）后在申请充电桩（7）之前不可能再持有更小号的资源，两方申请顺序一致，循环等待被数学上排除。
  • 破坏"持有并等待"，全有或全无 + 超时回退：要么一次性申请全部所需资源（拿不齐就全放掉重来），要么给每个等待加超时，超时后释放已持有的资源、退避随机时间再试。超时回退不保证无死锁，但加上随机退避后概率趋近于零，工程上简单可靠。

第三类土办法是物理层解决：把窄道改成单向循环道、加宽路口、把充电桩从 1 个扩到 3 个。很多"算法难解"的竞争问题，硬件改造的性价比高一个数量级，别急着写复杂的协议，先问资源本身能不能不做成瓶颈。

5. 数值算例：租期、吞吐与安全边际的账

取参数表里的窄道场景算完整链条：道长 18 m，道内速度 0.4 m/s，两端进出各 3 s 转向，单次通行时间 = 18/0.4 + 6 = 51 s。租期取 60 s，比任务时长多 9 s（约 18% 余量）；续租周期取租期三分之一，即 20 s，两次续租之间容得下两次丢包。吞吐方面：单方向串行放行时，每 51 s 通过一台，理论吞吐约 1.18 台/分钟；对向车流错峰时，一次"一来一回"需要 51 + 51 + 2×2.5（安全间隔）= 107 s，平均吞吐约 1.12 台/分钟，只比同向串行低 5%。这组数说明两件事：窄道的通过量本来就由物理通行时间封顶，协议层面优化的是公平与安全；对向错峰的安全间隔（2.5 s）相对 107 s 的周期占比很小，值得设置。

安全边际的来源要拆开看。时钟漂移用 20 ppm 的石英晶振估算：5 分钟累积漂移 20×10⁻⁶×300 ≈ 6 ms，对秒级租期完全无害；真正危险的是冷启动时钟差上分钟量级、以及管理器与持有者之间的网络黑洞，所以 5 s 级别的固定安全边际覆盖的是后者；晶振漂移的量级远小于它。窗口余量按 ETA 的 25% 计：51 s 的通行窗口给到 63.75 s，若实测通行时间的 P95 是 58 s，窗口仍留 5.75 s 缓冲；"接近资源 5 m 时的最终确认"把最后一段的 ETA 不确定性压缩到秒级，两个机制叠加后，"幽灵预约"（人没来窗口占着）与"窗口截断"（人到了窗口过期）两类失约被同时压低。

6. 退避为什么用随机区间：一次小计算

资源申请失败的退避取 1–5 s 随机（均匀分布，窗口宽 W = 4 s），它的作用可以算出来。两台机器人独立按此退避后重试，两个等待值相差不足 0.5 s 的概率（即"几乎同时重试、再次相撞"）为 1 − (1 − 0.5/4)² ≈ 23%；如果退避用固定值 3 s，这个概率是 100%，两台永远同步相撞。统一场景下的经验规律：随机退避把同步碰撞从"必然"降为"小概率"，多轮重试后碰撞概率连乘衰减，"申请失败是常态、重试必然成功"的系统行为就由这个小设计保证。这也是以太网 CSMA 与本章租约重试共享的同一条原理：用随机化打散同步，用次数上限兜底最坏情况。返回值上还要配合重试耗尽路径（返回 None 并上报调度器改派），保证任何一次资源申请失败都有明确归宿。

容量受限资源的账同样值得做。以 3 口充电站为例：单次充电 30 min，供给能力 3/0.5 h = 6 台/小时；20 台机器人平均每 4 小时补一次电，需求 20/4 = 5 台/小时，系统利用率 5/6 ≈ 83%。这两个数字直接回答运维问题：车队再加两台就会在高峰逼近 6 的上限（需求升到 5.5）；"高峰时段总有人抢位"与协议公平性无关，根因是容量余量只剩约 17%。此时租约加名额计数要做的只有一件事：把 83% 的利用率平稳分给所有申请者，并让拒绝带着重试时间返回；扩容还是排队的决策交给容量数据，加急消息优先级解决不了容量瓶颈。

实现思路与设计

资源管理器是一个集中式服务节点（允许单点，理由见 065 章的同类决策），接口三件套：

  1. 注册：资源以 YAML 声明（ID、类型、容量、位置、通行时间估计），启动时加载；不在运行时动态增删资源（增删走重新部署）。
  2. 获取/续租/释放：用服务（同步语义清晰）；获取返回"授予 + 租期截止时间"或"拒绝 + 预计可用的最早时间"，拒绝时给出 ETA 比干巴巴的拒绝有用得多，请求方可以据此决定等待还是换资源。
  3. 过期清扫与审计：管理器以 1 Hz 扫描租约表，回收过期条目并记日志；对"频繁被拒"的资源输出统计，作为扩容依据。

设计决策：为什么"拒绝时给出预计可用时间"值得多写一段协议？

没有 ETA 的拒绝（"资源忙，稍后再试"）迫使请求方盲目重试，四台机器人以 1 Hz 重试同一个充电桩，会形成轻量级拒绝服务攻击，还可能先到先得地插队。返回"预计 T+30 s 可用"让请求方进入定时等待或改选备用资源（例如另一个 15 m 外的充电桩），重试流量下降一个数量级。资源管理协议的设计目标落在"减少无谓的争抢"上；公平仲裁只是兜底手段。

关键代码与解读

片段 1：租约管理器的核心表与清扫

class LeaseManager(Node):
    """租约管理器：grant 带截止时间；过期自动回收，崩溃不再死锁。"""
    def __init__(self):
        super().__init__("lease_manager")
        self.leases = {}          # res_id -> (holder, expire_at, renew_deadline)
        self.create_service(AcquireLease, "/resource/acquire", self.on_acquire)
        self.create_service(ReleaseLease, "/resource/release", self.on_release)
        self.create_timer(1.0, self.sweep)          # 1 Hz 清扫足够：租期是秒级

    def on_acquire(self, req, resp):
        now = self.now()
        cur = self.leases.get(req.res_id)
        if cur and cur[1] > now:                    # 未过期：比较持有者
            if cur[0] == req.robot_id:              # 原持有者续租：延长到新截止
                self.leases[req.res_id] = (req.robot_id,
                                           now + req.duration, now + req.duration / 3)
                resp.granted = True
                resp.expire_at = now + req.duration
            else:
                resp.granted = False
                resp.retry_after = cur[1] - now     # 拒绝但给出"最早可用"
            return resp
        # 资源空闲或已过期：直接授予（过期回收与授予在同一临界区内完成）
        self.leases[req.res_id] = (req.robot_id, now + req.duration,
                                   now + req.duration / 3)
        resp.granted = True
        resp.expire_at = now + req.duration
        return resp

    def sweep(self):
        now = self.now()
        for rid, (holder, expire_at, _) in list(self.leases.items()):
            if expire_at <= now:
                self.get_logger().warn(f"租约过期回收：{rid} 原持有者 {holder}")
                del self.leases[rid]                # 回收即删除：下个申请立即成功

解读：这段代码有三个正确性关键点。（1）授予与过期回收在同一临界区内完成（ROS2 服务回调默认串行），不存在"清扫线程删一半、授予线程同时写"的竞态，这正是把清扫放进定时器回调、不让它另起线程的理由。（2）续租只允许原持有者：别的机器人拿着同一 ID 来"续租"会走拒绝分支，协议层面杜绝了冒名顶替。（3）拒绝返回 retry_after，把"何时再来"的计算从请求方挪到管理器（它才知道真实截止时间）。注意 expire_at <= now 用的是管理器时钟，若持有者时钟比管理器快 2 s，它会认为自己还有 2 s 而管理器已回收，窗口内就出现双持有。所以要么统一时间源，要么租期安全边际 ≥ 最大时钟偏差 + 网络抖动（经验值 ≥ 5 s）。

片段 2：窄道通行，双向预约窗口

def request_corridor(manager, robot, corridor, now, eta):
    """为窄道申请一个占用窗口 [t1, t2]；t1 为预计到达，t2 = t1 + 通行时长。"""
    t1 = now + eta
    t2 = t1 + corridor.traverse_time * 1.25      # 25% 余量：导航方差
    req = WindowRequest()
    req.res_id = corridor.id
    req.robot_id = robot.id
    req.t1, req.t2 = t1, t2
    req.direction = corridor.direction_of(robot) # 记录方向：同向可流水线
    resp = manager.call(req)                      # 同步服务：拿到裁决再动身
    if resp.granted:
        robot.set_deadline(t2)                    # 队尾期限：超时必须让出
        robot.announce("corridor_granted", resp.window_id)
    else:
        robot.wait_until(resp.retry_at)           # 到点再试，不做忙等重试
    return resp

def overlaps_with_clearance(a, b, gap=2.5):
    """窗口冲突判定：同向只需不重叠；对向还要预留安全间隔 gap。"""
    if a.t2 + (gap if a.direction != b.direction else 0.0) <= b.t1:
        return False
    if b.t2 + (gap if a.direction != b.direction else 0.0) <= a.t1:
        return False
    return True

解读：预约窗口把"互斥"精细化成"时间表"：两段窗口不重叠即可共存，窄道的通过量从"一次一车、走完再放"升级为"同向流水、对向错峰"。两个工程细节：（1）t2 = 通行时长 × 1.25 的余量有依据：窄道内实际速度受会车、转角影响，历史数据的 P95 通行时间才是正确采样目标；（2）对向窗口之间插入 gap = 2.5 s 的安全间隔，避免"前车刚出后车就进"在出口处擦碰。被拒绝时用 wait_until 定时等待，循环重试是禁止项：管理器既然算过可用时间，就把等待决策也交给它。最后一个隐含约束：窗口授予后机器人若中途故障停在道内，管理器必须能收到"卡住"通报（或租约超时）才能回收资源，因此窗口也要有租约语义，二者组合使用。

片段 3：多资源申请的退避重试

def acquire_all(manager, robot, needed, retries=5):
    """按全局资源序依次申请；失败则全部释放并随机退避重试。
    全局资源序 = 按资源编号排序申请，打破循环等待（死锁规避）。"""
    ordered = sorted(needed, key=lambda r: r.id)   # 编号升序，全队一致
    for attempt in range(retries):
        held = []
        ok = True
        for res in ordered:
            resp = manager.try_acquire(res.id, robot.id)
            if resp.granted:
                held.append(res)
            else:
                ok = False
                break                                # 有拿不到的：立即放弃已持有的
        if ok:
            return held                              # 全齐：返回进入执行
        for res in held:                             # 破坏“持有并等待”：全放掉
            manager.release(res.id, robot.id)
        backoff = random.uniform(1.0, 5.0)
        sleep_with_cancel(backoff)                   # 退避期间保持可被中断
    return None                                      # 重试耗尽：上报调度器改派

解读：acquire_all 把死锁规避的两个手段合在同一个小函数里：排序申请（打破循环等待）与 失败全放（打破持有并等待）。实践中二者留一即可，但两个都做几乎零成本，属于"安全带 + 安全气囊"式的冗余。三个细节：sorted 的键必须是全队一致的稳定编号（写进资源 YAML，不依赖加载顺序）；退避用随机区间，固定值会让多机同步重试撞在一起（这与以太网 CSMA 的指数退避同源）；重试耗尽后返回 None 并上报调度器，资源申请失败不是异常，是常态，系统必须有一条"任务改派或降级"的正常路径接住它。

常见坑

  • 租约没有过期机制：持有窄道的机器人断电，资源被"幽灵持有"，全场等到人工干预。修复：所有互斥资源一律走租约；管理器 1 Hz 清扫；清理事件写日志便于复盘。
  • 释放太早（人还没出窄道就 release）：下一台车收到授权进场，在出口处相撞。修复：释放前提是"物理离开"（出口传感器/里程计越界），并加 1–2 s 缓冲。
  • 时钟漂移下的租约双持有：持有者与管理器对"过期"判断不一致，窗口内两个持有者同时存在。修复：统一时间源；租期安全边际 ≥ 5 s；持有者本地看门狗（到点自停）兜底。
  • 无 ETA 的拒绝引发重试风暴：四台机器人 5 Hz 轮询同一个充电桩，服务端被打爆。修复：拒绝返回 retry_after；请求端用定时等待；对同一资源的重试频率限流。
  • 拿多个资源时顺序不一致：A 先拿充电桩再拿窄道、B 相反，两方各持一个互等。修复：全局资源序 + 超时回退；定期用静态检查扫描"申请顺序不一致"的调用路径。

练习与思考

  1. 窄道长 18 m，机器人速度 0.4 m/s，进出各需 3 s 转向。计算单次通行时间、建议租期与续租周期；若两端各有 2 台车排队，理想吞吐（台/分钟）是多少？★
    提示
    通行 ≈ 18/0.4 + 6 = 51 s，租期 60 s、续租 20 s；单向流水时吞吐 ≈ 60/51 ≈ 1.2 台/分钟；对向错峰要再加 gap，吞吐近似减半。
  2. 构造一个三资源死锁场景（机器人 A 持有 R2 等 R5、机器人 B 持有 R5 等 R2），说明为什么"按编号升序申请"能消除它，并写出如果 A 在拿 R2 成功、拿 R5 失败后的正确动作序列。★★
    提示
    升序申请下，持有 R5 时不可能再申请更小号的 R2，循环在规则层不成立；失败动作：release R2 → 随机退避 1–5 s → 重新从 R2 开始按序申请。
  3. 把窄道预约的窗口余量从 25% 改成 0%，用 ETA 误差 ±4 s 的导航数据仿真 100 次通行，预测"迟到作废"与"双车抢道"两类事件的数量变化，并解释余量、吞吐、安全性三者的权衡。★★
    提示
    余量 0 时 ETA 低估导致窗口截断（迟到作废率上升），高估导致资源闲置；更危险的是行程中变速使窗口尾部越界。余量本质是"用资源利用率买容错"，给定 ETA 分布后可解析算出推荐值。
  4. 设计电梯资源协议：容量 2 台、可重用、涉及楼层与门机时序。写出资源类型判定、租约参数（含门保持时间）、"有人按急停"时的回收流程，以及容量计数如何防止超载。★★★
    提示
    类型 = 容量受限时空资源；租约 = 预计到达 + 装载 + 行程 + 卸载 + 门机余量；急停时由管理器广播强制回收并置资源为维护态；容量计数在授予时预留名额，释放时归还，与普通信号量一致。

小结

  • 先定资源类型再定协议：独占可重用 → 租约；容量受限 → 计数信号量；时空冲突 → 预约窗口；一次性 → 带优先级的队列。
  • 租约 = 会过期的锁：期限 + 续租 + 本地看门狗，把"持有者崩溃"的最坏等待变成一个确定的上界；安全边际要覆盖时钟漂移。
  • 预约窗口让窄道流水线化：同向不重叠即可共存，对向加安全间隔；ETA 必须带余量，迟到作废防止幽灵预约。
  • 死锁规避两板斧：全局资源序（打破循环等待）与失败全放 + 随机退避（打破持有并等待）；申请失败是常态，要有改派路径。
  • 下一章把分配与资源合起来放进时间轴：顺序怎么排、并行怎么做、总工期怎么压，多机器人协同调度。
