第一篇 · Ray 基础与分布式编程

第 010 章：Ray与机器学习生态集成概览

把 Ray 核心之上的五个库放回一张图：Data 管数据、Train 管训练、Tune 管搜索、RLlib 管强化学习、Serve 管部署，先看清分工与组合方式，再决定作业该由谁主导。

  • 主题：Ray 生态 / 库层分工与组合
  • 关键机制：分层架构、库间协作（训练加搜索加服务）、资源预算共享
  • 预计学时：50 分钟
  • 前置章节：第 009 章

学习目标

  • 建立 Ray 库层的整体地图：五个库各自解决什么问题、建立在哪些核心原语之上。
  • 理解库间组合的三条主线：数据处理供给训练、搜索调度训练、检查点衔接部署。
  • 掌握资源预算在多层之间的分配方法，避免嵌套库重复占用导致排队。
  • 会根据任务特征选择入口库：自定义分布式算法用核心原语，监督训练用训练库，强化学习用 RLlib。
  • 能识别跨库协作中的版本与运行时环境陷阱。

背景与动机

前九章把 Ray 核心讲成了一个完整的工具集：任务、Actor、对象、依赖、资源、容错。但真实机器学习作业很少直接写核心原语，通常站在某种更高抽象上：数据管道、分布式训练器、超参搜索器、在线服务。Ray 生态把这四类抽象做成彼此可组合的库，统一共享底层的资源与容错机制。

组合带来选择困难：同一个需求（例如"把模型训练到目标精度"）可以从多个入口切入，入口选错会让后续每一步都别扭。更隐蔽的问题在资源层：外层库要资源，内层库也要资源，两份预算互相挤压时任务就开始排队。本章先建立全局地图与选择标准，后面三章分别深入 Data 与 Serve 的细节，RLlib 从第 015 章开始系统展开。

一句话定位：本章回答"谁管什么、怎么拼在一起"，各库的内部机制留给各自的专门章节。

核心原理

1. 分层地图：核心之上各管一段

库解决的问题建立在核心的哪些原语上
Data大规模数据读取、变换与批处理，流式执行任务图（每个块一个任务）、对象存储
Train把单机训练函数扩展到多进程多卡，统一检查点Actor（训练进程组）、放置组、对象引用
Tune多组超参的并行试验、调度与早停长驻试验进程（Actor 形态）、资源声明
RLlib强化学习训练循环：采样、学习、评估的分布式组织环境副本 Actor、训练进程、对象流转
Serve把模型发布为可伸缩的在线服务副本 Actor、路由、自动缩放

读这张表的方式是自上而下对照：每个库的并行度、资源与故障行为，最终都由核心原语决定。RLlib 的环境副本为什么是一个 Actor 池、Tune 的试验为什么占用整块资源、Serve 副本为什么能自动伸缩，答案都能在前九章找到。这也是先学核心的原因：库的行为不再神秘，只剩配置语法需要记忆。

2. 三条组合主线

库之间的协作可以归纳为三条数据流主线：

  1. 数据供给训练：Data 负责读取与预处理，产出分片数据集交给 Train 或 RLlib 消费。离线强化学习、行为克隆、监督预训练都走这条线。
  2. 搜索调度训练：Tune 作为外层驱动，把每一组超参变成一个试验，试验内部运行 Train 或 RLlib 的训练循环。外层管搜索与调度，内层管单次训练。
  3. 检查点衔接部署：训练产出的检查点由 Serve 加载并提供在线推理。检查点格式是两层之间的接口契约，接口不稳定就会在部署时暴露。
完整作业 = Data（供给）+ 训练库（Train 或 RLlib）+ Tune（搜索）+ Serve（发布） 各层按需选用；用到的层共享同一份资源预算

主线之间通过两类媒介对接：数据集（Dataset）与检查点（Checkpoint）。把这两类媒介的格式与位置约定清楚，是跨库协作设计的主要工作量。经验做法是让检查点包含"模型权重、结构描述、预处理参数"三件套，Serve 侧不依赖训练代码的其余部分即可还原服务。两类媒介的约定各有侧重：数据集约定"分片方式、列名与类型、样本权重语义"，检查点约定"目录结构、权重键名、版本号"；把约定写成简短的接口文档放进仓库，协作方按文档对接，比口头约定可靠得多，接口评审时逐字段过一遍。

3. 资源预算：嵌套层的分配原则

嵌套组合时，资源声明会出现两层账本：外层库要向集群声明试验或训练组的总预算，内层进程再从这个预算里细分。常见错误是两层各自按"我要多少"申报，总量超过集群容量，表现为部分任务永久排队。分配原则有三条：

  • 总量守恒：外层声明的总核数与显存数，不小于内层全部角色的声明之和；留出协调进程的余量。
  • 单一来源：内层角色数由外层参数推导（例如试验数乘以每试验的采样进程数），不要让两层各自独立配置。
  • 并行度上限对齐：外层并发试验数与内层单试验占用相乘，不应超过集群容量，否则搜索效率会被排队吞掉。

这三条在第 030 章（RLlib 与 Tune 集成）、第 066 章（资源与显存调优）会反复用到，本章先把框架立起来。

用 RLlib 加 Tune 的组合演示"单一来源"的推导：外层希望同时跑 T 个试验，每个试验需要 E 个环境副本、1 个学习器与 1 核协调预留。集群核数 C = 128、目标 T = 8 时，约束式 T × (E + 2) ≤ C 给出 E ≤ 14。把 E 写死为 16 会让每个试验占 18 核，8 个试验共需 144 核，最后 1 个试验长期排队。正确做法是从"目标试验数、集群容量、预留量"三个已知量反推 E，让内层参数成为外层的因变量，两层各自写死数值的组合迟早会超编。

4. 选择入口：从任务特征出发

  • 任务是自定义分布式算法（例如自研的参数同步协议）：直接用核心原语，任务与 Actor 是合适的抽象层。
  • 任务是监督学习的大规模训练（图像分类、推荐模型）：用 Train，天然获得多进程多卡扩展与检查点管理。
  • 任务是强化学习：用 RLlib，环境采样与学习循环的分布式组织已经内建。
  • 任务是找超参：用 Tune 包裹上述任一训练库，搜索算法与调度器直接复用。
  • 任务是发布模型：用 Serve，副本管理与批处理能力开箱可用。

选择标准是"任务的核心复杂度在哪"：复杂度在算法内部，用核心原语保持透明；复杂度在扩展与工程，用对应库吸收。选错入口的最小代价是写一堆本该由库提供的胶水代码，最大代价是并行结构与调度语义冲突。

5. 数值算例：试验调度、嵌套乘法与检查点体积

片段 3 的 9 组试验在 16 核集群上执行，每试验声明 4 核，同时并发 4 个试验。设单试验时长相同，9 组按 4、4、1 分三批推进：三批共提供 48 个核轮，实际只用了 36 个，整机利用率折算为 36 ÷ 48 = 75%。

试验数并发槽位（16 ÷ 4）批次数整机利用率
943（4+4+1）75%
1243（4+4+4）100%
842（4+4）100%

搜索空间的试验数取并发槽位的整数倍，可以消掉最后一批的空转；9 组的第三批把 12 个核闲置。嵌套乘法给出一条预算不等式：并发试验数 × 单试验核数 ≤ 集群核数 − 驱动预留。某作业设并发试验 8、单试验 8 个采样进程，需求 64 核而集群只有 32 核，有效试验并发被压到 4，资源满足度 32 ÷ 64 = 50%，排队中的试验既占元数据又拉长反馈周期。修复有两条：并发试验降为 4，或单试验进程降为 4；改哪一侧取决于"搜索广度"与"单试验收敛速度"哪个更关键。

检查点的体积账要提前算。设模型 5000 万参数、单精度存储，权重约 200 MB；Adam 优化器保存一阶与二阶动量，约 400 MB；合计每次检查点约 600 MB。若 9 个试验每个 epoch 都保存，15 轮共 9 × 15 × 600 MB = 81 GB；改为每 5 轮保存并保留最优，降至约 16 GB，约为原方案的五分之一。检查点频率在"恢复粒度"与"存储带宽成本"之间取值，练习 5 的契约设计也要受同一约束：字段越多，单次落盘越重，最小字段集合同时服务恢复、搜索、上线三个场景。

实现思路与设计

把一次完整作业落到库组合上的步骤：

  1. 拆任务阶段：列出数据准备、训练、搜索、评估、发布五个阶段，标注每个阶段的规模量级。
  2. 逐阶段选库：用上一节的选择标准逐段定库，跨阶段媒介（数据集与检查点）单独约定格式。
  3. 画资源总账：自上而下分配预算，核对总量守恒；把嵌套参数改成单一来源推导。
  4. 统一运行时环境：全部阶段使用同一套依赖描述，版本按成套组合锁定。
  5. 先小后大：用最小规模（2 个试验、4 个采样进程）打通全链路，再放大到目标规模。

版本成套的原则可以落成一条操作细则：把 Ray、上层库、深度学习框架与 CUDA 驱动记成一张四行版本表，写进作业仓库的依赖描述文件；升级时先改表、再改环境，两个动作放在同一次提交里。跨库接口（检查点格式、指标通道、数据集序列化）在版本之间可能漂移，升级验证先跑最小链路（2 个试验、每试验 4 个进程），确认通过再放大规模。

组合典型参数作用取值依据
Tune 试验数20–200搜索广度搜索空间维度与单试验耗时折中
单试验训练进程4–16内层并行度模型规模决定单进程显存档位
Data 并行读任务8–64数据吞吐存储带宽与块大小决定并发上限
Serve 副本数2–8在线吞吐与冗余请求速率除以单副本吞吐，留冗余
与上一章的差异点

第 009 章的恢复机制针对单个实体（任务、Actor）；本章引入的跨库作业把恢复责任分层：训练库管自身检查点，Tune 管试验级恢复，Serve 管副本替换。理解分层责任，故障时才知道该看哪一层的日志。日志查看顺序也遵循同一层次：单试验内部异常看训练库日志，试验被中止看搜索层日志，副本反复重启看服务层日志。

关键代码与解读

以下片段采用 Ray 2.x 时期的通用写法；接口随版本演进，以对应版本官方文档为准。

片段 1：同一次数据变换，验证库层的价值

import ray
from ray import data

ray.init(num_cpus=8)

# 库层写法：声明式变换链，执行被自动并行化与流式化
ds = (data.read_parquet("/data/offline/train-*.parquet")
      .map(lambda row: {"obs": row["obs"], "rew": float(row["reward"])})
      .filter(lambda row: row["rew"] > 0.0)     # 只保留正收益样本
      .repartition(16))                          # 分为 16 个并行块供下游消费

print("数据行数:", ds.count())                    # 触发执行：并行读取全部文件
shards = ds.split(4)                              # 切成 4 份，各供一个训练进程使用
print("分片数:", len(shards))

解读：这段代码的价值不在语法，而在层级的跃迁。同样的逻辑用核心原语写需要手工分块、提交任务图、汇总结果；库层把这些模式固化成声明式算子，并行度、执行顺序与内存管理由库统一负责。对强化学习场景，这条数据路径服务于离线训练（第 027 章行为克隆）：历史轨迹从存储读取、过滤、分片，直接喂养训练循环。样例行数与分片数都采用惰性执行，只有 count 与消费动作才真正触发计算。

片段 2：训练库的最小骨架

import ray
from ray import train
from ray.train import ScalingConfig
from ray.train.torch import TorchTrainer

def train_loop_per_worker(config):
    import torch
    # 训练库负责把进程组、设备绑定与数据分片准备就绪
    model = torch.nn.Linear(64, 1)
    opt = torch.optim.Adam(model.parameters(), lr=config["lr"])
    for epoch in range(config["epochs"]):
        # 一段内联的最小训练步：让片段自包含，无需外部数据源
        x = torch.randn(256, 64)
        y = torch.randn(256, 1)
        loss = torch.nn.functional.mse_loss(model(x), y)
        opt.zero_grad()
        loss.backward()
        opt.step()
        train.report({"loss": float(loss)})          # 指标上报走统一通道

trainer = TorchTrainer(
    train_loop_per_worker,
    train_loop_config={"lr": 1e-3, "epochs": 20},
    scaling_config=ScalingConfig(num_workers=8, use_gpu=True),  # 8 进程并行
)
result = trainer.fit()                    # 分布式执行由库层编排
print("检查点:", result.checkpoint.path)   # 检查点路径即跨库接口

解读：训练函数按"单进程视角"编写，扩展细节全部收进 ScalingConfig，这是训练库层的核心设计：把"写一次逻辑、运行在 N 个进程"固化成接口。对强化学习读者，这份骨架的价值是参照系：RLlib 的配置对象与它异曲同工，只是训练循环内部换成了采样加策略更新。返回结果中的检查点路径是衔接部署的契约，下一段把它交给搜索层。

片段 3：搜索层包裹训练，检查点作为媒介

from ray import tune
from ray.tune import Checkpoint

def build_model(hidden):
    import torch
    return torch.nn.Sequential(torch.nn.Linear(64, hidden), torch.nn.ReLU(),
                               torch.nn.Linear(hidden, 1))

def single_process_train_step(model, opt):
    import torch
    x, y = torch.randn(256, 64), torch.randn(256, 1)
    loss = torch.nn.functional.mse_loss(model(x), y)
    opt.zero_grad()
    loss.backward()
    opt.step()
    return float(loss)

def tune_trainable(config):
    """试验入口：单组超参对应一次完整训练。"""
    import torch
    model = build_model(config["hidden"])
    opt = torch.optim.SGD(model.parameters(), lr=config["lr"])
    for epoch in range(15):
        loss = single_process_train_step(model, opt)
        # 每个试验自带保存目录：检查点落盘在试验隔离的空间内
        ckpt = Checkpoint.from_dict({"weights": model.state_dict()})
        tune.report({"loss": loss}, checkpoint=ckpt)

tuner = tune.Tuner(
    tune_trainable,
    param_space={"lr": tune.grid_search([1e-4, 5e-4, 1e-3]),
                 "hidden": tune.grid_search([64, 128, 256])},   # 9 组组合
    run_config=tune.RunConfig(storage_path="/data/tune_runs"),
)
results = tuner.fit()                 # 9 个试验按资源自动排队执行
best = results.get_best_result(metric="loss", mode="min")
print("最优试验检查点:", best.checkpoint.path)

解读：三层在此处各就各位：Tune 负责把 9 组超参变成 9 个互相隔离的试验并调度资源，试验内部的训练逻辑来自上一段的模式，检查点作为产物被统一收集。搜索空间用 grid_search 示意，真实搜索用随机采样或贝叶斯优化（第 057、058 章）；每试验的检查点落在隔离目录，避免并发试验互相覆写，这是跨试验隔离最基本的纪律。get_best_result 按指定指标选出优胜者，其检查点路径随后交给 Serve 做发布，闭环完成。

常见坑

  • 版本不成套：单独升级某个子库而 Ray 主体保持旧版，接口错位以运行时报错或静默行为变化的形式出现。修复：按官方发布的成套组合锁定版本，升级整组进行。
  • 嵌套层资源总量超编：外层试验并发数与内层训练进程数各自配置，乘积累积超过集群容量。修复：内层参数由外层推导，画资源总账核对守恒。
  • 库内重复初始化集群：训练函数或试验入口内部再次调用 ray.init，连接冲突或产生孤立集群。修复：集群初始化只在驱动入口执行一次，全程复用。
  • 驱动进程直接读大数据：用通用表格工具在驱动进程里整表加载，内存暴涨且毫无并行。修复：数据读取交给数据层，训练侧只消费分片或批迭代器。
  • 检查点契约含糊：训练与部署各自理解检查点格式，发布时才发现缺字段。修复：检查点内容三件套（权重、结构描述、预处理参数）显式约定并做跨库验证。

    依次对应数据层、训练库、搜索层、服务库、核心原语。理由围绕"核心复杂度在数据、在扩展、在搜索、在发布、在协议本身"。
  2. 预测题：片段 3 的搜索空间在 16 核集群上执行，每个试验声明 4 核。预测同时并发执行的试验数，以及总调度轮次。★
    提示
    16 除 4 得 4 个并发试验，9 组试验分三轮左右完成。若并发上限设为 1，探索时间将成倍增加，搜索吞吐正是由这个乘法关系决定。
  3. 设计题：为一个"离线数据加监督预训练加强化学习微调加在线发布"的完整链路画库组合图，标注各层之间的媒介格式与资源预算分配。★★
    提示
    数据层产分片数据集，训练库与 RLlib 消费；搜索层包住微调阶段；检查点三件套交给服务层。预算自外向内逐层细分，媒介格式成文约定。
  4. 分析：某作业把外层试验并发设为 8，每个试验内又声明 8 个采样进程，共需 64 核，而集群只有 32 核。描述实际执行形态（哪些任务排队、利用率如何分布），并给出两种修复方案。★★
    提示
    实际并发试验数被资源饱和压到一半，其余试验排队；单试验内部也可能因资源碎片无法满配。修复：并发试验数与单试验进程数按乘法关系重排，或提高集群容量。
  5. 设计：为跨库作业定义检查点契约：列出最小字段集合，说明每个字段在恢复训练、继续搜索、上线服务三种场景中的作用，并设计一个校验用例。★★★
    提示
    字段至少含模型权重、网络结构描述、优化器状态、预处理参数与版本号。校验用例：仅用检查点与版本头文件，在服务侧加载并跑通一次示例推理。
