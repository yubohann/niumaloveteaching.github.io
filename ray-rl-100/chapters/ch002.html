第 002 章：Ray远程函数与Actor基础

Ray 只有两种执行原语：一次性的远程函数与长期存活的有状态 Actor。本章讲清两者的调度语义差异，以及"状态该放在哪里"这个设计问题的判定标准。

  • 主题：Ray 核心 / 两大执行原语
  • 关键机制：任务调度语义、Actor 方法队列、句柄传递、并发语义
  • 预计学时：55 分钟
  • 前置章节：第 001 章

学习目标

  • 理解远程函数（Remote Function）的调度语义：每次调用独立调度、无状态、可重试、执行位置不保证。
  • 理解 Actor 的调度语义：创建时锁定资源、方法调用经队列串行执行、状态在进程存活期间保持。
  • 掌握"状态放函数还是放 Actor"的判定标准，并能解释全局变量在远程函数中失效的原因。
  • 会写带状态的服务型 Actor，并理解 Actor 句柄（Handle）的序列化传递机制。
  • 能诊断两类典型问题：方法队列阻塞与 Actor 生命周期失控。

背景与动机

并行程序的核心困难是状态：哪些计算可以随意复制到任意进程，哪些计算必须固定在某个进程里累积状态。Ray 用两种原语切开这条边界。远程函数面向"可复制的纯计算"，Actor 面向"需要累积状态的实体"。混淆两者是分布式程序中最隐蔽的错误来源之一：把状态塞进远程函数，代码在单机测试时正常，上集群后结果随调度顺序漂移。

在强化学习训练链路里，这个区分无处不在：环境推进是有状态的（每一步改变环境内部状态），必须住在 Actor 里；一段奖励整形函数、一次优势估计、一批梯度聚合是无状态的，适合做远程函数。RLlib 内部的采样器（Sampler）、回放缓冲（Replay Buffer）也都按这一标准分别落在 Actor 与任务两种形态上。

本章把两种原语的语义讲透，并给出一条可操作的判定标准，后续章节的对象存储、并行池、异步接口都以此为基础展开。

核心原理

1. 远程函数：可复制、可重排、无状态

远程函数的语义可以浓缩为一句话：每次调用都是一次独立的任务，任务之间互不可见。这带来三个推论：

  • 执行位置不保证：同一个函数的前后两次调用可能落在不同机器、不同进程上。函数内定义的局部变量在任务结束后销毁。
  • 可重试性成立：因为无状态，节点故障后任务可以在别的节点重新执行，结果不受影响（第 009 章展开容错）。
  • 可重排性成立：调度器认为任务之间无依赖，可以按任意顺序、任意并行度执行。这也是远程函数天然并行、Actor 默认串行的根源。

关键陷阱在于 Python 的全局变量。工作进程是长期存活的进程，远程函数被反复调用时，模块级变量会在同一个进程内"看起来"被保留，但下一次调用可能换到另一个进程，取值随即归零或错乱。依赖全局变量的远程函数行为随调度波动，必须视为错误设计。

2. Actor：一次创建，长期存在的串行服务

Actor 的语义是把一个 Python 对象放进专属工作进程：

  1. 创建即占资源：Counter.remote() 在创建时按类装饰器声明的规格锁定 CPU/GPU，直到 Actor 销毁才释放。资源占用是持久的，这与任务"用完即还"截然不同。
  2. 方法调用排队：同一 Actor 的方法调用进入一个先进先出的队列，默认串行执行。任何两个方法不会交叠，因此方法内部读写实例变量无需加锁。
  3. 状态持续累积：实例变量在多次方法调用之间保持，这正是环境副本、计数器、回放缓冲需要的行为。
  4. 句柄可传递：Actor 句柄（ActorHandle）本身可以序列化，作为参数传给其他任务或其他 Actor。远程进程拿到句柄后即可调用该 Actor 的方法，调用路径与调用方位置无关。
方法队列执行时间 ≈ T₁ + T₂ + … + Tn（串行） 默认并发度为 1；单次方法耗时过长会把后续调用全部堵在队列中，这是单 Actor 吞吐的硬上限

串行队列既是安全边界也是吞吐瓶颈。它免去了锁与竞态，代价是所有方法共享一条执行流。需要更高并发时有两类手段：增加 Actor 副本把负载分片（第 005 章），或声明方法为异步执行（第 006 章）。

从实现层面看，Actor 方法调用走的是"确认加应答"协议：调用方发出请求后立即拿到对象引用，方法真正执行完成后结果被写入对象存储。这个协议与远程函数一致，因此 ray.get、ray.wait、依赖调度这些机制对两者通用。

3. 选用标准：状态在谁身上

判定口诀：计算前后需要"记得住"的东西，就用 Actor；一次调用内能自洽算完的，就用远程函数。介于两者之间的场景（例如每步推进都需要环境的随机数流）应按最强约束选 Actor，因为状态一致性比并行自由度更难事后补救。

判定标准之外还有一类混合形态值得单独识别：计算逻辑本身无状态，但初始化成本高昂（加载大模型权重、建立数据库连接、编译计算图）。每次调用都重新初始化会让固定成本压过收益，此时把初始化结果放进 Actor，让它以"缓存服务"的形态存在，方法调用只做查询与轻量变换。口诀可以扩展为第二句：无状态但初始化昂贵的组件，用 Actor 承载缓存，用远程函数做批量计算。RLlib 中策略推理服务（Policy Server）正是这一形态，第 020 章会把它的接口完整展开。

4. 数值算例：方法队列的等待放大

设某缓冲 Actor 单次方法的平均服务时长 s = 0.5 ms（对应吞吐上限 μ = 2000 次/秒），64 个生产者以合计 λ 的速率并发写入。服务时长近似固定、到达过程近似泊松时，等待时间可用 M/D/1 排队模型估算：平均排队等待 Wq = ρ × s ÷ (2 × (1 − ρ))，平均逗留时间 W = s + Wq，其中利用率 ρ = λ ÷ μ。系统内的平均排队长度约为 λ × W。

Wq = ρ s ÷ (2 (1 − ρ))，W = s + Wq，ρ = λ ÷ 2000 ρ → 1 时等待时间发散：利用率每逼近上限一档，延迟放大倍率增长更快

实现思路与设计

把一个待实现的组件落到两种原语上的设计步骤：

  1. 梳理状态：列出组件内所有跨越调用的变量（环境内部状态、随机数生成器、计数器、缓冲区）。列表非空即倾向 Actor。
  2. 评估调用频率与单次耗时：Actor 的吞吐上限由单次方法耗时决定；若单次耗时是瓶颈且状态可分片，就设计成 N 个 Actor 并行。
  3. 声明资源：函数在装饰器上声明单次调用需求；Actor 在类装饰器上声明持久需求。Actor 的声明值按峰值需求取，因为运行中不可回收。
  4. 规划生命周期：明确 Actor 何时创建、由谁持有、何时销毁。持有句柄的进程退出或句柄引用被回收后，Actor 可能连带销毁。
  5. 设计重试边界：无状态任务可放心重试；Actor 需要显式配置重启策略并承担状态重置的代价（第 009 章）。

Actor 生命周期与重试语义

生命周期部分需要补充三条运行时规则。其一，句柄引用计数决定存活：创建者与所有持有句柄的进程都丢弃引用后，Actor 会被自动销毁；把句柄存在局部变量里且函数返回，等同于发出销毁信号，跨调用复用必须让句柄在存活期被持续引用。其二，命名或分离模式：通过命名注册（namespace 加命名参数）创建的 Actor 可以脱离创建者存活，适用于跨作业复用的服务型实例，代价是销毁责任转移给使用方，忘记清理会留下长期占用资源的孤儿 Actor。其三，资源锁定在销毁前不释放：4 张显卡的机器上创建第 5 个声明 num_gpus=1 的 Actor 会永久排队，前 4 个不销毁就不会归还配额；ray.available_resources() 显示 GPU 为 0、进程状态却一切正常，这类"假死"用 ray list actors 核对常驻声明值即可定位。

重试语义在两种原语之间是非对称的。任务因节点故障默认自动重试（上限与版本相关，通常为 3 次），应用层异常不会被重试，会在 ray.get 取回时以异常形式抛出；Actor 默认不重启也不重试方法（重启与任务重试参数默认都是 0），进程崩溃即状态全部丢失。需要状态延续的 Actor 必须显式声明重启参数，并在"从上一次检查点恢复"与"清零重建"之间明确选择一种语义，这个选择在第 009 章结合回放缓冲与采样器再次出现。

与上一章的差异点

第 001 章的任务在结束后释放资源、丢弃全部上下文；本章的 Actor 引入持久资源占用与状态延续。资源账本的视角随之改变：Actor 越多，常驻占用越高，空闲 Actor 同样是成本。

设计示例：把一个环境副本落到 Actor 上

以强化学习环境副本为例走一遍五步流程，检验判定标准是否可操作。状态清单：环境当前观测、内部随机数生成器、累计步数与回合统计，四者都跨调用存活，判定落在 Actor。调用频率与耗时：单步推进为亚毫秒级，一个回合需要数千步，单 Actor 每秒可承载的步数即为采样吞吐上限，副本数按目标吞吐除以单副本步速反推。资源声明：环境推进以 CPU 计算为主，声明 num_cpus=1；若观测渲染需要 GPU，按峰值声明并在训练全程持有。生命周期：与训练流程同生共死，创建发生在训练开始前，销毁在训练结束或异常处理路径中显式执行。重试边界：环境内部状态无法从故障中恢复，因此不声明自动重启，由上层重建实例并重置。接口清单落为三项：reset()、step(action)、stats()。这份清单与 RLlib 环境执行器（EnvRunner）的职责划分一一对应，第 015 章的环境接口实现将逐项落地，第 023 章则讨论采样阶段的批次切分。

关键代码与解读

以下片段采用 Ray 2.x 时期的通用写法；接口随版本演进，以对应版本官方文档为准。

片段 1：远程函数无状态性的实证

import ray

ray.init(num_cpus=4)

@ray.remote(num_cpus=1)
def count_with_global(x):
    global_counter[0] += x     # 试探性依赖模块级可变对象
    return global_counter[0]

@ray.remote(num_cpus=1)
def count_local(x):
    return x + 1               # 无状态：结果只由参数决定，与执行位置无关

refs = [count_local.remote(i) for i in range(8)]
print(ray.get(refs))  # [1, 2, 3, 4, 5, 6, 7, 8]，与调度顺序无关

# 同一函数连续调用两次，观察两次读取到的"全局状态"是否一致
a = ray.get(count_with_global.remote(1))
b = ray.get(count_with_global.remote(1))
print(a, b)  # 可能为 1 2，也可能为 1 1：取决于两次调用是否落进同一进程

解读：留意两个函数的对比。count_local 的输出只由输入参数决定，无论调度器把它放到哪个进程、哪个节点，结果恒等，这就是可重试与可重排的物理基础。count_with_global 的返回值依赖执行进程的局部历史，两次同样的调用可能返回同样结果（落进同一进程）或不同结果（换到另一个进程），行为不可预测的根源是进程边界由调度器决定，全局变量只是暴露这一事实的载体。分布式程序里任何"记得住"的意图都必须显式建模为 Actor 状态或对象存储中的对象。

片段 2：计数器 Actor 与串行语义

import ray

ray.init(num_cpus=4)

@ray.remote
class StepCounter:
    def __init__(self, name):
        self.name = name
        self.total = 0            # 实例状态：在 Actor 存活期间持续累积

    def add(self, n):
        self.total += n           # 方法默认串行执行，读写无需加锁
        return self.total

    def snapshot(self):
        return self.name, self.total   # 快照接口：便于外部观察当前状态

counter = StepCounter.remote("env-0")   # 创建即占用资源，返回句柄

# 提交多次调用：它们按先进先出顺序在该 Actor 内执行
refs = [counter.add.remote(i) for i in range(1, 5)]
print(ray.get(refs))          # [1, 3, 6, 10]：调用顺序决定累加顺序
print(ray.get(counter.snapshot.remote()))   # ('env-0', 10)

# 两个独立 Actor 完全并行：状态互不干扰，编号即分区键
envs = [StepCounter.remote(f"env-{i}") for i in range(4)]
ray.get([envs[i].add.remote(1) for i in range(4)])
print(ray.get([e.snapshot.remote() for e in envs]))

解读：这份代码展示了 Actor 的三条语义。第一，队列顺序即执行顺序：四个 add 调用虽同时提交，但在 Actor 内严格串行，返回值 1、3、6、10 对应累计过程，任何两个调用不会交错。第二，状态与身份绑定：编号 env-0 到 env-3 的四个实例各自持有独立计数，这正是环境副本、分片统计的标准建模方式。第三，句柄是唯一访问入口：外部只能通过方法读写状态，无法绕过队列直接触碰实例变量，状态一致性由运行时保证。

片段 3：句柄跨进程传递

import ray

ray.init(num_cpus=4)

@ray.remote
class ReplayBuffer:
    def __init__(self):
        self.items = []

    def push(self, sample):
        self.items.append(sample)
        return len(self.items)

@ray.remote(num_cpus=1)
def producer(buffer, sample_id):
    # buffer 是 ActorHandle：参数序列化时只传"访问凭据"
    size = ray.get(buffer.push.remote({"id": sample_id, "obs": [0.1] * 8}))
    return sample_id, size

buffer = ReplayBuffer.remote()          # 创建唯一缓冲实例，集中持有全部样本
refs = [producer.remote(buffer, i) for i in range(8)]
print(ray.get(refs))   # 8 个生产者并发写入同一缓冲，由 Actor 队列保证顺序安全

解读：本片段是后续"分布式采样加集中缓冲"模式的雏形。关键机制在于 buffer 作为参数被序列化时，传递的只是 Actor 句柄，对象内容留在原进程，因此 8 个生产者进程可以并发调用同一个缓冲 Actor，写入顺序由队列裁定，数据始终只有一份。把"聚合点"建模为单一 Actor，可以避免每个生产者各持一份副本导致的合并开销；代价是聚合 Actor 成为吞吐瓶颈，拆分方案与队列治理留到第 005 章讨论。

常见坑

  • 用远程函数模拟有状态服务：把计数、缓冲、环境状态放进模块级变量或函数属性，单次运行内看似正常，任务被调度到其他进程后状态散落。症状是统计值随机偏小、环境重置行为异常。修复：迁移为 Actor。
  • 长方法堵死 Actor 队列：单次方法调用耗时过长，后续所有调用排队等待，表现为 P99 延迟剧烈恶化。修复：拆分方法、增加 Actor 副本，或对 IO 型方法启用并发（第 006 章）。
  • 为每次调用创建新 Actor：把 Actor 当廉价对象，循环内反复创建，导致资源申请与进程启动开销叠加，且失去状态累积的意义。修复：Actor 在循环外创建一次，循环内复用句柄。
  • Actor 生命周期意外终结：创建句柄后没有在存活进程中保留引用，解释器回收句柄，Actor 被判定为无人引用而销毁。症状是"忽然调用失败"或状态被重置。修复：在驱动进程显式持有句柄，或使用命名 Actor 并理解其引用规则。
  • 在 Actor 方法内长时间阻塞等待外部引用：方法内部调用 ray.get 等待另一个未就绪任务，整个队列被占用，形成互相等待。修复：先取回依赖再进入 Actor 调用，或改用异步 Actor。

  2. 预测：把片段 2 中四个 add 调用的提交顺序改为 4、3、2、1，snapshot 的返回值是多少？如果换成四个独立 Actor 并行累加，最终总计数是多少？★
    提示
    单 Actor 串行下最终值仍是 10，中间快照不同；四个独立 Actor 每人加 1，总和为 4，聚合需要额外一层汇总调用。
  3. 设计题：实现一个"滑动窗口统计器"，持续接收延迟样本，维护最近 100 个样本的均值与最大值。说明为什么它必须是 Actor，并给出接口清单与状态变量列表。★★
    提示
    窗口是跨调用累积的状态；接口至少包含 add(sample)、stats()、reset()。内部用双端队列维护窗口并增量更新统计量，避免每次重算。
  4. 分析：某流水线用 64 个生产者任务向单个缓冲 Actor 写入，平均每个样本写入耗时 0.5 毫秒。估算该 Actor 的每秒写入上限，并给出两种提升吞吐的分片策略。★★
    提示
    串行队列上限约 2000 次/秒。分片策略：按生产者编号取模分配到 4–8 个缓冲 Actor，或按批次写入让单次方法承载多样本，用批量摊薄每样本开销。
  5. 判断题：下列组件在强化学习训练链路中各应设计为远程函数还是 Actor，并陈述理由：奖励整形函数、环境副本、优势估计、梯度聚合、随机种子管理器。★★★
    提示
    环境副本与随机种子管理器持有跨步状态，选 Actor；梯度聚合若需要多轮累积状态选 Actor，单轮归约可用远程函数；奖励整形与优势估计是无状态变换，选远程函数。

小结

  • 远程函数语义：每次调用独立调度、执行位置不保证、无状态、可重试；依赖全局变量即错误设计。
  • Actor 语义：创建时锁定资源、方法经队列默认串行、状态跨调用保持；句柄可跨进程传递。
  • 判定标准：跨调用需要"记得住"的状态就放 Actor，单次调用能自洽算完的计算就放远程函数。
  • Actor 的串行队列既是免锁的安全边界，也是单实例吞吐上限；瓶颈出现时用分片或异步化解。
