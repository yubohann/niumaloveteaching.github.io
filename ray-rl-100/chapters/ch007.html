第 007 章：Ray集群配置与启动

从本机单进程集群走向多机集群：头节点与工作节点的分工、端口与目录的规划、驱动进程的连接方式，以及如何在集群上验证"任务真的跑在了别的机器上"。

  • 主题：Ray 核心 / 多机部署与初始化
  • 关键机制：头节点角色、节点注册、端口规划、运行时环境（Runtime Env）
  • 预计学时：55 分钟
  • 前置章节：第 006 章

学习目标

  • 理解集群拓扑：头节点承担的控制面职责与工作节点的计算面职责，以及单点风险的边界。
  • 掌握手工启动流程：头节点启动、工作节点注册、状态核对三步的标准命令与参数含义。
  • 会做端口与目录规划：控制面端口的开通范围、临时目录的磁盘选择。
  • 掌握驱动进程的两种连接方式（自动发现与显式地址），以及运行时环境对依赖一致的保障。
  • 能在集群上验证任务分布，诊断"任务全挤在一台机器"类问题。

背景与动机

本机模式的资源上限就是单台机器的核数，训练吞吐到顶后无法再扩展。跨机之后，资源池从"一台机器"变成"一组机器"，但随之而来的是新问题：哪个进程负责全局协调，节点之间怎么发现彼此，任务怎么落到正确的机器上。Ray 集群的启动过程本质上是把第 001 章的运行时组件按节点角色重新摆放：控制面收敛到头节点，数据面均摊到各工作节点。

手工启动是理解集群行为的最短路径：亲手执行过头节点与工作节点的启动命令，再看到节点出现在状态列表中，对后面自动缩放（Autoscaling）与故障恢复的机制就有了具体参照。RLlib 的大规模采样与 Tune 的分布式试验调度，都以本章的集群形态为运行基座。

本章覆盖拓扑分工、启动流程、端口规划、连接方式与验证方法五部分，自动扩缩容留到第 008 章。

核心原理

1. 拓扑分工：控制面与计算面

Ray 集群由一个头节点（Head Node）与若干工作节点（Worker Node）组成，各节点的进程布局如下：

节点角色常驻进程职责
头节点GCS、调度单元、对象存储、仪表盘、驱动进程（通常）全局状态、Actor 注册、节点管理、提交训练任务
工作节点调度单元、对象存储、工作进程执行任务与 Actor，本地资源记账

控制面集中在头节点的设计带来两个推论：其一，头节点故障影响全局，训练任务部署时应配合快照与重启机制（第 009 章展开）；其二，头节点的计算资源应与工作节点分开规划，驱动进程与作业提交本身要占用核数与内存，把训练负载也全压在头节点上会加剧单点压力。常见做法是头节点只做协调，或者接受头节点同时也作为计算节点但预留弹性。

2. 节点注册：工作节点如何加入

工作节点的启动命令携带头节点地址，启动过程中完成三件事：

  1. 连接与注册：工作节点向头节点的 GCS 注册自身，上报本机资源探测结果（核数、显存、自定义资源）。
  2. 服务拉起：工作节点本地拉起调度单元与对象存储，准备接受任务分派与对象存储。
  3. 心跳维持：此后节点与 GCS 之间保持心跳，心跳超时会触发节点移除与资源回收流程，这正是第 009 章故障检测的输入。
集群总资源 = Σ 各节点资源声明；任务调度只在声明范围内进行 4 节点 × 16 核 = 64 核总容量；节点资源声明与实际物理配置不一致是扩容事故的常见源头

资源探测在容器环境里可能读不到宿主机的真实配置（受编排平台限制），启动参数允许显式覆盖核数与显存，显式声明优先于自动探测，也是保证跨节点配置一致的最简单手段。

3. 地址、端口与目录

控制面通信依赖一组固定端口，集群规划时需在节点间防火墙放行：

  • GCS 端口：控制面主端口，工作节点注册与状态同步走这里；
  • 调度单元端口段：节点间任务分派使用，通常为一段连续区间；
  • 对象管理器端口：跨节点对象传输使用；
  • 仪表盘端口：集群状态可视化，仅需对管理网络开放。
通道默认端口口径放行范围
控制面与 GCS固定端口（常见默认 6379）全部节点之间
仪表盘固定端口（常见默认 8265）仅管理网络
节点与工作进程从高位区间自动分配节点之间按区间整体放行

端口号随版本与配置变化，以对应版本官方文档为准；规划的要点是把"自动分配的高位区间"整段放行，逐端口申请的方式在节点扩容后必然遗漏，故障以"注册成功但任务无法分派"的形态出现。

临时目录同样需要规划。运行时会在临时目录下放置套接字与溢写文件，默认位置可能落在容量较小的系统盘上。大规模任务的溢写量可达数十 GiB，临时目录应显式指向大容量数据盘，且各节点路径保持一致，便于日志与排障。

4. 驱动连接与依赖一致

驱动进程通过 ray.init(address="auto") 自动发现本机已启动的集群，适合在集群节点上提交作业的场景。连接方式决定了运行边界：

  • 集群内提交：驱动跑在某个集群节点上，使用自动发现，适合长作业与需要读取本地数据集的场景。
  • 集群外提交：驱动在开发机上，使用显式地址连接远程头节点，适合调试；开发机退出即作业中断，长训练不建议。
连接方式驱动位置生命周期绑定适用场景
自动发现集群内某节点与该节点上的进程绑定长训练作业、数据本地读取
显式地址集群外开发机与开发机会话绑定短时调试、临时验证
作业提交接口由集群托管由集群作业系统管理生产流程、断线保活

三者的关键差别是"谁为驱动的存活负责"：自动发现模式下节点进程退出即驱动消失；显式地址模式下开发机断网即作业中断；作业提交接口把驱动托管进集群，是生产环境的常见选择。

依赖一致依靠运行时环境（Runtime Environment）机制：作业可以声明自己的 Python 依赖或工作目录，运行时负责把依赖分发到涉及的节点，并在进程启动前激活。集群节点的基础环境保持干净、作业依赖由描述文件声明，是避免"某台机器版本不对"的标准实践。

5. 数值算例：从训练需求反推节点数量的容量账本

集群规模由训练需求反推，按四步核算。第一步定需求吞吐：每轮需要 1000000 环境步，轮时间预算 20 秒，需求吞吐为 1000000 ÷ 20 = 50000 步/秒。第二步定单副本速率：单环境副本在目标策略下实测约 500 步/秒，需要 50000 ÷ 500 = 100 个副本，每副本声明 1 核。第三步加训练与驱动的消耗：训练进程 16 核加 1 张卡，驱动与系统预留 12 核。第四步向上取整到整节点：总算力需求 100 + 16 + 12 = 128 核，按每节点 32 核组织，恰好 4 个工作节点，头节点另配 16 核专用于协调。

分项核算过程结果
需求吞吐1000000 步 ÷ 20 秒50000 步/秒
采样副本50000 ÷ 500（单副本速率）100 个，占 100 核
训练与驱动训练 16 核 + 预留 12 核28 核
工作节点数(100 + 28) ÷ 32 核4 个

账本算完必须做敏感性检验：若某节点实际只有 16 核可用（资源声明偏差或硬件差异），总采样核降为 96，吞吐上限降为 96 × 500 = 48000 步/秒，轮时间升为 1000000 ÷ 48000 ≈ 20.83 秒，超出预算约 4%。偏差会被逐节点放大，因此启动后用 ray status 核对资源总量与账本一致，是部署流程的必要步骤。账本的价值在于让容量问题在部署前暴露：需求吞吐、单副本速率、预留量三项中任何一项估计错误，都会直接转化为轮时间超支。

跨节点流量同样要进账本。按每步观测 84×84 单通道 float32 计 28224 字节：单副本每批 200 步产出约 5.6 MB，每 0.4 秒交付一批，即约 14.1 MB/秒；100 个副本合计约 1.41 GB/秒，超过 10 GbE 链路约 1.25 GB/秒的有效带宽，头节点入口成为网络瓶颈。缓解手段有三类：把观测精度从 float32 降到 uint8，字节数降为四分之一，汇聚流量回到约 353 MB/秒；启用序列化侧压缩；增大每批步数，并让节点先做局部合并以减少传输次数与协议开销。每节点内部流量为 25 × 14.1 ≈ 353 MB/秒，本身落在链路能力内，说明瓶颈集中在头节点入口方向，扩容前先核对这一路流量。

实现思路与设计

手工搭建一套可复现实验集群的步骤：

  1. 前置对齐：所有节点统一的 Python 与 Ray 版本、统一的临时目录路径、统一的时钟来源。
  2. 启动头节点：声明端口与资源，记录输出的连接地址。
  3. 启动工作节点：携带头节点地址加入；逐台核对注册成功。
  4. 状态验证：查看节点列表与总资源，确认与规划值一致。
  5. 分布验证：提交跨节点任务，核对执行位置的节点编号；通过后再部署真实训练作业。
  6. 退出清理：实验结束停止所有节点进程，避免残留进程占用端口与资源。
参数典型取值作用取值依据
num-cpus（每节点）16–64资源声明覆盖与物理核一致，容器内必须显式声明
num-gpus（每节点）0–8显存调度声明与物理卡数一致，多机训练时逐卡核对
temp-dir数据盘路径套接字与溢写目录容量充足、路径各节点一致
端口区间默认区间放行节点间通信安全策略按控制面最小开放

前置对齐中的三项各有其故障形态。Python 与 Ray 版本不一致会引发序列化错误与接口错位；临时目录路径不一致会让溢写文件与日志散落，排障时难以定位；时钟偏差超过心跳判定阈值时，节点会被误判为失效并从集群移除，其上任务触发重建。容器环境中的时钟由宿主机同步，但心跳超时阈值与网络抖动叠加仍可能产生误判，部署文档中应记录超时参数取值及其依据，作为排障基线。

与上一章的差异点

第 006 章的所有并发手段运行在单一进程边界内；本章把边界扩展到多台机器，跨机通信引入网络带宽与延迟约束，对象本地性（Locality）从优化项变成主要矛盾。后续章节的调度与容错都要在此基础上重新审视。

关键代码与解读

以下片段采用 Ray 2.x 时期的通用写法；接口随版本演进，以对应版本官方文档为准。

片段 1：头节点与工作节点的启动命令

# 头节点：声明控制面端口、资源规模与临时目录
ray start --head --port=6379 --num-cpus=16 --num-gpus=0 --temp-dir=/data/ray_tmp

# 输出中会打印工作节点使用的连接地址，例如：
#   ray start --address='192.168.1.10:6379'

# 每个工作节点：携带头节点地址加入，显式声明本机资源防止探测偏差
ray start --address='192.168.1.10:6379' --num-cpus=16 --num-gpus=8 --temp-dir=/data/ray_tmp

# 在任意节点上核对集群状态：节点列表、资源总量与当前空闲量
ray status

解读：命令里每个参数都对应一个易错点。--num-cpus 与 --num-gpus 把资源声明与实际硬件对齐，容器环境中这两个值常被显式覆盖；--temp-dir 指向大容量数据盘，避免系统盘被溢写文件占满。GCS 端口在每个集群中应唯一且固定，同一台机器上并存多个集群时必须为每个集群分配不同端口。工作节点加入后立即执行 ray status，把"预期资源总量"与"实际注册总量"做一次对照，是部署的标准动作。

片段 2：驱动进程连接集群并核对节点

import ray
import socket

ray.init(address="auto")      # 自动发现本机已启动的集群；跨机提交时改用地址串

nodes = ray.nodes()           # 节点视图：包含地址、状态与资源声明
alive = [n for n in nodes if n["Alive"]]
print("存活节点数:", len(alive))
for n in alive:
    print(n["NodeManagerAddress"], n["Resources"].get("CPU"), "核",
          n["Resources"].get("GPU", 0), "卡")

# 集群总资源与当前空闲资源对照：差值即已被占用的容量
print("总资源:", ray.cluster_resources())
print("空闲资源:", ray.available_resources())

解读：ray.nodes() 返回的视图是排查部署问题的第一现场：节点缺席说明注册失败，核数不符说明声明有偏差。把节点视图打印进作业日志，让每次训练的集群快照可追溯，后续出现性能异常时可以回溯当时的资源规模。注意自动发现要求驱动进程与集群在同一台机器上且能找到运行时配置；在容器编排环境中，这条判定依赖临时目录的可见性，跨容器提交应使用显式地址。

片段 3：验证任务真的分布到了不同机器

import ray

ray.init(address="auto")

@ray.remote(num_cpus=1)
def probe(local_id):
    import socket
    ctx = ray.get_runtime_context()      # 运行时上下文提供当前任务的身份信息
    return {
        "local": local_id,
        "host": socket.gethostname(),     # 执行所在主机名
        "node": ctx.get_node_id()[:8],    # 节点编号前缀：区分机器的稳定标识
    }

# 提交 32 个探针任务；调度器按资源与本地性把它们散列到各节点
placements = ray.get([probe.remote(i) for i in range(32)])
by_node = {}
for p in placements:
    by_node.setdefault(p["node"], []).append(p["host"])
for node_id, hosts in by_node.items():
    print(node_id, hosts[0], "任务数:", len(hosts))

解读：这是上线前的分布验证脚本。默认调度偏向负载均衡，32 个单核任务应大致按资源比例散落到 4 个节点上。只看到一台主机的任务集中，就要检查其他节点的注册状态与资源声明：工作节点未注册、资源声明为 0、或驱动进程连接错了集群，都会产生这种形态。任务返回值携带节点编号，把执行位置变成可核对的数据；单靠日志推断在集群上并不可靠；同样的探针模式可以推广到"数据是否落在预期的节点"的检查。

常见坑

  • 节点间版本不一致：头节点与工作节点上 Ray 或 Python 版本存在差异，注册表面成功，任务执行时报序列化或接口错误。修复：镜像统一基础环境，作业依赖用运行时环境描述文件声明。
  • 防火墙拦截控制面端口：能启动、无法注册，ray status 始终只有头节点。症状与资源不足相似但日志不同。修复：放行控制面端口区间与对象传输端口，或先在同网段验证连通性。
  • 容器内资源探测偏差：工作节点的调度单元读到宿主机的核数或读不到显卡，资源声明与实际不符。修复：启动参数显式声明核数与显存，并在节点视图里定期核对。
  • 临时目录落在小容量分区：溢写文件与套接字塞满系统盘，节点静默失去响应。修复：为所有节点配置统一的、位于数据盘的临时目录。
  • 残留进程与端口占用：实验结束未停止节点，重启时端口冲突或连接到旧集群的陈旧状态。修复：实验流程中加入统一的停止步骤，重启前核对进程与端口。

练习与思考

  1. 用两到四台机器（或容器）搭集群：头节点 16 核、每个工作节点 16 核加 8 卡。核对 ray status 的总资源与规划值，列出所有偏差并逐项解释。★
    提示
    常见偏差来源：自动探测把物理核数上报、容器内读不到显卡、资源声明遗漏。所有偏差都应能追溯到某个启动参数。
  2. 预测题：把片段 3 的探针任务从 32 个改为 128 个，声明不变。预测任务在节点间的分布形态变化，并说明调度器负载均衡与资源容量的关系。★
    提示
    任务数远大于核数时分布趋近按容量等比例；任意时刻任一两节点间的在途任务数差异应在核数量级以内。
  3. 设计题：为"头节点同时承担协调与部分训练负载"与"头节点仅协调"两种形态各写一份资源规划，给出各自的适用条件与风险点。★★
    提示
    共用形态省一台机器但单点压力大；专用形态多一台机器换稳定性。规划项至少包含驱动进程的核数预留与对象存储预算。
  4. 分析：某作业在开发机上用显式地址连接远程集群提交，训练进行到中途网络抖动，作业直接失败。从驱动连接方式的语义解释原因，并给出两种改进方案。★★
    提示
    集群外驱动的生命周期与作业绑定，连接中断即失去协调方。改进：把驱动部署进集群（自动发现模式），或使用作业提交接口托管驱动。
  5. 验证设计：设计一套集群健康验证清单，覆盖节点注册、资源声明、跨节点通信、共享存储四条通道，每项给出具体的验证命令或探针脚本思路。★★★
    提示
    节点注册看节点视图，资源声明核对数值，跨节点通信用探针任务互传对象，共享存储读写临时目录下的大文件。四条通道各自独立，任何一条异常都会以不同形态暴露。

小结

  • 集群拓扑分两面：头节点承担控制面（GCS、仪表盘、驱动），工作节点承担计算面（任务与 Actor 执行）。
  • 启动三步：头节点声明资源与端口，工作节点携带地址注册，ray status 核对总量；资源声明必须与实际硬件一致。
  • 端口区间与临时目录是部署规划的两个固定项；容器环境务必显式覆盖资源探测。
  • 驱动连接有集群内自动发现与跨机显式地址两种方式；长作业应把驱动部署进集群。
  • 下一章在手工集群之上引入弹性：资源管理与自动缩放，讲清资源声明、调度策略与扩缩容决策。
