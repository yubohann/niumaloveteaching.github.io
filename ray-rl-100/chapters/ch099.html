第 099 章：性能基准与成本分析

一句话：本章建立训练性能与成本的度量体系：基准协议、资源时间计量、效率分解与达到回报阈值的学习成本口径。

  • 主题：训练工程 / 性能基准（Benchmarking）与成本分析（Cost Analysis）
  • 关键机制：资源时间（Resource-time）、效率分解、成本到阈值、回归检测
  • 预计学时：60 分钟
  • 前置章节：第 098 章

学习目标

  • 掌握基准协议的五要素：场景、预算、指标组、重复次数与硬件口径，理解单次测量为何不构成基准。
  • 会用资源时间计量训练成本：以加速器小时与核心小时为单位累计声明资源与使用时长的乘积。
  • 会做效率分解：把预留资源拆为有效计算、空闲等待与重试浪费三部分，找出最大浪费项。
  • 掌握"成本到阈值"口径：用达到回报阈值所消耗的资源时间比较配置，替代单一的速度或回报指标。
  • 会设计回归检测流程：基准存档、阈值触发、复测确认。

背景与动机

调优工作持续产生"更快、更好"的说法，但这些说法缺少统一的度量口径就无法累积：吞吐提升可能来自硬件差异，回报提升可能来自随机幸运，墙钟缩短可能来自省略了评估与检查点。基准与成本分析的任务是把这些说法转成可比数字：同样的场景、同样的预算、同样的计量规则下，资源消耗与学习成果各是多少。

成本分析的视角比纯性能视角更完整：训练消耗的是"预留资源乘使用时长"，闲置的加速器、排队等待的采样进程、因故障重算的窗口都以资源时间计价。仅看墙钟时间会奖励"占用更多资源换更短时间"的配置，而不看资源时间的口径会奖励"省资源但极慢"的配置。资源时间口径把时间与资源合成一个标量，使两种偏差都进入同一账本。

核心原理

基准回答"在固定场景下性能是多少"，成本回答"这些性能花了多少资源"，两者用同一个协议产出可比数字。本节按协议、计量、效率、学习成本与回归依次展开。

1. 基准协议的要素

协议五要素与前几章的测量纪律一致，此处从"基准"视角重新组织：场景（任务与环境版本、网络与算法配置，全部冻结）；预算（环境步或资源时间，二者选一作为主口径）；指标组（采样吞吐、学习侧耗时、达到阈值所需资源时间、峰值显存）；重复（至少三次独立运行，报告各指标的中位数与四分位距）；硬件口径（型号、数量、加速库版本，记录在结果旁）。单次测量只能叫试运行，三次以上才构成基准。指标组里同时保留吞吐与学习成果两类：吞吐高而学不动的配置不构成候选。

2. 资源时间计量

成本以资源时间为单位：每个资源单元（加速器小时、核心小时）按"声明量乘挂钟时长"累计：

C = Σr allocr × durationr + Cretry + Corphan alloc 为资源声明量，duration 为占用时长；重试成本与孤儿资源（泄漏未回收）分别累计，不能混入主项

算例：一次实验占用 24 核与 1 张加速器各 6 小时，另有 2 小时的重试窗口与 0.5 小时的孤儿占用，则资源时间为 24×8.5 核心时与 1×8.5 加速器时。计量与编排层（第 095 章）的账目天然衔接：放置组的申请与释放记录就是资源时间的数据源，账目守恒即成本不漏记。把重试与孤儿单列，是因为它们是可压缩的浪费，与方法本身的消耗性质不同。

3. 效率分解

预留资源按去向分为三部分：有效计算（采样或学习真实推进）、空闲等待（屏障等待、队列空转、调度排队）与重试浪费（崩溃重算、重复采集）。定义效率 U = 有效计算时间 / 预留资源时间，把另外两项的和定义为浪费率。浪费的两个大头与前面章节的结论对应：屏障长尾（第 086 章）落在空闲等待，故障重算（第 090 章）落在重试浪费；检查点写入与评估开销计入有效计算还是开销，需要协议预先定义，建议计入开销并单列，防止"省略评估以提升效率"的指标操纵。

效率分析的价值在于指出优化顺序：浪费率 40% 的系统先去空闲与重试里找空间，再谈单步提速；浪费率 10% 以下的系统继续压缩的边际收益很小，应转向学习质量。这与第 085 章的"先解决等待空洞"结论一致，此处给出了统一的计量形式。

4. 学习成本口径

把学习成果与资源时间结合，得到两个常用口径：成本到阈值（达到目标回报所需的环境步数换算成资源时间，阈值与评估协议沿用第 097 章）；单位学习量成本（每百万环境步的资源时间，适合与学习质量无关的纯效率对比）。两者的选择取决于问题：选算法配置用成本到阈值，评估系统改动用单位学习量成本。数值算例：配置 A 在 300 万步达到阈值、单位成本 1.2 加速器时每百万步，总成本 3.6 加速器时；配置 B 在 500 万步达到阈值、单位成本 0.6，总成本 3.0。单位成本低者所需步数可能更多：学习效率与系统效率是两笔账，成本到阈值把两笔账合起来比较。

5. 硬件归一化与回归检测

跨硬件比较的两个风险是绝对吞吐不可比与加速库版本漂移。归一化手段：以参考工作负载（固定网络、固定批的前向与反向循环）在目标硬件上的吞吐作为换算基线，结果以"相对基线的比例"报告；同硬件比较则直接使用绝对量。硬件、驱动与加速库版本写入结果记录，版本变化时旧基准自动失效并要求复测。

回归检测把基准变成守门员：基准存档，把通过验收的配置的指标组与版本标识（第 098 章）入库；阈值触发，关键指标（如采样吞吐、单位成本）变动超过设定比例（如 10%）时告警；复测确认，告警后按协议重跑三次，确认变化稳定存在再归因，避免把噪声当回归。周期复测的频率与机群变动频率挂钩，硬件替换、驱动升级与框架升级是必测的三类事件。

实现思路与设计

基准与成本体系的建设分六步，产物是一份基准档案与一个成本计量库。

  1. 定义指标组：吞吐、学习成本口径、峰值显存、效率分解项，统一单位与计算公式。
  2. 实现计量：从编排层记录推导资源时间；重试与孤儿单列。
  3. 固化协议：场景、预算、重复次数与硬件口径写成基准脚本参数。
  4. 建立档案：验收通过的基准连同版本标识存档。
  5. 接入回归：阈值配置、告警、复测流程。
  6. 周期复测：按硬件与框架事件触发，报告对比历史基准。

第 098 章保证"同样的运行可以再产生一次"，本章在此基础上加上"产生一次的代价是多少"。复现性使成本数字可比，成本使复现性的投入有回报，两章共同构成训练工程的可运营性基础，也直接支撑最后一章的综合系统设计。

关键代码与解读

以下片段基于 Ray 2.x 时期的通用写法，接口随版本演进，以对应版本的官方文档为准。

片段 1：资源时间计量

def resource_time(job_records):
    """资源时间计量：按声明量与占用时长累计，重试与孤儿单列。
    数据源为编排层的申请与释放记录：账目守恒即成本不漏记。"""
    totals = {"core_h": 0.0, "gpu_h": 0.0,
              "retry_gpu_h": 0.0, "orphan_core_h": 0.0}
    for rec in job_records:
        hours = (rec["released_at"] - rec["allocated_at"]) / 3600.0
        cores = sum(b.get("CPU", 0) for b in rec["bundles"])
        gpus = sum(b.get("GPU", 0) for b in rec["bundles"])
        # 主项与浪费项分流：浪费项是优化目标，不混入方法成本
        if rec.get("is_retry"):
            totals["retry_gpu_h"] += gpus * hours
        elif rec.get("is_orphan"):
            totals["orphan_core_h"] += cores * hours
        else:
            totals["gpu_h"] += gpus * hours
            totals["core_h"] += cores * hours
    # 打印合并视图：主项加浪费项构成全量账单
    total_gpu = totals["gpu_h"] + totals["retry_gpu_h"]
    print(f"加速器时 {total_gpu:.1f}（含重试 {totals['retry_gpu_h']:.1f}），"
          f"核心时 {totals['core_h'] + totals['orphan_core_h']:.1f}")
    return totals

解读：计量函数把"成本"落实为可审计的加法。（1）时长取分配与释放时间戳之差：编排层的状态机记录天然提供这两个时间点，账目与第 095 章的守恒规则同源。（2）重试与孤儿从主项分流：它们是需要优化的浪费，与有效训练消耗分开报告才能支撑正确的投入决策。（3）输出合并视图加拆分视图：总账单用于对外汇报，拆分用于内部优化定位。

片段 2：成本到阈值与效率分解

def cost_to_threshold(steps_to_threshold, steps_per_second,
                      gpu_count, cpu_count):
    """成本到阈值：达阈值步数换算为资源时间。
    学习效率（多少步）与系统效率（多快）在此合并为一个数字。"""
    hours = steps_to_threshold / steps_per_second / 3600.0
    return {"gpu_h": hours * gpu_count, "core_h": hours * cpu_count}

def efficiency_split(busy_seconds, idle_seconds, retry_seconds):
    """效率分解：有效、空闲与重试三段占比。
    浪费率的优化顺序：先空闲与重试，后单步提速。"""
    total = busy_seconds + idle_seconds + retry_seconds
    if total <= 0:
        return {"u": 0.0, "idle": 0.0, "retry": 0.0}
    return {"u": busy_seconds / total,
            "idle": idle_seconds / total,
            "retry": retry_seconds / total}

# 读数示例：有效 62%、空闲 30%、重试 8% 时，
# 优先缩小空闲（屏障长尾与排队），单步提速的收益上限只有 62% 的分母
split = efficiency_split(busy_seconds=6200, idle_seconds=3000,
                         retry_seconds=800)

解读：两个函数回答"值不值"的问题。（1）成本到阈值把"更快"与"学得更省"合成为单指标，避免两个维度各自最优的配置无法排序。（2）效率分解给出优化顺序的定量依据：空闲与重试占比高时先修系统，占比低时优化方向转向算法与网络。（3）示例注释强调收益上限的判断方法：任何单步提速的收益都按有效计算时长的分母折算，浪费占比高时提速收益被浪费稀释。

片段 3：基准归档与回归检测

import json
import statistics

def archive_baseline(path, metrics, fingerprint, repeats=3):
    """基准归档：协议产出的指标组加版本标识入库。
    标识随存档：环境变化时旧基准自动失效，防止跨环境误比。"""
    record = {"metrics": metrics, "fingerprint": fingerprint,
              "repeats": repeats, "protocol": "bench-v1"}
    with open(path, "w", encoding="utf-8") as fh:
        json.dump(record, fh, sort_keys=True)
    return record

def check_regression(baseline, current, keys=("sps", "cost_per_mstep"),
                     ratio=0.10):
    """回归检测：关键指标变动超阈值即告警。
    告警只是线索：按协议重跑复测，确认变化稳定后再归因。"""
    alerts = []
    for key in keys:
        base = baseline["metrics"][key]
        now = current["metrics"][key]
        # 吞吐类指标下降为回归；成本类指标上升为回归，方向分别判定
        change = (now - base) / base
        threshold = -ratio if key in ("sps",) else ratio
        if change < threshold:
            alerts.append({"key": key, "base": base, "now": now,
                           "change": round(change, 4)})
    return alerts

# 三次测量取中位数写入 current：单次测量不得触发或解除告警
median_sps = statistics.median([1180.0, 1210.0, 1190.0])

解读：归档与检测构成基准的闭环。（1）版本标识随基准存档：同一指标在不同环境下天然不可比，失效条件写进数据，文档说明作为辅助。（2）回归方向按指标语义区分：吞吐下降与成本上升都判为回归，各自使用正确的符号阈值。（3）注释强调复测纪律：告警需要三次中位数确认，避免噪声触发与噪声解除，这是把基准变成可信守门员的最后一环。

常见坑

  • 单次测量当作结论：调度抖动或预热效应被当成性能变化。修复：三次以上重复，报告与判定都基于中位数。
  • 失败运行不计成本：崩溃与重启的资源消耗被忽略，成本报告系统性偏低。修复：重试与孤儿单列并入总账。
  • 墙钟时间替代成本：并行度高的配置被系统性高估为"高效"。修复：以资源时间为主口径，墙钟作为辅助口径并列记录。
  • 跨硬件直接比较：绝对吞吐受硬件与库版本影响。修复：版本标识入库、环境变化即失效、必要时用参考负载归一化。
  • 基准无复测纪律：告警被噪声触发或忽略，守门员失效。修复：阈值加三次复测流程，事件驱动复测写入规范。

练习与思考

  1. 计算题：某配置占用 16 核 1 卡，运行 5 小时，其中重试 1 小时、空闲 1.5 小时。求资源时间、效率 U 与浪费率。★
    提示
    16×5=80 核心时、1×5=5 加速器时（其中重试 1 小时）；有效 2.5 小时，U=2.5/5=50%，浪费率 50%（空闲 30% 加重试 20%）。
  2. 预测题：把采样并行度加倍后吞吐提升 30%、空闲率从 15% 升到 35%。预测资源时间与单位成本的变化方向。★
    提示
    资源总量增加而有效产出仅升三成，单位成本上升；应先修并行效率再扩容。
  3. 设计题：为三套候选配置设计成本比较方案：资源时间计量、成本到阈值计算、效率分解与统计口径，并说明什么情况会得出与"墙钟比较"相反的结论。★★
    提示
    高并行配置墙钟最短但资源时间可能最高；当并行效率低或空闲占比高时两种口径结论相反。
  4. 分析题：讨论"检查点与评估开销计入哪一类"对效率指标的影响，说明为什么协议必须预先定义该项，并给出一个防止指标操纵的定义方案。★★★
    提示
    计入有效会抬高 U 并激励过度检查点；计入开销并单列则指标可分解，操纵会在分项中暴露。

小结

  • 基准协议五要素：场景、预算、指标组、重复次数与硬件口径；单次测量不构成基准。
  • 成本以资源时间计量：声明量乘占用时长，重试与孤儿单列，账目与编排层守恒规则衔接。
  • 效率分解为有效、空闲与重试三段；浪费占比决定优化顺序，先修系统后提单步速度。
  • 成本到阈值把学习效率与系统效率合成一个标量；单位成本与阈值成本按问题选择。
  • 回归检测以标识失效与三次复测为纪律。下一章把这些机制合成完整的训练系统设计。
