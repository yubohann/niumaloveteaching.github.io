第 096 章：训练平台化：实验数据组织与检索

一句话：本章设计实验数据的存储与检索：实体与目录模型、清单与指标文件格式、索引与摘要的构建、以及筛选排序的查询路径。

  • 主题：平台化 / 实验数据管理（Experiment Data Management）
  • 关键机制：实体模型、追加式指标日志、派生索引、查询规划
  • 预计学时：65 分钟
  • 前置章节：第 095 章

学习目标

  • 掌握实验数据的实体模型：运行（Run）、试验（Trial）、检查点（Checkpoint）与指标序列（Metric Series）及其关系。
  • 会设计目录布局与清单（Manifest）文件，理解清单作为权威入口、索引作为派生物的定位。
  • 掌握指标文件的两种形态：追加式行日志与列式快照，以及各自的一致性保证与压缩策略。
  • 会构建标签索引与指标摘要，并规划"按配置筛选、按指标排序"的查询路径。
  • 会处理模式演进（Schema Evolution）与完整性校验：版本字段、校验和、幂等写入。

背景与动机

编排系统让大量作业并行运行，实验数据的规模随之膨胀：每次搜索产生数十个试验，每个试验有数千个指标点与若干检查点。没有统一组织方式时，数据以"散落的日志文件"形态存在，比较、回溯与再分析都退化为手工劳动。实验数据管理的任务是把这些产物组织成可查询的结构：谁在什么配置下产生了什么结果，指标与检查点在哪里，如何按条件找到最相关的一批运行。

与通用数据管理的差异有三点：其一，实验数据写入前进不回头，追加是主要模式；其二，查询以"筛选加排序"为主，聚合分析的复杂度有限，但要求低延迟交互；其三，数据的权威来源必须是训练进程写出的原始产物，任何索引都只能作为派生结构并在损坏时可重建。把"权威与派生"的边界划清，是本章全部设计的出发点。

核心原理

实验数据组织的核心是两级结构：权威层由运行目录与清单构成，不可重建；派生层由索引与摘要构成，可丢弃重建。本节按实体模型、存储格式、索引与查询依次展开。

1. 实体模型与标识

四个实体与两种关系：运行（一次训练任务）包含若干试验（一组超参配置的一次执行），试验产生指标序列与检查点，指标序列中的每个点对应一个训练步。标识设计遵循两条规则：全局唯一，运行标识由平台生成且从不复用，即使同名实验重复提交也得到不同标识；可组合，检查点与指标文件的路径由运行标识与试验序号组合而成，任何产物的归属可以从路径反查。

追加式写入的一个直接推论是：同一逻辑记录不得原地修改。修正指标错误采用"追加修正记录加引用标记"的方式，读取时按记录序号取最新有效版本。原地修改会让历史查询不可复现，并让派生索引与权威数据失去稳定对应。

2. 目录布局与清单

典型布局：运行目录下按试验分子目录，试验目录内含配置快照、指标文件、检查点目录与清单文件。清单的角色是权威入口：它声明该试验的标识、配置标识、指标文件清单与检查点清单，读取方先读清单再访问数据，不依赖目录遍历猜测内容。目录遍历看似方便，缺陷是并发写入过程中目录内容不稳定，清单的原子提交（第 088 章协议）给出了稳定边界。

路径内容写入方式
runs/<run_id>/spec.json作业规格与代码版本标识创建时一次写入
<trial>/config.json超参配置快照创建时一次写入
<trial>/metrics.jsonl追加式指标行逐行追加，行级完整性
<trial>/manifest.json清单：文件与检查点索引周期性原子重写
<trial>/checkpoints/<step>/检查点分片与清单原子提交（第 088 章）

3. 指标文件：追加日志与列式快照

追加式行日志（每行一个 JSON 对象）的优势是写入简单、故障窗口小：写入以行为原子单位，崩溃至多损坏最后一行，读取方跳过不完整行即可。长期运行下文件行数增长，但顺序读取与按键过滤仍然高效。列式快照（Parquet 等）用于需要按列扫描与压缩的场景：把行日志周期性地压实（Compaction）为列文件，压缩比通常是行日志的数倍，扫描只读所需列。

两种格式组成"热日志加冷快照"的层级：近期数据留在行日志供追加，历史数据压实为列文件供扫描；查询同时访问两层并按时间窗裁剪。绘图用的降采样要保持极值：按窗口取最小与最大值两条曲线，中间用均值，只取均值会把尖峰抹平，把不稳定运行的证据丢掉。

4. 派生索引的构建

索引加速"按配置筛选、按指标排序"的典型查询，包含两个部分：标签倒排索引（配置字段取值到试验集合的映射）与指标摘要（每试验每指标的极值、末值与统计量）。构建方式是从清单与指标文件离线聚合，产物可以是内存表或列文件。索引是派生数据，必须可全量重建；查询结果中的每个试验标识都应能在权威层找到对应产物，重建脚本按同一口径生成索引，保证索引与权威数据可比对。

摘要中的"最佳值"定义是口径问题：训练回报与评估回报、均值与滑动均值给出不同的最佳点。索引应保存多个摘要字段并记录口径标识，查询方按口径取用；把口径隐含在构建脚本里的做法，会让同一索引在不同查询里表达不同含义。

5. 查询路径规划

一次查询的执行按三段组织：候选生成，用标签索引与指标区间筛选得到候选集合；候选加载，按候选标识读取清单与必要的指标摘要；排序与分页，按排序键（如评估回报滑动均值）返回前 k 个，附带分页游标。查询规划的关键是让筛选尽可能发生在索引层，把加载限制在候选集合上；反过来的实现（先加载再过滤）在试验规模上升后延迟线性恶化。完整性约束在查询侧同样成立：查不到不等于不存在，索引重建完成前查询结果可能缺项，接口应返回索引的构建时间戳供判断。

5.1 存储增长与检查点的量级核算

指标数据的增长按"运行数 × 每运行试验数 × 每试验点数 × 单点字节数"核算。数值示例：每天 8 次运行、每次 10 个试验、每试验每天产生 3000 个指标点、单点 200 字节时，指标日增约 8 × 10 × 3000 × 200 字节 ≈ 48 MB，保留 90 天约 4.3 GB。

检查点才是容量主体：单点按 16 MB 量级（百万参数模型的完整状态）、每试验保留 5 份时，日增约 8 × 10 × 5 × 16 MB = 6.4 GB，90 天接近 600 GB。生命周期策略必须优先作用于检查点：最近若干份保留、里程碑版本转为归档、其余按规则清理；指标数据通过冷快照压缩可把占用压到五分之一量级。容量规划的顺序是先算检查点、再算指标，两者的量级差异通常超过一个数量级。

5.2 索引更新策略的对比

策略新鲜度写入开销一致性风险适用情形
训练进程同步更新最高训练热路径变重并发写需要加锁，损坏影响面大小规模、强实时需求
定时批量重建按重建周期滞后离线完成，不扰动训练低，重建产物原子替换常规选择
按需实时重建查询时最新查询延迟上升低，单次查询口径统一低频分析型查询

选择依据：默认采用定时批量重建，查询接口返回构建时间戳；对实时性要求高的看板缩短重建间隔；把索引写入训练热路径会拖慢训练。训练进程只负责写权威数据，派生层全部离线完成，这条边界让训练吞吐与数据检索互不干扰。

6. 模式演进与完整性

数据模式会随训练系统演进：新增指标字段、调整目录布局、增加摘要口径。演进策略是版本化加向后兼容：每个清单与记录携带模式版本号，读取方按版本分支解析；新增字段可选，删除字段先标记废弃再在下一个大版本移除。校验和与行数统计随清单一起保存，读取时先验证再解析，把损坏检测从"解析报错"提前到"读取入口"。幂等写入用"运行标识加步数"作为记录键，重放写入时按键去重，保证重试不产生重复点。

实现思路与设计

数据管理系统的实现分六步，产物是一份数据规范、一个写入库与一个查询接口。

  1. 冻结实体模型：运行、试验、检查点、指标序列的字段与关系；标识规则写入规范。
  2. 实现写入路径：清单原子提交、指标行追加、检查点协议复用；写入库供训练进程调用。
  3. 定义模式版本：清单与记录的版本字段、可选字段策略、废弃周期。
  4. 构建索引与摘要：离线聚合脚本，多口径摘要字段，构建时间戳入库。
  5. 实现查询接口：三段式查询路径、分页游标、索引新鲜度提示。
  6. 对账与演练：索引重建校验、损坏文件注入测试、删除恢复演练。

关键代码与解读

以下片段基于 Ray 2.x 时期的通用写法，接口随版本演进，以对应版本的官方文档为准。

片段 1：追加式指标写入器

import json
import os

class MetricWriter:
    """指标行写入：逐行追加，行内自含去重键。
    崩溃至多损坏最后一行，读取方跳过不完整行即可恢复。"""
    def __init__(self, path, run_id, trial_id, schema_version=2):
        self.path = path
        self.run_id = run_id
        self.trial_id = trial_id
        self.version = schema_version
        self.fh = open(path, "a", encoding="utf-8")
        self.seen = set()                 # 进程内去重：重试写入不产生重复点

    def write(self, step, metrics):
        key = (self.run_id, self.trial_id, int(step))
        if key in self.seen:
            return                        # 幂等：同一键的重复写入被忽略
        record = {"schema": self.version, "run": self.run_id,
                  "trial": self.trial_id, "step": int(step), **metrics}
        # 单行一次写入：行级原子性由缓冲刷写的整体性保证
        self.fh.write(json.dumps(record, separators=(",", ":")) + "\n")
        self.seen.add(key)
        if len(self.seen) % 50 == 0:
            self.fh.flush()               # 批量刷盘：兼顾耐久性与写入吞吐
            os.fsync(self.fh.fileno())

解读：写入器的三个设计点都服务于"故障窗口最小"。（1）每行自含运行、试验与步数：读取方不需要外部上下文即可解释一行，单行即可独立校验。（2）行级追加加批量刷盘：逐行 fsync 会把写入吞吐压低一个量级，按固定条数批量刷写把最坏丢失限制在数十个点，对训练趋势无影响。（3）进程内去重集合来自"运行标识加步数"的键：重试与补写的重复点被拦截，与清单中的行数统计配合可验证写入完整性。

片段 2：清单结构与原子提交

def write_manifest(trial_dir, run_id, trial_id, metrics_path, ckpt_steps):
    """清单是数据的权威入口：声明文件与检查点，读取方不遍历目录。
    周期原子重写：写入方用临时文件加改名，读者永远见到完整版本。"""
    manifest = {
        "schema": 2,                         # 模式版本：读取方按版本分支解析
        "run": run_id,
        "trial": trial_id,
        "metrics": {"path": os.path.basename(metrics_path),
                    "lines": count_lines(metrics_path)},
        "checkpoints": sorted(int(s) for s in ckpt_steps),
        "updated_at": iso_now(),
    }
    tmp = os.path.join(trial_dir, "manifest.json.tmp")
    with open(tmp, "w", encoding="utf-8") as fh:
        json.dump(manifest, fh)
        fh.flush()
        os.fsync(fh.fileno())                # 先确保内容落盘
    os.replace(tmp, os.path.join(trial_dir, "manifest.json"))   # 改名原子生效
    return manifest

def load_manifest(trial_dir):
    """读取方：解析失败视为清单不存在，按损坏处理并触发重建。"""
    with open(os.path.join(trial_dir, "manifest.json"), encoding="utf-8") as fh:
        return json.load(fh)

解读：清单协议把第 088 章的一致性纪律复用到数据层。（1）清单记录指标行数与检查点步数列表：这两个数字是完整性检查的基准，读取方可以用它们与实际文件对账。（2）写入走临时文件加 os.replace：读者在任意时刻看到的清单要么是旧版要么是新版，不存在中间态。（3）解析失败一律按损坏处理：尽力解析会把残缺内容带进下游，错误路径远比"当作不存在"复杂，重建机制会从行日志重新生成。

片段 3：三段式查询与索引重建

def query_runs(index, filters=None, sort_key="best_eval_ma", top_k=10):
    """查询路径：索引筛选 -> 候选加载 -> 排序分页。
    筛选尽量发生在索引层：先加载再过滤会让延迟随规模线性恶化。"""
    filters = filters or {}
    candidates = index                    # 索引行：每试验一行，含标签与摘要
    for field, allowed in filters.items():
        # 标签筛选：倒排索引给出该取值对应的试验集合
        allowed_set = set(allowed)
        candidates = [r for r in candidates if r.get(field) in allowed_set]
    # 候选加载阶段才读取重资源：此处示意读取摘要中的排序键
    loaded = [dict(r) for r in candidates]
    loaded.sort(key=lambda r: r.get(sort_key, float("-inf")), reverse=True)
    # 返回结果附带索引新鲜度：索引重建未完成时结果可能缺项
    return {"built_at": index_built_at(index), "items": loaded[:top_k]}

def rebuild_index(manifest_paths):
    """索引可全量重建：从清单与指标文件重放聚合。
    重建结果与在线构建按同一口径比对，保证索引可丢弃。"""
    rows = []
    for mp in manifest_paths:
        m = load_manifest(os.path.dirname(mp))
        summary = summarize_metrics(os.path.join(os.path.dirname(mp),
                                                 m["metrics"]["path"]))
        rows.append({"run": m["run"], "trial": m["trial"],
                     **summary, "built_at": iso_now()})
    return rows

解读：查询与重建函数互为对账。（1）筛选在索引行上完成，候选加载只读取摘要字段；排序键缺失时以负无穷兜底，不完整记录沉到末尾，整体排序不中断。（2）返回值携带索引构建时间戳：使用方据此判断结果是否覆盖了最新完成的试验。（3）重建脚本与在线构建共享 summarize_metrics 同一实现：口径只有一个来源，索引损坏时按清单重放即可完全恢复，验证了"派生数据可丢弃"的设计承诺。

常见坑

  • 运行标识复用或缺失：同名实验覆盖彼此的数据。修复：平台生成全局唯一标识，路径以它开头，提交层做唯一性校验。
  • 指标文件名带浮点数或时间戳：检索与排序困难，且格式随实现漂移。修复：固定文件名加行内字段，时间戳写进记录字段，路径保持稳定。
  • 索引与权威数据不同步：新完成的试验在查询中缺项，使用者误判为失败。修复：查询接口返回索引构建时间戳；索引按计划重建，重建脚本与在线构建同源。
  • 模式无版本字段：字段增减后读取方无法区分新旧记录，解析错位。修复：清单与记录携带模式版本，读取按版本分支。
  • 把大对象塞进指标行：图像或模型 blob 进入行日志使文件膨胀、扫描变慢。修复：大对象存独立路径，记录中只保存引用与校验和。

    终止依赖批量刷盘窗口；清单半写因改名原子性不存在；截断行由解析跳过并触发按行数对账。

  • 实体模型以运行、试验、检查点与指标序列组织；标识全局唯一且可从路径反查归属。
  • 清单是权威入口，索引是派生结构；权威与派生的边界是全章设计的主线。
  • 指标文件采用热日志加冷快照：行级追加保写入，列式压实保扫描，降采样保留极值。
  • 查询按"索引筛选、候选加载、排序分页"三段规划；模式版本与幂等键保证演进与重试的安全。
