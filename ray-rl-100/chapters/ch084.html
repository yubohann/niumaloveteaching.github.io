第 084 章：超参搜索实战：内存与显存预算

一句话：本章把训练的内存账本逐项拆开，给出回放缓冲、对象存储驻留、模型与优化器状态、激活值的估算方法，并把内存约束写进超参搜索的可行性过滤。

  • 主题：超参搜索 / 内存与显存预算（Memory Budget）
  • 关键机制：容量估算公式、峰值显存测量、可行性过滤、存储精度与分片
  • 预计学时：60 分钟
  • 前置章节：第 083 章

学习目标

  • 掌握回放缓冲（Replay Buffer）内存的估算公式，能按观测形状与容量手算出量级。
  • 理解显存的四类占用：参数、梯度、优化器状态（Optimizer States）、激活值（Activations），并能判断哪一类随批大小线性增长。
  • 会用工具测量峰值显存与对象存储驻留，验证估算值。
  • 掌握降低内存占用的常用手段：存储精度压缩、分片、卸载、小批上限、梯度检查点。
  • 会把内存预算转化为搜索空间的可行性过滤条件，避免试验因显存溢出（Out of Memory, OOM）大规模失败。

背景与动机

前两章的搜索维度（复用次数、并行度、批大小）每一个都在消耗内存：批越大，激活值越多；缓冲越大，常驻内存越多；并行 worker 越多，样本驻留与策略副本的份数越多。内存是这些参数共同的物理上限，越过它会以进程被杀或显存溢出收场，训练进度全部丢失。更隐蔽的问题发生在显存临界区：配置尚能运行，但显存碎片与峰值波动使个别迭代越界，表现为训练间歇性崩溃，易于误判为环境或通信故障。

把内存纳入搜索流程有两种做法。第一种是事后修补：试验因溢出失败后调小参数重跑，浪费调度资源。第二种是事前预算：按公式估算各组成部分，用实测校准，再把超出预算的组合从搜索空间中过滤掉。本章采用第二种做法，并强调一个工程事实：内存预算要先于性能目标确定，因为它约束的是可行性；优劣是可行性确定之后才轮到的问题。

核心原理

训练内存呈现为四本账：缓冲账、驻留账、优化器账与激活账，各自的增长变量不同，必须分别估算再汇总。本节按数据形态与增长规律逐项展开。

1. 回放缓冲的内存账

离策略与重放类方法把经验存入缓冲，其内存按下式估算：

Mbuffer = capacity × (obs_bytes + meta_bytes) obs_bytes 为单条观测的字节数，图像类观测须乘以帧堆叠（Frame Stack）数与通道字节；meta_bytes 含动作、回报、终止标志等标量，通常为几十字节量级

用一组图像观测的数值感受量级：单帧 84×84 的灰度图，按 1 字节每像素存储为 7056 字节，4 帧堆叠后为 28,224 字节（约 27.6 KiB）。容量 100 万条时，仅观测就需要约 26.3 GiB（约 28.2 GB）；若每像素按 4 字节的浮点存储，则膨胀到约 105 GiB，超出单机物理内存。结论很直接：图像类缓冲必须按 1 字节每像素存储，容量按可用内存的三分之一以内规划。低维观测的账则完全不同：9 维浮点观测加元数据约 100 字节，100 万条约 100 MB，可以轻松容纳多个缓冲。

2. 样本驻留与对象存储

并行采样期间，采到的样本以对象（Object）形式存放在 Ray 对象存储（Object Store）中，等待学习器消费。单轮驻留量约等于一个批的字节数：4000 步图像观测约 113 MB，低维观测不足 1 MB。真正的风险在图像任务上叠加两件事：一是多轮迭代并行推进时对象未及时释放，驻留量成倍累积；二是对象存储本身占用系统内存的固定比例（默认约三成，参数以对应版本为准），大数据批会挤压环境进程的内存空间。治理手段是控制批对象的大小与生命周期：及时释放已消费批次，避免把整个回合链路长期持有。

3. 显存的四类占用

学习器在 GPU 上的显存占用由四部分构成，增长规律各不相同：

组成部分典型规模增长变量说明
模型参数4 字节 × 参数量网络宽度与深度与批大小无关
梯度与参数同量级网络宽度与深度训练期常驻
优化器状态Adam 约 8 字节 × 参数量优化器类型一阶与二阶动量各一份
激活值小批量 × 每样本激活足迹小批大小反向传播依赖，峰值的主要变量

以 500 万参数的卷积网络、Adam 优化器为例：参数与梯度约 40 MB，优化器状态约 40 MB（按每参数 8 字节计），固定部分总计不到 100 MB；而小批 256 的卷积激活在任何合理分辨率下都会达到数百 MB 到数 GB 量级。结论是显存峰值的调节旋钮通常是批大小与网络深度，参数量本身的影响次之。此外还有工作区（Workspace）与显存碎片：卷积库为算法选择分配的临时空间、分配器保留的未释放块，通常占总量的 10% 到 20%，估算时应按 1.2 倍冗余计。

4. 测量：估算之后必须校准

估算提供数量级与可行性判断，实测提供校准值。显存测量的标准口径是"峰值已分配量"与"峰值保留量"两个计数：已分配量反映张量真实占用，保留量包含分配器缓存；两者差距大说明碎片严重，可通过限制批大小或统一张量形状缓解。测量时要注意三个细节：预热迭代的峰值通常高于稳态（库首次编译与缓存建立），报告应取稳态最小值，首轮的峰值代表性差；峰值出现在反向传播开始前，采样点要覆盖整个迭代，只在损失计算后采样会漏掉反向传播的峰值；多进程共卡时要把所有进程的占用相加。对象存储驻留量可从 Ray 状态接口按对象大小汇总，或在训练循环中记录未释放对象的引用计数。

5. 降低占用的技术手段

当估算结果超出预算时，按"先改存储格式、再改结构、最后改精度"的顺序尝试：存储格式方面，观测按 1 字节存、训练时在计算图中转换，缓冲内存直接缩小四倍；缓冲按时间窗口分片，近期数据放内存、旧数据落磁盘，命中率与内存各取所需。结构方面，降低网络宽度与深度按平方级别削减激活值；减小小批大小按比例削减激活值，是显存紧张时的第一选择。精度方面，混合精度训练把前向激活与算子临时量压缩一半，训练循环外另存一份浮点参数副本；梯度检查点（Gradient Checkpointing）用计算时间换显存，重算激活可把激活占用降到平方根量级，代价是迭代时间增加约三成。推理侧可给采样 worker 分配分数 GPU（Fractional GPU），让多个 worker 共享一张卡执行小批量前向。

6. 把内存写入搜索流程

搜索空间中的每个候选配置都应先经过一次可行性检查：按公式估算缓冲、批、激活的上限，与预算比较，超限候选直接剔除或降级参数。对显存敏感任务，排序指标除回报外补充"峰值显存"与"溢出次数"两个诊断项，供后续分析。若必须搜索大显存配置，可在空间中加入"小批大小"维度并设置上限，让调度器在安全区域内寻优。把可行性检查前置到搜索之外，比让调度器反复回收溢出试验更节省总资源。

实现思路与设计

内存预算的工作流程分五步：估算、测量、设限、过滤、监控。

  1. 逐项估算：按上节公式算出缓冲、驻留、优化器与激活四本账，并汇总峰值。
  2. 实测校准：用基线配置跑若干迭代，读取峰值显存与对象存储驻留，与估算比较；差异超过 30% 时修正模型假设（激活足迹、碎片系数）。
  3. 设定上限：为显存与内存分别设 80% 的告警线与 90% 的熔断线，预留余量给峰值波动与系统占用。
  4. 过滤搜索空间：把超限候选剔除，或给出降级映射（如把小批从 1024 映射到 512）。
  5. 运行期监控：逐迭代记录峰值显存，接近告警线时输出提示，便于在溢出前干预。

关键代码与解读

以下片段基于 Ray 2.x 时期的通用写法，接口随版本演进，以对应版本的官方文档为准。

片段 1：回放缓冲内存估算器

def buffer_memory(capacity, obs_shape, obs_bytes=1, meta_bytes=64):
    """估算回放缓冲的常驻内存，单位 GiB。
    obs_shape 为单帧形状，frames 表示帧堆叠数；元数据按标量组估算。"""
    frames, h, w = obs_shape
    per_sample = frames * h * w * obs_bytes + meta_bytes
    total = capacity * per_sample
    return total / (1024 ** 3), per_sample

# 图像观测：84x84 灰度、4 帧堆叠、uint8 存储
gib, per = buffer_memory(1_000_000, (4, 84, 84), obs_bytes=1)
print(f"每样本 {per} 字节，容量 100 万约 {gib:.1f} GiB")   # 约 27.6 KiB / 26.3 GiB
# 对照：同样容量按 float32 存储会膨胀到四倍以上，多数机器直接放不下
gib32, _ = buffer_memory(1_000_000, (4, 84, 84), obs_bytes=4)
print(f"float32 存储约 {gib32:.1f} GiB")                  # 约 105 GiB

解读：这个估算器的价值在于把"容量"这个抽象配置翻译成物理量。（1）把字节换算集中在函数内，改变观测量级（分辨率、堆叠数、精度）时可即时重算，无需重新推导。（2）元数据取 64 字节的保守值，覆盖动作、回报、终止标志与对齐填充。（3）两行对照输出呈现了数量级差异：同样的容量在 4 字节存储下膨胀到四倍，存储精度是缓冲设计的第一决策，先选中它再谈容量。

片段 2：峰值显存测量回调

import torch
from ray.tune import Callback

class GPUMemoryProbe(Callback):
    """在每个训练迭代结束时读取显存峰值，写入日志供预算复核。
    测量口径固定为"已分配峰值"，与缓存保留量区分开。"""
    def __init__(self, budget_gib):
        self.budget = budget_gib * (1024 ** 3)

    def on_trial_result(self, iteration, trials, trial, result, **info):
        if not torch.cuda.is_available():
            return
        # 已分配峰值：张量真实占用，不含分配器缓存，避免高估可用余量
        peak = torch.cuda.max_memory_allocated()
        ratio = peak / self.budget
        # 接近 80% 告警线时输出提示，便于在溢出前调整小批大小
        if ratio > 0.8:
            print(f"显存峰值 {peak / 2**20:.0f} MiB，占预算 {ratio:.0%}，接近告警线")
        # 清零峰值计数：下一个迭代重新统计，避免历史峰值掩盖当前趋势
        torch.cuda.reset_peak_memory_stats()

解读：这段回调把显存监控变成迭代级信号。（1）读取"已分配峰值"；"保留量"包含分配器缓存，会把可用余量系统性低估，两者比值是判断碎片程度的辅助口径。（2）告警线设在预算的 80%，为峰值波动与临时工作区留出余量；熔断线交由训练循环处理（捕获溢出异常并落检查点退出）。（3）每个迭代重置峰值统计，使信号反映当前配置；历史最坏值会掩盖当前趋势；日志中同时记录配置快照，便于事后把显存增长归因到具体参数变化。

片段 3：带内存可行性过滤的搜索空间

from ray import tune

MEMORY_BUDGET_GIB = 24.0          # 单卡预算（GiB）
ACTIVATION_PER_SAMPLE_MIB = 1.5   # 由基线实测标定的每样本激活足迹

def feasible(minibatch):
    """可行性过滤：按标定的激活足迹估计峰值，超出预算的候选不进入搜索。
    过滤发生在搜索之外，避免调度器把资源浪费在必然溢出的试验上。"""
    fixed = 1000.0                        # 参数、梯度、优化器与工作区（MiB）
    estimated = fixed + minibatch * ACTIVATION_PER_SAMPLE_MIB
    return estimated <= MEMORY_BUDGET_GIB * 1024 * 0.8

space = {
    # 只保留通过可行性检查的小批候选；上限由预算除以足迹推导
    "sgd_minibatch_size": tune.choice([m for m in (128, 256, 512, 1024) if feasible(m)]),
    "replay_capacity": tune.choice([100000, 200000, 400000]),
}

解读：这段代码把"内存是可行性约束"落实为一行显式规则。（1）每样本激活足迹由基线实测校准，它随网络结构变化，搜索网络结构时应重新标定。（2）0.8 的安全系数为碎片与工作区留余量，避免临界配置在个别迭代上越界。（3）缓冲容量与批大小分属内存与显存两个预算，同一次搜索中同时开放两维时，应分别过滤，再检查组合后的系统内存是否满足要求。

常见坑

  • 图像观测按浮点存储：缓冲内存膨胀四倍，容量被迫砍到设计值以下。修复：存储用 1 字节每像素，计算前在图内转为浮点并除以 255。
  • 忘记优化器状态：只按参数量估算显存，漏掉动量项后实际占用翻倍以上。修复：按参数、梯度、优化器状态常驻三项估算固定部分。
  • 对象存储挤压环境内存：图像批对象驻留量攀升，环境进程因内存不足被系统终止。修复：控制批对象大小与释放时机，必要时下调对象存储配额。
  • 把峰值测量放在错误位置：只在损失计算后采样，漏掉反向传播的峰值；或报告首轮数值，包含库初始化开销。修复：测量覆盖完整迭代并取稳态值。
  • 每 worker 环境副本叠加未计入：把每 worker 环境数从 2 提到 8 后，进程内存按倍数上升，触发系统级内存回收。修复：把并行度乘数显式计入内存预算，平台化环境按第 089 章的容量模型统一规划。

练习与思考

  1. 计算题：观测为 84×84 灰度、4 帧堆叠、1 字节存储，缓冲容量 50 万条。估算缓冲内存。若改用 2 帧堆叠并把容量减半，节省多少？★
    提示
    每样本约 27.6 KiB，50 万条约 13.2 GiB；2 帧并减半后约 3.3 GiB，节省约四分之三。
  2. 预测题：小批大小从 256 提高到 1024，模型与优化器状态不变。预测显存峰值的变化比例与训练稳定性变化。★
    提示
    激活值约占四倍，若其为峰值主导则总峰值显著上升；梯度噪声下降使更新更稳，但每轮更新次数减少，需复核复用预算。
  3. 设计题：为"单卡 24 GiB、图像观测、需 100 万条缓冲"的任务设计内存方案：缓冲是否分片、存储格式、批与小批上限、是否需要梯度检查点，并给出验证步骤。★★
    提示
    缓冲按 1 字节存并规划 3 片左右的时间窗口；激活预算留给小批 128 至 256；先用实测标定足迹再决定是否需要检查点。
  4. 推导题：设激活值近似随小批线性增长、固定部分为 F，写出"预算约束下最大小批"的表达式，并讨论安全系数 k 的作用与取值依据。★★★
    提示
    m ≤ (k·B − F)/a，a 为每样本激活足迹，B 为显存预算；k 覆盖碎片与工作区，0.8 是常见起点。

小结

  • 内存四本账：缓冲、驻留、优化器状态与激活；前三者按配置常量增长，激活随小批线性增长。
  • 图像缓冲必须按 1 字节每像素存储；容量按内存预算的三分之一以内规划。
  • 显存峰值的调节旋钮是小批大小与网络深度；碎片与工作区按 1.2 倍冗余估算。
  • 估算、实测、设限、过滤、监控五步把内存约束前置进搜索流程，避免溢出试验浪费调度资源。
