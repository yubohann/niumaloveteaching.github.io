第 098 章：复现性控制：种子、环境与版本

一句话：本章把复现性拆成版本、种子与执行三层控制，给出种子派生树、确定性开关与版本标识的可操作设计。

  • 主题：训练工程 / 复现性（Reproducibility）
  • 关键机制：三层控制、种子派生、确定性开关、版本标识
  • 预计学时：60 分钟
  • 前置章节：第 097 章

学习目标

  • 理解复现性的三级目标：位级一致、统计一致与功能一致，并会为任务声明所需级别。
  • 掌握三层控制结构：版本层锁定计算环境，种子层派生随机流，执行层约束非确定性来源。
  • 会设计种子派生树，避免简单递增种子带来的误差流相关，以及多进程共用种子导致的轨迹重复。
  • 了解深度框架确定性开关的代价与边界，能区分"可消除的非确定性"与"硬件层面的非确定性"。
  • 会采集与校验版本标识，把种子与标识随检查点一同保存，使恢复流程能够校验环境一致性。

背景与动机

前几章建立的比较、报告与容错流程都依赖一个前提：同样的配置与输入产生可解释的结果。缺少复现性控制时，实验之间的差异无法归因：策略差异、数据差异与随机差异混在一起，调优工作退化为猜测。强化学习训练对随机性尤其敏感：种子同时影响环境轨迹、策略采样、网络初始化与数据顺序，任何一处不受控，种子间方差就会吞掉配置间的真实差异。

复现性还有两个具体用途：其一是恢复验证，第 090 章的检查点恢复要求恢复到与未中断训练相同的轨迹，这依赖随机流状态的精确保存与还原；其二是审计追溯，数月后复查一条实验结论时，需要从记录中还原当时的代码、依赖与环境版本。本章的三层控制分别回应这三类需求：种子层服务恢复，版本层服务追溯，执行层服务比较。

核心原理

复现性控制的本质是把"随机"从不可控的自由变量变成有编号的输入：每一个随机源都有确定的名字与种子，整条随机流由这些输入完全决定。本节按目标层级、三层结构、种子派生与版本标识依次展开。

1. 复现性的三级目标

级别含义成本适用场景
位级一致同输入同硬件下逐步输出完全一致最高：需确定性算子与固定线程调试数值异常、恢复验证
统计一致多次运行的指标分布稳定可比中：多种子加固定协议比较与报告（第 097 章）
功能一致同协议下结论方向可复现低：记录完整配置与版本日常实验与迭代

声明所需级别是第一步：训练任务通常不需要位级一致，追求它会把大量算力花在算子约束上；但恢复验证场景例外，检查点恢复的正确性依赖随机流逐位还原。级别的选择写入实验配置，避免不同成员对"可复现"理解不一。

2. 三层控制结构

版本层锁定计算环境：代码提交标识、依赖清单、容器镜像摘要、运行时与加速库版本、环境（仿真器）版本。版本漂移是"代码没改但结果变了"的头号来源，依赖升级改变算子实现与默认参数，加速库升级改变浮点归约顺序。种子层为每个随机源派生独立种子（下节展开）。执行层约束非确定性来源：确定性算子开关、线程数与工作线程池固定、数据加载顺序固定、评估过程与训练过程隔离随机流。

3. 种子派生树

直接给所有随机源同一个种子，会让环境轨迹与网络初始化使用同一序列，产生难以察觉的相关；用"基础种子加进程编号"这类简单递增，则相邻种子序列在弱随机数生成器下可能相关。标准做法是基于摘要函数的派生：把基础种子、工作单元标识与随机流名称拼接，经摘要函数压成定长输出，取该输出作为流的种子。输出近似独立，且派生过程与工作单元编号、流名称一一对应，任何一处变化只影响对应流。

seed(stream) = Digest( base_seed ‖ unit_id ‖ stream_name ) mod 231 unit_id 为采样单元编号，stream_name 区分环境重置、策略采样、数据增强等流；同一流在重跑中稳定一致

流隔离的必要性来自恢复语义：训练中断恢复时，策略采样流需要从保存状态继续，环境重置流只需要保证"剩余回合的种子可复现"，两者独立性越高，部分恢复的正确性越容易论证。每个流的状态单独保存，是第 090 章检查点清单在种子维度的展开。

4. 环境复现的细节

环境侧的三个常见失守点：一是包装器的随机流，帧跳与动作重复包装、观测噪声包装各自持有随机状态，需要纳入种子派生，仅设置环境本身并不足够；二是重置语义，任务随机化在每次重置时抽样，评估与训练使用相同重置种子集才能比较，评估端要显式传入固定种子列表；三是版本浮动，仿真器补丁版本可能改变默认参数或终止判定，依赖清单必须锁定到补丁级。记录每回合使用的种子值，是把环境侧随机变为可回放的最直接手段。

5. 执行层：确定性开关与代价

深度框架提供确定性模式：约束卷积与归约算法选择、禁用非确定算子。开启后同一输入在同型硬件上得到一致输出，代价是部分算子回退到较慢实现、吞吐下降，且个别算子无确定性实现时需要显式替代。实践的分层策略：调试与恢复验证开启确定性；性能基准与长时间训练关闭，用统计一致保障可比较性。加速层面的非确定性（原子加法顺序、多流并发）通常无法完全消除，报告应写明"同硬件统计一致"这一级别的承诺。

6. 版本标识与校验

版本标识把计算环境压缩成一串可比对的字符串：代码提交、依赖清单摘要、容器镜像摘要、加速库与驱动版本、仿真器版本。采集时机为任务启动时，保存位置为运行清单、检查点与报告数据戳（与第 096、097 章衔接）。版本标识的用处有两个：恢复时校验"当前环境与检查点写入环境一致"，不一致时拒绝自动恢复并告警；审计时按标识重建环境。采集时应过滤无关的易变字段（如时间戳），保证同一环境重复采集得到稳定摘要。

实现思路与设计

复现性控制的落实分六步，产物是一份种子规范、一份确定性开关集与一个版本标识采集器。

  1. 声明目标级别：按任务用途选择位级、统计或功能一致，写入实验配置。
  2. 枚举随机源：环境重置、包装器、策略采样、网络初始化、数据顺序与增强，逐一登记。
  3. 实现种子派生：摘要派生函数加流名称约定；禁止在代码中直接使用全局随机。
  4. 配置确定性开关：按场景开关，记录开关状态到实验配置。
  5. 采集版本标识：启动与检查点写入时采集，恢复时校验。
  6. 验证：同种子重跑对照、种子敏感性分析（不同种子组的结论方向）。

关键代码与解读

以下片段基于 Ray 2.x 时期的通用写法，接口随版本演进，以对应版本的官方文档为准。

片段 1：基于摘要函数的种子派生

import hashlib

def derive_seed(base_seed, unit_id, stream_name, mod=2**31 - 1):
    """种子派生：拼接后取摘要再取模，替代简单递增。
    简单递增（seed+worker_id）在弱随机源下可能相关；
    摘要派生让同一基础种子下各流与各单元近似独立。"""
    payload = f"{base_seed}|{unit_id}|{stream_name}".encode("utf-8")
    digest = hashlib.sha256(payload).hexdigest()
    # 取摘要前 8 个十六进制字符即 32 位整数，再折叠到合法种子范围
    return int(digest[:8], 16) % mod

# 采样单元 3 的三个独立流：编号与流名都参与派生，任一处变化只影响该流
s_env = derive_seed(1234, unit_id=3, stream_name="env_reset")
s_pol = derive_seed(1234, unit_id=3, stream_name="policy_sample")
s_shf = derive_seed(1234, unit_id=3, stream_name="shuffle")
# 复核：不同流与不同单元的种子在可观察范围内互不相同
assert len({s_env, s_pol, s_shf}) == 3

解读：派生函数把"随机源治理"变成接口约定。（1）输入三要素固定：基础种子代表实验身份，单元标识区分并行实例，流名称区分用途；三者任一变即得到全新种子，变更可追踪。（2）摘要输出天然均匀，避免了递增种子的序列相关；取模后仍是整数，可直接传入环境的种子参数。（3）断言演示了基本自检：同一单元的三个流互不相同；工程上还可把全部派生出（种子、流名）对照表随实验配置保存，供事后重放。

片段 2：确定性开关的分层配置

import os
import random
import numpy as np
import torch

def set_determinism(level="statistical", base_seed=1234):
    """按目标级别配置确定性：级别越高约束越多、代价越大。
    位级一致用于调试与恢复验证；长时训练用统计一致即可。"""
    random.seed(base_seed)
    np.random.seed(base_seed % (2 ** 32))
    torch.manual_seed(base_seed)
    if torch.cuda.is_available():
        torch.cuda.manual_seed_all(base_seed)
    if level != "bit_exact":
        return                          # 统计一致到此为止：不启用算子约束
    # 位级一致：约束卷积算法选择并禁用非确定算子
    torch.backends.cudnn.deterministic = True
    torch.backends.cudnn.benchmark = False
    torch.use_deterministic_algorithms(True)
    # 固定线程工作池：线程数变化会改变归约顺序，从而改变浮点结果
    os.environ["OMP_NUM_THREADS"] = "1"
    os.environ["CUBLAS_WORKSPACE_CONFIG"] = ":4096:8"  # 约束工作区分配

解读：开关函数把级别映射到具体配置。（1）三个库的全局种子一次设定，作为"无流控制代码"的兜底；派生子流在各自模块内覆盖使用。（2）统计级别直接返回，避免为不需要的场景支付确定性开销；位级分支集中配置算子与线程约束。（3）注释写明代价与适用边界：确定性开关会限制算子选择进而影响吞吐，同时在多进程环境中线程数须显式固定，否则归约顺序仍会漂移。

片段 3：版本标识采集与恢复校验

import json
import platform
import subprocess

def collect_fingerprint(packages=("ray", "torch", "gymnasium", "numpy")):
    """版本标识：把计算环境压缩为可比对的标识。
    过滤易变字段（时间戳等），同一环境重复采集得到相同摘要。"""
    versions = {}
    for pkg in packages:
        try:
            out = subprocess.run(["pip", "show", pkg], capture_output=True,
                                 text=True, check=True).stdout
            versions[pkg] = next(l.split(": ", 1)[1] for l in out.splitlines()
                                 if l.startswith("Version:"))
        except Exception:
            versions[pkg] = "absent"     # 缺失依赖记为显式值，避免键消失
    fingerprint = {
        "python": platform.python_version(),
        "git": subprocess.run(["git", "rev-parse", "HEAD"],
                              capture_output=True, text=True).stdout.strip(),
        "packages": versions,
        "cuda": torch.version.cuda if torch.cuda.is_available() else None,
    }
    return fingerprint

def assert_compatible(current, saved):
    """恢复校验：当前环境与检查点写入环境不一致时拒绝自动恢复。
    不一致可能改变数值行为，静默续跑的轨迹不会被承认。"""
    if current != saved:
        raise RuntimeError(f"版本标识不一致，恢复被拒绝")
    return True

解读：标识采集与校验构成可追溯性的两端。（1）过滤采集范围到关键包与解释器、代码、加速层，摘要稳定且覆盖主要漂移来源；缺失依赖记为"absent"使字段集合固定，便于全量比对。（2）恢复校验采用严格相等：任何一项变化都会拒绝自动恢复并调用人工判断，宁可中断也不进入"未知环境续跑"。（3）版本标识随运行清单与检查点一同保存（与第 090、096 章衔接），审计场景可以据此重建当时的运行环境。

常见坑

  • 所有并行单元共用一个种子：各单元产生相同轨迹，样本多样性丧失。修复：用派生函数为每个单元分配独立种子并登记。
  • 只设置全局种子不控制流：第三方库内部随机流不受控，重跑结果漂移。修复：显式枚举随机源，逐流派发并写入配置。
  • 评估使用训练随机状态：评估顺序改变导致结果变化。修复：评估端固定种子集并冻结随机状态，评估前后重置。
  • 依赖版本浮动：未锁定补丁版本，升级后默认参数变化。修复：容器镜像或锁定清单固定到补丁级，版本标识随检查点校验。
  • 种子未随检查点保存：恢复后随机流从前不连续，轨迹与未中断训练不匹配。修复：随机流状态纳入检查点清单（第 090 章）。

练习与思考

  1. 计算题：base_seed = 7，单元 0 与 1 的 env_reset 流种子由同一摘要函数派生。说明为什么二者近似独立，而 7 与 8 作为单一种子直接使用时相关性更高。★
    提示
    摘要输出的比特近似均匀独立；相邻整数作为种子在部分生成器下低位相关，初始化序列可能重叠。
  2. 预测题：在统计级别下重跑同一配置两次，预测指标数值与报告结论的一致性程度，并说明与位级一致级别的差别。★
    提示
    统计级别下两次运行指标不同但分布一致，聚合结论方向稳定；位级级别下逐步数值完全一致但吞吐下降。
  3. 设计题：为"8 采样单元、图像输入、含数据增强"的训练设计种子与版本控制方案：流清单、派生输入、版本标识字段与恢复校验流程。★★
    提示
    流含 env/policy/augment/shuffle；派生输入含单元号与流名；标识含容器摘要与仿真器版本；恢复比对失败即人工处理。
  4. 分析题：讨论"同硬件统计一致"这一承诺为什么不包含跨硬件可复现，以及跨硬件比较实验应如何设计控制变量。★★★
    提示
    浮点归约顺序与算子实现随硬件变化；跨硬件比较应固定种子集与协议，把硬件差异作为独立变量记录并做多种子聚合对照。

小结

  • 复现性分位级、统计与功能三级；先声明目标级别，再选择控制强度。
  • 三层控制：版本层锁环境，种子层派生随机流，执行层约束非确定来源。
  • 种子派生用摘要函数从拼接输入生成；简单递增存在序列相关风险。每个随机源有名称与状态，状态随检查点保存。
  • 确定性开关按场景分层启用；跨硬件复现不在承诺范围内，比较实验需控制变量。
  • 版本标识随清单与检查点保存，恢复时严格校验。下一章建立性能与成本的度量体系。
