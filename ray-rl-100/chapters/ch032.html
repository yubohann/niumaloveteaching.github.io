第二篇 · RLlib 核心接口与训练

第 032 章：RLlib与WandB集成

WandB（Weights & Biases）把训练指标记录到远程服务，支持跨机器、跨成员的实验对比。本章讲清回调挂接的数据流、实验组织维度、认证与离线模式，以及远程记录对训练性能的影响。

  • 主题：RLlib 训练 / 实验跟踪平台
  • 关键机制：回调挂接、实验组织、认证与离线模式、上传节流
  • 预计学时：50 分钟
  • 前置章节：第 031 章

学习目标

  • 理解远程记录平台的挂接方式：训练结果经回调流向外部服务的数据路径。
  • 掌握实验组织维度：项目、运行、分组与标签的层次与检索价值。
  • 会配置认证与离线模式，理解多节点环境下的密钥分发要求。
  • 会控制上传频率与记录粒度，避免远程调用拖慢训练迭代。
  • 能把检查点与关键配置关联到运行记录，形成可追溯的实验档案。

背景与动机

本地面板适合单机观察，跨机器、跨成员的实验对比需要统一的记录中心：指标时间序列、配置快照与检查点位置集中存放，检索与分享不再依赖文件系统的物理位置。WandB 是这类服务的代表，通过回调挂接到 Tune 运行配置中，训练结果自动同步。

远程记录引入两个新约束：网络调用处在训练循环的临界路径上，阻塞与重试策略直接影响迭代时间；认证凭据需要分发到每个执行试验的节点。把上传当作带预算的旁路流量来设计，远程服务才会成为助力。上一章建立了本地曲线视图，本章扩展到远程与协作场景。

核心原理

远程记录的关键词是挂接点、组织维度与流量控制。

1. 回调挂接与数据流

集成入口是 Tune 的运行配置回调列表：日志回调对象在每个试验的生命周期节点被调用，把训练结果字典中的标量转成记录请求发往服务端。数据流为：训练循环产生结果、日志回调抽取标量、客户端库缓冲与批量上传。上传发生在试验的迭代边界上，与采样和学习的计算线程同进程；因此回调内的网络等待时间会直接叠加到迭代时间上。客户端库通常提供缓冲与异步上传，配置项用于控制批量大小与刷新频率。

2. 实验组织维度

记录按项目（Project）汇集，每次训练是一次运行（Run），同一实验的多组参数用分组（Group）加标签（Tags）关联。组织策略的实用检验是检索场景：能否在一分钟内找出"上周学习率扫描中评估回报前十的运行"。可检索性取决于两件事：分组标签是否覆盖切片维度（算法、环境、并行度），配置快照是否完整进入记录。配置快照由日志回调从试验配置自动提取，特殊字段（环境标识、代码版本）应显式写入。

3. 认证与离线模式

认证凭据通过环境变量或凭据文件提供，客户端在首次记录时校验；多节点训练要求每个承载试验的节点都能读到凭据，常见做法是经部署系统注入环境变量。离线模式下记录先写到本地目录，训练结束后用同步命令上传，适合隔离环境或网络受限的集群。离线与在线记录的运行标识需要区分，同步时检查是否与既有运行冲突。

4. 上传节流与内容规划

上传量由三个因子相乘：记录频率、每次记录的标量数量、运行数量。控制手段分别对应三者：标量按迭代记录（自然频率低）、面板按需展开的分类前缀（减少默认展开展示、并不减少上传量）、试验数量预算。把每步级的高频量留在本地统计，只上传聚合结果，是控制上传量的主要手段。检查点与关键配置作为运行相伴的记录项上传，大小受限于服务的制品额度，应与检查点保留策略联动。

5. 上传流量的数值估算

流量总量模型：总量 ≈ 运行数 R × 每运行记录数 F × 每条记录标量数 S × 单标量字节数 b。数值示例：20 个运行、每个运行 200 轮、每轮 200 个标量、单标量按 40 字节计，总量约为 20 × 200 × 200 × 40 字节 = 32 MB，属于可控量级。若把每步级的动作分布（8 个标量）按每秒 4000 步的频率逐点上报，单个环境每秒产生 32000 个记录点，流量放大数个数量级；改为回合聚合后上报，同一信息压缩到每轮 8 个标量。

上传总量 ≈ R × F × S × b R = 20、F = 200、S = 200、b = 40 字节时约 32 MB；三个因子各有对应的削减手段，聚合上报的缩减倍数约等于原始频率与聚合频率之比

6. 在线与离线模式的对比

维度在线模式离线模式
网络依赖训练全程需要连接服务端训练期无网络访问
可见时效实时出现在面板同步完成后可见
断网影响需要重试与丢弃策略兜底无影响，记录留在本地目录
运维动作凭据分发与连通性检查收尾同步与冲突核对
适用集群联网稳定、需要实时监控隔离环境、带宽受限

选择依据：联网稳定且需要实时观察时用在线模式；隔离集群与受限网络用离线模式，同步作为实验收尾的固定步骤。两种模式共用同一套上传代码路径，切换通过环境变量完成，训练脚本无需感知网络状态。

7. 上传等待对迭代时间的影响

上传发生在迭代边界，等待时间直接叠加到迭代周期。数值示例：每轮同步等待 20 毫秒、迭代周期 1 秒时开销约 2%，处于可接受范围；网络抖动使等待涨到 200 毫秒时开销升到两成，训练吞吐明显下降。容忍边界按迭代时间比例设定：等待期望超过迭代时间的百分之五时应缩短超时、加大批量提交间隔或切换离线模式，三种手段按对观测实时性的影响从小到大排列，逐级尝试。超时与丢弃策略的取舍标准是训练连续性优先：记录点可以少记，迭代节奏不能被打乱。

8. 运行标识与恢复

每次训练对应一个运行标识；恢复训练沿用原标识可以续接曲线，新建标识则产生一段独立记录。续接的前提是运行未被关闭且服务端允许追加。跨机器分片训练时，各节点写同一运行需要避免标识冲突；离线记录同步到既有项目时，先检索同名运行再决定追加或改名。运行标识同时写入本地实验目录的元数据文件，本地目录与服务端记录可以互相定位，归档与检索都有据可查。

9. 刷新间隔与崩溃容忍的量化

客户端库把记录缓冲后批量上传，缓冲的刷新间隔决定两件事：崩溃时最多丢失多少记录，以及上传请求的密度。训练迭代 0.5 秒、每轮产生一批标量时，三档刷新间隔的对照如下：

刷新间隔崩溃时的最大丢失请求密度（每分钟）适用情形
5 秒约 10 轮记录约 12 次需要近实时观察的调试期
30 秒约 60 轮记录约 2 次默认折中
训练结束时一次进程异常时全体记录1 次离线模式，配合本地归档
丢失窗口 ≈ 刷新间隔；请求密度 = 60 / 刷新间隔（按每条记录一次请求推算，客户端批量提交会进一步压缩） 长训练里 60 轮记录的丢失通常可接受；短试验（数十轮即结束）用 30 秒刷新等于把半段曲线置于风险中，短试验应缩短刷新间隔

缓冲占用的上界同样可算：每轮 200 个标量、单标量按 40 字节计约 8 KB，60 轮缓冲不足 500 KB，内存不构成约束。真正需要核对的是上传失败时的队列行为：带重试的实现会在网络故障时累积队列，队列无限增长会拖到故障恢复后集中补传、占满带宽；队列设上界并按最旧丢弃，保证内存与网络占用可控，丢弃计数写入本地日志供训练收尾核对。

离线同步的耗时按归档体积估算：20 个运行、每运行 200 轮、每轮 200 个标量的档案约 32 MB，按 5 MB/s 的有效上传速度约 6.4 秒，是收尾动作里最轻的一项；带检查点制品上传时体积按 GB 计，同步耗时升到分钟量级，应独立安排时间窗口，并核对服务端运行总数与本地目录数一致；两数不等时以本地目录为准逐条补齐，避免半程同步在服务端留下空运行。

实现思路与设计

配置顺序：认证就绪、挂接回调、约定命名、控制频率、验证端到端可见。

配置项示例值作用取值依据
项目名fixed-goal-pilot实验集合按任务与阶段命名，避免长期复用同一个项目名
分组lr-scan关联同批试验与实验目录的命名规则保持一致
上传频率每轮一次标量记录与迭代边界对齐，避免每步上传
运行模式在线或离线网络策略隔离集群用离线加事后同步
设计决策：为什么远程上传必须做超时与失败容忍？

记录服务出现网络抖动时，客户端默认的重试会在训练线程上等待；等待时间叠加到每轮迭代，训练整体变慢，严重时试验超时被调度器替换。正确做法是给上传设置短超时、允许丢弃个别记录点，并把连接失败作为可观测事件记录到本地日志。训练数据的完整性优先于记录数据的完整性，两者的可容忍度按数量级区分。

凭据管理遵守最小权限与轮换纪律：按项目签发凭证，轮换时更新部署变量并重启受影响试验；日志输出需脱敏，凭据出现在日志中的风险高于丢失本身。标签数量需要节制，稳定维度入标签、一次性实验特征入分组名，标签过多会稀释检索价值。上传失败计数、丢弃记录数与重试耗时三项进入本地日志，训练收尾时汇总核对，与远程运行的记录数对齐。运行数预算按乘法估算：5 名成员各挂 2 组、每组 10 个试验时并发运行约 100 个，按每运行 200 轮、每轮 200 个标量计，档案规模约 400 万标量与 160 MB；接近配额时先合并重复扫描压缩运行数，再用白名单压缩记录粒度。

归档时远程记录与本地结果文件成对保存：运行标识写入实验目录元数据，目录名写入运行描述，两侧可以互相定位。运行描述字段写入关键配置摘要，检索时不展开完整配置即可判断内容；上传记录保留迭代号与样本步数两列，缺任一列都会让离线重组出现口径歧义。同步前检索同名运行，冲突时优先改名，保留两段记录的完整性。自定义指标的列表结构在部分版本中以统计摘要上传，读取脚本需要兼容均值与标准差两种呈现。

与上一章差异：第 031 章的事件文件落在本地目录，读取依赖文件系统；本章的记录保存在服务端，检索与分享面向多机多成员，代价是认证与网络管理。两套通道可以并存：本地事件文件用于逐点复核，远程记录用于对比与归档。下一章转向输入模态，讨论图像观测的处理链路。

关键代码与解读

片段 1：挂接日志回调

from ray import tune
from ray.tune.integration.wandb import WandbLoggerCallback
from ray.tune import RunConfig

# 凭据从环境变量读取：多节点部署时由作业系统统一注入，
# 代码与配置中不出现密钥明文
tuner = tune.Tuner(
    "PPO",
    param_space={
        "env": LineGoalEnv,
        "lr": tune.grid_search([1e-4, 3e-4]),
        "train_batch_size": 8000,
    },
    run_config=RunConfig(
        callbacks=[
            WandbLoggerCallback(
                project="fixed-goal-pilot",
                group="lr-scan-032",           # 同批试验归组，便于对比面板折叠
                tags=["pilot", "ppo"],         # 标签承载检索维度
            ),
        ],
        stop={"training_iteration": 40},
    ),
)
results = tuner.fit()

解读：配置把认证、组织与生命周期交给回调对象。分组与标签是实验检索的骨架：分组对应一批参数扫描，标签对应算法与环境等稳定维度；命名规则应与实验目录保持一致，两套系统才能互相指引。回调挂接在试验级，试验数即运行数，运行数直接影响上传流量与配额，首轮扫描建议控制在十个以内。回调参数随版本演进，以对应版本文档为准。

片段 2：自定义指标上传

import wandb


def log_extra_metrics(result, prefix="diag"):
    """在训练结果回调中追加自定义量：仅记录聚合后的标量。"""
    records = {
        f"{prefix}/train_eval_gap": (
            result.get("episode_return_mean", 0.0)
            - result.get("evaluation", {}).get("episode_return_mean", 0.0)),
        f"{prefix}/learn_to_sample_ratio": (
            result["info"]["timers"]["learn_time_ms"]
            / max(result["info"]["timers"]["sample_time_ms"], 1.0)),
    }
    # 每轮一次的小字典上传；高频原始量留在本地统计，不进远程记录
    wandb.log(records, step=result.get("training_iteration", 0))

解读：自定义量与第 031 章的命名前缀策略一致，面板可按前缀折叠。函数只上传聚合标量，训练与评估差值和耗时比值都是每轮一个数的量级，上传成本可忽略；把每步动作分布之类的原始量上传会立即放大流量。若集成路径不直接暴露底层记录接口，可以把同样的键写入训练结果字典，由日志回调统一抽取，效果等价且更接近框架原生路径。

片段 3：离线模式与同步

import os


def configure_wandb_mode(offline, local_dir="wandb_offline"):
    """切换在线与离线记录：隔离集群先本地落盘，训练后统一同步。"""
    if offline:
        # 离线模式：记录写本地目录，训练过程不访问网络
        os.environ["WANDB_MODE"] = "offline"
        os.environ["WANDB_DIR"] = local_dir
    else:
        os.environ["WANDB_MODE"] = "online"
        # 凭据经环境变量注入；缺失时训练应尽快失败，逐轮重试会消耗算力
        assert os.environ.get("WANDB_API_KEY"), "缺少凭据环境变量"


# 训练结束后在可联网节点执行同步命令：
# wandb sync wandb_offline/ --append
configure_wandb_mode(offline=True)

解读：模式切换用环境变量完成，训练代码不感知网络状态，便于同一份脚本在隔离集群与联网环境间迁移。凭据断言让配置错误在启动阶段暴露：若等到逐轮记录时才发现认证失败，训练已消耗的算力无法追回。离线目录需要与训练日志目录一起纳入归档清单，同步命令在联网节点补传；补传前确认运行标识无冲突。

常见坑

  • 凭据缺失或未分发：训练启动后逐轮记录失败。症状是日志反复出现认证错误。修复：启动阶段断言凭据存在，部署系统统一注入环境变量。
  • 每步上传指标：把高频原始量写进远程记录。症状是训练迭代周期性变慢。修复：本地统计每步量，按迭代上传聚合结果。
  • 项目与分组命名随意：多次实验混入同一命名空间，对比面板无法筛选。症状是检索耗时且容易选错基线。修复：项目按任务与阶段划分，分组与实验目录同规则命名。
  • 离线模式忘记同步：隔离集群训练完成后记录仍留在本地。症状是服务端缺少整批运行。修复：收尾清单加入同步步骤，并把离线目录纳入归档路径。
  • 上传阻塞训练线程：网络抖动时逐轮等待重试。症状是迭代时间出现与记录周期同步的尖峰。修复：短超时加丢弃策略，本地日志记录连接失败次数。

练习与思考

  1. 列出远程记录流量公式的三个因子，并为每个因子给出一条具体的削减手段。★
    提示
    流量约等于运行数 × 记录频率 × 每次标量数；分别对应试验预算、按迭代记录、只上传聚合量。
  2. 设计命名规范：项目、分组、标签三个层级分别承载什么维度，使"按算法与环境筛选、按扫描批次对比"两种检索都可行。★
    提示
    项目承载任务，分组承载一次扫描，标签承载算法、环境与并行度等切片维度。
  3. 推导：上传耗时对训练墙钟时间的影响模型，说明超时与丢弃策略的取舍边界。★★
    提示
    影响约为每轮上传等待乘以迭代数；等待期望高于迭代时间的百分之几时应缩短超时；记录完整性与训练时长的兑换比例决定了丢弃阈值。
  4. 设计验证清单：从认证、挂接、指标可见、频率与离线同步五项，给出每项的验证动作。★★
    提示
    选项卡启动阶段检查凭据、单试验确认曲线出现、对照本地结果字典核对关键标量、观察迭代时间无周期尖峰、离线运行后执行同步并核对运行数。
  5. 设计实验：同一训练分别在在线与离线模式下运行，比较迭代时间与最终记录完整性，给出集群选型建议。★★★
    提示
    在线模式观察上传等待占比，离线模式观察本地目录体积与同步耗时；网络不稳定或带宽受限的集群倾向离线加归档同步。

小结

  • WandB 通过 Tune 日志回调挂接：训练结果经回调抽取标量后缓冲上传，网络等待直接计入迭代时间。
  • 项目、运行、分组与标签构成实验检索骨架，命名规则与实验目录保持一致。
  • 凭据经环境变量分发，启动阶段校验；隔离集群用离线模式加事后同步。
  • 上传量由运行数、记录频率与标量数量共同决定，高频原始量留在本地聚合。
  • 上传超时与丢弃策略保护训练线程，记录完整性与训练连续性按重要性分级。
