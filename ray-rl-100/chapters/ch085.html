第 085 章：训练吞吐与采样效率分析

一句话：本章把训练一轮迭代的时间拆成采样、学习与通信三段账，给出吞吐指标的口径定义、瓶颈定位流程与可复用的基准测试方法。

  • 主题：训练工程 / 吞吐分析（Throughput Analysis）
  • 关键机制：迭代时间分解、硬件效率、瓶颈判定、基准测试协议
  • 预计学时：55 分钟
  • 前置章节：第 084 章

学习目标

  • 理解四个彼此独立的分析口径：采样吞吐（SPS）、更新吞吐、采样效率、硬件效率，并说明各自回答什么问题。
  • 掌握迭代时间分解模型，能把一轮训练的时间拆成采样、学习、通信与聚合四段。
  • 学会用"哪一侧在等待"的方法判定瓶颈位于采样端还是学习端。
  • 会按固定协议搭建基准测试：预热、重复测量、稳态取值、口径记录。
  • 能为自己的训练任务建立一份可复现的吞吐报告模板。

背景与动机

前面四章的搜索维度（损失系数、复用预算、并行度、内存）最终都会反映到两个数字上：训练一轮要用多少时间，以及同样的时间能推进多少学习。缺少统一的分析口径时，调优容易陷入"改了配置、时间变了、不知道哪一段变了"的混乱。例如把并行度加倍后单轮迭代时间反而上升，可能因为采样侧提速但学习侧排队加长，也可能因为通信占比上升；不拆开时间账，就无法给出修正方向。

另一个常见混淆是把吞吐当作学习效果：采样吞吐提升三成不意味着达到目标回报更快，因为更大的批可能改变学习轨迹；反之学习质量相近的两套配置，吞吐高者显然更优，因为同样的样本预算消耗更少的墙钟时间。本章把"快"与"好"严格分开计量，先讲全部口径，再讲分解与测量，最后给出瓶颈判定与优化顺序。

核心原理

吞吐分析的核心动作是把一轮迭代的墙钟时间拆开，判断时间花在哪一段，再决定优化哪一段。本节从口径定义开始，逐层分解到瓶颈判定。

1. 四个分析口径

口径定义单位回答的问题
采样吞吐 SPS每秒推进的环境步数步/秒数据管道供给能力
更新吞吐每秒完成的梯度更新次数次/秒学习侧计算能力
采样效率达到回报阈值所需的样本量步算法的数据利用质量
硬件效率实测 SPS 与理论线性上限之比比率资源利用是否划算

四者相互独立：采样效率高的算法可能在低效硬件配置上跑得慢；吞吐高的系统可能因为批结构变化导致学习质量下降。任何调优结论都应声明关注的是哪一个口径，混用会得出"变快了但没变好"或"变好了但更慢"这类无法行动的报告。

2. 迭代时间分解

同步更新模式下，一轮迭代的墙钟时间可以写成四段之和：

Titer = Tsample + Tlearn + Tcomm + Taggregate Tsample 为并行采集时间（由最慢 worker 决定），Tlearn 为学习器更新时间，Tcomm 为权重广播与样本回传，Taggregate 为指标聚合与调度开销

采样吞吐与迭代时间的关系为 SPS = B / Titer，B 为批大小。代入一组典型数值：B = 4000，Tsample = 5 秒，Tlearn = 2 秒，Tcomm 与 Taggregate 合计 1 秒，则 Titer = 8 秒，SPS = 500 步/秒。四段占比决定了优化方向：采样占 62.5% 时，提高并行度或降低单步成本收益最大；学习占了大头时，优化应转向网络规模、批处理效率与算子选择。

各段内部还可再分：Tsample 包含环境步进时间、策略前向推理与观测预处理；Tlearn 包含前向、反向与优化器更新，反向约是前向的两倍计算量；Tcomm 与策略网络的参数量成正比，小网络低维观测时通常不足总量的百分之几，大视觉网络时可以到一成以上。

3. 瓶颈判定："谁在等"

判断瓶颈的可靠依据是等待结构：单轮时间占比会被抖动误导，连续多轮中"谁先完成、谁后完成"才给出稳定信号。在同步模式下，如果采样 worker 每轮结束都空闲等待新一轮权重下发，说明学习侧是瓶颈（采样供给超过学习消化能力）；如果学习器每轮开始处于空闲状态等待样本就绪，说明采样侧是瓶颈。框架计时器里体现为两侧的"空闲比"：采样间隔中学习耗时的占比、学习循环中等待批队列的占比。连续若干轮观察空闲比，比单轮耗时更能稳定地指示瓶颈，因为它排除了偶发抖动。

常见的瓶颈形态有三类。采样受限：低维观测、简单环境、强并行硬件上常见，表现为学习器长期空闲等待，优化方向是增大采样规模或减少每步预处理开销。学习受限：大视觉网络、高复用比配置上常见，表现为 worker 长时间空转，优化方向是改进网络效率与批处理、降低每步更新数量需求。通信受限：跨节点部署、大策略网络时常见，表现为 Tcomm 随节点数上升而显著增长，优化方向是减少权重广播频率（降低梯度同步频次）与压缩传输。

4. 硬件效率与边际收益

硬件效率的上限是把所有采样实例按单实例步率线性叠加：E = SPS / (N × r)。效率低于 0.8 时，投入更多核的边际收益开始快速递减（第 083 章的缩放曲线）。学习侧同理：GPU 利用率长期低于 50% 说明存在等待空洞，正确方向是扩容采样端，GPU 本身扩容解决不了采样等待。调优顺序应先解决"等待空洞"，再追求单点速度：让两侧都接近满负荷之后再优化单步成本，收益才不会被空洞吞掉。

5. 基准测试协议

吞吐数字只有在一个固定协议下才有意义，协议包含五项约定：预热（丢弃前一到两轮迭代，避开库初始化与缓存建立）；时长（至少十轮迭代或两分钟，取较长者，以覆盖调度抖动）；取值（报中位数与四分位距，极值单独列示）；口径（明确 SPS 按环境步计、批量是否含截断重复样本、计时用单调时钟）；记录（并行度、批大小、硬件型号、框架版本随结果一并存档）。对照实验中除被测变量外全部配置冻结。

实现思路与设计

建立吞吐分析的流程分五步，产出物是一份可复跑的基准报告。

  1. 明确目标口径：先声明本轮优化关注 SPS 还是采样效率；两者同时看时分开成两张表。
  2. 搭建基准：写一个独立脚本，固定随机种子与全部配置，按协议跑测量并输出分解数据。
  3. 绘制分解表：逐迭代记录四段耗时与两侧空闲比，形成时间序列；单轮快照不足以判定瓶颈。
  4. 定位瓶颈与验证：按"谁在等"给出假设，只改一个变量做对照实验，确认分解结构按预期变化。
  5. 固化报告：把协议五项约定与结果一起存档，作为后续变更的对照基线。

关键代码与解读

以下片段基于 Ray 2.x 时期的通用写法，接口随版本演进，以对应版本的官方文档为准。

片段 1：从训练结果中提取时间分解

def print_breakdown(result):
    """把一轮迭代的时间拆成采样、学习与其余部分，打印占比。
    口径固定为毫秒，来源为框架计时器，便于跨版本核对。"""
    s = result["timers"]["sample_time_ms"]
    l = result["timers"]["learn_time_ms"]
    total = result["time_this_iter_s"] * 1000.0
    # 分解项相加未必等于总时间：差值即通信与聚合开销
    other = max(total - s - l, 0.0)
    steps = result["env_runners"]["num_env_steps_sampled_this_iter"]
    sps = steps / max(result["time_this_iter_s"], 1e-9)
    print(f"迭代 {total:.0f} ms | 采样 {s:.0f} ({s/total:.0%}) | "
          f"学习 {l:.0f} ({l/total:.0%}) | 通信与聚合 {other:.0f}")
    # SPS 按环境步口径计算：明确它衡量数据供给，不衡量学习质量
    print(f"采样吞吐 {sps:.0f} 步/秒（批 {steps} 步）")
    return {"sample": s, "learn": l, "other": other, "sps": sps}

解读：这段打印函数刻意保留了"差值项"。（1）把总时间减去采样与学习得到"其余"，它吸收了通信、聚合与调度开销；其余项异常大时，说明瓶颈可能落在传输上，两端计算未必是主因。（2）占比同时输出绝对值与百分比：跨机器比较看百分比结构，同机回归看绝对值漂移。（3）SPS 的注释强调口径分离，避免后续把吞吐变化误读为算法改进，这一约定应写入团队的分析文档。

片段 2：带预热与重复的基准测量

import statistics
import time

def benchmark(algo, warmup=2, iters=12):
    """固定协议基准：预热若干轮后连续测量，报告中位数与四分位距。
    预热期用于建立算子缓存与稳定内存分配，测量期不改变任何配置。"""
    for _ in range(warmup):
        algo.train()                           # 预热样本不进入统计
    sps_samples = []
    for _ in range(iters):
        result = algo.train()
        steps = result["env_runners"]["num_env_steps_sampled_this_iter"]
        sps_samples.append(steps / max(result["time_this_iter_s"], 1e-9))
    sps_samples.sort()
    mid = statistics.median(sps_samples)
    # 四分位距反映方差：IQR 大说明存在跨迭代抖动，需先查调度或内存压力
    q1 = sps_samples[len(sps_samples) // 4]
    q3 = sps_samples[(3 * len(sps_samples)) // 4]
    print(f"SPS 中位数 {mid:.0f}，四分位距 [{q1:.0f}, {q3:.0f}]")
    return mid, (q1, q3)

解读：这段基准的每个约定都对应一类测量偏差。（1）预热丢弃前两轮，避开库加载、显存分配器扩张与对象存储建连的瞬时开销，这些开销会把首轮时间抬高数倍。（2）用中位数与四分位距代替均值，方差信息保留下来：抖动大本身就是结论，指向调度或内存压力。（3）测量期不改变任何配置，包括不打日志级别、不改评估频率，保证被测系统处于同一状态。

片段 3：滚动吞吐与瓶颈信号

class ThroughputTracker:
    """维护滚动窗口的吞吐与空闲比，用连续观察代替单轮快照。"""
    def __init__(self, window=8):
        self.window = window
        self.history = []

    def update(self, sample_ms, learn_ms, total_ms):
        # 采样间隔 = 总时间 - 学习时间：其中越大，采样端越闲
        sample_idle = max(total_ms - learn_ms - sample_ms, 0.0) / total_ms
        # 学习等待 = 总时间 - 采样时间 - 学习时间：体现学习开始前等样本的时长
        learn_wait = max(total_ms - sample_ms - learn_ms, 0.0) / total_ms
        self.history.append((sample_idle, learn_wait))
        if len(self.history) > self.window:
            self.history.pop(0)
        s_idle = sum(h[0] for h in self.history) / len(self.history)
        l_idle = sum(h[1] for h in self.history) / len(self.history)
        # 连续多轮采样端空闲高：学习侧是瓶颈；反之采样侧是瓶颈
        if s_idle > 0.2 and s_idle > l_idle:
            print("采样端长期空闲：学习侧构成瓶颈，优先优化学习效率")
        elif l_idle > 0.2:
            print("学习端长期等待样本：采样侧构成瓶颈，优先扩大采样并行度")

解读：这个跟踪器的判定逻辑建立在一个可观测的代理量上。（1）同步模式下，两侧的时间差就是空闲证据：采样段用时短于总时间，说明 worker 在等待；学习段用时短于总时间，说明学习器在等待。（2）滚动窗口抑制单轮噪声，阈值 20% 是把偶发调度抖动与结构性空闲区分开的经验线。（3）输出的是行动指引：两类结论分别指向学习侧与采样侧的优化清单，与第 083、089 章的扩容方法衔接。

常见坑

  • 跳过预热直接报告首轮：首轮包含库初始化与缓存建立，数值常偏高数倍。修复：预热至少两轮，并在报告中注明预热策略。
  • 把训练回报变化当作吞吐结论：吞吐口径只描述数据供给能力，回报变化属于学习质量，两者混用无法归因。修复：报告中分开列示，并注明各自的口径定义。
  • 用不同任务或不同环境版本的 SPS 直接比较：单步代价与终止逻辑不同，数字不可比。修复：对照实验冻结环境版本与终止条件，跨任务比较只用硬件效率与相对值。
  • 测量期开启调试日志与高频评估：日志写盘与评估回合挤占计算时间，测量值系统性偏低。修复：测量期使用生产日志级别与正常评估频率，或固定评估频率后再比较。
  • 只看均值不看方差：均值掩盖迭代间抖动，而抖动往往指向内存压力或调度问题。修复：报告中位数与四分位距，抖动异常时先排查资源竞争。

练习与思考

  1. 计算题：一轮迭代采样 5 秒、学习 2 秒、通信与聚合 1 秒，批 4000 步。求 SPS 与三段占比。若采样并行度加倍使采样时间减半，新的 SPS 是多少？★
    提示
    原 SPS = 500；采样减半后 T=5.5 秒，SPS ≈ 727，提升 45%。
  2. 预测题：学习端长期等待样本、GPU 利用率不足 50%。把复用轮数从 4 提到 8，预测两侧空闲比与 SPS 的变化。★
    提示
    学习时间上升、采样等待更久，SPS 可能下降；只有增加采样供给才是对的方向。
  3. 设计题：为跨两台机器的训练任务设计吞吐基准协议：预热、时长、取值、口径与记录字段，并说明跨机通信开销应如何单独测量。★★
    提示
    固定五要素；跨机开销用"其余项"与网络采样工具交叉验证；对照实验只改拓扑一个变量。
  4. 分析题：证明"学习器空闲比高"与"采样端空闲比高"在同步模式下互斥的近似性，并给出两者同时偏高的一种可能解释。★★★
    提示
    同步屏障下总时间由较长一段决定，两侧一般不会同时显著空闲；同时偏高通常说明第三类开销（通信、聚合或调度）占比大。

小结

  • 四个口径彼此独立：采样吞吐、更新吞吐、采样效率与硬件效率，各自回答不同问题。
  • 迭代时间拆成采样、学习、通信与聚合四段；分解结构决定优化方向，SPS = 批大小 ÷ 迭代时间。
  • 瓶颈判定看"谁在等"：连续多轮的空闲比是比单轮耗时更可靠的证据。
  • 基准协议五要素：预热、时长、取值、口径、记录；中位数与四分位距同时报告。
  • 下一章进入更新节奏本身：异步与同步两种更新模型在吞吐与偏差上的取舍。
