第三篇 · 端到端与配方

第 060 讲｜第三篇复盘：端到端 vs 模块化

第三篇从 CNN+RNN 的样本低效走到 OVRL-v2 的正向 scaling，共 20 讲。本讲不引入新方法，把第 041 至 059 讲的端到端结果与第二篇的模块化结果放进同一张决策表，用可解释性、数据、算力、泛化四轴给出选型框架，回答三个问题：端到端在什么条件下反超，模块化在什么条件下保有优势，混合方案如何分工。产出物是一张证据总表、一套选型流程与一份阶段自测。

  • 主题：篇末复盘 / 范式选型 / 成本与泛化对照
  • 关键公式：选型 = f(词汇, 数据, 算力, 归因, 稳健性)
  • 预计学时：80 分钟
  • 前置章节：第 059 讲 仿真吞吐与训练工程

学习目标

  • 能在一张表里复述第 041 至 059 讲代表配方的范式、数据、代表成绩与成本量级，并为每个数字标注协议。
  • 会算端到端与模块化的同协议差值：PirlNav 对 Stretch 基线的 SR、SPL 交换，PirlNav 对 DD-PPO 的倍率，辅助任务配方的相对提升。
  • 能按四轴框架做选型：给定词汇范围、演示与算力预算、归因需求与噪声条件，选端到端、模块化或混合，并写出判据与验证实验。
  • 会读正向 scaling 的证据与边界：OVRL-v2 的压缩层与训练改进带来了什么，为什么 64.0% 与 65.0% 属于同档。
  • 能完成阶段自测，定位第三篇薄弱环节，并说出第四篇需要补齐的能力（开放词汇、零样本与长尾）。

背景与动机

第 041 讲给出的起点并不乐观：CNN+RNN 端到端策略在没有配方时既过拟合又样本低效，这也是 2020 年前后模块化方案占优的原因。第三篇的二十讲把配方补齐：DD-PPO 解决分布式同步与规模（第 042 讲），表征预训练与 CLIP 骨干改善迁移（第 043、044、045 讲），辅助任务与探索奖励让稀疏成功信号可学（第 046、047 讲），人类演示与 BC→RL 两阶段把成功率推到 65.0%（第 048 至 052 讲），OVRL-v2 用 ViT 与压缩层给出正向 scaling（第 053、054 讲），第 056 至 059 讲补齐噪声、混合任务、真机落差与吞吐。到 2023 年，HM3D 验证集上端到端与模块化已经同档，个别 split 上端到端领先 5 个百分点。

但「同档」不等于「替代」。第 040 讲的第二篇复盘已经给出模块化的两张底牌：训练成本低至特定对手的 1/1600 量级，跨数据集迁移约为端到端对照的 95 倍。第三篇又给出端到端的条件性：65.0% 依赖 77k 条人类演示（约 2,378 人时）与 300M 步 RL 微调，换成零样本检测的开放词汇场景，端到端相对优势会随类别语义距离衰减。复盘的任务是把这些条件整理成可执行的选型流程，为立项提供判据。

口径提醒：本讲只比较带协议卡的数字。HM3D 语义 v0.1、MP3D 2021 与 2022 验证集三套协议互不换算；第 040 讲的复盘规则在本讲继续生效。

读法分三层。其一，反超是配方与数据的联合效应，与「范式标签」无关：DD-PPO 与 PirlNav 同属端到端，成功率差 39 个百分点，差距来自人类演示与两阶段微调。其二，同协议内端到端领先幅度有限：test-std 上 +5.0 点且 SPL 低 1.0 点，属于成功率与效率的交换；test-challenge 上 +9.0 点加 +4.0 点 SPL，优势更稳。其三，验证集与测试集差距要单列：PirlNav 的 val 70.4 / 34.1 比 test-std 高 5.4 个百分点，正式比较绑定 test 分割。

MP3D 一侧的证据来自辅助任务配方：24.5% / 8.1% 相对前 SOTA 的 17.9% / 7.5% 提升 36.87% 与 8.00%（按论文「+37% 与 +8%」的概括回算）。这条结果的意义在于证明端到端的短板可以通过辅助任务与探索奖励修复，也为后续「辅助任务 + 演示 + RL」的组合提供了机理：辅助任务压低循环网络的有效维度，让长程规划在低维平滑动力学上变得可学。

3. 模块化的对应证据

第二篇的系统对照给出模块化劣势的归因。第 040 讲汇总的 2022 验证集（2,000 条，同协议）中：OracleSem + Uniform + PointNav 为 64 / 32，PIRLNav 62 / 28，OVRL2 65 / 28；把检测从真值换成 Detic 零样本后，PredSem 掉到 30 / 14，落后 OVRL2 达 35 个百分点。模块化的成绩由检测质量主导，检测退化造成的落差超过任何单模块改进。

跨域与稳健性各有证据。迁移方面，模块化复用预训练 PointNav 从 MP3D 换到 HM3D 保持约 38% 成功率，而同场端到端模型掉到 0.3% 至 0.5% 区间，折算约 95 倍。稳健性方面，噪声注入使基于地图的 VLFM 成功率最多降 6.4 个百分点，而只用 RGB 序列的 DAgRL 加开放检测器最多降 0.3 个百分点（HM3D-OVON 噪声协议，Yokoyama 等，2024；第 056 讲）。两条证据都指向同一结论：模块化赢在可复用与可归因的结构，端到端赢在把感知与决策联合优化后对分布内数据的拟合能力。

失败结构给出改进优先级。PirlNav 对最好策略的 592 条验证失败标注中，缺失标注 27%、跨楼层 21%、识别失败 20%，前三项合计 68%；其余为最后一米 12%、导航网格失败 9%、语义混淆 5%、绕圈 4%、探索失败 2%。其中 27% 属于数据问题，跨楼层 21% 属于任务结构问题，只有约四分之一的失败与策略网络直接相关。这组数字提醒：换范式之前，先确认失败链是否落在范式能解决的环节。

5. 混合方案的分工原则

证据支持的分工有三条。第一条，检测交给开放词汇基础模型：DAgRL 加 OWLv2 检测器后，在 HM3D-OVON 三档评估上成功率提升 9.6 至 18.8 个百分点，追平并超过模块化的泛化优势。第二条，导航与探索交给学到的策略：同样在噪声注入下，学到的探索策略对里程计误差不敏感。第三条，停止与校核保留可替换接口：误停与漏检合计占失败的三至四成，保留一个可独立验证的停止模块便于定位问题。这三条构成「学习做主、模块兜底」的混合范式，也是第四篇多数方法的骨架。

实现思路与设计

复盘落地为三件工具：选型评分、成本核算与同协议判定。目标是在立项阶段就把路线、预算与验收标准写清楚。

选型流程

先过两条硬门槛：目标词表是否超出检测器的已有词汇，演示与在线专家是否可得。两个问题四种组合：词表封闭且有演示，端到端两阶段配方优先；词表封闭但无演示，先跑模块化零样本基线，再评估自动专家生成；词表开放但有检测器，混合方案（检测前端加学习导航）；词表开放且无检测预算，模块化零样本或纯 VLM 方案。硬门槛之后，用四轴打分细化，其中可解释性按团队运维能力加权。

关键代码与解读

三段代码分别把选型、成本与反超判定做成可复用函数。

片段 1：四轴选型函数

def choose_paradigm(open_vocab, demo_hours, gpu_budget, need_attribution):
    """四轴选型：开放词汇、演示预算、GPU 预算、归因需求。"""
    if open_vocab and demo_hours < 100:
        return "模块化或混合：零样本检测前端，不依赖任务演示"
    if open_vocab:
        return "混合：开放词汇检测加学到的导航策略"
    if need_attribution and gpu_budget < 8:
        return "模块化：逐模块日志优先"
    if demo_hours >= 2000 and gpu_budget >= 8:
        return "端到端：BC 加 RL 两阶段配方"
    return "混合：先跑零样本基线，按数据补齐端到端"

print(choose_paradigm(False, 2378, 16, False))   # 端到端
print(choose_paradigm(True, 0, 1, False))        # 模块化或混合
print(choose_paradigm(True, 2378, 16, True))     # 混合

解读：（1）判断顺序按证据强度排列，开放词汇与演示缺失先于算力判断，避免用算力硬撑错误路线；（2）阈值 100 人时与 2,000 人时来自课程证据（77k 条演示约 2,378 人时），团队可按自身采集效率重标，但要在实验记录里注明；（3）归因需求单独成支，因为失败日志是模块化不可替代的价值；（4）函数返回路线加理由，便于评审逐条质疑。

片段 2：训练成本三字段核算

def cost_record(name, demo_hours=0.0, rl_steps=0.0, gpu_days=0.0,
                reused_weights=False):
    """成本只记原语字段；折算系数由团队口径另行固定。"""
    return {"name": name, "demo_hours": demo_hours, "rl_steps": rl_steps,
            "gpu_days": gpu_days, "reused": reused_weights}

rows = [
    cost_record("DD-PPO", rl_steps=2.5e9, gpu_days=64 * 3),
    cost_record("PirlNav", demo_hours=2378, rl_steps=300e6),
    cost_record("Stretch 模块化", reused_weights=True, gpu_days=0.5),
]
for r in rows:
    print(r["name"], "演示人时", r["demo_hours"],
          "RL 步数", r["rl_steps"], "卡日", r["gpu_days"],
          "复用权重", r["reused"])
# 任何跨行总和之前，先确认三字段的定义与是否含预训练

解读：（1）成本拆成三个不可互换的原语字段，演示人时反映采集成本、RL 步数反映仿真负载、卡日反映算力占用；（2）DD-PPO 的 192 卡日由 64 卡乘 3 天得上限，实际按论文「少于 3 天」取下限口径时应标「小于 192」；（3）复用公开权重的方案把 reused 标为真，比较时单列，避免把社区成本记成自身成本；（4）若团队要合成单一指数，折算系数必须冻结并在论文与内部报告中同时披露。

片段 3：同协议反超判定

def dominance(a, b, margin=1.0):
    """同协议内比较 SR；协议键不一致直接拒绝，差值在 margin 内算同档。"""
    if a["protocol"] != b["protocol"]:
        raise ValueError("协议不一致，禁止排名：%s 对 %s" % (a["protocol"], b["protocol"]))
    dsr = a["sr"] - b["sr"]
    if dsr > margin:
        verdict = "%s 领先" % a["name"]
    elif dsr < -margin:
        verdict = "%s 领先" % b["name"]
    else:
        verdict = "同档"
    return dsr, verdict

pirlnav = {"name": "PirlNav", "protocol": "HM3D-v0.1-test-std", "sr": 65.0}
stretch = {"name": "Stretch", "protocol": "HM3D-v0.1-test-std", "sr": 60.0}
ovrl2 = {"name": "OVRL-v2", "protocol": "HM3D-v0.1-test-std", "sr": 64.0}
print(dominance(pirlnav, stretch))   # (5.0, 'PirlNav 领先')
print(dominance(pirlnav, ovrl2))     # (1.0, '同档') 边界值按含端点处理

解读：（1）协议键是字典键，训练时就统一命名，避免事后人工对齐；（2）margin 默认 1.0 个百分点，可按重复实验的置信区间上调；（3）同档分支显式输出，防止把 1.0 点的差距包装成反超；（4）同一函数可直接用于第 061 讲的三档开放词汇比较，只需把协议键改为对应的 split 名。

常见坑

  • 用范式标签替代条件判断：症状是写下「端到端更强」或「模块化已过时」的结论。根因是忽略检测口径与训练量两个条件。修复：任何范式结论必须附「同协议、检测来源、训练量」三要素；参照 PirlNav 65.0 与 DD-PPO 26.0 同属端到端的反例。
  • 跨协议并排数字：症状是把 MP3D 的 24.5 / 8.1、HM3D v0.1 的 65.0 / 33.0 与 OVON 的 41.3 / 21.2 放进同一张排名表。根因是数据集、类别数与判据不同。修复：本讲总表按协议分块，跨块只对照能力与成本。
  • 把训练量记成方法优势：症状是引用 PirlNav 65.0 时省略 77k 演示与 300M 步微调。根因是只抄结果列。修复：成绩与成本同表；演示人时、RL 步数、卡日三字段缺一不可。
  • 只看成功率不看 SPL 与失败结构：症状是把 65.0 / 33.0 对 60.0 / 34.0 描述为全面领先。根因是忽略 1.0 点的 SPL 回退与 68% 的失败集中在数据与结构。修复：SR 与 SPL 成对报告，复盘表附失败分类占比。
  • 用验证集结论替代测试集：症状是用 70.4 的 val 成绩对外声明领先。根因是 val 与训练场景同源成分更多。修复：正式比较绑定 test 分割；val 只用于选点与迭代。
  • 把仿真排名外推到真机：症状是假设 65.0 的仿真策略在真机同序。根因是第 058 讲所示的落差来源（检测、执行、传感分布）。修复：立项时并列仿真与真机两级验收指标，真机部分按第 087 至 096 讲的协议执行。

  3. 给定任务：25 类家用目标、8 张 GPU 可用、无人类演示但可自动生成前沿探索专家、需要逐模块记录失败。按四轴框架选一条主路线与一条备选，写出判据、预期短板与验证实验。★★
    提示

    提示
    接口：检测段输出目标框与深度坐标，导航段以 RGB 序列与目标嵌入为输入，停止段独立校验 1 m 条件。数据：导航段用 DAgger 加 RL，两阶段；检测段用开放词汇模型权重。矩阵为 3 档 split 乘有噪声与无噪声两档，控制变量锁同一检测器与同一 PointNav 权重。验收标准按 split 分别报告 SR 与 SPL，并要求噪声下 SR 降幅不超过 1 个百分点。相对纯端到端的优势在未见类别的泛化，相对纯模块化的优势在噪声下的定位鲁棒性与误停率。

小结

  • 第三篇证据总表：DD-PPO 26.0 / 12.0（HM3D v0.1，汇总口径）、辅助任务 24.5 / 8.1（MP3D 2021）、Habitat-Web 55.0 / 22.0、PirlNav 65.0 / 33.0、OVRL-v2 64.0 与 ImageNav 82.0、Stretch 模块化 60.0 / 34.0；每行绑定协议与成本。
  • 同协议数字账：test-std 上端到端领先 5.0 点但 SPL 低 1.0 点；test-challenge 上领先 9.0 点与 4.0 点；对早期 DD-PPO 的 2.50 倍差距来自演示与两阶段配方；MP3D 上辅助任务相对提升 36.87% 与 8.00%。
  • 模块化证据：真值检测时 64 / 32 与训练充分的端到端同档；零样本检测时落后 35 个百分点；跨域迁移约 95 倍；噪声下地图方案 SR 最多降 6.4 点，RGB 端到端最多降 0.3 点。
  • 四轴框架：可解释性、数据、算力、泛化，加噪声与定位一条工程开关；输出为主路线、备选与验证实验三件套。
  • 失败结构：缺失标注 27%、跨楼层 21%、识别失败 20%，前三项 68%；改进优先级先数据与结构，再感知，最后策略网络。
