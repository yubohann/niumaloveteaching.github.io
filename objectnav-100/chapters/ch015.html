第一篇 · 任务、仿真与评测地基

第 015 讲｜ProcTHOR：程序化生成

上一讲看到手工与扫描路线的规模上限：RoboTHOR 只有 89 个公寓，HM3D 也只有 1,000 个静态场景。本讲讨论第三条路线：ProcTHOR 用程序化生成把可交互住宅扩到 10,000 个，并给出规模消融的量化证据。学完能说清生成流水线的每一步、多样性的五个来源、规模收益的对数斜率，以及这条路线与扫描数据之间仍然存在的分布差距。

  • 主题：程序化生成 / 场景多样性 / 规模消融 / 0-shot 泛化
  • 关键公式：v(N) = v(N0) · (N / N0)b（性能对训练规模的幂律拟合）
  • 预计学时：60 分钟
  • 前置章节：第 014 讲（AI2-THOR / RoboTHOR）

学习目标

  • 能画出 ProcTHOR 的生成流水线：户型规格、外墙切割、递归分区、连通约束、资产与语义资产组放置、材质与光照采样、校验器。
  • 能列举多样性的五个来源，并用 16 规格、>1000 亿布局、108 类 / 1633 实例资产、18 组语义资产组等数字说明规模。
  • 能用消融表实算 0-shot 性能对训练屋数的对数斜率，解释斜率差异，并说清为什么不能把它外推到任意规模。
  • 能核算生成与渲染成本：单屋 1.44 GPU 秒、8 卡 120 进程下 25 亿步的渲染墙钟量级。
  • 能判断程序化环境与扫描环境的分布差距，给出「预训练加微调」「纯 0-shot」两条路线的适用判据与边界。

背景与动机

第 014 讲结尾留下一个规模问题：RoboTHOR 的训练集只有 60 个公寓，模型很容易记住场景；HM3D 把扫描场景扩到 1,000 个，又受限于静态、不可交互、采集周期长。行业内多次观察到同一现象，训练场景不足时，端到端模型在未见环境上的表现会明显下降，单靠换网络结构难以补救。一个自然的假设是：只要训练环境的数量与多样性足够大，泛化问题就能显著缓解。程序化生成正是验证该假设的工程路径。

Deitke 等（2022）提出 ProcTHOR，建在 AI2-THOR 之上：输入一份户型规格，输出一间完全可交互、带物理引擎的住宅。论文采样了 10,000 间住宅（ProcTHOR-10K），配上 1,000 间验证与 1,000 间测试，并用最简单的 CNN 加 GRU 架构、只吃 RGB 图像训练，在六个具身基准上取得当时的最好结果，其中三个是零样本成绩。这个结果的含义超出模型本身：它把「数据规模」变成了具身智能的可控变量。

本讲解决三个问题：生成流水线如何工作、多样性如何量化、规模收益如何读。第 016 讲接着讨论观察与动作口径，第 042 讲会用到这里的吞吐数字做训练工程核算。

核心原理

1. 从手工到程序化：问题定义

程序化生成的目标函数可以写成一句话：在给定户型规格的条件下，采样一间满足物理与常识约束、且分布足够多样的住宅。用符号表示，设规格为 σ，资产库为 A，材质库为 M，光照参数为 L，生成器 G 输出场景 s 的 JSON 规格：

s ~ G(σ; A, M, L)，  σ ∈ Σ，|Σ| = 16 Σ 为户型规格集合；论文用 16 种规格作为种子，可组合出 1000 亿量级的布局

生成对象不只是几何布局。ProcTHOR 的场景继承 AI2-THOR 的物理与交互能力：门可以开、灯可以开关、物体可以抓取与改变状态。与扫描路线相比，这是结构性的差别：HM3D 一类扫描场景可以做导航与识别，无法做带物理的交互；与 OpenRooms 等扫描加标注路线相比，程序化生成不需要为每个物体手工标注材质。代价是分布保真度：程序化住宅来自生成器的先验，扫描住宅来自真实世界的统计。

2. 生成流水线

论文给出的流水线分阶段执行，每一步都是条件采样：

  1. 户型规格：例如「1 卧室接 1 浴室、1 厨房、1 客厅」。16 种规格覆盖 1 到 10 个房间的住宅，用于控制规模分布。
  2. 外墙切割：用迭代边界切割得到外部轮廓，形状从简单矩形到复杂多边形。
  3. 递归分区：用 Lopes 等的递归布局算法把轮廓切成目标房间；边长下限保证房间可导航。
  4. 连通约束：按常识规则确定门的位置，例如浴室更常只有一个入口，卧室常与相邻浴室相连。
  5. 资产放置：先放地面大件（床、餐桌），再放墙挂件（窗户、画），最后放台面物件（杯子、盘子）；语义资产组（Semantic Asset Group, SAG）按共现关系依赖采样，例如餐桌配四把椅子。
  6. 材质与光照：墙面从 40 种纯色与 122 种纹理中采样，地板 55 种材质；光照含一盏方向光与若干点光源，模拟一天中的不同时段。
  7. 校验器：检查可导航性、物体是否互相穿模、房间是否连通；不合格的户型丢弃或重采样。

每一步都保留了随机性，因此同一规格可以生成大量不同的住宅。论文报告 16 种规格合计可产生超过 1000 亿个布局；资产侧 108 类、1633 个实例，配合 18 组语义资产组，可组合出约 1930 万种组实例配置。存储方面，场景以 JSON 规格保存，运行时加载进 AI2-THOR，磁盘开销远小于网格数据。

4. ProcTHOR-10K 与规模对比

论文采样的数据集为 10,000 训练住宅，另有 1,000 验证与 1,000 测试，合计 12,000。住宅从 1 个房间到 10 个房间，分布覆盖小户型到大家庭住宅。与既有数据集的规模对比如下：

  • 相对 iTHOR 的 120 个房间，规模为其 83.3 倍；
  • 相对 RoboTHOR 的 89 个公寓，规模为其 112.4 倍；
  • 相对 HM3D 的 1,000 个扫描场景，规模为其 10.0 倍，且每个场景可交互。

生成成本低得出乎直觉：10,000 间住宅在单台工作站上用 4 张 RTX A5000 生成，耗时 1 小时，折合每屋 1.44 GPU 秒。与 RoboTHOR 单场景约 30 分钟的人工重配置相比，单位场景的成本比约 1250 倍。需要注意，这里比较的只是「生成」与「布置」两个环节；物理验真、渲染开销与下游训练成本不在其中。

读法要克制。第一，斜率在 0.12 到 0.31 之间，意味着规模每扩 10 倍，0-shot 性能提升三成到一倍，收益存在但递减，且论文只提供四个数据点、单一训练配置，不能外推到 100K 或更大。第二，消融并不单调：ArchitecTHOR 的 SR 在 100 到 1,000 之间从 18.6% 回落到 17.2%（SPL 仍从 0.102 升到 0.122），HM3D 在 100 到 1,000 之间两项都回落，说明单点结果包含训练方差与优化动力学因素，结论要以整体趋势支撑。第三，AI2-iTHOR 的起点高（10 屋就有 28.7%），因为它的房间风格与 ProcTHOR 更接近；HM3D 起点只有 1.60%，扫描场景与合成场景的外观统计差异最大，这正是下一节讨论的分布差距。

规模收益最终要落到下游成绩才有说服力。论文的完整结果分 0-shot 与微调两栏：RoboTHOR 上 0-shot 为 55.0% / 0.237，微调到 65.2% / 0.288，对比在 RoboTHOR 训练集上训练的 EmbCLIP 基线 47.0% / 0.200；AI2-iTHOR 上微调 77.5% / 0.621，对比基线 68.4% / 0.516；ArchitecTHOR 上微调 31.4% / 0.195，对比 18.5% / 0.118；HM3D 上微调 53.0% / 0.270，与同期榜单的 FusionNav 54.0% / 0.270 接近，换更大骨干后为 54.4% / 0.318。六个基准里，模型只吃 RGB、不用地图、不用人类任务监督。这条结论直接支撑第 016 讲的判断：观察口径与训练规模共同决定能走多远。

6. 渲染与训练吞吐

大规模训练要求仿真吞吐跟得上。论文在 8 张 Quadro RTX 8000、120 个并行进程下测得：导航动作的小户型 8,599 帧每秒、大户型 3,208 帧每秒；交互动作 6,488 与 2,861；环境查询 480,205 与 433,587。把导航帧率当作渲染侧上界，25 亿步以下的时间账如下（仅渲染，不含策略前向与梯度更新）：

经验步数小户型渲染墙钟大户型渲染墙钟
1 亿3.23 小时8.66 小时
10 亿32.30 小时86.59 小时
25 亿80.76 小时216.47 小时

作为对照，第 017 讲会看到 DD-PPO 在 2019 年的硬件上用 64 张 V100 训练 25 亿步，墙钟不到 3 天。两者任务、传感器与硬件都不同，数字不能直接比较；这里要建立的习惯是：任何「训练了多少步」的说法，都要连同环境数、并行进程、单步渲染成本与墙钟一起给出，否则无法复现。另一个工程点是场景规格的加载方式：静态生成一次存成数据集，或在训练循环里动态生成。前者可复现，后者多样性更高但实验记录更难对齐；论文的消融用静态数据集固定口径。

7. 边界与失效

  • 分布差距：程序化住宅来自生成器先验，与真实扫描的外观统计、房间比例、物体摆放习惯都可能有系统偏差。HM3D 上的 0-shot 只有 9.70% / 0.060，微调后回到 53.0% / 0.270，说明差距主要靠目标域数据弥合。
  • 单层限制：ProcTHOR 住宅为单层、1 至 10 个房间；HM3D 含多楼层建筑。跨楼层导航与楼梯代价需要别的环境（第 034 讲 MFNP 会回到这个问题）。
  • 验证器能力有限：校验器保证可导航与无穿模，难以保证常识合理性，例如家具风格混搭、物件摆放别扭；这类偏差会以长尾形式进入训练分布。
  • 动态材质随机化的口径风险：训练期每次载入重采材质可以提升多样性，但验证与测试若也开着随机化，同一策略在不同时刻的分数会漂移，复现实验必须先冻结评测材质。
  • 资产划分泄漏：训练、验证、测试的资产必须不重叠；若为了多样性把测试资产放进训练，ArchitecTHOR 一类测试集的意义会被稀释。

实现思路与设计

把程序化生成接入课程工作流，需要三个设计件：生成参数表、数据使用策略表、训练配方表。

3. 训练配方

论文的配方刻意简单，用来隔离数据规模的作用：视觉编码器用 CLIP 预训练的 ResNet50 骨干（重排任务）或三层卷积（机械臂任务），时序模块用 GRU，输入只含 RGB，不加深度、不做显式建图、不用人类演示；训练框架为 AllenAct；消融实验把每个模型训到训练期 80% 成功率为止。本课程复现时建议先锁定这套配方，再逐一改动，避免同时移动多个变量。

设计决策：把「规模」设为自变量

把训练屋数写成显式配置，固定模型、步数、评测协议，只移动这一维，才能把 0.06 到 0.21 的 SPL 变化归因到数据规模。若训练步数随数据集一起变，规模效应与训练预算效应纠缠，结论无法解释。

设计决策：测试集要来自另一种分布

ProcTHOR 自带的 1,000 测试屋与训练屋同源，容易高估泛化；ArchitecTHOR 的 10 个美术住宅来自更接近真实人工设计的分布，更能检验「学到的是程序化先验还是通用常识」。报告时应同时给出两个测试集的数字。

生成器版本要进实验记录

程序化生成器的采样逻辑一旦改动，同规格采样出的分布随版本漂移。实验记录至少固定：生成器版本、16 规格清单、资产划分、材质随机化开关、随机种子。缺一项，同分布复现就无从谈起。

关键代码与解读

三段教学代码覆盖核心机制：户型切分、语义资产组放置、规模消融拟合与吞吐核算。代码为教学简化实现，思路与论文流水线一致。

片段 1：户型切分与连通检查

import numpy as np

def sample_rooms(spec, rng):
    """把户型规格展开成房间类型列表，如 1 卧 + 1 卫 + 1 厨 + 1 客。"""
    rooms = [room for room, count in spec.items() for _ in range(count)]
    rng.shuffle(rooms)                        # 打乱后交给分区算法
    return rooms

def cut_rect(rect, horizontal, ratio):
    """按给定比例切一刀，返回两个子矩形。"""
    x0, y0, x1, y1 = rect
    if horizontal:
        yc = y0 + ratio * (y1 - y0)
        return (x0, y0, x1, yc), (x0, yc, x1, y1)
    xc = x0 + ratio * (x1 - x0)
    return (x0, y0, xc, y1), (xc, y0, x1, y1)

def split_until(rect, rooms, rng, min_side=1.5, depth=0):
    """递归切分到房间数匹配；边长下限保证房间可导航。"""
    w, h = rect[2] - rect[0], rect[3] - rect[1]
    if len(rooms) == 1 or depth >= 6 or w * h < min_side ** 2 * len(rooms):
        return {rooms[0]: rect}               # 退化情形整体作为一个房间
    too_narrow = w < 2 * min_side             # 宽度不足时禁止纵向切
    horizontal = True if too_narrow else rng.random() < 0.5
    ratio = rng.uniform(0.35, 0.65)           # 限制极端长条
    a, b = cut_rect(rect, horizontal, ratio)
    half = len(rooms) // 2
    out = split_until(a, rooms[:half], rng, min_side, depth + 1)
    out.update(split_until(b, rooms[half:], rng, min_side, depth + 1))
    return out

解读：（1）递归二分是 Lopes 等布局算法的简化版本，比例限制与边长下限共同防止出现不可用房间。（2）房间类型在切分前打乱，使同规格产生多样布局。（3）真实实现还要按常识规则调整连通与门窗，这里留作练习。（4）同一随机种子应复现同一布局，种子进入实验记录。

片段 2：语义资产组放置与可导航面积

def place_sag(room_poly, sag, free_mask, rng, clearance=0.4, tries=64):
    """在保持可导航面积的前提下放置语义资产组；放不下返回 None。"""
    x0, y0, x1, y1 = room_poly
    for _ in range(tries):                    # 有界拒绝采样，保证生成时间可控
        x, y = rng.uniform(x0, x1), rng.uniform(y0, y1)
        cells = free_mask.cells_under_sag(sag, x, y)
        if cells is None:                     # 越界或与已有物体重叠
            continue
        if free_mask.navigable_fraction_after(cells) < 0.45:
            continue                          # 摆放后过道不足，拒绝该位置
        free_mask.reserve(cells)              # 占位，后续资产不可重叠
        return sag.instantiate(x, y, rng)     # 采样组内朝向与材质
    return None                               # 多次失败则跳过该组

def check_house(free_mask, rooms):
    """校验器的教学版：连通性 + 可导航比例 + 无穿模。"""
    if not free_mask.connected(rooms):
        return False                          # 所有房间必须可达
    if free_mask.navigable_fraction() < 0.45:
        return False                          # 全局可导航面积不足
    return not free_mask.has_overlap()        # 物体两两不穿模

解读：（1）拒绝采样把「按常识摆放」与「保证可走」两个目标一起处理，尝试次数有界以控制生成成本。（2）0.45 的可导航比例是教学阈值，实际阈值随生成器版本；关键是它必须与校验器一致，否则生成与验收口径打架。（3）SAG 的依赖采样保证餐桌配椅、床配枕这类共现关系。（4）校验失败直接丢弃户型，数据集统计要把丢弃率一并报告。

片段 3：规模斜率与吞吐核算

import math

def loglog_slope(counts, values):
    """双对数坐标下取首尾两档估计幂律指数 b（局部趋势口径）。"""
    return math.log(values[-1] / values[0]) / math.log(counts[-1] / counts[0])

counts = [10, 100, 1000, 10000]
robothor_sr = [8.53, 20.9, 33.1, 44.5]        # 0-shot SR，单位 %
b = loglog_slope(counts, robothor_sr)
print("RoboTHOR SR 斜率 b =", round(b, 3))      # 0.239
print("每 10 倍规模倍率 =", round(10 ** b, 2))  # 1.73

fps_small, fps_large = 8599, 3208              # 8 卡 120 进程导航帧率
for steps in (1e8, 1e9, 2.5e9):
    print(f"{steps:.0e} 步渲染墙钟（小时）：",
          round(steps / fps_small / 3600, 2), "/",
          round(steps / fps_large / 3600, 2))

# 输出：2.5e+09 步渲染墙钟（小时）： 80.76 / 216.47
# 注：只含渲染，不含策略前向、反向与通信开销

解读：（1）斜率对端点敏感，四个数据点只能给出趋势，报告时应附原始点与拟合区间。（2）非单调的中间点不允许被挑选性引用，例如只引 100 到 1,000 的回落会得出相反结论。（3）吞吐核算只给下界，实际墙钟要加上策略网络与调度开销。（4）把这段脚本与评测记录放在一起，任何「用了多少数据、训了多久」的声明都可回溯。

常见坑

  • 把 0-shot 低分读成模型弱：症状是看到 HM3D 上 9.70% / 0.060 就否定预训练价值。根因是忽略了扫描域与合成域的分布差距；同一模型微调后回到 53.0% / 0.270。修复：0-shot 与微调成绩成对报告，并把分布差距作为实验结论的一部分。
  • 动态材质随机化泄漏进评测：症状是同一策略两次评测分数不同，或评测分数异常偏高。根因是训练与评测都开着材质随机化，评测分布的难度每刻变化。修复：评测固定材质与光照种子，训练侧保留随机化并在记录中注明。
  • 资产或规格泄漏：症状是测试分数远高于预期，换测试集后大幅回落。根因是训练与测试共享资产实例或户型规格。修复：训练、验证、测试资产三方不重叠；测试规格与训练规格清单分开登记，并做集合检查。
  • 只报 SR 不报 SPL：症状是 0-shot 的 SR 看着可以（如 55.0%），真实效率却差。根因是 0-shot SPL 往往只有 0.2 上下，路径冗长问题被 SR 掩盖。修复：SR 与 SPL 成对报告，并附失败类型的粗分类。
  • 把渲染帧率直接当训练吞吐：症状是估算的墙钟比实际短几倍。根因是策略前向、梯度更新、进程同步与场景重置都未计入。修复：用「渲染时间占单步总时间的比例」标定后才做外推，并给出实测吞吐。

小结

  • ProcTHOR 在 AI2-THOR 之上做程序化生成：户型规格、外墙切割、递归分区、连通约束、资产与语义资产组放置、材质光照采样、校验器七个阶段。
  • 多样性来自五个维度：16 规格的 1000 亿量级布局、108 类 / 1633 实例资产、18 组约 1930 万组合的语义资产组、162 种墙面与 55 种地板材质、可变光照。
  • ProcTHOR-10K 是 iTHOR 的 83.3 倍、RoboTHOR 的 112.4 倍、HM3D 的 10.0 倍；生成成本 1.44 GPU 秒每屋，与人工布置的比值约 1250 倍。
  • 0-shot 规模消融的斜率在 0.12 至 0.31 之间：RoboTHOR SR 0.239、HM3D SPL 0.311、ArchitecTHOR 0.126、AI2-iTHOR 0.118；中间点存在非单调回落，结论以趋势为准。
  • 微调仍必要：RoboTHOR 55.0% 到 65.2%，HM3D 9.70% 到 53.0%；ArchitecTHOR 用来检验跨分布泛化的真实性。
