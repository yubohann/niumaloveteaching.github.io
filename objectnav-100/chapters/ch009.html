第一篇 · 任务、仿真与评测地基

第 009 讲｜Habitat-Lab 上手与停更后果

Habitat-Lab 是任务、数据集、配置与训练的高层框架，ObjectNav 生态的绝大多数论文与挑战基线都建立在它之上。本讲给出可复现的安装与验证流程、Hydra 配置的读法与 PPO 基线命令，并正面处理一个工程事实：官方声明 v0.3.4 之后不再对该项目做活跃开发与维护。学会锁定版本、读懂停更后果、选择替代路线，是后续所有复现实验的前置条件。

  • 主题：环境搭建 / 配置系统 / PPO 基线 / 维护状态
  • 关键公式：环境步数 = 总步数 / 并行环境数；墙钟 = 总步数 / 实测步速
  • 预计学时：70 分钟
  • 前置章节：第 008 讲

学习目标

  • 能按官方文档写出 Habitat-Sim、Habitat-Lab、Habitat-Baselines 的三段安装流程，并给每一步配一条可执行的验收命令。
  • 能说明仓库的三层结构与 Hydra 配置的组合方式，会用命令行覆盖读取 objectnav_mp3d 实例的关键参数。
  • 能跑通 PPO 基线命令，解释 trainer_name=ver 的用途，并说出预训练模型按数据集与观察模态的划分。
  • 能画出 v0.3.0 到 v0.3.4 的发布时间线，解释「v0.3.4 之后不再官方维护」的含义与工程后果。
  • 能为一个复现项目设计版本锁定与替代路线方案（tag、通道、容器、分支自维护），并列出必须固定的清单。

背景与动机

第 006 至 008 讲把 Habitat 的三代能力讲完了：平台架构与性能、物理仿真与家务重排、类人与社交协作。能力要变成实验，必须落到一台机器上。Habitat-Lab 的公开仓库承担的正是这个角色：它把仿真的细粒度接口包成任务、数据集与配置，向上提供强化学习、模仿学习与多智能体训练的基线，向下对接 Habitat-Sim 的渲染与物理。课程后续要跑的 MP3D、HM3D、OVON 评测与复现实验，入口都在这里。

这个入口有一个必须先说清的工程事实。仓库 README 顶部给出警示：v0.3.4 之后，项目不再获得原维护团队的活跃开发与维护，欢迎社区自行分支并继续开发。这个风险已经发生，依赖管理的做法随之改变：Python 版本、NumPy 上限、Habitat-Sim 的 C++ 二进制与 conda 求解都进入冻结状态，任何上游更新都可能在没有官方适配的情况下破坏环境。写本讲的目的是让读者在上手第一步就建立版本纪律，避免实验失败后再补救。

本讲解决四件事：官方安装路径与验收；配置系统的读法与覆盖方式；PPO 基线的运行与产出；停更之后的版本锁定与替代路线。本讲不重复 Habitat-Sim 的渲染原理（第 006 讲）与物理引擎细节（第 007 讲），也不展开 ObjectNav 数据集本身（第 010 讲起）。所有命令与版本号来自公开仓库文档与发布记录，写作时点以文中标注为准。

核心原理

1. 三层结构与依赖关系

公开仓库分为三个可独立安装的部分，理解三者的边界可以省掉大量排错时间：

层包名职责
核心库habitat-lab任务定义、数据集加载、配置系统、Gym 接口、评测度量
基线库habitat-baselinesPPO、分层策略、多智能体与社交任务训练、训练器实现
交互层habitat-hitl人在环客户端/服务器、VR 与 XR 接入、数据采集

依赖方向是单向的：baselines 与 hitl 依赖核心库，核心库依赖 Habitat-Sim。Habitat-Sim 是带 C++ 扩展的仿真器，通过 conda 二进制分发，因此 Python 包管理器与 conda 通道之间存在强耦合。安装文档因此要求先建好 conda 环境（Python 3.9、CMake 3.14 以上），再从 conda-forge 与 aihabitat 通道装模拟器，最后用 pip 的可编辑模式安装两个 Python 包。把安装顺序颠倒，或者用 pip 单独安装模拟器，是环境失败的最常见来源。

三个包对应三种使用切面：只做数据与评测，装核心库足够；要训练策略，必须装基线库；要做真人在环实验，才需要交互层。后文的所有命令都建立在三个包齐备的假设上。

2. Hydra 配置系统与实例解析

Habitat-Lab 用 Hydra 组织配置：一个入口 yaml 通过 defaults 列表组合若干子配置，运行时可在命令行用 键=值 覆盖任意字段。以 objectnav_mp3d 入口为例，它的 defaults 组合了基础配置、任务配置、传感器配置与数据集配置四块，解析后的关键值如下：

配置键值说明
habitat.environment.max_episode_steps500单 episode 环境步预算
habitat.simulator.turn_angle30转身角度，与 2020 共识一致
habitat.simulator.agents.main_agent.radius0.18 m对齐 LoCoBot 的本体半径
habitat.simulator.agents.main_agent.height0.88 m本体高度
rgb_sensor / depth_sensor640 × 480，水平视场 79°彩色与深度同步
depth_sensor.min_depth / max_depth0.5 / 5.0 m量程随配置版本变化，引用时以对应版本口径为准
habitat.simulator.habitat_sim_v0.allow_slidingFalse关闭碰撞滑动

这份解析值本身就是一堂口径课。它说明三件事：第一，任务参数位于配置层，与代码分离，改参不需要改源码；第二，不同配置入口对应不同数据集与传感器组合，objectnav_mp3d 与 HM3D 版入口不能互换；第三，配置值会随仓库版本移动，实验记录必须同时保存入口名与覆盖列表，只写「用了 Habitat 默认配置」无法复现。

cfgresolved = compose(defaults) ⊕ overrides，  override 形如 key=value ⊕ 表示按 Hydra 规则逐字段合并；列表型字段用方括号追加，标量字段直接替换

覆盖机制是复现实验的主力工具。常用例子包括：把 habitat.environment.max_episode_steps 调大做长程压力测试；把并行环境数按显存缩放；把 habitat_baselines.evaluate=True 从训练切换为评估。每次覆盖都应写进实验日志，因为合并后的配置才是最终运行口径。

3. PPO 基线：从论文到命令

基线库实现的近端策略优化（Proximal Policy Optimization, PPO）来自 Schulman 等（2017），代码结构参考公开的 A2C/PPO/ACKTR 实现。它覆盖三个观察模态（RGB、RGBD、Depth）与两个数据集（Matterport3D、Gibson）的预训练模型，是 ObjectNav 论文里最常被引用的起点基线。常用命令形态如下：

操作命令要点产出
训练（示例数据）python -u -m habitat_baselines.run --config-name=pointnav/ppo_pointnav_example.yaml检查点与 tensorboard 日志
切换训练器追加 habitat_baselines.trainer_name=ver以墙钟换效率的替代训练器
评估追加 habitat_baselines.evaluate=True在指定检查点上跑评测集
预训练模型按观察模态分 RGB / RGBD / Depth 三份，覆盖两个数据集免训练复现基线数字

两个细节值得强调。其一，示例配置 ppo_pointnav_example.yaml 面向小规模数据与冒烟测试，公开文档另有一份面向大规模训练的超参配置，并默认加载 Gibson 数据；换成 MP3D 需要在 defaults 中把数据集项改为对应入口。其二，训练器 ver 是文档明确提供的省时选项，通过命令行或配置切换，行为与原训练器在样本效率上存在差别，切换训练器后不应直接与切换前的曲线对比。

4. 发布时间线与维护状态

把官方发布记录整理成时间线，可以看清维护节奏的变化：

版本发布日期主要内容距上一版
v0.3.02023-10-20Habitat 3.0：多智能体训练、类人、HSSD、HITL 重排应用首个 0.3 版本
v0.3.12024-03-15HITL 独立包、远程 VR 评估、Spot 社交导航147 天
v0.3.22024-10-30HITL 界面与数据采集体系、仿真工具函数229 天
v0.3.32025-01-27CI 迁移与 PyPI 发布、HITL 维护性修复89 天
v0.3.42026-05-07XR 控制器、发现服务器、XR 读取应用；CI 升级到 Python 3.12；依赖上限调整465 天

最后一行是信号。v0.3.3 到 v0.3.4 相隔 465 天，几乎是前一间隔 89 天的五倍；v0.3.0 到 v0.3.4 的总跨度为 930 天。发布说明同时出现两条方向相反的线索：CI 环境升级到 Python 3.12，而安装文档仍以 Python 3.9 为口径。这正是一个项目进入冻结期的典型状态，文档与流水线开始漂移，用户必须自己选择对齐哪一侧。

维护状态原文要点

仓库 README 明确写道：v0.3.4 之后，项目不再获得原维护团队的活跃开发与维护，社区可以自行分支并继续开发。工程含义是：不会再有官方缺陷修复、平台适配与安全更新；所有版本问题需要使用者自行解决或依赖社区分支。把这句话读成「项目不可用」是误读，把这句话读成「可以随便升级依赖」同样是误读，正确姿势是冻结版本并自带补丁能力。

Python 版本的分叉值得单独提醒。v0.3.4 的 CI 已经升级到 Python 3.12，说明源码层面对新解释器做过测试；但仿真器是以二进制方式分发的 C++ 扩展，能否在 3.12 上直接安装取决于 conda 通道是否同步提供对应构建。冻结期内，最稳妥的路线仍是对齐安装文档的 3.9 口径，或者整体使用容器，把解释器与二进制的组合一次性固定。若必须在 3.12 上工作，先把仿真器加载与一条 episode 的步进跑通，再迁移训练代码，避免在混合栈里同时排查两类问题。

5. 数值算例：发布间隔与训练墙钟

先用发布间隔做一次趋势判断。四个间隔为 147、229、89、465 天；去掉最后一个异常值，前三个间隔的均值为 (147 + 229 + 89) / 3 = 155 天；最后一个间隔是均值的 3.0 倍。这说明冻结前的节奏大约是五个月一版，冻结信号出现在 2025 到 2026 年之间。

再做训练规模与墙钟的换算。社交任务公开配方使用 1e9 环境步，这是本课程反复出现的大规模训练量级（第 017 讲会给出 2.5B 步的经典对照）。墙钟时间等于总步数除以实测步速，下表给出三档假设：

实测步速（环境步/秒）1e9 步所需小时折算天数适用场景
2001388.957.9单卡小内存、物理仿真为主
500555.623.1中等并行、图像观察
1000277.811.6高并行、观察较轻

并行环境数决定单个环境承担的步数：1e9 步除以 12、24、64 个环境，分别是约 8.33e7、4.17e7、1.56e7 步每环境。墙钟并不随并行度线性下降，因为仿真吞吐、GPU 前向与数据拷贝会先后成为瓶颈，第 059 讲会用吞吐核算表把这条曲线算清。当前只需记住两个公式：每环境步数 = 总步数 / 并行环境数，墙钟 = 总步数 / 实测步速。任何「训练要多久」的估计都建立在这两个式子上，离开实测步速的估计没有意义。

小规模验证的账也同样算。片段 2 的冒烟配置是 1e6 步、8 个并行环境，按 500 步/秒的实测步速约 33.3 分钟（1e6 / 500 / 60）；若步速只有 200 步/秒则拉长到约 83.3 分钟。先用小规模确认配置解析、日志与检查点路径，再投放大规模训练，是冻结期项目的基本节奏，因为版本问题在小规模阶段暴露的修复成本最低。

验收也不应止步于「导入成功」。建议在装好环境后跑一条固定种子的短程 episode，记录三个数字：动作步数、累计回报、实测步速，作为该环境的基线。以后每次重建环境先复跑这条 episode，三个数字在容许噪声内一致，才允许开始正式训练。这个做法把「环境是否还是原来那个环境」变成一个可检查的布尔问题，比凭印象判断可靠。

6. 停更的工程后果

冻结一个单体仿真框架，后果可以按依赖链从上到下拆开：

层冻结后的风险触发条件缓解
Python 运行时文档口径 3.9 与 CI 口径 3.12 分叉，旧依赖在新解释器失配用新 Python 建环境按文档钉 3.9，或整体容器化
数值库NumPy 大版本升级破坏编译扩展pip 自由求解锁上限（v0.3.4 的 CI 已给出一个上限写法），生成锁文件
仿真二进制conda 通道求解失败或与 pip 包错配混装来源、通道缓存变化固定通道与构建号，缓存安装包离线复用

修复与适配上游 PyTorch、驱动更新后无官方补丁升级 GPU 栈自行分支打补丁，或选用社区维护分支

这份表同时是一份复现清单：每一行都对应一个必须冻结的对象。第 010 讲开始进入具体数据集，读者会频繁遇到「同一份代码在不同数据版本上结果不同」的问题，届时回到本表按行排查即可。

7. 替代路线与选择判据

停更之后有三条现实路线，适用场景不同：

路线做法优劣势
钉死官方 tag检出 v0.3.4 tag 或对应提交，锁依赖，自存数据最贴近论文口径；缺失新修复，需要自建补丁流程
容器复现使用官方挑战镜像（公开的 2022 基础镜像）跑评测，训练另备环境环境一致性好；镜像内组件固定，扩展受限
分支自维护基于 v0.3.4 建内部分支，只打必要补丁可控性最好；维护成本与回归测试责任全部自担

选择判据可以压缩成三个问题：实验是否需要与公开榜单逐位对齐；团队是否具备维护 C++/Python 混合栈的能力；硬件与驱动是否长期不变。三个答案都偏向稳定时就选容器或官方 tag；需要持续集成、硬件会更新时就建内部分支。千万不要在同一批次实验里混用多条路线，环境差异会混入算法对比，之后无法归因。

实现思路与设计

把本讲落成一套可交接的工程配置，需要三张表：安装与验收、版本锁定、风险记录。安装流程按公开文档复述为五步，每一步都给出验收动作：

步骤操作要点验收
1. 建环境conda 创建 Python 3.9、CMake 3.14 以上的环境并激活python 与 cmake 版本命令输出符合要求
2. 装仿真器从 conda-forge 与 aihabitat 通道安装 Habitat-Sim（含物理支持变体）导入 habitat_sim 成功，打印版本
3. 装核心库克隆 stable 分支或以 v0.3.4 tag 检出，pip 可编辑安装 habitat-lab导入 habitat 成功，能加载配置
4. 装基线库pip 可编辑安装 habitat-baselines 及其子模块依赖能 import habitat_baselines 并列出配置
5. 冒烟测试运行示例脚本与测试场景下载工具episode 正常跑完可步进；测试场景可加载

两点提醒。测试场景数据不含语义标注，只能用于接口冒烟，验证 ObjectNav 需要另下带语义的数据集；示例脚本以重排任务为例，与导航任务的配置入口不同。把冒烟测试当作「任务可跑」的证明，会在正式数据上再次排错。

版本锁定表把必须固定和可浮动的对象分开，避免锁得过死或过松：

对象建议理由
Habitat-Lab钉到 v0.3.4 tag最后官方版本；stable 分支会移动
Habitat-Sim钉到带构建号的 conda 包C++ 扩展对构建敏感
Python3.9（按安装文档）与文档口径一致，避开 3.12 分叉
NumPy锁上限，不随 pip 漂移v0.3.4 的 CI 固定了一个上限以稳定求解
PyTorch按 CUDA 驱动成对固定升级任一侧都可能需要重编译扩展
数据集与 episode本地存档并记录下载标识在线源可能消失；版本错配直接改变评测

风险记录表用于交接：每条风险写清触发条件与缓解动作，训练出现环境级故障时按表处理，不靠记忆排错。

风险触发条件缓解动作
模拟器导入失败pip 与 conda 混装、ABI 不一致重建环境，按文档顺序重装
向量化环境挂起子进程异常被静默打开调试环境变量切换为慢速向量环境定位
依赖求解失败通道更新或 pip 自由求解使用锁文件与离线包缓存
数据不可下载在线源变动启用本地存档副本
回归测试失效切换训练器或并行度固定冒烟配置，跑固定步数比对日志
设计决策：stable 分支不作为复现基准

安装文档给出的克隆方式是 stable 分支，它适合起步，却在复现时留下隐患：分支内容会随时间移动，两次克隆可能得到不同代码。复现项目应当检出 tag 或提交号，并把该标识写进实验记录与锁文件，让「当时用的哪份代码」可查。

设计决策：调试开关只在排错时打开

向量化环境为了吞吐牺牲了报错信息，异常可能表现为挂起。文档提供了调试环境变量，打开后改用逐线程执行、信息完整但更慢的向量环境。它的正确用法是排错时临时开启，定位后立刻关闭，长期开启会让训练墙钟显著变长。

冻结清单必须随实验走

一份可复现的 Habitat 实验记录至少包含：Habitat-Lab 提交号、Habitat-Sim 包构建号、Python 与数值库版本、配置入口与完整覆盖列表、数据集与 episode 文件标识、随机种子、实测步速与墙钟。任何一项缺失，都可能在半年后变成无法解释的结果差异。

工程目录建议按职责分离，减少环境问题与算法问题互相污染：configs/ 存放实验入口与覆盖列表，runs/ 存放按实验编号归档的日志、检查点与配置快照，data/ 只读挂载数据集与 episode，locks/ 存放依赖锁文件与包清单。四个目录的命名规则写进团队约定，任何一次训练都能从实验编号反查到上述冻结清单。目录纪律看似琐碎，它决定了停更环境中「昨晚的结果还能不能复现」这个问题的答案。

关键代码与解读

下面三段代码分别对应上手三个动作：开训前预检版本组合、按 Hydra 规则启动 PPO、把解析后的配置冻结成快照。

片段 1：开训前版本预检

import sys
from importlib.metadata import version, PackageNotFoundError

PINS = {"habitat-lab": "0.3.4", "habitat-baselines": "0.3.4", "habitat-sim": ""}

def preflight():
    if sys.version_info[:2] != (3, 9):
        print("提示: 安装文档以 Python 3.9 为口径, 当前为", sys.version.split()[0])
    for pkg, want in PINS.items():
        try:
            got = version(pkg)
        except PackageNotFoundError:
            raise SystemExit("缺少 %s: 请先完成对应安装步骤" % pkg)
        if want and not got.startswith(want):
            raise SystemExit("%s 版本 %s, 期望前缀 %s" % (pkg, got, want))
    print("预检通过: 三个包齐备, 可以进入训练")

preflight()

解读：（1）三个包分别对应核心库、基线库与仿真器，任一缺失都直接失败，避免训练半小时后才在回调里报导入错误。（2）Python 版本只提示不拦截，因为下游工具链可能与 3.9 分叉，提示信息足以让使用者做决定。（3）期望值用前缀匹配，兼容 0.3.4 之后的补丁级后缀，同时拦住从 0.3.x 跳到其它次版本的情况。（4）该脚本放进项目仓库的入口，作为每次建环境的固定动作，比写在文档里的口头约定可靠。

片段 2：按覆盖规则启动 PPO

import subprocess

BASE = ["python", "-u", "-m", "habitat_baselines.run"]

def run_ppo(overrides, evaluate=False):
    cmd = BASE + [
        "--config-name=pointnav/ppo_pointnav_example.yaml",
        "habitat_baselines.evaluate=%s" % evaluate,
        "habitat_baselines.trainer_name=ver",   # 文档给出的省时训练器
    ] + list(overrides)
    print("将执行:", " ".join(cmd))
    subprocess.run(cmd, check=True)

run_ppo([
    "habitat_baselines.total_num_steps=1000000",
    "habitat_baselines.num_environments=8",
    "habitat_baselines.tensorboard_dir=runs/009",
])

解读：（1）Hydra 的覆盖项就是普通命令行参数，直接拼进列表即可，无需解析 yaml；把覆盖集中成列表便于日志留存。（2）布尔值用字符串形式传入，与 Hydra 的解析约定一致。（3）示例配置面向小数据冒烟，先用 1e6 步与 8 个环境验证流程，再放大规模；放大时并行度与总步数要同步调整，否则每环境步数变化会让学习曲线形状改变。（4）切换 ver 训练器后，与原训练器的曲线不可直接对比，实验记录里必须写明。

片段 3：解析配置并冻结快照

import json
import habitat

KEYS = [
    "habitat.environment.max_episode_steps",
    "habitat.simulator.turn_angle",
    "habitat.simulator.agents.main_agent.height",
    "habitat.simulator.agents.main_agent.radius",
    "habitat.simulator.habitat_sim_v0.allow_sliding",
]

def freeze_manifest(entry, overrides, out_path):
    """把入口配置与覆盖合并后, 抽取关键字段存成快照。"""
    cfg = habitat.get_config(entry, overrides=overrides)
    snap = {k: cfg.get(k) for k in KEYS}
    with open(out_path, "w", encoding="utf-8") as f:
        json.dump(snap, f, ensure_ascii=False, indent=2)
    return snap

print(freeze_manifest("benchmark/nav/objectnav/objectnav_mp3d.yaml", [],
                      "objectnav_mp3d_manifest.json"))

解读：（1）habitat.get_config 按入口名组合 defaults，并接收覆盖列表，得到与运行时一致的解析结果，内含 OmegaConf 的点路径读取能力。（2）只抽取关键字段写成 JSON 快照，比整份配置更可读，也便于跨实验对比差异。（3）这个快照应和检查点一起归档，评审或复现时先看快照再看代码。（4）若解析时抛出字段不存在，优先检查入口名是否属于当前仓库版本，冻结期最常见的问题是照旧文档用了已被移动的配置键。

常见误区

  • 只装了核心库：症状是训练脚本报找不到 habitat_baselines。根因是核心库安装不包含基线子包，文档要求单独安装。修复：追加基线库的可编辑安装，并把它写进环境清单。
  • pip 与 conda 混装仿真器：症状是导入仿真器报符号错误或运行时崩溃。根因是 C++ 扩展与编译期依赖不匹配。修复：删环境重建，按文档的通道与顺序安装；如需离线，缓存同一构建号的包。
  • 向量环境静默挂起：症状是训练进程不动、无报错、CPU 占用异常。根因是子进程异常被向量化封装吞掉。修复：打开调试环境变量，切换到信息完整的慢速向量环境定位问题，修复后关闭。
  • 把 stable 分支当作固定版本：症状是两个月后重跑，结果漂移且无法归因。根因是分支内容持续更新。修复：检出 v0.3.4 tag 或记录完整提交号，写进实验记录与锁文件。
  • 无视停更后自由升级：症状是换新机器后环境全线失败，旧实验无法重跑。根因是上游依赖更新与冻结项目失配。修复：生成锁文件、缓存包与数据，用容器或内部分支承接补丁。

  1. 写出安装五步中每一步的验收动作，并说明为什么「测试场景能加载」不等于「ObjectNav 可跑」。★
    提示
    验收关注导入、版本、示例步进与数据加载。测试场景不含语义标注，ObjectNav 需要带语义标注的场景与对应 episode 数据集。
  2. 用发布时间线计算：前三个版本间隔的均值，以及最后一个间隔相对均值的倍数；据此说明冻结信号出现的时间段。★
    提示
    均值 155 天，最后间隔 465 天约为 3.0 倍，信号出现在 2025 到 2026 年之间的版本迭代上。
  3. 设总步数 1e9，并行环境从 24 增到 64。计算每环境步数的变化；再结合墙钟不随并行度线性下降的事实，解释为什么扩并行只能部分缩短训练时间。★★
    提示
    每环境步数从约 4.17e7 降到 1.56e7，降幅 62.5%。瓶颈会从仿真吞吐转向 GPU 前向与数据搬运，边际收益递减，需要用实测步速推算墙钟，核数只能作为参考。
  4. 给出三个故障现象（导入失败、挂起、求解失败），分别写出根因与修复动作，并说明哪一项最可能由停更引起。★★
    提示
    导入失败多为混装；挂起为向量环境吞错；求解失败常因上游依赖更新与冻结通道失配。第三项与停更关系最直接，缓解手段是锁文件、离线缓存与容器。
  5. 〈综合〉为一个即将开始的 ObjectNav 复现项目写「环境冻结方案」：列出至少八个必须固定的对象、你们的获得方式、验证方法与失败回退；再论证在「严格对齐公开榜单」与「持续升级硬件」两个目标之间，方案应如何取舍。★★★
    提示
    固定对象可含：代码 tag、仿真器构建号、Python、数值库、PyTorch 与 CUDA、配置入口与覆盖、数据与 episode、随机种子。对齐榜单优先官方 tag 加容器；持续升级硬件则需要内部分支承载补丁，两套环境并行维护，不同批次实验不混用。

小结

  • Habitat 仓库分核心库、基线库与交互层三层，依赖方向单向；安装顺序与通道纪律决定了环境成败。
  • 配置由 Hydra 组合，命令行覆盖是复现的主力工具；解析后的 objectnav_mp3d 关键值（500 步预算、30° 转身、0.18 m 半径、79° 视场、关闭滑动）应记录进实验日志。
  • PPO 基线提供 RGB、RGBD、Depth 三种模态与两个数据集的预训练模型；训练器与配置入口按用途切换，切换后曲线不可直接对比。
  • v0.3.4（2026-05-07）是最后官方版本，间隔 465 天显著拉长，README 声明此后不再官方维护；文档口径 3.9 与 CI 口径 3.12 的分叉是冻结期典型现象。
  • 冻结期工程做法是钉 tag、锁依赖、存数据、缓存包；替代路线为官方 tag、挑战容器、内部分支三选一，同一批实验不混用。
