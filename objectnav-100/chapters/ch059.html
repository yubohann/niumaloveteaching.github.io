第三篇 · 端到端与配方

第 059 讲｜仿真吞吐与训练工程

第 041 至 058 讲给出了端到端配方，但配方能否跑完由仿真吞吐决定。本讲以 Habitat 2.0（Szot 等，2021，arXiv:2106.14405v2）的基准数据为主线，建立三本账：SPS（每秒仿真步数）的口径账、单进程到八卡的扩展账、步数到墙钟的换算账；再拆解惰性仿真、流水线交错与简化复用三项提速工程，最后给出测量协议与瓶颈诊断流程。

  • 主题：仿真吞吐 / 并行扩展 / 训练墙钟 / 性能测量协议
  • 关键公式：RTF = SPS / 30；W = N / SPS总
  • 预计学时：80 分钟
  • 前置章节：第 058 讲 Sim 与真机落差量化

学习目标

  • 会算：由 SPS 求实时因子 RTF = SPS / 30，由步数预算与总吞吐求墙钟，并核算多进程与多卡相对单进程的扩展效率。
  • 会测：按 Idle 与 Interact 双场景、10 次运行、95% 置信区间的协议测量 SPS，并区分纯仿真吞吐与端到端训练有效吞吐。
  • 会判断：把训练循环拆成仿真、推理、优化三段，依据各段耗时与显存占用决定加进程、加卡，或改渲染与网络配置。
  • 会读：Habitat 2.0 的三项提速工程（惰性仿真、渲染与物理交错、简化与复用）及其消融数字，界定 850× 实时因子声明的适用口径。
  • 会设计：给定 48 小时训练窗口与步数预算，反推所需总吞吐、并行配置与回退方案，并写出验收指标。

背景与动机

第 042 讲把 DD-PPO（Wijmans 等，2020）的 2.5B 步规模与 107 倍加速比讲成了算法与同步协议；第 007 讲介绍了 Habitat 2.0 的物理仿真与 HAB 任务。两者之间缺一本账：仿真器每秒能推进多少步、这些步数怎样随进程与 GPU 扩展、多少步能换成一小时训练。缺少这本账，配方表只是纸面数字。以第 049 讲的 PirlNav 为例，RL 微调 300M 步在 16 卡 DD-PPO 上完成；若单进程交互场景只有 510 SPS，仅采样就需要约 163 小时，等于约 6.8 天纯仿真时间，尚未计入策略推理与优化。

Habitat 2.0 给出的答案分两层。工程层，它把渲染与物理做成流水线，并用三项惰性化手段减少无谓计算，使单个 ReplicaCAD 场景内的 Fetch 交互基准从无优化时的 242 SPS 提到 1191 SPS（Idle 场景），八卡 64 进程达到 25,734 SPS。方法层，它把「仿真步」定义清楚：一步包含 1 次渲染与 4 次物理子步，合计 1/30 秒仿真时间，因此 30 SPS 恰好是实时，25,734 SPS 对应约 858 倍实时。吞吐不是孤立的性能数字，它由场景、传感器、物理负载与并行方式共同决定；报告口径不全会让复现结果相差一个数量级。

本讲沿用第 007 讲的任务定义与平台描述，不再重复 HAB 的任务分解；关注点放在吞吐测量、扩展与换算。第 060 讲回顾时会把本讲的三本账与第 041 至 058 讲的配方并排，回答「什么配方在什么算力下可行」。

核心原理

1. 仿真步、SPS 与实时因子

Habitat 2.0 的基准配置中，每个仿真步包含 1 次渲染与 4 次物理子步，每个物理子步模拟 1/120 秒，合计 1/30 秒仿真时间。传感器为 Fetch 头部与臂部两台 128×128 RGB-D 相机，实验台配置为双路 Intel Xeon Gold 6226R（合计 32 核 64 线程）与 8 张 NVIDIA 2080 Ti。单卡基准将进程限制在 8 核 16 线程，多进程基准在单卡上启动 16 个进程，八卡基准启动 64 个进程（每卡 8 个）。

RTF = SPS / 30 30 SPS 对应 1 倍实时；1191 SPS 对应 39.70 倍；25,734 SPS 对应 857.80 倍（论文概括为 850×）

基准分两个场景。Idle：机器人在客厅中央远离家具，执行随机动作，不与物体交互；Interact：机器人靠近冰箱，沿预计算轨迹执行有代表性的交互动作。两种场景的负载结构不同：Idle 主要是渲染与碰撞查询，Interact 增加抓取、抽屉与冰箱铰链等约束求解。下表把关键值换算成实时因子，其中论文报告的 850× 实时指八卡 Idle 场景，与八卡 Interact 的 256.63 倍不是同一负载。

消融行给出优化的贡献结构。以单进程 Idle 为例：完整系统 1191 SPS，关闭渲染优化降到 781 SPS（降幅 34.42%），关闭物理优化降到 271 SPS（降幅 77.25%），全部关闭降到 242 SPS（降幅 79.68%）。单进程 Interact 的次序相反：完整 510 SPS，关闭渲染优化降到 282 SPS（降幅 44.71%），关闭物理优化降到 358 SPS（降幅 29.80%）。负载不同，瓶颈不同；任何单项优化的收益都必须绑定场景报告。

2. 并行扩展账

把单进程成绩当基线，可算出各级扩展倍数与效率。单卡 16 进程在 Idle 下为 6.873 倍（理论线性 16 倍，效率 42.96%），Interact 下为 3.255 倍（效率 20.35%）；八卡 64 进程在 Idle 下为 21.607 倍（理论 64 倍，效率 33.76%），Interact 下为 15.096 倍（效率 23.59%）。若以「八个单进程」为八卡的对照基线，八卡聚合只提升到 2.701 倍（Idle）；Interact 为 1.887 倍。

三条读数。第一，每进程分摊吞吐随并发上升而下降：Idle 从 1191 降到 402 SPS，说明单卡 GPU 时间片与 CPU 物理线程都被共享；聚合吞吐仍上升，直到核心资源饱和。第二，交互场景的并行收益更低：物理约束求解占用 CPU，单卡 16 进程只剩 20.35% 效率，瓶颈从 GPU 转向 CPU。第三，八卡不是单卡的 8 倍：2.701 倍是扣除 CPU 竞争与调度开销后的实测值。论文把每卡 8 进程定为八卡基准的默认配额，提示 8 核 16 线程是这台机器的经验折中点，核数更多的机器需要重新扫描。

3. 从步数到墙钟

训练墙钟由步数预算除以总吞吐得到，前提是仿真、推理与优化三段完全重叠。端到端训练循环的实际耗时模型为：

W ≈ N / (SPS总 · η)，其中 η ≈ t仿真 / (t仿真 + t推理 + t优化摊销) t 为单个环境步的三段平均耗时；η 为仿真段占比，也称训练有效利用率

下表用八卡 Interact 的 7699 SPS 与单进程 510 SPS 分别估算 300M 步与 2.5B 步的墙钟。300M 步是 PirlNav（Ramrakhya 等，2023）与 HM3D-OVON 开源基线（Yokoyama 等，2024）的微调量级，2.5B 步是 DD-PPO 的 PointNav 规模。

DD-PPO 的公开账目提供交叉校验：2.5B 步在 64 卡上不到 3 天完成，折算聚合吞吐约 9,645 步/秒，每卡约 150.7 步/秒；其「90% 峰值性能在 100M 步、8 卡不到 1 天」对应每卡约 144.7 步/秒。与 Habitat 2.0 纯仿真数字在同一口径下相差约 6–20 倍（每卡 150.7 步/秒，对应单实例 1400 步/秒或八卡折算后的 962–3000 步/秒），原因是口径不同：DD-PPO 的每卡有效吞吐包含策略前向、梯度更新与通信，且观测分辨率与物理负载不同。把纯仿真 SPS 直接当作训练吞吐，是复现计划里最常见的估算错误。

三段耗时的占比可以量化。设单环境步的仿真段 2.0 毫秒、推理段 0.5 毫秒、优化摊销 0.5 毫秒，则单进程模型吞吐 1 / 0.003 = 333.3 步/秒，64 进程理想聚合 21,333 步/秒；仿真段占比 η = 2.0 / 3.0 = 66.7%。若推理段升到 2.5 毫秒（大骨干或高分辨率），单进程吞吐降到 200 步/秒，η 降到 40%。先测三段耗时再定并行规模，比照搬「每卡 8 进程」更可靠。

4. 三项提速工程

Habitat 2.0 的设计原则是「速度优先于能力广度」，由此放弃非刚体动力学与触觉、音频等能力。提速由三项工程实现。

  • 惰性仿真：只更新机器人当前交互所涉及的部件。机器人被视为唯一可施加非重力作用的主体，远处物体不重算物理；底盘沿导航网格运动学移动，不模拟轮地接触；物体进入物理休眠后复用场景图变换与视锥剔除结果；相对基座受约束的部件（如柜体侧板）按静态处理。
  • 渲染与物理交错：物理在 CPU、渲染在 GPU，串行执行时总有一侧空转。Habitat 2.0 把策略输入改为上一时刻的观测，即 π(at | ot−1)，使状态转移 st+1 与观测渲染 ot 并行。若渲染与物理耗时均衡，串行耗时 2T 可压到 T，上限 2 倍收益。一步观察延迟同时带来更接近真实传感器的时序，人类视觉系统延迟约 150 毫秒，已有研究显示在仿真中引入感知延迟有利于迁移到真机。
  • 简化与复用：纹理采用 Basis 超压缩格式，显存占用降低 4 至 6 倍；为物体生成凸分解碰撞代理，渲染资产与碰撞资产分离；资产预取并缓存，缩短场景切换的重置时间。这三项让单卡能容纳更多并发实例。

与同类系统的量级对照可以校准期望。论文汇总表中，Habitat 1.0 为 3,000 SPS，AI2-THOR 为 30 至 60 SPS，ManipulaTHOR 为 30 至 40 SPS，ThreeDWorld 为 5 至 168 SPS，SAPIEN 为 200 至 400 SPS，RLBench 为 1 至 60 SPS，iGibson 为 100 SPS，Habitat 2.0 单实例表值为 1,400 SPS。iGibson 与 Habitat 2.0 同用 Bullet 物理引擎，前者经 PyBullet 封装、后者用 C++ 低层集成：单进程 Idle 下，Habitat 2.0 关闭全部优化为 242 SPS（iGibson 的 2.42 倍），开启优化为 1191 SPS（11.91 倍）。论文把这一量级概括为约 100 倍提速，对应实验周期从 6 个月压到 2 天以内（6 个月按 180 天折算，除以 100 得 1.8 天）。对照表注明各系统硬件与资产不同，只能读量级，不能读倍数排序。

5. 适用边界

第一，场景与传感器绑定。上述数字来自 ReplicaCAD 公寓与 Fetch 双 128×128 相机；换成 HM3D 全屋扫描、640×480 观测或多相机配置，吞吐会显著变化，必须重测。第二，能力边界。Habitat 2.0 不支持可形变体、切割焊接等状态变换与音频触觉，涉及其中的任务不在该口径内。第三，实时因子的相对性。850× 指八卡 Idle；同一系统的八卡 Interact 只有 256.63×，单进程 Interact 只有 17×。第四，并行效率随硬件变化。8 核 16 线程的配额来自基准机，核心更多或更少的机器应重新扫描每卡进程数。第五，论文版本差异。本讲数字取 v2（2022 年 7 月修订版）；引用时标明版本与出处，保证数字可回溯。

瓶颈诊断流程

采集三段耗时后按占比决策。设 GPU 利用率、CPU 利用率与步进耗时同时记录：仿真段占比超过 70% 且 GPU 未饱和时，优先增加环境进程数与每卡进程数；仿真段占比高且 CPU 饱和时，检查物理负载、减少交互物体或改用更简碰撞代理；推理段占比超过 40% 时，先缩小视觉骨干或提高批大小，再考虑加卡；优化摊销占比高时，减少每轮 PPO 更新次数或降低更新频率。扩展扫描从每卡 4 进程起，到 16 进程止；若 16 进程相对 8 进程的聚合提升低于 10%，把 8 进程定为默认。

关键代码与解读

三段代码分别覆盖换算、测量与诊断。全部片段用本讲的公开数字验证，输出与正文表格对应。

片段 1：墙钟与并行效率核算

def wallclock(steps, sps, utilization=1.0):
    """由步数预算与总吞吐估算墙钟小时数；utilization 为仿真段占比。"""
    effective = sps * utilization                  # 有效训练吞吐
    return steps / effective / 3600.0

def efficiency(agg, single, scale):
    """聚合吞吐相对单实例线性扩展的效率。"""
    return agg / (single * scale)

print("300M @ 7699 SPS:", round(wallclock(300_000_000, 7699), 2), "h")
print("2.5B @ 7699 SPS:", round(wallclock(2_500_000_000, 7699) / 24, 2), "天")
print("idle 八卡效率:", round(efficiency(25734, 1191, 64), 4))
print("interact 八卡效率:", round(efficiency(7699, 510, 64), 4))
# 300M @ 7699 SPS: 10.82 h
# 2.5B @ 7699 SPS: 3.76 天
# idle 八卡效率: 0.3376
# interact 八卡效率: 0.2359

解读：（1）第一式把「纯仿真吞吐」与「训练有效吞吐」分开，utilization 缺失会把墙钟低估约 1.5 倍；（2）效率函数以单实例成绩为基线，scale 取理论并发数，33.76% 与 23.59% 直接暴露资源竞争；（3）输出保留四位小数，避免在报告里出现「差不多三成」这类无法追溯的表述；（4）实际规划时把结果向上取整并预留 20% 重跑余量，因为中断恢复与评测也占用同一批卡。

片段 2：Idle / Interact 双场景 SPS 测量

import statistics, time

def measure_sps(step_fn, interactions=False, warmup=20, runs=10, steps_per_run=200):
    """按 10 次运行报均值与 95% 置信区间；warmup 排除首轮冷启动。"""
    for _ in range(warmup):
        step_fn(interactions)                      # 预热资产与着色器
    samples = []
    for _ in range(runs):
        start = time.perf_counter()
        for _ in range(steps_per_run):
            step_fn(interactions)
        elapsed = time.perf_counter() - start
        samples.append(steps_per_run / elapsed)    # 单次运行 SPS
    mean = statistics.mean(samples)
    sem = statistics.stdev(samples) / len(samples) ** 0.5
    ci95 = 1.96 * sem                              # 正态近似，样本量 10
    return mean, ci95

# 用法：scene.reset(); measure_sps(lambda i: scene.step(random_action(), interact=i))
# 输出示例（论文单进程）：Idle 1191 ± 36；Interact 510 ± 6

解读：（1）预热不可省，首轮加载纹理与编译着色器会把均值拉低一个数量级；（2）先跑 warmup 再计时，且每次运行独立计时后取统计量，避免把一次长跑切成十段造成伪独立性；（3）95% 置信区间用 1.96 倍标准误，样本量增至 30 时改查 t 分布表；（4）Interact 场景必须注入代表性动作序列，随机动作会退化成 Idle 负载；（5）报告时同时给出场景、进程数、卡数与分辨率，否则数字无法复现。

片段 3：三段耗时诊断

def diagnose(t_sim_ms, t_infer_ms, t_sgd_ms, n_proc):
    """输入单环境步的三段平均耗时（毫秒），输出吞吐与瓶颈建议。"""
    t_total = t_sim_ms + t_infer_ms + t_sgd_ms
    per_proc = 1000.0 / t_total                    # 单进程步/秒
    agg = per_proc * n_proc                        # 理想聚合，未计竞争
    share = {"仿真": t_sim_ms / t_total,
             "推理": t_infer_ms / t_total,
             "优化": t_sgd_ms / t_total}
    bottleneck = max(share, key=share.get)
    advice = {"仿真": "增加环境进程或简物理负载",
              "推理": "缩小骨干或增大推理批",
              "优化": "减少每轮 PPO 更新次数"}[bottleneck]
    return per_proc, agg, share, advice

print(diagnose(2.0, 0.5, 0.5, 64))
# (333.33, 21333.3, {'仿真': 0.667, '推理': 0.167, '优化': 0.167}, '增加环境进程或简物理负载')
print(diagnose(2.0, 2.5, 0.5, 64))
# (200.0, 12800.0, {'仿真': 0.4, '推理': 0.5, '优化': 0.1}, '缩小骨干或增大推理批')

解读：（1）三段耗时来自实际剖析数据，避免用估计值，仿真段用 SPS 倒数、推理段用前向计时、优化段用更新总时长除以两次更新之间的交互步数；（2）理想聚合未计资源竞争，落地时乘上片段 1 的扩展效率；（3）两组示例展示同一硬件改变骨干规模后瓶颈转移，说明诊断必须在目标配置上做；（4）瓶颈建议只给方向，具体参数由扫描实验决定，记录扫描表以便复现。

常见误区

  • 用 Idle 数字申报训练吞吐：症状是复现者按 1191 SPS 排计划，实际交互训练只有 510 SPS，工期翻倍。根因是 Idle 不含抓取与铰链约束求解。修复：训练计划一律采用 Interact 口径；两个场景并列报告。
  • 把纯仿真 SPS 当端到端吞吐：症状是估算的训练时间比实测短一个数量级。根因是遗漏策略推理与梯度更新两段耗时。修复：用片段 3 测三段占比，按有效吞吐排期；参照 DD-PPO 每卡约 150 步/秒的有效量级做校准。
  • 进程数盲目加倍：症状是单卡从 8 进程加到 16 进程，聚合吞吐只涨不到一成，节点负载还更高。根因是 GPU 与 CPU 已饱和，资源竞争吞掉收益。修复：从每卡 4 进程起做 1、4、8、16 四点的扫描，以聚合吞吐的拐点定默认值。
  • 测量无置信区间或忽略预热：症状是同一配置两次测量差 20% 以上，无法判断优化是否有效。根因是首轮加载与单次采样。修复：预热后独立运行 10 次，报告均值与 95% 置信区间；置信区间重叠时不下结论。
  • 跨平台与跨版本横比：症状是用 1,400 SPS 对照 iGibson 的 100 SPS，得出 14 倍结论。根因是硬件、资材与能力集合不同，且论文单实例表值与基准表值口径有别。修复：跨系统只读量级并注明对照表性质；引用 Habitat 2.0 数字时标 v2 版本与场景。
  • 实时因子与仿真步定义脱节：症状是把 850× 直接套到交互场景或 60 Hz 控制任务上，得出错误预算。根因是 30 SPS 对应 1 倍实时的前提为 1/30 秒仿真步。修复：先确认步定义与传感器频率，再换算 RTF；换控制频率后重新计算。

小结

  • SPS 口径：1 步 = 1 渲染 + 4 物理子步（1/30 秒仿真），实时因子 RTF = SPS / 30；Habitat 2.0 v2 单进程 Idle 1191、Interact 510，八卡 25,734 与 7,699，分别对应 857.80 与 256.63 倍实时。
  • 扩展账：16 进程单卡相对单进程 6.873 倍（Idle），八卡 64 进程 21.607 倍，线性效率 33.76%；Interact 效率 20.35% 与 23.59%，瓶颈在 CPU 物理。
  • 墙钟账：W = N / (SPS总 · η)；300M 步在八卡 Interact 下 10.82 小时、单进程 163.4 小时；2.5B 步在八卡 Interact 下 3.76 天。DD-PPO 的有效吞吐每卡约 150 步/秒，与纯仿真数字不可直接互换。
  • 三项提速工程：惰性仿真（局部物理、导航网格底盘、休眠复用）、渲染物理交错（策略延迟一步，上限 2 倍）、简化复用（纹理压缩 4 至 6 倍、凸分解、资产缓存）；单进程 Idle 从无优化 242 提到 1191 SPS。
  • 工程纪律：Idle 与 Interact 双场景、10 次运行与 95% 置信区间、固定 CPU 配额与资产；先测三段耗时，再定进程与卡数；跨系统只读量级并标版本。
