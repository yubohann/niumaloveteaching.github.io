第五篇 · 真机、Sim2Real 与系统集成

第 097 讲｜工程栈全景

本讲把第五篇用过的组件排成一张分层工程栈，标出每层的接口、维护状态与替换成本。仿真侧以 Habitat-Lab 为基座（habitat-lab README，2026-10-01 抓取；v0.3.4 之后官方停止积极维护），桥接侧用 ROS-X-Habitat（Chen 等 2022，CRV，arXiv:2109.07703）连通 Habitat Sim v2 与 ROS 生态，真机侧以 spot-sim2real（GitHub，同日抓取）组织 ROS 1 进程、技能与微服务，感知插件用 SAM 2（Ravi 等 2024，arXiv:2408.00714v2）做视频跟踪、用 FoundationPose（Wen 等 2024，CVPR Highlight）做 6D 位姿。实算帧周期与预算：9.33 Hz 对应 107.2 ms，预热期 11.20 Hz 对应 89.3 ms，网络往返均值 8.12 ms 占帧周期 7.6%，启动健康窗 70 秒，日志 9 个顶层键。最后给出移植清单与 ROS 1 到 ROS 2 的映射，衔接第 04 门 ROS 2 系统集成课。

  • 主题：工程栈 / 仿真桥接 / 进程架构 / 感知微服务 / 版本维护 / 接口契约
  • 关键公式：Tframe = 1 / fsensor；fservice ≤ min(fsource, 1 / Tservice)；往返占比 = RTT / Tframe
  • 预计学时：90 分钟
  • 前置章节：第 096 讲（真机评测方法学）

学习目标

  • 复述：画出六层工程栈，说清每层的组件、接口与在第 091 至 096 讲中的使用位置。
  • 会算：由传感器频率换算帧周期与微服务预算，计算网络往返与轮询延迟在预算中的占比。
  • 会设计：为一条新项目给出栈选型、接口契约、健康检查与降级策略，并写移植清单。
  • 会判断：依据维护状态与版本事实做依赖决策，识别 ROS 1 生命周期、坐标约定与预热假象三类风险。
  • 会迁移：把 ROS 1 的参数式技能调用与话题契约映射到第 04 门课的 ROS 2 概念。

背景与动机

第五篇讲到收尾，组件已经分散出现：第 091 讲拆过 spot-sim2real 的进程与技能，第 092 讲用 ROS 参数调用技能，第 093 讲在 Spot 上部署 VLFM，第 094 讲处理足式平台，第 095 讲部署两级 VLA。分散出现带来一个副作用：读者知道每个组件做什么，却不容易回答「换仿真器要动哪一层」「上游停止维护后哪一层最先坏」「新机器人要改哪些接口」。本讲补这张总图。

总图按依赖方向分六层：资产与数据、仿真引擎、仿真到机器人中间件的桥、机器人中间件、感知与技能服务、策略与任务逻辑。每层只暴露有限接口，替换成本由接口的耦合度决定。Habitat-Lab 与 ROS-X-Habitat 属于仿真侧，spot-sim2real 属于真机侧，SAM 2 与 FoundationPose 是挂在真机侧话题与进程上的感知服务。本讲同时为第 098 讲的方法路线图提供工程约束输入，为第 099 讲的复现清单提供版本与预算依据。

核心原理

1. 六层栈与接口契约

把课程中出现过的组件按依赖排成六层，每层的输入输出与替换成本如下表。判据是接口宽度：接口越窄、越基于通用标准（文件格式、ROS 话题、Python API），替换成本越低。

层组件示例层间接口替换成本
资产与数据HM3D、ReplicaCAD、HSSD、扫描资产场景与 episode 文件中（资产格式稳定，制作成本高）
仿真引擎Habitat-Sim、Habitat-Lab、Isaac Lab、GazeboPython API / gym 接口高（任务与传感器配置深度耦合）
桥接层ROS-X-Habitat、rosbridge 式进程ROS 话题与服务中（协议标准，语义需逐项核对）
机器人中间件spot-sim2real 的 ROS 1 节点组话题、参数、技能入口高（与本体 SDK 绑定）
感知与技能服务SAM 2 跟踪、FoundationPose 位姿、技能执行器ROS 话题加进程间套接字低至中（进程隔离，契约清晰）
策略与任务逻辑VLFM、两级 VLA、评测脚本航点、语言动作、停止信号中（论文代码版本碎片化）

替换成本的规律与第 095 讲的教训一致：契约越接近自然语言或通用标准，耦合越松；契约越依赖具体 SDK 的调用序列与坐标约定，耦合越紧。本讲后文按层展开仿真基座、桥接、真机进程与微服务四块，并给出时序预算与版本决策。

2. 仿真基座：Habitat-Lab 的能力与边界

Habitat-Lab 的定位是模块化高层库，官方 README 列出四组能力：可配置的单机与多机任务定义（导航、重排、指令跟随、问答、跟人）；可配置的本体与传感器；训练与评测工具，覆盖模仿学习、强化学习与无学习的 SensePlanAct 流水线；人在回路交互。仿真核心是 Habitat-Sim，物理能力由编译选项开启。安装路径为三件套：conda 创建 Python 3.9 以上、CMake 3.14 以上的环境；从 aihabitat 频道安装 habitat-sim（含 Bullet 物理用 withbullet 变体）；克隆仓库并分别可编辑安装 habitat-lab 与 habitat-baselines。示例脚本用 gym 接口创建任务，也可以用配置对象覆盖参数，官方配置键文档给出覆盖路径。

维护状态必须写进版本决策。README 顶部警告：超过 v0.3.4 之后，该项目不再由原团队做官方积极开发与维护。抓取时仓库有 3.1k 星标、691 个分支副本；Docker 镜像大约每年为挑战赛更新一次，README 给出的测试镜像示例标签为 2022 系列。调试提示值得记录：向量化环境为了速度牺牲报错信息，排错时把 HABITAT_ENV_DEBUG 置 1 可切换到信息更全但更慢的线程化实现。工程结论是三条：把 Habitat 版本钉死并保留可编译的容器或 conda 环境；以挑战赛镜像做基准复现，不用它当通用依赖；对停更层预留迁移预算，迁移目标可以是 Isaac Lab 或自维护分支。

3. 桥接层：ROS-X-Habitat 的职责

ROS-X-Habitat（Chen、Yang、Mitchell，CRV 2022，arXiv:2109.07703）的定位是把 Habitat 平台与 ROS 资源互相打通：对外提供标准通信协议，让学习型智能体与仿真器交换数据；对内启用物理与照片级渲染，服务视觉智能体的训练与测试。论文摘要给出三条可检验的主张：对 RGBD 导航智能体的导航性能与仿真速度影响很小；一组标准 ROS 建图、规划与导航工具可以直接运行在 Habitat Sim v2 上；Habitat 智能体可以运行在标准 ROS 仿真器 Gazebo 中。三条主张都绑定具体的工作负载与当年的硬件环境。

维护方面，Habitat-Lab 的 README 明确 ROS-X-Habitat 由 UBC 实验室开发维护，尚未获得 Habitat 团队官方支持。引入桥接层的判据是两个问题：项目是否已有 ROS 代码资产需要复用；团队是否接受在 ROS 1 语义下工作。若两者都成立，桥接的收益是把仿真与真机共用一套话题契约；若不成立，直接使用 Habitat 的 Python API 更省事。重要纪律：论文的「影响很小」是相对结论，复现时要在自己的观察尺寸、控制频率与场景规模上重测，不能直接引用为性能保证。

4. 真机层：spot-sim2real 的进程架构

真机侧组件在第 091 讲已逐项拆过，这里关注进程与接口的全局安排。仓库把功能分成四块：底层包装器负责与本体控制接口通信；实验包承载技能、配置与主流程；感知与工具目录收集感知组件；ROS 通信目录对接外部进程。运行前先选择连接模式：以太网速度最好但布线繁琐；接入点模式由机器人发射网络，适合远距离遥控；客户端模式接入外部路由器，仓库推荐的日常选择。机器人地址写入环境变量，先做连通性检查。

启动脚本一次拉起 4 个终端复用会话：ROS 主节点、图像发布、本体感觉、语音合成。README 要求 4 个会话在启动后 70 秒内全部存活，任何会话提前退出都判定启动失败，并建议重跑 2 至 3 次以排除主节点慢启动。技能调用采用非阻塞写入：调用方把「时间戳、技能名、参数」写入 ROS 参数，常驻技能执行器以 10 Hz 轮询，识别到新时间戳后执行对应技能；同一时间只允许一个技能在跑。每次运行前必须复位到 home 位姿，原因是里程计会随行走漂移，而路径点坐标以 home 为参考系。急停节点需要常驻，操作员用键盘即可终止。这套安排的工程含义是：真机层把「调试接口」与「安全接口」都做成独立进程，任何一个上层策略崩溃都不关闭急停通道。

5. 感知微服务：SAM 2 与 FoundationPose

SAM 2（Ravi 等 2024，arXiv:2408.00714v2）在仓库里承担开放集分割与视频跟踪，接入方式有两个细节：安装到独立的 conda 环境，原因是主环境 Python 版本较低；对上游代码做小改造，使其直接接收原始 RGB 图像，不再要求视频文件路径。跟踪服务以独立进程运行，是否启用由 ROS 参数控制，技能侧可以在打开与关闭动作上复用同一跟踪器。论文给出的上游能力数字是：图像分割比第一代 SAM 快 6 倍，视频分割所需交互次数少 3 倍。

FoundationPose（Wen 等 2024，CVPR Highlight）承担 6D 位姿估计与跟踪，在仓库中的集成形态是第三方子模块加进程间套接字服务：位姿模型作为微服务运行，通过消息套接字通信，启动脚本一并拉起。集成范围当前只覆盖三类对象（瓶子、企鹅玩偶、纸杯），新对象需要按仓库说明用 360 度视频重建网格。抓取技能可开启位姿估计与位姿校正两个开关：位姿估计告诉抓取接口采用自上而下或侧向接近，校正会先手工调整物体姿态再放置；朝向求解器能让物体面向相机，但会在放置前多消耗一次抓取尝试，因此默认关闭。两个服务的共同价值是故障隔离与依赖隔离，共同代价是序列化开销、额外进程与版本漂移，需要健康检查与降级策略配套。

6. 时序、预算与健壮性实算

把可观测的读数换算成预算。图像可视化脚本在 README 示例中打印各话题频率，静态阶段读数包括原始头部深度 9.33 Hz、手部彩色 9.33 Hz、掩码检测可视化 11.20 Hz；检测器完成初始化后读数转为动态，示例中降到 4.11 至 6.87 Hz。按周期换算：9.33 Hz 对应 107.2 ms，11.20 Hz 对应 89.3 ms，6.87 Hz 对应 145.6 ms，4.11 Hz 对应 243.3 ms。频率从 9.33 降到 4.11，帧率下降 55.9%；预热期的 11.20 Hz 恒定读数比示例动态阶段 4.11 Hz 高出 172.5%（后者相对前者低 63.3%），这个「过快且恒定」正是 README 用来判断检测器未就绪的信号。

环节示例读数相对 107.2 ms 帧周期风险与处置
源帧周期107.2 ms（9.33 Hz）100%网络模式与负载变化会改变实际频率
网络往返均值 8.12 ms（8.87 / 7.36 两次）7.6%（6.9% 至 8.3%）无线抖动；关键链路优先有线
技能轮询陈旧10 Hz 轮询，最坏 100 ms最多 93%轮询频率与技能粒度匹配；参数写入带时间戳
模型预热恒定 11.20 Hz 假象不适用预热门控；恒定输出计入健康检查
启动健康窗70 秒，4 个会话约 653 个帧周期任一会话退出即重跑，建议 2 至 3 次

微服务的预算公式是 fservice ≤ min(fsource, 1 / Tservice)，其中 Tservice 为单帧处理时长，需要实测填入。以 107.2 ms 帧周期为例，若跟踪服务单帧耗时 40 ms，则上限为 25 Hz，源帧率 9.33 Hz 是瓶颈；若耗时 150 ms，则服务只能以 6.7 Hz 输出，低于源帧率，UI 与技能必须容忍跳帧。技能参数轮询的平均等待为半个周期即 50 ms，最坏 100 ms；调用方在 100 ms 内看到的是旧技能状态，因此技能粒度过细会把延迟放大成抖动。日志字段同样进入契约：顶层 9 个键覆盖时间戳、相机数据（含内参 3×3 与外参 4×4）、视觉到基座变换 4×4、基座位姿、6 个机械臂关节、夹持状态与力；这套字段足以离线回放与失败复盘。

7. ROS 1 到 ROS 2 的映射

spot-sim2real 建立在 ROS 1 之上，使用主节点、rospy 与参数服务器；ROS 1 的 Noetic 版本已在 2025 年 5 月结束官方支持。第 04 门课讲授的 ROS 2 在概念上有一一对应，迁移时可以按表核对，但 QoS 与时间语义需要重新决策。

ROS 1 概念ROS 2 对应迁移注意事项
主节点 roscore分布式发现（DDS）无中心节点；网络配置与域号显式设置
rospy / roscpprclpy / rclcpp节点生命周期与执行器模型不同
参数服务器节点参数（可声明、可动态更新）非阻塞技能调用改为服务或动作接口更自然
话题 / 服务话题 / 服务 / 动作QoS 可靠性、历史深度、截止时间需要按链路配置
TFtf2时间戳与静态变换的发布方式调整
launch 文件launch.py进程管理与参数注入写法替换

迁移路线有三条。容器冻结：把整套 ROS 1 环境打进镜像，短期最省事，长期依赖冻结。桥接共存：用 ros1_bridge 或仓库自带的 TCP 桥把 ROS 1 侧包装成可见接口，新代码用 ROS 2 编写，适合渐进迁移。整体移植：把技能执行器与急停等关键节点改写成 rclpy，接口与验收测试同步重写，成本最高但债务最少。判据是项目寿命与协作者规模：教学与短期复现选容器冻结，多人长期项目选桥接共存并制定节点移植顺序，急停与安全节点应最先迁移。

8. 版本与维护矩阵

抓取时的维护快照：Habitat-Lab 超过 v0.3.4 无官方积极维护，星标 3.1k、分支副本 691；ROS-X-Habitat 由 UBC 实验室维护，非官方支持，论文版本为 2022 年；spot-sim2real 有 146 次提交、103 个星标、7 个分支副本、30 个未关闭议题与 47 个未合并拉取请求，处于活跃状态；SAM 2 与 FoundationPose 的上游项目持续更新。决策纪律是把「停更层」与「活跃层」分开治理：停更层锁版本、留镜像；活跃层锁提交号、留契约测试；所有层记录抓取日期，因为本讲与第 091 讲的全部快照只代表抓取时点。

关键代码与解读

三段代码分别覆盖微服务看门狗、坐标链校验与 ROS 1 技能调用的接口骨架。第三段保留 ROS 1 写法并注明 ROS 2 对应表达。

片段 1：微服务看门狗与降级

class TrackingWatchdog:
    """跟踪服务看门狗：时间戳停滞或输出长期恒定都判定异常并降级。"""

    def __init__(self, repeat_limit=10):
        self.repeat_limit = repeat_limit
        self.last_stamp = None
        self.last_value = None
        self.repeat = 0

    def on_message(self, stamp, value, control):
        if self.last_stamp is not None and stamp <= self.last_stamp:
            return "stale"                    # 时间戳不前进，消息无新信息
        self.last_stamp = stamp
        if value == self.last_value:
            self.repeat += 1                  # 恒定输出常见于模型尚未就绪
        else:
            self.repeat = 0
            self.last_value = value
        if self.repeat >= self.repeat_limit:
            control.set_param("enable_tracking", False)
            return "degraded"                 # 关闭跟踪技能，主流程继续
        return "ok"

解读：（1）只看「有消息」不足以保证服务健康，README 示例里检测器未就绪时话题频率会恒定在 11.20 Hz，比正常动态阶段还高；双重判据把这种假象识别为异常。（2）降级动作是关闭跟踪参数并返回状态字符串，调用方按字符串决定继续或暂停，故障不被静默吞掉。（3）重复阈值取 10 是教学默认，应按服务帧率折算成时间窗，例如 10 Hz 服务对应 1 秒。

片段 2：坐标链与时间戳校验

import numpy as np

def check_chain(base_T_camera, vision_T_base, stamp_age, tol=1e-3):
    """校验外参与位姿链：旋转正交、行列式为 1、变换可合成、时间戳新鲜。"""
    R = base_T_camera[:3, :3]
    ortho_err = float(np.abs(R @ R.T - np.eye(3)).max())
    determinant = float(np.linalg.det(R))
    assert ortho_err < tol, "rotation not orthonormal: %.5f" % ortho_err
    assert abs(determinant - 1.0) < tol, "determinant off: %.5f" % determinant
    vision_T_camera = vision_T_base @ base_T_camera      # 相机到视觉系
    assert vision_T_camera.shape == (4, 4)
    if stamp_age > 0.1:
        return "stale pose: %.3f s" % stamp_age
    return "ok"

解读：（1）日志里的 base_T_camera 与 vision_T_base 都是 4×4 齐次变换，误把旋转矩阵当变换矩阵或转置用错是常见错误；正交性与行列式检查能在启动阶段暴露大部分转置与缩放问题。（2）合成顺序按符号阅读，右乘表示在相机系内施加变换；实现时用最小样例点验证方向，不凭记忆写乘法顺序。（3）时间戳年龄超过 0.1 秒返回陈旧状态，与 107.2 ms 的帧周期同量级，位姿过期时位置控制必须降速或暂停。

片段 3：非阻塞技能调用（ROS 1 写法与 ROS 2 对照）

import time
import rospy

def request_skill(skill, target, timeout=30.0, poll_hz=10.0):
    """非阻塞技能调用：参数写入携带时间戳，轮询等待状态，超时返回失败。"""
    payload = "%f,%s,%s" % (time.time(), skill, target)
    rospy.set_param("skill_name_input", payload)
    deadline = time.time() + timeout
    while time.time() < deadline:
        state = rospy.get_param("skill_state", "idle")
        if state == "done":
            return True
        if state == "failed":
            return False
        rospy.sleep(1.0 / poll_hz)        # 10 Hz 轮询，最坏陈旧 100 ms
    rospy.logwarn("skill %s timeout after %.1f s" % (skill, timeout))
    return False
    # ROS 2 对照：节点声明参数或改服务、动作接口；rclpy.spin 配执行器

解读：（1）参数值内嵌写入时刻，执行器只处理新时间戳，重复写入旧值不会重复触发技能，这是第 091 讲非阻塞设计的关键防重复机制。（2）轮询周期 100 ms 决定状态可见延迟，技能粒度小于该周期的调用会退化为抖动源，必要时改事件回调或动作接口。（3）超时后返回失败，不进入无限等待，调用方据此进入重试或降级；迁移到 ROS 2 时，参数轮询可改为服务调用或动作接口，并且要显式配置 QoS。

常见坑

  • 忽略 ROS 1 生命周期：症状是某天基础镜像源或 Python 依赖消失，构建失败。根因是 Noetic 已于 2025 年 5 月结束官方支持，生态补丁逐步停止。修复：容器冻结依赖；制定移植顺序；安全节点最先迁到 ROS 2。
  • 把所有依赖装进一个环境：症状是安装跟踪服务后主环境 Python 版本被改坏，技能节点起不来。根因是不同项目对解释器与库版本要求冲突。修复：微服务独立环境，跨进程只传数据；为每个服务写启动与健康检查脚本。
  • 坐标变换约定混乱：症状是目标位置系统性偏一个轴向或尺度。根因是 4×4 变换的转置、旋转正交性与合成顺序没有校验，或相机光学系与基座系方向约定不一致。修复：启动时跑正交性与行列式检查；用已知方向的标定物做投影复核。
  • 预热期恒定输出被当作健康：症状是检测器未就绪时可视化频率异常高，技能误触发。根因是恒定输出缺少变化信息，监控只看消息到达。修复：看门狗同时检测时间戳前进与输出变化；技能启动前加预热门控。
  • 外推桥接层的开销结论：症状是照搬论文的「影响很小」后实测丢帧。根因是原结论绑定 2022 年的工作负载与硬件配置。修复：在自己的观察尺寸、频率与场景规模上重测桥接开销；把帧率与延迟写入验收表。

小结

  • 六层栈：资产、仿真引擎、桥接、机器人中间件、感知与技能服务、策略与任务逻辑；接口越接近通用标准，替换成本越低。
  • 仿真侧：Habitat-Lab 提供任务、本体、训练与人在回路能力，v0.3.4 之后官方停止积极维护；ROS-X-Habitat 桥接 ROS 与仿真，由 UBC 维护且非官方支持，其开销结论需自测。
  • 真机侧：spot-sim2real 用 4 个终端会话、70 秒健康窗、参数式非阻塞技能与常驻急停组织运行；SAM 2 与 FoundationPose 以独立环境或套接字微服务接入，前者跟踪、后者 6D 位姿。
  • 时序实测：9.33 Hz 对应 107.2 ms 帧周期，网络往返均值 8.12 ms 占 7.6%，10 Hz 轮询最坏陈旧 100 ms；恒定频率输出是预热假象，看门狗要同时检查时间戳与输出变化。
  • 版本纪律：停更层锁 tag 留镜像，活跃层锁提交号留契约测试；ROS 1 已在 2025 年 5 月结束支持，迁移按容器冻结、桥接共存、整体移植三条路线择一。
