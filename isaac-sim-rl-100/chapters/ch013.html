第一篇 · 仿真环境与训练框架

第 013 章：使用OmniGraph创建事件驱动

换一种组织逻辑的方式：把"每个物理步做什么"从 Python 循环搬进场景内的节点图。理解触发源、数据流与执行规则，并想清楚什么时候图更合适、什么时候 Python 循环不可替代。

  • 主题：仿真环境 / 事件驱动与图式计算
  • 相关组件：Isaac Sim（OmniGraph / Action Graph）
  • 预计学时：50 分钟
  • 前置章节：第 012 章

学习目标

  • 理解 OmniGraph 的三要素：节点（计算单元）、端口连线（数据流）与触发源（何时执行）。
  • 说清常见的触发源区别：OnPlaybackTick、OnPhysicsStep、OnImpulseEvent 各自的执行时机与频率。
  • 会用代码构建一个最小 Action Graph：物理步触发 → 自定义 Python 节点 → 输出/记录。
  • 理解"图与 Python 循环的协作与分工"：哪些逻辑适合放进图，哪些必须留在环境代码里。
  • 会排查图的常见问题：不执行、执行两次、数据错误、静默失败。

背景与动机

到目前为止，我们的所有逻辑都写在 Python 里：world.step() 一步、读传感器、算奖励。这条主线在 RL 里不会变，训练需要同步、可控、可复现的循环。但 Isaac Sim 的内部世界并不只有这条主线：很多系统（相机管线、ROS 桥、UI 面板、遥操作设备）需要在"合适的时刻"被驱动；把它们塞进某个 while 循环"抢着"驱动会打乱时序。OmniGraph 就是 Isaac Sim 提供的"挂在应用更新循环上的声明式逻辑"。

为什么 RL 学习者也要掌握它？读懂官方示例（大量教程用 Action Graph 组装逻辑）、搭建传感器数据管线、用事件驱动处理标定/监控/触发式重置这类"杂务"。

核心原理

1. 节点、端口与数据流

OmniGraph 的计算模型是一张有向图：节点（node）是带输入/输出端口（port）的小计算单元（例如"读取仿真时间"、"转换四元数"、"写一个变量"）；连线（connection）把上游的输出接到下游的输入，构成数据流。每个端口有明确的数据类型（浮点、整数、数组、token 等），类型不匹配的连线在构建时就会被拒绝，这是图式编程相对字符串脚本的一个优势：错误尽量在连线时暴露，避免拖到运行时才报错。

与"函数调用"的心智对比：函数是"我要它算，它就立刻算"（命令式）；图是"连好线之后，让调度器在合适的时刻推着数据走"（声明式）。你在 Python 里删掉循环，逻辑也不会消失，它活在场景文件里，随应用更新循环持续运行。

2. 触发源：图何时执行

纯数据流图还需要一个"起点"：谁先动起来？这就是触发节点的作用。常见的有：

触发节点执行时机频率量级典型用途
OnPlaybackTick每次应用更新/渲染帧与渲染帧率一致（如 60 fps）UI、可视化、与渲染相关的逻辑
OnPhysicsStep每个物理步60 Hz（本课程默认）需要与物理严格同步的逻辑
OnImpulseEvent被手动/其他节点触发时按需一次性动作：重置、标定、触发采样
OnStageEventUSD 场景变化时事件驱动资产热加载、场景切换响应

选错触发源是图逻辑出错的第一大来源。一个典型事故：用 OnPlaybackTick 做"每物理步积分一次"的计数，渲染帧率会随性能和设置波动（训练时 render=False 甚至几乎不渲染），计数与物理时间脱钩。记住一个原则：与物理相关的量用 OnPhysicsStep；与显示相关的量用 OnPlaybackTick；一次性动作挂事件。

3. 执行规则：always、on-demand 与"只算变化"

每个节点还有一个"何时重新求值"的设置：每帧必然、被请求时才求值（pull 模式）、输入变化时求值。组合决定性能：挂在 OnPhysicsStep 上每步运行的脚本节点会成为仿真瓶颈，而"变化时才求值"的节点稳态几乎免费。图越大，执行规则越比节点数量重要。

4. 与 RL 环境的边界

图不是万能的：训练需要"给动作 → 步进 → 读观测 → 算奖励"的严格顺序与数值可复现，而图里的时序由调度器决定、还可能随帧率变化。合理的分工是：

  • 留在 Python：控制、观测、奖励、重置、训练循环，一切影响学习信号的东西。
  • 放进图：数据搬运与格式转换（传感器管线）、与 Kit 应用生命周期绑定的逻辑、UI 与监控、事件驱动的外部交互（收到消息就做某事）。

5. 图的执行开销：每步成本与预算占比

图挂在应用更新循环上，等于把一部分计算固定摊进每个物理步。设触发频率 f、单次链路的墙钟耗时 Tgraph、物理步周期 Tstep：

开销占比 = f · Tgraph / Tstep f = 60 Hz、T_step ≈ 16.7 ms；T_graph = 0.2 ms 时占比约 1.2%，T_graph = 2 ms 时占比约 12%

数值对照：轻量搬运节点（读一个值、写一个变量）的单次开销在几十微秒量级，几十个节点合计也仅占每步预算的百分之一二；一个每步执行的脚本节点若做矩阵运算或碰撞查询，单次耗时容易达到毫秒级，占比跳到 10% 以上，RTF 随之下降。设计规则：把"每步执行"留给搬运与轻量判断，单次耗时按 0.1 ms 量级规划；重计算放到 Python 侧按需调用。

6. 三种触发源在 300 步对账实验中的期望计数

把片段 2 的对账实验扩展成对照表，触发源选对与选错的表现一目了然：

触发源render=True 跑 300 步render=False 跑 300 步结论
OnPhysicsStep300300与物理步严格对齐，物理逻辑的唯一正确选择
OnPlaybackTick约 300（渲染帧与物理步 1:1 时）可能远小于 300 或停止推进计数随渲染配置漂移，不能承载物理逻辑
OnImpulseEvent等于 Python 侧触发次数等于 Python 侧触发次数由调用方决定，适合一次性动作

使用方法是"先跑 300 步，再对照期望值"。计数不符时按两个方向排查：小于说明触发被节流或图未激活；大于说明同一信号连了多条路径或存在重复触发。

7. 活动量与调度：两种求值策略

图上的节点分为"持续活动"与"按需"两类，调度器决定何时求值。常见配置的名称与行为随版本有差异，概念上分为两种：按执行流调度（沿连线顺序执行，与触发源配合，行为确定）与按数据推送（输入变化才求值，稳态开销接近零）。

两者对性能的影响可以用第 5 节的公式折算：一条"每步执行"的链路在 60 Hz 下持续消耗预算，推送模式在输入不变时几乎不产生求值成本。工程建议：与物理同步的链路用执行流调度保证时序；纯数据转换链路用按需求值换取空闲。切换调度方式会改变数值出现的时机，切换后重新跑一次 300 步对账实验，确认计数与阶段都没有变。建图评审时给每个"每步执行"的节点标注单次耗时量级与预算占比；新增节点先测耗时，再接业务逻辑，这条顺序能拦住大多数吞吐问题。

8. 图预算与触发延迟的核算

先用一组量级参考建立"节点成本表"：搬运与算术类节点单次约 20–50 µs；数据类型转换节点约 30–100 µs；只做记录或判断的脚本节点约 0.1 ms；含矩阵运算或碰撞查询的脚本节点 1–5 ms。物理步周期按 16.7 ms 计，若给图留 3% 的预算，可用时间是 0.5 ms。

把节点成本代进去做两个典型对账：一条 20 个轻量节点构成的链路约 20 × 20 µs = 0.4 ms，占满 3% 预算的八成，属于"可用但不能再加"的状态；反过来，8 条各含 2 ms 重计算的每步链路合计 16 ms，吃掉步进预算的约 96%，RTF 会跌到 1 以下，仿真进度几乎停滞。两条对账给出图设计的上限规则：所有"每步执行"链路的总耗时控制在步进预算的 5% 以内，单条链路的节点数保持在几十个量级，重计算一律移出每步路径。

触发延迟同样有量化口径。OnPhysicsStep 上的链路与物理步同步，图内读到的是当步积分后的状态；从 Python 侧送入的数据（脉冲事件的一次性动作）会在下一次图求值时被消费，最坏滞后一个物理步，约 16.7 ms。对重置审计、监控落盘这类用途，这个量级足够；若要求事件时刻与物理时刻对齐到一步以内，应把事件时间戳作为数据一起送入，在图内记录时间，避免依赖消费时刻。对账实验的容差也说明一下：图在被创建的当步可能尚未激活，300 步实验里出现 299 与 300 的差别属于正常，判据要看更长的窗口：连续记录 10000 步，计数对物理步数的斜率严格为 1 才算通过。

触发源的对照数据可以进一步做成验收指标：以 10000 步为窗口，统计"每步平均触发次数"。参考值：OnPhysicsStep 的读数应严格为 1.0；OnPlaybackTick 在渲染关闭时取决于应用配置，可能是低于 1.0 的任意值甚至接近 0，这正是它不能承载物理逻辑的直接证据；OnImpulseEvent 的读数等于 Python 侧主动触发的次数，用来验证"该响应的都响应了、不该响应的没有多余触发"。三项读数写进图模块的验收清单，任何改动触发配置的提交都要重跑一遍。

再看一个中级失效场景：同一段逻辑既挂了 OnPhysicsStep 又挂了 OnPlaybackTick（本意是"物理时算一次、渲染时再记一笔"），在渲染开启时读数约为 2 倍物理步数，关闭渲染后掉回 1 倍附近。对账计数会立刻暴露这个 2 倍关系，排查方向也明确：检查是否存在双触发源。结论仍是那句话：图的正确性先由计数证明，再由业务逻辑使用；先计数、后逻辑的两段式开发，在 OmniGraph 这种异步调度环境里省下的调试时间远超多写几行记录的开销。

实现思路与设计

构建一个最小事件驱动图（例：每物理步记录一次仿真时间与关节速度）：

  1. 定义目标与触发时机（每物理步 → 选 OnPhysicsStep；若要降为周期性触发，加一个"计数器取模"节点）。
  2. 列出节点清单（触发节点 → 读时间节点 → 计算/记录节点 → 输出节点）。
  3. 建图（用 Graph 编辑器手动连，或用 og.Controller.edit 代码建；真的扩产建议代码化，图能进版本管理）。
  4. 配置执行规则（逻辑链路上的节点设为每步执行，其余按需）。
  5. 调试（打开 Graph 编辑器看连线与错误；用打印/写变量节点先验证触发频率，再接业务逻辑）。
  6. 与 Python 交界的检查（图读写的数据要能被子/主循环观察到，明确"谁在何时读"）。
设计思维：为什么"先验证触发频率"是无价的调试习惯？

图的问题十有八九出在执行时机上：没触发、触发两次、在错误的阶段触发。先让图做一件唯一可见的事（比如每步给一个计数器加一并打印），确认频率与阶段，再往里加逻辑，这能把"神秘的不工作"压缩成"确定的数值问题"。这个习惯对后面调试相机管线与 ROS 桥同样适用。

三种建图方式的对比

方式优点缺点适用
Graph 编辑器手动连所见即所得，适合探索与调试难版本化、易误连、参数分散原型验证、一次性实验
og.Controller 代码建图可参数化、能进版本管理、可重建需要熟悉键值结构与节点名训练管线、需要复现的工程
直接编辑 USD 场景文件完全可控、可批量替换可读性差、易破坏文件结构批量资产处理、脚本化迁移

选择倾向：教学与排错用编辑器，工程化落点用代码建图。两条路产生的是同一份场景数据，可以先在编辑器里连出正确结构，再把结构翻译成 og.Controller.edit 的字典；翻译过程本身就是一次端口类型与参数值的核对。

关键代码与解读

片段 1：用代码构建最小 Action Graph（OmniGraph API 随版本有差异，以官方文档为准）

import omni.graph.core as og  # OmniGraph 的 Python 接口（路径随版本变化）

GRAPH_PATH = "/World/Graphs/StepLogger"   # 图在场景树中的位置：随场景保存，可复现

og.Controller.edit(
    {"graph_path": GRAPH_PATH, "evaluator_name": "execution"},
    {
        og.Controller.Keys.CREATE_NODES: [
            ("step_trigger", "omni.graph.action.OnPhysicsStep"),  # 触发源：每物理步发出信号
            ("log_step", "omni.graph.scriptnode.ScriptNode"),     # Python 脚本节点：执行自定义逻辑
        ],
        og.Controller.Keys.CONNECT: [
            ("step_trigger.outputs:step", "log_step.inputs:execIn"),  # 把触发信号连到脚本节点
        ],
        og.Controller.Keys.SET_VALUES: [
            # 内嵌脚本：每物理步把一次计数写进节点自身的内部状态
            ("log_step.inputs:script", """
count = db.inputs.count + 1
db.internal_state["step_count"] = count
"""),
            ("log_step.inputs:count", 0),   # 初始计数
        ],
    },
)
# 图构建完成后立即生效：触发信号由执行器调度，无需在 Python 里每步调用它

解读：这段代码把 1–3 节的理论落成了实处。CREATE_NODES 相当于从"节点库"里取出两个积木；CONNECT 把触发节点的 step 输出接到脚本节点的执行输入端，注意连的是执行信号（与数值端口区分开），这是触发型图的关键：节点被"敲一下"才执行，数据到来本身不会触发它。SET_VALUES 里内嵌的脚本做了一件最小的事：计数。og.Controller.Keys 的键值字典风格是标准建图方式；用代码建图的价值在于：图能进版本管理、能参数化、能在 CI 里重建，换链路只需改字典。

片段 2：读出图内状态，与 Python 循环对账

import numpy as np

def read_graph_counter(graph_path):
    """从图里读回计数：验证触发频率是否等于物理步数。"""
    node = og.Controller.node(f"{graph_path}/log_step")     # 按路径取到节点对象
    attr = og.Controller.attribute("internal_state:step_count", node)  # 读内部状态属性
    return og.Controller.get(attr)                          # 取出 Python 数值

# 对账实验：从 Python 侧步进 300 步，比较两次读数之差
before = read_graph_counter(GRAPH_PATH)
for i in range(300):
    world.step(render=False)          # render=False 时 PlaybackTick 可能不推进，正好检验触发源
after = read_graph_counter(GRAPH_PATH)
print(f"图内计数增加 {after - before} 次，期望 300（每物理步一次）")
# 若明显小于 300：触发源被节流或图未激活；若大于 300：存在重复触发

解读：这段"对账"是 4 节思想的实操：图与 Python 是两个时间线，必须用可计数的观测来验证它们的关系。render=False 的步进是这个实验的精髓，它在物理上推进了 300 步，但可能不触发 Playback 相关的事件；如果你的图误用了 OnPlaybackTick，这个差值会暴露问题。把"图内计数与物理步数一致"作为验收条件写进文档，任何后来改动触发源的人都能被这个断言拦住。读取路径 .../log_step 与属性名 internal_state:step_count 的写法随版本有差异，但"先取节点、再取属性、最后取值"三段式是稳定结构。

常见坑

  • 触发源选错：用 OnPlaybackTick 做物理相关计数，训练时 render=False 导致频率对不上。修复：物理量一律 OnPhysicsStep，并用片段 2 的对账实验验收。
  • 图静默失败：节点报错不打进 Python 控制台，现象是"什么都没发生"。修复：先在 Graph 编辑器里打开图看错误标记与控制台输出，再回看代码建图的路径与键值。
  • 重复执行：触发信号连了多条路径或有多个触发源，逻辑执行两次。修复：对账计数（期望值 vs 实际值）能立刻暴露；图结构尽量保持单主线。
  • 端口类型不匹配：整数端口接到浮点端口、token 接到字符串，构建时就报错或静默转换出错误值。修复：确认端口类型，必要时显式加转换节点。
  • 在图里做重运算：把状态估计、碰撞查询这类大计算放进每物理步的脚本节点，仿真速率骤降。修复：把它留在 Python 侧按需调用；图只做轻量搬运与记录。

练习与思考

  1. 用代码构建一个"每物理步计数"的图，并用片段 2 的对账实验验证它的频率与 world.step() 一致。★
    提示
    先确认图计数器随步进精确增长；再故意换成 OnPlaybackTick 重跑，观察 render=False 下的差异。
  2. 做一个"每 60 个物理步执行一次"的图：在 OnPhysicsStep 后接取模/计数器节点，验证约每仿真 1 秒触发。★★
    提示
    计数取模 60 等于 0 时触发后续链路；用打印节点确认平均间隔。
  3. 设计一个监控图：在内部状态里维持"最近 100 步的关节速度均方值"，并让 Python 侧每个回合读一次。★★
    提示
    图内做滑动窗口需要数组或累加器，权衡执行规则里的"每步执行；也可以只累加与总数、Python 侧做除法。
  4. 对比实验：同一段逻辑分别用 OnPlaybackTick 与 OnPhysicsStep 触发，在渲染开/关两种模式下各跑 300 步，记录两种触发的次数并解释差异。★★★
    提示
    渲染关闭时 PlaybackTick 的推进方式会变化（取决于应用配置），这正是"物理逻辑不能挂在渲染触发上"的直接证据。
  5. 判断论证：列举 3 个"必须留在 Python"与 3 个"适合放进图"的逻辑，并为每个给出理由（时序确定性、执行频率、依赖关系）。★★
    提示
    从 4 节的边界表出发：影响学习信号的留 Python；数据搬运、生命周期、事件响应进图。

小结

  • OmniGraph = 节点 + 端口连线 + 触发源：声明式地描述"何时、对什么数据、做什么计算"，逻辑随场景保存并挂在应用更新循环上。
  • 触发源决定时序：物理相关用 OnPhysicsStep、显示相关用 OnPlaybackTick、一次性动作用事件；用"计数对账"验证触发频率。
  • 执行规则（每帧/按需/变化时）决定性能；图里放重计算是仿真吞吐的隐形杀手。
  • RL 的主体循环仍然留给 Python；图承担数据管线、生命周期与事件响应，两者用可观测的接口交互。
  • 图的求值策略（持续执行与按需推送）决定稳态开销：与物理同步的链路用执行流，纯数据转换链路用按需。
