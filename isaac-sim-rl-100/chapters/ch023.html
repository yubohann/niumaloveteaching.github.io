第 023 章：使用RL-Games训练机器人

换成 NVIDIA 官方高吞吐训练库：一份 YAML 描述网络与 PPO 全部超参，训练脚本一行命令拉起，机器人策略从配置到收敛全程可复现。

  • 主题：训练框架 / 配置驱动训练
  • 相关组件：RL-Games、Isaac Sim、OmniIsaacGymEnvs（作为宿主）
  • 预计学时：50 分钟
  • 前置章节：第 022 章

学习目标

  • 定位 RL-Games 在 Isaac 生态中的角色：它是训练器（trainer），环境由宿主项目提供，理解"训练器与环境的接口契约"。
  • 读懂一份 RL-Games 训练配置：horizon、minibatch、mini-epochs、clip、学习率等参数之间的关系与推荐量级。
  • 掌握观测归一化、价值归一化这类"隐式预处理"为什么内建在 RL-Games 里，以及它们对机器人任务的影响。
  • 会把第 022 章的批量环境接到 RL-Games 的接口上，并用一行命令启动训练与恢复（resume）。
  • 说清 RL-Games 与 Isaac Lab 内置的 rsl_rl 的差异，知道什么场景选哪个。

背景与动机

第 022 章解决了"环境怎么并行"，但学习器那一侧你还在手写 PPO。自己写的 PPO 通常卡在两件事上：超参没调对、训练不可复现。RL-Games 是 NVIDIA 机器人团队维护的高吞吐强化学习库，最初为 Isaac Gym 生态打造，如今仍作为 OmniIsaacGymEnvs 的默认训练后端。它的三个特点正好对上机器人训练的痛点：

  • 配置驱动：网络结构、PPO 超参、训练轮数全部写在 YAML 里，实验即文件，换参数不用改代码，天然可复现、可对比。
  • 吞吐优先：所有数据通路按张量批处理设计，与第 022 章的 (N, dim) 观测天然匹配，4096 环境 × 16 步的采样在秒级完成。
  • 内建实用技巧：观测归一化、优势归一化、KL 自适应学习率、值函数裁剪都是默认项，这些恰是机器人任务里最容易踩坑的部分。

本章不深挖 PPO 数学（第 017–020 章已铺垫），重点是学会用这套工具、读懂它的配置文件、理解每个默认值背后的理由。这些配置思想在后续所有训练章节里反复出现。

核心原理

1. 训练器与环境的契约：谁负责什么

RL-Games 的架构可以概括为一句话：环境负责"物理与数据"，训练器负责"学习与调度"。环境要向训练器暴露的最小接口包括：观测与动作的维度声明、step（批量）、reset（批量）、以及训练/评估模式切换（训练时随机化，评估时固定）。

在 Isaac 生态里这个契约具体表现为：OmniIsaacGymEnvs 里的 VecTask 子类实现这些方法，RL-Games 的 runner 按配置调用它们。所以"用 RL-Games 训练"实际是三件事：写一个满足契约的环境、写一份配置文件、把两者在启动脚本里接起来。理解这一点，换任何训练器（rsl_rl、skrl）时你只需要重新核对接口，算法本身不必重推。

2. 采样结构：horizon 与 minibatch 的几何关系

RL-Games 的 PPO 每轮收集的数据量是：

batch = num_envs × horizon_length 例：4096 环境 × 16 步 = 65536 条 transition；minibatch_size=16384 时恰好整除，每轮 4 个 minibatch

horizon 控制"一次采集多长再更新"，它同时决定优势估计（GAE）的时间视野。机器人控制任务里 horizon 常取 8–32：太小，时序差分信号传不远（值函数学不动）；太大，样本变"陈旧"，策略已经变了但数据还是旧策略采的，PPO 的重要性权重比值漂移，训练不稳。

为什么要把 batch 拆成 minibatch 并多次遍历（mini_epochs）？这是 PPO 的精髓：同一批数据可以安全地做几次梯度更新，更新次数的实际上限由策略偏离程度（KL 散度）决定，固定 epoch 数只是名义值。RL-Games 默认打开自适应 KL 学习率：KL 偏大就降学习率，偏小就升，把训练稳定性和速度同时压出来。

3. 内建归一化：为什么机器人任务离不开它

机器人观测是"量纲大杂烩"：关节角 ±3.14 rad、速度 ±5 rad/s、目标距离 ±1 m、接触力 0–50 N。直接喂给 MLP，梯度会被大数值维度主导。RL-Games 的解法是运行时归一化（running normalization）：对每个观测维度维护在线均值与方差，更新公式是

x̂ = (x − μ) / (σ + ε)， μ ← (1−α)μ + αx， σ² ← (1−α)σ² + α(x−μ)² α 为滑动系数；训练前 1 万步用数据把统计量"喂稳"，之后再评估策略

与离线归一化（先跑一批数据算好均值方差）相比，运行时归一化自动适应课程学习与域随机化带来的分布漂移，这正是机器人训练最需要的。但有一个副作用必须知道：归一化统计量随训练变化，策略的前端输入是非平稳的。所以评估时必须冻结统计量，否则同一个策略在不同时刻测出的成功率会漂移。

4. 与 rsl_rl 的关系：同源不同代

Isaac Lab 的默认训练后端是 rsl_rl（苏黎世联邦理工 Robotic Systems Lab 出品），思路与 RL-Games 一脉相承：PPO + 张量环境 + YAML 配置。差异主要在工程细节：rsl_rl 更强调按 rollout 分块存储、与 Isaac Lab 的 manager-based 环境耦合更紧；RL-Games 历史更长、配置项更多、在 OmniIsaacGymEnvs 里开箱即用。选型原则：新项目用 Isaac Lab + rsl_rl；维护旧 Isaac Gym 风格工程或需要复用社区配置时用 RL-Games。两者的调参直觉完全互通。

5. 完整算例：一轮 PPO 更新的时间账

把 022 章的单步预算与本章的更新结构拼起来算一轮完整更新。采样量 = 4096 × 16 = 65536 条 transition。时间分三段：

阶段计算耗时（ms）
采样16 个控制步 × 20.5 ms/步328
梯度更新（上限）4 个 minibatch × 5 个 mini-epoch，单次前向+反传约 6 ms120
评估与日志（摊销）定期评估、TensorBoard、checkpoint 轮转30
合计65536 条 / 478 ms478

折算吞吐约 13.7 万条/秒，这是乐观上限；评估回合与渲染一旦计入，实测常落到 5–10 万条/秒区间。另有两点结构信息。第一，采样占 69% 的时间，更新的 20 次梯度步只占 25%，所以"提高吞吐"的主战场仍在环境侧（022 章的结论在这里得到延续）；把 mini_epochs 从 5 降到 3 省下的是小头，且可能降低样本效率。第二，按这个吞吐，1 亿条 transition 的墙钟时间在 12–33 分钟量级（5 万条/秒对应 33 分钟），与第 022 章的端到端口径互相印证：训练时长的数量级由吞吐决定，而吞吐要按含更新的口径报告。

6. 网络容量的参数量核算

观测 24 维、动作 7 维时，三种常用 MLP 的参数量（actor 与 critic 共享主干，各自外接头层）：

units主干参数总参数（含两个头）fp32 大小
[256, 128]39 29640 3280.16 MB
[512, 256, 128]177 024178 0560.71 MB
[1024, 512, 256]681 728683 7842.74 MB

读数：即使最大的配置 68 万参数，fp32 也只有 2.74 MB，加上梯度与 Adam 两个动量约 11 MB，显存上完全不是约束。网络宽度影响的是每步推理与反传的时间（进 5 节的时间账），不是显存。容量选择因此只按任务复杂度来：24 维观测、7 维动作的姿态控制任务，[512, 256, 128] 已远超需求；回报学不动时先查奖励与 horizon，再怀疑容量。另一个结构细节：[512, 256, 128] 的主干里，512×256 的中间层占 131 328 个参数、约 74%，加宽网络的代价主要砸在中间层，极端窄-宽-窄的层型并不划算。

三者的核心超参直觉互通：clip 0.2、gamma 0.99、lambda 0.95 可以照抄。真正的差异在"隐形工程"：归一化统计量的生命周期、恢复的完整性、评估模式的切换。手写 PPO 能跑通训练循环之后，这些才是把实验做扎实的部分，也正是本章把框架用起来的理由。

8. 失效模式：KL 自适应与归一化的边界

  • KL 自适应的上下探振荡：典型序列是 lr 3e-4 时 KL 冲到 0.035，超过阈值两倍（0.032），lr 降到 2e-4；随后 KL 回落到 0.006，低于阈值一半（0.008），lr 又升回 3e-4。若 lr 在两点间反复横跳，KL 曲线呈锯齿、回报平台化。修复：把 kl_threshold 适当收紧，或给 lr 设上下限截断振荡。
  • 归一化统计量的非平稳性：训练前一万步里统计量自身在漂移，策略前端输入分布随之变化，等价于"目标函数在动"。这是正常代价，换来的收益是自动适应课程学习与域随机化；边界在于评估：冻结统计量后同一策略可复测，但如果任务分布随后改变，旧统计量会让成绩缓慢劣化，需要重新校准。
  • minibatch 尺寸的两端：minibatch 太小（如 4096 以下）时内核启动与同步开销占比升高，GPU 利用率掉；大于 batch 时逻辑上无意义。合理区间是 batch 的 1/8 到 1/2。
  • 稀疏奖励下的优势归一化：优势除以 batch 标准差会同时放大信号与噪声；奖励稀疏时分子近乎全零、分母很小，归一化输出几乎全是噪声。修复：先在奖励侧缩放（抬升 5 cm 给 1.0 这类 O(1) 设计），再进归一化。

实现思路与设计

接入 RL-Games 的完整链路是"选宿主 → 注册环境 → 写配置 → 启动训练 → 恢复与评估"。逐段说明：

  1. 选宿主项目：优先在 OmniIsaacGymEnvs 框架内加任务（下一章会展开它），因为注册表、启动脚本、日志目录都已建好。若要独立工程，则自行初始化环境并调用 RL-Games 的 runner。
  2. 环境满足契约：声明 num_envs、obs_dim、act_dim；step 返回的四个量都是 batch 维打头的张量；提供 set_train()/set_eval() 切换随机化。
  3. 写训练配置：网络（MLP 层数与宽度）、PPO（horizon、minibatch、mini_epochs、clip、lr）、归一化开关、奖励尺度缩放。
  4. 启动：训练脚本读取 YAML，构造环境与 runner，主循环采样-更新交替；日志与 checkpoint 落盘。
  5. 恢复与评估：checkpoint 里保存网络、优化器、归一化统计量三者；评估时载入全部三样，冻结随机化。
参数推荐起点理由
horizon_length16短期任务 8 够用；涉及长时序（开门）可加到 32
minibatch_sizebatch / 44 个 minibatch 是吞吐与稳定性的常见平衡点
mini_epochs5配合自适应 KL，属于"上限"，实际由 KL 提前终止
learning_rate3e-4 → 1e-3（自适应）4096 环境大 batch 下 3e-4 偏保守，KL 自适应会自动上探
clip0.2PPO 标准值；机器人任务不建议比 0.1 更小
gamma / lambda0.99 / 0.95控制周期 60 Hz 时有效视野约 1.7 s，适合操作任务
设计思维：奖励尺度也要"归一化"

RL-Games 配置里通常有一个 reward_shaping 或奖励缩放项。原因：PPO 对奖励的绝对尺度不像 Q-learning 那样敏感，但优势归一化是按 batch 统计的，如果大部分步奖励≈0（稀疏任务），归一化会把少量非零奖励放大成噪声。常见做法是把每步奖励缩放至 O(1) 量级（如抬升 5 cm 奖励 1.0、每步时间惩罚 0.01），让信号密度与数值尺度同时可控。

关键代码与解读

片段 1：一份可用的训练 YAML（节选自典型配置）

params:
  config:                       # 全局训练参数：采样结构与优化器都在这里
    name: franka_reach_ppo       # 实验名，决定日志与 checkpoint 目录
    env_name: rlgpu              # 宿主环境的注册名（OmniIsaacGymEnvs 约定）
    horizon_length: 16           # 每次采集 16 个控制步再更新：兼顾视野与新鲜度
    minibatch_size: 16384        # 4096 环境 × 16 步 / 4，恰好整除便于 GPU 满负荷
    mini_epochs: 5               # 同一批数据最多回炉 5 次，KL 过大时提前停
    learning_rate: 3e-4          # 起始学习率；KL 自适应会在此基础上浮动
    clip: 0.2                    # PPO 概率比裁剪，抑制单次更新的策略漂移
    gamma: 0.99                  # 折扣因子：60 Hz 下有效视野约 1.7 秒
    lam: 0.95                    # GAE 平滑系数，控制偏差-方差折中
    kl_threshold: 0.016          # KL 超过它就降 lr：这是"稳"的关键闸门
    normalize_input: True        # 观测在线归一化：机器人多量纲观测的刚需
    normalize_value: True        # 价值在线归一化：回报尺度未知时防止值网络震荡
    bounds_loss_coef: 0.001      # 轻推关节靠近限位中位的正则，避免贴边抖动
  network:                       # 网络结构：actor 与 critic 默认共享主干
    name: actor_critic
    separate: False              # True 则 actor/critic 各一套 MLP（显存换个性化）
    units: [512, 256, 128]       # 三层 MLP：机器人任务足够，过深反而难训
    activation: elu              # ELU 负区间光滑，比 ReLU 更适合连续控制

解读：先看几何关系，minibatch_size 取 16384，是因为 batch=65536 要能被整除；改 N 或 horizon 时这里必须同步改，否则会浪费尾部数据。再看两个归一化开关：normalize_input 处理观测量纲，normalize_value 处理回报尺度，机器人任务里建议都开；关闭它们只在你已有明确外部预处理时才有意义。最后看 kl_threshold：它是自适应学习率的判据，每个 mini-epoch 后统计新旧策略的 KL，超过 0.016 降 lr、低于一半升 lr。这个 0.016 不是魔法数字，它来自实践：超过 0.02 时策略行为变化过大，PPO 理论上的"保守更新"假设就失效了。注意关掉 schedule 里的固定学习率衰减、改用 KL 自适应，是 RL-Games 相比手写 PPO 最省心的部分之一。

片段 2：环境侧接口，提供训练器需要的一切

class FrankaReachTask(VecTask):          # 宿主基类：自带 num_envs、设备、张量工具
    def __init__(self, cfg):
        super().__init__(cfg, ...)       # 版本差异：4.x 前是 cfg 字典，之后为任务配置对象
        self._num_envs = cfg["env"]["numEnvs"]        # 4096：与训练 YAML 的 N 保持一致
        self._obs_dim = 3 + 7 + 7 * 2                 # 目标(3) + 关节(7) + 关节速度(7)+夹爪(7)
        self._act_dim = 7                             # 7 自由度位置增量：连续动作
        # 训练器约定：观测与动作空间必须是 batch 维打头的张量
        self.obs_space = gym.spaces.Box(low=-np.inf, high=np.inf,
                                        shape=(self._num_envs, self._obs_dim))
        self.act_space = gym.spaces.Box(low=-1.0, high=1.0,
                                        shape=(self._num_envs, self._act_dim))

    def set_train(self):
        self.randomize = True            # 训练模式打开域随机化：物体位置、质量、摩擦
    def set_eval(self):
        self.randomize = False           # 评估模式冻结随机化与观测噪声，成绩才可比

    def step(self, actions):
        self._apply_actions(actions * self.action_scale)   # 训练器输出 [-1,1]，这里放大到关节增量
        for _ in range(self.decimation):
            self._world.step(render=False)
        obs = self._build_obs()                            # (N, obs_dim)
        rew = self._reward()                               # (N,)
        done = self._fail_and_timeout()                    # (N,)
        info = {"successes": self._check_success()}        # 评估指标随 step 返回
        return obs, rew, done, info

解读：这段代码的每个字段都在回答训练器的一个需求。为什么动作空间写 [-1,1]、不用真实关节量纲？因为策略网络输出经 tanh 落在 [-1,1]，环境侧再做 actions × action_scale 的仿射映射，把量纲转换集中在环境里；这样策略无需学习"动作的绝对刻度"，缩放超参也可以在 YAML 里被 sweep。为什么 set_train/set_eval 单独成对？域随机化、观测噪声、动作延迟如果评估时还开着，两次测得的成功率没有可比性；训练器会在切换阶段自动调用它们。为什么 info 里带 successes？RL-Games 的日志系统会把它聚合成成功率曲线，这是比回报更可靠的进度指标，尤其奖励被塑形过时。

片段 3：启动、恢复与评估入口

# 训练：脚本内部会读 YAML、构造环境、把 runner 跑起来
# python train.py --task FrankaReach --num_envs 4096 --config franka_reach_ppo.yaml
from rl_games.torch_runner import Runner

def launch(config_path: str, checkpoint: str = None):
    runner = Runner()                        # 训练器实例：什么都不做，直到喂它配置
    runner.load(config_path)                 # 解析 YAML：网络/PPO/归一化全部就位
    runner.reset()                           # 构造网络与优化器；此刻才会分配显存
    if checkpoint:                           # 断点恢复：三样东西都要从盘上回来
        runner.restore(checkpoint)           # 网络权重 + 优化器状态 + 归一化统计量
        # 少恢复归一化统计量，相当于把观测分布"重置"，初期回报会明显跳水
    runner.run({                             # 采样本、更新、定期评估与存档的主循环
        "train": True,                       # False 则只评估：加载策略跑固定回合数
        "play": False,
        "checkpoint": "runs/franka_reach_ppo",   # 日志与权重的落盘目录
    })

解读：注意 load → reset → restore → run 这个顺序，它与常见框架的"构造即分配"不同：RL-Games 把"读配置"和"建模型"显式分开，好处是同一份配置可以在 CPU 上先做校验、再决定设备与精度。恢复训练时特别强调第三样东西，归一化统计量。它在 checkpoint 里与网络权重同存，如果只载入权重忽略统计量，策略面对的是一个"没校准的输入标尺"，表现为恢复后成功率骤降再缓慢回升。这种问题在日志上像个"训练不稳定"，实战里 90% 的偶发性恢复退化都出在这里。最后一行的目录建议用任务名 + 时间戳，RL-Games 默认在其下建 nn/ 与 summaries/ 子目录，便于多组实验对比。

常见坑

  • batch 不整除：改了 num_envs 或 horizon_length 却忘了同步 minibatch_size，训练器会对尾部数据做 padding，浪费 10–30% 的样本。症状：吞吐低于理论值、不同实验之间方差变大。修复：三者保持整倍关系。
  • 恢复训练只加载权重：忘记恢复观测归一化与优化器状态，回报曲线在恢复点跳水。修复：用 runner 的 restore 一条龙恢复，别手工 load_state_dict 只拿网络。
  • 评估时忘记冻结随机化：set_eval() 没生效或评估脚本自建环境时没调它，两次评估成功率差 20 个点很常见。修复：评估统一走"载入 checkpoint + 固定种子"。
  • 观测归一化在早期影响探索：前几千步统计量不准，归一化后的观测"忽大忽小"，早期回报噪声大。症状：训练开头 2000 步奖励剧烈抖动后转好。修复：属于正常现象，别急着回滚；可以预热几千步再开梯度更新。
  • 版本路径差异：Isaac Sim 4.x/5.x 里工具链目录与包路径与 2022.x 不同（如 omni.isaac.* 大量迁移到 isaacsim.*），RL-Games 独立安装与随宿主打包的版本 API 也略有出入。症状：import rl_games 失败或 runner 参数不匹配。修复：跟着宿主版本提供的示例配置走，不要混用旧教程的导入路径。
  • 两处 num_envs 不一致：环境配置里的 numEnvs 与训练 YAML 的并行度各写一份，改了其中一处就报 shape 不匹配或静默错位。症状：启动即报维度错误，或日志里步数对不上。修复：以启动脚本注入为单一来源，或启动时显式校验两个值相等。
  • 稀疏奖励直接开优势归一化：不做奖励缩放就上 normalize_value，优势被"零除以零"式的统计放大成噪声，表现为回报方差大而成功率不动。修复：先把每步奖励设计到 O(1) 量级，再启用归一化；用成功率和回报两条曲线是否同向作为体检。

练习与思考

  1. 把 minibatch_size 从 16384 改成 12000（不再整除 65536），训练 200 个 update，观察吞吐与回报曲线的变化，解释你看到的差异。★
    提示
    关注每秒步数日志与每个 epoch 实际用到的样本数；Padding 或丢弃都会让"同样的墙钟时间"训得更少。
  2. 关闭 normalize_input 训练同一个任务，对比收敛步数。预测哪些观测维度会主导梯度。★★
    提示
    看看你的观测各维度量纲：关节速度 ±5、接触力 0–50，与归一化后的差距。关闭后通常需要显著调低 lr 才能稳住。
  3. 设计一个实验验证"恢复归一化统计量"的重要性：保存 checkpoint 后，手工只恢复网络权重 vs 完整恢复，对比恢复后前 100 个 update 的平均回报。★★
    提示
    两次实验用同一个 checkpoint 与同一随机种子，差异只能归因于统计量；差异的恢复时间也值得记录。
  4. 把 horizon_length 从 16 加到 64，分析两件事：每 update 样本量翻四倍后 lr 该如何调整（线性缩放假设）；以及"陈旧数据"效应对开门这类长时序任务是否反而有利，用实验说话。★★★
    提示
    大 batch 常配合更大 lr（或用 KL 自适应自动接管）；陈旧数据的利弊要看任务信用分配距离，结论以成功率作准，回报曲线只作参考。
  5. 比较题：为你的任务写一份 rsl_rl 风格的配置（rollout 长度、num_mini_batches、learning_epochs），与本章 RL-Games 配置逐项对应。哪些概念一一对应，哪些是各自独有的？★★★
    提示
    horizon↔rollout、minibatch↔num_mini_batches、mini_epochs↔learning_epochs；RL-Games 独有的观测/价值归一化在 rsl_rl 里通常要自己写，反之 rsl_rl 的对称 actor-critic 更常出现在其默认配置中。
  6. 按 5 节的时间账复算：若把 horizon 从 16 改到 32，采样与更新各占多少毫秒（更新按 8 个 minibatch × 5 epoch 估）、每轮样本量与吞吐如何变化？★★
    提示
    采样 32×20.5 = 656 ms；更新上限 40×6 = 240 ms；加 30 ms 摊销后每轮约 926 ms、131072 条，吞吐约 14.2 万条/s，与 horizon=16 的 13.7 万接近，说明吞吐对 horizon 不敏感而视野翻倍。
  7. 用 6 节的方法手算 [256, 256, 256] 主干在 obs=48、act=12 时的参数量，并与 [512, 256, 128] 对比，说明"加宽"与"加深"哪个涨参数更快。★★★
    提示
    逐层 w×h+h 相加；比较相邻层宽度变化对参数总量的贡献，每加宽一层会让前后两层同时变大，而层数增加只叠加中间层。

小结

  • RL-Games 是"训练器"，只管学习和调度；环境负责物理与数据，二者用张量契约对接（batch 维打头、set_train/set_eval、step 返回四元组）。
  • 采样几何：batch = num_envs × horizon，minibatch 必须整除 batch；horizon 同时决定 GAE 的视野上限。
  • 观测/价值归一化是机器人训练的刚需，且 checkpoint 恢复时要连统计量一起恢复。
  • KL 自适应学习率让 mini_epochs 只作上限（KL 达标即提前停），配置文件里常用量级：lr 3e-4、clip 0.2、gamma 0.99、lambda 0.95、KL 阈值约 0.016。
  • 下一章把它们组装起来：用 OmniIsaacGymEnvs 把任务注册进框架，一行命令完成"环境 + 训练器"的联合启动。
