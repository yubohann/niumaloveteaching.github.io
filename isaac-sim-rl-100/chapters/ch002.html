第一篇 · 仿真环境与训练框架

第 002 章：加载机器人模型

把一台真正的机器人搬进仿真场景：看懂 USD 资产的引用机制，加载 Franka 机械臂，读懂它的关节树与自由度，并为后面所有控制章节建立"名字到索引"的索引表。

  • 主题：仿真环境 / 机器人资产与关节体（Articulation）
  • 相关组件：Isaac Sim（USD、PhysX Articulation）
  • 预计学时：45 分钟
  • 前置章节：第 001 章

学习目标

  • 理解 USD 资产的引用机制（reference / composition）：加载机器人采用"引用一棵子树"的方式，文件内容不复制。
  • 说清 Articulation（关节体）是什么：它和"一堆由约束连接的刚体"在物理求解上的本质区别。
  • 掌握加载机器人的标准三步：add_reference_to_stage → Robot 封装加入场景 → world.reset()。
  • 会读取自由度数、关节名列表，并建立"关节名 → DOF 索引"的映射，这是后续每章控制的通用地基。
  • 理解固定基座与浮动基座机器人在自由度与位姿接口上的差别。

背景与动机

第 001 章的世界里只有一个立方体。要做机器人强化学习，场景里必须站着一台真实的机器人：带正确的连杆质量与惯量、真实的关节限位、可渲染的视觉网格。Isaac Sim 自带的机器人资产（Franka、UR、四足、移动底盘）都以 USD 格式发布，加载动作看起来只有两行代码，但背后涉及两个关键概念：USD 的组合机制和 PhysX 的 articulation 求解。不理解它们，后面就会反复踩"关节顺序对不上""机器人软趴趴""改姿态不生效"这类坑。

本章的产出是后续所有章节的操作对象：一个已加载、已复位、关节索引已建表的机器人。

核心原理

1. 加载 = 引用，不是复制

USD（Universal Scene Description）把场景描述成一棵 prim（图元）树，每个 prim 有一个路径，例如 /World/Franka/panda_link0。add_reference_to_stage() 做的事是：在场景图的目标路径下挂一条"组合弧（composition arc）"，指向磁盘上的资产文件。资产内容不复制、不展开成新的图元，stage 里只是多了一个指针，打开场景时由 USD 的组合引擎把两边数据合并成最终结果。

为什么这很重要？同一份 Franka 资产可以被引用进成百上千个场景而只占一份定义；修改资产文件，所有引用处同步更新。后面做并行训练时，数千个机器人视觉上各不相同（不同位姿），但共享同一份几何与物理定义，显存与加载开销因此可控。

2. Articulation：机器人不是"一堆刚体"

朴素做法是把每个连杆当独立刚体、用关节约束把它们连起来。通用物理引擎里约束是"软"的：求解器迭代地消除违反量，受力大时关节会被拉开（数值上表现为"散架""拉长"）。

PhysX 对机器人给出了专门的表示：Articulation（关节体）。它把整棵关节树当作一个整体，用关节空间的广义坐标 q 描述状态：

q = [q1, q2, …, qn]，n = nDOF n_DOF 是自由度总数：机械臂只有一个等于关节数的 DOF 向量；浮动基座机器人要额外加 6 个（3 平动 + 3 转动）

求解器直接对 q 积分，连杆之间的连接由树结构"自动消去"，不存在约束被拉开的可能。收益有两层：连接精确（关节永远不会分离）与效率高（只对 n 个自由度求解，省去对每个刚体的 6 自由度分别积分再配约束的流程）。代价是：机器人的状态与命令必须走 articulation 的接口，你不能随意对某个连杆"凭空施加速度"。

由此得到两类机器人的差别：

类型n_DOF典型代表位姿接口
固定基座（fixed base）= 关节数（Franka 手臂 7，含夹爪 9）Franka、UR10基座位姿由场景摆放；一般不需要读 base pose
浮动基座（floating base）= 6 + 关节数四足、人形、无人机base 位姿是状态的一部分，get_world_pose() 返回躯干位姿

3. 关节链条与索引

机械臂的末端位姿由运动学链条连乘得到，这是后面所有操作任务的基础：

Tee(q) = Tbase · T1(q1) · T2(q2) · … · T7(q7) · Ttool 每个 T_i 是绕关节轴的刚体变换；q_i 就是 DOF 向量里的第 i 个分量

关键工程事实：DOF 的排列顺序由资产文件决定，不同机器人、甚至同一机器人的不同版本都可能不同。因此代码里从不硬编码"第 2 号关节是肘部"，正确做法是先读 dof_names，再按名字查索引。这个模式后面配置驱动器（003）、施加控制（004–006）、设计奖励（019）时都会复用。

此外，关节的限位、默认姿态、驱动参数都编码在资产里：Franka 关节 1 的限位约 ±2.8973 rad。加载后直接查询，比从说明书抄更可靠。

4. 组合弧与多实例：共享定义的量化意义

引用在 USD 里的落点是一条组合弧（composition arc）：目标 prim 的最终属性由"本地编辑层 + 被引用层"按强度顺序合成。合成规则带来两个工程习惯：本地修改（把机器人挪到不同位置、改驱动参数）只存在于当前场景层，不会污染资产文件；资产文件升级（替换一版网格）所有引用处自动获得更新。

把共享的意义量化。设一台机器人的网格与碰撞数据合计 M MB，训练场景有 N 个实例，每实例的位姿与状态附加数据约 S：

C复制 ≈ N · M   C引用 ≈ M + N · S 示意量级：M = 20 MB、S = 20 KB、N = 4096 时，C_复制 ≈ 82 GB，C_引用 ≈ 100 MB，相差三个数量级

这就是并行训练场景必须使用引用机制的原因：显存、加载时间、资产修改成本三项同时受益。需要注意的是，引用省下的是"定义"的重复，每个实例的位姿、关节状态、接触缓存仍然独立，这部分开销随 N 线性增长。

5. 求解规模对比：articulation 与约束式建模

若把 Franka 的 9 个连杆按"刚体 + 约束"的通用方式建模：每个刚体有 6 个状态自由度，共 54 维；8 个关节约束还要以迭代方式逐轮消除违反量。articulation 的广义坐标只有 9 维，关节连接由树结构直接消去：

nrigid = 6 · nlinks = 6 × 9 = 54  对比  nDOF = 9 求解维度降到约 1/6；乘上 4096 个平行实例，这个差距直接体现在每帧物理耗时上

两类建模的差别还可以从误差角度理解：约束求解器的关节"软度"在受力大时表现为可测的拉开量，而 articulation 的约束误差在数值上被直接消去，只剩下积分误差。对奖励函数敏感的任务（例如抓取力必须精确），这个差别会改变策略学到的行为。

6. 关节限位：从资产查询取数

关节限位是策略动作空间设计的第一手约束。Franka 的量级：joint1 限位约 ±2.8973 rad（约 ±166°），joint4 约 −3.07 至 −0.07 rad（肘部无法完全伸直）。加载时读取限位数组，把它作为动作缩放与裁剪的参数。数值算例：若按 joint1 的 ±2.9 rad 统一设置关节 4 的输出区间，区间总宽 5.8 rad，而物理有效区间宽约 3.0 rad，交集只有 2.83 rad，约 51% 的输出区间落在限位之外，这些动作的实际效果等于撞在限位上不动。按每个关节的真实区间设置动作边界，可以让同样的策略输出覆盖更有效的运动范围。

7. 默认姿态的限位余量核对

导入资产的默认关节姿态（示例：[0, −0.785, 0, −2.356, 0, 1.571, 0.785]，以实际资产为准）是后续所有随机化与动作设计的基准点。把它与限位表逐关节相减，得到"离最近限位"的余量，这组数是初始状态设计的第一手依据：

关节默认角（rad）离最近限位余量折算角度随机扰动建议
joint2（大臂）−0.7850.978 rad约 56°±0.2 rad 以内
joint4（肘）−2.3560.716 rad约 41°±0.15 rad 以内
joint61.5711.589 rad约 91°±0.3 rad 以内
joint7（腕）0.7852.112 rad约 121°±0.4 rad 以内

为什么余量值得单独成表？因为 012 章的初始状态随机化以默认姿态为基准，004 章的相对动作表示也以它为原点。若某关节余量只有 0.1 rad 量级，±0.1 rad 的均匀扰动会有相当比例撞在限位上：观测里的归一化角度长期贴边、动作被裁剪，策略学到的分布随之偏斜。余量最小的 joint4 约为 0.716 rad，±0.1 rad 扰动占用约 14%（0.1 / 0.716），±0.3 rad 时占用约 42%，撞限位概率明显上升，这就是表中"扰动建议"一列的来源。

选择默认姿态的一条量化准则：把关节放在行程中点附近。joint4 的行程为 [−3.0718, −0.0698]，中点约 −1.571 rad，与默认值 −2.356 rad 相距 0.785 rad；若把默认姿态改到中点，两侧余量对称化，随机化的可用宽度在两侧分布更均匀。行程很宽的关节（joint2 两侧各约 1.76 rad）按余量最小的一侧设定扰动上限即可。

失效模式与修复：默认姿态离限位不足 0.05 rad 时，仿真一启动观测就贴边，动作裁剪比例高，训练早期成功率长期为零；修复方式是更换默认姿态（把关节挪到行程中点附近），或在随机化里对每个关节单独设置不对称的安全区间。这类问题靠观察关节角时间序列的 min/max 就能发现，不必等训练曲线报错。

把核对固化成加载流程的一部分，三条断言即可：关节向量长度等于 num_dofs；每个已知关节名都能在 dof_names 里找到；各关节的默认姿态余量最小值大于 0.1 rad。第一条拦住"7 维姿态写给 9 维资产"这类长度错误；第二条拦住资产版本变化导致的名字缺失；第三条拦住"默认姿态贴着限位"的隐性坏配置。三条都通过再打印余量表存进实验记录，后续换资产时把新表与旧表相减，异常立现。

再补一个索引错误的量化后果：若代码里用了 dof_index.get(name, -1) 而名字拼错，写入会落到最后一个关节上。对 9 自由度的 Franka，错写落在 finger2 上，表面现象是"腕部目标不动、夹爪莫名开合"，排查时很容易误判为控制器问题。索引一旦建立就用断言固化（assert name in dof_index），把静默错位变成启动即报错，这是跨资产代码最基本的防线。

实现思路与设计

加载一台机器人的完整顺序（每步的理由写在括号里）：

  1. 确认资产路径（在不同版本中资产根目录会变化，先在资产浏览器里把路径确认下来，别在网上抄一个写死）。
  2. add_reference_to_stage()（把资产子树引用到 /World/Robots/... 这样的路径下；引用点选择决定了以后传感器挂在哪）。
  3. 用 Robot 类封装并加入 scene（Robot 是 Articulation 的机器人专用子类，提供关节读写、基座位姿、夹爪等便利接口；只有加入 scene 才会在 reset() 时统一初始化）。
  4. world.reset()（此刻 PhysX 才真正建立 articulation 的物理视图；在它之前读关节状态会拿到空值或报错）。
  5. 打印校验（DOF 数是否与预期一致？关节名列表是否符合预期？这一步是"加载成功"的唯一可信证据）。
  6. 建立名字 → 索引映射（供后续所有控制代码查询）。
设计思维：Robot/Articulation 封装在 prim 之上补了什么？

直接拿 USD prim 你只能改属性、动变换，不知道"物理时间"与"物理状态"。Robot 封装在 prim 之上补齐了三件事：关节状态读写、基座位姿接口、reset 语义，这正是 RL 环境需要的全部机器人接口。记住这个分层习惯：USD 管描述，Robot 管状态与控制，奖励与观测在你自己的环境类里做。

参数取值示例选择理由

资产层面的三个开关，按任务目标逐项选择：

选择项取值理由
关节版本7 DOF（纯臂）/ 9 DOF（含夹爪）动作维度每减少一维，探索空间规模随之下降，到达类任务优先用 7 维

三个开关里，最先决定的是关节版本，因为它同时改变动作维度、观测维度与奖励设计；碰撞几何与实例化标志属于"不改任务语义、只改成本"的选项，可以最后再逐项测试。

关键代码与解读

片段 1：加载资产并登记为 Robot（API 路径随版本变化，以官方文档为准）

from isaacsim import SimulationApp  # 先起 Kit，再导入其余模块（第 001 章的铁律）
app = SimulationApp({"headless": True})  # 本片段只做校验，不开窗口更省资源

from isaacsim.core.api import World
from isaacsim.core.api.robots import Robot
from isaacsim.core.utils.stage import add_reference_to_stage  # 老版本在 omni.isaac.core.utils.stage

world = World(physics_dt=1.0 / 60.0, rendering_dt=1.0 / 60.0)

usd_path = "/Isaac/Robots/Franka/franka.usd"  # 版本间资产根目录有差异，先到资产浏览器确认
prim_path = "/World/Robots/Franka"  # 引用落点：整棵机器人子树都挂在这个路径下
add_reference_to_stage(usd_path=usd_path, prim_path=prim_path)
# 引用只登记、不复制：stage 里多了一个指向资产的指针，多个实例共享一份定义

robot = world.scene.add(Robot(prim_path=prim_path, name="franka"))
# Robot 封装了 articulation 的全部常用接口；加入 scene 后才会被 reset 统一初始化
world.reset()  # 真正建立 PhysX 侧视图的时刻：此前的关节查询都不可信

print("DOF 数:", robot.num_dofs)   # 预期 9（7 关节 + 2 手指）；版本间可能是方法调用 num_dofs()
print("关节名:", robot.dof_names)  # 建立索引表的原始数据，顺序由资产决定

解读：这段代码的三个关键行为。第一，引用落点选了 /World/Robots/Franka：多留一层 Robots 目录，后面加相机、桌子、目标物时各归各位，多机器人也不会命名冲突。第二，Robot 必须由 scene.add 登记：场景管理器在 world.reset() 时统一对所有登记对象做初始化，漏登记的表现是"物体看得见，但读状态报错"。第三，校验放在最后：加载后立刻打印 DOF 数，如果预期 9 却得到 7，说明加载的是不含夹爪的版本，早发现早换资产。

片段 2：建立关节名到索引的映射并读取状态

# 不同资产的 DOF 排列不同，绝不能把"第 0 号"当成某个具体关节写死
dof_index = {name: i for i, name in enumerate(robot.dof_names)}
print("夹爪手指索引:", dof_index.get("panda_finger_joint1", -1))  # -1 表示不存在，暴露资产问题

world.step(render=False)  # 先步进一帧：让物理状态被真实积分出来，再读才可靠

q = robot.get_joint_positions()    # 形状 (9,) 的数组，单位：弧度 / 米
qd = robot.get_joint_velocities()  # 速度也有专门的读取接口，奖励函数里常用来惩罚动作剧烈
for name in robot.dof_names:
    i = dof_index[name]            # 一切按名字查索引，不依赖排序
    print(f"{name:24s} q={q[i]:+.3f} rad  qd={qd[i]:+.3f}")  # 对齐打印，核对默认姿态

解读：这个"先建映射、再按名字取数"的模式看似啰嗦，却是跨资产代码可复用的唯一正确姿势。设想你把到达任务从 Franka 换到 UR10：两者关节数不同、顺序不同，但 dof_index["elbow_joint"] 这样的写法不需要改。world.step() 放在读取之前，是因为 reset() 之后状态还是"待积分"的初始值，先步进一帧再读，拿到的才是物理引擎实际认可的状态。

片段 3：设置基座位姿与关节初始姿态

# 机械臂工作位置：把整机挪到台面右前方，方便后续放置目标物
robot.set_world_pose(position=(0.3, 0.0, 0.0))  # 对固定基座机器人，部分版本需在 reset 前用 prim 变换设置
# 说明：固定基座 articulation 的 base 是"不可被物理解算移动的"，
# 想要机器人整体换位置，最稳的做法是设置 prim 的 xform 后重新 reset。

# 写初始关节姿态：这是"瞬移"，不是控制命令，所以只允许在 reset 阶段使用
arm_pose = [0.0, -0.785, 0.0, -2.356, 0.0, 1.571, 0.785]  # 常见的"手肘抬起"预备姿态
robot.set_joint_positions(arm_pose + [0.04, 0.04])  # 两指各留 4 cm 开口，长度必须等于 DOF 数
robot.set_joint_velocities([0.0] * 9)  # 速度必须一起归零：只改位置不归零会残留动能，机器人会抖
world.step(render=False)
print("复位后的前三个关节:", robot.get_joint_positions()[:3])  # 验证写入生效

解读：这段代码集中体现 articulation 的"状态写入"语义。第一，关节状态写入是瞬移：直接改物理状态，不是施加控制，只该在重置逻辑里出现（第 011、012 章会把它系统化）。第二，写入长度必须与 DOF 数一致：含夹爪的 Franka 是 9 个 DOF，只写 7 个会报长度错误，遇到第一反应是检查资产版本。第三，位置和速度要成对设置：物理引擎的下一帧用当前速度继续积分，速度不清零，机器人会带着上一状态的速度"飞出去"，表现为难以解释的抖动。

常见坑

  • 资产路径写死：官方资产的根目录在版本间会调整，照抄旧教程路径会得到"文件不存在"或加载后场景里什么都没有。修复：在资产浏览器里确认实际路径，并写成脚本顶部的常量。
  • 忘记 world.reset() 就读取关节状态：PhysX 侧视图尚未建立，症状是报句柄为空、返回全零或异常值。修复：加载后立刻 reset 再读。
  • 把 DOF 顺序当固定契约：跨资产复制代码时把"第 2 个关节"当肘部，换机器人后控制错位。修复：永远用 dof_names 建映射，索引只在映射里查一次。
  • 仿真中途瞬移关节：在控制循环里直接 set_joint_positions()，会绕过驱动器、产生无穷大等效速度，表现为抖动、穿透甚至求解器发散。修复：运行期只发控制命令（004–006 章），状态写入仅限重置。
  • 角度与弧度混用：限位从 UI 面板抄来可能是角度值。记住 Franka 关节限位约 ±2.9 rad（≈166°），接口一律用弧度；打印时用 math.degrees() 换算成度确认。

练习与思考

  1. 再加载一台 UR10 或 Jetbot，对比 num_dofs 与 dof_names，说明自由度数量和命名方式的差异来源。★
    提示
    UR10 是 6 关节机械臂；Jetbot 是两轮差速底盘。想想哪些关节是转向、哪些是滚动，DOF 分别是多少。
  2. 写一个函数 joint_index(robot, name)：名字不存在时抛出带可用名字列表的异常。解释为什么跨资产代码需要这层保护。★★
    提示
    对比 dof_index.get(name, -1) 静默返回 -1 的后果：错误会推迟到给 q[-1] 写入时爆发，报错位置远离根因。
  3. 把初始关节姿态改为"肘部弯曲约 90°"，说明设置动作应该放在 world.reset() 之前还是之后，并解释为什么必须同时清零速度。★★
    提示
    在 reset 之前写入的值可能被 reset 覆盖；写入位置与速度是一组动作，参考片段 3 的顺序验证。
  4. 实验设计：把 prim 落点从 /World/Robots/Franka 改成 /World/Arm，先预测哪些代码需要同步修改，再实际验证。★★
    提示
    受影响的至少有：add_reference_to_stage 的参数、Robot 的 prim_path。思考如果程序里有多处硬编码路径，这种重构为什么会出错。
  5. 从数值稳定性和效率两个角度，解释 reduced-coordinate articulation 为什么比"刚体 + 约束"更适合机器人强化学习，并举一个能暴露差异的场景。★★★
    提示
    想象一台负载 5 kg 的机械臂高速摆动：约束求解器为满足软约束需要多轮迭代，而 articulation 直接把约束消去；再想并行上千台时开销差多少。

小结

  • 加载机器人 = 在 USD 场景图里引用一棵资产子树；不复制内容，多实例共享定义，这是并行训练的资产基础。
  • 机器人应以 Articulation 的形式交给 PhysX：用关节空间广义坐标求解，连接精确、效率高；代价是必须走 articulation 接口。
  • 加载三步缺一不可：add_reference_to_stage → Robot 加入 scene → world.reset()；之后立即打印 DOF 与关节名校验。
  • 永远按 dof_names 建"名字 → 索引"映射，不依赖 DOF 顺序；状态写入（瞬移）只允许在重置阶段，且位置与速度成对设置。
